# W-4 verification — JoinIntoStitcher paged-child guard (T211 r1 n2/3)

- Anchor: `src/nextorm.core/Builders/Joins/JoinIntoStitcher.cs:112-114` (`Stitch(..., allowPerParentTopN: true)`)
  returning before the per-parent loop in `EntityBuilderEagerLoading.ValidateLoadWithForJoinInto`
  (`:576-577`).
- Question: does the stitcher bypass the paged guard so in-memory `JoinInto` + paged `LoadWith` is no
  longer fail-closed?

## Verdict: fail-closed is retained; no production change.

`allowPerParentTopN: true` is only used inside `Stitch`, which is reached by:

- the single-query `LoadWith` path (which runs `ValidatePerParentPaging` during preparation), and
- the `JoinInto` terminals **after** `JoinIntoStitcher.Execute`/`ExecuteAsync` have already called
  `ValidateLoadWithForJoinInto(builder)` with the default `allowPerParentTopN: false` (`:62`, `:75`).

So a plain `JoinInto` never reaches `Stitch` with a paged `LoadWith` unfiltered: the entry guard throws
`NotSupportedException("*Limit/Offset/Page*")` before the pair command is built, prepared, cached or
executed.

Probes (green, `Feature=D211`, `tests/nextorm.core.tests/EagerLoadPerParentPagingTests.cs`):

- `EagerLoadPerParentPagingJoinIntoTests.JoinInto_WithPagedLoadWith_InMemory_IsRejectedFailClosedBeforeSql`
  — metadata collection overload + `LoadWith(...Limit(1))` throws before any SQL.
- `EagerLoadPerParentPagingJoinIntoTests.JoinIntoExplicitKey_WithPagedLoadWith_InMemory_IsRejectedFailClosedBeforeSql`
  — `JoinInto<TChild,TKey>` explicit-key overload + `LoadWith(...Offset(1))` throws identically.
- `EagerLoadPerParentPagingJoinIntoTests.JoinInto_WithUnpagedLoadWith_KeepsWorking`
  — unchanged behavior: `JoinInto` + unpaged `LoadWith` still stitches both collections.

No production change made (verified unreachable rather than speculatively fixed).
