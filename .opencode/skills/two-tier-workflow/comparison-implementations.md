# Сценарий: сравнение реализаций одной фичи

Встроенный сценарий каркаса [`two-tier-workflow`](SKILL.md). Задача: есть N реализаций одной и той
же фичи (свои руки, варианты кандидатов, эталон) — нужно сравнить их по качеству кода, поведению,
перфомансу, читабельности и документации и выдать обоснованный рейтинг.

## 0. Рамка (делает оркестратор до вызова scout)

Зафиксировать письменно и не менять по ходу:

- **Постановка** — что за фича, где она в репо, что считается успехом.
- **Что фиксировано, что варьируется** — например: база, версия, язык, тулинг, модель исполнителя
  фиксированы; различается только среда/подход/автор варианта. Если варьируется больше одного
  фактора — пометить риск и сформулировать это в `Confidence`.
- **Рубрика** — шаблон ниже; при отсутствии своей брать дефолтную.
- **Бюджет** — сколько вызовов brains и доборов допускается.

**Слепые метки.** Вариантам дать нейтральные имена (`A/B/C`) и **перемешать порядок**; соответствие
`A → какой вариант` знает только оркестратор и не сообщает ни scout'у, ни brains. Иначе судья
подсознательно привяжется к порядку/названию.

## 1. Стандартный набор доказательств (это делает scout, по одному evidence-файлу на вариант)

| Что | Как добывается | Зачем |
|---|---|---|
| Изменённые файлы и диффстат | `git diff --stat <base>...<вариант>`, список новых файлов | объём и зона воздействия (`scope`) |
| Свои тесты варианта | `dotnet test tests/<proj> -c Debug` — сырой итог (total/failed/succeeded) | регрессия; **не** доказательство фичи |
| Портированные эталонные тесты | порт тестов из эталона на публичный API варианта (**только переименования**, `src/` не трогать), прогон, `NOT-PORTED` с причинами | единственная внешняя линейка поведения |
| Пересечение с эталоном | список файлов варианта ∩ файлов эталона | насколько решение похоже на «золотое» |
| Поведение по критериям | по каждому критерию рубрики — улика с `file:line` (SQL-рендер, ключ плана, in-memory, негативные кейсы) | основа для оценки, а не для догадки |
| Перфоманс (если в рубрике) | бенчмарк/замер с точной командой; для .NET — существующие бенчмарк-проекты репо | аргумент вместо «кажется быстрее» |
| Документация | пути и диффстат доков EN/RU, проверка зеркальности | ось `docs` |

Порт тестов — самое хрупкое место: если варианту не хватает эквивалента внутреннего API, тест
уходит в `NOT-PORTED` **с причиной**, а не подгоняется правкой `src/`.

## 2. Вердикт (делает brains)

На вход — задание, рубрика и evidence-файлы. На выход:

```markdown
## Verdict
<1 абзац, 2–4 ссылки на улики>

## Scores
| Критерий | A | B | C | Улика |
|---|---|---|---|---|
| R1 ... | 0/1/2 | ... | ... | [evidence-A §Facts, path:line] |
| quality: correctness/design/api_naming/tests/edge_coverage/docs_en_ru/scope | 0–5 | | | |

## Ranking
1. <метка> — почему (со ссылками)
2. ...

## Top findings
- P1 `path:line` — суть [evidence-NN]

## Missing facts
- <конкретная проверка> — иначе `нет`

## Confidence
high|medium|low — что снижает
```

Обязательно: каждая оценка со ссылкой на улику; при нехватке фактов — `Missing facts` вместо догадки;
если разрыв меньше шума метода — сказать «ничья/в пределах погрешности».

## 3. Шаблон рубрики

Дефолт (проверен на #94): **acceptance 0/1/2** по критериям постановки + **quality 0–5** по осям
`correctness, design, api_naming, tests, edge_coverage, docs_en_ru, scope_decision`, плюс `total` с
**закреплёнными весами** (веса указать в рамке — иначе итог не воспроизводим).

`edge_coverage` (0–5) — покрытие краевых ветвей: 5 — каждый вариант (тип сущности/значения
`class`/`struct`, отсутствие parameterless ctor, `null`/неинициализированное состояние, явная
проекция vs вся сущность, join/подзапрос, квотирование вкл/выкл) покрыт тестом или явным guard'ом;
0 — тесты только на happy-path. Выставляется только по уликам scout'а; нет улик — в `Missing facts`.

Пример acceptance-критериев из #94: R1 хранилище объявлено и наполняется при чтении; R2 SQL рендерит
`select <mapped>, *` с квотированием; R3 join/проекция отклоняются понятной ошибкой; R4 маркер входит
в ключ плана; R5 in-memory наполняет тот же словарь; R6 write-side реализован либо явно отложен и
задокументирован EN+RU.

Требования к рубрике (иначе она бесполезна для сравнения):

- критерии формулируются по **наблюдаемому поведению**, а не по конкретной реализации эталона;
- у каждого критерия есть негативный кейс (иначе все получат максимум и критерий не различает);
- **покрытие краевых ветвей оценивается отдельно** (`edge_coverage`): по каждому варианту — тест,
  guard или «не проверено»; без этой оси дыры вроде непокрытой value-type-ветки #94 не всплывают;
- веса `total` закреплены до судейства;
- «частично» описывается словами (что именно считается половиной), а не оставляется на вкус судьи.

## 4. Грабли (собрано на реальном прогоне)

- **Порядок и метки.** Дают `a1/a2/a3` — судья тянется к первому. Метки — случайные, порядок —
  перемешан, соответствие знает только оркестратор.
- **Эталон среди вариантов** получает максимум «по инерции». Требовать по каждому критерию улику.
- **Порт тестов правит `src`** — тогда сравнивается не реализация, а подгонка. `src` менять нельзя.
- **Считать «src тронут»** надо вычитанием множеств (файлы варианта минус файлы, которых не было в
  его патче), иначе в метрику попадает сам патч варианта.
- **Патч без untracked-файлов** — часть решения теряется. Собирать дифф с `git add -A -N`.
- **Свои тесты зелёные у всех** — это регрессия, а не доказательство. Различает только внешний
  (портированный) набор.
- **Критерий, который никто не выполняет** (в #94 — R3), не различает варианты: либо чинить
  формулировку, либо не включать в `total`.
- **Одна попытка на вариант** — разницу в 1–2 балла нельзя считать значимой; при возможности делать
  повторы, иначе явно писать в `Confidence`.
- **Судить дорогой моделью десяток диффов** — главный источник счёта. Сначала улики, потом один
  вызов; доборы — только по списку `Missing facts`.

## 5. Выходной отчёт

Оркестратор собирает: рамку, таблицу доказательств, `Scores`/`Ranking` от brains, находки с
`file:line`, ограничения метода и пути к evidence-файлам. Каждое утверждение отчёта должно быть
проверяемо по улике; расхождения scout'а и brains трактуются в пользу улики.
