# nextorm: оверлей brainstorming

Проектное дополнение к глобальному скиллу **`brainstorming`**. Загружай его **вместе** с
глобальным и **сначала** глобальный: он ведёт контекст, вопросы и дизайн. Этот оверлей добавляет
проверку прежних решений перед интервью и правило трекинга задач в GitHub и не меняет hard
approval gates, классификацию путей (spike/bounded/architectural) и терминальные состояния.
PDCA здесь не запускается: если работа идёт по циклу, действует `nextorm-pdca`, а не этот оверлей.

## Перед прожаркой: восстанови прежние решения

**До первого содержательного вопроса по каждой задаче** проверь через `scout` существующие
дизайн-спеки и позднейшие записи решений. Ссылка в issue или пересказ его тела не заменяет
проверку самой спеки. Для списка/milestone проверка нужна по каждой задаче, не только первой.

1. `scout` читает указанную спеку; если ссылки нет — точечно ищет по issue/теме в
   `docs/specs/design/`, `docs/superpowers/specs/` и связанных status/plan/handoff/collection-записях.
   Возвращает `file:line`: согласованные решения, явно открытые вопросы, фактический этап.
2. Различай **пройденную прожарку/согласованный дизайн**, **апрув письменной спеки** и
   **разрешение реализации**. «Спека ждёт ревью» не означает «дизайн ещё не обсуждали»;
   наличие файла само по себе не подтверждает ни один апрув.
3. При расхождении issue, спеки и статуса проверь позднейшее **явное** решение и его область
   действия. Дата или наличие реализации не заменяют разрешение; не переноси апрув на соседние задачи.
4. Перед вопросом кратко обозначь, что уже решено и что осталось открытым, с указателем на спеку.
   Продолжай только по неразобранным вопросам. Если открытых вопросов нет — сообщи, что повторная
   прожарка не нужна, и обозначь фактический следующий этап без автоматического перехода через гейт.
5. Вернуться к согласованному решению можно при новом факте, конкретном противоречии или явном
   запросе пользователя: назови основание и обсуждай только эту дельту, не начинай интервью заново.
6. Если артефакт недоступен — сообщи о пробеле и запроси недостающий контекст; не выдавай
   «не проверено» за «спеки/решения нет».

Скорость интервью и экономия контекста не отменяют проверку: факты собирает `scout`,
primary получает короткую сводку, а не весь файл.

## Когда нужен issue

- Чистые вопросы без согласованной задачи реализации и throwaway-спайки — issue **не нужен**.
- Для сохранённой согласованной фичи/рефакторинга/фикса — независимо от того, bounded он или
  architectural — GitHub-трекинг **обязателен** на переходе «согласованный scope → письменная
  спека (user review) / handoff в планирование или реализацию». Не жди, пока пользователь
  попросит тикет.
- Для architectural-пути тикет создан **до** запроса written-spec review.
- При изменении scope обновляй **тот же** issue до следующей спеки/handoff.

## Обязательная запись задачи

Отслеживаемая задача содержит: `GitHub issue: #N + проверенный URL`; `milestone: точное название`;
`agreed scope/acceptance`; `spec/plan: путь, если есть`; `status: фактические апрувы/реализация/
блокер`. Эти поля — в спеке/handoff, когда они есть; для bounded не выдумывай spec-план. Не
хардкодь номер текущего issue или milestone: бери их из фактического репозитория/запроса.

## Как выполнять (дешёвые роли)

1. **scout** — проверь remote текущего репозитория, наличие подходящего issue, целевой milestone
   и доступность/аутентификацию gh. Без секретов.
2. Есть подходящий issue — **обнови его**; иначе создай **один** issue в текущем репозитории
   (проектная инструкция пользователя о трекинге задачи это разрешает).
3. **coder** — сетевые мутации: `gh -R <проверенный owner/repo> issue create --milestone
   <проверенное название> --body-file ...`.
4. Проверь фактические URL, title, state, milestone, body — только потом докладывай «готово».
5. Перед записью ищи существующие issue; при повторах/таймаутах повторяй поиск, чтобы не плодить
   дубликаты. Если пользователь дал точный номер — включи его в поиск.
6. Labels — только существующие подходящие; не выдумывай milestone и не назначай assignee сам.
7. Milestone задан пользователем — проверь точное совпадение. Не задан: если ветка **точно**
   отображается на существующий открытый milestone — бери проверенное название; иначе задай один
   уточняющий вопрос, но не создавай issue с неправильным milestone.
8. В чужой репозиторий ничего не пиши без явного указания.

## Тело issue

Самодостаточные согласованный scope, исключения, совместимость, решения и критерии приёмки.
Ссылки на локальную спеку — инлайном, если она не опубликована (никаких фейковых GitHub blob
URL). Статусы user-gate не искажай. Публикация issue ≠ апрув спеки ≠ исполнение продукта ≠
закрытие.

## Блокеры и границы

- При блокере доступа/сети: состояние `not created` + блокер, локальная спека **не** заменяет
  issue, гейт **не** объявляется пройденным, handoff сохраняет блокер. Не раскрывай токены и не
  читай файлы хостов gh.
- Коммиты/push/merge базовый скилл не разрешает: действуют явные правила репозитория и указание
  пользователя. Автозакрытие issue при планировании/«готово» не делай; тесты, принятая
  реализация и закрытие по политике пользователя — отдельно.

## Частые ошибки

| Ошибка | Исправление |
|---|---|
| «спека есть ⇒ тикет есть» | Нет: нужен `#N` и проверенный URL |
| «пользователь не попросил» | Согласованная задача сама включает проектное правило |
| «scope поменялся — создам новый дубликат» | Обновляй тот же issue |
| «В issue есть ссылка — можно сразу задавать вопросы» | Сначала проверь спеку и позднейшие решения через `scout` |
| «Письменная спека ждёт апрува — прожарку начинаем заново» | Восстанови согласованный дизайн; обсуждай только открытые вопросы |
