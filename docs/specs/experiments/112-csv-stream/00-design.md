# 00 — Дизайн эксперимента: #112 (потоковый CSV в `Stream`) — влияние модели решений

> Дата: 2026-09-29. Статус: **предрегистрация** (рубрика и база фиксируются ДО любых реализаций).
> Отчёт по итогам — `01-scenario.md`…`06-caveats.md` этого же каталога.

## 1. Зачем ещё один прогон

Прогон №2 (`94-skill-comparison-2`) оставил открытым вопрос: `a3` (PDCA) проиграл, потому что
плоха **среда**, или потому что **решения** (`plan`/`check`) шли на DS вместо Sol? Развести не
удалось: `upstream` в #94 был готовым артефактом с собственным контекстом, а базу задавал RFC с
рецептом — то есть сравнение тянуло три конфаундера сразу (модель судьи, готовый эталон, спойлер в
базе).

#112 (`Потоковая выдача csv в Stream`) — **новый** носитель: в базе его нет, эталонного диффа нет,
рецепта нет. Обе стороны пишут с нуля → можно изолировать **одну** переменную.

## 2. Гипотеза

При одинаковых входе (только текст issue), базе и регламенте разница между `a3` и `upstream`
объясняется **моделью агентов решений**: `a3` — `plan`/`check` на `deepseek/deepseek-flash`,
`upstream` — на `opencode/gpt-6-sol` (в обоих случаях `coder` — DS).

## 3. Дизайн

### Стороны

| Сторона | Что | Модели решений | Где |
|---|---|---|---|

## 5. Предрегистрированная рубрика (только для судьи)

Замораживается **до** реализаций; рукам и `upstream` не показывается. Выводится строго из issue
#112. Файл-рубрика хэшируется, хэш — в отчёт.

### L2 — критерии (0/1/2), `total` холистически

| # | Критерий |
|---|---|
| R1 | **Поверхность**: терминал есть на `QueryCommand<TResult>` **и** `EntityBuilder<TEntity>`; пишет CSV в переданный `Stream`; требует явного `Select` (иначе ошибка) |
| R2 | **Стриминг/память**: построчно из ридера, без материализации всего результата и без создания `TResult` на строку; аллокации O(буфера), не O(размера результата) |
| R3 | **Без боксинга**: типизированный доступ к колонкам; в горячем пути нет упаковки значений в `object` |
| R4 | **Корректность CSV**: разделитель, заголовок, экранирование (запятые/кавычки/переводы строк/кавычка внутри), `NULL` |
| R5 | **Владение/ресурсы**: выходной `Stream` не закрывается и не `Dispose`-ится (только `Flush`); ридер/команда освобождаются; корректный путь при исключении |
| R6 | **Охват**: sync **и** async терминалы (`CancellationToken`, `params`); поведение in-memory определено (fallback или `NotSupportedException`) и задокументировано; применимость у провайдеров |

### L3 — scope аудита

Аллокации/перф горячего пути; корректность `IDisposable`/владения; ключ и bounded-ность кэша;
DRY с существующими стриминговыми терминалами (`ToAsyncEnumerable`, LOB `ToStream`); подавления
(`SuppressMessage`/`NoWarn`); XML-doc публичных членов; достаточность тестов (эдж: экранирование,
`NULL`, пустой результат, отмена).

## 6. Судья

**L2** — один агент `deepseek/deepseek-flash`, как в прогоне №2 (J1). Судья **не слеп** (читает код) —
ограничение метода (§11). Рубрика §5 видна судье; реализаций-эталонов нет.

**L3 — два потока**, оба на всех четырёх целях, против одного scope §5:

| Поток | Кто | Как |
|---|---|---|
| L3-generic | `deepseek/deepseek-flash` primary | generic-аудит, как в №2 |
| L3-specialist | `nextorm-code-auditor` | dispatch'ится сабагентом из primary; **read-only** (deny edit), на **копии** дерева; модель **pinned DS** |

`nextorm-code-auditor` — `mode: subagent` и по умолчанию правит два регистра
(`code-smells-review.md`, `API-NAMING-REVIEW.md`), поэтому в роли судьи он обязательно изолируется:
deny edit + одноразовая копия дерева (регистры не задевают оцениваемое дерево). Модель обоих потоков
одинакова у всех целей → сравнение `a3 ↔ upstream` не конфаундится моделью L3. Смещение специалиста
(тянет проектные конвенции, мог зваться руками при реализации) снимается наличием generic-контроля.

## 7. Измерения и harness

Переиспользуем harness `exp94` (single-DS-профиль; `NO_PORT=1`):

- **L1** — свои тесты руки (`dotnet test`, свой набор). **Эталонный порт не выполняется**: у #112 нет
  референса на момент прогона, а его тесты писались бы под чужой API (ошибка метода #94).
- **L2** — судья против рубрики §5 (JSON в `eval/out/<target>.l2.jsonl`).
- **L3** — два потока против scope §5 (см. §6): `eval/out/<target>.l3.jsonl` (generic) и
  `eval/out/<target>.l3-specialist.jsonl` (`nextorm-code-auditor`); в отчёте — оба и их согласие.
- `upstream` судится **тем же** набором судей (L2 + оба L3), чтобы итоги были в одной шкале.
- Стоимость — `dbmetrics.py` (родитель + подагенты).

## 8. Этапы

1. Клонировать `0f1f222` в clean-room, санитизировать §4, зафиксировать base-коммит (хэш).
2. Заморозить рубрику §5 (хэш).
3. Ворктри `exp/{a1-bare,a2-skill,a3-pdca}` от базы.
4. Ворктри `upstream` (санитизированный) — штатный PDCA на #112 (`plan`/`check` = Sol, `coder` = DS).
5. Прогнать a1/a2/a3 (вход = issue, сеть запрещена).
6. `compare.py` → патчи/диффстаты; прогон оценки на a1/a2/a3/upstream: L2-судья + L3-generic +
   L3-specialist (`nextorm-code-auditor`, read-only, на копиях деревьев).
7. `report.py` → отчёт; стоимость; архив; CRLF.

## 9. Отчётность

`docs/specs/experiments/112-csv-stream/` (+ `artifacts/`: патчи, диффстаты, jsonl судьи обоих L3-потоков,
L1-логи), CRLF. Итог — сравнение `a3` vs `upstream` как основной вывод, `a1`/`a2` — среда-контекст;

## 10. Критерий успеха самого эксперимента

- Реализации независимы (нет взаимного просмотра) и обе стартовали от одной санитизированной базы.
- Рубрика и база заморожены до старта (хэши зафиксированы).
- Получен измеримый вердикт по паре `a3` ↔ `upstream` при общем входе/базе/судье.
- Явно названы оставшиеся конфаундеры, если вердикт неоднозначен.

## 11. Чего эксперимент НЕ закрывает

- **Одна попытка на сторону** — дисперсия не измерена.
- **Судья не слеп** (L2/L3-generic) — первый-взглядовый сдвиг возможен.
- **L3-specialist смещён** в сторону проектных конвенций и мог зваться руками при реализации →
  generic-контроль обязателен; расхождение потоков трактуется как сигнал, а не как ошибка одной
  стороны.
- **Без эталонного L1** — внешней линейки поведения нет, только свои тесты.
- **`total` холистичен** — при низком разрешении рубрики смена судьи двигает баллы (см. №2).
- Абсолютные числа несравнимы с №1/№2 напрямую (другой носитель).
