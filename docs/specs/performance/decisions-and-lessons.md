# Performance: решения, уроки, прототипы

Единственное место, где фиксируются **устойчивые выводы** перф-работ по `nextorm.core`: что решено и
почему, что проверено и отклонено, что осталось прототипом. Это не отчёт о прогонах — цифры и таблицы
живут в `benchmark-report.md`, сырые артефакты — в `benchmarks/BenchmarkDotNet.Artifacts`, приёмочные
пороги — в `acceptance-benchmarks.md`.

Правило отбора: сюда попадает только то, что должно пережить следующую сессию и предотвратить повторную
работу. Результат одного прогона — не вывод; вывод — это отношение, воспроизведённое дважды, либо
проверенный факт о коде.

> Исторические записи `docs/specs/status/**` ссылаются на прежние `performance-findings.md`
> (находки `M1..M13`, `I1..I6`) и `performance optimizations.md`. Оба файла слиты в этот; идентификаторы
> `M*`/`I*` сохранены, чтобы старые ссылки оставались осмысленными.

## 1. Принятые решения

### R1. `Prepare()` — санкционированный быстрый путь повторного выполнения

Пользователь, выполняющий одну форму запроса много раз, должен держать `IPreparedQueryCommand`, а не
пересобирать fluent-запрос. Явный `Prepare()` быстрее implicit-кэша (≈1.47× по времени, ≈5× по
аллокациям) и быстрее Dapper на всех измеренных классах. Продвигается в `docs/engine/03-plan-cache-and-reuse.md`
(EN + RU).

### R2. Implicit plan cache остаётся дефолтом

Кэш включён по умолчанию, per-thread (`[ThreadStatic]`), без общего mutable-состояния (см. L8).
Отказ от кэша — не «иногда быстрее», а худший из трёх вариантов: ≈2.4× медленнее кэша и ≈3.5× медленнее
`Prepare()`, плюс Gen1 на каждый вызов из-за пересоздания `DbCommand`/`CreateParameter`.

### R3. Fresh-fluent warm-паритет с Dapper снят как цель

Критерий «≤ ±3 % от Dapper» для не-prepared fluent-арм'ов недостижим безопасной локальной правкой:
Dapper сравнивается с константным SQL, а fluent обязан построить и захешировать свежее дерево выражения
на каждый вызов. Переоткрытие — только как отдельная структурная задача (shape-keyed кэш подготовленных
команд) с собственным бенчмарк-гейтом, потому что она трогает семантику cache-ключа.

### R4. `SqlBuilder` остаётся `struct`

Сейчас — `internal readonly struct` с контекстом сборки (`src/nextorm.core/DataContext/SqlBuilder.cs`).
Гипотеза «`sealed class`/`ref struct` ускорит» не подтвердилась: интерфейса нет, вызовы идут по
локальной переменной, defensive copy отсутствует, а класс добавил бы heap-аллокацию на каждое
построение SQL (в visitor'ах — до нескольких на подзапрос).

### R5. Пулированный `StringBuilder` возвращается только через `try/finally`

`MakeJoin`/`MakeFrom`/`MakeSelect` возвращают буфер в `ObjectPool` на любом пути, включая исключение
при рендеринге. Без этого одно исключение навсегда «съедает» буфер пула.

### R6. `params`: span на sync-путях, массив на async/streaming

- Синхронные терминалы принимают `params ReadOnlySpan<object?>` (`LangVersion=latest`): 0 heap-аллокаций
  на аргумент вместо 24 + 8·n байт.
- Async/streaming остаются на `params object?[]`: массив — транспорт, он переживает `await` и хранится
  в `ResultSetEnumerator`.
- Внутри expression-дерева `params ReadOnlySpan` запрещён компилятором (**CS8640**/**CS9226**, даже при
  нуле аргументов), поэтому рядом с span-формой стоит точный zero-arg overload (`Any(builder)`) — он
  expression-safe и не создаёт массив. `stackalloc object?[n]` для managed-типа не компилируется.

### R7. `sealed` — сужение API, а не перф-рычаг

`ResultSetEnumerator<T>`, `InMemoryEnumerator<TResult,TEntity>`, `InMemoryCompiledQuery<TResult,TEntity>`,
`QueryCommand<TResult>` остаются `sealed`. JIT с tiered PGO и так девиртуализирует мономорфные
интерфейсные вызовы — выигрыш не измерим. Правка ценна только ужесточением поверхности; если
минимальность публичного API перестанет быть приоритетом, её можно откатить без перф-последствий.
Нельзя: `EntityBuilder<TEntity>` и `PreparedQueryCommand` — у них есть наследники.

### R8. Повторное извлечение параметров — только когда есть вычисляемые параметры

`DbPreparedQueryCommand.NeedsParamRefresh` выставляется на cache-miss и только если среди параметров есть
не-`SqlFunctions.Parameter` (захваченная переменная, замыкание). На cache-hit `ExtractParams` вызывается
лишь при `NeedsParamRefresh == true`; реальные значения плейсхолдеров всё равно подставляет
`GetDbCommand` из runtime-массива. Дало −18 % аллокаций кэшированного пути (см. `benchmark-report.md`).

### R9. Бюджет конструирования (M13 / #240) закрыт принятым residual'ом

Структурные сокращения отгружены (ownership-seam + COW + `QueryShape`, коммит `3ae2e80e`), но цель
`≤ 1.20×` по аллокациям для `RecursiveCte`/`Except`/`Intersect` в утверждённом скоупе недостижима.
Владелец принял это 2026-10-16 как **named residual релиза 1.0.9-rc3**; порог `1.20` и замороженный
рецепт D201-3 не менялись. Продолжение — отдельные задачи: #244 (CTE / recursive CTE), #245 (EXCEPT /
INTERSECT). Попутно закрыты два пре-существующих дефекта неизменяемости: `a.Union(b).Except(c)` больше
не мутирует переиспользуемый `b`, и устранён алиасинг `_sorting`.

### R10. Хэширование выражения — без общего mutable-состояния

`ExpressionPlanEqualityComparer` держит visitor per-(thread, comparer) через `[ThreadStatic]` + проверку
владельца. Общий visitor ломал согласованность `GetHashCode`/`Equals` под конкуренцией (запись
недостижима в словаре → повторная компиляция плана). Регресс-тест:
`ExpressionPlanEqualityComparerTests.GetHashCode_ShouldBeThreadSafe`.

### R11. Iteration-14 (#165): prepare-путь не аллоцирует на CTE-lookup

Пять предложений цикла отгружены полностью; стек-атрибуция аллокационного профиля не удалась, поэтому
корневые причины были локализованы кодовым анализом:

- per-call `HashSet<QueryCommand>` в `HasDataModifyingCte` — для уже подготовленной команды `Mutation`
  читается прямо из нормализованного списка CTE (рекурсивный обход сохранён для неподготовленной);
- eager `ExpansionState` в `NavigationExpansion.Expand` создавался даже без навигаций — добавлен ранний
  выход, если у root-типа нет зарегистрированных relationships;
- безусловный обход `CteHoister.EnsureNoUnhoistedCtes` — fast path для leaf-команды без CTE и без рёбер
  графа;
- плюс guard на обычную `int`-проекцию: `NavigationCountNarrowingProbe` не запускается, когда в registry
  нет команд, для которых возможно narrowing широкого navigation count.

Warm CTE reuse возвращён к **0 B/op**. Остаток prepare-арм'ов CTE/Join4 (11–16 % от базы `1.0.9-a`)
принят как полоса шума хоста (< ~20 %); условие переоткрытия — §5.

### R12. Тёплые скалярные агрегаты: per-context кэш неизменяемых артефактов (D243 / #243)

Кэшированный путь `Count()`/`LongCount()`/`Sum(x => x.Member)` больше не строит заново определение
запроса, список выборки, нормализованный ключ плана и команду — артефакты переиспользуются через
`ScalarArtifactCache` (`src/nextorm.core/DataContext/ScalarArtifactCache.cs`).

- **Белый список:** только `Count()`/`LongCount()` без аргументов и `Sum` по единственному
  `MemberExpression`, чей экземпляр — параметр лямбды (одна отображённая скалярная колонка).
  `Avg`/`Min`/`Max`/`Stdev*`/`Var*`/`*_distinct` и любые другие тела селектора идут обычным путём.
- **Все guard'ы fail-closed** (возврат на обычный путь, без угадывания): непустые аргументы вызова;
  не SQL-провайдер (in-memory сохраняет свой исполнитель); выключенный кэш планов контекста; любое
  SQL-влияющее состояние билдера (`EntityBuilder.IsPlainScalarScope`); любой применимый фильтр;
  `Sum` не на одну скалярную колонку.
- **Владение:** кэш в `QueryCache` конкретного контекста, ёмкость 16, FIFO, линейный поиск. Хранится
  только структурный ключ (типы, терминал, `MemberInfo`) + ключ плана; билдер, мутабельная команда,
  замыкание, аргументы и результат **не удерживаются**. Очистка — `PurgeQueryCache()`,
  `DataContextCache.Clear()`, `DisposeStaff()`; статических/глобальных словарей нет, два контекста не
  делят ни одной записи.
- **Публикация и исполнение:** артефакт публикуется только если план принадлежит `QueryPlanStore` этого
  типа контекста, иначе инертен; аргументы текущего вызова привязываются к сохранённой prepared-команде,
  результат пересчитывается каждый раз (мемоизации значения нет), `throwIfNull: false` сохраняет
  семантику `Sum` по пустому набору.
- **Публичный API не менялся**; `Prepare()` и shared `QueryCommand` не затронуты (никакого
  `Cache = false` ради одного вызова).

Закреплено 24 новыми тестами (15 SQLite, 4 core in-memory, 5 core artifact-store): closure/parameter
freshness, фильтры, повторные вызовы, очистка кэша, thread-local recipe и отсутствие sticky `_dontCache`.

Бюджеты: `Count` 408 B/op против 2 864 у linq2db, `Sum` 970 против 3 490; prepared-контроли
408 / 410 / 4 736 B не изменились. Замеры — `benchmark-report.md`, «Итерация 18».

Deferred register (всё осталось в `1.0.9-rc3`):

- `Avg`/`Min`/`Max`, статистические агрегаты и async fast path — триггер: новый измеренный
  allocation-regression либо доказанно бесплатное расширение;
- captured/composite селекторы — триггер: измеренный allocation-hotspot в таком селекторе;
- JoinInto/filter/temp/nested источники — триггер: измеренный провал соответствующего сценария;
- Category-B сценарии #240 — отдельное измерение должно показать регрессию от этого diff;
- интеграция `d243_aggregate_gate.py` с `iteration14_gate.py` — после барьера коллекции.

### R13. Iteration-15 / #183: cached-path B1+B2 поставлены, дизайн закрыт

- Цикл 2 (#183) закончил только Stage A: B1/B2 в нём остались незакоммиченными, issue закрыт как
  `DONE (with limitation)` — это записано в `iteration-15-cached-path-results.md`.
- Затем **B1** (структурное сравнение выражений без лишних equality-скоупов) и **B2** (immutable
  guarded `ParamRefreshRecipe` для привязки свежих захватов) поставлены коммитом `322f9be2`
  (2026-10-05), файл `src/nextorm.core/DataContext/Cache/ParamRefreshRecipe.cs`.
- Эффект подтверждён Итерацией 16: cached-hit аллокации `Where` −1 944 B/op (−27…30 %), `Join`
  −424…−576 B/op, warm CTE 0 B, prepared байт-в-байт, статистически надёжной временной регрессии нет;
  разрыв с Dapper сокращён именно на cache-lookup/param-refresh, а не на материализации.
- **Инварианты B2**, которые нельзя терять при правках refresh-пути: recipe не удерживает mutable
  `DbCommand`/enumerator и не захватывает свежее замыкание; форма валидируется до вычисления значений;
  неподдержанные случаи уходят в оригинальный `ExtractParams` **до** evaluation; двойного evaluation
  замыканий нет; fallback mismatch-safe, а не `Debug.Assert`.
- **Hash-only / fingerprint identity без полной структурной проверки исключена** — не использовать как
  shortcut в кэше планов даже под давлением perf-задачи.

### R14. T201 / #201: pre-prepare reuse поставлен, паритет с LINQ to DB — нет

- Цель: cached-путь против non-compiled LINQ to DB на пяти сценариях (`Cte`, `RecursiveCte`, `Except`,
  `Intersect`, `Distinct`) — время `≤ 1.05`, аллокации `≤ 1.00`.
- **Поставлено в коде:** verified pre-prepare reuse (D201-3) — lookup по value-free raw shape, валидация
  владельца, транзакциональное применение через staged key, fallback на обычную подготовку при любом
  mismatch (`QueryPlanner.GetPreparedQueryCommand`, `QueryPlanStore.TryGetRaw`, `ApplyPreparationFrom`,
  `DiscardStagedPreparation`).
- **Результат:** время MET на обоих валидных раундах для всех пяти сценариев (0.48–0.58× — быстрее
  linq2db), **аллокации FAIL везде**: +8.4 % Distinct, +24.1 % Cte, +38.2 % Except, +39.2 % Intersect,
  +64.8 % RecursiveCte. Относительно своего baseline кандидат дал −14…−21 %, но до `≤ 1.00` не дошёл.
- Acceptance-контроль улучшился (Cached/Prepared: время 1.84 → 1.57, аллокации 7.77 → 5.98), публичная
  поверхность идентична (`equal = true`), покрытие 87.5 / 79.2. Незакрытое наблюдение:
  `SqliteBenchmarkWhere.Nextorm_Cached_ToListAsync` +8.11 % аллокаций между фазами — так и осталось
  наблюдением для CHECK.
- **Итог:** #201 закрыт `NOT_PLANNED`, цель переписана в #240 на `1.20×` (residual принят), продолжение —
  #244/#245. Паритет `≤ 1.00` не переоткрывать без нового решения владельца; числа — в
  `m12-3-prepare-command-results.md`.

## 3. Прототипы и отклонённые гипотезы

| Гипотеза | Проверка | Итог |
|---|---|---|
| Кэш строк алиасов (`"t" + idx`) в `DefaultAliasProvider` | Замер `Build_Sql` / `Build_Sql_Join` без plan-кэша | Эффект <1 %, в шуме. **Откачено:** стоимость генерации SQL доминируется visitor-машинерией, а не строками. |
| `SqlBuilder` как `sealed class` / `ref struct` | Разбор кода + оценка аллокаций | **Отклонено** (R4): выигрыша нет, класс добавил бы аллокации. |

## 4. Уроки

### 4.1 Измерения

- **L1. Файловая система может съесть весь эффект.** Прогоны с SQLite на `/mnt/c` (WSL↔Windows) давали
  ~0.9 мс на запрос и «победу Dapper». На tmpfs картина перевернулась. Абсолютные времена сравнимы
  только внутри одной конфигурации; БД для замеров — на нативном ФС или tmpfs.
- **L2. Быстрый режим не разрешает наносекунды.** `Job.ShortRun` + `InProcessEmitToolchain`: у
  значительной части методов `Error > Mean`, разброс между сессиями до ±30 %. Отношения (6×, 1.5×)
  стабильны, абсолюты — нет. Эффекты в 1–2 нс требуют `NEXTORM_BENCH_FULL=1` (полный out-of-process
  `Job.Default`); путь к БД задаётся `NEXTORM_BENCH_DB`, дефолт — `/tmp/nextorm-bench/test.db`, не
  `/mnt/c`.
- **L3. Один арм — одна переменная.** Рабочая схема: DB-bound baseline против plan-only арм'ов,
  «NoParam» против «Param» для изоляции извлечения параметров. Декомпозиция проверяется на сходимость
  (сумма слагаемых ≈ измеренному целому), иначе модель неверна.
- **L4. Мерить надо то, что есть в проде.** Сравнитель выражений, созданный внутри метода бенчмарка,
  показал аллокацию самого сравнителя и его visitor'а, которых в проде нет: там он кэшируется на команде.
  Объект, чья стоимость измеряется, должен иметь тот же lifetime, что и в рантайме.
- **L5. Кэш не отменяет стоимость формы.** Найти план в словаре можно только построив команду и посчитав
  её хэш; поэтому cache-hit не бесплатен, и «переписать кэш» не устраняет построение expression-tree.
- **L6. Проигрыш по модели использования лечится документацией, а не ядром.** Fresh-fluent проигрывает
  Dapper by design; правильный ответ — продвигать `Prepare()` и снять цель паритета, а не переделывать
  cache-ключи.
- **L7. Сначала потолок, потом рефакторинг.** Для #5 сначала измерена максимально возможная экономия
  (≈⅓ оверхеда, из них доминирующая часть недостижима) — и только затем принято решение не делать.
  Порядок «оцени ceiling → реши» дешевле, чем «сделай → замерь → откати».
- **L17. Решение о перфе принимается по отношению и CI, а не по среднему.** `point = nx.mean / linq.mean`,
  `ratio_low = nx.ci_low / linq.ci_high`, `ratio_high = nx.ci_high / linq.ci_low`; MET только если
  `point ≤ T` **и** `ratio_high ≤ T`; FAIL только если `point > T` **и** `ratio_low > T`; иначе OPEN.
  CI — не ниже 99 %, значения не округлять. Раунд отбрасывается только по операциональной причине
  (падение бенчмарка, не тот job, устаревшие отчёты), а не потому что отношение неудобное. Правило шума
  (~20 %) никогда не ослабляет утверждённый допуск. Заморожено в `m12-3-prepare-command-results.md` §3
  и используется гейтом T240.
- **L18. Стриминг LOB — O(буфера), buffered — O(размера).** При росте значения 1 → 8 МиБ
  (`ToStream`/`ToTextReader` с буфером 64 КиБ) аллокации растут ×1.00–1.08: PostgreSQL BLOB ≈72 → 78 KB,
  CLOB ≈140 KB (не растёт), SQL Server BLOB ≈76 → 81 KB, CLOB ≈272 → 294 KB. Buffered-проекция
  (`.First()` в `byte[]`/`string`) растёт ровно ×8.0 (1.01 → 8.01 МиБ и т.д.). Следствие: на PostgreSQL и
  SQL Server терминалы дают реальную экономию; на MySQL/MariaDB и ClickHouse — нет, драйвер буферизует
  значение целиком (`SupportsSequentialAccess = false`, терминал бросает `NotSupportedException`).
  Замер — `benchmark-report.md`, «LOB streaming vs buffered».

### 4.2 Кэш, состояние, параллелизм

- **L8. Общее mutable-состояние в кэше — дефект корректности, а не перф-мелочь.** Общий visitor давал
  до 49 971 из 50 000 неверных хэшей под `Parallel.For`; ключ попадал в один bucket, искался в другом.
  Любая оптимизация, разделяющая изменяемый объект между потоками, требует регресс-теста на
  многопоточность.
- **L9. Ветка cache-hit обязана повторять семантику miss.** `createEnumerator` игнорировался на hit,
  поэтому форма, впервые выполненная `ToList`, кэшировалась без enumerator'а и следующий стриминговый
  вызов падал с NRE. Контракты обеих веток закреплены тестами `PlanCacheTests`.
- **L10. `paramMode` не рендерит SQL — не резолвить в нём алиасы.** Попытка разрешить алиас в paramMode
  давала `FindAlias == null` и `InvalidOperationException` на cached-Join. Проверка режима должна стоять
  там же, где строится текст.
- **L11. Отсутствие enumerator'а — не NRE.** `DataContext.RequireEnumerator` бросает
  `InvalidOperationException` с инструкцией (`Prepare(nonStreamUsing: false)`), а не разыменовывает `null`.

### 4.3 API и expression trees

- **L12. Span-параметры несовместимы с expression-деревьями.** CS8640/CS9226 возникают даже при нуле
  аргументов; спасение — точный overload без `params`, который выбирается в normal form.
- **L13. `stackalloc` для managed-типа не существует**; «сэкономить массив» через stackalloc в safe-коде
  нельзя — только через span-параметры компилятора.

### 4.4 Процесс

- **L14. Отрицательный результат — тоже результат, и он должен быть записан.** Половина ценности этого
  файла — список проверенных и откаченных гипотез: иначе их переизобретают каждые несколько месяцев.
- **L15. Закрытие решением легитимно, но требует триггера переоткрытия.** «Не делаем» без условия
  возврата превращается в «забыли»; см. §5.
- **L16. Арм в реестре обязан совпадать с тем, что реально меряется.** `Where for-loop (100)` был
  `Nextorm_CachedForLoop_ToListAsync`, где `.Prepare()` вызывается один раз до 100-операционного
  цикла: победа prepared-vs-raw читалась как победа cached-пути. Исправлено в `benchmark-report.md`;
  при добавлении армов проверяй, где стоит `Prepare()` и что попадает в timed-body.

## 5. Триггеры переоткрытия

- **CTE prepare-арм'ы:** два сопоставимых прогона в одном job'е превышают 120 % базы `1.0.9-a` → открывать
  заново. Бюджетный гейт: `scripts/perf/iteration14-budgets.json`, `scripts/perf/iteration14_gate.py`
  (zero-строки warm CTE reuse = 0 B/op, `budget` = `ceil(After × 1.25)`).
- **M13 residual:** продолжение только через #244 (CTE / recursive CTE) и #245 (EXCEPT / INTERSECT);
  порог `1.20×` и рецепт D201-3 не пересматривать.
- **Тёплые агрегаты (R12):** расширение белого списка только по триггерам из R12; `Avg`/`Min`/`Max` и
  captured-селекторы — не «до кучи», а от измеренного регресса.
- **Fresh-fluent паритет (R3):** только как структурная задача M12 #3 с отдельным бенчмарк-гейтом.
- **M10 (R7):** откат `sealed` допустим в любой момент, если важнее минимальная публичная поверхность;
  перф-последствий нет.
- **Гигиена бенчмарков (тикета нет):** `SqliteBenchmarkMakeSelect` и `ExpressionsExperiments` содержат
  только закомментированные `[Benchmark]`; `SqliteBenchmarkCachedPlan` скрывает `Error`/`StdDev`. Пока
  не исправлено, «полный прогон» молча пропускает кейсы.
