# Итерация 14: предложения по исправлению регрессий производительности

Дата: 2026-10-03.

Источник: [benchmark-report.md — Итерация 14](benchmark-report.md), раздел начиная со строки 1555.

Сравнение: `v1.0.9-a` (`624dce0`) → `1.0.9-b` (`713dcde`).

Статус: аналитический отчёт с предложениями на согласование. Сохранение отчёта не означает согласование scope, апрув письменной спецификации или разрешение реализации. GitHub issue для этих исправлений создан — **#165**; статус реализации см. `## Статус` ниже.

## Цель и ограничения

Устранить регресс аллокаций non-prepared/fluent (implicit-cache) prepare-пути без изменения поведения API, SQL и корректности кэширования. Основной критерий — аллокации; время выполнения в Итерации 14 существенно шумит и является вторичным сигналом.

Предпочтительное направление — локальные оптимизации prepare-пути и отдельный аллокационный регресс-гейт, без перестройки кэша. Prepared execution по данным отчёта не получил роста аллокаций; его бюджет необходимо сохранить.

Отчёт подготовлен по анализу существующих результатов и текущего кода. Новые профили, бенчмарки и тесты при подготовке предложений не запускались. Объяснения конкретных байтовых дельт остаются гипотезами до инструментальной атрибуции.

## 1. CTE lookup: убрать повторное выделение HashSet

**Приоритет: высокий. Самое изолированное исправление.**

В исходном отчёте предполагается поломка мемоизации plan-key. Проверка кода указывает на другую причину:

- `src/nextorm.core/Query/QueryCommand.Plan.cs` не изменился относительно `v1.0.9-a`.
- Перед каждым lookup добавлена проверка `HasDataModifyingCte` — `src/nextorm.core/DataContext/QueryPlanner.cs:547`.
- Для любой команды с CTE она создаёт `HashSet<QueryCommand>` и его внутренние массивы — `src/nextorm.core/Query/QueryCommand.cs:557–573`.

Это соответствует наблюдаемому разделению: CTE/recursive CTE получили **176 B/lookup**, а reused join остался на **0 B**. Точную байтовую атрибуцию ещё нужно подтвердить измерением. Код поддерживает гипотезу о дополнительной аллокации в DML-CTE guard, а не о поломке мемоизации ключа.

### Предлагаемое исправление

- Для уже подготовленной команды с полным, нормализованным списком CTE проверять `Mutation` непосредственно в этом списке, без рекурсивного обхода и `HashSet`. До реализации подтвердить полноту списка для всех применимых prepared-путей.
- Для неподготовленной команды сохранить рекурсивную проверку: DML может находиться внутри тела read-CTE.
- Не вводить новый постоянный флаг мемоизации на первом шаге: это добавит вопросы инвалидирования, которых можно избежать.

### Ограничения корректности

DML-CTE не кэшируются; запрет кэширования остаётся локальным `storeInCache: false`, без изменения sticky-свойства `queryCommand.Cache`. Сохранить обнаружение nested DML, отказ для недопустимого размещения CTE и корректность общей команды Any/Count.

### Приёмка

- `Cte_Warm_Reused` и `RecursiveCte_Warm_Reused` возвращаются к **0 B/lookup** после прогрева.
- Проходят тесты nested DML, повторного исполнения мутаций и последующего read-cache lookup.
- Добавляются проверки недостающих сочетаний, если исправление их затрагивает: explicit prepared DML и DML рядом с recursive read-CTE.

**Статус (issue #165):** baseline снят; стековая атрибуция аллокационного профиля не удалась — **Note**; причина локализована кодовым анализом.

## 2. Обычный SELECT: не создавать состояние навигационного прохода

**Приоритет: высокий. Основной кандидат на сокращение общего регресса.**

`NavigationExpansion.Expand` вызывается при каждой подготовке. Даже запрос без навигаций создаёт:

- `ExpansionState`;
- два словаря и список;
- `RewriteVisitor` для лямбд;
- `List<PropertyInfo>(4)` при разборе обычных `it.Id`.

Источники: `src/nextorm.core/Visitors/NavigationExpansion.cs:43–69, 285–287, 321–329, 715–746`.

### Предлагаемое исправление в два этапа

1. **Ранний выход до создания state**, если у root-типа, который фактически использует проход, отсутствуют зарегистрированные relationships. Проверка должна учитывать актуальные метаданные, а не навсегда запоминать «у CLR-типа нет навигаций».
2. Для типов с relationships сделать отрицательный разбор `it.Id` без выделения списка: сначала установить корень цепочки и наличие первого navigation-hop, затем собирать полный путь.

Второй этап сложнее и должен идти отдельным изменением, после измерения первого. Не распространять вывод о root-типе автоматически на независимые вложенные команды: каждая имеет собственную подготовку и тип источника.

### Приёмка

Уменьшение аллокаций `Build_Baseline_SimpleSelect`, `RePrepare_PlanOnly_Param` и `*_Prepare_NoHash`; сохранение SQL и поведения implicit navigation, включая цепочки, collection-терминалы, nullability и повторную подготовку. Добавить прямые проверки no-navigation/simple-member путей, которые сейчас преимущественно покрыты косвенно.

**Статус (issue #165):** реализовано и проверено — warm CTE reuse возвращён к **0 B/op**.

## 3. Проверка размещения CTE: дешёвый путь для простых команд

**Приоритет: высокий, но не удалять проверку целиком.**

`CteHoister.EnsureNoUnhoistedCtes` вызывается и без CTE. Она создаёт два `HashSet` и запускает обход графа команд:

- вызов — `src/nextorm.core/Query/QueryCommand.QueryPreparer.cs:320`;
- реализация — `src/nextorm.core/Builders/CteHoister.cs:66–133`.

### Предлагаемое исправление

- Для leaf-команды без CTE и без рёбер к другим командам — ранний выход до создания обходчика и коллекций.
- Остальные структуры обхода создавать лениво, когда они действительно нужны.
- В первой версии сохранить полный обход сложного графа.

**Нельзя** ограничиться условием «у корня нет CTE»: проверка должна продолжать обнаруживать недопустимые declarations внутри derived-table, join, union и `ColumnShape`, а также других существующих рёбер обхода (`ReferencedQueries`, `Pivot.Inner`, `Mutation.Source`).

Во вложенных запросах этот расход повторяется при подготовке разных узлов. Перенос проверки на один корневой обход стоит рассматривать лишь вторым этапом: он существенно рискованнее локального fast path.

### Приёмка

Снижение аллокаций подготовки простого SELECT без ослабления диагностики unhoisted CTE. Существующие проверки `SubQuery` и `ColumnShape` дополнить покрытием затронутых рёбер графа; не считать отсутствие CTE у корня доказательством отсутствия CTE в подграфе.

**Статус (issue #165):** реализовано и проверено.

## 4. Не запускать probe для обычной int-проекции

**Приоритет: средний. Небольшая сопутствующая оптимизация.**

Для `Select(it => it.Id)` создаётся `NavigationCountNarrowingProbe`, хотя никакого navigation count нет:

- `src/nextorm.core/Query/QueryCommand.QueryPreparer.cs:513–514, 568–569, 610–611`;
- `src/nextorm.core/Visitors/CorrelatedQueryExpressionVisitor.cs:921–952`.

### Предложение

Возвращать `false` без visitor, если registry не содержит команд, для которых возможно narrowing широкого navigation count. Начать с очевидного случая пустого registry. Не добавлять постоянный registry-флаг без определения его жизненного цикла и сброса при повторной подготовке.

### Приёмка

Сохранить различение обычного `int`, `Count()` с checked narrowing и `LongCount()`. Нельзя заменять существующую проверку происхождения узла простым распознаванием `Convert`. Добавить проверки обычной int-проекции и этих count-вариантов.

**Статус (issue #165):** реализовано и проверено.

## 5. Аллокационный гейт — часть исправления

Сейчас CI не контролирует этот бюджет. Поэтому прежние улучшения Итераций 12–13 не защитили prepare-путь от новой регрессии.

Предлагаемый минимальный набор:

| Сценарий | Что контролировать |
|---|---|
| Simple select | Базовую стоимость подготовки без новых фич |
| `RePrepare_PlanOnly_Param` | Повторную подготовку |
| CTE / recursive CTE / Join4 / IN `Prepare_NoHash` | Стоимость разных форм дерева |
| CTE / recursive CTE `Warm_Reused` | **0 B/lookup** |
| `CachedPlan.Build_Sql` | Совокупный бюджет |
| Prepared execution | Отсутствие роста относительно базы |

Бюджеты фиксировать в **B на логическую операцию**: ряд текущих бенчмарков содержит внутренний цикл ×100. Setup, прогрев метаданных и первоначальное заполнение кэша не должны попадать в проверяемую область.

Для обычных запросов ориентир — приблизиться к `v1.0.9-a`, а не принять HEAD как новую норму. Допуски для функционально более сложных сценариев определить по замерам и явно согласовать до включения гейта. Шумное время выполнения не делать жёстким CI-критерием. Числовые бюджеты для ненулевых сценариев пока не утверждены; данный отчёт не является готовой спецификацией CI-гейта.

**Статус (issue #165):** гейт реализован (`eng/perf/*`, шаг CI) — ожидает CHECK.

## Рекомендуемый порядок

1. Зафиксировать baseline и получить **профиль аллокаций со стеками**, а не только CPU-профиль.
2. Исправить CTE lookup отдельным небольшим изменением.
3. Добавить no-navigation и leaf-command fast paths; измерять вклад каждого отдельно.
4. Оптимизировать разбор navigation paths и count probe.
5. Закрепить бюджеты в автоматической проверке.

Для изменений query-path использовать существующий acceptance-набор дополнительно к целевым allocation-бенчмаркам. Если затронута семантика провайдеров, включая DML-CTE или navigation count, прогнать соответствующие SQL-generation и container-backed integration-тесты; пропущенные провайдеры не считать проверенными.

## Рассмотренные подходы и исключения

- **Рекомендуется:** локальные fast paths с раздельными замерами. Они адресуют найденные конкретные расходы и ограничивают риск.
- **Возможный второй этап:** переработка общих обходов графа после профилирования. Потенциальный эффект выше на вложенных запросах, но необходимо заново доказать полноту валидации.
- **Не рекомендуется в этом scope:** общий shape-keyed prepared-command cache или широкое переписывание visitors. Это отдельная архитектурная задача. Перевод пользователей на `Prepare()` тоже не исправляет регрессию implicit-cache пути.

## Уточнения исходного отчёта и открытые вопросы

- Гипотезу о сломанной CTE-мемоизации следует уточнить: по коду мемоизация продолжает работать; новый подозреваемый — обход `HasDataModifyingCte`. Сам `benchmark-report.md` при сохранении этого отчёта не изменялся.
- Вклад `MemberTranslator` и фильтров пока не подтверждён для простого prepare-only сценария.
- Точная пообъектная атрибуция общей дельты prepare требует профиля аллокаций; кодовый анализ не заменяет его.
- Числовые ненулевые allocation-бюджеты и способ запуска гейта в CI ещё нужно согласовать.
- Принятие предложений, issue/milestone, written-spec review и разрешение реализации остаются отдельными этапами.
