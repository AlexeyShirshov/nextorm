# Роутинг данных по топологиям

Внутренняя спека. Внешний трекер: [#394](https://github.com/AlexeyShirshov/nextorm/issues/394)
(milestone **1.0.10**). Родительские решения:
[#69](https://github.com/AlexeyShirshov/nextorm/issues/69) (шардирование),
[#65](https://github.com/AlexeyShirshov/nextorm/issues/65) (mapping scope).

Статус: реализованы инкременты 1 и 2 (контракты, маршрутизация в контексте, инвариант одной
топологии, round-robin, пиннинг хоста, транзакция на маршрутизированном хосте, публичный гайд) — см.
«Состояние реализации» и «Закрытые вопросы реализации».

## Контекст

Шардирование (#69) уже дало движку то, чего раньше не было: один `DataContext` держит **несколько
соединений** и выбирает соединение на команду. Решение о соединении принимает
`DataContext.ManagerFor(MappingScope)` (`src/nextorm.core/DataContext/DataContext.cs:303-323`):
числовой ключ scope трактуется как бакет, кольцо топологии отдаёт шард, соединение создаётся лениво и
кэшируется по `shardId` (`DataContext.cs:29-30, 318-328`), закрывается вместе с контекстом
(`DataContext.cs:1936-1938`). Исполнитель спрашивает роутер на каждую команду через делегат
`_managerForScope` (`DataContext/QueryExecutor.cs:21,42,54,268,287,341`).

Это ровно та развилка, которую надо назвать общим механизмом: **роутинг данных**. Шардирование —
его частный случай.

## Терминология

- **Роутинг** — механизм, который по правилам выбирает, на каком **хосте** выполнять команду.
- **Топология** (`IHostTopology`) — источник хостов роутинга. За ней может стоять несколько
  соединений шардинга (кольцо бакетов), несколько обычных соединений без шардинга (round-robin,
  RPS-подобный критерий, пользовательский пикер) или что-то иное.
- **Хост** (`HostTarget`) — конкретное соединение внутри топологии: стабильный идентификатор +
  строка подключения. Вес, здоровье, нагрузка — дело топологии, не движка.
- **Правило роутинга** — структурное (тип/неймспейс/сборка) или по данным (значения объявленных
  свойств). Правило по данным называется **шардированием**.
- **Mapping scope** — слой имён (#65): ключ → таблица/схема/колонки/префикс параметров. Роутинг его
  контракт не меняет и наоборот: scope может существовать без роутинга (multi-tenancy на одном
  соединении).

## Модель: четыре слоя, четыре вопроса

| Вопрос | Слой | Состояние |
|---|---|---|
| Какая логическая область у сущности/команды | `IEntityScopeResolver` → `MappingScope` | есть, общий |
| Какие физические имена | `IEntityMetadataProvider` | есть, общий |
| На какой топологии выполнять | `IEntityRouteResolver` → `HostTarget` | **новый слой** |
| Как топология выбирает хост | `IHostTopology` | **новый контракт**; шардинг — одна из реализаций |

Ключевое следствие: сегодня `scope == MappingScope.Default` означает «соединение контекста». При
структурном роутинге у сущности **нет ключа данных**: её scope — `Default`, а жить она должна на
своём хосте. Поэтому решение о хосте обязано быть функцией пары `(Type entityType, MappingScope
scope)`, а не одного scope; «нет правила» — вот что теперь означает соединение контекста.

## Контракты

```csharp
// Правило роутинга: структура + данные + пользовательская логика.
public interface IEntityRouteResolver
{
    bool TryResolve(Type entityType, in MappingScope scope, out RouteTarget target);
}

// Таргет — имя топологии; к конкретному соединению не привязан.
public readonly record struct RouteTarget(string Topology);

// Топология: выдаёт хост под команду. Вес/здоровье/нагрузку решает сама.
public interface IHostTopology
{
    string Name { get; }
    bool TryGetHost(in TopologyContext context, out HostTarget host);
}

// Хост: стабильный id (ключ кэша соединений) + строка подключения.
public readonly record struct HostTarget(string Id, string ConnectionString);

public readonly struct TopologyContext
{
    public Type EntityType { get; init; }
    public MappingScope Scope { get; init; }
    public CommandKind Kind { get; init; }   // Read | Write — для read/write-пикеров
}
```

Шардинг становится комбинацией:

- правило по данным — существующий `ShardRouter` (`Sharding/IShardRouter.cs`): ключ → бакет → scope;
- топология — `ShardTopology`, которая **реализует `IHostTopology`** и добавляет шардинг-специфичное:
  `Ring`, `PlacementMode`, `ShardIds`, `GetConnectionString(shardId)` — то есть
  `IShardTopology : IHostTopology` (+ свои члены), а `UseSharding(IShardTopology)` сохраняет подпись.
  Переименование `IShardTopology` в `IHostTopology` не делается: общий контракт — новый и базовый,
  шардинговый остаётся производным и по-прежнему читается как шардинговый.

Топология без шардинга — другая реализация `IHostTopology` (несколько соединений, выбор по кругу или
по пользовательскому критерию), без единой строки изменений в движке.

### Три способа задать правило

```csharp
[RouteTo("crm")]                       // 1. атрибут на типе
public sealed class Customer { ... }
```

```csharp
var builder = new DataContextBuilder()
    .UseDataRouting(routing => routing
        .RouteNamespace("Acme.Crm", "crm")        // 2. регистрация на билдере
        .RouteAssembly(typeof(Customer).Assembly, "crm")
        .UseResolver(new MyRuleResolver()));      // 3. кастомный резолвер
```

Порядок применения — от частного к общему: атрибут типа → кастомные резолверы в порядке регистрации →
регистрация по неймспейсу/сборке → отказ (соединение контекста).

## Когда что резолвится

| Что | Когда | Почему |
|---|---|---|
| Статические правила: атрибут, неймспейс, сборка | один раз на тип (кэш в таблице правил), результат подставляется при каждом выполнении | правило зависит только от типа; аллокаций нет, на команду — поиск в словаре |
| Правила по данным (шардинг) | так же: тип + scope, scope приходит из билдера | ключ данных превращается в scope на этапе билдера |
| Кастомные пикеры топологии (round-robin, RPS, здоровье) | **перед выполнением** каждой команды (`IHostTopology.TryGetHost`) | выбор зависит от момента, а не от типа |

Уточнение по сравнению с исходным решением: маршрут **не** кладётся в prepared command. Подготовленные
планы кэшируются и переиспользуются (в том числе между контекстами), а правила роутинга — конфигурация
контекста, поэтому маршрут резолвится при выполнении из `(тип сущности, scope)`; дорогая часть
(рефлексия по атрибуту, сопоставление неймспейса) кэшируется в таблице правил, так что цена команды —
несколько поисков в словаре. Если позже понадобится нулевая стоимость, маршрут можно положить в
prepared command и включить идентичность правила в ключ плана — это отдельное решение.

Следствие: план **не размножается** от выбора хоста — в ключе тип, scope и форма запроса, но не
`HostTarget`. Кэш соединений контекста ключуется `HostTarget.Id` (`topologyName/hostId`), поэтому
шардинг и round-robin используют один и тот же механизм.

## Соединение контекста = дефолтная топология (принято)

Раньше строка подключения контекста и топологии сосуществовали: соединение контекста обслуживало
команды без правила, а топологии — остальные. Это два ответа на один вопрос, поэтому правило сузили:

- контекст **без роутинга** — только строка подключения (простейшая топология из одного хоста);
- контекст **с роутингом** — только билдер: `UseDefaultTopology(...)` называет топологию (либо сразу
  регистрирует однохостовую из строки подключения), её хост и есть соединение контекста;
- одновременная передача строки подключения (или готового соединения) и роутинга —
  `InvalidOperationException` при создании контекста; роутинг без дефолтной топологии — тоже;
- дефолтная топология спрашивается **один раз** при создании контекста, её хост стабилен на время
  жизни контекста: на нём выполняются команды без правила, raw SQL и транзакция контекста;
- `PinHost` дефолтной топологии и маршрутизированная транзакция на ней отклоняются — для соединения
  контекста есть `ITransactionManager`; пиннинг и routed-транзакции относятся к остальным топологиям.

## Аффинность соединения (принято)

- Пока активна транзакция (`ITransactionManager`), хост **пиннится**: все команды идут на то же
  соединение, иначе транзакция врёт.
- Без транзакции дефолт — выбор хоста на команду (максимум параллелизма для round-robin/RPS).
- Явный пиннинг доступен вызывающему: `PinHost(topology, hostId)` возвращает `HostPin : IDisposable`,
  поэтому пиннинг ограничивается областью `using`; `UnpinHost` снимает его без дескриптора.
- Read-your-writes в топологии без шардинга не гарантируется движком: это свойство конкретной
  топологии (пикер обязан учитывать, что запись и следующее чтение должны попасть на один хост, если
  приложение этого требует).

## Валидация: где она дешёвая

На построении модели (один раз на тип, до первого запроса):

- правило ссылается на незарегистрированную топологию — ошибка при регистрации, не при запросе;
- два правила на один тип (атрибут + неймспейс с разными таргетами) — ошибка; одинаковый таргет —
  допустимо и идемпотентно;
- топология без хостов — ошибка при регистрации;
- правило по данным у типа без объявленного ключа — ошибка при построении метаданных типа;
- неймспейс-правило без подходящего типа — не ошибка (пустая выборка допустима), но пишется в лог
  «правило не сработало ни разу».

На планировании запроса — инвариант одной топологии: все источники команды (FROM, join, подзапросы,
CTE, target/`USING` у DML, `LoadWith` в режиме single-query) обязаны резолвиться в **один**
`RouteTarget`. Нарушение — `NotSupportedException` (новый публичный тип исключения не вводим: в
репозитории уже принято кидать `NotSupportedException` там, где клиентского обхода нет):

```
Query mixes topologies: 'Acme.Crm.Customer' -> 'crm', 'Acme.Billing.Invoice' -> 'billing'.
One statement must resolve to a single topology; split the query or place both entities on one topology.
```

Проверка бесплатна: множество источников известно до генерации SQL, резолв — чистая функция типа и
scope.

## Границы

- Кросс-топологическая композиция запрещена: один SQL — одна топология. Клиентского join нет.
- Транзакция действует в пределах одного хоста; для шардинга — в пределах соединения шарда
  (fan-out не одна транзакция, уже задокументировано).
- `AcrossBuckets()` — возможность шардинговой топологии, не общего слоя.
- Топология не знает о планах, метаданных и именах; правило не знает о соединениях.

## Что меняется в существующем коде

- `DataContext.ManagerFor(MappingScope)` → `ManagerFor(Type, MappingScope)`: резолв правила →
  `RouteTarget` → `IHostTopology.TryGetHost` → менеджер; кэш ключуется `HostTarget.Id`
  (`DataContext.cs:303-328`).
- `QueryExecutor._managerForScope` (`QueryExecutor.cs:21,42`) принимает тип+scope либо готовый
  `HostTarget` из prepared command (для статических правил).
- `IShardTopology` получает базу `IHostTopology`; `ShardTopology` реализует `TryGetHost` через кольцо.
  Публичная поверхность меняется в невыпущенном API (`PublicAPI.Unshipped.txt`), миграции для
  пользователей нет.
- `UseSharding` сохраняет публичную семантику: правило по данным + шардинговая топология.

## Состояние реализации

Инкремент 1 (`tests/nextorm.core.tests/Routing/DataRoutingTests.cs`):

- контракты `IHostTopology`, `HostTarget`, `TopologyContext`, `CommandKind`, `RouteTarget`,
  `IEntityRouteResolver`, `[RouteTo]`, `DataRoutingBuilder`/`UseDataRouting`;
- `ShardTopology` реализует `IHostTopology` (`Name` + `TryGetHost`), `IShardTopology : IHostTopology`,
  `UseSharding` регистрирует топологию и правило по данным (`ShardRouteResolver`), поведение шардинга
  не изменилось;
- `DataContext` резолвит маршрут на команду (`RouteFor`), кэширует соединение на хост
  (`topology/host`), закрывает их вместе с контекстом;
- правила: атрибут типа и сборки, `RouteNamespace`, `RouteAssembly`, кастомные резолверы;
  конфликт двух правил с разными таргетами — `InvalidOperationException`; правило на
  незарегистрированную топологию — ошибка при создании контекста (декларированные правила) или на
  первом маршрутизированном запросе (атрибут);
- команда внутри транзакции, уходящая на другой хост, — `InvalidOperationException`;
- мутации (insert/update/delete/merge/truncate) маршрутизируются по типу сущности команды.

Инкремент 2 (`tests/nextorm.core.tests/Routing/TopologyRoutingTests.cs`):

- инвариант одной топологии на команду: `CommandRouteSources.Collect` обходит `FROM`, join,
  подзапросы (`From.SubQuery`, `ReferencedQueries`), CTE и ветви union; набор едет в prepared command
  как `RouteSources` (типы, не маршрут) и резолвится при выполнении. Две разные топологии —
  `NotSupportedException` с обоими источниками; источник без правила допустим и едет на выбранном
  хосте. Тип-проекция join (`Projection<...>`) разворачивается в элементы;
- `RoundRobinTopology` — референсная топология без шардинга: несколько соединений, атомарный счётчик,
  свои идентификаторы хостов, пиннинг учитывается; `PinHost` возвращает `HostPin : IDisposable`
  (освобождение снимает пиннинг, повторный пиннинг той же топологии заменяет его, старый дескриптор
  становится no-op);
- физические имена в raw SQL: плейсхолдеры `{schema}`, `{table}`, `{qualified}` раскрываются при
  построении плана из метаданных привязанной сущности (`BindEntity`) и scope команды; без токенов текст
  выводится дословно, `{schema}` требует объявленной схемы, квотирование — по `QuoteIdentifiers`;
  публичный `GetPhysicalTableName<TEntity>(scope)` отдаёт те же `Schema`/`TableName`/`QualifiedName`
  для SQL, собираемого вне построителя. Размещение по умолчанию — `SchemaPerBucket`
  (`{placeholder}_{bucket}.{table}`, placeholder — схема сущности или `bucket`);
- дефолтная топология: `UseDefaultTopology(name)` / `UseDefaultTopology(name, connectionString)`
  (последний регистрирует однохостовую `RoundRobinTopology`); контекст с роутингом создаётся из
  билдера (`new PostgresDataContext(builder)` у каждого провайдера), строка подключения рядом с
  роутингом и роутинг без дефолтной топологии — ошибка при создании; хост дефолтной топологии
  резолвится один раз и становится соединением контекста; в DI-расширениях добавлены безпараметрические
  `UsePostgres()`/`UseSqlite()`/`UseSqlServer()`/`UseMySql()`/`UseMariaDb()`/`UseClickHouse()`, которые
  создают контекст из билдера;
- пиннинг хоста: `DataContext.PinHost`/`UnpinHost`, `TopologyContext.HostId`; топология обязана вернуть
  закреплённый хост (контекст проверяет идентификатор), иначе — `InvalidOperationException`;
  `ShardTopology` и `RoundRobinTopology` пиннинг поддерживают;
- транзакция на маршрутизированном хосте: роль `IRoutedTransactionManager` (не расширяет
  `ITransactionManager`, чтобы не ломать сторонние реализации) + extension-методы на `DataContext`.
  Начатая транзакция пиннит топологию к выбранному хосту; исполнитель берёт транзакцию у того
  менеджера, на котором выполняет команду (раньше — всегда у менеджера контекста). Команда вне хоста
  открытой маршрутизированной транзакции — `InvalidOperationException`; один контекст несёт одну
  транзакцию; savepoints остаются на соединении контекста;
- батч — одна сессия и один round trip, поэтому маршрутизируется как целое: `RenderBatch` собирает
  у каждого шага (query, CTAS-источник, мутация, capture) его `(MappingScope, источники)` и требует
  одну топологию и одну область на весь батч; результат едет в `BatchPlan.Route` (`BatchRoute`), и
  исполнитель резолвит соединение через `ManagerFor` уже на выполнение (батч внутри
  маршрутизированной транзакции присоединяется к её хосту). Два разных топологии или две области —
  `NotSupportedException` ещё при рендере (`ToSql()` тоже), шаг без правила едет на выбранном хосте;
  `CommandRouteSources` обходит и `from.TempTable.Source`, поэтому чтение ленивой временной таблицы
  маршрутизируется по сущностям её источника, а `BatchRunner` больше не держит соединение контекста;
- материализация (`ToTable`/`ToTempTable`, `DropExisting`, шаг `CreateTempTable` батча) маршрутизируется
  по сущностям исходного запроса, а не по типу проекции: `MutationCommand.RouteSources` (у
  `CreateTableAsCommand` — из `CommandRouteSources.Collect(Source)`), `MappingScope` берётся у источника,
  `DropTableCommand` несёт те же scope/источники; раньше CTAS уходил на соединение контекста, хотя его
  SQL читал таблицу бакета (`tests/nextorm.core.tests/Routing/MaterializationRoutingTests.cs`);
- публичный гайд `docs/guide/34-routing-data-to-topologies.md` (EN + RU), раздел «Sharding as data
  routing» в гайде 35, «One batch, one topology» в гайде 34, записи в toc;
  `tests/nextorm.core.tests/Routing/BatchRoutingTests.cs`.

Осталось (не входит в инкремент 2):

- `LoadWith` split queries выполняются отдельными командами и потому маршрутизируются каждая сама;
  single-query вариант покрыт инвариантом (join в том же запросе);
- фабрика соединения вместо строки в `HostTarget` (провайдеры без connection string) — не в v1;
- savepoints и вложенные транзакции на маршрутизированном хосте;
- bulk-путь (`BulkInsertBuilder`) остаётся на соединении контекста и не знает бакета: у
  `BulkInsertCommand` нет `MappingScope`, имя цели резолвится из метаданных дефолтной области;
- `ExecuteRaw`/`ExecuteProcedure` не несут scope и идут на соединение контекста (это описано в
  гайдах).

## Принятые решения (вопросы закрыты)

1. **Аффинность** — см. раздел выше: пиннинг при транзакции, выбор на команду без неё, явный пиннинг
   доступен.
2. **Контракт топологии** — только «выдай соединение»; вес, здоровье, нагрузка, RPS — пользовательские
   пикеры внутри `IHostTopology`/`IEntityRouteResolver`, движок их не знает.
3. **Точка резолва** — статические правила (тип, неймспейс, сборка) в prepared; всё остальное перед
   выполнением.
4. **Слой и шардинг** — новый слой `IHostTopology`; шардинг его использует как базовый контракт
   (`IShardTopology : IHostTopology`), а не отдельный параллельный механизм.
5. **Диагностика** — `NotSupportedException` с фиксированным форматом сообщения (см. выше), без нового
   типа исключения в v1.

## Закрытые вопросы реализации

- Состав `TopologyContext`: `Scope`, `Kind`, `HostId` (пиннинг). Тип сущности в контекст не входит:
  правило уже выбрано до вызова топологии.
- Форма пиннинга: метод контекста (`PinHost`/`UnpinHost`) плюс неявный пиннинг на время
  маршрутизированной транзакции; scope единицы работы не понадобился.
- `HostTarget` несёт строку подключения; фабрика соединения — возможное расширение, не в v1.

## Критерии приёмки (черновик)

- Структурный роутинг работает для чтения и для insert/update/delete/merge/truncate.
- Кастомный резолвер подключается без изменения движка.
- Топология без шардинга: несколько соединений, round-robin, транзакция пиннит хост, явный пиннинг
  работает.
- Кросс-топологическая команда падает на планировании с сообщением, перечисляющим источники.
- Статические правила не создают план на хост; round-robin не размножает планы.
- Шардирование сохраняет поведение и публичный API (`UseSharding`, `AcrossBuckets`).
