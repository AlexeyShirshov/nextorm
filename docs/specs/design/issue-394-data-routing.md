# Роутинг данных по топологиям

Внутренняя спека. Внешний трекер: [#394](https://github.com/AlexeyShirshov/nextorm/issues/394)
(milestone **1.0.10**). Родительские решения:
[#69](https://github.com/AlexeyShirshov/nextorm/issues/69) (шардирование),
[#65](https://github.com/AlexeyShirshov/nextorm/issues/65) (mapping scope).

Статус: решения по открытым вопросам приняты (см. «Принятые решения»); код не начат.

## Контекст

Шардирование (#69) уже дало движку то, чего раньше не было: один `DataContext` держит **несколько
соединений** и выбирает соединение на команду. Решение о соединении принимает
`DataContext.ManagerFor(MappingScope)` (`src/nextorm.core/DataContext/DataContext.cs:303-323`):
числовой ключ scope трактуется как бакет, кольцо топологии отдаёт шард, соединение создаётся лениво и
кэшируется по `shardId` (`DataContext.cs:29-30, 318-328`), закрывается вместе с контекстом
(`DataContext.cs:1936-1938`). Исполнитель спрашивает роутер на каждую команду через делегат
`_managerForScope` (`DataContext/QueryExecutor.cs:21,42,54,268,287,341`).

Это ровно та развилка, которую надо назвать общим механизмом: **роутинг данных**. Шардирование —
его частный случай.

## Терминология

- **Роутинг** — механизм, который по правилам выбирает, на каком **хосте** выполнять команду.
- **Топология** (`IHostTopology`) — источник хостов роутинга. За ней может стоять несколько
  соединений шардинга (кольцо бакетов), несколько обычных соединений без шардинга (round-robin,
  RPS-подобный критерий, пользовательский пикер) или что-то иное.
- **Хост** (`HostTarget`) — конкретное соединение внутри топологии: стабильный идентификатор +
  строка подключения. Вес, здоровье, нагрузка — дело топологии, не движка.
- **Правило роутинга** — структурное (тип/неймспейс/сборка) или по данным (значения объявленных
  свойств). Правило по данным называется **шардированием**.
- **Mapping scope** — слой имён (#65): ключ → таблица/схема/колонки/префикс параметров. Роутинг его
  контракт не меняет и наоборот: scope может существовать без роутинга (multi-tenancy на одном
  соединении).

## Модель: четыре слоя, четыре вопроса

| Вопрос | Слой | Состояние |
|---|---|---|
| Какая логическая область у сущности/команды | `IEntityScopeResolver` → `MappingScope` | есть, общий |
| Какие физические имена | `IEntityMetadataProvider` | есть, общий |
| На какой топологии выполнять | `IEntityRouteResolver` → `HostTarget` | **новый слой** |
| Как топология выбирает хост | `IHostTopology` | **новый контракт**; шардинг — одна из реализаций |

Ключевое следствие: сегодня `scope == MappingScope.Default` означает «соединение контекста». При
структурном роутинге у сущности **нет ключа данных**: её scope — `Default`, а жить она должна на
своём хосте. Поэтому решение о хосте обязано быть функцией пары `(Type entityType, MappingScope
scope)`, а не одного scope; «нет правила» — вот что теперь означает соединение контекста.

## Контракты

```csharp
// Правило роутинга: структура + данные + пользовательская логика.
public interface IEntityRouteResolver
{
    bool TryResolve(Type entityType, in MappingScope scope, out RouteTarget target);
}

// Таргет — имя топологии; к конкретному соединению не привязан.
public readonly record struct RouteTarget(string Topology);

// Топология: выдаёт хост под команду. Вес/здоровье/нагрузку решает сама.
public interface IHostTopology
{
    string Name { get; }
    bool TryGetHost(in TopologyContext context, out HostTarget host);
}

// Хост: стабильный id (ключ кэша соединений) + строка подключения.
public readonly record struct HostTarget(string Id, string ConnectionString);

public readonly struct TopologyContext
{
    public Type EntityType { get; init; }
    public MappingScope Scope { get; init; }
    public CommandKind Kind { get; init; }   // Read | Write — для read/write-пикеров
}
```

Шардинг становится комбинацией:

- правило по данным — существующий `ShardRouter` (`Sharding/IShardRouter.cs`): ключ → бакет → scope;
- топология — `ShardTopology`, которая **реализует `IHostTopology`** и добавляет шардинг-специфичное:
  `Ring`, `PlacementMode`, `ShardIds`, `GetConnectionString(shardId)` — то есть
  `IShardTopology : IHostTopology` (+ свои члены), а `UseSharding(IShardTopology)` сохраняет подпись.
  Переименование `IShardTopology` в `IHostTopology` не делается: общий контракт — новый и базовый,
  шардинговый остаётся производным и по-прежнему читается как шардинговый.

Топология без шардинга — другая реализация `IHostTopology` (несколько соединений, выбор по кругу или
по пользовательскому критерию), без единой строки изменений в движке.

### Три способа задать правило

```csharp
[RouteTo("crm")]                       // 1. атрибут на типе
public sealed class Customer { ... }
```

```csharp
var builder = new DataContextBuilder()
    .UseDataRouting(routing => routing
        .RouteNamespace("Acme.Crm", "crm")        // 2. регистрация на билдере
        .RouteAssembly(typeof(Customer).Assembly, "crm")
        .UseResolver(new MyRuleResolver()));      // 3. кастомный резолвер
```

Порядок применения — от частного к общему: атрибут типа → кастомные резолверы в порядке регистрации →
регистрация по неймспейсу/сборке → отказ (соединение контекста).

## Когда что резолвится

| Что | Когда | Почему |
|---|---|---|
| Статические правила: атрибут, неймспейс, сборка | при подготовке команды (prepared), результат лежит в prepared command | правило зависит только от типа; резолв один раз на (тип, scope, форма) |
| Правила по данным (шардинг) | при подготовке: scope уже часть ключа плана | ключ данных превращается в scope на этапе билдера |
| Кастомные пикеры топологии (round-robin, RPS, здоровье) | **перед выполнением** каждой команды | выбор зависит от момента, а не от типа; в ключ плана не входит |

Следствие: план **не размножается** от выбора хоста — в ключе тип, scope и форма запроса, но не
`HostTarget`. Кэш соединений контекста ключуется `HostTarget.Id` (`topologyName/hostId`), поэтому
шардинг и round-robin используют один и тот же механизм.

## Аффинность соединения (принято)

- Пока активна транзакция (`ITransactionManager`), хост **пиннится**: все команды идут на то же
  соединение, иначе транзакция врёт.
- Без транзакции дефолт — выбор хоста на команду (максимум параллелизма для round-robin/RPS).
- Явный пиннинг доступен вызывающему (например, `PinHost()` на контексте или scope единицы работы) —
  форма API решается при реализации, требование зафиксировано.
- Read-your-writes в топологии без шардинга не гарантируется движком: это свойство конкретной
  топологии (пикер обязан учитывать, что запись и следующее чтение должны попасть на один хост, если
  приложение этого требует).

## Валидация: где она дешёвая

На построении модели (один раз на тип, до первого запроса):

- правило ссылается на незарегистрированную топологию — ошибка при регистрации, не при запросе;
- два правила на один тип (атрибут + неймспейс с разными таргетами) — ошибка; одинаковый таргет —
  допустимо и идемпотентно;
- топология без хостов — ошибка при регистрации;
- правило по данным у типа без объявленного ключа — ошибка при построении метаданных типа;
- неймспейс-правило без подходящего типа — не ошибка (пустая выборка допустима), но пишется в лог
  «правило не сработало ни разу».

На планировании запроса — инвариант одной топологии: все источники команды (FROM, join, подзапросы,
CTE, target/`USING` у DML, `LoadWith` в режиме single-query) обязаны резолвиться в **один**
`RouteTarget`. Нарушение — `NotSupportedException` (новый публичный тип исключения не вводим: в
репозитории уже принято кидать `NotSupportedException` там, где клиентского обхода нет):

```
Query mixes topologies: 'Acme.Crm.Customer' -> 'crm', 'Acme.Billing.Invoice' -> 'billing'.
One statement must resolve to a single topology; split the query or place both entities on one topology.
```

Проверка бесплатна: множество источников известно до генерации SQL, резолв — чистая функция типа и
scope.

## Границы

- Кросс-топологическая композиция запрещена: один SQL — одна топология. Клиентского join нет.
- Транзакция действует в пределах одного хоста; для шардинга — в пределах соединения шарда
  (fan-out не одна транзакция, уже задокументировано).
- `AcrossBuckets()` — возможность шардинговой топологии, не общего слоя.
- Топология не знает о планах, метаданных и именах; правило не знает о соединениях.

## Что меняется в существующем коде

- `DataContext.ManagerFor(MappingScope)` → `ManagerFor(Type, MappingScope)`: резолв правила →
  `RouteTarget` → `IHostTopology.TryGetHost` → менеджер; кэш ключуется `HostTarget.Id`
  (`DataContext.cs:303-328`).
- `QueryExecutor._managerForScope` (`QueryExecutor.cs:21,42`) принимает тип+scope либо готовый
  `HostTarget` из prepared command (для статических правил).
- `IShardTopology` получает базу `IHostTopology`; `ShardTopology` реализует `TryGetHost` через кольцо.
  Публичная поверхность меняется в невыпущенном API (`PublicAPI.Unshipped.txt`), миграции для
  пользователей нет.
- `UseSharding` сохраняет публичную семантику: правило по данным + шардинговая топология.

## Принятые решения (вопросы закрыты)

1. **Аффинность** — см. раздел выше: пиннинг при транзакции, выбор на команду без неё, явный пиннинг
   доступен.
2. **Контракт топологии** — только «выдай соединение»; вес, здоровье, нагрузка, RPS — пользовательские
   пикеры внутри `IHostTopology`/`IEntityRouteResolver`, движок их не знает.
3. **Точка резолва** — статические правила (тип, неймспейс, сборка) в prepared; всё остальное перед
   выполнением.
4. **Слой и шардинг** — новый слой `IHostTopology`; шардинг его использует как базовый контракт
   (`IShardTopology : IHostTopology`), а не отдельный параллельный механизм.
5. **Диагностика** — `NotSupportedException` с фиксированным форматом сообщения (см. выше), без нового
   типа исключения в v1.

## Открытые вопросы (реализация)

- Точный состав `TopologyContext` (достаточно ли `EntityType`, `Scope`, `Kind`).
- Форма явного пиннинга: метод контекста против scope единицы работы.
- Может ли `HostTarget` нести фабрику соединения вместо строки (для провайдеров без строки) — не в v1.

## Критерии приёмки (черновик)

- Структурный роутинг работает для чтения и для insert/update/delete/merge/truncate.
- Кастомный резолвер подключается без изменения движка.
- Топология без шардинга: несколько соединений, round-robin, транзакция пиннит хост, явный пиннинг
  работает.
- Кросс-топологическая команда падает на планировании с сообщением, перечисляющим источники.
- Статические правила не создают план на хост; round-robin не размножает планы.
- Шардирование сохраняет поведение и публичный API (`UseSharding`, `AcrossBuckets`).
