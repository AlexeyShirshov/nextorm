# #144 — Native SelectWhereMax/Min: PostgreSQL и ClickHouse

**Дата:** 2026-10-01
**Статус:** Дизайн согласован; реализация отгружается в collection `1.0.9-b-2` (PDCA task 2, issue #144).

**Ссылки:**
- Issue: https://github.com/AlexeyShirshov/nextorm/issues/144
- Portable `SelectWhereMax/Min` отгружен в #115, commit `9dd018a`.

---

## 1. Цель

Добавить **нативные SQL-стратегии** для текущего публичного API `SelectWhereMax/Min`, не меняя
контракт, отгруженный в #115. Цель — корректная нативная SQL-генерация для PostgreSQL и ClickHouse;
**обещания измеренного ускорения нет**.

## 2. Принятые решения (утверждены)

### 2.1 Семантика (не меняется)

- `One` — ровно **одна произвольная настоящая winning-строка источника** на партицию; все
  возвращаемые поля берутся из **той же самой строки**.
- `All` — все связанные (tied) winners, через существующий portable lowering.
- Сравнение ties идёт **только** по selector'у; пользовательский `OrderBy` влияет **только** на
  выдачу (output), а не на выбор победителя. API tie-break **нет**.
- Строки, у которых **любой** компонент экстремального ключа `NULL`, исключаются; группы, полностью
  состоящие из `NULL`-ключей, опускаются.
- Nullable-ключи групп поддерживаются; nullable payload сохраняется.
- Пустой вход возвращает **ноль строк**, включая global-случай.

### 2.2 Покрытие

- `One` в формах whole-row и projection × global и group — для PG и CH.
- Все **8 базовых нативных комбинаций** (2 провайдера × 2 формы результата × 2 формы партиции)
  должны иметь SQL- и integration-ассерты на поддержанных простых ключах.
- Составные ключи — по **лексикографическому** порядку компонентов; покрыты и `Max`, и `Min`.
- Базовые integer-скаляр и составной ключ могут быть приёмочными примерами, но это **не** заявление,
  что ВСЕ типы ключей автоматически eligible.
- Неподдержанные/непроверенные типы и выражения откатываются на portable; для CH ключевые компоненты
  floating-point (включая составные) откатываются из-за неподтверждённого паритета NaN-сравнения в
  целевом CH 25.8.
- Дополнительные типы допускаются **только** с явными parity-тестами.
- Расширения множества допустимых query shapes **нет**.

### 2.3 Автоматический выбор стратегии

Выбор — **автоматический и детерминированный**, по провайдеру + форме/типу запроса. Нет
per-instance переключателя, нет нового пользовательского opt-in, нет retry при ошибке БД.

### 2.4 Производительность исключена

Измерения производительности **явно исключены пользователем**: без серверного бенчмаркинга, без BDN,
без таймингов/аллокаций cached-path. Это не «опционально» и не «nonblocking» — их просто нет в
области. Приёмка — только корректность и факт нативной SQL-генерации; измеренное ускорение не
обещается.

## 3. Архитектура и поток данных

### 3.1 Гейт совместимости

- Существующие проверки совместимости и гейт `SupportsSelectWhereMinMax` выполняются **до** выбора
  стратегии.
- Флаг сохраняет своё значение «поддержка portable-фичи»: у всех шести встроенных диалектов он уже
  `true`; исходный комментарий в issue «false у всех провайдеров» — устаревший.

### 3.2 Изоляция нативной генерации

- Нативная генерация изолируется в **опциональной провайдерной capability**, по принятому в репозитории
  шаблону nullable renderer capability.
- Отсутствующая/дефолтная capability = portable; это работает и для кастомных диалектов.
- **Запрещено:** ветвление по имени провайдера в generic `SqlBuilder`; дублирование правил
  validation/null/projection/distinct/output sorting; раскрытие внутреннего состояния extreme-row
  команды через новый публичный API.
- Точные сигнатуры renderer'а — деталь implementation-плана, здесь они **не фиксируются**.

### 3.3 Кэш планов

- Ключ `QueryPlanStore` включает `ContextType` + `Plan`, но **не** экземпляр диалекта.
- Встроенная стратегия стабильна; portable-тестовые контексты используют отдельные конкретные типы,
  чтобы избежать cache aliasing.
- Никакой mutable-конфигурации стратегии и никаких sticky-изменений `QueryCommand.Cache`.

### 3.4 Концептуальный конвейер

`validation` → выбор `native`/`portable` **до** side-effecting рендеринга → `source Where` +
фильтрация `key-component IS NOT NULL` → выбор winning **source row** → существующие внешние
projection/Distinct/output sorting.

- Fallback решается **до** мутации `SqlBuildContext` (params/aliases/column scopes); никакое частичное
  нативное состояние не протекает в portable-генерацию.
- Сохраняются mapping/column aliases, scalar- и object-проекции, целостность «та же строка».
- Volatile/непроверенные формы выражений **не** становятся eligible по предположению.

### 3.5 PostgreSQL

- Grouped: `DISTINCT ON (group) ORDER BY group, <полный экстремальный ключ> ASC (Min) / DESC (Max)`.
  Дополнительных гарантий tie-break нет.
- Global: внутренний `ORDER BY <экстремальный ключ> LIMIT 1`.
- Эти внутренние клаузы **не** легализуют пользовательский paging, запрещённый guard'ами.
- Финальный пользовательский `OrderBy` должен быть **внешним**, а не вплетённым в выбор tied-winner.

### 3.6 ClickHouse

- Один `argMin/argMax(tuple(source-row payload), key scalar/tuple)` на группу (или global); tuple
  защищает nullable-поля и целостность строки.
- Проекция применяется **снаружи** выбора winning-строки.
- Обработка nullable-групп сохраняет существующее поведение.
- Global-агрегат на пустом входе обычно отдаёт default-row: его нужно **явно подавить** по числу
  входных строк (например, `HAVING count() > 0` над **отфильтрованным** входом; нужен integration-тест).
- Обеспечить отсутствие all-null групп; **не** полагаться на собственный null-skipping агрегата.
- Это **не** отдельный `argMax` на поле и **не** сырой nullable-скаляр как payload.
- Иллюстративная SQL-форма может быть опущена; заявления «проверено на сервере» нет.

## 4. Provider × форма

| Форма запроса | PostgreSQL | ClickHouse | Прочие провайдеры |
| --- | --- | --- | --- |
| `One` global, whole-row/projection | `ORDER BY <экстремальный ключ> LIMIT 1` | tuple `argMin/argMax` (global suppress empty) | window |
| `One` grouped, whole-row/projection | `DISTINCT ON` | tuple `argMin/argMax` | window |
| `All` | portable window | portable window | portable window |
| Неподдержанные/непроверенные ключи/типы | window | window | window |

Обе операции, `Min` и `Max`, покрыты. Сигнатуры публичного .NET API не меняются. Отсутствующая shared capability
работает для кастомных диалектов; fail-closed validation по-прежнему применяется.

## 5. Приёмка и тестирование

### 5.1 SQL generation

- Ассерт факта попадания в **нативную ветку** для всех 8 базовых комбинаций.
- `Min`/`Max` на скалярных и составных поддержанных ключах.
- Позиции внешних `Where`/null-обработки/projection/Distinct/`OrderBy` — где применимо.
- Alias collisions, mapped columns, null defaults.
- `All` и ineligible типы — fallback.
- Неподдержанные модификаторы по-прежнему отвергаются **до** dispatch.

### 5.2 Integration (реальные PG/CH)

Сравнение native vs forced-portable на **DISTINCT конкретных типах контекста**:

- уникальные ключи — точно та же строка/множество значений, без учёта неспецифицированного порядка вывода;
- ties `One` — ровно один валидный winner на партицию с целостной полной строкой и корректной
  проекцией, **не** побайтовое равенство ID;
- `All` — множества winners и fallback;
- nullable-компоненты ключа, all-null партиции, nullable-группы/payload, пустой global/group,
  фильтры, убирающие максимум;
- object- и scalar-проекции, проекция, зависящая от нескольких полей;
- output ordering и Distinct.

Планируются portable nonregression-тесты для остальных провайдеров.

Integration требует скилла `running-integration-tests` и `DOCKER_HOST`; пропущенные провайдеры **не**
являются passing evidence. Для написания этого документа тесты **не запускались**.

### 5.3 Документация и гигиена

- EN/RU публичные доки описывают автоматический выбор стратегии и caveats; **публичные доки не
  ссылаются на specs**, внутренние ссылки на specs допустимы.
- Устаревший комментарий в `SqlDialectBase` исправляется при будущей реализации.
- Обычные build/analyzer-проверки планируются; без suppression-shortcuts; CRLF.
- Требования по perf-доказательствам нет.

## 6. Non-goals

- Детерминированный tie-break.
- Нативный `All`.
- Расширение guarded-комбинаций (joins/paging/CTE и т.п.).
- Per-instance переключатель.
- Retry-to-portable.
- Новый SQL function API.
- Измерения производительности и обещанные выигрыши.
- Реализация сейчас.

## 7. Риски и остаточные детали

**Риски, разрешённые консервативно:** NaN в CH 25.8 → fallback; null payload → tuple; подавление
пустой агрегации; разделение стратегии в кэше; согласование общей внешней семантики.

**Остаточные implementation-детали (не нерешённые требования):**

- минимальный контракт renderer'а;
- extraction/aliasing для реконструированной CH-строки;
- явная протестированная матрица eligibility типов.

## 8. Handoff

Следующий шаг — **пользователь проверяет эту письменную спецификацию**. Implementation-план
составляется **только после явного одобрения письменной спеки**, не автоматически. Реализация и
коммиты не авторизованы.
