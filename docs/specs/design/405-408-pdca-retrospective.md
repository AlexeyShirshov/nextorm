# Ретроспектива коллекции PDCA #405–#408

Все четыре задачи приняты по отдельности, итоговая проверка коллекции прошла.
Результаты и [статусы задач](../../../.pdca/status/collection-405-407.md)
вошли в `1.0.12` через merge-коммит `a6a05f68`. Здесь собраны выводы, которые
пригодятся в следующих циклах, без журналов и временных артефактов.

## Что изменить в следующих коллекциях

1. **Фиксировать статус на входе, а критерии разбирать по задачам.** При первом
   запуске путь к статусу не передали, а пробел в критериях одной задачи (#407)
   остановил всю коллекцию. Передавайте канонический путь статуса при запуске
   и сохраняйте решение PLAN сразу. Если критерии отдельной задачи не удалось
   определить, записывайте её терминальный исход отдельно: это не приёмка задачи
   и не причина останавливать другие подготовленные задачи. См. [разбор двух
   процессных дефектов](405-407-pdca-process-defects.md).
2. **Добавлять задачи в хвост очереди, не прерывая активную работу.** Новый цикл
   #407 после уточнений и добавленная позднее #408 получили отдельные решения
   о месте в очереди. Их исходный коммит назначали после приёмки и локального
   коммита предшественника. Перед обработкой нового запроса сверяйте
   зафиксированное состояние текущей задачи: при сжатии контекста сессии
   понадобилось восстановление из статуса, но счётчики и кандидат сохранились.
3. **Сопоставлять изменения с проверками на итоговом дереве.** Между задачами
   изменились некоторые общие файлы. На границе интеграционной проверки
   сопоставляйте для каждой задачи проверенный снимок, изменившиеся файлы и
   прогоны на пересекающихся путях. Документ #408 не менял входы сборки, поэтому
   проверку коллекции завершили без лишней пересборки. При последующем слиянии
   с разошедшейся `1.0.12` входы изменились: на новом дереве повторно прошли
   46 модульных и 7 живых тестов SQL Server, а также 2 сценария SQLite.

## Уроки отдельных задач

### #405: захват SQL Server `OUTPUT INTO` для `UPDATE` и `DELETE` с `JOIN`

- Для `wslc` запрашивайте свободный loopback-порт у Windows (`127.0.0.1:0`), а не
  проверяйте его доступность в WSL. Не отбрасывайте порты выше `59999`. При сбое
  старта сохраняйте диагностический вывод ошибки без учётных данных.
- К первой независимой проверке прикладывайте наблюдение о том, какой SQL,
  какую причину отказа и какие ограничения в гайдах проверяет кандидат.
  Зелёный счётчик сам по себе не отвечает на эти вопросы.
- Если блокер связан только с доступом к БД, не меняйте принятый к проверке
  снимок и не увеличивайте счётчик попыток реализации. После восстановления
  доступа сверяйте сборку и точные ID тестов для неё, прежде чем продолжить
  отложенную проверку.

### #406: запись и фильтрованное чтение постоянной таблицы в одном батче

- Если критерий требует одну команду, считайте старты команд `SqlClient` на
  конкретном соединении, отдельно от подготовки и очистки. Статистика сетевых
  обменов и текст команды дополняют эту проверку, а не заменяют её.
- До первой сборки проверьте лимит файлов в целевой папке. Если после сборки
  переместился только модульный тест, повторяйте лишь затронутую проверку,
  предварительно подтвердив, что входы интеграционной сборки не изменились.

### #407: `OutputInto` и `OutputIntoThenOutput` для standalone `MERGE`

- Провайдерные fluent-операции над общими билдерами размещайте в пакете
  провайдера, если они не входят в общий контракт Core. В этом случае расширения
  SQL Server сохранили обычный `Returning()` и батчевый контракт #266.
- При изменении генерации результата DML проверьте специализированные пути SQL
  наряду с общим. Отдельный путь key upsert сначала обходил новый `OUTPUT`;
  целевые тесты выявили это до независимой проверки.

### #408: эквиваленты серверного захвата DML у других провайдеров

- Отделяйте возможности движка от того, что предоставляет NextORM, и отмечайте,
  какой пример выполнен, а какой подтверждён версионным первоисточником.
  Четыре пробы выполнены на SQLite 3.37.2; примеры для PostgreSQL, MariaDB, MySQL
  и ClickHouse не запускали на живых серверах.
- В воспроизводимом примере разделяйте подготовку, одну мутацию в одном вызове
  и отдельное наблюдение. Клиентский `RETURNING`, повторное чтение таблицы и
  передача строк мутации дальнейшей SQL-операции — разные контракты.
  См. [матрицу движков](D408-dml-capture-provider-matrix.md).
