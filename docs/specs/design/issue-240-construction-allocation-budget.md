## 1. Отношение к #201 / T201

#201 закрыт владельцем (`not planned`); его terminal `incomplete` не переоткрывается, результаты не
пересматриваются, а замороженный alloc-критерий #201 **не применяется** для ретроспективного PASS.
#240 — отдельная задача со своим дизайном и своим бюджетом (§4).

Наследуются ограничения #201: не подменять измеряемый сценарий удержанием mutable
query/builder/prepared-артефакта; не менять cache-key/семантику кэша без отдельного дизайна; публичный
prepared/compiled API — отдельный скоуп. Пороги #235/#238 не меняются.

## 2. Intent

Снизить аллокации построения fluent-команд так, чтобы каждая из пяти Category B сценариев benchmark
`SqliteBenchmarkFeaturesFairCached` (Cte, RecursiveCte, Except, Intersect, Distinct) давала ≤ **1.20 ×**
LINQ to DB в том же раунде (same-round, по существующему правилу сравнения), при сохранении публичного
API, наблюдаемого поведения и сценария «свежий запрос на каждый вызов».

Сверка с артефактами: все числа совпадают с `artifacts/diag240/alloc-phases.json`. Одно расхождение по
подписи столбца: в диктовке третий столбец NextORM назван `exec`, фактически это `prepared` — повторный
запуск уже построенной команды; `exec` есть только в ветке LINQ (повторное перечисление построенного
`IQueryable`). Здесь и далее используется фактическая подпись `prepared`.

- `full ×10` воспроизводит замороженные BDN-числа кандидата: отклонение ≈2.3 % (Cte) и максимум ≈3.5 %
  (RecursiveCte) — в пределах заявленных ~3.5 %.
- `NextORM build / LINQ build` = 1.44 / 2.04 / 1.78 / 1.78 / 1.87 → «в 1.4–2.0 раза дороже на построении».
- `NextORM prepared / LINQ exec` = 3.29 / 3.51 / 3.06 / 3.03 / 3.15 → «примерно втрое дешевле на
  выполнении/материализации».

Вывод: **обе** библиотеки пересобирают запрос на каждый вызов; LINQ to DB строит дешевле, но выполняет
дороже. Весь излишек локализован в построении.

Атрибуция по типам (EventPipe gc-verbose + TraceEvent; `report-nexorm.*` / `report-linq.*`):

| тип (family) | NextORM | доля | LINQ |
| --- | --- | --- | --- |
| `QueryCommand<T>` (5 типов) | 1 140.7 МБ | 24.9 % | нет |
| `RawShape` (дескрипторы рецепта) | 630.8 МБ | 13.8 % | нет |
| `QueryDefinition` | 380.1 МБ | 8.3 % | нет |
| `EntityBuilder<*>` (без `JoinedEntityBuilder`) | 259.4 МБ | 5.7 % | нет |
| `CapturedValueScan` | 47.8 МБ | 1.0 % | нет |
| `QueryPlan` + обвязка компаратора | 95.5 МБ | 2.1 % | нет |
| `System.RuntimeMethodInfoStub` | 339.3 МБ | 7.4 % | 342.8 МБ |

Типы, присутствующие **только** в трейсе NextORM (50 из 106), — **2 956.4 МБ из 4 582.1 МБ = 64.5 %**;
цифра диктовки подтверждена. Уточнения по числам диктовки: `EntityBuilder<*> ≈259 МБ` — это сумма без
`JoinedEntityBuilder` (43.8 МБ), вся семья `EntityBuilder*` = 303.2 МБ; `QueryPlan ≈96 МБ` — это
`QueryPlan` + `Func<QueryPlanEqualityComparer>` + `Lazy<...>`, вся семья компараторов (6 типов) = 122.8 МБ;
`RuntimeMethodInfoStub` ≈339 против ≈343 МБ — сходится (общая expression/reflection-машинерия сопоставима).

Оговорки: AllocationTick сэмплируется примерно раз в 100 КБ, ранжирование статистическое; трейсы
агрегируют все пять форм; PDB/IL-offset в трейсе нет.

## 4. Решения владельца (согласовано в прожарке)

1. Порог **20 %** (≤1.20 × LINQ to DB, same-round) обязателен для всех пяти сценариев, **включая
   RecursiveCte**; без усреднения между сценариями.
2. Публичный API и наблюдаемое поведение не меняются; сценарий (свежий запрос строится на каждый вызов)
   сохраняется — как и LINQ to DB строит заново.
3. Кэширующий «рецепт» D201-3 (capture/verify/apply: `RawShape`-дескрипторы, обход замыканий,
   компараторы) **не трогаем**.
4. Архитектурные изменения разрешены, но инвариант неизменяемости сохраняется: `QueryCommand` (и вся
   fluent-цепочка) не мутируется после создания, каждый шаг даёт новый объект — как узлы expression tree;
   никакого shared mutable state.
5. Допустимы и структурное сокращение (меньше объектов, структурное разделение, отказ от лишних копий),
   и пулинг/переиспользование временных буферов.
6. Обязательные ограничения: **нет утечек памяти, нет деградации производительности, нет потери
   функциональности**.
7. Milestone — `1.0.9-rc3`.
8. Порог **1.20×** — **жёсткое приёмочное условие** для всех пяти сценариев. Если в ходе планирования
   или реализации выяснится, что цель недостижима в рамках §6 (неприкосновенный рецепт, неизменяемость,
   отсутствие утечек/деградации/потери функциональности, неизменный SQL/API), это **эскалация владельцу
   с доказательствами** — а не молчаливое ослабление порога, не подгонка под бенчмарк и не самовольное
   снятие ограничений.

## 5. Бюджет при неуменьшаемом рецепте

Числа B/op (замороженный раунд D201-5 + вклад рецепта из атрибуции; рецепт — оценка probe с точностью
~1–2 %):

| сценарий | текущий кандидат | LINQ same-round | цель 1.2× | рецепт | бюджет на построение+выполнение | сейчас вне рецепта | нужно срезать |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Cte | 115 130 | 92 802 | 111 362 | 20 409 | 90 953 | 94 721 | ~4 % |
| RecursiveCte | 144 243 | 87 522 | 105 026 | 36 706 | 68 320 | 107 537 | ~36 % |
| Except | 71 523 | 51 760 | 62 112 | 21 567 | 40 545 | 49 956 | ~19 % |
| Intersect | 71 363 | 51 280 | 61 536 | 21 630 | 39 906 | 49 733 | ~20 % |
| Distinct | 43 440 | 40 080 | 48 096 | 9 587 | 38 509 | 33 853 | уже проходит |

Источники и сверка: `текущий кандидат` и `LINQ same-round` — замороженный раунд D201-5
(`docs/specs/status/D201-cached-parity-1.md`, строки 1391–1392: 115 130/144 243/71 523/71 363/43 440 против
92 802/87 522/51 760/51 280/40 080); `рецепт` — 20 409 / 36 706 / 21 567 / 21 630 / 9 587 (там же, строки
1480–1481, и `artifacts/pdca/T201/rv1/diagnostics/attribution.md`); `цель 1.2×` = LINQ × 1.2;
`бюджет` = `цель − рецепт`; `вне рецепта` = `кандидат − рецепт`; `нужно срезать` =
(`вне рецепта − бюджет`) / `вне рецепта` — относительная доля текущих непокрытых рецептом байтов,
которую требуется убрать (4.0 / 36.5 / 18.8 / 19.8 %, для Distinct бюджет ≥ остатка — проходит).

**Пометка:** это диагностическая оценка, а не приёмочное доказательство; приёмка — BDN (§8).

**Знаменатель и точность.** Приёмка считается по **same-round** ratio в новых валидных раундах (§9), а
не по числам этой таблицы: они — индикативный бюджет из замороженного раунда D201-5 (точность ~±2 %,
дрейф конкурента между раундами до ~2.9 %). Индикативный headroom RecursiveCte ≈ **+23 %** «вне рецепта»
против **+24.4 %** в `attribution.md` — расхождение ~1 360 B/op из-за иной схемы вычитания; на вывод
«нужно срезать ~36 %» оно не влияет.

## 6. Инварианты и ограничения

- Неизменяемость `QueryCommand`/билдеров (решение 4): шаг не мутирует предыдущий объект.
- Публичный API-совместимость: поверхность не ломаем. Публичными (факт builder-check) являются
  `QueryDefinition` (`public sealed record`), `QueryCommand`, `QueryCommand<TResult>`,
  `EntityBuilder<TEntity>` и публичный вход `DataContextExtensions.CreateCommand<T>(IDataContext,
  QueryDefinition)`; их типы и сигнатуры **не меняем** (в частности, `QueryDefinition` не превращаем в
  `struct` и не удаляем). Кандидаты §7 применимы только к **внутренним** структурам, не входящим в этот
  публичный контракт.
- Генерируемый SQL и результаты идентичны; семантику кэша/plan-key без отдельного дизайна не меняем.
- Пулинг: буферы не переживают вызов/не протекают, нет неограниченного роста, корректность при
  конкурентном использовании (DataContext/команд) не ухудшается.
- Владение при пулинге: пулированные/scratch-буферы **не должны быть достижимы из объектов, переживающих
  вызов** (возвращаемые неизменяемые команды/билдеры); всё, что становится частью неизменяемого объекта, —
  корректно принадлежащая неизменяемая память. Пул допустим только для транзитных вычислений внутри
  вызова; детальный дизайн владения — на этапе плана.
- Улучшение — в общем пути построения, применимо ко всем провайдерам и запросам; **никакой
  benchmark-specific логики**.
- Действующее ограничение по времени (ratio ≤1.05 vs LINQ, сейчас MET) сохраняется: «нет деградации
  производительности».

## 7. Направления (кандидаты; детализация — планировщику)

- Устранять создание `QueryDefinition` на каждый шаг и на каждое чтение `Definition` **только там, где это
  внутренний путь**, не входящий в публичный контракт (§6); публичный `QueryDefinition` остаётся как есть.
  Внутренний аксессор `QueryCommand.Definition` — `internal`.
- Не копировать массивы, которые после построения не мутируются (структурное разделение под
  неизменяемостью).
- Set-операции (Distinct/Except/Intersect/UnionAll): не клонировать всю команду, а только изменяемый слот.
- Пулинг/scratch для транзитных буферов построения.
- Убрать повторные `.ToArray()`/`_joins.Clone()`.

Все кандидаты применимы только к **внутренним** структурам, не входящим в публичную поверхность (§6).
Это кандидаты, а не обязательный список; выбор — по измерению.

## 8. Риски

- Пулинг и владение буферами → утечки/повреждение/гонки; нужен явный дизайн владения.
- Изменение внутренней структуры может поменять SQL/план → недопустимо.
- Оптимизация под пять сценариев рискует стать подгонкой → недопустимо.
- Перенос работы из построения в выполнение может ухудшить время/exec-аллокации.
- Жёсткость порога (решение 8): **1.20×** — приёмочное условие для всех пяти сценариев; недостижимость в
  рамках §6 → эскалация владельцу с доказательствами, а не ослабление порога, подгонка под бенчмарк или
  самовольное снятие ограничений.

## 9. Приёмка (для будущего плана; сейчас ничего не запускать)

- BDN `SqliteBenchmarkFeaturesFairCached`: все пять alloc-строк ≤1.20 × LINQ same-round; два валидных
  раунда; правило across-round; time ≤1.05 сохраняется.
- Публичный API-совместимость: публичная поверхность проверяется компиляцией потребителей/
  существующими тестами; конкретный механизм — планировщику (в репозитории нет `PublicAPI*.txt`).
- Инвариант неизменяемости: тест, что после шага предыдущий `QueryCommand` не изменился.
- Отсутствие утечек/стабильность: повторные вызовы не растят память (steady-state), пул возвращается.
- Функциональная эквивалентность: unit + integration (SQLite + контейнерные провайдеры по проектной
  инструкции running-integration-tests; skipped провайдер ≠ green), SQL-снапшоты без изменений.
- Общий (не benchmark-specific) тест: произвольные запросы тоже аллоцируют меньше.
- Документация: если поведение видимо пользователю — обновить EN+RU; иначе без правок.

## 10. Non-goals
