### S1-EVIDENCE-HISTORY — перезапись raw-лога попытки и устаревшая CHECK-запись

- **Симптом:** финальный raw-лог попытки 1 был перезаписан; оставшийся `attempts/native-run-1.log` — ранний probe с `no such table: SimpleEntity`, а не утраченный финальный лог. В статусе одновременно было написано `CHECK not run`, хотя далее записаны три раунда CHECK и полный CHECK-report принятия.
- **Корневая причина:** сырые данные разных попыток не были изолированы по идентичности попытки и один и тот же путь использовался повторно; обновление записи CHECK не синхронизировали с состоявшимися CHECK-раундами.
- **Эффект на попытки/циклы:** исходная фактура первой попытки утрачена без возможности восстановления; позднейшие сводки не заменяют raw-log. Статус противоречил реальной истории фаз, создавая неверное recovery-состояние. Критерии S1 всё же были приняты по доступным свидетельствам, но историю попытки восстановить нельзя.
- **Evidence:** `.pdca/status/T366-rc5-1.md:245` (утрата финального raw log попытки 1); `.pdca/status/T366-rc5-1.md:247-253` (три CHECK rounds при отметке not run в историческом содержимом); `.pdca/status/T366-rc5-1.md:256-312` (полный отчёт CHECK); `.pdca/365-366-r2/items/T366/step1/rv1/runtime-failures.md:3,20-33`; `.pdca/365-366-r2/items/T366/step1/rv1/attempts/native-run-1.log` (доступный ранний probe, не утраченный финальный лог).
- **Предотвращение:** каждый raw-run получает уникальный файл внутри `attempts/nN/`; не перезаписывать существующий лог и не направлять два запуска в один файл. После каждого фактического перехода CHECK незамедлительно обновлять CHECK-запись и shared progress log; `not run` допустимо только если CHECK действительно не запускался. Перед передачей проверить, что указатели и состояние соответствуют фактически созданным артефактам.

### T365-N4-evidence-receipt-drift — строки manifest не соответствовали измерительному CSV

- **Симптом:** CHECK T365 подтвердил процессный дрейф evidence: после частичного исправления generation receipts совпадали с manifest, а gate-логи стали непустыми, однако сами manifest-строки сохраняли устаревшие predicates и противоречили результатам CSV. В частности manifest показывал `24 open / 2 met`, ошибочный статус для прошедшего сценария и иные значения no-component control. Успешные gate rc=0 не означали согласованность содержимого с фактическими измерениями.
- **Корневая причина:** receipt-слой механически проецировал строки manifest; эта проверка доказывала только совпадение receipt↔manifest, но не сверяла manifest-предикаты/статусы/значения с исходным CSV. Непустые gate-логи устранили отсутствие читаемого вывода, но не устранили семантический drift источника и его проекции.
- **Эффект на попытки/циклы:** находка осталась открытой после evidence re-gather N=4; существующая проверка подтверждала внутреннее совпадение receipt/manifest, но не позволяла считать данные измерения достоверно отражёнными в manifest. Итоговый CHECK T365 остался `not accepted`, AC6 `unmet`, остальные перечисленные критерии `unverified`; дефект процесса не менял и не переоткрывал issue #365.
- **Evidence:** `.pdca/status/T365-rc5-4.md:59-62,95,130` (вердикт/находка, открытый defect key, описание re-gather); `.pdca/365-366-r2/items/T365/rv3/check-report-final.md:28-30` (подтверждённый drift и точные discrepant totals); `.pdca/365-366-r2/items/T365/rv3/manifest.json:60-67,220-227,301-307` (устаревшие строки, указанные CHECK); `.pdca/365-366-r2/items/T365/rv3/measure/summary.csv:2-24` (измерительные значения/статусы, как указаны CHECK); `.pdca/365-366-r2/items/T365/rv3/evidence/receipt-consistency.md:1-7` (receipt mechanically projected, согласован только с manifest); `.pdca/365-366-r2/items/T365/rv3/logs/evidence-lint-r3.log:1-2` и `.pdca/365-366-r2/items/T365/rv3/logs/inner-loop-manifest-r3.log:1-2` (gate logs содержат команды и `rc=0`; их непустота не подтверждает CSV↔manifest семантическую согласованность).
- **Предотвращение:** создавать manifest predicates, status и значения из измерительного CSV либо выполнять отдельную проверку, которая для каждой требуемой строки сравнивает идентификатор/статус/предикат/ключевые числа с CSV; receipt-проверка должна дополнительно сохранять binding к первичному CSV. Успешные структурные/provenance gates не считать семантическим оракулом. При финальной сверке проверять источник → manifest → receipt, включая статусы и значения; сохранять полные непустые stdout/stderr gate-логи. #365 не переоткрывался и его вердикт здесь не пересматривался.

## 2. Общий вывод

Для повторяемых прогонов требуется раздельная идентичность raw-артефактов по попытке; для структурированных доказательств — проверяемая цепочка от первичного измерения до manifest и receipt. Согласованность только между производными артефактами не доказывает их соответствие первичному источнику.

## 3. Recurrence @ S2/r1/n1 — S1-EVIDENCE-HISTORY

- **Событие:** после зафиксированной меры предотвращения новый прогон снова перезаписал чужие raw-evidence пути: `tests/nextorm.integration.tests/Aot/AotNativeRunTests.cs` записывал результат напрямую в `step1/rv1/attempts/native-run-3.log` и `step1/rv1/oracle.md`. Счётчик попытки S2 остаётся `n=1/3`; это recurrence дефекта процесса, а не новая продуктовая попытка.
- **Первопричина:** мера предотвращения охватывала размещение новых логов в attempt-каталогах, но не инвентаризацию всех существующих писателей, направленных в защищённые ступени. Старый adapter имел hard-coded пути S1; CHECK по S2 не требуется для установления самого факта перезаписи.
- **Эффект:** прежние S1 файлы потеряны/перезаписаны; их текущее содержимое — вывод S2 и не может цитироваться как S1-evidence. Snapshot `.pdca/365-366-r2/items/T366/step1/rv1/snapshot/SHA256SUMS.md` не содержит хэшей ни `attempts/native-run-3.log`, ни `oracle.md`; доказать байтовую идентичность или восстановить исходники по этому snapshot нельзя. Принятие S1 остаётся как было записано; backfill/подмена запрещены.
- **Доказательства:** `.pdca/365-366-r2/items/T366/step2/rv1/attempts/n1/s1-overwrite-incident.md`; полученные от перезаписанного adapter файлы сохранены как `.pdca/365-366-r2/items/T366/step2/rv1/attempts/n1/native-run-produced-by-adapter.log` и `oracle-produced-by-adapter.md`; исторический writer — прежний S1 snapshot `tests/nextorm.integration.tests/Aot/AotNativeRunTests.cs` с жёстко заданными путями (снимок/хэши в `step1/rv1/snapshot/SHA256SUMS.md`); текущая запись и recurrence history — `.pdca/status/T366-rc5-1.md`.
- **Предотвращение:** adapter принимает run-scoped evidence directory, пишет только в него; без заданного параметра использует отдельный случайный каталог `/tmp/opencode/...`, никогда `.pdca` или чужую ступень. До запуска инвентаризировать все output writers в adapter и runner, затем проверить, что только пути текущего `run-id` изменены.
