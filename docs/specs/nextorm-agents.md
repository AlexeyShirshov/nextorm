## 2. Телеметрия: кто и когда вызывался

Источник: `~/.local/share/opencode/opencode.db`, таблица `session_v2` (колонки `agent`, `parent_id`,
`time_created`) + `session_message` для времени последнего сообщения. Учитываются только созданные
child-сессии; вызов, отклонённый permissions до старта, следа не оставляет.

```
select agent, count(*) n, datetime(max(time_updated)/1000,'unixepoch','localtime') last_seen
from session_v2 where agent like 'nextorm-%' group by agent order by last_seen desc;
```

Ключевой факт: **все 16 запусков code-auditor и все 10 запусков design-engineer имеют
parent = `build`**. Ни одного запуска из `pdca-orchestrator`, `pdca-check`, `pdca-planner`.
`nextorm-scout` вызывался из `build` (47), а также из старых `auditor` (12) и `judge` (10).

Стоимость прогона: code-auditor $0.051, design-engineer $0.044, scout $0.031, brains $0.054.
Аргумент «не диспатчим, потому что дорого» данными не подтверждается.

## 3. Механизм PDCA: почему текст встроен в оверлей

Это не вкусовое решение, а следствие прав ролей:

- `~/.config/opencode/agents/pdca-planner.md` — единственная запись в permissions: `"*": deny`.
  У планировщика **нет ни одного инструмента**; он работает только по брифу, который ему передают.
- `pdca-check.md:8-20` — `"*": deny`, чтение только `.pdca/**`, `TestResults/**`,
  `StrykerOutput/**`; в §«Boundaries» (строка 91): «You do not read product code or diffs, edit
  files, or spawn subagents».
- `pdca-orchestrator.md:12-21` — `task` allowlist: `pdca-planner`, `pdca-executor`, `pdca-check`,
  `pdca-escalate`, `pdca-scout`, `pdca-security-auditor`, `docfx-specialist`, `"dotnet-*"`.
  Глобы `nextorm-*` нет.
- Глобальный скилл `pdca-dotnet` проектных агентов не упоминает вовсе.

**Следствие (правило репозитория):** всё, что должны знать роли `pdca-*`, обязано быть **в тексте
оверлея** `nextorm-pdca`. Указатель на `.opencode/agents/*.md` до planner/check не доходит — файл
существует, права прочитать нет. Обратное тоже верно: указатель на файл допустим только для
агентов с реальным доступом на чтение.

**Цена:** инварианты дизайна существуют в двух копиях — в оверлее (inline, обязательно) и в
`nextorm-design-engineer.md` (для интерактивного вызова). В шапку §PLAN оверлея добавлена
инструкция синхронизировать обе копии; дрейф уже наблюдался: 12 инвариантов в списке, «(1–10)» в
формате вывода, «1–7» в агенте.

## 4. Агент против скилла: что реально различается

Скилл не может «диспатчить» другие скиллы: он лишь велит модели загрузить их через `skill`, и тела
лягут в **тот же** контекст, с той же моделью и теми же правами.

| | агент (субагент) | скилл |
|---|---|---|
| Контекст | отдельная сессия; после возврата остаётся только summary | тела скиллов остаются в текущей сессии до компакции |
| Модель | своя, по `# tier` | модель вызывающего |
| Права | принудительные, проверяются харнессом | права вызывающего, ограничение только на словах |
| Изоляция | ревьюер не видит рассуждений автора | наследует контекст и выводы автора |

Размер загружаемого контекста (замер по `skills-deepseek/*/SKILL.md`):

- `nextorm-design-engineer` грузит `dotnet-solid-principles` (22.6 KB) + `type-design-performance`
  (15.5 KB) + `analyzing-dotnet-performance` (12.7 KB) = **≈ 51 KB (~13k токенов)**.
- `nextorm-code-auditor` грузит 4 предзагруженных (`dotnet-csharp-code-smells` 8.0 KB,
  `slopwatch` 8.6 KB, `dotnet-api-surface-validation` 21.8 KB, `api-design` 14.7 KB) = **≈ 53 KB**,
  плюс 5 on-demand ещё **≈ 74 KB** (`dotnet-library-api-compat`, `dotnet-editorconfig`,
  `dotnet-add-analyzers`, `dotnet-api-docs`, `dotnet-csharp-nullable-reference-types`).

В субагенте этот контекст умирает вместе с ним; в скилле он остаётся в основной сессии и
оплачивается на каждом следующем сообщении. При двух-трёх ревью в одной сессии это +30–40k токенов.

## 5. Разбор по агентам

### 5.1 `nextorm-design-engineer`

Смешивает две роли: ревью и применение фиксов (`edit: allow`). Из-за этого главный смысл ограды
пропадает — единственное принудительное ограничение здесь `git commit/push: deny`. Из 163 строк
~30 дублируют инварианты оверлея, ~25 — конвенции AGENTS.md. В цикле недостижим (см. §3).

Варианты:

- **A. Только скилл** `nextorm-design-review` (знание + три загружаемых скилла + формат вывода).
  Агент удаляется. Цена: +13k токенов в основной сессии на каждое ревью, нет ограды, модель
  вызывающего.
- **B. Скилл + тонкий агент** (рекомендация). Знание — в скилле; агент 10–15 строк: «загрузи скилл,
  отревьюй `<target>`, верни находки; файлы не трогай», `edit: deny`. Изоляция и одноразовый
  контекст остаются, дубли исчезают, применение фиксов уходит в `build`/`pdca-executor`.
- **C. Оставить как есть.** Работает, но оставляет 150 строк частичных дублей и агента, чья
  единственная уникальная роль — изоляция — не декларирована.

Открытый вопрос: оставлять ли за агентом право править код (тогда ограда слабая) или сделать его
чистым ревьюером.

### 5.2 `nextorm-code-auditor`

Тот же класс, но защищён сильнее:

- **Принудительная ограда**: `edit: "*": deny`, разрешены ровно два файла —
  `docs/specs/design/API-NAMING-REVIEW.md` и `docs/specs/design/code-smells-review.md`. Скилл
  исполнялся бы с правами `build`, то есть мог бы править `src/**` «по ходу аудита».
- **Постоянный артефакт**: регистры, а не одноразовый отчёт.
- **Реальное использование**: 16 запусков, последний 2026-10-20 (релизный гейт `1.0.9-rc3`).

Проблемы: §CHECK оверлея — 112 строк / 10.8 KB, почти размер агента (вынужденное дублирование,
см. §3); агент и `pdca-executor` оба пишут в регистры — роли разные (вне цикла автор — аудитор, в
цикле автор — executor, заверяет check), но нигде не сказано, кто главный; агент ссылается на
`nextorm-design-engineer` как на применяющего фиксы — ссылка сломается, если того сделать
`edit: deny`.

Предпочтительный разрез тот же, что B: скилл `nextorm-code-audit` (знание: 9 скиллов, две линзы,
работа с регистрами, счётчики suppression/slop, формат вывода, процедура optional-`null`) + тонкий
агент, который сохраняет ограду на два файла.

### 5.3 Уже удалён: `nextorm-performance-analyst`

0 запусков за всю историю стора (с 2026-09-27). Единственное уникальное содержание — triage
«in-memory vs ADO» — перенесено в оверлей. Восстанавливать не нужно; если маршрутизация понадобится
как отдельный шаг, её делает PLAN.

### 5.4 `nextorm-inmemory-perf-analyst`

0 запусков. Кандидат на удаление по тому же основанию, что и triage-роутер, но с оговоркой: он
несёт предметную процедуру (материализаторы, group-by, set operations, `InMemoryBenchmark*`),
которой больше нигде нет. Решение отложено до первого реального in-memory перф-цикла.

### 5.5 `nextorm-brains`

23 запуска в один день (2026-09-28), затем тишина. Роль «слепого арбитра» с урезанными правами
(чтение только evidence и `docs/specs/**`) — единственный агент, где изоляция от кода заявлена
явно. Удалять только если роль больше не нужна; отсутствие запусков само по себе не аргумент.

### 5.6 `nextorm-scout`

69 запусков, последний 2026-10-13 — самый используемый агент. Пересекается с глобальными `scout`
(read-only разведка) и `pdca-scout` (evidence-поток). В оверлее brainstorming указано различие:
`scout` — когда нужна сводка, `nextorm-scout` — когда нужен evidence-файл. Три скаута — цена
когнитивной нагрузки, а не контекстной; разводить их стоит только если начнут путаться.

## 6. Рекомендация (не утверждена)

1. Знание — в скиллы: `nextorm-design-review`, `nextorm-code-audit`.
2. Агенты — тонкие оболочки: изоляция (design-engineer) и ограда на два регистра (code-auditor).
3. Применение фиксов — в `build`/`pdca-executor`, не в ревьюере.
4. Инварианты остаются inline в `nextorm-pdca` — иначе planner/check их не получат (§3).
5. Один писатель регистров на контекст: вне цикла — аудитор, в цикле — executor; зафиксировать это
   в оверлее явно.

## 8. Как перепроверить телеметрию

```bash
sqlite3 ~/.local/share/opencode/opencode.db "
select c.agent, coalesce(p.agent,'(root)') parent, count(*) runs,
       datetime(max(c.time_created)/1000,'unixepoch','localtime') last_run
from session_v2 c left join session_v2 p on p.id = c.parent_id
where c.agent like 'nextorm-%'
group by c.agent, parent order by runs desc;"
```
