# Limitations and out-of-scope features

> nextorm is a query builder with a small explicit DML surface: it generates `SELECT` statements (and parameterised `INSERT ... VALUES`, `INSERT ... SELECT`, key upserts, `MERGE`, `DELETE` and `UPDATE`) and materialises their results, and deliberately leaves change tracking and `SaveChanges` to the caller.

**Prerequisites:** [Provider overview](../providers/overview.md) · [API reference](api-reference.md)

## Overview

This page lists the capabilities that are **not** part of nextorm, with a one-line reason for each.

## Limitations

| Area with limitations | Rationale |
|---|---|
| **DML — remaining restrictions** | **`INSERT ... VALUES`, `INSERT ... SELECT` and key upsert are implemented** ([`CreateInsertBuilder`](../guide/15-insert-statement.md); row return through `RETURNING`/`OUTPUT` on PostgreSQL, SQLite and SQL Server, batched rows unordered; a server-side source hoists its CTEs before `INSERT` and rejects runtime `SqlFunctions.Parameter` placeholders). PostgreSQL also supports **data-modifying CTEs** (`With(name, insert)`/`With(name, update)`/`With(name, delete)` for single-table and join/multi-table `INSERT`/`UPDATE`/`DELETE` bodies, each requiring a `RETURNING` projection → [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1), [data-modifying CTE](../guide/15-insert-statement.md#data-modifying-cte-postgresql)). **Upsert** ([`CreateMergeBuilder`](xref:NextORM.Core.DataContextExtensions.CreateMergeBuilder``1(NextORM.Core.IDataContext,System.Action{NextORM.Core.EntityMetadataBuilder{``0}})) → [`MergeBuilder<T>`](xref:NextORM.Core.MergeBuilder`1), [upsert](../guide/19-merge-statement.md#upsert-key-merge)) renders the provider's native form — `INSERT ... ON CONFLICT ... DO UPDATE` (PostgreSQL, SQLite), `INSERT ... ON DUPLICATE KEY UPDATE` (MySQL, MariaDB) or `MERGE ... USING (VALUES ...)` (SQL Server); ClickHouse rejects it. Under an active global query filter the full `MERGE` (SQL Server, PostgreSQL 15+) isolates the target in the `ON` predicate so a hidden row is never matched, updated or deleted, while the `ON CONFLICT` / `ON DUPLICATE KEY` key upserts **refuse** with `NotSupportedException` (fail closed; `IgnoreFilters()` restores them). A source key colliding with a hidden target row still surfaces the provider's native unique-constraint error from the insert arm — for whichever unique index it hits, not only the merge key (an existence oracle; a composite key including the filter column mitigates the primary/merge key only), while an update-only or delete-only merge is a silent no-op — and the source-value pre-check stays a separate TOCTOU read (`QueryFilterValidator`) that validates source values, not target rows (see [Write-target isolation](../advanced/query-filters.md#write-target-isolation)). **`DELETE`** ([`CreateDeleteBuilder`](../guide/16-delete-statement.md) → [`DeleteBuilder<T>`](xref:NextORM.Core.DeleteBuilder`1), `Delete<T>(entity)`, [`delete`](../guide/16-delete-statement.md)) renders a parameterised `DELETE FROM <table> [WHERE ...]` — by predicate, by the entity's declared key, or the whole table with an explicit `All()`; `Returning()` returns the removed rows on PostgreSQL/SQLite (`RETURNING`) and SQL Server (`OUTPUT`), `CreateTruncateBuilder<T>()` renders `TRUNCATE TABLE`, ClickHouse deletes through `ALTER TABLE ... DELETE ... SETTINGS mutations_sync = 1`. A multi-table `DELETE` based on an INNER join ([`From<T>().Join(...).Delete()`](../guide/16-delete-statement.md#delete-based-on-a-join)) is supported on PostgreSQL, SQL Server, MySQL and MariaDB, and rejected by SQLite and ClickHouse. **`UPDATE`** ([`CreateUpdateBuilder`](../guide/17-update-statement.md) → [`UpdateBuilder<T>`](xref:NextORM.Core.UpdateBuilder`1), `Update<T>(entity)`) renders a parameterised `UPDATE <table> SET ... [WHERE ...]` on PostgreSQL, SQL Server, SQLite, MySQL and MariaDB; ClickHouse updates through `ALTER TABLE ... UPDATE ... SETTINGS mutations_sync = 1` (synchronous, but reports no affected-row count); `Returning()` returns the updated rows on PostgreSQL/SQLite (`RETURNING`) and SQL Server (`OUTPUT`), and on MariaDB only when an explicit server version 13.0+ is configured. A multi-table `UPDATE` based on an INNER join ([`From<T>().Join(...).CreateUpdateJoinBuilder()`](../guide/17-update-statement.md#updating-from-a-join)) is supported on PostgreSQL/SQLite (`FROM`), SQL Server and MySQL/MariaDB, and rejected by ClickHouse. Full `MERGE` with `WHEN MATCHED`/`WHEN NOT MATCHED`/`WHEN NOT MATCHED BY SOURCE` branches and `MERGE ... RETURNING`/`OUTPUT` are available on SQL Server and PostgreSQL 15+ and rejected by the other providers. There is no change tracking and no `SaveChanges`: writes are explicit commands. A query can be materialized into a persistent table with `CREATE TABLE ... AS SELECT` ([`ToTempTable`/`ToTable`](../guide/18-create-table-as.md), `ToTempTable(name)`/`ToTable(name)`) on PostgreSQL, SQLite, MySQL, MariaDB, SQL Server and ClickHouse: SQL Server renders `SELECT ... INTO` (a session-scoped table is `ToTable("#name")`) and ClickHouse renders `CREATE TABLE ... ENGINE = MergeTree ... AS SELECT`. The temporary `ToTempTable` form is available on PostgreSQL, SQLite, MySQL and MariaDB only — SQL Server has no `CREATE TEMPORARY TABLE ... AS SELECT` (use `#name`) and ClickHouse has no temporary `AS SELECT`. A side-effecting statement and a following read can be sent as a single batch with the general `BatchBuilder` (`CreateTempTable`/`CreateTable` materialisations and `Insert`/`Update`/`Delete`/`Truncate` DML steps before one reading query), as one round trip on one session, on PostgreSQL, SQL Server, MySQL, MariaDB and SQLite; ClickHouse rejects a batch with `NotSupportedException`, and a DML step may not request returned rows (`Returning()` produces a different builder type). SQL Server sends the batch as one `;`-joined command rather than `SqlBatch`, which runs each command in its own scope, so a `#temp` stays visible across the statements. Batch execution is not routed through the query interceptors: their events carry a `DbCommand`, while a `DbBatch` command is a `DbBatchCommand`. |
| **Server-version-gated syntax** | Two capabilities depend on the server version and are gated by an **explicitly configured version** — nextorm never probes the live server. PostgreSQL's aggregate `FILTER (WHERE ...)` needs 9.4+; a dialect pinned below that rejects it with `NotSupportedException`, while an unset version assumes 9.4+ and enables it. MariaDB's `UPDATE ... RETURNING` is enabled only at an explicit 13.0+ ([`SupportsUpdateReturning`](xref:NextORM.Core.ISqlDialect.SupportsUpdateReturning)); unset or older rejects it with `NotSupportedException`, and insert/delete `RETURNING` and `ANY_VALUE` (13.2) are unchanged. PostgreSQL enforces one immutable server version per **concrete context type** for the process lifetime, because `FILTER` affects the cached `SELECT` SQL; a different version for the same concrete type throws `InvalidOperationException`, so a process that needs several PostgreSQL versions declares a distinct context subclass per version. MariaDB imposes **no such guard**: different versions may be used on the same context type because its gated operation (`UPDATE ... RETURNING`) is a mutation whose SQL is not plan-cached. See [PostgreSQL provider](../providers/postgres.md#server-version) and [MariaDB provider](../providers/mariadb.md#server-version). |
| **`Prepare()` / plan cache for DML** | Every mutation renders and executes one command per call — mutating builders are deliberately not prepared or plan-cached. Optimisation in nextorm targets read-only queries only (explicit `Prepare`, the implicit plan cache, benchmarks). |
| **Bulk-copy flags outside SQL Server** | `BulkInsertOptions.CheckConstraints`/`TableLock`/`KeepNulls`/`FireTriggers` map to `SqlBulkCopyOptions` on the SQL Server native `SqlBulkCopy` path. The PostgreSQL `COPY` path and the portable `INSERT ... VALUES` path (MySQL/MariaDB/SQLite/ClickHouse, and SQL Server when `Returning*` or `KeepIdentity` forces the portable path) reject a requested flag with `NotSupportedException` instead of ignoring it. ClickHouse `MaxDegreeOfParallelism`/`WithoutSession` are not exposed: `ClickHouse.Driver` 1.4.0's `ClickHouseBulkCopy` is obsolete and the non-obsolete `ClickHouseClient.InsertBinaryAsync` needs its own client, while the session is a connection-string setting (`UseSession`), not a per-write option. `UseInternalTransaction` is deliberately never set (nextorm opens no implicit transaction). See [Bulk insert](../guide/20-bulk-insert.md#sql-server-bulk-copy-options). |
| **Implicit navigation queries / joins from navigation properties** | A relationship is declared explicitly with `HasMany`/`HasOne` or [`RelationshipAttribute`](xref:NextORM.Core.RelationshipAttribute), and [`JoinInto`](xref:NextORM.Core.EntityBuilder`1) loads a child collection or reference in a single denormalized round trip — one-to-many, one-to-one and, through an explicit junction (`HasManyThrough`/`JoinOptions.ManyToMany`), many-to-many; LEFT by default, with an INNER overload and an explicit-key fallback (see [Relationships](relationships.md)). **Implicit navigation queries are supported for declared relationships**: a reference navigation is used as a scalar chain or a presence check and a collection navigation exposes exactly four direct terminals (`Any`/`Count`/`LongCount`/the `Count` property), expanded server-side as a correlated subquery or a `LEFT JOIN`; the collection navigation can be adapted with `AsEntityBuilder<T>` (see [Implicit navigation queries](../guide/29-implicit-navigation.md)). There is still no convention over foreign keys and no implicit join inference; adapter LINQ composition, a bare reference-adapter projection and predicate overloads fail closed. A multi-hop presence check (`a.Parent.Parent == null`) and the reference adapter (`Any`/`Count`/`LongCount` ≡ `nav != null`) are supported on every SQL provider; a collection reached through a reference is supported on every SQL provider except ClickHouse, which cannot correlate a subquery on a joined source and rejects the shape with `NotSupportedException`; `Count`/the `Count` property are a checked `int` (the 64-bit count is narrowed only at materialisation and throws `OverflowException` out of range), while `LongCount` is 64-bit end to end. The ClickHouse reference→collection gate is an **accepted provider limitation** (not a defect), and navigation over a temp-table/TVP source is **deferred**: a lazy temp-table read source is an untyped `TableAlias` with no navigation surface, so a navigation member cannot be read over it (the trigger is a navigation source combined with a temp-table/TVP path); navigation declared before the temp-table boundary is still expanded into the materialising `CREATE TEMPORARY TABLE ... AS SELECT`. `JoinInto` rejects with `NotSupportedException` a composite relationship or junction key, a many-to-many relationship under `AsSingleQuery`, an undeclared relationship (unless the explicit-key overload is used), a derived (`As`) or joined projection source, a join kind other than `Inner`/`Left`, mismatched explicit key types and more than seven child collections; mixing `JoinInto` with any other join on the same builder is rejected (declare `JoinInto` on a plain entity source only), and a ClickHouse `j => j.WithStrictness(Any)` option on a `JoinInto` truncates the loaded collection to one child while the other modifiers (`All`, `Asof`, `Global`) pass through; relationship metadata fails closed on an unmapped foreign key, a keyless principal or an FK/principal-key type mismatch. Explicit joins remain the general surface: [`Join`](xref:NextORM.Core.EntityBuilder`1.Join``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`LeftJoin`](xref:NextORM.Core.EntityBuilder`1.LeftJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`RightJoin`](xref:NextORM.Core.EntityBuilder`1.RightJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`FullJoin`](xref:NextORM.Core.EntityBuilder`1.FullJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`CrossJoin`](xref:NextORM.Core.EntityBuilder`1.CrossJoin``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) (see [Joins](../guide/02-joins.md)). **Deduplication needs a mapped key**: parent dedup and child identity fall back to reference identity when the respective side declares no key, and on a SQL provider every row is a fresh instance, so repeated/cartesian rows then survive — give the parent and child a mapped key (`[Key]`/`Key()`/the `Id` convention) or use the explicit-key overload with a keyed child. `IRelationshipMetadata.Inverse` is resolved lazily on its **first read** and cached, so register both sides before reading it. |
| **Selecting a joined entity as a whole** | After a join the accumulated projection is positional (`Item1`..`Item8`, one item per source in join order) and only its columns can be selected (`Select(p => p.Item1.Id)`); a projection member that is the entity itself (`Select(p => p.Item1)`) is not a column and is rejected. Give the sides semantic names by projecting into a named type (`Select(p => new { Order = p.Item1.Id, Customer = p.Item2.RequiredString })`); see [Joins](../guide/02-joins.md#addressing-the-projection). |
| **Correlated `APPLY` / `LATERAL` source** | [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) accept a lambda that receives the left-hand row, so the applied source can reference the outer row on a lateral-capable provider (SQL Server `CROSS/OUTER APPLY`, PostgreSQL/MySQL/MariaDB `... LATERAL`). Dialects without a lateral source (SQLite, ClickHouse) reject `APPLY` outright. The correlation lambda cannot reference a join projection — apply it to a single-entity source. |
| **[`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) / [`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) on SQL providers** | [`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) throw `NotSupportedException`; the explicit [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) join surface covers the correlated equivalent (see [Joins](../guide/02-joins.md)). |
| **Correlated scalar terminals (`First`/`Single` and their `*OrDefault` forms)** | A missing row yields `null` for a nullable projection and `default` (for example `0`) for a non-nullable value projection when the terminal is `FirstOrDefault`/`SingleOrDefault`. `First`/`Single` on a non-nullable value projection throw when no row matches. `Single`/`SingleOrDefault` over more than one row throw on every provider whose scalar subqueries enforce cardinality (PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse); SQLite does not enforce it, so a numeric `Single`/`SingleOrDefault` over more than one row raises a database error through a rendered `case when count(*) > 1 then <numeric overflow> else value end` guard, and a non-numeric projection is rejected with `NotSupportedException`. |
| **Locking table hints outside SQL Server** | The locking table hints (`WithTableHint("nolock")` → `WITH (NOLOCK)`) are supported on SQL Server only, on the query's `FROM` table and, through the per-join `JoinOptions.WithJoinTableHint` passed to a join, on that join; the native index hints of MySQL/MariaDB (`USE`/`FORCE`/`IGNORE INDEX`), SQLite (`INDEXED BY`/`NOT INDEXED`) and SQL Server (`WITH (INDEX(...))`) are a separate surface ([`WithIndex`](../guide/13-query-hints.md#index-hints), [`ISqlDialect.IndexHints`](xref:NextORM.Core.ISqlDialect.IndexHints)). Statement-level hints are wired on SQL Server (`OPTION (...)`), PostgreSQL and MySQL/MariaDB (`/*+ ... */`); SQLite and ClickHouse reject `Hint(...)` with `NotSupportedException`. Join (`JoinOptions.WithJoinHint`), subquery (`FromOptions.WithSubQueryHint`) and tables-in-scope (`WithTablesInScopeHint`) hints follow the same gates: SQL Server renders the join hint inside `JOIN` and the scope hint as `WITH (...)` on every table (it rejects a subquery hint, because T-SQL cannot append one to a subselect), PostgreSQL/MySQL/MariaDB fold them into the inline `/*+ ... */`, and SQLite/ClickHouse reject them (see [Query hints](../guide/13-query-hints.md)). |
| **Upper-case SQL keywords — tuple/row constructors stay provider-canonical** | `DataContextBuilder.UseKeywordCase(KeywordCase.Upper)`, `EntityBuilder<TEntity>.WithKeywordCase(...)` and `QueryCommand<T>.WithKeywordCase(...)` case the keywords emitted by the core statement builder (`select`, `from`, `where`, `join`, `group by`, `order by`, `with`, `insert`, `values`, ...), by the expression translators (`and`/`or`/`not`, `case`/`when`/`then`/`else`/`end`, `cast(... as ...)`, `is [not] null`, `like`, `in`, `exists`, `over` and window frames), by the common dialect clauses (aliases `as`, paging `limit`/`offset`/`fetch`/`top`, `with [recursive]`, the join keywords, table/index hints) and by every dialect-rendered clause: `for json`/`for xml`, the grouping modifiers (`rollup`/`cube`/`grouping sets`/`with totals`), `for system_time ...`, `apply`, `settings`, `final`, `sample`, the DML `returning`/`output`, the query-hint `option (...)`/`option (maxrecursion ...)` and the capability clauses (`for update`/`for share`, `tablesample ... repeatable`, `limit by`, `array join`, `distinct on`, `pivot`/`unpivot`). The row/tuple constructors `ROW(...)` (PostgreSQL) and `tuple(...)` (ClickHouse) are treated as function-like constructors and keep the provider's canonical spelling in both cases (consistent with the function-name policy). Identifiers, string literals, function names, type names and raw SQL are never affected, and `KeywordCase.Lower` (the default) is byte-for-byte the historical output. |
| **Server-side array/JSON element access (`x[i]`)** | Only a captured (closed-over) collection indexed inside the query is supported ([captured collection lookup](../guide/01-filtering-where.md#captured-collection-lookup-dictcolumn)): a constant key folds to a parameter and a column key renders a portable `CASE`. Element access on a server-side array/JSON column or an array-returning expression (`groupArray(x)[0]`, `array_agg(x)[1]`, `json['k']`) has no portable SQL form and throws `NotSupportedException` (a custom indexer likewise) instead of binding the whole collection. The native forms differ (`arr[i]` on PostgreSQL, `arrayElement(arr, i)` on ClickHouse, JSON paths elsewhere), so they would need a separate dialect hook. |
| **ClickHouse native `JSON` column type** | The native-JSON functions (`JSONAllPaths`/`JSONAllPathsWithTypes`/`toJSONString`, alongside `JSON_VALUE`/`JSON_QUERY`/`JSON_EXISTS`) are wired on `ClickHouseFunctions` and gated by [`SupportsJsonExtract`](xref:NextORM.Core.ISqlDialect.SupportsJsonExtract), a native `JSON` *column* maps a bare `System.Text.Json.Nodes.JsonObject` property for both read and parameter (`ClickHouse.Driver` surfaces `JSON` as `JsonObject`); the projection must be a named shape (`Select(x => new { x.Doc })` or a DTO) because a bare top-level scalar `Select(x => x.Doc)` is not handled by the core projection classifier. An empty `{}` stays a non-null object and SQL `NULL` becomes `null`; `[JsonColumn]` `Native`, bare `JsonDocument`/`JsonElement`, a bare `string` and the legacy `Object('json')` alias are not supported. See [JSON support](../guide/14-json.md#map-a-clr-object-to-a-native-json-column). |
| **`untuple` (ClickHouse)** | `untuple(tuple)` is not mapped: it expands a tuple into several result columns, which has no single scalar CLR shape in a projection. Project the `Tuple(...)` as `System.Tuple<...>` and read its elements with `tupleElement`/`System.Tuple<...>.ItemN` instead. |
| **Row-value (tuple) surface: remaining restrictions** | Row constructs (`System.Tuple.Create(a, b)` / `new Tuple<T1, T2>(a, b)`) are supported as **direct `==`/`!=` comparison operands** in predicates (`WHERE`/`HAVING`/`JOIN ON`): PostgreSQL renders `ROW(a, b)` and `(row).fN`, ClickHouse `tuple(a, b)`/`tupleElement`, and MySQL/MariaDB/SQLite the flat ANSI `(a, b)` (for example `(a, b) = (c, d)`), which those engines accept as a row-comparison operand. An inline constructor's `.ItemN` folds to the scalar argument everywhere. On MySQL/MariaDB/SQLite a constructor in `Select`/`ORDER BY`/`GROUP BY` or as a function argument, and any server-side `.ItemN`, throws `NotSupportedException` at preparation (naming the provider); SQL Server rejects constructors. `<`/`>`/`<=`/`>=` and relational `ValueTuple` operands are inexpressible in C#/expression trees (a language boundary, not a product limitation). Still open: tuple `IN`/`Contains` over a list of CLR tuples ([#193](https://github.com/AlexeyShirshov/nextorm/issues/193)) and materialising a raw `ROW(...)`/row value back into `System.Tuple<...>` ([#194](https://github.com/AlexeyShirshov/nextorm/issues/194); on PostgreSQL Npgsql needs `EnableRecords()`/`MapComposite`). See [Scalar functions](../scalar-functions/index.md). |
| **Binding the element of several `ARRAY JOIN` expressions at once (ClickHouse)** | [`ArrayJoinElement`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.ArrayJoinElement``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,System.Collections.Generic.IEnumerable{``1}}}))/[`LeftArrayJoinElement`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.LeftArrayJoinElement``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,System.Collections.Generic.IEnumerable{``1}}})) bind the element of exactly one array expression to `p.Element`; a second call, a call on a joined query, or a call after `Where`/`Having` throws `InvalidOperationException`. When you array-join several arrays and do not need the typed element, use [`ArrayJoin`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.ArrayJoin``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,``1}}))/[`LeftArrayJoin`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.LeftArrayJoin``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,``1}})), which accept several expressions (see [ClickHouse provider](../providers/clickhouse.md)); these array-join members are extension methods in `NextORM.ClickHouse` (`using NextORM.ClickHouse;`). |
| **ClickHouse aggregate-function state (`-State`/`-Merge`, `runningAccumulate`)** | `uniqState`/`sumState`/`countState`/… return an opaque `AggregateFunction(...)` value, which nextorm does not model: `ClickHouse.Driver` 1.4.0 throws `AggregateFunctionException` from `FrameworkType`/`Read`/`Write`, so such a column cannot be materialised into or passed as a CLR value (the driver message points at the matching `-Merge`). `uniqMerge(uniqState(x))` is itself illegal (`ILLEGAL_AGGREGATION`), so a `-Merge` needs a state produced server-side (a subquery or a state table), and `runningAccumulate` is deprecated in ClickHouse 25.8 (`DEPRECATED_FUNCTION`, needs `allow_deprecated_error_prone_window_functions`). |
| **String formatting and collation beyond the documented subset** | `string.Format`/interpolation/`value.ToString(format)` translate only the culture-invariant subset: `N`/`F`/`D`/`X` numbers (per provider) and the `yyyy yy MM dd HH mm ss` date tokens with the separators `- / . : T` and space. Any other specifier, and any culture other than `CultureInfo.InvariantCulture`, throws `NotSupportedException`. The ordinal `StringComparison` overloads accept only `Ordinal`/`OrdinalIgnoreCase` (`InvariantCulture`/`CurrentCulture` throw); SQLite additionally rejects the case-sensitive ordinal `Contains`/`StartsWith`/`EndsWith` because its `LIKE` is always case-insensitive regardless of collation ([`SupportsOrdinalLike`](xref:NextORM.Core.ISqlDialect.SupportsOrdinalLike)). See [Ordinal comparison and collation](../scalar-functions/01-string-functions.md#ordinal-comparison-and-collation). |
| **Column-level collation on ClickHouse and DDL** | A collation declared on a mapped property ([`CollationAttribute`](xref:NextORM.Core.CollationAttribute) / [`EntityPropertyBuilder<T>.Collation`](xref:NextORM.Core.EntityPropertyBuilder`1.Collation(System.String))) is applied to the column in collation-sensitive query operations on the providers that support per-expression collation ([`SupportsCollation`](xref:NextORM.Core.ISqlDialect.SupportsCollation)): PostgreSQL, SQL Server, MySQL/MariaDB and SQLite. ClickHouse has no `COLLATE` clause and rejects a collated column with `NotSupportedException`. nextorm never emits a collation in a column definition (its only DDL is `CREATE TABLE ... AS SELECT`, which carries no explicit column collation), so the declaration describes the collation of an **existing** column and does not create it. See [Column collation](../scalar-functions/01-string-functions.md#column-collation). |
| **Regular expressions** | A constant-pattern `Regex.IsMatch`/`Regex.Replace` translates on PostgreSQL, MySQL/MariaDB, ClickHouse, SQLite and SQL Server 2025+ ([`SupportsRegex`](xref:NextORM.Core.ISqlDialect.SupportsRegex)); on SQL Server the match renders as `REGEXP_LIKE`, which requires database compatibility level 170, while `REGEXP_REPLACE` is available at every level — SQL Server 2022 and earlier have no `REGEXP_*` functions. The pattern, replacement and options must be compile-time constants, only `RegexOptions.IgnoreCase` maps, and the pattern executes on the provider's own engine (POSIX/ICU/PCRE/RE2/.NET), so complex patterns (lookaround, backreferences) and replacement group references are not portable. See [Regular expressions](../scalar-functions/01-string-functions.md#regular-expressions). |
| **Stored procedures (dedicated API) and dynamic SQL** | nextorm builds `SELECT` statements from LINQ, and assembling SQL at runtime is outside the builder surface. A stored procedure can be invoked either as raw `EXEC`/`CALL` text through `ExecuteRaw`, or by name through the dedicated `CommandType.StoredProcedure` API [`ExecuteProcedure`](xref:NextORM.Core.IRawCommandExecutor.ExecuteProcedure(System.String,System.Collections.Generic.IReadOnlyList{NextORM.Core.ProcedureParameter}))/`ExecuteProcedureAsync`, including parameters, output parameters, a return value (SQL Server) and several result sets (see [Raw SQL](../guide/12-raw-sql.md#stored-procedures-executeprocedure)). SQL Server, PostgreSQL and MySQL/MariaDB execute procedures; SQLite and ClickHouse throw `NotSupportedException`. Raw SQL for a whole query remains available — [`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)). |
| **Multiple result sets from a batch: eager and sequential** | **Supported** on the `SupportsBatch` providers (PostgreSQL, SQL Server, MySQL, MariaDB, SQLite): `AddQuery<TResult>` adds any number of result-bearing queries and `Execute()`/`ExecuteAsync()` run the batch once and return a `BatchResult` — the result is directly enumerable: `foreach`/`await foreach` yields one `ResultSet` cursor per set, each exposing `Index`/`FieldCount`/`ColumnNames` and reading its own set with a per-set `Read<T>()`/`ReadAsync<T>()`, which is what lets sets with different element types be read; the positional `Read<TResult>()` path remains for a same-`T` sequence, each set read once and type-checked, and the two traversal modes cannot be mixed (see [Executing statements in one batch](../guide/23-sql-batch.md#multiple-result-sets)). The sets are buffered eagerly, so there is no streaming and no random access, and only the single-result `BatchQuery<TResult>` terminal streams (`ToAsyncEnumerable`); both `BatchQuery<TResult>.ToSql()` (single result) and `BatchBuilder.ToSql()` (multi-result, requires at least one result step) render the batch without executing it. ClickHouse rejects batches. Raw commands are covered separately: `ProcedureResult` follows the same cursor model over its live reader — enumerate it (`foreach`/`await foreach`) or call `Read<T>()` once per set, in order (see [Raw SQL](../guide/12-raw-sql.md#multiple-result-sets)). |
| **External sources (`OPENROWSET`/`OPENQUERY`, linked servers)** | Out of scope; the connection's own schema is queried. The per-query `WithServer`/`WithDatabase` overrides only change the **name** rendered in `FROM` (up to SQL Server's four-part `server.database.schema.table`); opening a linked server or a cross-database connection remains the caller's/DBA's concern. |
| **Per-query source override beyond the provider's levels** | A dialect renders only the levels it can express: PostgreSQL a schema, SQLite a schema/attached database, MySQL/MariaDB/ClickHouse a database, SQL Server up to the four-part name. `WithDatabase`/`WithServer` on a provider that did not opt into the level is rejected with `NotSupportedException` rather than silently dropped, `WithTableExpression` (raw SQL as the table source) cannot be combined with the name qualifiers. See [Per-query source overrides](../querying/02-query-sources.md#per-query-source-overrides). |
| **ClickHouse `format`/`merge`/`input` table functions** | Not pre-declared on `SqlFunctions.ClickHouse`: `format` and `merge` infer their schema at runtime and `input` is valid only in `INSERT ... SELECT`, so none has a caller-declared `TRow` shape. Use `FromSql` or a user-declared `[SqlTableFunction]` wrapper. The free-form ClickHouse `values` and PostgreSQL `jsonb_to_record`/`jsonb_to_recordset` **are** exposed through a caller-declared `TRow` schema ([Dynamic result schema](../guide/11-table-valued-functions.md#dynamic-result-schema)). |
| **PostgreSQL `json_populate_record(set)`** | The `json_populate_record`/`json_populate_recordset` variants populate a caller-supplied **base record type** instead of a free-form column list, so they need a mapped composite per provider; only the free-form `jsonb_to_record`/`jsonb_to_recordset` are exposed. See [Dynamic record schema](../guide/provider-specific/postgresql.md#dynamic-record-schema). |
| **DDL / administrative commands** | Only a query-materialisation subset is generated: `CREATE [TEMPORARY] TABLE ... AS SELECT` ([`ToTempTable`/`ToTable`](../guide/18-create-table-as.md), or the lazy `AsTempTable`; SQL Server renders `SELECT ... INTO`), `DROP TABLE IF EXISTS` (via `CreateTableOptions.DropExisting`) and `TRUNCATE TABLE` ([`CreateTruncateBuilder<T>`](../guide/16-delete-statement.md#truncating-a-table)). Arbitrary `CREATE`/`ALTER`/`DROP` (indexes, constraints, column changes), `OPTIMIZE`, `RENAME`, table variables and other administrative statements are not generated; use a batch `Raw(sql)` step, `ExecuteRaw`, or your own commands. |
| **SQLite FTS index maintenance** | SQLite has its own FTS3/FTS4/FTS5 **query** surface (`SqlFunctions.Sqlite`: `Match`, FTS5 `FTS5bm25`/`Highlight`/`Snippet`/`Rank`, FTS3/4 helpers and the FTS5 table-valued `MatchTable` `FROM` source), but nextorm does not generate the FTS5 maintenance/control statements (`AutoMerge`, `CrisisMerge`, `Merge`, `Optimize`, `Rebuild`, `IntegrityCheck`) — deferred to [#195](https://github.com/AlexeyShirshov/nextorm/issues/195)/[#196](https://github.com/AlexeyShirshov/nextorm/issues/196); create and tune the virtual table with raw SQL. FTS3/4 `Rank` expects a connection-registered `rank` UDF. |
| **Unit of work, `SaveChanges` and change tracking / CDC** | nextorm does not own a unit of work or track entities, and there is no `SaveChanges`. It can run its queries inside a transaction, however: start one with [`ITransactionManager`](xref:NextORM.Core.ITransactionManager) or enlist in an externally owned one (EF Core, Dapper, raw ADO.NET) with `UseTransaction`. Writes remain explicit `INSERT`/`UPDATE`/`DELETE`/`MERGE` commands; concurrency is checked explicitly (token in `WHERE` + affected-row count) and a change-tracking layer can be built on top — see [Optimistic concurrency and change tracking](../guide/24-optimistic-concurrency.md). ClickHouse has no transaction and rejects it. |
| **EF Core integration: `SaveChanges` bridge and per-context mapping** | The [`nextorm.entityframeworkcore`](integration-efcore.md) package runs nextorm reads and writes over an existing EF Core `DbContext` connection and current transaction and maps entities from the EF `IModel`; nextorm reads and writes executed there participate in that shared transaction (verified on PostgreSQL, SQL Server and MySQL), but there is no change-tracking sync and no `SaveChanges` bridge: nextorm DML bypasses EF's change tracker, so rows it wrote are unknown to the tracker. The mapping is registered in nextorm's process-wide metadata cache keyed by `Type`, so **at most one mapping per CLR type exists per process** — two `DbContext`s that map the same type differently cannot both be served: the second, different registration throws `InvalidOperationException`. A `SaveChanges`/change-tracking bridge is explicitly out of scope. The non-relational EF `InMemory` provider has no `DbConnection` and is not supported. Global query filters declared on the EF model **are** imported into nextorm's filter pipeline for the supported relational adapters; a bridge-bound context whose imported filter metadata is later dropped (`DataContextCache.Clear()` or a sliding-expiration eviction) fails closed with the documented `InvalidOperationException` on the next query or DML build instead of running unfiltered, and recovers by creating/rebinding a context through the bridge. The ClickHouse no-EF-adapter slice and the MariaDB-specific shared-connection certification remain open units in `1.0.9-b`. See [EF Core integration](integration-efcore.md) and [EF Core query-filter bridge](ef-core-query-filters.md). |
| **Command timeout on ClickHouse** | `UseCommandTimeout`/`WithCommandTimeout` set the ADO.NET `DbCommand.CommandTimeout` on every SQL provider, but `ClickHouse.Driver` 1.4.0 does not map it to the HTTP request — the connection `Timeout` (default two minutes) bounds the request instead — so the value has no effect there. A per-query override applies to read queries; DML commands and batches use the context default. |
| **PostgreSQL `oid` and other `uint`-backed system types through a `uint` parameter** | Npgsql maps `oid` and other system types backed by `uint` (for example `cid`) to CLR `uint`, so reading one into a `uint` property works, but nextorm binds a `uint` parameter as `xid`, and `oid = xid` has no operator (SQLSTATE 42883) — comparing or writing such a target through a `uint` parameter therefore fails. Compare through a `bigint` cast (`Where(e => (long)e.Oid == (long)value)`) or run raw SQL with a `bigint` parameter and an explicit `::oid` cast. See [PostgreSQL provider](../guide/provider-specific/postgresql.md). |
| **Interceptors beyond the command/connection lifecycle** | The shipped surface is [`IQueryInterceptor`](xref:NextORM.Core.IQueryInterceptor) and [`IConnectionInterceptor`](xref:NextORM.Core.IConnectionInterceptor) (see [Interceptors](../infrastructure/03-interceptors.md)). There is no exception interceptor - translate a provider exception with a `try`/`catch` around the terminal call. An interceptor must not change `CommandText` (the command belongs to a cached plan). Global query filters are a separate layer. |
| **Dynamic columns - write side** | The **read side** is implemented: a writable property assignable from `Dictionary<string, object?>` marked with [`DynamicColumnsAttribute`](xref:NextORM.Core.DynamicColumnsAttribute) (or the fluent `EntityPropertyBuilder<T>.DynamicColumnsStore`) receives the row's unmapped columns when the entity is queried as a whole - the statement renders `select <mapped>, *` (``select t1.<mapped>, `t1`.*`` on MySQL/MariaDB, whose dialect alias-qualifies the star via `RequiresQualifiedSelectStar`) and the store is materialised from the result set on every SQL provider (see [Dynamic columns](../guide/27-dynamic-columns.md)). **The write side is implemented for `INSERT`, `UPDATE` and `MERGE`**: the store's dictionary keys are rendered as physical columns and their values as bound parameters. Keys are ordinal-sorted, so the column order is deterministic; every dynamic key is identifier-quoted with the dialect's quoting even when the global identifier-quoting option (`UseQuotedIdentifiers`) is off, and the naming convention is skipped (the key is used as the physical column name); an empty key or a key containing a NUL character is rejected. A present key with a `null` value writes SQL `NULL`, while a missing key is omitted - on `INSERT` the column default applies, on `UPDATE`/`MERGE` the column is left unchanged (you cannot clear a column by omitting its key); a multi-row `INSERT` requires the same key set on every row, and in `MERGE` dynamic columns go to the source/`INSERT`/`SET`, never into `ON`. Values bind from the runtime CLR value with no per-key `IPropertyValueConverter`/JSON (pass-through), mirroring read-side materialisation. **Remaining restrictions:** no per-key converters or JSON columns; nextorm tracks no changes; a column cannot be cleared by omission; there is no key allow-list (keys are identifier-quoted and validated instead). The read side is still limited to a single physical source (a query with joins rejects the store with `NotSupportedException`) and to an entity queried as a whole (an explicit projection does not collect it). On SQL reads the store is created even when it starts `null`; on write a `null` or empty store contributes no dynamic columns. The store-bearing entity must be a reference type: a value-type (`struct`) entity that declares a store is rejected with `InvalidOperationException` when its metadata is built, rather than boxing silently - use a reference type. |
| **Dynamic columns - parameterless constructor** | An entity that declares a dynamic-columns store must be a reference type with a public parameterless constructor. The store is materialised with member-init (each mapped column is bound by name and the store receives the star fields), so the regular longest-constructor strategy does not apply to it; a store-bearing entity without a public parameterless constructor is rejected during preparation with a `QueryPreparationException`. The same store is read by the write side. |
| **Value converters to `TimeSpan` in table-valued parameters on providers without a native duration type** | A value converter owns its provider representation in the general write seam (a converted `TimeSpan` is bound as-is), but a table parameter has no native duration binding on SQL Server, SQLite and ClickHouse. A mapped-entity column whose converter targets `TimeSpan` is therefore rejected with `NotSupportedException` when the parameter's columns are built, before any row is consumed; bind the converted value as its integer storage instead. PostgreSQL (`interval`) and MySQL/MariaDB (`TIME`) keep the converted `TimeSpan`. |
| **Streaming a LOB (`ToStream`/`ToTextReader`) outside PostgreSQL, SQL Server, SQLite** | The streaming terminals return a `Stream`/`TextReader` that owns the `DbDataReader` and a per-call `DbCommand` until disposed; in this release they are implemented for PostgreSQL, SQL Server and SQLite. On SQLite the query source must expose SQLite `rowid` (a normal rowid table): a `view` or `WITHOUT ROWID` table fails closed with the raw `Microsoft.Data.Sqlite.SqliteException: no such column: rowid`, with no buffered fallback. The locator can only be appended to a single-source projection, so joins/several sources, `DISTINCT`/`DISTINCT ON`, `UNION`, `GROUP BY` and aggregates are not supported (they may fail with a driver error), and on a single-column projection a raw `WithSql` override is rejected with `NotSupportedException` (a `rowid` locator cannot be added safely), while a raw projection of two or more columns is rejected with the usual `InvalidOperationException`. MySQL/MariaDB and ClickHouse reject the terminal with `NotSupportedException`; the buffered `byte[]`/`string` projection remains available on every provider. The multi-column `ToDataReader`/`ToDataReaderAsync` terminal is available on PostgreSQL and SQL Server only: SQLite fails closed because its streaming projection always carries the `rowid` locator, MySQL/MariaDB and ClickHouse have no sequential-access support. See [Streaming large objects](../guide/26-large-objects.md). |
| **CSV export (`WriteCsv`/`WriteCsvAsync`) over unsupported projections** | The CSV terminals stream a `Select` result to a caller-supplied `Stream` on every SQL provider (PostgreSQL, SQL Server, SQLite, MySQL, MariaDB, ClickHouse); the destination stream is never closed. The CSV terminal reads every supported column without boxing, including SQL Server numeric columns: after the reader is open it resolves the column's actual storage type through the provider's `MapTypedColumnExpression` hook, reads it with a storage-typed getter and converts it with a typed `Convert.To<T>`, never through `GetValue`/`Convert.ChangeType(object)` (since [#168](https://github.com/AlexeyShirshov/nextorm/issues/168) the same storage-typed dispatch — `MapColumnExpression` resolving the reader's field type at runtime — also backs the shared buffered materialization path, so a normal `ToList` no longer boxes SQL Server numerics either). A projection column that has no single scalar CSV form or whose storage type is unknown/cannot be converted — a nested entity or collection, an array other than `byte[]`, a tuple, a dictionary, an arbitrary object, or a column mapped through an object-based converter or a `GetValue` fallback — is rejected before the header (and any data row) is written. `null`/`DBNull` is written as the configured `NullMarker` (default `\N`) while an empty string is an empty field, so the two are distinguishable, and the rest of the dialect (UTF-8 without BOM, RFC 4180 escaping, CRLF, invariant culture, `O`/`D` formats) is fixed. The spreadsheet formula-injection guard (CWE-1236) is opt-in: `ExcelMode = true` prefixes `'` to a field starting with `=`, `+`, `-` or `@` after any `ValueTransform` and before RFC 4180 quoting, so callers exporting untrusted data should enable it (the default is off). A `byte[]` column is read whole-field (typed `GetFieldValue<byte[]>`) and Base64-encoded for the row, so memory is bounded by the largest field/row rather than a fixed buffer; chunked LOB streaming is a future slice (trigger: demand for exporting large binary columns). A query reading a lazy temporary table created with `AsTempTable` is not a single statement (it needs a `DROP` + `CREATE TEMPORARY TABLE ... AS SELECT` + read batch on one session), so the terminal rejects it with `NotSupportedException` before the header (and any data row) is written, without executing the batch and with no buffered fallback. See [Streaming data to a Stream](../guide/28-streaming-data.md#csv). |

## Known edge cases

- **Same-name closure-variable collision.** A captured variable read by a global query filter and a different captured variable read by the user's `On(...)` that share the same CLR name render as the same parameter name, so the placeholders collide; rename one of the variables.
- **Raw-source filter binding is best-effort and unverified.** `FromSql`/`From(string)` apply a global filter only after [`BindEntity<TEntity>`](xref:NextORM.Core.EntityBuilderExtensions.BindEntity``1(NextORM.Core.EntityBuilder{NextORM.Core.TableAlias},System.Collections.Generic.IReadOnlyCollection{System.String})) declares the entity type and the output columns; a filter whose required columns are missing is skipped with a `RawSourceFilterSkipped` warning on the `NextORM.QueryFilters` category (reason `MissingColumns`, physical mapped column names) instead of throwing, while with an empty declared-column list a filter with a proven zero-column dependency is still applied and a column-dependent or undetermined filter is skipped with reason `UndeterminedColumns`. The column list is the caller's word — nextorm neither parses the raw SQL nor validates it against a schema, so a declared column the fragment does not actually return is accepted and can make a filter run against the wrong shape. Binding is not a security guarantee; a provider without raw-source support rejects the source. See [Filters on bound raw sources](query-filters.md#filters-on-bound-raw-sources).

## Not limitations

The following are fully implemented and verified; they appear in the *done* column of the gap analysis,
not in the list above:

- joins of every type (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, plus `CROSS APPLY`/`OUTER APPLY` and the lateral equivalent where supported; no `FULL JOIN` on MySQL/MariaDB) and arity 2–8, including a derived query as either side (the primary `FROM` source or the joined table);
- correlated scalar subqueries and correlated `EXISTS`/`IN`/`ANY`/`ALL` in `SELECT`, `WHERE`, `ORDER BY` and `HAVING` on every SQL provider at any nesting depth (see [Subqueries](../guide/05-subqueries.md));
- `CASE WHEN` / ternary / `switch`, `COALESCE`, numeric `CAST`;
- string, math and date/time scalar functions and `LIKE`;
- the cross-provider scalar string/number functions ([`SqlFunctions.Sql`](xref:NextORM.Core.SqlFunctions.Sql) `left`/`right`/`lpad`/`rpad`/`repeat`/`reverse`/`space`/`concat_ws`/`translate`/`ascii`/`@char`), with the per-name gates above;
- date arithmetic (`date_add`/`end_of_month`/`date_diff`/`date_from_parts` and `DateTime.Add*`) on PostgreSQL, SQL Server, ClickHouse, MySQL/MariaDB and SQLite, plus `date_trunc` on PostgreSQL/SQL Server/ClickHouse and `string_agg` on PostgreSQL/SQL Server/ClickHouse/MySQL/MariaDB/SQLite;
- the bitwise (`bit_and`/`bit_or`/`bit_xor`), statistical (`corr`/`covar_*`) and `argMin`/`argMax` aggregates on ClickHouse;
- binary columns - a `byte[]` property or projection maps to `bytea` (PostgreSQL), `varbinary`/`image` (SQL Server) or `blob` (SQLite);
- LOB streaming on PostgreSQL, SQL Server and SQLite - a single `byte[]`/`string` column is read as a `Stream`/`TextReader` with `CommandBehavior.SequentialAccess` and O(buffer) memory, without materialising the whole value (on SQLite the query source must expose `rowid`), and PostgreSQL/SQL Server additionally hand a multi-column result over as a caller-owned `DbDataReader` through `ToDataReader`/`ToDataReaderAsync`;
- unsigned 64-bit integer columns - a `ulong`/`ulong?` property or projection materialises through the row reader's `DbDataReader.GetFieldValue<ulong>` accessor on providers with a native unsigned type (ClickHouse `UInt64`, MySQL/MariaDB `BIGINT UNSIGNED`), with no SQL cast; PostgreSQL, SQL Server and SQLite have no unsigned integer type and expose that range only as `numeric`/`decimal`;
- `IN` over a list/array, logical `!` and unary operators;
- `SELECT DISTINCT`, `INTERSECT`/`EXCEPT`, CTEs (including recursive), window functions and `GROUP BY ROLLUP`/`CUBE`/`GROUPING SETS` (`CUBE`/`GROUPING SETS` not on MySQL/MariaDB);
- data-modifying CTEs (`WITH n AS (INSERT|UPDATE|DELETE ... RETURNING ...)`, single-table and join/multi-table) on PostgreSQL, read typed through [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1) (see [data-modifying CTE](../guide/15-insert-statement.md#data-modifying-cte-postgresql));
- `OUTPUT ... INTO <target>` on SQL Server — `Returning(...).OutputInto(target)` writes the modified rows into an existing table, `Returning(...).OutputIntoThenOutput(target)` writes them and returns them to the client (see [insert guide](../guide/15-insert-statement.md#writing-the-modified-rows-into-a-table-output-into));
- key-upsert `Returning()` — PostgreSQL/SQLite append `RETURNING` to `ON CONFLICT ... DO UPDATE`, SQL Server renders `MERGE ... OUTPUT`; MySQL/MariaDB reject it with `NotSupportedException` (see [upsert](../guide/19-merge-statement.md#returning-the-merged-rows));
- user-defined scalar functions (`[SqlFunction]`) and table-valued functions (`[SqlTableFunction]`);
- the ClickHouse server/cluster table functions `url`/`s3`/`file`/`remote`/`remoteSecure`/`cluster`/`clusterAllReplicas`, pre-declared on `SqlFunctions.ClickHouse.*` with a caller-declared generic `TRow` row interface (they are gated by [`SupportsTableFunction`](xref:NextORM.Core.ISqlDialect.SupportsTableFunction(System.String)); see [Table-valued functions](../guide/11-table-valued-functions.md#built-in-table-functions));
- full-text predicates (`SqlFunctions.Sql.contains`/`freetext`) on SQL Server, PostgreSQL and MySQL/MariaDB, full-text ranking (SQL Server `containstable`/`freetexttable` with `KEY`/`RANK`, PostgreSQL `ts_rank`/`ts_rank_cd`), text-JSON functions (`json_value`/`json_query`/`json_modify`/`isjson`) on SQL Server and MySQL/MariaDB and the SQL Server `openjson`/`string_split` table functions (plus user-declared `[SqlTableFunction]` wrappers, including MySQL `JSON_TABLE` via `CallClause`); the cross-provider `contains`/`freetext` predicates stay unsupported on SQLite (it throws), whose own SQLite-specific FTS3/FTS4/FTS5 query surface (`Match`, FTS5 `FTS5bm25`/`Highlight`/`Snippet`/`Rank`, FTS3/4 helpers and the FTS5 table-valued `MatchTable` `FROM` source) is available;
- statement-level query hints on SQL Server (`OPTION (...)`), PostgreSQL and MySQL/MariaDB (`/*+ ... */`), table hints on SQL Server (`Hint(...)`, `WithTableHint(...)`, the per-join `JoinOptions.WithJoinTableHint(...)`), join/subquery/tables-in-scope hints (`JoinOptions.WithJoinHint`, `FromOptions.WithSubQueryHint`, `WithTablesInScopeHint`), JSON output (`ForJson(...)` → `FOR JSON PATH`/`AUTO`) and XML output (`ForXml(...)` → `FOR XML`);
- the XML data-type methods on SQL Server (`xml_value`/`xml_query`/`xml_exist` → `xml.value('xpath', 'type')`/`xml.query('xpath')`/`xml.exist('xpath')`, and the `.nodes` rowset via `xml_nodes` as a `CrossApply`/`OuterApply` source);
- raw SQL as a whole query ([`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)) / [`PrepareFromSql`](xref:NextORM.Core.EntityExtensions.PrepareFromSql``1(NextORM.Core.EntityBuilder{``0},System.String))) and as a composable `FROM` source ([`FromSql`](xref:NextORM.Core.DataContextExtensions.FromSql(NextORM.Core.IDataContext,System.String,System.Object)), rendered as a derived table), plus the implicit plan cache / [`Prepare`](xref:NextORM.Core.EntityBuilderExtensions.Prepare``1(NextORM.Core.EntityBuilder{``0},System.Boolean,System.Threading.CancellationToken)) reuse paths;
- raw command execution against the context (`ExecuteRaw`/`ExecuteRawAsync`, and stored procedures through `ExecuteProcedure`/`ExecuteProcedureAsync`, returning a disposable `ProcedureResult`) with named/`DbType`/`Size` parameters, sequential result sets, and output/return-value parameters (see [Raw SQL](../guide/12-raw-sql.md#executing-raw-commands-executeraw));
- per-query source overrides (`WithTableName`/`WithSchema`/`WithDatabase`/`WithServer`/`WithTableExpression`) on every SQL provider, part of the plan-cache key (see [Per-query source overrides](../querying/02-query-sources.md#per-query-source-overrides)).
