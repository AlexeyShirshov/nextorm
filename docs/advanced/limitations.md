# Limitations and out-of-scope features

> nextorm is a query builder with a small explicit DML surface: it generates `SELECT` statements (and parameterised `INSERT ... VALUES`, `INSERT ... SELECT`, key upserts, `MERGE`, `DELETE` and `UPDATE`) and materialises their results, and deliberately leaves change tracking and `SaveChanges` to the caller.

**Prerequisites:** [Provider overview](../providers/overview.md) · [API reference](api-reference.md)

## Overview

This page lists the capabilities that are **not** part of nextorm, with a one-line reason for each.

## Out of scope

| Not supported | Rationale |
|---|---|
| **DML** — `INSERT`, `UPDATE`, `DELETE`, `MERGE` | **`INSERT ... VALUES`, `INSERT ... SELECT` and key upsert are implemented** ([`InsertInto`](../guide/19-insert-statement.md); row return through `RETURNING`/`OUTPUT` on PostgreSQL, SQLite and SQL Server, batched rows unordered; a server-side source hoists its CTEs before `INSERT` and rejects runtime `SqlFunctions.Parameter` placeholders). PostgreSQL also supports **data-modifying CTEs** (`With(name, insert)` → [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1), [data-modifying CTE](../guide/19-insert-statement.md#data-modifying-cte-postgresql)). **Upsert** ([`MergeInto`](xref:NextORM.Core.DataContextExtensions.MergeInto``1(NextORM.Core.IDataContext,System.Action{NextORM.Core.EntityMetadataBuilder{``0}})) → [`MergeBuilder<T>`](xref:NextORM.Core.MergeBuilder`1), [upsert](../guide/23-merge-statement.md#upsert-key-merge)) renders the provider's native form — `INSERT ... ON CONFLICT ... DO UPDATE` (PostgreSQL, SQLite), `INSERT ... ON DUPLICATE KEY UPDATE` (MySQL, MariaDB) or `MERGE ... USING (VALUES ...)` (SQL Server); ClickHouse rejects it, while the in-memory provider applies the upsert to the registered sequence. **`DELETE`** ([`DeleteFrom`](../guide/20-delete-statement.md) → [`DeleteBuilder<T>`](xref:NextORM.Core.DeleteBuilder`1), `Delete<T>(entity)`, [`delete`](../guide/20-delete-statement.md)) renders a parameterised `DELETE FROM <table> [WHERE ...]` — by predicate, by the entity's declared key, or the whole table with an explicit `All()`; `Returning()` returns the removed rows on PostgreSQL/SQLite (`RETURNING`) and SQL Server (`OUTPUT`), `Truncate<T>()` renders `TRUNCATE TABLE`, ClickHouse deletes through `ALTER TABLE ... DELETE ... SETTINGS mutations_sync = 1`. A multi-table `DELETE` based on an INNER join ([`From<T>().Join(...).Delete()`](../guide/20-delete-statement.md#delete-based-on-a-join)) is supported on PostgreSQL, SQL Server, MySQL and MariaDB, and rejected by SQLite and ClickHouse. **`UPDATE`** ([`Update`](../guide/21-update-statement.md) → [`UpdateBuilder<T>`](xref:NextORM.Core.UpdateBuilder`1), `Update<T>(entity)`) renders a parameterised `UPDATE <table> SET ... [WHERE ...]` on PostgreSQL, SQL Server, SQLite, MySQL and MariaDB; ClickHouse updates through `ALTER TABLE ... UPDATE ... SETTINGS mutations_sync = 1` (synchronous, but reports no affected-row count) and the in-memory provider rejects it; `Returning()` returns the updated rows on PostgreSQL/SQLite (`RETURNING`) and SQL Server (`OUTPUT`). A multi-table `UPDATE` based on an INNER join ([`From<T>().Join(...).UpdateJoin()`](../guide/21-update-statement.md#updating-from-a-join)) is supported on PostgreSQL/SQLite (`FROM`), SQL Server and MySQL/MariaDB, and rejected by ClickHouse. Full `MERGE` with `WHEN MATCHED`/`WHEN NOT MATCHED`/`WHEN NOT MATCHED BY SOURCE` branches and `MERGE ... RETURNING`/`OUTPUT` are available on SQL Server and PostgreSQL 15+ and rejected by the other providers. `INSERT` on the in-memory provider is out of scope by design: that context is a query surface over caller-registered collections (`WithData`), not a database emulation (unlike the EF Core in-memory provider, where `Add` + `SaveChanges` are part of the database model), and no write terminal (`INSERT`/`DELETE`/`TRUNCATE`) is available on it, except the key-upsert merge applied to the registered sequence. There is no change tracking and no `SaveChanges`: writes are explicit commands. A query can be materialized into a persistent table with `CREATE TABLE ... AS SELECT` ([`ToTempTable`/`ToTable`](../guide/22-create-table-as.md), `ToTempTable(name)`/`ToTable(name)`) on PostgreSQL, SQLite, MySQL, MariaDB, SQL Server and ClickHouse: SQL Server renders `SELECT ... INTO` (a session-scoped table is `ToTable("#name")`) and ClickHouse renders `CREATE TABLE ... ENGINE = MergeTree ... AS SELECT`. The temporary `ToTempTable` form is available on PostgreSQL, SQLite, MySQL and MariaDB only — SQL Server has no `CREATE TEMPORARY TABLE ... AS SELECT` (use `#name`) and ClickHouse has no temporary `AS SELECT`. A side-effecting statement and a following read can be sent as a single batch with the general `BatchBuilder` (`CreateTempTable`/`CreateTable` materialisations and `Insert`/`Update`/`Delete`/`Truncate` DML steps before one reading query), as one round trip on one session, on PostgreSQL, SQL Server, MySQL, MariaDB and SQLite; ClickHouse and the in-memory context reject a batch with `NotSupportedException`, and a DML step may not request returned rows (`Returning()` produces a different builder type). SQL Server sends the batch as one `;`-joined command rather than `SqlBatch`, which runs each command in its own scope, so a `#temp` stays visible across the statements. Batch execution is not routed through the query interceptors: their events carry a `DbCommand`, while a `DbBatch` command is a `DbBatchCommand`. |
| **`Prepare()` / plan cache for DML** | Every mutation renders and executes one command per call — mutating builders are deliberately not prepared or plan-cached. Optimisation in nextorm targets read-only queries only (explicit `Prepare`, the implicit plan cache, benchmarks). |
| **Navigation properties / relationship metadata** | There is no relationship metadata and no implicit join inference; you write joins explicitly with [`Join`](xref:NextORM.Core.EntityBuilder`1.Join``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`LeftJoin`](xref:NextORM.Core.EntityBuilder`1.LeftJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`RightJoin`](xref:NextORM.Core.EntityBuilder`1.RightJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`FullJoin`](xref:NextORM.Core.EntityBuilder`1.FullJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`CrossJoin`](xref:NextORM.Core.EntityBuilder`1.CrossJoin``1(NextORM.Core.EntityBuilder{``0}))/[`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0})) (see [Joins](../guide/03-joins.md)). |
| **Selecting a joined entity as a whole** | After a join the accumulated projection is positional (`Item1`..`Item8`, one item per source in join order) and only its columns can be selected (`Select(p => p.Item1.Id)`); a projection member that is the entity itself (`Select(p => p.Item1)`) is not a column and is rejected. Give the sides semantic names by projecting into a named type (`Select(p => new { Order = p.Item1.Id, Customer = p.Item2.RequiredString })`); see [Joins](../guide/03-joins.md#addressing-the-projection). |
| **Correlated `APPLY` / `LATERAL` source** | [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0})) accept a lambda that receives the left-hand row, so the applied source can reference the outer row on a lateral-capable provider (SQL Server `CROSS/OUTER APPLY`, PostgreSQL/MySQL/MariaDB `... LATERAL`). Dialects without a lateral source (SQLite, ClickHouse) reject `APPLY` outright; the in-memory provider does not support it. The correlation lambda cannot reference a join projection — apply it to a single-entity source. |
| **[`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) / [`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) on SQL providers** | These LINQ operators are implemented for the in-memory provider only, where correlation is a plain delegate. On a SQL provider [`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) throw `NotSupportedException`; the explicit [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0})) join surface covers the non-correlated equivalent (see [Joins](../guide/03-joins.md)). |
| **Correlated subqueries in the in-memory provider beyond depth one** | Correlation works for scalar subqueries (including aggregate terminals) and `EXISTS`/`IN` in `SELECT`, `WHERE` and `ORDER BY` on every SQL provider at any nesting depth, and on the in-memory provider for depth-one correlation, evaluated once per outer row (see [Subqueries](../guide/06-subqueries.md#correlated-scalar-subquery)). The remaining in-memory forms reject with `NotSupportedException`: correlation depth greater than one, an outer reference inside the inner projection or `ORDER BY`, a correlated `GROUP BY`/`HAVING`, an async source, and mixing outer references with explicit `SqlFunctions.Parameter` placeholders. |
| **Correlated scalar terminals (`First`/`Single` and their `*OrDefault` forms)** | A missing row yields `null` for a nullable projection and `default` (for example `0`) for a non-nullable value projection when the terminal is `FirstOrDefault`/`SingleOrDefault`. `First`/`Single` on a non-nullable value projection throw when no row matches. `Single`/`SingleOrDefault` over more than one row throw on every provider whose scalar subqueries enforce cardinality (PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse); SQLite does not enforce it, so a numeric `Single`/`SingleOrDefault` over more than one row raises a database error through a rendered `case when count(*) > 1 then <numeric overflow> else value end` guard, and a non-numeric projection is rejected with `NotSupportedException`. |
| **`INTERSECT ALL` / `EXCEPT ALL` on SQL Server and SQLite** | Neither engine can express these variants, so the dialect rejects them with a `NotSupportedException`; `INTERSECT` / `EXCEPT` (without `ALL`) and `UNION` / `UNION ALL` work everywhere. PostgreSQL supports both `ALL` variants. |
| **Locking table hints outside SQL Server** | The locking table hints (`WithTableHint("nolock")` → `WITH (NOLOCK)`) are supported on SQL Server only; the native index hints of MySQL/MariaDB (`USE`/`FORCE`/`IGNORE INDEX`), SQLite (`INDEXED BY`/`NOT INDEXED`) and SQL Server (`WITH (INDEX(...))`) are a separate surface ([`WithIndex`](../guide/17-query-hints.md#index-hints), [`ISqlDialect.IndexHints`](xref:NextORM.Core.ISqlDialect.IndexHints)). Statement-level hints are wired on SQL Server (`OPTION (...)`), PostgreSQL and MySQL/MariaDB (`/*+ ... */`); SQLite and ClickHouse reject `Hint(...)` with `NotSupportedException` (see [Query hints](../guide/17-query-hints.md)). |
| **Upper-case SQL keywords — tuple/row constructors stay provider-canonical** | `DataContextBuilder.UseKeywordCase(KeywordCase.Upper)`, `EntityBuilder<TEntity>.WithKeywordCase(...)` and `QueryCommand<T>.WithKeywordCase(...)` case the keywords emitted by the core statement builder (`select`, `from`, `where`, `join`, `group by`, `order by`, `with`, `insert`, `values`, ...), by the expression translators (`and`/`or`/`not`, `case`/`when`/`then`/`else`/`end`, `cast(... as ...)`, `is [not] null`, `like`, `in`, `exists`, `over` and window frames), by the common dialect clauses (aliases `as`, paging `limit`/`offset`/`fetch`/`top`, `with [recursive]`, the join keywords, table/index hints) and by every dialect-rendered clause: `for json`/`for xml`, the grouping modifiers (`rollup`/`cube`/`grouping sets`/`with totals`), `for system_time ...`, `apply`, `settings`, `final`, `sample`, the DML `returning`/`output`, the query-hint `option (...)`/`option (maxrecursion ...)` and the capability clauses (`for update`/`for share`, `tablesample ... repeatable`, `limit by`, `array join`, `distinct on`, `pivot`/`unpivot`). The row/tuple constructors `ROW(...)` (PostgreSQL) and `tuple(...)` (ClickHouse) are treated as function-like constructors and keep the provider's canonical spelling in both cases (consistent with the function-name policy). Identifiers, string literals, function names, type names and raw SQL are never affected, and `KeywordCase.Lower` (the default) is byte-for-byte the historical output. |
| **Array functions outside PostgreSQL** | The array-parameter `any`/`all` quantifiers (`column = any(@array)`) and the array functions (`cardinality`, `array_length`, ...) require a provider with native arrays; only PostgreSQL opts in ([`SupportsArrays`](xref:NextORM.Core.ISqlDialect.SupportsArrays)). Other dialects reject them with `NotSupportedException` (see [Scalar functions](../scalar-functions/06-arrays.md#arrays-postgresql)). |
| **Server-side array/JSON element access (`x[i]`)** | Only a captured (closed-over) collection indexed inside the query is supported ([captured collection lookup](../guide/02-filtering-where.md#captured-collection-lookup-dictcolumn)): a constant key folds to a parameter and a column key renders a portable `CASE`. Element access on a server-side array/JSON column or an array-returning expression (`groupArray(x)[0]`, `array_agg(x)[1]`, `json['k']`) has no portable SQL form and throws `NotSupportedException` (a custom indexer likewise) instead of binding the whole collection. The native forms differ (`arr[i]` on PostgreSQL, `arrayElement(arr, i)` on ClickHouse, JSON paths elsewhere), so they would need a separate dialect hook. |
| **`string.Split` outside ClickHouse** | The CLR `string.Split` is rendered as `splitByChar(separator, value)` only on ClickHouse ([`StringSplit`](xref:NextORM.Core.ISqlDialect.StringSplit)); PostgreSQL reaches it through its own `string_to_array` array-operand path, while SQL Server (`STRING_SPLIT` is a table-valued function), MySQL/MariaDB and SQLite have no scalar array split and reject it. Only a one-character separator is supported (no `splitByString`), and the result is a `string[]` that can be projected directly or used as the operand of another array function. |
| **Native JSON functions outside PostgreSQL** | The `json`/`jsonb` functions and operators (`json_agg`, `json_build_object`, `->`, `->>`, `#>`, `@>`, `?`, ...) require a provider with a JSON type; only PostgreSQL opts in ([`SupportsJson`](xref:NextORM.Core.ISqlDialect.SupportsJson)). SQL Server, MySQL and MariaDB provide the text-JSON subset (`json_value`/`json_query`/`json_modify`/`isjson`, [`SupportsTextJson`](xref:NextORM.Core.ISqlDialect.SupportsTextJson)) over a normal text column instead (MySQL/MariaDB render it through `JSON_EXTRACT`/`JSON_SET`). Other dialects reject both surfaces with `NotSupportedException` (see [Scalar functions](../scalar-functions/07-json-and-xml.md#json-and-jsonb-postgresql)). |
| **ClickHouse native `JSON` column type** | The native-JSON functions (`JSONAllPaths`/`JSONAllPathsWithTypes`/`toJSONString`, alongside `JSON_VALUE`/`JSON_QUERY`/`JSON_EXISTS`) are wired on `ClickHouseFunctions` and gated by [`SupportsJsonExtract`](xref:NextORM.Core.ISqlDialect.SupportsJsonExtract), but a native `JSON` *column* is not mapped to a CLR type: `ClickHouse.Driver` reads it as `System.Text.Json.Nodes.JsonObject`, which the row reader cannot materialise. Use JSON stored in a `String` column (or cast the column in SQL) when you need to materialise it; a dedicated type-mapping/reader is a separate backlog item. |
| **`greatest`/`least` on providers that do not opt in** | The functions are gated by [`SupportsGreatestLeast`](xref:NextORM.Core.ISqlDialect.SupportsGreatestLeast); PostgreSQL, MySQL/MariaDB, ClickHouse, SQL Server 2022+ and SQLite opt in. SQLite maps them to its multi-argument scalar `max`/`min` (a single argument returns the argument itself, because `max`/`min` with one argument is an aggregate). NULL semantics differ: PostgreSQL, SQL Server 2022+ and ClickHouse 24.12+ ignore NULL arguments, while MySQL/MariaDB and SQLite return NULL when any argument is NULL. A provider that does not opt in rejects them with `NotSupportedException`. `nullif` is ANSI and always available. |
| **Cross-provider scalar functions on providers without the function** | `left`/`right`/`lpad`/`rpad`/`repeat`/`reverse`/`space`/`concat_ws`/`translate`/`ascii`/`@char` are gated **per name** by [`IScalarFunctions.Supports`](xref:NextORM.Core.IScalarFunctions.Supports(System.String)). MySQL/MariaDB have no `translate`; SQLite has no `lpad`/`rpad`/`repeat`/`reverse`/`space`/`translate`, so those are rejected there with `NotSupportedException`. `left`/`right`/`lpad`/`rpad` count characters (ClickHouse uses its `*UTF8` variants); `concat_ws` skips NULL arguments everywhere except ClickHouse, whose `concatWithSeparator` returns NULL. `ascii`/`char` follow the provider's native code-unit rules for non-ASCII input (ClickHouse treats `char(n)` as a byte string), and a negative `n` to `left`/`right` is provider-specific. The in-memory provider evaluates the calls through their CLR equivalents and reads a negative `n` as PostgreSQL does ("all but the last/first |n|"), so use a non-negative `n` for portable queries. See [Scalar functions](../scalar-functions/01-string-functions.md#cross-provider-scalar-functions). |
| **`date_trunc` outside PostgreSQL, SQL Server and ClickHouse** | `date_trunc` is gated by [`SupportsDateTrunc`](xref:NextORM.Core.ISqlDialect.SupportsDateTrunc); PostgreSQL, SQL Server 2022+ (`datetrunc`) and ClickHouse (`dateTrunc`) opt in. |
| **ClickHouse date conversion/part functions outside ClickHouse** | The `toDate`/`toDateTime`/`toDate32`, `toYear`/..., `toStartOf*`, `toMonday`, `toYYYYMM`/`toYYYYMMDD` and `toUnixTimestamp` surface ([`DateConversion`](xref:NextORM.Core.ISqlDialect.DateConversion)) is ClickHouse-only; other providers reject it with `NotSupportedException`. The portable equivalents are `date_trunc`/`date_add`/`end_of_month` and the `DateTime` parts (see [Scalar functions](../scalar-functions/03-date-and-time.md#date-conversion-and-parts-clickhouse)). |
| **ClickHouse `multiIf` and `lagInFrame`/`leadInFrame` outside ClickHouse** | The multi-branch `multi_if` ([`MultiIf`](xref:NextORM.Core.ISqlDialect.MultiIf)) and the frame-respecting `lag_in_frame`/`lead_in_frame` window functions ([`SupportsInFrameWindowFunctions`](xref:NextORM.Core.ISqlDialect.SupportsInFrameWindowFunctions)) are ClickHouse-only; other providers reject them with `NotSupportedException`. Multi-branch conditions are portable through `iif`/the C# conditional (rendering `CASE WHEN`), and the standard `lag`/`lead` are the partition-based substitutes — but ClickHouse itself rejects an explicit frame on those, so a frame-aware neighbour needs `lagInFrame`/`leadInFrame`. |
| **`array_agg` outside PostgreSQL** | `array_agg` is gated by [`SupportsArrayAgg`](xref:NextORM.Core.ISqlDialect.SupportsArrayAgg) and requires a provider with an array type, so only PostgreSQL opts in. `string_agg` is gated separately by [`SupportsStringAgg`](xref:NextORM.Core.ISqlDialect.SupportsStringAgg) and is also available on SQL Server 2017+ and ClickHouse (`arrayStringConcat(groupArray(x), delimiter)`). An `array_agg` result is an `Array(T)` column, materialised by the row reader as `T[]`, so it can be projected directly as well as used inside the query (for example in a `HAVING`). |
| **`untuple` (ClickHouse)** | `untuple(tuple)` is not mapped: it expands a tuple into several result columns, which has no single scalar CLR shape in a projection. Project the `Tuple(...)` as `System.Tuple<...>` and read its elements with `tupleElement`/`System.Tuple<...>.ItemN` instead. |
| **PostgreSQL row-value materialisation, tuple `IN`, and non-PostgreSQL `(a, b)` constructors** | Row values are constructible and comparable on PostgreSQL (`ROW(a, b)`, elements via `(row).fN`) and ClickHouse (`tuple(a, b)`, `tupleElement`); an inline constructor's `.ItemN` folds to the argument everywhere. Still open: materialising a raw `ROW(...)` back into `System.Tuple<...>` on PostgreSQL (Npgsql needs `EnableRecords()`/`MapComposite`), tuple `IN`/`Contains` over a list of CLR tuples, and the `(a, b)` constructor on MySQL/MariaDB/SQLite (phase 2). See [Scalar functions](../scalar-functions/index.md). |
| **Binding the element of several `ARRAY JOIN` expressions at once (ClickHouse)** | [`ArrayJoinElement`](xref:NextORM.Core.EntityBuilder`1.ArrayJoinElement``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`LeftArrayJoinElement`](xref:NextORM.Core.EntityBuilder`1.LeftArrayJoinElement``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) bind the element of exactly one array expression to `p.Element`; a second call, a call on a joined query, or a call after `Where`/`Having` throws `InvalidOperationException`. When you array-join several arrays and do not need the typed element, use [`ArrayJoin`](xref:NextORM.Core.EntityBuilder`1.ArrayJoin``1(System.Linq.Expressions.Expression{System.Func{`0,``0}}))/[`LeftArrayJoin`](xref:NextORM.Core.EntityBuilder`1.LeftArrayJoin``1(System.Linq.Expressions.Expression{System.Func{`0,``0}})), which accept several expressions (see [ClickHouse provider](../providers/clickhouse.md)). |
| **ClickHouse aggregate-function state (`-State`/`-Merge`, `runningAccumulate`)** | `uniqState`/`sumState`/`countState`/… return an opaque `AggregateFunction(...)` value, which nextorm does not model: `ClickHouse.Driver` 1.4.0 throws `AggregateFunctionException` from `FrameworkType`/`Read`/`Write`, so such a column cannot be materialised into or passed as a CLR value (the driver message points at the matching `-Merge`). `uniqMerge(uniqState(x))` is itself illegal (`ILLEGAL_AGGREGATION`), so a `-Merge` needs a state produced server-side (a subquery or a state table), and `runningAccumulate` is deprecated in ClickHouse 25.8 (`DEPRECATED_FUNCTION`, needs `allow_deprecated_error_prone_window_functions`). |
| **Boolean and regression aggregates outside PostgreSQL** | `bool_and`/`bool_or`/`every` ([`SupportsBooleanAggregates`](xref:NextORM.Core.ISqlDialect.SupportsBooleanAggregates)) and the `regr_*` family ([`SupportsRegressionAggregates`](xref:NextORM.Core.ISqlDialect.SupportsRegressionAggregates)) are PostgreSQL-only. `corr`/`covar_*` ([`SupportsStatisticalAggregates`](xref:NextORM.Core.ISqlDialect.SupportsStatisticalAggregates)) are also available on ClickHouse (`corr`/`covarPop`/`covarSamp`). |
| **Aggregate `FILTER` outside PostgreSQL, SQLite and ClickHouse** | A filtered aggregate is rendered according to [`AggregateFilterStyle`](xref:NextORM.Core.ISqlDialect.AggregateFilterStyle): PostgreSQL and SQLite render the ANSI `FILTER (WHERE ...)` clause, ClickHouse renders the `-If` combinator (`countIf`/`sumIf`/...), and MySQL/MariaDB, SQL Server and the in-memory provider reject it with `NotSupportedException`. |
| **`GROUP BY CUBE`/`GROUPING SETS` on MySQL/MariaDB and the in-memory provider** | MySQL/MariaDB have no `CUBE` or `GROUPING SETS`, and the in-memory provider supports none of `ROLLUP`/`CUBE`/`GROUPING SETS`; these reject the modifier with `NotSupportedException`. `ROLLUP` works on every SQL provider (see [Grouping and aggregates](../guide/04-grouping-and-aggregates.md#rollup-and-cube)). |
| **String formatting and collation beyond the documented subset** | `string.Format`/interpolation/`value.ToString(format)` translate only the culture-invariant subset: `N`/`F`/`D`/`X` numbers (per provider) and the `yyyy yy MM dd HH mm ss` date tokens with the separators `- / . : T` and space. Any other specifier, and any culture other than `CultureInfo.InvariantCulture`, throws `NotSupportedException`. The ordinal `StringComparison` overloads accept only `Ordinal`/`OrdinalIgnoreCase` (`InvariantCulture`/`CurrentCulture` throw); SQLite additionally rejects the case-sensitive ordinal `Contains`/`StartsWith`/`EndsWith` because its `LIKE` is always case-insensitive regardless of collation ([`SupportsOrdinalLike`](xref:NextORM.Core.ISqlDialect.SupportsOrdinalLike)). See [Ordinal comparison and collation](../scalar-functions/01-string-functions.md#ordinal-comparison-and-collation). |
| **Column-level collation on ClickHouse and DDL** | A collation declared on a mapped property ([`CollationAttribute`](xref:NextORM.Core.CollationAttribute) / [`EntityPropertyBuilder<T>.Collation`](xref:NextORM.Core.EntityPropertyBuilder`1.Collation(System.String))) is applied to the column in collation-sensitive query operations on the providers that support per-expression collation ([`SupportsCollation`](xref:NextORM.Core.ISqlDialect.SupportsCollation)): PostgreSQL, SQL Server, MySQL/MariaDB and SQLite. ClickHouse has no `COLLATE` clause and rejects a collated column with `NotSupportedException`. nextorm generates no DDL, so the declaration describes the collation of an **existing** column and does not create it. See [Column collation](../scalar-functions/01-string-functions.md#column-collation). |
| **Regular expressions** | A constant-pattern `Regex.IsMatch`/`Regex.Replace` translates on PostgreSQL, MySQL/MariaDB, ClickHouse, SQLite and SQL Server 2025+ ([`SupportsRegex`](xref:NextORM.Core.ISqlDialect.SupportsRegex)); on SQL Server the match renders as `REGEXP_LIKE`, which requires database compatibility level 170, while `REGEXP_REPLACE` is available at every level — SQL Server 2022 and earlier have no `REGEXP_*` functions. The pattern, replacement and options must be compile-time constants, only `RegexOptions.IgnoreCase` maps, and the pattern executes on the provider's own engine (POSIX/ICU/PCRE/RE2/.NET), so complex patterns (lookaround, backreferences) and replacement group references are not portable. See [Regular expressions](../scalar-functions/01-string-functions.md#regular-expressions). |
| **Stored procedures and dynamic SQL** | nextorm builds `SELECT` statements from LINQ; calling a stored procedure or assembling SQL at runtime is outside the builder surface (raw SQL for a whole query is available — [`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String))). |
| **Multiple result sets from one command** | A batch runs its side-effecting statements and then the single result-bearing query; the executor navigates past the side-effecting statements' empty sets (`NextResult`), but no public terminal materialises several result sets in order. Reading every set a stored procedure returns is not exposed yet (deferred). |
| **`OUTPUT ... INTO` outside SQL Server** | Only SQL Server can write modified rows into an existing table through `OUTPUT ... INTO` ([`SupportsOutputInto`](xref:NextORM.Core.ISqlDialect.SupportsOutputInto)); every other provider rejects `OutputInto`/`OutputIntoThenOutput` with `NotSupportedException`. nextorm does not declare a table variable (`DECLARE @t TABLE ...`) — the target is an existing table name (deferred). |
| **External sources (`OPENROWSET`/`OPENQUERY`, linked servers)** | Out of scope; the connection's own schema is queried. |
| **ClickHouse `format`/`merge`/`input` table functions** | Not pre-declared on `SqlFunctions.ClickHouse`: `format` and `merge` infer their schema at runtime and `input` is valid only in `INSERT ... SELECT`, so none has a caller-declared `TRow` shape. Use `FromSql` or a user-declared `[SqlTableFunction]` wrapper. The free-form ClickHouse `values` and PostgreSQL `jsonb_to_record`/`jsonb_to_recordset` **are** exposed through a caller-declared `TRow` schema ([Dynamic result schema](../guide/13-table-valued-functions.md#dynamic-result-schema)). |
| **PostgreSQL `json_populate_record(set)`** | The `json_populate_record`/`json_populate_recordset` variants populate a caller-supplied **base record type** instead of a free-form column list, so they need a mapped composite per provider; only the free-form `jsonb_to_record`/`jsonb_to_recordset` are exposed. See [Dynamic record schema](../guide/provider-specific/postgresql.md#dynamic-record-schema). |
| **DDL / administrative commands** | `CREATE`/`ALTER`/`DROP`, `OPTIMIZE`, `RENAME` and similar are not generated; use your own commands. |
| **Unit of work, `SaveChanges` and change tracking / CDC** | nextorm does not own a unit of work or track entities, and there is no `SaveChanges`. It can run its queries inside a transaction, however: start one with [`ITransactionManager`](xref:NextORM.Core.ITransactionManager) or enlist in an externally owned one (EF Core, Dapper, raw ADO.NET) with `UseTransaction`. Writes remain explicit `INSERT`/`UPDATE`/`DELETE`/`MERGE` commands; concurrency is checked explicitly (token in `WHERE` + affected-row count) and a change-tracking layer can be built on top — see [Optimistic concurrency and change tracking](../guide/29-optimistic-concurrency.md). ClickHouse has no transaction and rejects it. |
| **Row-locking wait modes (`NOWAIT`/`SKIP LOCKED`) outside PostgreSQL, MySQL, MariaDB and SQL Server** | [`LockWaitMode`](xref:NextORM.Core.LockWaitMode) is expressed by the four dialects that lock rows ([`ILockRenderer`](xref:NextORM.Core.ILockRenderer)): PostgreSQL renders `FOR UPDATE`/`FOR SHARE [NOWAIT \| SKIP LOCKED]` (9.5+); MySQL 8.0.1+ renders `FOR UPDATE`/`FOR SHARE [NOWAIT \| SKIP LOCKED]`, and a shared lock with a wait mode switches from `LOCK IN SHARE MODE` (which takes no lock option) to `FOR SHARE`; MariaDB appends the mode to `FOR UPDATE`/`LOCK IN SHARE MODE` (`NOWAIT` 10.3+, `SKIP LOCKED` 10.6+); SQL Server attaches `NOWAIT`/`READPAST` to the same table hint, where `READPAST` skips any locked row and so approximates `SKIP LOCKED`. Version floors are documented, not server-version-gated. SQLite, ClickHouse and the in-memory provider reject any row lock, wait mode or not. |

| **Interceptors beyond the command/connection lifecycle** | The shipped surface is [`IQueryInterceptor`](xref:NextORM.Core.IQueryInterceptor) and [`IConnectionInterceptor`](xref:NextORM.Core.IConnectionInterceptor) (see [Interceptors](../guide/27-interceptors.md)). There is no exception interceptor - translate a provider exception with a `try`/`catch` around the terminal call - and no interceptors for the in-memory provider, which has no command or connection. An interceptor must not change `CommandText` (the command belongs to a cached plan). Global query filters are a separate layer. |

| **Native range/multirange columns outside PostgreSQL** | Native range types (`int4range`…`daterange`) and multirange types (`int4multirange`…`datemultirange`) exist only on PostgreSQL, gated by [`SupportsRanges`](xref:NextORM.Core.ISqlDialect.SupportsRanges). On the other providers a bare `Range<T>`/`Range<T>[]` column is rejected with `NotSupportedException`. A `Range<T>` property can instead be stored as a pair of scalar columns with [`RangeColumnsAttribute`](xref:NextORM.Core.RangeColumnsAttribute) (or the fluent `EntityPropertyBuilder<T>.RangeColumns(...)`, gated by [`SupportsRangeColumns`](xref:NextORM.Core.ISqlDialect.SupportsRangeColumns)): the two bounds are read and written, <c>NULL</c> meaning an unbounded side, and the predicate/inspection surface (`overlaps`, `range_contains`/`range_contained_by`, the positional and adjacency predicates, `lower`/`upper`/`isempty`/…) is translated over the pair. Range-returning operators (`range_union`/`range_intersection`/`range_difference`, the constructors) and the `range_agg`/`range_intersect_agg` aggregates have no scalar form over a pair and stay PostgreSQL-only, as do multirange columns; the in-memory provider evaluates the whole surface against CLR [`Range<T>`](xref:NextORM.Core.Range`1)/`Range<T>[]` values. |

## Not limitations

The following are fully implemented and verified; they appear in the *done* column of the gap analysis,
not in the list above:

- joins of every type (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, plus `CROSS APPLY`/`OUTER APPLY` and the lateral equivalent where supported) and arity 2–8, including a derived query as either side (the primary `FROM` source or the joined table);
- correlated scalar subqueries and correlated `EXISTS`/`IN`/`ANY`/`ALL` in `SELECT`, `WHERE`, `ORDER BY` and `HAVING` on every SQL provider at any nesting depth, and depth-one correlated scalar/`EXISTS`/`IN` in `SELECT`/`WHERE`/`ORDER BY` on the in-memory provider (see [Subqueries](../guide/06-subqueries.md));
- `CASE WHEN` / ternary / `switch`, `COALESCE`, numeric `CAST`;
- string, math and date/time scalar functions and `LIKE`;
- the cross-provider scalar string/number functions ([`SqlFunctions.Sql`](xref:NextORM.Core.SqlFunctions.Sql) `left`/`right`/`lpad`/`rpad`/`repeat`/`reverse`/`space`/`concat_ws`/`translate`/`ascii`/`@char`), with the per-name gates above, and evaluated in-memory through their CLR equivalents;
- date arithmetic (`date_add`/`end_of_month`/`date_diff`/`date_from_parts` and `DateTime.Add*`) on PostgreSQL, SQL Server, ClickHouse, MySQL/MariaDB and SQLite, plus `date_trunc` on PostgreSQL/SQL Server/ClickHouse and `string_agg` on PostgreSQL/SQL Server/ClickHouse/MySQL/MariaDB/SQLite;
- the bitwise (`bit_and`/`bit_or`/`bit_xor`), statistical (`corr`/`covar_*`) and `argMin`/`argMax` aggregates on ClickHouse;
- binary columns - a `byte[]` property or projection maps to `bytea` (PostgreSQL), `varbinary`/`image` (SQL Server) or `blob` (SQLite);
- unsigned 64-bit integer columns - a `ulong`/`ulong?` property or projection materialises through the row reader's `DbDataReader.GetFieldValue<ulong>` accessor on providers with a native unsigned type (ClickHouse `UInt64`, MySQL/MariaDB `BIGINT UNSIGNED`), with no SQL cast; PostgreSQL, SQL Server and SQLite have no unsigned integer type and expose that range only as `numeric`/`decimal`;
- `IN` over a list/array, logical `!` and unary operators;
- `SELECT DISTINCT`, `INTERSECT`/`EXCEPT`, CTEs (including recursive), window functions and `GROUP BY ROLLUP`/`CUBE`/`GROUPING SETS` (`CUBE` and `GROUPING SETS` except MySQL/MariaDB);
- data-modifying CTEs (`WITH n AS (INSERT ... RETURNING ...)`) on PostgreSQL, read typed through [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1) (see [data-modifying CTE](../guide/19-insert-statement.md#data-modifying-cte-postgresql));
- `OUTPUT ... INTO <target>` on SQL Server — `Returning(...).OutputInto(target)` writes the modified rows into an existing table, `Returning(...).OutputIntoThenOutput(target)` writes them and returns them to the client (see [insert guide](../guide/19-insert-statement.md#writing-the-modified-rows-into-a-table-output-into));
- key-upsert `Returning()` — PostgreSQL/SQLite append `RETURNING` to `ON CONFLICT ... DO UPDATE`, SQL Server renders `MERGE ... OUTPUT`; MySQL/MariaDB reject it with `NotSupportedException` (see [upsert](../guide/23-merge-statement.md#returning-the-merged-rows));
- user-defined scalar functions (`[SqlFunction]`) and table-valued functions (`[SqlTableFunction]`);
- the ClickHouse server/cluster table functions `url`/`s3`/`file`/`remote`/`remoteSecure`/`cluster`/`clusterAllReplicas`, pre-declared on `SqlFunctions.ClickHouse.*` with a caller-declared generic `TRow` row interface (they are gated by [`SupportsTableFunction`](xref:NextORM.Core.ISqlDialect.SupportsTableFunction(System.String)); see [Table-valued functions](../guide/13-table-valued-functions.md#built-in-table-functions));
- full-text predicates (`SqlFunctions.Sql.contains`/`freetext`) on SQL Server, PostgreSQL and MySQL/MariaDB, full-text ranking (SQL Server `containstable`/`freetexttable` with `KEY`/`RANK`, PostgreSQL `ts_rank`/`ts_rank_cd`), text-JSON functions (`json_value`/`json_query`/`json_modify`/`isjson`) on SQL Server and MySQL/MariaDB and the SQL Server `openjson`/`string_split` table functions (plus user-declared `[SqlTableFunction]` wrappers, including MySQL `JSON_TABLE` via `CallClause`);
- statement-level query hints on SQL Server (`OPTION (...)`), PostgreSQL and MySQL/MariaDB (`/*+ ... */`), table hints on SQL Server (`Hint(...)`, `WithTableHint(...)`), JSON output (`ForJson(...)` → `FOR JSON PATH`/`AUTO`) and XML output (`ForXml(...)` → `FOR XML`);
- the XML data-type methods on SQL Server (`xml_value`/`xml_query`/`xml_exist` → `xml.value('xpath', 'type')`/`xml.query('xpath')`/`xml.exist('xpath')`, and the `.nodes` rowset via `xml_nodes` as a `CrossApply`/`OuterApply` source);
- raw SQL as a whole query ([`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)) / [`PrepareFromSql`](xref:NextORM.Core.EntityExtensions.PrepareFromSql``1(NextORM.Core.EntityBuilder{``0},System.String))) and as a composable `FROM` source ([`FromSql`](xref:NextORM.Core.DataContextExtensions.FromSql(NextORM.Core.IDataContext,System.String,System.Object)), rendered as a derived table), plus the implicit plan cache / [`Prepare`](xref:NextORM.Core.EntityBuilderExtensions.Prepare``1(NextORM.Core.EntityBuilder{``0},System.Boolean,System.Threading.CancellationToken)) reuse paths.
