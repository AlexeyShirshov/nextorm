# Limitations and out-of-scope features

> nextorm is a query builder with a small explicit DML surface: it generates `SELECT` statements (and parameterised `INSERT ... VALUES`, `INSERT ... SELECT`, key upserts, `MERGE`, `DELETE` and `UPDATE`) and materialises their results, and deliberately leaves change tracking and `SaveChanges` to the caller.

**Prerequisites:** [Provider overview](../connecting-providers/overview.md) · [API reference](api-reference.md)

## Overview

This page lists the capabilities that are **not** part of nextorm, with a one-line reason for each.

## Limitations

| Area with limitations | Rationale |
|---|---|
| **DML — remaining restrictions** | ClickHouse rejects key upsert, and full `MERGE` (`WHEN MATCHED`/`WHEN NOT MATCHED`/`WHEN NOT MATCHED BY SOURCE` branches and `MERGE ... RETURNING`/`OUTPUT`) exists only on SQL Server and PostgreSQL 15+ — the other providers reject both. Under an active global query filter the `ON CONFLICT` / `ON DUPLICATE KEY` key upserts **refuse** with `NotSupportedException` (fail closed; `IgnoreFilters()` restores them): a source key colliding with a hidden target row still surfaces the provider's native unique-constraint error from the insert arm — for whichever unique index it hits, not only the merge key (an existence oracle; a composite key including the filter column mitigates the primary/merge key only) — while an update-only or delete-only merge is a silent no-op, and the source-value pre-check stays a separate TOCTOU read (`QueryFilterValidator`) that validates source values, not target rows (see [Write-target isolation](query-filters.md#write-target-isolation)). A multi-table `DELETE` based on an INNER join ([`From<T>().Join(...).Delete()`](../guide/18-delete-statement.md#delete-based-on-a-join)) is rejected by SQLite and ClickHouse, a multi-table `UPDATE` based on an INNER join ([`From<T>().Join(...).CreateUpdateJoinBuilder()`](../guide/19-update-statement.md#updating-from-a-join)) by ClickHouse, MariaDB's `UPDATE ... RETURNING` is available only at an explicitly configured 13.0+ ([`SupportsUpdateReturning`](xref:NextORM.Core.ISqlDialect.SupportsUpdateReturning)), and a ClickHouse `ALTER TABLE ... UPDATE` reports no affected-row count. The temporary form of `CREATE TABLE ... AS SELECT` ([`ToTempTable`](../guide/20-create-table-as.md)) is available on PostgreSQL, SQLite, MySQL and MariaDB only: SQL Server has no `CREATE TEMPORARY TABLE ... AS SELECT` (use a session-scoped [`ToTable("#name")`](../guide/20-create-table-as.md)) and ClickHouse has no temporary `AS SELECT`. ClickHouse rejects a batch with `NotSupportedException`, a DML batch step may not request returned rows (`Returning()` produces a different builder type), and batch execution is not routed through the query interceptors: their events carry a `DbCommand`, while a `DbBatch` command is a `DbBatchCommand`. There is no change tracking and no `SaveChanges`: writes are explicit commands. |
| **Server-version-gated syntax** | nextorm never probes the live server, so a version-dependent capability is available only when its version is **explicitly configured**. PostgreSQL's aggregate `FILTER (WHERE ...)` needs 9.4+: a dialect pinned below that rejects it with `NotSupportedException`, while an **unset** version silently assumes 9.4+ and enables it. MariaDB's `UPDATE ... RETURNING` is enabled only at an explicit 13.0+ ([`SupportsUpdateReturning`](xref:NextORM.Core.ISqlDialect.SupportsUpdateReturning)); unset or older rejects it with `NotSupportedException`. MariaDB's `months_between` (12.2.1), `to_date` (12.3), `to_number` (12.2 family, enforced 12.2.1), `gen_random_uuid` → `uuid_v4()` and `uuidv7` → `uuid_v7()` (both 11.7) are gated the same way: an unversioned context refuses them at translation/preparation instead of emitting SQL the server rejects, and no platform equivalent (`TIMESTAMPDIFF`, `STR_TO_DATE`, a decimal cast, `UUID()`) is substituted. PostgreSQL's `array_reverse`/`array_sort`/`uuidv7` are a targeted exception to the permissive unset default: `array_reverse` exists in no current release and `array_sort`/`uuidv7` arrived only in 18, so all three are refused at preparation (`The PostgreSQL function 'array_reverse' is not supported by this provider.`, the same message naming `array_sort`, and `The uuidv7 function is not supported by this provider.`) when the configured version is below 18 **or unset**; no `NULL`, unchanged array or v4 UUID is substituted, and no other unset-version gate changes. PostgreSQL enforces one immutable server version per **concrete context type** for the process lifetime, because `FILTER` affects the cached `SELECT` SQL; a different version for the same concrete type throws `InvalidOperationException`, so a process that needs several PostgreSQL versions declares a distinct context subclass per version. See [PostgreSQL provider](../connecting-providers/postgres.md#server-version) and [MariaDB provider](../connecting-providers/mariadb.md#server-version). |
| **Recursive CTE — SQL Server requires `UNION ALL`** | A legacy `WithRecursive` declaration whose body is a distinct `UNION` (`anchor.Union(step)`) is rejected by SQL Server ("does not contain a top-level UNION ALL operator"), so nextorm fails closed while the query is prepared — before execution and before the plan cache — with an actionable `NotSupportedException`. Migrate to `UnionAll` or the typed `AsRecursiveCte` API. See [CTE](../guide/10-cte.md#sql-server-legacy-recursive-cte-must-use-union-all). |
| **`Prepare()` / plan cache for DML** | Every mutation renders and executes one command per call — mutating builders are deliberately not prepared or plan-cached. Optimisation in nextorm targets read-only queries only (explicit `Prepare`, the implicit plan cache, benchmarks). |
| **Bulk insert — remaining boundaries** | `BulkInsertMode` defaults to `Auto`: it prefers the native path only when every supplied option and preflight prerequisite is compatible, and otherwise takes the portable `INSERT ... VALUES` path only when that path honours the request; `Native` refuses by name instead of falling back (SQLite has no native path) and `Portable` refuses a native-only option by name instead of ignoring it. `BulkInsertOptions.ServerName` is **not available** — a bulk insert never reroutes to another server — and `DatabaseName` is dialect-scoped (PostgreSQL addresses only the connection's current database; the other providers render it per their own qualification). Of the bulk-copy flags `TableLock`/`FireTriggers` stay SQL Server-native only, `CheckConstraints=false` is honoured only where a scoped control exists (SQL Server native, MariaDB, SQLite outside an active transaction), and `KeepNulls=false` is accepted only for a default-equivalent shape (every written column nullable with a NULL/absent SQL default) — every other request is refused, never accepted and left inert. `Returning*` always writes through the portable path and is refused on MySQL, MariaDB and ClickHouse. `Timeout` is one whole-invocation `TimeSpan` budget on every path, never reset per batch; an expired budget is a `TimeoutException` and a caller cancellation always wins. Creating or dropping a temporary table and any whole-load, rollback, throughput or per-row-commit guarantee remain out of scope. No blanket "every limit is supported" claim is made for any provider. See [Bulk insert](../guide/22-bulk-insert.md). |
| **Implicit navigation queries / joins from navigation properties** | There is no convention over foreign keys and no implicit join inference: a relationship must be declared explicitly (`HasMany`/`HasOne`/`HasOneToOne`/`HasManyThrough`/`[Relationship]`, see [Relationships](../relationships/relationships.md)), and the fluent helpers declare a **single** key column — a composite-key relationship must come from relationship metadata that lists the components. `IRelationshipMetadata.Inverse` is resolved lazily on its **first read** and cached, so register both sides before reading it. Adapter LINQ composition, a bare reference-adapter projection and predicate overloads fail closed, and a collection navigation exposes only four direct terminals (`Any`/`Count`/`LongCount`/the `Count` property); `Count`/the `Count` property are a checked `int` (the 64-bit count is narrowed at materialisation and throws `OverflowException` out of range), while `LongCount` is 64-bit end to end. A collection reached through a reference is rejected by ClickHouse, which cannot correlate a subquery on a joined source and throws `NotSupportedException` (an **accepted provider limitation**, not a defect). Navigation over a temp-table/TVP source is **not available (fail-closed)**: a lazy temp-table read source is an untyped `TableAlias`, so a navigation member cannot be read over it — there is no base-table fallback and no exception. A table-valued parameter (TVP) has **no query root**: it is parameter-only, bound through `ProcedureParameter.Table<T>` on a raw command or stored procedure, and there is no `From<T>` TVP source. `LoadWith` nests to level 2 and deeper; unexpressible nested shapes, a conflicting nested mode, a cyclic graph and the projection arity cap fail closed with `NotSupportedException` (see [Eager loading](../relationships/eager-loading.md#nested-graphs-level-2-and-deeper)). `JoinInto` child sources support `Where` only; other query modifiers throw `NotSupportedException` before execution. `JoinInto` rejects with `NotSupportedException` an undeclared relationship (unless the explicit-key overload is used), a derived (`As`) or joined projection source as the builder it is declared on, a join kind other than `Inner`/`Left`, mismatched explicit key types and more than seven child collections; mixing `JoinInto` with any other join on the same builder is rejected (declare it on a plain entity source only), a ClickHouse `j => j.WithStrictness(Any)` option truncates the loaded collection to one child, and relationship metadata fails closed on an unmapped foreign key, a keyless principal or an FK/principal-key type mismatch. **Deduplication needs a mapped key**: parent dedup and child identity fall back to reference identity when the respective side declares no key, and on a SQL provider every row is a fresh instance, so repeated/cartesian rows then survive — give the parent and child a mapped key (`[Key]`/`Key()`/the `Id` convention) or use the explicit-key overload with a keyed child. |
| **Reference navigation inside a correlated predicate — supported; correlated eager loading — not** | A declared reference navigation used inside a correlated `EXISTS`/`IN` body or a correlated scalar subquery is **supported**: the hop is joined on the outer command and the nested command reads the joined alias, emitted as a portable `LEFT JOIN` plus a correlated subquery (no `APPLY`/`LATERAL` on SQLite or ClickHouse), at hop 1 and hop 2+, for scalar comparison, bare presence and scalar projection. This is a predicate/scalar form only — it adds no collection capability and no new join form, and ClickHouse keeps rejecting a collection reached through a reference. **Correlated eager loading is a different surface and stays unsupported**: [`EagerLoadMode.Correlated`](../relationships/eager-loading.md#correlated-and-per-parent-paging) is reserved and rejected with `NotSupportedException` during preparation — before SQL generation and before a plan entry — so no per-parent correlated graph is loaded. See [Implicit navigation queries](../relationships/implicit-navigation.md). |
| **One-to-one foreign-key uniqueness (declaration-time trust)** | The uniqueness of a one-to-one child foreign key is **declaration-time trust** — the core neither inspects the database schema or the data nor emits a uniqueness constraint, so a non-unique foreign key is accepted when the relationship is declared ([`HasOneToOne`](xref:NextORM.Core.EntityMetadataBuilder`1) or a local `JoinOptions.OneToOne`, see [Relationships](../relationships/relationships.md#one-to-one-reference)). The only guard is a per-parent runtime backstop in `JoinInto`: two distinct **non-null child identities** for one parent throw `InvalidOperationException` at materialization, while repeated identical rows and keyless/null-identity repeats are tolerated (the first child wins). Schema/unique-index validation and an optional metadata-build rejection are **out of scope** (a separately agreed feature). |
| **Selecting a joined entity as a whole** | After a join the accumulated projection is positional (`Item1`..`Item8`, one item per source in join order), so the sides carry no semantic names until you project into a named type; a wildcard `SELECT *` is never generated, comparing whole entities in a predicate and casting an item to an unrelated result type are not supported. See [Joins](../guide/04-joins.md#addressing-the-projection). |
| **Bare derived-source materialization depends on the projection's expression shape** | A subquery/derived source (`From(query)`/`From(builder)`) is read through an explicit outer `Select`; a projection-less read (`From(inner).ToList()`) is accepted only when the inner select list is already a set of resolved column references (a mapped column, a renamed projected member, a computed scalar addressed by its output name). A projection that needs re-translation — an anonymous `new { x.Id }` or a MemberInit/constructor DTO `new Dto { Id = x.Id }` — is refused during preparation with `QueryPreparationException` ("…without an explicit outer Select…"). This is an **expression-shape** restriction, not an anonymous-type requirement, and DTO projection support on a direct read does not imply bare derived-read support: add the outer `Select` (for example `Select(x => x.Id)`). This rewrite works with member-init DTO and positional-record projections; the tested constructor-only class projection has a known pre-existing failure (`Cannot find inner column Id`), so use one of those supported forms instead. See [Subqueries](../guide/07-subqueries.md#subquery-as-a-from-source) and [Query sources](../guide/01-query-sources.md#subquery-as-source). |
| **Named join aliases and the root alias** | The named path is **expression-only and SQL-providers-only**: the in-memory provider fails closed with `NotSupportedException` on **any** alias (a join alias or a root alias, mixed chains included), and a generated alias member read outside an expression tree throws `NotSupportedException` by design. `JoinInto` (the single-query relationship loader) has **no** alias surface and never takes an `Alias.<Name>` argument. The source-less (type-only) form carries an alias too — `.Join<TJoin>((left, right) => …, Alias.X[, options])` on the root `EntityBuilder<T>` and on the `JoinedEntityBuilder` receivers arities 2–7 (resulting slots 2–8) — and it is the only **join** alias form that accepts join options; `CrossJoin`/`CrossApply`/`OuterApply` take no condition and therefore stay source-explicit-only, a raw-table source is not resolvable by type, and MySQL/MariaDB still refuse `FullJoin` in every form with `NotSupportedException` (`Full join`). The flat typed chain stops at eight slots (`Projection<T1..T8>`) — a scope bound, not a compile-time rejection, because the inherited members of the generic base still compile; project the accumulated join into a named type with `As<T>` to continue past eight tables. `.WithAlias` is root-only (after a join or a second root alias it is a `NORMGEN008` compile error and a runtime fail-closed guard), and a chain whose **root or an intermediate joined step** projects an **anonymous** type is rejected with `NORMGEN009` — the **last** joined step may stay anonymous. See [Joins](../guide/04-joins.md#named-join-aliases). |
| **Correlated `APPLY` / `LATERAL` — provider support and the source cap** | A correlated [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) after a join is supported on **SQL Server** (`cross apply` / `outer apply`), **PostgreSQL** and **MySQL 8.0.14+** (`cross join lateral` / `left join lateral … on true`) on a **flat 3–8 total source** chain (2–7 preceding sources plus the applied one), on both the positional `JoinedEntityBuilder<T1..Tn>` receivers and the generated alias receivers, with `EntityBuilder<T>` or `QueryCommand<T>` lambda returns and an optional `Action<JoinOptions>`; a **ninth** correlated source is refused with `NotSupportedException` while the query is prepared — before the applied source is evaluated — instead of nesting the projection. **MariaDB 11.4 refuses both kinds before SQL execution**: it has no lateral derived table, so its dialect reports `SupportsApply == false` and the capability guard throws during preparation, before any `DbCommand` reaches the connection. SQLite and ClickHouse are refused the same way, and the in-memory provider rejects `APPLY` outright. See [Joins](../guide/04-joins.md#correlated-apply-after-a-join). |
| **[`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) / [`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) on SQL providers** | [`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) throw `NotSupportedException`; the explicit [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) join surface covers the correlated equivalent (see [Joins](../guide/04-joins.md)). |
| **Correlated scalar terminals (`First`/`Single` and their `*OrDefault` forms)** | `Single`/`SingleOrDefault` over more than one row throw on every provider whose scalar subqueries enforce cardinality (PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse); SQLite does not enforce it, so a numeric `Single`/`SingleOrDefault` over more than one row raises a database error through a rendered `case when count(*) > 1 then <numeric overflow> else value end` guard, and a non-numeric projection is rejected with `NotSupportedException`. `First`/`Single` on a non-nullable value projection throw when no row matches. |
| **Locking table hints outside SQL Server** | A locking table hint (`WithTableHint("nolock")` → `WITH (NOLOCK)`) is applied on SQL Server only, on the query's `FROM` table or on a single join through `JoinOptions.WithJoinTableHint`; the native index hints of MySQL/MariaDB (`USE`/`FORCE`/`IGNORE INDEX`), SQLite (`INDEXED BY`/`NOT INDEXED`) and SQL Server (`WITH (INDEX(...))`) are a separate surface ([`WithIndex`](../guide/15-query-hints.md#index-hints), [`ISqlDialect.IndexHints`](xref:NextORM.Core.ISqlDialect.IndexHints)). SQLite and ClickHouse reject `Hint(...)` with `NotSupportedException`, and the same gates apply to join (`JoinOptions.WithJoinHint`), subquery (`FromOptions.WithSubQueryHint`) and tables-in-scope (`WithTablesInScopeHint`) hints; SQL Server additionally rejects a subquery hint, because T-SQL cannot append one to a subselect (see [Query hints](../guide/15-query-hints.md)). |
| **MariaDB has no source-level row lock (`FOR UPDATE OF`)** | A source-level lock ([`FromOptions.ForUpdate`](xref:NextORM.Core.FromOptions.ForUpdate)/[`FromOptions.ForShare`](xref:NextORM.Core.FromOptions.ForShare), [`JoinOptions.ForUpdate`](xref:NextORM.Core.JoinOptions.ForUpdate)/[`JoinOptions.ForShare`](xref:NextORM.Core.JoinOptions.ForShare)) requires a dialect whose [`ILockRenderer.SupportsSourceLocks`](xref:NextORM.Core.ILockRenderer.SupportsSourceLocks) is `true` (PostgreSQL, MySQL, SQL Server). MariaDB's grammar has no `FOR UPDATE OF`/`FOR SHARE OF`, so a source-level lock is rejected deterministically with `NotSupportedException` (fail-closed): it is never silently ignored, replaced by a whole-query lock, or emitted as an unsupported `OF`. SQLite and ClickHouse have no row locking at all and reject both a whole-query and a source-level lock. |
| **SQL Server whole-query lock hints every source** | A whole-query [`ForUpdate`](xref:NextORM.Core.EntityBuilder`1.ForUpdate)/[`ForShare`](xref:NextORM.Core.EntityBuilder`1.ForShare) places the `with (updlock)`/`with (holdlock)` hint on **every** physical `FROM`/`JOIN` source (previously the primary source only), so a multi-table query locks more tables than before; a source-level lock keeps the hint on the chosen source. |
| **SQL Server `WITH TIES` with a positive `OFFSET`** | T-SQL accepts `WITH TIES` only in `TOP(n)`, never in `OFFSET … FETCH`, so the combination is refused while the query is prepared — before any SQL is rendered, sent or cached — with `NotSupportedException` (`SQL Server does not support WITH TIES with a non-zero OFFSET. Use WithTies() without OFFSET.`). There is no emulation and no silently dropped tie expansion: use `WithTies()` without an `OFFSET` (the `TOP(n) WITH TIES` form) or ordinary paging without ties. See [Sorting and paging](../guide/06-sorting-and-paging.md). |
| **Explicit NULL placement where the `CASE` emulation cannot repeat the key** | [`NullsPosition`](xref:NextORM.Core.NullsPosition)`First`/`Last` is native on SQLite, PostgreSQL and ClickHouse but emulated on SQL Server, MySQL and MariaDB with `CASE WHEN <key> IS NULL … END ASC, <key>`, which repeats the ordering key. There an explicit placement on a `DISTINCT`/`DISTINCT ON` query — or together with ClickHouse-style `LIMIT BY` — fails closed with `BuildSqlCommandException` before execution, because the repeated key is not a select-list expression; the placement is never silently dropped. A provider with native support repeats nothing, so `DISTINCT`, `DISTINCT ON` and `LIMIT BY` keep the native modifier there. Use `NullsPosition.Default` or a native provider on those shapes. See [Sorting and paging](../guide/06-sorting-and-paging.md#null-ordering-and-placement). |
| **Upper-case SQL keywords — tuple/row constructors stay provider-canonical** | With `KeywordCase.Upper` (`DataContextBuilder.UseKeywordCase`, `EntityBuilder<TEntity>.WithKeywordCase`, `QueryCommand<T>.WithKeywordCase`) every core, translator, dialect and capability keyword is upper-cased, but the row/tuple constructors `ROW(...)` (PostgreSQL) and `tuple(...)` (ClickHouse) are treated as function-like constructors and keep the provider's canonical spelling. Identifiers, string literals, function names, type names and raw SQL are never affected. |
| **Statement layout is not configurable** | Every generated `SELECT` — the top level and nested forms (a derived-table `FROM`, a CTE body, the `SELECT` inside `INSERT ... SELECT`/`CREATE TABLE ... AS SELECT`) — starts its `FROM` and each `JOIN` on a new line, unconditionally: there is no opt-in flag, no indentation level and no blank lines. Generated SQL uses `\n` only — never `\r` — on every provider and every OS. Raw SQL you pass through (`WithSql`, `WithTableExpression`, `ExecuteRaw`, `Raw`, procedure text), string literals and parameter values are **never** reflowed: nextorm does not parse or reformat opaque input. |
| **Server-side array/JSON element access (`x[i]`)** | Only a captured (closed-over) collection indexed inside the query is supported ([captured collection lookup](../guide/03-filtering-where.md#captured-collection-lookup-dictcolumn)): a constant key folds to a parameter and a column key renders a portable `CASE`. Element access on a server-side array/JSON column or an array-returning expression (`groupArray(x)[0]`, `array_agg(x)[1]`, `json['k']`) has no portable SQL form and throws `NotSupportedException` (a custom indexer likewise) instead of binding the whole collection. The native forms differ (`arr[i]` on PostgreSQL, `arrayElement(arr, i)` on ClickHouse, JSON paths elsewhere), so they would need a separate dialect hook. |
| **ClickHouse native `JSON` column type** | The native `JSON` *column* type is object-rooted: an array or scalar root fails closed, and a bare `string` read over a `JSON` column is not supported — nor is the legacy `Object('json')` alias, which needs a connection-level `allow_experimental_object_type` that nextorm never sets (and even then reads materialize as `Tuple<SByte,String>`). A JSON projection must be a **named shape** (`Select(x => new { x.Doc })` or a DTO), because a bare top-level scalar `Select(x => x.Doc)` is not handled by the core projection classifier. See [JSON support](../guide/16-json.md#map-a-clr-object-to-a-native-json-column). |
| **MySQL/MariaDB JSON columns and `JsonColumnStorage.Native`** | nextorm does not generate column DDL: a `json` column must already exist, declared by you. MySQL 8 has a real `json` type and MariaDB's `JSON` is a `LONGTEXT` alias with a `json_valid()` CHECK (reported as `longtext`); both are supported through the **text** storage (`Auto`/`Text`), because `MySqlConnector` cannot bind `JsonElement`/`JsonDocument`/`JsonNode` (`MySqlDbType.JSON` accepts strings only) and always reads the column back as `string`. An explicit `Native` is refused on both engines with a `NotSupportedException` naming the dialect, before any command runs. MySQL compares a `json` document as a typed value — a string operand does not equal it — and the `Text` storage does no equality translation. See [JSON support](../guide/16-json.md#map-a-clr-object-to-a-native-json-column). |
| **SQL Server native `json` column — scalar roots and the JSON `null` document** | SQL Server 2025+ has a distinct `json` type, but a native `json` column accepts **object and array documents only**: a scalar root (string, number, boolean) and the JSON `null` document are rejected by the **server** with error **13609**, at execution. That is a server limitation, not a library refusal — nextorm adds no client-side rule — so use the text storage (`Auto`/`Text`) for such payloads. The native type is reachable only from a context built with an explicit `Version(17, 0)` or higher; the default unversioned context and 2016–2022 contexts stay text-only, and `Native` there throws the dialect-named `NotSupportedException` before any command runs. nextorm generates no column DDL, so moving a column to `json` is a migration step. See [JSON support](../guide/16-json.md#native-json-on-sql-server-2025). |
| **Azure SQL DB/MI/Fabric — native `json` is not activatable** | Azure SQL Database, Azure SQL Managed Instance and Microsoft Fabric are built on the same engine and support the native `json` type, but they report `SERVERPROPERTY('ProductMajorVersion') = 12`, so the version argument cannot identify them: there is no supported way for a context to declare "Azure/Fabric, native `json` available" and the capability stays off. Tracked in [#345](https://github.com/AlexeyShirshov/nextorm/issues/345). |
| **`untuple` (ClickHouse)** | `untuple(tuple)` is not mapped: it expands a tuple into several result columns, which has no single scalar CLR shape in a projection. Project the `Tuple(...)` as `System.Tuple<...>` and read its elements with `tupleElement`/`System.Tuple<...>.ItemN` instead. |
| **Row-value (tuple) surface: remaining restrictions** | Relational operands (`<`/`>`/`<=`/`>=`) and relational `ValueTuple` operands are inexpressible in C#/expression trees (a language boundary, not a product limitation). On MySQL/MariaDB/SQLite a row constructor in `Select`/`ORDER BY`/`GROUP BY` or as a function argument, and any server-side `.ItemN`, throws `NotSupportedException` at preparation (naming the provider); SQL Server rejects constructors **and every tuple `IN`/`Contains` form** up front with `NotSupportedException` (`SQL Server does not support tuple IN/Contains translation.`), including a null collection, a null reference-tuple entry, arity ≥8 and nested tuples, so no evaluation error can surface there. On the supporting providers a nullable tuple element (`List<(int, int)?>`) throws `NotSupportedException`, arity ≥8/`Rest`/nested tuples throw `NotSupportedException`, and a tuple-typed `QueryCommand` (subquery) right-hand side is deferred (not supported yet, no future milestone promised). Materialising a raw `ROW(...)`/row value is PostgreSQL-only: `ValueTuple`, arity ≥8, a nested or empty `ROW`, several or mixed record columns, an unregistered named composite and a named composite declared as `System.Tuple` remain guarded with `NotSupportedException` (see [Raw SQL](../guide/14-raw-sql.md#postgresql-raw-rows-and-composites) and [Scalar functions](../scalar-functions/index.md)). A **top-level** generic `ValueTuple.Create(...)` factory call and an explicit `new ValueTuple<...>(...)` construction are unsupported projections in their own right: both are refused during preparation with a `NotSupportedException` that names the projection type and the `Select` position, before any SQL is rendered or a database is touched — project an explicit DTO or anonymous shape instead. `Tuple.Create` is not a universal substitute (it keeps the provider/context restrictions above), and no nested tuple support is claimed. See [Projections](../guide/02-projections.md#tuple). |
| **Binding the element of several `ARRAY JOIN` expressions at once (ClickHouse)** | [`ArrayJoinElement`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.ArrayJoinElement``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,System.Collections.Generic.IEnumerable{``1}}}))/[`LeftArrayJoinElement`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.LeftArrayJoinElement``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,System.Collections.Generic.IEnumerable{``1}}})) bind the element of exactly one array expression to `p.Element`: a second call, a call on a joined query, or a call after `Where`/`Having` throws `InvalidOperationException`. | **Dynamic columns - write side** | The **read side** is implemented: a writable property assignable from `Dictionary<string, object?>` marked with [`DynamicColumnsAttribute`](xref:NextORM.Core.DynamicColumnsAttribute) (or the fluent `EntityPropertyBuilder<T>.DynamicColumnsStore`) receives the row's unmapped columns when the entity is queried as a whole - the statement renders `select <mapped>, *` (``select t1.<mapped>, `t1`.*`` on MySQL/MariaDB, whose dialect alias-qualifies the star via `RequiresQualifiedSelectStar`) and the store is materialised from the result set on every SQL provider (see [Dynamic columns](../guide/29-dynamic-columns.md)). **The write side is implemented for `INSERT`, `UPDATE` and `MERGE`**: the store's dictionary keys are rendered as physical columns and their values as bound parameters. Keys are ordinal-sorted, so the column order is deterministic; every dynamic key is identifier-quoted with the dialect's quoting even when the global identifier-quoting option (`UseQuotedIdentifiers`) is off, and the naming convention is skipped (the key is used as the physical column name); an empty key or a key containing a NUL character is rejected. Both decimal array **result** shapes are materialised since [#337](https://github.com/AlexeyShirshov/nextorm/issues/337): `Array(Nullable(Decimal(38,10)))` → `decimal?[]` and `Array(Decimal(38,10))` → `decimal[]`, through the direct, member-bound, multi-column and raw read routes, with every representable value preserved exactly; a `Decimal(38,10)` element whose scaled mantissa exceeds 96 bits (for example `1e19`, whose mantissa at scale 10 is `1e29` while CLR `decimal`'s mantissa is `2^96 − 1`) fails closed with the driver's `OverflowException` (`Value cannot be represented as System.Decimal`), because the pinned driver does not trim trailing zeros and a mathematically smaller representation is not substituted. See [Arrays (ClickHouse)](../scalar-functions/06-arrays.md#arrays-clickhouse). |
| **Percentiles and median (`percentile_cont`/`percentile_disc`/`median`/`percentile`) — per-provider refusals** | The four names are not portable and are never emulated. **SQLite** refuses all four: the shipped build has no `median` aggregate and reports `SQLITE_ENABLE_PERCENTILE=0`, and nextorm produces no window rewrite or custom aggregate in its place. **MySQL** refuses all four: it has neither the functions nor the `WITHIN GROUP` grammar (`PERCENTILE_CONT` is MariaDB-only), so `SqlFunctions.MySql.median(v).Over(...)` and `SqlFunctions.MySql.percentile(fraction, v)` throw with the provider named. **ClickHouse** supports only the native `median` aggregate (the `quantile` family, approximate) and refuses the percentile names; no `quantile*` alias is created. **SQL Server** and **MariaDB** expose only the analytic `percentile_cont(f) within group (order by x) over (...)` shape (one row per input row, partition-only `OVER`; a window `ORDER BY` or a frame is refused), while **PostgreSQL** exposes the ordered-set aggregate (one row per group, never `OVER`) and refuses a non-floating-point sort expression for the interpolating `percentile_cont`/`median`. The generic `percentile(fraction, value)` is refused by every provider — it never aliases the continuous form — and a fraction is always `[0, 1]`, never a 0–100 percentage (finite and constant; a row-dependent fraction is refused). |

## Known edge cases

- **Same-name closure-variable collision.** A captured variable read by a global query filter and a different captured variable read by the user's `On(...)` that share the same CLR name render as the same parameter name, so the placeholders collide; rename one of the variables.
- **Raw-source filter binding is best-effort and unverified.** `FromSql`/`From(string)` apply a global filter only after [`BindEntity<TEntity>`](xref:NextORM.Core.EntityBuilderExtensions.BindEntity``1(NextORM.Core.EntityBuilder{NextORM.Core.TableAlias},System.Collections.Generic.IReadOnlyCollection{System.String})) declares the entity type and the output columns; a filter whose required columns are missing is skipped with a `RawSourceFilterSkipped` warning on the `NextORM.QueryFilters` category (reason `MissingColumns`, physical mapped column names) instead of throwing, while with an empty declared-column list a filter with a proven zero-column dependency is still applied and a column-dependent or undetermined filter is skipped with reason `UndeterminedColumns`. The column list is the caller's word — nextorm neither parses the raw SQL nor validates it against a schema, so a declared column the fragment does not actually return is accepted and can make a filter run against the wrong shape. Binding is not a security guarantee; a provider without raw-source support rejects the source. See [Filters on bound raw sources](query-filters.md#filters-on-bound-raw-sources).

## Not limitations

The following are fully implemented and verified; they are documented on their own pages and are not
limitations:

- joins of every type (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, plus `CROSS APPLY`/`OUTER APPLY` and the lateral equivalent where supported, including a correlated apply after a join on a flat 3–8 source chain; no `FULL JOIN` on MySQL/MariaDB) and arity 2–8, including a derived query as either side (the primary `FROM` source or the joined table);
- derived/subquery sources read through an explicit outer `Select`, including renamed and computed inner columns (see [Subqueries](../guide/07-subqueries.md#subquery-as-a-from-source)), and DTO/record/constructor projections on a direct read (see [Projections](../guide/02-projections.md#dto)) — the expression-shape restriction above concerns only a *projection-less* read of a derived source;
- correlated scalar subqueries and correlated `EXISTS`/`IN`/`ANY`/`ALL` in `SELECT`, `WHERE`, `ORDER BY` and `HAVING` on every SQL provider at any nesting depth (see [Subqueries](../guide/07-subqueries.md));
- `CASE WHEN` / ternary / `switch`, `COALESCE`, numeric `CAST`;
- string, math and date/time scalar functions and `LIKE`;
- the cross-provider scalar string/number functions ([`SqlFunctions.Sql`](xref:NextORM.Core.SqlFunctions.Sql) `left`/`right`/`lpad`/`rpad`/`repeat`/`reverse`/`space`/`concat_ws`/`translate`/`ascii`/`@char`), with the per-name gates above;
- date arithmetic (`date_add`/`end_of_month`/`date_diff`/`date_from_parts` and `DateTime.Add*`) on PostgreSQL, SQL Server, ClickHouse, MySQL/MariaDB and SQLite, plus `date_trunc` on PostgreSQL/SQL Server/ClickHouse and `string_agg` on PostgreSQL/SQL Server/ClickHouse/MySQL/MariaDB/SQLite;
- server-side `DateTimeOffset` translation — `.Now`/`.UtcNow`, the seven date parts and the seven `Add*` members on every SQL provider (the client clock/local time zone is never used; only SQL Server preserves the offset) (see [Date and time](../scalar-functions/03-date-and-time.md#datetimeoffset));
- the bitwise (`bit_and`/`bit_or`/`bit_xor`), statistical (`corr`/`covar_*`) and `argMin`/`argMax` aggregates on ClickHouse;
- binary columns - a `byte[]` property or projection maps to `bytea` (PostgreSQL), `varbinary`/`image` (SQL Server) or `blob` (SQLite);
- LOB streaming on PostgreSQL, SQL Server and SQLite - a single `byte[]`/`string` column is read as a `Stream`/`TextReader` with `CommandBehavior.SequentialAccess` and O(buffer) memory, without materialising the whole value (on SQLite the query source must expose `rowid`), and PostgreSQL, SQL Server and SQLite additionally hand a multi-column result over as a caller-owned `DbDataReader` through `ToDataReader`/`ToDataReaderAsync` (on SQLite that reader is buffered and locator-free, so a LOB column is read whole rather than chunked);
- unsigned 64-bit integer columns - a `ulong`/`ulong?` property or projection materialises through the row reader's `DbDataReader.GetFieldValue<ulong>` accessor on providers with a native unsigned type (ClickHouse `UInt64`, MySQL/MariaDB `BIGINT UNSIGNED`), with no SQL cast; PostgreSQL, SQL Server and SQLite have no unsigned integer type and expose that range only as `numeric`/`decimal`;
- `IN` over a list/array, logical `!` and unary operators;
- `SELECT DISTINCT`, `INTERSECT`/`EXCEPT`, CTEs (including recursive), window functions and `GROUP BY ROLLUP`/`CUBE`/`GROUPING SETS` (`CUBE`/`GROUPING SETS` not on MySQL/MariaDB);
- data-modifying CTEs (`WITH n AS (INSERT|UPDATE|DELETE ... RETURNING ...)`, single-table and join/multi-table) on PostgreSQL, read typed through [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1) (see [data-modifying CTE](../guide/17-insert-statement.md#data-modifying-cte-postgresql));
- `OUTPUT ... INTO <target>` on SQL Server — `Returning(...).OutputInto(target)` writes the modified rows into an existing table, `Returning(...).OutputIntoThenOutput(target)` writes them and returns them to the client (see [insert guide](../guide/17-insert-statement.md#writing-the-modified-rows-into-a-table-output-into));
- key-upsert `Returning()` — PostgreSQL/SQLite append `RETURNING` to `ON CONFLICT ... DO UPDATE`, SQL Server renders `MERGE ... OUTPUT`; MySQL/MariaDB reject it with `NotSupportedException` (see [upsert](../guide/21-merge-statement.md#returning-the-merged-rows));
- user-defined scalar functions (`[SqlFunction]`) and table-valued-function runtime factories (`TvfEntityBuilder<T>`);
- the ClickHouse server/cluster table functions `url`/`s3`/`file`/`remote`/`remoteSecure`/`cluster`/`clusterAllReplicas`, pre-declared on `SqlFunctions.ClickHouse.*` with a caller-declared generic `TRow` row interface (they are gated by [`SupportsTableFunction`](xref:NextORM.Core.ISqlDialect.SupportsTableFunction(System.String)); see [Table-valued functions](../guide/13-table-valued-functions.md#built-in-table-functions));
- full-text predicates (`SqlFunctions.Sql.contains`/`freetext`) on SQL Server, PostgreSQL and MySQL/MariaDB, full-text ranking (SQL Server `containstable`/`freetexttable` with `KEY`/`RANK`, PostgreSQL `ts_rank`/`ts_rank_cd`), text-JSON functions (`json_value`/`json_query`/`json_modify`/`isjson`) on SQL Server and MySQL/MariaDB and the SQL Server `openjson`/`string_split` table functions (plus user-declared `TvfEntityBuilder<T>` factories, including MySQL `JSON_TABLE` via `callClause`); the cross-provider `contains`/`freetext` predicates stay unsupported on SQLite (it throws), whose own SQLite-specific FTS3/FTS4/FTS5 query surface (`Match`, FTS5 `FTS5bm25`/`Highlight`/`Snippet`/`Rank`, FTS3/4 helpers and the FTS5 table-valued `MatchTable` `FROM` source) is available, together with the SQLite-only FTS5 maintenance command builder (`CreateSqliteFts5CommandBuilder`: `AutoMerge`/`CrisisMerge`/`Merge`/`Optimize`/`Rebuild`/`IntegrityCheck`, with sync/async terminals);
- statement-level query hints on SQL Server (`OPTION (...)`), PostgreSQL and MySQL/MariaDB (`/*+ ... */`), table hints on SQL Server (`Hint(...)`, `WithTableHint(...)`, the per-join `JoinOptions.WithJoinTableHint(...)`), join/subquery/tables-in-scope hints (`JoinOptions.WithJoinHint`, `FromOptions.WithSubQueryHint`, `WithTablesInScopeHint`), JSON output (`ForJson(...)` → `FOR JSON PATH`/`AUTO`) and XML output (`ForXml(...)` → `FOR XML`);
- the XML data-type methods on SQL Server (`xml_value`/`xml_query`/`xml_exist` → `xml.value('xpath', 'type')`/`xml.query('xpath')`/`xml.exist('xpath')`, and the `.nodes` rowset via `xml_nodes` as a `CrossApply`/`OuterApply` source);
- raw SQL as a whole query ([`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)) / [`PrepareFromSql`](xref:NextORM.Core.EntityExtensions.PrepareFromSql``1(NextORM.Core.EntityBuilder{``0},System.String))) and as a composable `FROM` source ([`FromSql`](xref:NextORM.Core.DataContextExtensions.FromSql(NextORM.Core.IDataContext,System.String,System.Object)), rendered as a derived table), plus the implicit plan cache / [`Prepare`](xref:NextORM.Core.EntityBuilderExtensions.Prepare``1(NextORM.Core.EntityBuilder{``0},NextORM.Core.PrepareOptions,System.Threading.CancellationToken)) reuse paths;
- raw command execution against the context (`ExecuteRaw`/`ExecuteRawAsync`, and stored procedures through `ExecuteProcedure`/`ExecuteProcedureAsync`, returning a disposable `ProcedureResult`) with named/`DbType`/`Size` parameters, sequential result sets, and output/return-value parameters (see [Raw SQL](../guide/14-raw-sql.md#executing-raw-commands-executeraw));
- per-query source overrides (`WithTableName`/`WithSchema`/`WithDatabase`/`WithServer`/`WithTableExpression`) on every SQL provider, part of the plan-cache key (see [Per-query source overrides](../guide/01-query-sources.md#per-query-source-overrides)).
