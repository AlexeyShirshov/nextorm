# Построение запроса: fluent к SQL

> Здесь прослеживается путь от цепочки вызовов построителя к SQL конкретного провайдера. Построитель записывает описание запроса в [`QueryCommand<TResult>`](xref:NextORM.Core.QueryCommand`1); `QueryPreparer` формирует подготовленные части запроса и ключ `QueryPlan`, а затем `SqlBuilder` строит SQL с учётом диалекта провайдера. Полный путь, включая исполнение и результат, описан в [обзоре движка](index.md).

## Построенная команда

`ctx.From<TEntity>()` — одна из фабрик построителей контекста (см. [точки входа построителей](index.md#точки-входа-построителей)). Она возвращает [`EntityBuilder<TEntity>`](xref:NextORM.Core.EntityBuilder`1). Каждый метод цепочки (`Where`, `Join`, `Select`, `OrderBy`, `GroupBy`, `With` и методы задания хинтов) записывает часть запроса в [`QueryCommand<TResult>`](xref:NextORM.Core.QueryCommand`1). На этом этапе команда лишь описывает запрос: она не является открытым соединением и ничего ещё не исполняет.

Остальные фабрики создают построители других команд (`InsertBuilder<T>`, `UpdateBuilder<T>`, `DeleteBuilder<T>`, `MergeBuilder<T>`, `BatchBuilder`, ...). Отдельные пути формируют и выполняют команды изменения данных и батчи; кэш планов из этой страницы к ним не относится. Здесь рассматривается путь `SELECT`.

Остальную часть конвейера запускает терминал (`ToListAsync`, `FirstAsync`, `ToAsyncEnumerable`, ...). `Select` задаёт для команды тип `TResult`, и терминалы возвращают именно такую проекцию.

## Подготовка

Подготовка превращает записанный запрос в части, которыми пользуются следующие этапы. `QueryPreparer` обрабатывает источник и соединения, колонки и проекцию, `WHERE` и pre-`WHERE`, группировку, сортировку, CTE и хинты; он же вычисляет хэши для ключа плана. Подготовка выполняется до поиска в кэше. После неё команда хранит подготовленные части и текущий хэш плана.

Для преобразования записанных выражений `QueryPreparer` использует обходчики выражений — проходы, которые обходят и преобразуют части их структуры. Например, `CorrelatedQueryExpressionVisitor` переписывает коррелированные подзапросы, а обходчики для `WHERE` и базовых выражений переводят предикаты. Результат — внутреннее описание выборки (`SelectExpression`), которое `SqlBuilder` затем преобразует в SQL.

## Ключ плана

`QueryPlan` фиксирует *структурную форму* запроса, а не значения времени выполнения. Вызовы с разными экземплярами лямбды, но одинаковой формой получают один ключ: кэш может повторно использовать план, даже когда значения параметров меняются. [`QueryPlanStore`](03-plan-cache-and-reuse.md) хранит планы в кэше, отдельном для каждого потока, с ключом `(тип контекста, QueryPlan)`. Чтобы отключить поиск для одной команды, используйте `QueryCommand<TResult>.Cache`; правила описаны на странице [Кэш планов и переиспользование](03-plan-cache-and-reuse.md).

## Генерация SQL

`SqlBuilder` формирует подготовленную команду через `ISqlDialect` провайдера и получает SQL-текст с упорядоченным списком параметров. Диалект преобразует одну и ту же форму запроса в SQL для SQLite, SQL Server, PostgreSQL, MySQL/MariaDB или ClickHouse; см. [SQL для конкретных провайдеров](../guide/provider-specific-sql/overview.md). На следующем этапе параметры привязываются к `DbCommand` (см. [исполнение и строки](02-execution-and-rows.md)).

## In-memory

[Провайдер in-memory](../connecting-providers/in-memory.md) исполняет ту же команду и проекцию без SQL: нет ни диалекта, ни `DbCommand`, поэтому подготовленное выражение компилируется и вычисляется прямо по данным в памяти.
