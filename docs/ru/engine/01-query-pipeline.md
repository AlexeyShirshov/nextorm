# Построение запроса: fluent к SQL

> Как fluent-запрос превращается в SQL-текст и ключ плана. [`QueryCommand<TResult>`](xref:NextORM.Core.QueryCommand`1) строится fluent-поверхностью, подготавливается `QueryPreparer` (через expression-visitors), получает ключ `QueryPlan` и рендерится `SqlBuilder` против диалекта провайдера. Общая картина — в [обзоре движка](index.md).

## Построенная команда

`ctx.From<TEntity>()` — одна из фабрик построителей на контексте (все перечислены в разделе [точки входа построителей](index.md#точки-входа-построителей)); она возвращает [`EntityBuilder<TEntity>`](xref:NextORM.Core.EntityBuilder`1). Каждый fluent-оператор (`Where`, `Join`, `Select`, `OrderBy`, `GroupBy`, `With`, хинты, ...) записывает часть намерения в [`QueryCommand<TResult>`](xref:NextORM.Core.QueryCommand`1). Пока ничего не исполняется — команда это описание запроса, а не живое соединение.

Остальные фабрики открывают другие формы утверждений и возвращают свои построители (`InsertBuilder<T>`, `UpdateBuilder<T>`, `DeleteBuilder<T>`, `MergeBuilder<T>`, `BatchBuilder`, ...). Такие утверждения рендерятся и исполняются путями мутаций и батчей, а не кэшем планов, о котором здесь речь; эта страница идёт по пути `SELECT`.

Именно вызываемый терминал (`ToListAsync`, `FirstAsync`, `ToAsyncEnumerable`, ...) прогоняет команду через остальной конвейер. Один и тот же тип команды несёт проекцию, так что `Select` фиксирует `TResult` один раз, и терминалы возвращают эту форму.

## Подготовка

`QueryPreparer` обходит записанные части и превращает их в подготовленные фрагменты клауз плюс хэши, образующие ключ плана: источник и соединения, колонки/проекция, `WHERE` / pre-`WHERE`, группировка, сортировка, CTE и хинты. Подготовка идёт до поиска в кэше, поэтому после неё команда несёт подготовленные фрагменты и актуальный хэш плана.

Дерево выражений транслируется expression-visitors — например `CorrelatedQueryExpressionVisitor` переписывает коррелированные подзапросы, а `WHERE`/базовые visitors управляют трансляцией предикатов. На выходе — внутреннее описание выборки (`SelectExpression`), которое рендерит SQL-билдер.

## Ключ плана

`QueryPlan` фиксирует *структурную форму* запроса, а не его значения времени выполнения. Два вызова с разным экземпляром лямбды, но одной формой дают один ключ и потому попадание в кэш; значения параметров времени выполнения переносятся отдельно. [`QueryPlanStore`](03-plan-cache-and-reuse.md) хранит планы в потоково-локальном кэше с ключом `(тип контекста, QueryPlan)`. Отключить поиск для одной команды можно через `QueryCommand<TResult>.Cache`; правила описаны на странице [Кэш планов и переиспользование](03-plan-cache-and-reuse.md).

## Генерация SQL

`SqlBuilder` рендерит подготовленную команду через `ISqlDialect` провайдера, получая SQL-текст и упорядоченный список параметров. Именно диалект делает так, что одна и та же форма компилируется в SQL для SQLite, SQL Server, PostgreSQL, MySQL/MariaDB или ClickHouse — см. [Провайдер-специфичный SQL](../guide/provider-specific-sql/overview.md). Параметры привязываются к реальному `DbCommand` на следующем этапе ([исполнение и строки](02-execution-and-rows.md)).

## In-memory

[Провайдер in-memory](../connecting-providers/in-memory.md) исполняет ту же команду и проекцию без SQL: нет ни диалекта, ни `DbCommand`, поэтому подготовленное выражение компилируется и вычисляется прямо по данным в памяти.
