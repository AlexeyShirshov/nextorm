# Исполнение и строки

> Что происходит после появления SQL: `DbCommand` исполняется, `DbDataReader` читается, а результат формируется — материализуется в объекты или коллекции, сворачивается в одну строку или агрегат, передаётся потоком, сериализуется в JSON/CSV или отдаётся «сырым». Общая картина — в [обзоре движка](index.md).

## Исполнение команды

Подготовленный SQL-текст привязывается к провайдерному `DbCommand` (создаётся через `DataContext.CreateCommand`, параметры добавляются по порядку) и запускается `QueryExecutor` через ADO.NET `ExecuteReader`. Команда и получившийся `DbDataReader` владеются вместе (`CommandReaderOwner`), поэтому ридер и его команда освобождаются как одно целое.

## Материализация

Когда проекции нужны объекты, маппер строк, скомпилированный `RowMapperFactory`, читает каждую строку из `DbDataReader` и строит сущность, DTO, record, кортеж или анонимный тип — формы описаны в разделе [Проекции](../guide/02-projections.md). Маппер компилируется один раз на форму плана и переиспользуется для каждой строки.

Nullable-скаляр агрегата материализуется как `null`. Если проекция — nullable-значимый тип (четыре семейства вариативности `Stdev`/`Stdevp`/`Var`/`Varp` — первые агрегаты, возвращающие `T?`), nullable-путь чтения маппера защищает геттер значения проверкой `IsDBNull`, поэтому SQL `NULL` доходит до вызывающего как `null`, а не бросает исключение из незащищённого геттера. Объявленный `T?` терминала и nullable-проекция — одно решение: `AggregateTerminalRewriter` проецирует агрегат как `Nullable<T>`, когда параметр агрегата — `T?`.

## Терминалы и формы результата

| Терминал | Результат |
|---|---|
| `ToList` / `ToArray` / `ToHashSet` / `ToDictionary` | **Буферизованная коллекция**: каждая строка материализуется в список, массив, множество или словарь. |
| `First` / `FirstOrDefault`, `Single` / `SingleOrDefault`, `Last` / `LastOrDefault` | **Одна строка**: одна материализованная строка (или `default`). |
| `Count` / `LongCount`, `Sum` / `Avg` / `Min` / `Max`, `Stdev` / `Stdevp` / `Var` / `Varp` | **Агрегат**: запрос переписывается в скалярный `SELECT` (`COUNT(*)`, `SUM(...)`, ...) и возвращается одно значение; построчно ничего не материализуется. |
| `Any` / `ExecuteScalar` | **Скалярная проверка или значение**: `bool` либо значение единственной проекционной колонки. |
| `ToEnumerable` / `ToAsyncEnumerable` / `Pipeline` | **Поток**: строки материализуются лениво по мере перебора. |
| `WriteJson` / `WriteCsv` | **Сериализация**: строки пишутся напрямую из ридера в JSON или CSV **без материализации**. |
| `ToDataReader` / `ToStream` / `ToTextReader` | **«Сырой» результат**: вызывающему отдаётся исходный `DbDataReader`, `Stream` или `TextReader`; он же им владеет и освобождает. |
| `Prepare` | **Компиляция без исполнения**: возвращает `IPreparedQueryCommand<TResult>` (см. [кэш планов и переиспользование](03-plan-cache-and-reuse.md)). |

Все терминалы существуют в синхронной и асинхронной форме (`ToList`/`ToListAsync`, `ToEnumerable`/`ToAsyncEnumerable`, `WriteJson`/`WriteJsonAsync`, ...); единственный без асинхронной пары — `Prepare`. Кроме `Prepare`, они принимают параметры запроса позиционно. Буферизованные и потоковые терминалы переиспользуют один и тот же план; различается лишь момент материализации. Сериализующие терминалы полностью обходят маппер строк. Агрегатные терминалы объявлены на построителе сущности (`ctx.From<T>()`) и принимают селектор — у `Count()`/`LongCount()` его нет, — а `ToDataReader`, `ToStream`, `ToTextReader` и `Pipeline` объявлены на `QueryCommand<TResult>`, который возвращает `Select`.

Построители мутаций (`CreateInsertBuilder`/`CreateUpdateBuilder`/`CreateDeleteBuilder`/`CreateMergeBuilder`/`CreateBulkInsertBuilder`) показывают ту же идею с другой стороны: `ToSql()` рендерит утверждение, не исполняя его, а `Insert()`/`Update()`/`Delete()`/`Merge()`/`BulkInsert()` — их исполняющие терминалы; см. главы Руководства из раздела [точки входа построителей](index.md#точки-входа-построителей).

## In-memory

[Провайдер in-memory](../connecting-providers/in-memory.md) даёт те же формы результата без `DbDataReader`: скомпилированный запрос перебирает данные в памяти, а материализатор строит объекты напрямую.
