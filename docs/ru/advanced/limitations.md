# Ограничения и возможности вне области охвата

> nextorm — построитель запросов с небольшой явной поверхностью DML: он генерирует инструкции `SELECT` (и параметризованные `INSERT ... VALUES`, `INSERT ... SELECT`, key upsert и `DELETE`) и материализует их результаты, и намеренно оставляет отслеживание изменений, `UPDATE` и полный `MERGE` с ветками вызывающей стороне.

**Предварительные требования:** [Provider overview](../providers/overview.md) · [API reference](api-reference.md)

## Обзор

На этой странице перечислены возможности, которые **не** являются частью nextorm, с однострочной причиной для каждой.

## Вне области охвата

| Не поддерживается | Обоснование |
|---|---|
| **DML** — `INSERT`, `UPDATE`, `DELETE`, `MERGE` | **`INSERT ... VALUES`, `INSERT ... SELECT` и key upsert реализованы** ([`InsertInto`](../guide/19-insert-statement.md); возврат строк через `RETURNING`/`OUTPUT` на PostgreSQL, SQLite и SQL Server, строки батча неупорядочены; серверный источник поднимает свои CTE перед `INSERT` и отклоняет рантайм-плейсхолдеры `SqlFunctions.Parameter`). PostgreSQL также поддерживает **модифицирующие CTE** (`With(имя, insert)` → [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1), [модифицирующий CTE](../guide/19-insert-statement.md#модифицирующий-cte-postgresql)). **Upsert** ([`MergeInto`](xref:NextORM.Core.DataContextExtensions.MergeInto``1(NextORM.Core.IDataContext,System.Action{NextORM.Core.EntityMetadataBuilder{``0}})) → [`MergeBuilder<T>`](xref:NextORM.Core.MergeBuilder`1), [upsert](../guide/19-insert-statement.md#upsert-key-merge)) рендерит родную форму провайдера — `INSERT ... ON CONFLICT ... DO UPDATE` (PostgreSQL, SQLite), `INSERT ... ON DUPLICATE KEY UPDATE` (MySQL, MariaDB) или `MERGE ... USING (VALUES ...)` (SQL Server); ClickHouse и провайдер in-memory его отклоняют. **`DELETE`** ([`DeleteFrom`](../guide/20-delete-statement.md) → [`DeleteBuilder<T>`](xref:NextORM.Core.DeleteBuilder`1), `Delete<T>(entity)`, [удаление](../guide/20-delete-statement.md)) рендерит параметризованный `DELETE FROM <table> [WHERE ...]` — по предикату, по объявленному ключу сущности или всю таблицу с явным `All()`; `Returning()` возвращает удалённые строки на PostgreSQL/SQLite (`RETURNING`) и SQL Server (`OUTPUT`), `Truncate<T>()` рендерит `TRUNCATE TABLE`, ClickHouse удаляет через `ALTER TABLE ... DELETE ... SETTINGS mutations_sync = 1`. Multi-table `DELETE` по INNER-соединению ([`From<T>().Join(...).Delete()`](../guide/20-delete-statement.md#удаление-по-соединению)) поддерживается на PostgreSQL, SQL Server, MySQL и MariaDB и отклоняется SQLite и ClickHouse. `UPDATE`, полный `MERGE` с произвольными ветками `WHEN MATCHED`/`WHEN NOT MATCHED` и `MERGE ... RETURNING` — нет. `INSERT` в провайдере in-memory — вне области по замыслу: этот контекст — поверхность запросов по коллекциям, зарегистрированным вызывающим кодом (`WithData`), а не эмуляция базы данных (в отличие от in-memory-провайдера EF Core, где `Add` + `SaveChanges` — часть модели БД), и ни один терминал записи (`INSERT`/`DELETE`/`TRUNCATE`) на нём недоступен. Отслеживания изменений и `SaveChanges` нет: запись — это явные команды. |
| **`Prepare()` / кэш планов для DML** | Каждая мутация рендерит и выполняет одну команду за вызов — билдеры мутаций намеренно не готовятся и не кладутся в кэш планов. Оптимизация в nextorm нацелена только на read-only запросы (явный `Prepare`, неявный кэш планов, бенчмарки). |
| **Навигационные свойства / метаданные связей** | Метаданных связей нет, и нет неявного вывода соединений; вы пишете соединения явно с помощью [`Join`](xref:NextORM.Core.EntityBuilder`1.Join``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`LeftJoin`](xref:NextORM.Core.EntityBuilder`1.LeftJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`RightJoin`](xref:NextORM.Core.EntityBuilder`1.RightJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`FullJoin`](xref:NextORM.Core.EntityBuilder`1.FullJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}}))/[`CrossJoin`](xref:NextORM.Core.EntityBuilder`1.CrossJoin``1(NextORM.Core.EntityBuilder{``0}))/[`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0})) (см. [Соединения](../guide/03-joins.md)). |
| **Выбор соединённой сущности целиком** | После соединения накопленная проекция позиционна (`Item1`..`Item8`, по одному элементу на источник в порядке соединений), и выбирать можно только её колонки (`Select(p => p.Item1.Id)`); член проекции, являющийся сущностью целиком (`Select(p => p.Item1)`), колонкой не является и отклоняется. Придайте сторонам осмысленные имена, спроецировав в именованный тип (`Select(p => new { Order = p.Item1.Id, Customer = p.Item2.RequiredString })`); см. [Соединения](../guide/03-joins.md#адресация-проекции). |
| **Коррелированный источник `APPLY` / `LATERAL`** | [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0})) принимают лямбду, получающую строку левой стороны, поэтому применяемый источник может ссылаться на внешнюю строку у провайдера с lateral-источником (SQL Server `CROSS/OUTER APPLY`, PostgreSQL/MySQL/MariaDB `... LATERAL`). Диалекты без lateral-источника (SQLite, ClickHouse) отклоняют `APPLY`; провайдер in-memory его не поддерживает. Лямбда корреляции не может ссылаться на проекцию соединения — применяйте её к источнику из одной сущности. |
| **[`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) / [`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) на SQL-провайдерах** | Эти LINQ-операторы реализованы только для провайдера in-memory, где корреляция — обычный делегат. На SQL-провайдере [`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) бросают `NotSupportedException`; явная поверхность соединений [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0})) покрывает некоррелированный эквивалент (см. [Соединения](../guide/03-joins.md)). |
| **Коррелированные подзапросы в провайдере in-memory глубже одного уровня** | Корреляция работает для скалярных подзапросов (включая агрегатные терминалы) и `EXISTS`/`IN` в `SELECT`, `WHERE` и `ORDER BY` у каждого SQL-провайдера на любой глубине вложенности, а у провайдера in-memory — для корреляции глубины один, с вычислением на каждую внешнюю строку (см. [Подзапросы](../guide/06-subqueries.md#коррелированный-скалярный-подзапрос)). Оставшиеся формы in-memory отклоняются с `NotSupportedException`: глубина корреляции больше одной, ссылка на внешнюю строку во внутренней проекции или `ORDER BY`, коррелированный `GROUP BY`/`HAVING`, асинхронный источник и смешение внешних ссылок с явными `SqlFunctions.Parameter`-плейсхолдерами. |
| **Коррелированный скаляр: терминалы `First`/`Single` и их `*OrDefault`-формы** | При nullable-проекции отсутствие строки даёт `null`, при non-nullable value-проекции терминалы `FirstOrDefault`/`SingleOrDefault` дают `default` (например `0`). `First`/`Single` на non-nullable value-проекции бросают исключение, если строки нет. `Single`/`SingleOrDefault` при более чем одной строке бросают у всех провайдеров, чьи скалярные подзапросы проверяют кардинальность (PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse); SQLite её не проверяет, поэтому там числовой `Single`/`SingleOrDefault` при более чем одной строке поднимает ошибку БД через рендер-гард `case when count(*) > 1 then <числовое переполнение> else value end`, а нечисловая проекция отклоняется с `NotSupportedException`. |
| **`INTERSECT ALL` / `EXCEPT ALL` в SQL Server и SQLite** | Ни один из этих движков не может выразить такие варианты, поэтому диалект отклоняет их с `NotSupportedException`; `INTERSECT` / `EXCEPT` (без `ALL`) и `UNION` / `UNION ALL` работают везде. PostgreSQL поддерживает оба варианта `ALL`. |
| **Блокирующие табличные хинты вне SQL Server** | Блокирующие табличные хинты (`WithTableHint("nolock")` → `WITH (NOLOCK)`) поддерживаются только в SQL Server; нативные index-хинты MySQL/MariaDB (`USE`/`FORCE`/`IGNORE INDEX`), SQLite (`INDEXED BY`/`NOT INDEXED`) и SQL Server (`WITH (INDEX(...))`) — отдельная поверхность ([`WithIndex`](../guide/17-query-hints.md#index-хинты), [`ISqlDialect.IndexHints`](xref:NextORM.Core.ISqlDialect.IndexHints)). Хинты уровня инструкции подключены в SQL Server (`OPTION (...)`), PostgreSQL и MySQL/MariaDB (`/*+ ... */`); SQLite и ClickHouse отклоняют `Hint(...)` через `NotSupportedException` (см. [Хинты запросов](../guide/17-query-hints.md)). |
| **ВЕРХНИЙ регистр SQL-ключевых слов — конструкторы row/tuple остаются каноничными для провайдера** | `DataContextBuilder.UseKeywordCase(KeywordCase.Upper)`, `EntityBuilder<TEntity>.WithKeywordCase(...)` и `QueryCommand<T>.WithKeywordCase(...)` поднимают регистр ключевых слов, которые эмитит ядро сборки инструкции (`select`, `from`, `where`, `join`, `group by`, `order by`, `with`, `insert`, `values`, ...), трансляторы выражений (`and`/`or`/`not`, `case`/`when`/`then`/`else`/`end`, `cast(... as ...)`, `is [not] null`, `like`, `in`, `exists`, `over` и оконные фреймы), общие диалектные клозы (алиасы `as`, пагинация `limit`/`offset`/`fetch`/`top`, `with [recursive]`, ключевые слова join, table/index-хинты) и **все диалектные клозы**: `for json`/`for xml`, модификаторы группировки (`rollup`/`cube`/`grouping sets`/`with totals`), `for system_time ...`, `apply`, `settings`, `final`, `sample`, DML `returning`/`output`, query-hint `option (...)`/`option (maxrecursion ...)` и capability-клозы (`for update`/`for share`, `tablesample ... repeatable`, `limit by`, `array join`, `distinct on`, `pivot`/`unpivot`). Конструкторы row/tuple `ROW(...)` (PostgreSQL) и `tuple(...)` (ClickHouse) трактуются как функциональные конструкторы и сохраняют каноничное написание провайдера в обоих режимах (согласовано с политикой имён функций). Идентификаторы, строковые литералы, имена функций, имена типов и raw SQL не меняются никогда, а `KeywordCase.Lower` (по умолчанию) побайтово совпадает с прежним выводом. |
| **Функции массивов вне PostgreSQL** | Квантификаторы `any`/`all` над параметром-массивом (`column = any(@array)`) и функции массивов (`cardinality`, `array_length`, ...) требуют провайдера с нативными массивами; его включает только PostgreSQL ([`SupportsArrays`](xref:NextORM.Core.ISqlDialect.SupportsArrays)). Остальные диалекты отклоняют их через `NotSupportedException` (см. [Скалярные функции](../guide/11-scalar-functions.md#массивы-postgresql)). |
| **`string.Split` вне ClickHouse** | CLR-метод `string.Split` рендерится как `splitByChar(separator, value)` только в ClickHouse ([`StringSplit`](xref:NextORM.Core.ISqlDialect.StringSplit)); PostgreSQL покрывает его своим array-операндным путём `string_to_array`, а SQL Server (`STRING_SPLIT` — табличная функция), MySQL/MariaDB и SQLite не имеют скалярного разбиения на массив и отклоняют вызов. Поддерживается только одноразрядный разделитель (без `splitByString`), а результат — `string[]`, который можно проецировать напрямую или использовать внутри другой array-функции. |
| **Нативные JSON-функции вне PostgreSQL** | Функции и операторы `json`/`jsonb` (`json_agg`, `json_build_object`, `->`, `->>`, `#>`, `@>`, `?`, ...) требуют провайдера с типом JSON; его включает только PostgreSQL ([`SupportsJson`](xref:NextORM.Core.ISqlDialect.SupportsJson)). В SQL Server, MySQL и MariaDB вместо этого есть текстовое подмножество JSON (`json_value`/`json_query`/`json_modify`/`isjson`, [`SupportsTextJson`](xref:NextORM.Core.ISqlDialect.SupportsTextJson)) над обычной текстовой колонкой (MySQL/MariaDB рендерят его через `JSON_EXTRACT`/`JSON_SET`). Остальные диалекты отклоняют обе поверхности через `NotSupportedException` (см. [Скалярные функции](../guide/11-scalar-functions.md#json-и-jsonb-postgresql)). |
| **Нативный тип колонки `JSON` в ClickHouse** | Функции нативного JSON (`JSONAllPaths`/`JSONAllPathsWithTypes`/`toJSONString`, наряду с `JSON_VALUE`/`JSON_QUERY`/`JSON_EXISTS`) подключены на `ClickHouseFunctions` и включаются флагом [`SupportsJsonExtract`](xref:NextORM.Core.ISqlDialect.SupportsJsonExtract), но нативная *колонка* `JSON` не отображается на CLR-тип: `ClickHouse.Driver` читает её как `System.Text.Json.Nodes.JsonObject`, который row reader материализовать не умеет. Храните JSON в колонке `String` (или приведите колонку в SQL), если её нужно материализовать; отдельный type-mapping/reader — отдельный пункт бэклога. |
| **`greatest`/`least` у провайдеров без поддержки** | Функции включаются флагом [`SupportsGreatestLeast`](xref:NextORM.Core.ISqlDialect.SupportsGreatestLeast); PostgreSQL, MySQL/MariaDB, ClickHouse, SQL Server 2022+ и SQLite его включают. SQLite рендерит многоаргументные скалярные `max`/`min` (один аргумент возвращается как есть, так как `max`/`min` с одним аргументом — агрегат). Семантика NULL различается: PostgreSQL, SQL Server 2022+ и ClickHouse 24.12+ игнорируют NULL-аргументы, а MySQL/MariaDB и SQLite возвращают NULL, если любой аргумент NULL. Провайдер, не включивший флаг, отклоняет вызовы через `NotSupportedException`. `nullif` — ANSI и доступен всегда. |
| **`date_trunc` вне PostgreSQL, SQL Server и ClickHouse** | `date_trunc` включается флагом [`SupportsDateTrunc`](xref:NextORM.Core.ISqlDialect.SupportsDateTrunc); его включают PostgreSQL, SQL Server 2022+ (`datetrunc`) и ClickHouse (`dateTrunc`). |
| **Функции приведения/частей даты ClickHouse вне ClickHouse** | Поверхность `toDate`/`toDateTime`/`toDate32`, `toYear`/…, `toStartOf*`, `toMonday`, `toYYYYMM`/`toYYYYMMDD` и `toUnixTimestamp` ([`DateConversion`](xref:NextORM.Core.ISqlDialect.DateConversion)) доступна только в ClickHouse; остальные провайдеры отклоняют её через `NotSupportedException`. Портируемые аналоги — `date_trunc`/`date_add`/`end_of_month` и части `DateTime` (см. [Скалярные функции](../guide/11-scalar-functions.md#приведение-и-части-даты-clickhouse)). |
| **ClickHouse `multiIf` и `lagInFrame`/`leadInFrame` вне ClickHouse** | Многоветвевный `multi_if` ([`MultiIf`](xref:NextORM.Core.ISqlDialect.MultiIf)) и учитывающие фрейм оконные `lag_in_frame`/`lead_in_frame` ([`SupportsInFrameWindowFunctions`](xref:NextORM.Core.ISqlDialect.SupportsInFrameWindowFunctions)) доступны только в ClickHouse; остальные провайдеры отклоняют их через `NotSupportedException`. Многоветвевные условия портируемы через `iif`/C#-тернарник (рендерит `CASE WHEN`), а стандартные `lag`/`lead` — замена на основе партишена; но сам ClickHouse отвергает явный фрейм у них, поэтому frame-aware сосед требует `lagInFrame`/`leadInFrame`. |
| **`array_agg` вне PostgreSQL** | `array_agg` включается флагом [`SupportsArrayAgg`](xref:NextORM.Core.ISqlDialect.SupportsArrayAgg) и требует типа-массива на стороне провайдера, поэтому его включает только PostgreSQL. `string_agg` включается отдельным флагом [`SupportsStringAgg`](xref:NextORM.Core.ISqlDialect.SupportsStringAgg) и доступен также в SQL Server 2017+ и ClickHouse (`arrayStringConcat(groupArray(x), delimiter)`). Результат `array_agg` — колонка `Array(T)`, которую row reader материализует как `T[]`, поэтому её можно проецировать напрямую, а также использовать внутри запроса (например, в `HAVING`). |
| **`untuple` (ClickHouse)** | `untuple(tuple)` не отображается: он разворачивает кортеж в несколько колонок результата, и у такого выражения нет единой скалярной CLR-формы в проекции. Проецируйте `Tuple(...)` как `System.Tuple<...>` и читайте элементы через `tupleElement`/`System.Tuple<...>.ItemN`. |
| **Материализация row-значений PostgreSQL, tuple `IN` и конструктор `(a, b)` вне PostgreSQL** | Row-значения конструируются и сравниваются в PostgreSQL (`ROW(a, b)`, элементы через `(row).fN`) и ClickHouse (`tuple(a, b)`, `tupleElement`); `.ItemN` inline-конструктора сворачивается в аргумент везде. Пока открыто: материализация «сырого» `ROW(...)` обратно в `System.Tuple<...>` в PostgreSQL (Npgsql требует `EnableRecords()`/`MapComposite`), tuple `IN`/`Contains` по списку CLR-кортежей и конструктор `(a, b)` в MySQL/MariaDB/SQLite (фаза 2). См. [Скалярные функции](../guide/11-scalar-functions.md). |
| **Привязка сразу нескольких элементов `ARRAY JOIN` (ClickHouse)** | [`ArrayJoinElement`](xref:NextORM.Core.EntityBuilder`1.ArrayJoinElement``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`LeftArrayJoinElement`](xref:NextORM.Core.EntityBuilder`1.LeftArrayJoinElement``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) привязывают элемент ровно одного array-выражения к `p.Element`; повторный вызов, вызов на соединённом запросе или вызов после `Where`/`Having` бросают `InvalidOperationException`. Когда вы делаете array join нескольких массивов и типизированный элемент не нужен, используйте [`ArrayJoin`](xref:NextORM.Core.EntityBuilder`1.ArrayJoin``1(System.Linq.Expressions.Expression{System.Func{`0,``0}}))/[`LeftArrayJoin`](xref:NextORM.Core.EntityBuilder`1.LeftArrayJoin``1(System.Linq.Expressions.Expression{System.Func{`0,``0}})), принимающие несколько выражений (см. [провайдер ClickHouse](../providers/clickhouse.md)). |
| **Состояние агрегатных функций ClickHouse (`-State`/`-Merge`, `runningAccumulate`)** | `uniqState`/`sumState`/`countState`/… возвращают opaque-значение `AggregateFunction(...)`, которое nextorm не моделирует: `ClickHouse.Driver` 1.4.0 бросает `AggregateFunctionException` из `FrameworkType`/`Read`/`Write`, поэтому такую колонку нельзя материализовать в CLR-значение или передать как него (сообщение драйвера указывает на парный `-Merge`). Сам `uniqMerge(uniqState(x))` запрещён (`ILLEGAL_AGGREGATION`), поэтому `-Merge` требует состояния, полученного на сервере (подзапрос или таблица-состояние), а `runningAccumulate` в ClickHouse 25.8 объявлен устаревшим (`DEPRECATED_FUNCTION`, нужен `allow_deprecated_error_prone_window_functions`). |
| **Логические и регрессионные агрегаты вне PostgreSQL** | `bool_and`/`bool_or`/`every` ([`SupportsBooleanAggregates`](xref:NextORM.Core.ISqlDialect.SupportsBooleanAggregates)) и семейство `regr_*` ([`SupportsRegressionAggregates`](xref:NextORM.Core.ISqlDialect.SupportsRegressionAggregates)) доступны только в PostgreSQL. `corr`/`covar_*` ([`SupportsStatisticalAggregates`](xref:NextORM.Core.ISqlDialect.SupportsStatisticalAggregates)) доступны также в ClickHouse (`corr`/`covarPop`/`covarSamp`). |
| **`FILTER` у агрегатов вне PostgreSQL и SQLite** | Предложение `FILTER (WHERE ...)` включается флагом [`SupportsFilter`](xref:NextORM.Core.ISqlDialect.SupportsFilter); его включают PostgreSQL и SQLite, а MySQL/MariaDB и SQL Server — нет. ClickHouse тоже его отклоняет, но предоставляет аналог фильтрованного агрегата — комбинаторы `-If` (`count_if`/`sum_if`/`avg_if`/`min_if`/`max_if`, [`SupportsIfAggregates`](xref:NextORM.Core.ISqlDialect.SupportsIfAggregates)). |
| **`GROUP BY CUBE`/`GROUPING SETS` в MySQL/MariaDB и в провайдере in-memory** | В MySQL/MariaDB нет `CUBE` и `GROUPING SETS`, а провайдер in-memory не поддерживает ни `ROLLUP`, ни `CUBE`, ни `GROUPING SETS`; они отклоняют модификатор через `NotSupportedException`. `ROLLUP` работает на всех SQL-провайдерах (см. [Группировка и агрегаты](../guide/04-grouping-and-aggregates.md#rollup-и-cube)). |
| **Хранимые процедуры и динамический SQL** | nextorm строит `SELECT`-запросы из LINQ; вызов хранимой процедуры или сборка SQL во время выполнения — вне поверхности билдера (сырой SQL для запроса целиком доступен — [`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String))). |
| **Внешние источники (`OPENROWSET`/`OPENQUERY`, linked servers)** | Вне области охвата; запрашивается схема самого соединения. |
| **Табличные функции ClickHouse `format`/`merge`/`input`** | Не предобъявлены на `SqlFunctions.ClickHouse`: `format` и `merge` выводят схему в рантайме, а `input` допустима только в `INSERT ... SELECT`, поэтому ни у одной нет схемы `TRow`, объявляемой вызывающим. Используйте `FromSql` или пользовательскую обёртку `[SqlTableFunction]`. |
| **DDL / административные команды** | `CREATE`/`ALTER`/`DROP`, `OPTIMIZE`, `RENAME` и подобные не генерируются; используйте свои команды. |
| **Транзакции, `SaveChanges` и отслеживание изменений / CDC** | nextorm не владеет единицей работы и не отслеживает сущности; участие только для чтения в транзакции, управляемой вызывающим кодом, не является частью API. |

## Не ограничения

Следующее полностью реализовано и проверено; оно появляется в столбце *готово* анализа пробелов,
а не в списке выше:

- соединения любого типа (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, а также `CROSS APPLY`/`OUTER APPLY` и lateral-эквивалент там, где поддерживается) и арности 2–8, включая производный запрос с любой стороны (первичный источник `FROM` или присоединяемая таблица);
- коррелированные скалярные подзапросы и коррелированные `EXISTS`/`IN`/`ANY`/`ALL` в `SELECT`, `WHERE`, `ORDER BY` и `HAVING` у каждого SQL-провайдера на любой глубине вложенности, а также коррелированный скаляр/`EXISTS`/`IN` глубины один в `SELECT`/`WHERE`/`ORDER BY` у провайдера in-memory (см. [Подзапросы](../guide/06-subqueries.md));
- `CASE WHEN` / тернарный оператор / `switch`, `COALESCE`, числовой `CAST`;
- строковые, математические и date/time скалярные функции и `LIKE`;
- арифметика дат (`date_add`/`end_of_month`/`date_diff`/`date_from_parts` и `DateTime.Add*`) в PostgreSQL, SQL Server, ClickHouse, MySQL/MariaDB и SQLite, а также `date_trunc` в PostgreSQL/SQL Server/ClickHouse и `string_agg` в PostgreSQL/SQL Server/ClickHouse/MySQL/MariaDB/SQLite;
- битовые (`bit_and`/`bit_or`/`bit_xor`), статистические (`corr`/`covar_*`), `argMin`/`argMax` и `-If` (`count_if`/...) агрегаты в ClickHouse;
- бинарные столбцы — свойство или проекция `byte[]` отображается на `bytea` (PostgreSQL), `varbinary`/`image` (SQL Server) или `blob` (SQLite);
- 64-битные беззнаковые целые — свойство или проекция `ulong`/`ulong?` материализуется через аксессор построителя строк `DbDataReader.GetFieldValue<ulong>` у провайдеров с нативным беззнаковым типом (ClickHouse `UInt64`, MySQL/MariaDB `BIGINT UNSIGNED`), без SQL-приведения; в PostgreSQL, SQL Server и SQLite беззнакового целого нет, и этот диапазон выражается только `numeric`/`decimal`;
- `IN` по списку/массиву, логические `!` и унарные операторы;
- `SELECT DISTINCT`, `INTERSECT`/`EXCEPT`, CTE (включая рекурсивные) и оконные функции;
- модифицирующие CTE (`WITH n AS (INSERT ... RETURNING ...)`) на PostgreSQL, читаются типизированно через [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1) (см. [модифицирующий CTE](../guide/19-insert-statement.md#модифицирующий-cte-postgresql));
- пользовательские скалярные функции (`[SqlFunction]`) и табличные функции (`[SqlTableFunction]`);
- серверные/кластерные табличные функции ClickHouse `url`/`s3`/`file`/`remote`/`remoteSecure`/`cluster`/`clusterAllReplicas`, предобъявленные на `SqlFunctions.ClickHouse.*` с generic-интерфейсом строки `TRow`, объявляемым вызывающим (гейт — [`SupportsTableFunction`](xref:NextORM.Core.ISqlDialect.SupportsTableFunction(System.String)); см. [Табличные функции](../guide/13-table-valued-functions.md#встроенные-табличные-функции));
- предикаты полнотекстового поиска (`SqlFunctions.Sql.contains`/`freetext`) в SQL Server, PostgreSQL и MySQL/MariaDB, полнотекстовое ранжирование (SQL Server `containstable`/`freetexttable` с `KEY`/`RANK`, PostgreSQL `ts_rank`/`ts_rank_cd`), текстовые JSON-функции (`json_value`/`json_query`/`json_modify`/`isjson`) в SQL Server и MySQL/MariaDB и табличные функции SQL Server `openjson`/`string_split` (а также пользовательские обёртки `[SqlTableFunction]`, включая MySQL `JSON_TABLE` через `CallClause`);
- хинты уровня инструкции в SQL Server (`OPTION (...)`), PostgreSQL и MySQL/MariaDB (`/*+ ... */`), табличные хинты в SQL Server (`Hint(...)`, `WithTableHint(...)`), JSON-вывод (`ForJson(...)` → `FOR JSON PATH`/`AUTO`) и XML-вывод (`ForXml(...)` → `FOR XML`);
- методы типа XML в SQL Server (`xml_value`/`xml_query`/`xml_exist` → `xml.value('xpath', 'type')`/`xml.query('xpath')`/`xml.exist('xpath')`, а также rowset `.nodes` через `xml_nodes` как источник `CrossApply`/`OuterApply`);
- raw SQL для запроса целиком ([`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)) / [`PrepareFromSql`](xref:NextORM.Core.EntityExtensions.PrepareFromSql``1(NextORM.Core.EntityBuilder{``0},System.String))) и как композируемый источник `FROM` ([`FromSql`](xref:NextORM.Core.DataContextExtensions.FromSql(NextORM.Core.IDataContext,System.String,System.Object)), рендерится как производная таблица), а также пути переиспользования неявного кэша планов / [`Prepare`](xref:NextORM.Core.EntityBuilderExtensions.Prepare``1(NextORM.Core.EntityBuilder{``0},System.Boolean,System.Threading.CancellationToken)).
