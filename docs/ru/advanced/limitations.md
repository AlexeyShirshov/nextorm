# Ограничения и возможности вне области охвата

> nextorm — построитель запросов с небольшой явной поверхностью DML: он генерирует инструкции `SELECT` (и параметризованные `INSERT ... VALUES`, `INSERT ... SELECT`, key upsert, `MERGE`, `DELETE` и `UPDATE`) и материализует их результаты, и намеренно оставляет отслеживание изменений и `SaveChanges` вызывающей стороне.

**Предварительные требования:** [Provider overview](../providers/overview.md) · [API reference](api-reference.md)

## Обзор

На этой странице перечислены возможности, которые **не** являются частью nextorm, с однострочной причиной для каждой.

## Вне области охвата

| Не поддерживается | Обоснование |
|---|---|
| **DML** — `INSERT`, `UPDATE`, `DELETE`, `MERGE` | **`INSERT ... VALUES`, `INSERT ... SELECT` и key upsert реализованы** ([`InsertInto`](../guide/15-insert-statement.md); возврат строк через `RETURNING`/`OUTPUT` на PostgreSQL, SQLite и SQL Server, строки батча неупорядочены; серверный источник поднимает свои CTE перед `INSERT` и отклоняет рантайм-плейсхолдеры `SqlFunctions.Parameter`). PostgreSQL также поддерживает **модифицирующие CTE** (`With(имя, insert)`/`With(имя, update)`/`With(имя, delete)` для однотабличных и join/multi-table тел `INSERT`/`UPDATE`/`DELETE`, каждое требует проекцию `RETURNING` → [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1), [модифицирующий CTE](../guide/15-insert-statement.md#модифицирующий-cte-postgresql)). **Upsert** ([`MergeInto`](xref:NextORM.Core.DataContextExtensions.MergeInto``1(NextORM.Core.IDataContext,System.Action{NextORM.Core.EntityMetadataBuilder{``0}})) → [`MergeBuilder<T>`](xref:NextORM.Core.MergeBuilder`1), [upsert](../guide/19-merge-statement.md#upsert-key-merge)) рендерит родную форму провайдера — `INSERT ... ON CONFLICT ... DO UPDATE` (PostgreSQL, SQLite), `INSERT ... ON DUPLICATE KEY UPDATE` (MySQL, MariaDB) или `MERGE ... USING (VALUES ...)` (SQL Server); ClickHouse их отклоняет, а провайдер in-memory применяет upsert к зарегистрированной последовательности. При активном глобальном фильтре запросов полный `MERGE` (SQL Server, PostgreSQL 15+) изолирует цель в предикате `ON`, поэтому скрытая строка никогда не сопоставляется, не обновляется и не удаляется, а key upsert `ON CONFLICT` / `ON DUPLICATE KEY` / in-memory **отказывает** с `NotSupportedException` (fail closed; `IgnoreFilters()` их восстанавливает). Ключ источника, совпавший со скрытой строкой цели, всё равно вскрывает нативную ошибку нарушения уникальности провайдера из insert-ветки — по любому задетому уникальному индексу, а не только по ключу совпадения (оракул существования; составной ключ, включающий столбец фильтра, смягчает только первичный/ключ совпадения), тогда как merge только с update- или delete-веткой — молчаливый no-op — а pre-check значений источника остаётся отдельным чтением с окном TOCTOU (`QueryFilterValidator`), проверяющим значения источника, а не строки цели (см. [Изоляция цели записи](../advanced/query-filters.md#изоляция-цели-записи)). **`DELETE`** ([`DeleteFrom`](../guide/16-delete-statement.md) → [`DeleteBuilder<T>`](xref:NextORM.Core.DeleteBuilder`1), `Delete<T>(entity)`, [удаление](../guide/16-delete-statement.md)) рендерит параметризованный `DELETE FROM <table> [WHERE ...]` — по предикату, по объявленному ключу сущности или всю таблицу с явным `All()`; `Returning()` возвращает удалённые строки на PostgreSQL/SQLite (`RETURNING`) и SQL Server (`OUTPUT`), `Truncate<T>()` рендерит `TRUNCATE TABLE`, ClickHouse удаляет через `ALTER TABLE ... DELETE ... SETTINGS mutations_sync = 1`. Multi-table `DELETE` по INNER-соединению ([`From<T>().Join(...).Delete()`](../guide/16-delete-statement.md#удаление-по-соединению)) поддерживается на PostgreSQL, SQL Server, MySQL и MariaDB и отклоняется SQLite и ClickHouse. **`UPDATE`** ([`Update`](../guide/17-update-statement.md) → [`UpdateBuilder<T>`](xref:NextORM.Core.UpdateBuilder`1), `Update<T>(entity)`) рендерит параметризованный `UPDATE <table> SET ... [WHERE ...]` на PostgreSQL, SQL Server, SQLite, MySQL и MariaDB; ClickHouse обновляет через `ALTER TABLE ... UPDATE ... SETTINGS mutations_sync = 1` (синхронно, но число затронутых строк не возвращает), а провайдер in-memory его отклоняет; `Returning()` возвращает обновлённые строки на PostgreSQL/SQLite (`RETURNING`) и SQL Server (`OUTPUT`). Multi-table `UPDATE` по INNER-соединению ([`From<T>().Join(...).UpdateJoin()`](../guide/17-update-statement.md#обновление-из-join)) поддерживается на PostgreSQL/SQLite (`FROM`), SQL Server и MySQL/MariaDB и отклоняется ClickHouse. Полный `MERGE` с ветками `WHEN MATCHED`/`WHEN NOT MATCHED`/`WHEN NOT MATCHED BY SOURCE` и `MERGE ... RETURNING`/`OUTPUT` доступны на SQL Server и PostgreSQL 15+ и отклоняются остальными провайдерами. `INSERT` в провайдере in-memory — вне области по замыслу: этот контекст — поверхность запросов по коллекциям, зарегистрированным вызывающим кодом (`WithData`), а не эмуляция базы данных (в отличие от in-memory-провайдера EF Core, где `Add` + `SaveChanges` — часть модели БД), и ни один терминал записи (`INSERT`/`DELETE`/`TRUNCATE`) на нём недоступен, кроме key-upsert merge, применяемого к зарегистрированной последовательности. Отслеживания изменений и `SaveChanges` нет: запись — это явные команды. Запрос можно материализовать в постоянную таблицу через `CREATE TABLE ... AS SELECT` ([`ToTempTable`/`ToTable`](../guide/18-create-table-as.md)) на PostgreSQL, SQLite, MySQL, MariaDB, SQL Server и ClickHouse: SQL Server рендерит `SELECT ... INTO` (таблица уровня сессии — `ToTable("#name")`), ClickHouse — `CREATE TABLE ... ENGINE = MergeTree ... AS SELECT`. Временная форма `ToTempTable` доступна только на PostgreSQL, SQLite, MySQL и MariaDB: в SQL Server нет `CREATE TEMPORARY TABLE ... AS SELECT` (используйте `#name`), а ClickHouse не допускает временный `AS SELECT`. Утверждение с побочным эффектом и последующее чтение можно отправить одним батчем через общий `BatchBuilder` (материализации `CreateTempTable`/`CreateTable` и DML-шаги `Insert`/`Update`/`Delete`/`Truncate` перед одним читающим запросом), одним round trip на одной сессии, на PostgreSQL, SQL Server, MySQL, MariaDB и SQLite; ClickHouse и in-memory-контекст отклоняют батч с `NotSupportedException`, а DML-шаг не может запрашивать возврат строк (`Returning()` даёт другой тип билдера). SQL Server отправляет батч одной `;`-склеенной командой, а не `SqlBatch`, который выполняет каждую команду в своей области видимости, поэтому `#temp` остаётся видимой между утверждениями. Выполнение батча не проходит через интерцепторы запросов: их события несут `DbCommand`, тогда как команда `DbBatch` — это `DbBatchCommand`. |
| **`Prepare()` / кэш планов для DML** | Каждая мутация рендерит и выполняет одну команду за вызов — билдеры мутаций намеренно не готовятся и не кладутся в кэш планов. Оптимизация в nextorm нацелена только на read-only запросы (явный `Prepare`, неявный кэш планов, бенчмарки). |
| **Bulk-copy флаги вне SQL Server** | `BulkInsertOptions.CheckConstraints`/`TableLock`/`KeepNulls`/`FireTriggers` отображаются в `SqlBulkCopyOptions` на нативном пути `SqlBulkCopy` в SQL Server. Путь `COPY` в PostgreSQL и портируемый `INSERT ... VALUES` (MySQL/MariaDB/SQLite/ClickHouse, а также SQL Server, когда `Returning*` или `KeepIdentity` переключают запись на портируемый путь) отклоняют запрошенный флаг через `NotSupportedException`, а не игнорируют его. ClickHouse `MaxDegreeOfParallelism`/`WithoutSession` не выставляются: `ClickHouseBulkCopy` в `ClickHouse.Driver` 1.4.0 устарел, а не-устаревший `ClickHouseClient.InsertBinaryAsync` требует собственного клиента; сессия — настройка строки подключения (`UseSession`), а не пер-записная опция. `UseInternalTransaction` намеренно не выставляется (nextorm не открывает неявную транзакцию). См. [Массовая вставка](../guide/20-bulk-insert.md#опции-bulk-copy-в-sql-server). |
| **Неявные соединения из навигационных свойств** | Метаданные связей теперь есть: связь объявляется явно через `HasMany`/`HasOne` или [`RelationshipAttribute`](xref:NextORM.Core.RelationshipAttribute), а [`JoinInto`](xref:NextORM.Core.EntityBuilder`1) загружает дочернюю коллекцию или ссылку за один денормализованный round trip — one-to-many, one-to-one и, через явный junction (`HasManyThrough`/`JoinOptions.ManyToMany`), many-to-many; по умолчанию LEFT, есть перегрузка INNER и fallback с явными ключами (см. [Связи](relationships.md)). **Неявный вывод соединений по-прежнему не реализован**: навигационное свойство никогда не превращается в соединение автоматически, конвенции по внешним ключам нет. `JoinInto` отклоняет с `NotSupportedException` составной ключ связи или junction, связь many-to-many под `AsSingleQuery`, необъявленную связь (кроме перегрузки с явными ключами), производный (`As`) или соединённый источник проекции, вид соединения, отличный от `Inner`/`Left`, несовпадающие типы явных ключей и более семи дочерних коллекций; смешивание `JoinInto` с любым другим соединением на одном билдере отклоняется (объявляйте `JoinInto` только на простом источнике сущности), а ClickHouse-опция `j => j.WithStrictness(Any)` на `JoinInto` усекает загруженную коллекцию до одного ребёнка, тогда как остальные модификаторы (`All`, `Asof`, `Global`) проходят без изменений; метаданные связи «падают закрыто» при неотображённом внешнем ключе, principal-типе без ключа или несовпадении типов FK/principal-ключа. Явные соединения остаются общей поверхностью: [`Join`](xref:NextORM.Core.EntityBuilder`1.Join``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`LeftJoin`](xref:NextORM.Core.EntityBuilder`1.LeftJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`RightJoin`](xref:NextORM.Core.EntityBuilder`1.RightJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`FullJoin`](xref:NextORM.Core.EntityBuilder`1.FullJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`CrossJoin`](xref:NextORM.Core.EntityBuilder`1.CrossJoin``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) (см. [Соединения](../guide/02-joins.md)). **Дедупликация требует отображённого ключа**: дедупликация родителей и идентичность ребёнка возвращаются к ссылочной идентичности, когда у соответствующей стороны не объявлен ключ, а на SQL-провайдере каждая строка — новый экземпляр, поэтому повторы/декартовы строки сохраняются — задайте родителю и ребёнку отображённый ключ (`[Key]`/`Key()`/соглашение `Id`) или используйте перегрузку с явными ключами и ключевым ребёнком. `IRelationshipMetadata.Inverse` разрешается лениво при **первом чтении** и кэшируется, поэтому регистрируйте обе стороны до его чтения. |
| **Выбор соединённой сущности целиком** | После соединения накопленная проекция позиционна (`Item1`..`Item8`, по одному элементу на источник в порядке соединений), и выбирать можно только её колонки (`Select(p => p.Item1.Id)`); член проекции, являющийся сущностью целиком (`Select(p => p.Item1)`), колонкой не является и отклоняется. Придайте сторонам осмысленные имена, спроецировав в именованный тип (`Select(p => new { Order = p.Item1.Id, Customer = p.Item2.RequiredString })`); см. [Соединения](../guide/02-joins.md#адресация-проекции). |
| **Коррелированный источник `APPLY` / `LATERAL`** | [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) принимают лямбду, получающую строку левой стороны, поэтому применяемый источник может ссылаться на внешнюю строку у провайдера с lateral-источником (SQL Server `CROSS/OUTER APPLY`, PostgreSQL/MySQL/MariaDB `... LATERAL`). Диалекты без lateral-источника (SQLite, ClickHouse) отклоняют `APPLY`; провайдер in-memory его не поддерживает. Лямбда корреляции не может ссылаться на проекцию соединения — применяйте её к источнику из одной сущности. |
| **[`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) / [`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) на SQL-провайдерах** | Эти LINQ-операторы реализованы только для провайдера in-memory, где корреляция — обычный делегат. На SQL-провайдере [`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) бросают `NotSupportedException`; явная поверхность соединений [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) покрывает некоррелированный эквивалент (см. [Соединения](../guide/02-joins.md)). |
| **Коррелированные подзапросы в провайдере in-memory глубже одного уровня** | Корреляция работает для скалярных подзапросов (включая агрегатные терминалы) и `EXISTS`/`IN` в `SELECT`, `WHERE` и `ORDER BY` у каждого SQL-провайдера на любой глубине вложенности, а у провайдера in-memory — для корреляции глубины один, с вычислением на каждую внешнюю строку (см. [Подзапросы](../guide/05-subqueries.md#коррелированный-скалярный-подзапрос)). Оставшиеся формы in-memory отклоняются с `NotSupportedException`: глубина корреляции больше одной, ссылка на внешнюю строку во внутренней проекции или `ORDER BY`, коррелированный `GROUP BY`/`HAVING`, асинхронный источник и смешение внешних ссылок с явными `SqlFunctions.Parameter`-плейсхолдерами. |
| **Коррелированный скаляр: терминалы `First`/`Single` и их `*OrDefault`-формы** | При nullable-проекции отсутствие строки даёт `null`, при non-nullable value-проекции терминалы `FirstOrDefault`/`SingleOrDefault` дают `default` (например `0`). `First`/`Single` на non-nullable value-проекции бросают исключение, если строки нет. `Single`/`SingleOrDefault` при более чем одной строке бросают у всех провайдеров, чьи скалярные подзапросы проверяют кардинальность (PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse); SQLite её не проверяет, поэтому там числовой `Single`/`SingleOrDefault` при более чем одной строке поднимает ошибку БД через рендер-гард `case when count(*) > 1 then <числовое переполнение> else value end`, а нечисловая проекция отклоняется с `NotSupportedException`. |
| **`INTERSECT ALL` / `EXCEPT ALL` в SQL Server и SQLite** | Ни один из этих движков не может выразить такие варианты, поэтому диалект отклоняет их с `NotSupportedException`; `INTERSECT` / `EXCEPT` (без `ALL`) и `UNION` / `UNION ALL` работают везде. PostgreSQL поддерживает оба варианта `ALL`. |
| **Блокирующие табличные хинты вне SQL Server** | Блокирующие табличные хинты (`WithTableHint("nolock")` → `WITH (NOLOCK)`) поддерживаются только в SQL Server, для таблицы запроса в `FROM` и, через пер-join опцию `JoinOptions.WithJoinTableHint`, переданную соединению; нативные index-хинты MySQL/MariaDB (`USE`/`FORCE`/`IGNORE INDEX`), SQLite (`INDEXED BY`/`NOT INDEXED`) и SQL Server (`WITH (INDEX(...))`) — отдельная поверхность ([`WithIndex`](../guide/13-query-hints.md#index-хинты), [`ISqlDialect.IndexHints`](xref:NextORM.Core.ISqlDialect.IndexHints)). Хинты уровня инструкции подключены в SQL Server (`OPTION (...)`), PostgreSQL и MySQL/MariaDB (`/*+ ... */`); SQLite и ClickHouse отклоняют `Hint(...)` через `NotSupportedException`. Хинты join (`JoinOptions.WithJoinHint`), подзапроса (`FromOptions.WithSubQueryHint`) и области видимости (`WithTablesInScopeHint`) следуют тем же гейтам: SQL Server рендерит join-хинт внутри `JOIN`, а хинт области — как `WITH (...)` на каждой таблице, PostgreSQL/MySQL/MariaDB сворачивают их во встроенный `/*+ ... */`, а SQLite/ClickHouse/in-memory их отклоняют (см. [Хинты запросов](../guide/13-query-hints.md)). |
| **ВЕРХНИЙ регистр SQL-ключевых слов — конструкторы row/tuple остаются каноничными для провайдера** | `DataContextBuilder.UseKeywordCase(KeywordCase.Upper)`, `EntityBuilder<TEntity>.WithKeywordCase(...)` и `QueryCommand<T>.WithKeywordCase(...)` поднимают регистр ключевых слов, которые эмитит ядро сборки инструкции (`select`, `from`, `where`, `join`, `group by`, `order by`, `with`, `insert`, `values`, ...), трансляторы выражений (`and`/`or`/`not`, `case`/`when`/`then`/`else`/`end`, `cast(... as ...)`, `is [not] null`, `like`, `in`, `exists`, `over` и оконные фреймы), общие диалектные клозы (алиасы `as`, пагинация `limit`/`offset`/`fetch`/`top`, `with [recursive]`, ключевые слова join, table/index-хинты) и **все диалектные клозы**: `for json`/`for xml`, модификаторы группировки (`rollup`/`cube`/`grouping sets`/`with totals`), `for system_time ...`, `apply`, `settings`, `final`, `sample`, DML `returning`/`output`, query-hint `option (...)`/`option (maxrecursion ...)` и capability-клозы (`for update`/`for share`, `tablesample ... repeatable`, `limit by`, `array join`, `distinct on`, `pivot`/`unpivot`). Конструкторы row/tuple `ROW(...)` (PostgreSQL) и `tuple(...)` (ClickHouse) трактуются как функциональные конструкторы и сохраняют каноничное написание провайдера в обоих режимах (согласовано с политикой имён функций). Идентификаторы, строковые литералы, имена функций, имена типов и raw SQL не меняются никогда, а `KeywordCase.Lower` (по умолчанию) побайтово совпадает с прежним выводом. |
| **Функции массивов вне PostgreSQL** | Квантификаторы `any`/`all` над параметром-массивом (`column = any(@array)`) и функции массивов (`cardinality`, `array_length`, ...) требуют провайдера с нативными массивами; его включает только PostgreSQL ([`SupportsArrays`](xref:NextORM.Core.ISqlDialect.SupportsArrays)). Остальные диалекты отклоняют их через `NotSupportedException` (см. [Скалярные функции](../scalar-functions/06-arrays.md#массивы-postgresql)). |

| **Единица работы, `SaveChanges` и отслеживание изменений / CDC** | nextorm не владеет единицей работы и не отслеживает сущности, а `SaveChanges` нет. При этом запросы можно выполнять внутри транзакции: начать её через [`ITransactionManager`](xref:NextORM.Core.ITransactionManager) или встроиться в чужую (EF Core, Dapper, сырой ADO.NET) через `UseTransaction`. Запись остаётся явными командами `INSERT`/`UPDATE`/`DELETE`/`MERGE`; конкурентность проверяется явно (токен в `WHERE` + число затронутых строк), а слой отслеживания изменений можно построить сверху — см. [Оптимистичная конкурентность и отслеживание изменений](../guide/24-optimistic-concurrency.md). В ClickHouse транзакций нет, он их отклоняет. |
| **Интеграция с EF Core: мост `SaveChanges` и маппинг на контекст** | Пакет [`nextorm.entityframeworkcore`](integration-efcore.md) выполняет чтения и запись nextorm поверх соединения существующего EF Core `DbContext` и его текущей транзакции и отображает сущности из EF `IModel`; чтения и запись nextorm, выполненные там, участвуют в этой общей транзакции (проверено на PostgreSQL, SQL Server и MySQL), но синхронизации отслеживания изменений и моста `SaveChanges` нет: DML nextorm идёт в обход трекера изменений EF, поэтому записанные им строки трекеру неизвестны. Маппинг регистрируется в процесс-глобальном кэше метаданных nextorm с ключом по `Type`, поэтому **на процесс существует не более одного маппинга на CLR-тип** — два `DbContext`, отображающие один тип по-разному, не могут обслуживаться одновременно: вторая, отличающаяся регистрация бросает `InvalidOperationException`. Мост `SaveChanges`/отслеживания изменений явно вне области. У нереляционного EF-провайдера `InMemory` нет `DbConnection`, он не поддерживается. См. [Интеграция с EF Core](integration-efcore.md). |
| **Режимы ожидания блокировки строк (`NOWAIT`/`SKIP LOCKED`) вне PostgreSQL, MySQL, MariaDB и SQL Server** | [`LockWaitMode`](xref:NextORM.Core.LockWaitMode) выражают четыре диалекта, умеющие блокировать строки ([`ILockRenderer`](xref:NextORM.Core.ILockRenderer)): PostgreSQL рендерит `FOR UPDATE`/`FOR SHARE [NOWAIT \| SKIP LOCKED]` (9.5+); MySQL 8.0.1+ рендерит `FOR UPDATE`/`FOR SHARE [NOWAIT \| SKIP LOCKED]`, причём разделяемая блокировка с режимом переключается с `LOCK IN SHARE MODE` (не принимающего lock-option) на `FOR SHARE`; MariaDB дописывает режим к `FOR UPDATE`/`LOCK IN SHARE MODE` (`NOWAIT` 10.3+, `SKIP LOCKED` 10.6+); SQL Server добавляет `NOWAIT`/`READPAST` в тот же табличный хинт, где `READPAST` пропускает любую заблокированную строку и потому приближает `SKIP LOCKED`. Пороги версий документируются, а не гейтятся по версии сервера. SQLite, ClickHouse и in-memory провайдер отклоняют любую блокировку строк — с режимом или без. |
| **Интерцепторы за пределами жизненного цикла команды/соединения** | Поставленный интерфейс — [`IQueryInterceptor`](xref:NextORM.Core.IQueryInterceptor) и [`IConnectionInterceptor`](xref:NextORM.Core.IConnectionInterceptor) (см. [Интерцепторы](../infrastructure/03-interceptors.md)). Exception-интерцептора нет — транслируйте исключение провайдера через `try`/`catch` вокруг вызова терминала; интерцепторов для in-memory провайдера нет, у него нет команды и соединения. Интерцептор не должен менять `CommandText` (команда принадлежит кэшированному плану). Глобальные фильтры запросов — отдельный слой. |
| **Динамические колонки — сторона записи** | **Сторона чтения** реализована: свойство с сеттером, допускающее присваивание из `Dictionary<string, object?>`, помеченное [`DynamicColumnsAttribute`](xref:NextORM.Core.DynamicColumnsAttribute) (или флюентно `EntityPropertyBuilder<T>.DynamicColumnsStore`), получает не сопоставленные колонки строки, когда сущность запрашивается целиком, — инструкция рендерит `select <mapped>, *` (``select t1.<mapped>, `t1`.*`` в MySQL/MariaDB, чей диалект алиасит `*` через `RequiresQualifiedSelectStar`), и хранилище материализуется из набора результатов у каждого SQL-провайдера и в in-memory-контексте (см. [Динамические колонки](../guide/27-dynamic-columns.md)). **Сторона записи реализована для `INSERT`, `UPDATE` и `MERGE`**: ключи словаря-хранилища рендерятся физическими колонками, а их значения — связанными параметрами. Ключи сортируются порядково (ordinal), поэтому порядок колонок детерминирован; каждый динамический ключ квотируется квотированием диалекта, даже когда глобальная опция квотирования идентификаторов (`UseQuotedIdentifiers`) выключена, а соглашение об именовании пропускается (ключ используется как имя физической колонки); пустой ключ или ключ с символом NUL отклоняется. Присутствующий ключ со значением `null` пишет SQL `NULL`, а отсутствующий ключ опускается — в `INSERT` применяется значение по умолчанию колонки, в `UPDATE`/`MERGE` колонка остаётся неизменной (очистить колонку, опустив её ключ, нельзя); многострочный `INSERT` требует одинакового набора ключей во всех строках, а в `MERGE` динамические колонки идут в source/`INSERT`/`SET` и никогда в `ON`. Значения связываются из рантайм-CLR-значения без пер-ключевого `IPropertyValueConverter`/JSON (pass-through), что зеркалит материализацию стороны чтения. **Оставшиеся ограничения:** нет пер-ключевых конвертеров и JSON-колонок; nextorm не отслеживает изменения; колонку нельзя очистить опусканием ключа; нет allow-list ключей (ключи вместо этого квотируются и валидируются); а in-memory-провайдер сторону записи не реализует. Сторона чтения по-прежнему ограничена одним физическим источником (запрос с соединениями отклоняет хранилище с `NotSupportedException`) и сущностью, запрашиваемой целиком (явная проекция хранилище не собирает). На SQL-чтении хранилище создаётся, даже если изначально оно `null`; на записи `null`-хранилище или хранилище без ключей не даёт динамических колонок. Сущность с хранилищем должна быть ссылочного типа: сущность value-типа (`struct`), объявляющая хранилище, отклоняется с `InvalidOperationException` при построении метаданных, а не упаковывается молча (boxing) — используйте ссылочный тип. |
| **Динамические колонки — конструктор без параметров** | Сущность, объявляющая хранилище динамических колонок, должна быть ссылочного типа и иметь публичный конструктор без параметров. Хранилище материализуется через member-init (каждая сопоставленная колонка привязывается по имени, а хранилище получает поля `*`), поэтому обычная стратегия самого длинного конструктора к ней не применяется; сущность с хранилищем без публичного конструктора без параметров отклоняется при подготовке с `QueryPreparationException`. То же хранилище читает и сторона записи. |

| **Нативные range/multirange-колонки вне PostgreSQL** | Нативные range-типы (`int4range`…`daterange`) и multirange-типы (`int4multirange`…`datemultirange`) есть только в PostgreSQL и гейтятся [`SupportsRanges`](xref:NextORM.Core.ISqlDialect.SupportsRanges). В остальных провайдерах «голая» колонка `Range<T>`/`Range<T>[]` отклоняется с `NotSupportedException`. Вместо неё свойство `Range<T>` можно хранить парой скалярных колонок через [`RangeColumnsAttribute`](xref:NextORM.Core.RangeColumnsAttribute) (или флюентно `EntityPropertyBuilder<T>.RangeColumns(...)`, гейт [`SupportsRangeColumns`](xref:NextORM.Core.ISqlDialect.SupportsRangeColumns)): обе границы читаются и пишутся, <c>NULL</c> означает неограниченную сторону, а предикаты/инспекция (`overlaps`, `range_contains`/`range_contained_by`, позиционные и adjacency-предикаты, `lower`/`upper`/`isempty`/…) транслируются поверх пары. Range-возвращающие операторы (`range_union`/`range_intersection`/`range_difference`, конструкторы) и агрегаты `range_agg`/`range_intersect_agg` не имеют скалярной формы над парой и остаются только в PostgreSQL, как и multirange-колонки; in-memory провайдер вычисляет всю поверхность над CLR-значениями [`Range<T>`](xref:NextORM.Core.Range`1)/`Range<T>[]`. |

| **Табличные параметры в провайдере in-memory** | SQL Server связывает табличный параметр нативно (пользовательский табличный тип); PostgreSQL, MySQL/MariaDB и SQLite эмулируют его типизированным массивом или JSON-документом, а ClickHouse — связанным `Array(T)`/`Array(Tuple(...))`, разворачиваемым на сервере через `arrayJoin(@p)` (`ProcedureParameter.Table<T>`). Только у провайдера in-memory табличного параметра нет, и он бросает `NotSupportedException`. В ClickHouse `TypeName` отклоняется, а хранимых процедур нет, поэтому параметр потребляется SQL из `ExecuteRaw`/`ExecuteRawAsync`, вызывающим `arrayJoin`. См. [Сырой SQL](../guide/12-raw-sql.md#табличные-параметры). |
| **Конвертеры значений в `TimeSpan` в табличных параметрах на провайдерах без нативного типа длительности** | В общем шве записи конвертер владеет провайдерным представлением (сконвертированный `TimeSpan` связывается как есть), но у табличного параметра нет нативного связывания длительности в SQL Server, SQLite и ClickHouse. Поэтому столбец отображаемой сущности, конвертер которого нацелен на `TimeSpan`, отклоняется через `NotSupportedException` при построении столбцов параметра, до потребления строк; связывайте сконвертированное значение как его целочисленное хранение. PostgreSQL (`interval`) и MySQL/MariaDB (`TIME`) сохраняют сконвертированный `TimeSpan`. |
| **Потоковое чтение LOB (`ToStream`/`ToTextReader`) вне PostgreSQL, SQL Server, SQLite и провайдера in-memory** | Терминалы стриминга возвращают `Stream`/`TextReader`, владеющий `DbDataReader` и per-call `DbCommand` до освобождения; в этом выпуске они реализованы для PostgreSQL, SQL Server и SQLite. В SQLite источник запроса должен раскрывать `rowid` (обычная rowid-таблица): таблица `view` или `WITHOUT ROWID` падает fail-closed с сырым `Microsoft.Data.Sqlite.SqliteException: no such column: rowid`, без буферизованного фолбэка. Локатор можно добавить только к одноисточниковой проекции, поэтому соединения/несколько источников, `DISTINCT`/`DISTINCT ON`, `UNION`, `GROUP BY` и агрегаты не поддерживаются (могут падать с ошибкой драйвера), а для одноколоночной проекции переопределение сырым `WithSql` отклоняется с `NotSupportedException` (rowid-локатор нельзя безопасно добавить), тогда как сырая проекция из двух и более колонок отклоняется обычным `InvalidOperationException`. MySQL/MariaDB и ClickHouse отклоняют терминал через `NotSupportedException`; провайдер in-memory отдаёт его из материализованного значения как принадлежащий вызывающему `MemoryStream`/`StringReader` (читается только первая строка; пустой результат или `NULL` в первом значении дают `Stream.Null`/`TextReader.Null`), а буферизованная проекция `byte[]`/`string` остаётся доступной у каждого провайдера. Многоколоночный терминал `ToDataReader`/`ToDataReaderAsync` доступен только на PostgreSQL и SQL Server: SQLite падает fail-closed, потому что его потоковая проекция всегда несёт локатор `rowid`, MySQL/MariaDB и ClickHouse не имеют поддержки sequential access, а у провайдера in-memory нет `DbDataReader`. См. [Потоковое чтение больших объектов](../guide/26-large-objects.md). |
| **Экспорт CSV (`WriteCsv`/`WriteCsvAsync`) на провайдере in-memory и поверх неподдерживаемых проекций** | Терминалы CSV отдают результат `Select` в предоставленный вызывающим `Stream` на каждом SQL-провайдере (PostgreSQL, SQL Server, SQLite, MySQL, MariaDB, ClickHouse); поток назначения никогда не закрывается. У контекста in-memory нет `DbDataReader`, и он отклоняет терминал через `NotSupportedException` (как `ToDataReader`), без буферизованного фолбэка. Терминал CSV читает каждую поддерживаемую колонку без боксинга, включая числовые колонки SQL Server: после открытия reader'а он определяет фактический storage-тип колонки через hook `MapTypedColumnExpression` у провайдера, читает её storage-типизированным getter'ом и конвертирует типизированным `Convert.To<T>`, никогда через `GetValue`/`Convert.ChangeType(object)` (боксинг, который выполняет общий путь буферизованной материализации через `MapColumnExpression` при обычном `ToList`, к пути CSV не относится). Колонка проекции, у которой нет единой скалярной CSV-формы либо чей storage-тип неизвестен и не поддаётся конвертации, — вложенная сущность или коллекция, массив, отличный от `byte[]`, кортеж, словарь, произвольный объект или колонка, отображённая через объектный конвертер либо фолбэк на `GetValue`, — отклоняется до записи заголовка (и любой строки данных). `null`/`DBNull` пишется как настроенный `NullMarker` (по умолчанию `\N`), а пустая строка — как пустое поле, поэтому их можно различить, а остальной диалект (UTF-8 без BOM, экранирование по RFC 4180, CRLF, invariant-культура, форматы `O`/`D`) фиксирован. Защита от инъекции формул в табличные процессоры (CWE-1236) опциональна: `ExcelMode = true` добавляет префикс `'` полю, начинающемуся с `=`, `+`, `-` или `@`, после любого `ValueTransform` и до экранирования по RFC 4180, поэтому вызывающему, экспортирующему недоверенные данные, следует её включить (по умолчанию выключена). Колонка `byte[]` читается как поле целиком (типизированный `GetFieldValue<byte[]>`) и кодируется в Base64 для строки, поэтому память ограничена наибольшим полем/строкой, а не фиксированным буфером; chunked LOB streaming — будущий срез (триггер: спрос на экспорт крупных бинарных колонок). Запрос, читающий ленивую временную таблицу, созданную через `AsTempTable`, — не одна инструкция (нужен батч `DROP` + `CREATE TEMPORARY TABLE ... AS SELECT` + чтение на одной сессии), поэтому терминал отклоняет его с `NotSupportedException` до записи заголовка (и любой строки данных), не выполняя батч и без буферизованного фолбэка. См. [Потоковая выдача результатов запроса в CSV](../guide/28-csv-export.md). |

## Известные крайние случаи

- **Столкновение одноимённых захваченных переменных (существовало раньше, не связано с merge).** Захваченная переменная, читаемая глобальным фильтром запросов, и другая захваченная переменная, читаемая пользовательским `On(...)`, с одинаковым именем CLR дают одно и то же имя параметра, поэтому плейсхолдеры сталкиваются; переименуйте одну из переменных.

## Не ограничения

Следующее полностью реализовано и проверено; оно появляется в столбце *готово* анализа пробелов,
а не в списке выше:

- соединения любого типа (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, а также `CROSS APPLY`/`OUTER APPLY` и lateral-эквивалент там, где поддерживается) и арности 2–8, включая производный запрос с любой стороны (первичный источник `FROM` или присоединяемая таблица);
- коррелированные скалярные подзапросы и коррелированные `EXISTS`/`IN`/`ANY`/`ALL` в `SELECT`, `WHERE`, `ORDER BY` и `HAVING` у каждого SQL-провайдера на любой глубине вложенности, а также коррелированный скаляр/`EXISTS`/`IN` глубины один в `SELECT`/`WHERE`/`ORDER BY` у провайдера in-memory (см. [Подзапросы](../guide/05-subqueries.md));
- `CASE WHEN` / тернарный оператор / `switch`, `COALESCE`, числовой `CAST`;
- строковые, математические и date/time скалярные функции и `LIKE`;
- кросс-провайдерные скалярные строковые/числовые функции ([`SqlFunctions.Sql`](xref:NextORM.Core.SqlFunctions.Sql) `left`/`right`/`lpad`/`rpad`/`repeat`/`reverse`/`space`/`concat_ws`/`translate`/`ascii`/`@char`) с описанными выше гейтами по имени; in-memory провайдер вычисляет их через CLR-эквиваленты;
- арифметика дат (`date_add`/`end_of_month`/`date_diff`/`date_from_parts` и `DateTime.Add*`) в PostgreSQL, SQL Server, ClickHouse, MySQL/MariaDB и SQLite, а также `date_trunc` в PostgreSQL/SQL Server/ClickHouse и `string_agg` в PostgreSQL/SQL Server/ClickHouse/MySQL/MariaDB/SQLite;
- битовые (`bit_and`/`bit_or`/`bit_xor`), статистические (`corr`/`covar_*`) и `argMin`/`argMax` агрегаты в ClickHouse;
- бинарные столбцы — свойство или проекция `byte[]` отображается на `bytea` (PostgreSQL), `varbinary`/`image` (SQL Server) или `blob` (SQLite);
- потоковое чтение LOB в PostgreSQL, SQL Server и SQLite — одна колонка `byte[]`/`string` читается как `Stream`/`TextReader` с `CommandBehavior.SequentialAccess` и памятью O(буфера), без материализации всего значения (в SQLite источник запроса должен раскрывать `rowid`), а PostgreSQL/SQL Server дополнительно отдают многоколоночный результат как принадлежащий вызывающему `DbDataReader` через `ToDataReader`/`ToDataReaderAsync`; провайдер in-memory отдаёт скалярные терминалы из материализованного значения как принадлежащий вызывающему `MemoryStream`/`StringReader` (см. [Потоковое чтение больших объектов](../guide/26-large-objects.md));
- 64-битные беззнаковые целые — свойство или проекция `ulong`/`ulong?` материализуется через аксессор построителя строк `DbDataReader.GetFieldValue<ulong>` у провайдеров с нативным беззнаковым типом (ClickHouse `UInt64`, MySQL/MariaDB `BIGINT UNSIGNED`), без SQL-приведения; в PostgreSQL, SQL Server и SQLite беззнакового целого нет, и этот диапазон выражается только `numeric`/`decimal`;
- `IN` по списку/массиву, логические `!` и унарные операторы;
- `SELECT DISTINCT`, `INTERSECT`/`EXCEPT`, CTE (включая рекурсивные) и оконные функции;
- модифицирующие CTE (`WITH n AS (INSERT|UPDATE|DELETE ... RETURNING ...)`, однотабличные и join/multi-table) на PostgreSQL, читаются типизированно через [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1) (см. [модифицирующий CTE](../guide/15-insert-statement.md#модифицирующий-cte-postgresql));
- `OUTPUT ... INTO <target>` на SQL Server — `Returning(...).OutputInto(target)` записывает изменённые строки в существующую таблицу, `Returning(...).OutputIntoThenOutput(target)` записывает их и возвращает клиенту (см. [гайд по вставке](../guide/15-insert-statement.md#запись-изменённых-строк-в-таблицу-output-into));
- key-upsert `Returning()` — PostgreSQL/SQLite добавляют `RETURNING` к `ON CONFLICT ... DO UPDATE`, SQL Server рендерит `MERGE ... OUTPUT`; MySQL/MariaDB отклоняют его с `NotSupportedException` (см. [upsert](../guide/19-merge-statement.md#возврат-слитых-строк));
- пользовательские скалярные функции (`[SqlFunction]`) и табличные функции (`[SqlTableFunction]`);
- серверные/кластерные табличные функции ClickHouse `url`/`s3`/`file`/`remote`/`remoteSecure`/`cluster`/`clusterAllReplicas`, предобъявленные на `SqlFunctions.ClickHouse.*` с generic-интерфейсом строки `TRow`, объявляемым вызывающим (гейт — [`SupportsTableFunction`](xref:NextORM.Core.ISqlDialect.SupportsTableFunction(System.String)); см. [Табличные функции](../guide/11-table-valued-functions.md#встроенные-табличные-функции));
- предикаты полнотекстового поиска (`SqlFunctions.Sql.contains`/`freetext`) в SQL Server, PostgreSQL и MySQL/MariaDB, полнотекстовое ранжирование (SQL Server `containstable`/`freetexttable` с `KEY`/`RANK`, PostgreSQL `ts_rank`/`ts_rank_cd`), текстовые JSON-функции (`json_value`/`json_query`/`json_modify`/`isjson`) в SQL Server и MySQL/MariaDB и табличные функции SQL Server `openjson`/`string_split` (а также пользовательские обёртки `[SqlTableFunction]`, включая MySQL `JSON_TABLE` через `CallClause`);
- хинты уровня инструкции в SQL Server (`OPTION (...)`), PostgreSQL и MySQL/MariaDB (`/*+ ... */`), табличные хинты в SQL Server (`Hint(...)`, `WithTableHint(...)`, пер-join `JoinOptions.WithJoinTableHint(...)`), хинты join/подзапроса/области видимости (`JoinOptions.WithJoinHint`, `FromOptions.WithSubQueryHint`, `WithTablesInScopeHint`), JSON-вывод (`ForJson(...)` → `FOR JSON PATH`/`AUTO`) и XML-вывод (`ForXml(...)` → `FOR XML`);
- методы типа XML в SQL Server (`xml_value`/`xml_query`/`xml_exist` → `xml.value('xpath', 'type')`/`xml.query('xpath')`/`xml.exist('xpath')`, а также rowset `.nodes` через `xml_nodes` как источник `CrossApply`/`OuterApply`);
- raw SQL для запроса целиком ([`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)) / [`PrepareFromSql`](xref:NextORM.Core.EntityExtensions.PrepareFromSql``1(NextORM.Core.EntityBuilder{``0},System.String))) и как композируемый источник `FROM` ([`FromSql`](xref:NextORM.Core.DataContextExtensions.FromSql(NextORM.Core.IDataContext,System.String,System.Object)), рендерится как производная таблица), а также пути переиспользования неявного кэша планов / [`Prepare`](xref:NextORM.Core.EntityBuilderExtensions.Prepare``1(NextORM.Core.EntityBuilder{``0},System.Boolean,System.Threading.CancellationToken));
- выполнение сырых команд в контексте (`ExecuteRaw`/`ExecuteRawAsync`, а также хранимые процедуры через `ExecuteProcedure`/`ExecuteProcedureAsync`, возвращающие освобождаемый `ProcedureResult`) с именованными параметрами/`DbType`/`Size`, последовательными наборами результатов и выходными параметрами/возвращаемым значением (см. [Сырой SQL](../guide/12-raw-sql.md#выполнение-сырых-команд-executeraw));
- переопределение источника на запрос (`WithTableName`/`WithSchema`/`WithDatabase`/`WithServer`/`WithTableExpression`) у всех SQL-провайдеров, входит в ключ кэша планов (см. [Переопределение источника для запроса](../querying/02-query-sources.md#переопределение-источника-для-запроса)).
