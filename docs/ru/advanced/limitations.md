# Ограничения и возможности вне области охвата

> nextorm — построитель запросов с небольшой явной поверхностью DML: он генерирует инструкции `SELECT` (и параметризованные `INSERT ... VALUES`, `INSERT ... SELECT`, key upsert, `MERGE`, `DELETE` и `UPDATE`) и материализует их результаты, и намеренно оставляет отслеживание изменений и `SaveChanges` вызывающей стороне.

**Предварительные требования:** [Provider overview](../connecting-providers/overview.md) · [API reference](api-reference.md)

## Обзор

На этой странице перечислены возможности, которые **не** являются частью nextorm, с однострочной причиной для каждой.

## Ограничения

| Блок, где есть ограничения | Обоснование |
|---|---|
| **DML — остаточные ограничения** | ClickHouse отклоняет key upsert, а полный `MERGE` (ветви `WHEN MATCHED`/`WHEN NOT MATCHED`/`WHEN NOT MATCHED BY SOURCE` и `MERGE ... RETURNING`/`OUTPUT`) есть только в SQL Server и PostgreSQL 15+ — остальные провайдеры отклоняют и то, и другое. При активном глобальном фильтре запросов key upsert'ы `ON CONFLICT` / `ON DUPLICATE KEY` **отказывают** с `NotSupportedException` (fail closed; `IgnoreFilters()` их возвращает): ключ источника, сталкивающийся со скрытой целевой строкой, всё равно проявляет нативную ошибку уникального ограничения провайдера из ветви вставки — по любому уникальному индексу, в который он попадает, а не только по ключу слияния (оракул существования; составной ключ, включающий столбец фильтра, смягчает только первичный/merge-ключ), а merge только на обновление или только на удаление — тихий no-op; предпроверка значений источника остаётся отдельным TOCTOU-чтением (`QueryFilterValidator`), которое проверяет значения источника, а не целевые строки (см. [Изоляция цели записи](query-filters.md#изоляция-цели-записи)). Многотабличный `DELETE` на основе INNER join ([`From<T>().Join(...).Delete()`](../guide/18-delete-statement.md#удаление-по-соединению)) отклоняется SQLite и ClickHouse, многотабличный `UPDATE` на основе INNER join ([`From<T>().Join(...).CreateUpdateJoinBuilder()`](../guide/19-update-statement.md#обновление-из-join)) — ClickHouse, `UPDATE ... RETURNING` в MariaDB доступен только при явно настроенной версии 13.0+ ([`SupportsUpdateReturning`](xref:NextORM.Core.ISqlDialect.SupportsUpdateReturning)), а `ALTER TABLE ... UPDATE` в ClickHouse не сообщает число затронутых строк. Временная форма `CREATE TABLE ... AS SELECT` ([`ToTempTable`](../guide/20-create-table-as.md)) доступна только в PostgreSQL, SQLite, MySQL и MariaDB: в SQL Server нет `CREATE TEMPORARY TABLE ... AS SELECT` (используйте привязанную к сессии [`ToTable("#name")`](../guide/20-create-table-as.md)), а в ClickHouse нет временного `AS SELECT`. ClickHouse отклоняет батч с `NotSupportedException`, шаг DML в батче не может запрашивать возвращаемые строки (`Returning()` даёт другой тип билдера), и выполнение батча не проходит через интерсепторы запросов: их события несут `DbCommand`, а команда `DbBatch` — это `DbBatchCommand`. Отслеживания изменений и `SaveChanges` нет: записи — это явные команды. |
| **Синтаксис, зависящий от версии сервера** | nextorm никогда не опрашивает живой сервер, поэтому зависящая от версии возможность доступна только при **явно настроенной** версии. Агрегатный `FILTER (WHERE ...)` в PostgreSQL требует 9.4+: диалект, закреплённый ниже, отклоняет его с `NotSupportedException`, а **незаданная** версия молча предполагает 9.4+ и включает его. `UPDATE ... RETURNING` в MariaDB включается только при явной 13.0+ ([`SupportsUpdateReturning`](xref:NextORM.Core.ISqlDialect.SupportsUpdateReturning)); незаданная или более старая версия отклоняет его с `NotSupportedException`. PostgreSQL закрепляет одну неизменяемую версию сервера на **конкретный тип контекста** на всё время жизни процесса, поскольку `FILTER` влияет на кэшированный SQL `SELECT`; другая версия для того же конкретного типа бросает `InvalidOperationException`, поэтому процессу с несколькими версиями PostgreSQL нужен отдельный подкласс контекста на каждую версию. См. [PostgreSQL провайдер](../connecting-providers/postgres.md#версия-сервера) и [MariaDB провайдер](../connecting-providers/mariadb.md#версия-сервера). |
| **Рекурсивный CTE — SQL Server требует `UNION ALL`** | Устаревшее объявление `WithRecursive`, тело которого — distinct `UNION` (`anchor.Union(step)`), SQL Server отвергает («does not contain a top-level UNION ALL operator»), поэтому nextorm падает fail-closed во время подготовки запроса — до выполнения и до кэша планов — с действенным `NotSupportedException`. Переходите на `UnionAll` или типизированный API `AsRecursiveCte`. См. [CTE](../guide/10-cte.md#sql-server-устаревший-рекурсивный-cte-требует-union-all). |
| **`Prepare()` / кэш планов для DML** | Каждая мутация рендерит и выполняет одну команду за вызов — билдеры мутаций намеренно не готовятся и не кладутся в кэш планов. Оптимизация в nextorm нацелена только на read-only запросы (явный `Prepare`, неявный кэш планов, бенчмарки). |
| **Bulk-copy флаги вне SQL Server** | `BulkInsertOptions.CheckConstraints`/`TableLock`/`KeepNulls`/`FireTriggers` учитываются только нативным путём `SqlBulkCopy` в SQL Server: путь `COPY` в PostgreSQL и портируемый путь `INSERT ... VALUES` (MySQL/MariaDB/SQLite/ClickHouse, а также SQL Server, когда `Returning*` или `KeepIdentity` вынуждает портируемый путь) отклоняют запрошенный флаг с `NotSupportedException` вместо того, чтобы его игнорировать. `MaxDegreeOfParallelism`/`WithoutSession` в ClickHouse не экспонируются: `ClickHouseBulkCopy` из `ClickHouse.Driver` 1.4.0 устарел, а неустаревшему `ClickHouseClient.InsertBinaryAsync` нужен собственный клиент, тогда как сессия — это настройка строки подключения (`UseSession`), а не опция записи. `UseInternalTransaction` намеренно никогда не выставляется (nextorm не открывает неявную транзакцию). См. [Bulk insert](../guide/22-bulk-insert.md#опции-bulk-copy-в-sql-server). |
| **Неявные навигационные запросы / соединения из навигационных свойств** | Соглашения по внешним ключам и неявного вывода соединений нет: связь нужно объявить явно (`HasMany`/`HasOne`/`HasOneToOne`/`HasManyThrough`/`[Relationship]`, см. [Связи](../relationships/relationships.md)), а fluent-помощники объявляют **один** ключевой столбец — связь с составным ключом должна приходить из метаданных связи, где перечислены компоненты. `IRelationshipMetadata.Inverse` вычисляется лениво при **первом чтении** и кэшируется, поэтому регистрируйте обе стороны до чтения. Композиция LINQ поверх адаптера, проекция самого reference-адаптера и перегрузки предикатов падают fail-closed, а навигация-коллекция даёт ровно четыре прямых терминала (`Any`/`Count`/`LongCount`/свойство `Count`); `Count`/свойство `Count` — проверяемый `int` (64-битный счёт сужается при материализации и бросает `OverflowException` при выходе за диапазон), тогда как `LongCount` 64-битный сквозным образом. Коллекция, достигнутая через reference, отклоняется ClickHouse, который не может коррелировать подзапрос по join-источнику и бросает `NotSupportedException` (**принятое ограничение провайдера**, не дефект). Навигация поверх источника временной таблицы/TVP **недоступна (fail-closed)**: ленивый read-источник временной таблицы — это нетипизированный `TableAlias`, поэтому навигационный член по нему не читается — ни фолбэка на базовую таблицу, ни исключения. Табличный параметр (TVP) **не имеет корня запроса**: он пригоден только как параметр, привязывается через `ProcedureParameter.Table<T>` на сырой команде или хранимой процедуре, и источника `From<T>` для TVP нет. `LoadWith` вкладывается до уровня 2 и глубже; невыразимые вложенные формы, конфликтующий вложенный режим, циклический граф и потолок арности проекции падают fail-closed с `NotSupportedException` (см. [Жадная загрузка](../relationships/eager-loading.md#вложенные-графы-второй-уровень-и-глубже)). Дочерние источники `JoinInto` поддерживают только `Where`; остальные модификаторы запроса вызывают `NotSupportedException` до выполнения. `JoinInto` отклоняет с `NotSupportedException` необъявленную связь (если не используется перегрузка с явным ключом), производный (`As`) или присоединённый источник проекции на том билдере, где он объявлен, тип соединения, отличный от `Inner`/`Left`, несовпадающие типы явных ключей и более семи дочерних коллекций; смешивание `JoinInto` с любым другим соединением на том же билдере отклоняется (объявляйте его только на простом источнике сущности), опция ClickHouse `j => j.WithStrictness(Any)` обрезает загруженную коллекцию до одного потомка, а метаданные связи падают fail-closed при несмэппленном внешнем ключе, принципале без ключа или несовпадении типов FK/ключа принципала. **Дедупликация требует смэппленного ключа**: дедупликация родителя и идентичность потомка откатываются к ссылочной идентичности, когда соответствующая сторона не объявила ключ, а у SQL-провайдера каждая строка — новый экземпляр, поэтому повторные/декартовы строки выживают — задайте смэппленный ключ родителю и потомку (`[Key]`/`Key()`/соглашение `Id`) или используйте перегрузку с явным ключом и потомком с ключом. |
| **Ссылочная навигация внутри коррелированного предиката — поддерживается; коррелированная жадная загрузка — нет** | Объявленная ссылочная навигация, использованная внутри коррелированного тела `EXISTS`/`IN` или коррелированного скалярного подзапроса, **поддерживается**: переход соединяется на внешней команде, а вложенная команда читает присоединённый псевдоним — портируемый `LEFT JOIN` плюс коррелированный подзапрос (без `APPLY`/`LATERAL` на SQLite и ClickHouse), на переходе 1 и 2+, для скалярного сравнения, проверки присутствия и скалярной проекции. Это только предикатная/скалярная форма — она не добавляет ни коллекционных возможностей, ни новой формы соединения, и ClickHouse по-прежнему отвергает коллекцию, достигнутую через ссылку. **Коррелированная жадная загрузка — другая поверхность и остаётся неподдерживаемой**: [`EagerLoadMode.Correlated`](../relationships/eager-loading.md#correlated-и-постраничная-выборка-на-родителя) зарезервирован и отвергается с `NotSupportedException` во время подготовки — до генерации SQL и до записи в план, — поэтому коррелированный граф на каждого родителя не загружается. См. [Неявные навигационные запросы](../relationships/implicit-navigation.md). |
| **Уникальность внешнего ключа one-to-one (доверие на этапе объявления)** | Уникальность внешнего ключа потомка в one-to-one — это **доверие на этапе объявления**: ядро не проверяет ни схему базы, ни данные и не создаёт ограничение уникальности, поэтому неуникальный внешний ключ принимается при объявлении связи ([`HasOneToOne`](xref:NextORM.Core.EntityMetadataBuilder`1) или локальный `JoinOptions.OneToOne`, см. [Связи](../relationships/relationships.md#one-to-one-ссылка)). Единственная защита — рантайм-барьер на родителя в `JoinInto`: две разные **не-null идентичности потомков** для одного родителя бросают `InvalidOperationException` при материализации, а повторяющиеся идентичные строки и повторы с отсутствующей/null идентичностью допускаются (побеждает первый потомок). Проверка схемы/уникального индекса и необязательное отклонение при построении метаданных — **вне области охвата** (отдельно согласуемая возможность). |
| **Выбор присоединённой сущности целиком** | После соединения накопленная проекция позиционна (`Item1`..`Item8`, по одному элементу на источник в порядке соединения), поэтому стороны не имеют семантических имён, пока вы не спроектируете их в именованный тип; `SELECT *` никогда не генерируется, сравнение сущностей целиком в предикате и приведение элемента к несвязанному типу результата не поддерживаются. См. [Соединения](../guide/04-joins.md#адресация-проекции). |
| **«Голая» материализация производного источника зависит от формы выражения проекции** | Подзапрос/производный источник (`From(query)`/`From(builder)`) читается через явный внешний `Select`; чтение без проекции (`From(inner).ToList()`) допускается, только если внутренний список выборки уже состоит из разрешённых ссылок на столбцы (столбец сущности, переименованный спроецированный член, вычисляемый скаляр по его выходному имени). Проекция, требующая повторного перевода, — анонимная `new { x.Id }` или MemberInit/конструкторная DTO `new Dto { Id = x.Id }` — отклоняется на этапе подготовки с `QueryPreparationException` («…without an explicit outer Select…»). Это ограничение **формы выражения**, а не требование анонимного типа, и поддержка DTO-проекций при прямом чтении не означает поддержку «голого» чтения производного источника: добавьте внешний `Select` (например, `Select(x => x.Id)`). Этот вариант работает с DTO, создаваемыми через инициализатор членов, и позиционными записями; для проверенной проекции класса, создаваемого только через конструктор, существует ранее выявленная ошибка (`Cannot find inner column Id`), поэтому используйте одну из этих поддерживаемых форм. См. [Подзапросы](../guide/07-subqueries.md#подзапрос-как-источник-from) и [Источники запроса](../guide/01-query-sources.md#подзапрос-в-качестве-источника). |
| **Именованные псевдонимы соединений и псевдоним корня** | Именованный путь — **только выражения и только SQL-провайдеры**: in-memory провайдер падает fail-closed с `NotSupportedException` на **любом** псевдониме (псевдоним соединения или корня, включая смешанные цепочки), а чтение сгенерированного члена-псевдонима вне дерева выражений по дизайну бросает `NotSupportedException`. У `JoinInto` (загрузчика связи одним запросом) **нет** поверхности псевдонимов, и он никогда не принимает аргумент `Alias.<Name>`. Форма без явного источника тоже несёт псевдоним — `.Join<TJoin>((left, right) => …, Alias.X[, options])` на корневом `EntityBuilder<T>` и на получателях `JoinedEntityBuilder` арностей 2–7 (результирующие слоты 2–8), — и это единственная форма псевдонима, принимающая опции соединения; `CrossJoin`/`CrossApply`/`OuterApply` не принимают условия и потому остаются только с явным источником, источник-сырая таблица не разрешается по типу, а MySQL/MariaDB по-прежнему отклоняют `FullJoin` в каждой форме с `NotSupportedException` (`Full join`). Плоская типизированная цепочка останавливается на восьми слотах (`Projection<T1..T8>`) — это граница области, а не отказ на этапе компиляции, потому что унаследованные члены generic-базы всё ещё компилируются; чтобы продолжить дальше восьми таблиц, спроектируйте накопленное соединение в именованный тип через `As<T>`. `.WithAlias` доступен только на корне (после соединения или второго псевдонима корня это ошибка компиляции `NORMGEN008` и рантайм-барьер fail-closed), а цепочка, где **корень или промежуточный присоединённый шаг** проектирует **анонимный** тип, отклоняется с `NORMGEN009` — **последний** присоединённый шаг может оставаться анонимным. См. [Соединения](../guide/04-joins.md#именованные-псевдонимы-соединений). |
| **Коррелированный источник `APPLY` / `LATERAL`** | Диалекты без lateral-источника (SQLite, ClickHouse) отклоняют [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) сразу, а лямбда корреляции не может ссылаться на проекцию соединения — применяйте её к источнику одной сущности. |
| **[`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) / [`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) на SQL-провайдерах** | [`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) бросают `NotSupportedException`; коррелированный эквивалент покрывает явная поверхность соединений [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) (см. [Соединения](../guide/04-joins.md)). |
| **Коррелированные скалярные терминалы (`First`/`Single` и их `*OrDefault`)** | `Single`/`SingleOrDefault` по более чем одной строке бросают у каждого провайдера, чьи скалярные подзапросы проверяют кардинальность (PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse); SQLite её не проверяет, поэтому числовой `Single`/`SingleOrDefault` по более чем одной строке вызывает ошибку базы через отрендеренный барьер `case when count(*) > 1 then <numeric overflow> else value end`, а нечисловая проекция отклоняется с `NotSupportedException`. `First`/`Single` по не-nullable проекции значения бросают, когда ни одна строка не совпала. |
| **Блокирующие табличные хинты вне SQL Server** | Блокирующий табличный хинт (`WithTableHint("nolock")` → `WITH (NOLOCK)`) применяется только в SQL Server, к таблице `FROM` запроса или к одному соединению через `JoinOptions.WithJoinTableHint`; нативные index-хинты MySQL/MariaDB (`USE`/`FORCE`/`IGNORE INDEX`), SQLite (`INDEXED BY`/`NOT INDEXED`) и SQL Server (`WITH (INDEX(...))`) — отдельная поверхность ([`WithIndex`](../guide/15-query-hints.md#index-хинты), [`ISqlDialect.IndexHints`](xref:NextORM.Core.ISqlDialect.IndexHints)). SQLite и ClickHouse отклоняют `Hint(...)` с `NotSupportedException`, и те же гейты действуют для хинтов соединения (`JoinOptions.WithJoinHint`), подзапроса (`FromOptions.WithSubQueryHint`) и области видимости таблиц (`WithTablesInScopeHint`); SQL Server дополнительно отклоняет хинт подзапроса, потому что T-SQL не может дописать его к подзапросу (см. [Хинты запросов](../guide/15-query-hints.md)). |
| **В MariaDB нет блокировки уровня источника (`FOR UPDATE OF`)** | Блокировка уровня источника ([`FromOptions.ForUpdate`](xref:NextORM.Core.FromOptions.ForUpdate)/[`FromOptions.ForShare`](xref:NextORM.Core.FromOptions.ForShare), [`JoinOptions.ForUpdate`](xref:NextORM.Core.JoinOptions.ForUpdate)/[`JoinOptions.ForShare`](xref:NextORM.Core.JoinOptions.ForShare)) требует диалекта, у которого [`ILockRenderer.SupportsSourceLocks`](xref:NextORM.Core.ILockRenderer.SupportsSourceLocks) равен `true` (PostgreSQL, MySQL, SQL Server). В грамматике MariaDB нет `FOR UPDATE OF`/`FOR SHARE OF`, поэтому блокировка уровня источника детерминированно отклоняется с `NotSupportedException` (fail-closed): она никогда не игнорируется молча, не заменяется блокировкой всего запроса и не рендерится как неподдерживаемый `OF`. В SQLite и ClickHouse блокировки строк нет вовсе, и они отклоняют и блокировку всего запроса, и блокировку уровня источника. |
| **Блокирующие хинты всего запроса в SQL Server охватывают каждый источник** | Блокировка всего запроса [`ForUpdate`](xref:NextORM.Core.EntityBuilder`1.ForUpdate)/[`ForShare`](xref:NextORM.Core.EntityBuilder`1.ForShare) ставит хинт `with (updlock)`/`with (holdlock)` на **каждый** физический источник `FROM`/`JOIN` (раньше — только на первичный), поэтому многотабличный запрос блокирует больше таблиц, чем прежде; блокировка уровня источника оставляет хинт на выбранном источнике. |
| **Ключевые слова в верхнем регистре — конструкторы tuple/row сохраняют канонический вид провайдера** | При `KeywordCase.Upper` (`DataContextBuilder.UseKeywordCase`, `EntityBuilder<TEntity>.WithKeywordCase`, `QueryCommand<T>.WithKeywordCase`) в верхний регистр переводятся все ключевые слова ядра, трансляторов, диалектов и возможностей, но конструкторы строк/tuple `ROW(...)` (PostgreSQL) и `tuple(...)` (ClickHouse) трактуются как function-like конструкторы и сохраняют каноническое написание провайдера. Идентификаторы, строковые литералы, имена функций, имена типов и сырой SQL не затрагиваются никогда. |
| **Раскладка инструкции не настраивается** | Каждый сгенерированный `SELECT` — верхний и вложенные формы (производная таблица в `FROM`, тело CTE, `SELECT` внутри `INSERT ... SELECT`/`CREATE TABLE ... AS SELECT`) — начинает `FROM` и каждое `JOIN` с новой строки, безусловно: нет ни флага включения, ни уровня отступа, ни пустых строк. Сгенерированный SQL использует только `\n` — никогда `\r` — у каждого провайдера и в каждой ОС. Передаваемый вами сырой SQL (`WithSql`, `WithTableExpression`, `ExecuteRaw`, `Raw`, текст процедуры), строковые литералы и значения параметров **никогда** не переформатируются: nextorm не разбирает и не переформатирует непрозрачный ввод. |
| **Доступ к элементу серверного массива/JSON (`x[i]`)** | Поддерживается только индексирование захваченной (замкнутой) коллекции внутри запроса ([lookup по захваченной коллекции](../guide/03-filtering-where.md#lookup-по-захваченной-коллекции-dictcolumn)): константный ключ сводится к параметру, а ключ-столбец рендерит портируемый `CASE`. Доступ к элементу серверного столбца-массива/JSON или выражения, возвращающего массив (`groupArray(x)[0]`, `array_agg(x)[1]`, `json['k']`), не имеет портируемой SQL-формы и бросает `NotSupportedException` (как и пользовательский индексатор) вместо привязки всей коллекции. Нативные формы различаются (`arr[i]` в PostgreSQL, `arrayElement(arr, i)` в ClickHouse, JSON-пути в остальных), поэтому им нужен отдельный хук диалекта. |
| **Нативный тип колонки `JSON` в ClickHouse** | Нативный тип колонки `JSON` имеет объектный корень: массив или скалярный корень падает fail-closed, а чтение простой `string` поверх колонки `JSON` не поддерживается — как и устаревший псевдоним `Object('json')`, которому нужен connection-level `allow_experimental_object_type`, который nextorm никогда не выставляет (и даже тогда чтения материализуются как `Tuple<SByte,String>`). JSON-проекция должна быть **именованной формы** (`Select(x => new { x.Doc })` или DTO), потому что простой скаляр верхнего уровня `Select(x => x.Doc)` не обрабатывается классификатором проекций ядра. См. [Поддержка JSON](../guide/16-json.md#отобразить-clr-объект-на-нативную-json-колонку). |
| **`untuple` (ClickHouse)** | `untuple(tuple)` не смэпплена: она разворачивает tuple в несколько колонок результата, что не имеет единой скалярной CLR-формы в проекции. Проектируйте `Tuple(...)` как `System.Tuple<...>` и читайте элементы через `tupleElement`/`System.Tuple<...>.ItemN`. |
| **Поверхность row-value (tuple): остаточные ограничения** | Реляционные операнды (`<`/`>`/`<=`/`>=`) и реляционные операнды `ValueTuple` невыразимы в C#/деревьях выражений (граница языка, а не ограничение продукта). В MySQL/MariaDB/SQLite конструктор строки в `Select`/`ORDER BY`/`GROUP BY` или в аргументе функции, а также любой серверный `.ItemN` бросают `NotSupportedException` при подготовке (с указанием провайдера); SQL Server отклоняет конструкторы **и любую форму tuple `IN`/`Contains`** заранее с `NotSupportedException` (`SQL Server does not support tuple IN/Contains translation.`), включая null-коллекцию, null-элемент reference-tuple, арность ≥8 и вложенные tuple, так что ошибка вычисления там возникнуть не может. У поддерживающих провайдеров nullable-элемент tuple (`List<(int, int)?>`) бросает `NotSupportedException`, арность ≥8/`Rest`/вложенные tuple бросают `NotSupportedException`, а правая часть `QueryCommand` (подзапроса) tuple-типа отложена (пока не поддерживается, будущая веха не обещана). Материализация сырого `ROW(...)`/row value есть только в PostgreSQL: `ValueTuple`, арность ≥8, вложенный или пустой `ROW`, несколько или смешанные record-колонки, незарегистрированный именованный composite и именованный composite, объявленный как `System.Tuple`, остаются под барьером `NotSupportedException` (см. [Сырой SQL](../guide/14-raw-sql.md#сырые-postgresql-строки-и-composite-типы) и [Скалярные функции](../scalar-functions/index.md)). |
| **Привязка элемента нескольких выражений `ARRAY JOIN` сразу (ClickHouse)** | [`ArrayJoinElement`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.ArrayJoinElement``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,System.Collections.Generic.IEnumerable{``1}}}))/[`LeftArrayJoinElement`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.LeftArrayJoinElement``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,System.Collections.Generic.IEnumerable{``1}}})) привязывают элемент ровно одного выражения-массива к `p.Element`: второй вызов, вызов на соединённом запросе или вызов после `Where`/`Having` бросает `InvalidOperationException`. Если вы делаете array-join нескольких массивов и типизированный элемент не нужен, используйте [`ArrayJoin`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.ArrayJoin``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,``1}}))/[`LeftArrayJoin`](xref:NextORM.ClickHouse.ClickHouseEntityBuilderExtensions.LeftArrayJoin``2(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{``0,``1}})); эти члены array-join — методы расширения в `NextORM.ClickHouse` (`using NextORM.ClickHouse;`). |
| **Состояние агрегатных функций ClickHouse (`-State`/`-Merge`, `runningAccumulate`)** | `uniqState`/`sumState`/`countState`/… возвращают непрозрачное значение `AggregateFunction(...)`, которое nextorm не моделирует: `ClickHouse.Driver` 1.4.0 бросает `AggregateFunctionException` из `FrameworkType`/`Read`/`Write`, поэтому такую колонку нельзя материализовать в CLR-значение или передать как него (сообщение драйвера указывает на парную `-Merge`). Сам `uniqMerge(uniqState(x))` нелегален (`ILLEGAL_AGGREGATION`), поэтому `-Merge` нуждается в состоянии, полученном на сервере (подзапрос или таблица состояний), а `runningAccumulate` устарела в ClickHouse 25.8 (`DEPRECATED_FUNCTION`, нужен `allow_deprecated_error_prone_window_functions`). |
| **Форматирование строк и коллация за пределами документированного подмножества** | `string.Format`/интерполяция/`value.ToString(format)` транслируют только culture-invariant подмножество: числа `N`/`F`/`D`/`X` (по провайдеру) и токены даты `yyyy yy MM dd HH mm ss` с разделителями `- / . : T` и пробелом. Любой другой спецификатор и любая культура, кроме `CultureInfo.InvariantCulture`, бросают `NotSupportedException`. Перегрузки порядкового `StringComparison` принимают только `Ordinal`/`OrdinalIgnoreCase` (`InvariantCulture`/`CurrentCulture` бросают); SQLite дополнительно отклоняет регистрозависимые порядковые `Contains`/`StartsWith`/`EndsWith`, потому что его `LIKE` всегда регистронезависим независимо от коллации ([`SupportsOrdinalLike`](xref:NextORM.Core.ISqlDialect.SupportsOrdinalLike)). См. [Ordinal-сравнение и коллация](../scalar-functions/01-string-functions.md#ordinal-сравнение-и-коллация). |
| **Null-safe-сравнение захваченных значений — точная область** | `==`/`!=` между колонкой nullable-типа значения или строкой и **захваченной** переменной nullable/string-типа подчиняются семантике равенства с null из C# в обоих порядках операндов (`null == null` — true, `null != null` — false, ровно один null даёт `==` false / `!=` true) и являются SQL-null-total; `<`/`>`/`<=`/`>=` сохраняют обычное сравнение. `HasValue`/`!HasValue` у смэппленной колонки `Nullable<T>` рендерят `is not null`/`is null`. Эти формы поддерживаются только в предикатах (`WHERE`, коррелированный `Exists`), логических проекциях `SELECT` (материализуются в non-nullable `bool`; SQL Server — `bit`) и `JOIN ON`, где меняется только выражение `ON`. **Не** перезаписываются и не являются null-safe: сравнение nullable-колонки с другой nullable-колонкой (в `WHERE`, `SELECT` или `JOIN ON`), `ORDER BY`, `GROUP BY`, `PARTITION BY`/`ORDER BY` оконных функций, `LIMIT BY` в ClickHouse, `Nullable<T>.Value`, вручную построенный `DefaultExpression` и оператор `IS [NOT] DISTINCT FROM` (issue #288) — сравнение колонок между собой и нативная различимость остаются отдельной работой. Сравнение строк использует обычную коллацию провайдера; коллация CLR не обещается. |
| **Offset `DateTimeOffset` не сохраняется вне SQL Server** | Только нативный `datetimeoffset` в SQL Server сохраняет offset значения: PostgreSQL хранит момент (`timestamp with time zone`) и материализует каноническое значение с нулевым offset, MySQL/MariaDB (`datetime`) и ClickHouse (`DateTime64(6)`) не хранят offset как часть значения, а SQLite пишет UTC-момент текстом (точность до миллисекунд). Члены без серверной трансляции (`.Offset`, `.UtcDateTime`, `.LocalDateTime`, `.Date`, `.Ticks`, `.DayOfWeek`, `.ToOffset(...)`, `.AddTicks(...)`, `.Add(TimeSpan)`) падают fail-closed с `NotSupportedException`. См. [Дата и время](../scalar-functions/03-date-and-time.md#datetimeoffset). |
| **Простые скалярные проекции значений `enum` и `DateTimeOffset`** | Реляционная проекция, *тип результата* которой — enum без конвертера значений (`Select(it => it.State)`, `Select(it => it.MaybeState)` и генерируемые тела `Min`/`Max`), отклоняется при подготовке с `NotSupportedException` (`Enum scalar projections without a value converter are not supported in a server-side query.`), а сконвертированный enum-скаляр остаётся поддержанным. Члены `DateTimeOffset` без серверной трансляции падают fail-closed в любой реляционной форме проекции, включая простой скаляр (`Select(v => v.Created.DayOfWeek)`, `.First()`), который раньше проявлялся как ошибка конструктора материализатора строк. Оба отказа включаются только при маппинге строк (`IContextEnvironment.NeedMapping`), поэтому клиентская материализация in-memory-провайдера не меняется. См. [Проекции](../guide/02-projections.md#примитивная-и-скалярная-проекция) и [Дата и время](../scalar-functions/03-date-and-time.md#datetimeoffset). |
| **Коллация на уровне столбца в ClickHouse и DDL** | В ClickHouse нет клаузы `COLLATE`, и он отклоняет колонку с коллацией с `NotSupportedException`, а nextorm никогда не выводит коллацию в определении столбца (его единственный DDL — `CREATE TABLE ... AS SELECT`, который не несёт явной коллации столбцов), поэтому объявленные [`CollationAttribute`](xref:NextORM.Core.CollationAttribute) / [`Collation(...)`](xref:NextORM.Core.EntityPropertyBuilder`1.Collation(System.String)) описывают коллацию **существующего** столбца и не создают её. | **Регулярные выражения** | Шаблон, замена и опции должны быть константами времени компиляции, отображается только `RegexOptions.IgnoreCase`, а шаблон исполняется собственным движком провайдера (POSIX/ICU/PCRE/RE2/.NET), поэтому сложные шаблоны (lookaround, обратные ссылки) и ссылки на группы в замене непортируемы. | **Хранимые процедуры и динамический SQL** | Сборка SQL во время выполнения — вне поверхности построителя, а хранимые процедуры не поддерживаются в SQLite и ClickHouse, которые бросают `NotSupportedException`; в остальных они вызываются как сырой текст `EXEC`/`CALL` через `ExecuteRaw` либо по имени через `ExecuteProcedure`/`ExecuteProcedureAsync` (см. [Сырой SQL](../guide/14-raw-sql.md#хранимые-процедуры-executeprocedure)). |
| **Несколько наборов результатов из батча** | Наборы результатов буферизуются жадно — потоковой передачи и произвольного доступа нет — и только терминал `BatchQuery<TResult>` с одним результатом стримит (`ToAsyncEnumerable`); позиционный путь `Read<TResult>()` и курсорный обход `Read<T>()` по набору смешивать нельзя. Дискриминатор и выбор по типу времени выполнения не поддерживаются; см. [ограничение наследования](#inheritance-limitations). Используйте явные предикаты по сопоставленным столбцам. |
| **Смежные платформы и инструменты (не планируются)** | Несколько соседних направлений намеренно вне nextorm: **скаффолдинг схемы / генерация кода** — маппинги объявляются в коде (`[Column]`/`[Table]`, fluent-билдер, связи), и ничего не выводится из живой схемы; **дополнительные ADO.NET-провайдеры** — поставляемый набор: PostgreSQL, SQL Server, SQLite, MySQL, MariaDB и ClickHouse (Oracle, Firebird, DB2, SAP HANA, Informix, Sybase, Redshift, DuckDB, YDB, Access и SQL CE не планируются); **F#-специфичный маппинг** (`option`, однорегистровые размеченные объединения), **драйвер LINQPad** и **удалённый/gRPC контекст**; **переключатель инлайнинга SQL** — намеренно только параметризация; inline-режим не планируется (см. [Управление кэшем](../engine/03-plan-cache-and-reuse.md#управление-кэшем)); и **типизированный делегат скомпилированного запроса** — [`Prepare`](../engine/03-plan-cache-and-reuse.md#явный-prepare) покрывает компиляцию-один-раз и переиспользование, но это состоятельная однопоточная команда с позиционными параметрами, а не потокобезопасный типизированный `Func<...>`; неявный кэш планов — потоковая альтернатива, а типизированный конкурентный делегат не планируется. |
| **Обслуживание индексов FTS в SQLite** | Билдер команд обслуживания (`IDataContext.CreateSqliteFts5CommandBuilder(tableName)` → `AutoMerge`/`CrisisMerge`/`Merge`/`Optimize`/`Rebuild`/`IntegrityCheck`) существует только для SQLite: у любого другого провайдера поверхность обслуживания бросает `NotSupportedException` до любого обращения к базе, невалидная цель — null, пустое, пробельное или содержащее NUL имя таблицы — отклоняется, а `Rebuild` contentless FTS5 падает нативно. FTS3/4 `Rank` ожидает зарегистрированную в подключении UDF `rank`, а сама виртуальная таблица создаётся сырым SQL. Это инструкции уровня команд — не скалярные/табличные функции и не часть `SqlFunctions.Sqlite`. |
| **Unit of work, `SaveChanges` и отслеживание изменений / CDC** | nextorm не владеет unit of work и не отслеживает сущности, и `SaveChanges` нет: записи — явные команды, конкурентность нужно проверять явно (токен в `WHERE` + число затронутых строк), а слой отслеживания изменений приходится строить сверху — см. [Оптимистичная конкурентность и отслеживание изменений](../guide/26-optimistic-concurrency.md). В ClickHouse нет транзакции, и он её отклоняет. |
| **Интеграция с EF Core: мост `SaveChanges` и маппинг на контекст** | Синхронизации отслеживания изменений и моста `SaveChanges` нет: DML nextorm обходит change tracker EF, поэтому записанные им строки трекеру неизвестны, и мост явно вне области охвата. Маппинг регистрируется в процессном кэше метаданных nextorm с ключом по `Type`, поэтому **не более одного маппинга на CLR-тип на процесс** — два `DbContext`, маппящие один тип по-разному, не могут обслуживаться оба: вторая, отличающаяся регистрация бросает `InvalidOperationException`. Нереляционный провайдер EF `InMemory` не имеет `DbConnection` и не поддерживается. Контекст, привязанный через мост, у которого импортированные метаданные фильтров позже потеряны (`DataContextCache.Clear()` или вытеснение по скользящему сроку), падает fail-closed с `InvalidOperationException` на следующем запросе или построении DML вместо работы без фильтров. Срез ClickHouse без EF-адаптера и сертификация общего подключения для MariaDB остаются открытыми единицами в `1.0.9-b`. См. [Интеграция с EF Core](integration-efcore.md). |
| **Таймаут команды в ClickHouse** | `UseCommandTimeout`/`WithCommandTimeout` выставляют ADO.NET `DbCommand.CommandTimeout` у каждого SQL-провайдера, но `ClickHouse.Driver` 1.4.0 не переносит его на HTTP-запрос — запрос ограничивает `Timeout` подключения (по умолчанию две минуты) — поэтому там значение не действует. Переопределение на запрос применяется к read-запросам; команды DML и батчи используют значение контекста по умолчанию. |
| **PostgreSQL `oid` и другие системные типы на `uint` через параметр `uint`** | Npgsql отображает `oid` и другие системные типы на базе `uint` (например `cid`) на CLR `uint`, поэтому чтение в свойство `uint` работает, но nextorm привязывает параметр `uint` как `xid`, а у `oid = xid` нет оператора (SQLSTATE 42883) — сравнение или запись такой цели через параметр `uint` поэтому падает. Сравнивайте через приведение к `bigint` (`Where(e => (long)e.Oid == (long)value)`) или выполняйте сырой SQL с параметром `bigint` и явным приведением `::oid`. См. [PostgreSQL провайдер](../guide/provider-specific-sql/postgresql.md). |
| **Типы PostgreSQL, отсутствующие в каталоге типов Npgsql** | Классификация composite авторитетна: колонка считается именованным composite только тогда, когда так говорит загруженный каталог типов Npgsql, и никогда — по dotted-имени типа данных или форме исключения. На чистом каталоге несмэппленный не-composite тип (например `hstore` или `ltree`) даёт обычную ошибку «None of the result-set columns (...) matches a mapped property» вместо диагностики именованного composite, а настоящий composite, типа которого нет в загруженном каталоге, деградирует до той же обычной ошибки, пока нет авторитетных метаданных типа (сознательный компромисс — холодный каталог не даёт вердикта о composite вместо вводящего в заблуждение). Composite нужно зарегистрировать через `MapComposite<T>` до чтения, а перезагрузка типов должна нацеливаться на процессный неявный источник данных Npgsql, связанный с той же строкой подключения, что и контекст. |
| **Интерсепторы за пределами жизненного цикла команды/соединения** | Интерсептора исключений нет — транслируйте исключение провайдера через `try`/`catch` вокруг терминального вызова, и интерсептор не должен менять `CommandText` (команда принадлежит кэшированному плану). Глобальные фильтры запросов — отдельный слой. См. [Интерсепторы](../infrastructure/02-interceptors.md). |
| **Динамические столбцы — остаточные ограничения** | Нет пер-ключевых `IPropertyValueConverter`/JSON: значения привязываются из рантайм CLR-значения (pass-through). nextorm не отслеживает изменения, столбец нельзя очистить пропуском ключа (пропущенный ключ опускается из `UPDATE`/`MERGE`, поэтому SQL `NULL` пишет только присутствующий ключ со значением `null`), белого списка ключей нет (вместо этого ключи кавычатся как идентификаторы и валидируются), многострочный `INSERT` требует одинакового набора ключей в каждой строке, а в `MERGE` динамические столбцы попадают в источник/`INSERT`/`SET` и никогда в `ON`. Чтение ограничено одним физическим источником (запрос с соединениями отклоняет хранилище с `NotSupportedException`) и сущностью, читаемой целиком (явная проекция его не собирает). Сущность с хранилищем должна быть ссылочным типом с публичным конструктором без параметров: `struct` с хранилищем отклоняется с `InvalidOperationException` при построении метаданных, а отсутствие публичного конструктора без параметров — при подготовке с `QueryPreparationException`. См. [Динамические столбцы](../guide/29-dynamic-columns.md). |
| **Конвертеры значений в `TimeSpan` в табличных параметрах у провайдеров без нативного типа длительности** | У табличного параметра нет нативной привязки длительности в SQL Server, SQLite и ClickHouse, поэтому колонка смэппленной сущности, конвертер которой нацелен на `TimeSpan`, отклоняется с `NotSupportedException` при построении столбцов параметра, до чтения любой строки; привязывайте сконвертированное значение как его целочисленное хранилище. PostgreSQL (`interval`) и MySQL/MariaDB (`TIME`) сохраняют сконвертированный `TimeSpan`. |
| **Потоковая передача LOB (`ToStream`/`ToTextReader`) вне PostgreSQL, SQL Server, SQLite** | В MySQL/MariaDB и ClickHouse нет последовательного доступа, и они отклоняют потоковые терминалы и многоколоночный `ToDataReader` с `NotSupportedException` (буферизованная проекция `byte[]`/`string` там остаётся доступной). В SQLite источник запроса должен раскрывать `rowid`: `view` или таблица `WITHOUT ROWID` падает fail-closed сырым `Microsoft.Data.Sqlite.SqliteException: no such column: rowid`, без буферизованного фолбэка; локатор можно дописать только к проекции с одним источником, поэтому соединения/несколько источников, `DISTINCT`/`DISTINCT ON`, `UNION`, `GROUP BY` и агрегаты не поддерживаются (могут упасть ошибкой драйвера), проекция с одним столбцом и сырым переопределением `WithSql` отклоняется с `NotSupportedException` (локатор `rowid` нельзя добавить безопасно), а сырая проекция двух и более столбцов — обычным `InvalidOperationException`. См. [Потоковая передача больших объектов](../guide/28-large-objects.md). |
| **CSV-выгрузка (`WriteCsv`/`WriteCsvAsync`) на неподдерживаемых проекциях** | Колонка проекции, у которой нет единой скалярной CSV-формы или тип хранилища неизвестен/не конвертируется — вложенная сущность или коллекция, массив кроме `byte[]`, tuple, словарь, произвольный объект либо колонка, смэппленная через объектный конвертер или фолбэк `GetValue`, — отклоняется до заголовка (и любой строки данных). Защита от инъекции формул в таблицы (CWE-1236) **по умолчанию выключена**: `ExcelMode = true` — опция, поэтому при выгрузке недоверенных данных её нужно включать. Запрос, читающий ленивую временную таблицу `AsTempTable`, отклоняется с `NotSupportedException` до заголовка, потому что это батч (`DROP` + `CREATE TEMPORARY TABLE ... AS SELECT` + чтение на одной сессии), а не одна инструкция. В MySQL/MariaDB/ClickHouse и для любого бинарного случая вне прямо хранимой колонки `byte[]` у провайдера с последовательным доступом колонка `byte[]` читается целым полем, поэтому память ограничена самым большим полем/строкой, а не фиксированным буфером 12 КиБ. Поток назначения никогда не закрывается и не освобождается, а остальной диалект (UTF-8 без BOM, экранирование RFC 4180, CRLF, инвариантная культура, форматы `O`/`D`) фиксирован. См. [Потоковая передача данных в Stream](../guide/30-streaming-data.md#csv). |
| **Строковые и char-значения передаются точно, но нативные ограничения сравнения остаются** | Строковое значение или значение `char` передаётся точно — встроенным литералом или связанным параметром — в пределах корректного Unicode, представимого в целевом типе колонки базы (непарные UTF-16 суррогаты — вне области охвата): экранирование зависит от провайдера, PostgreSQL рендерит `E'…'` с `\\` и `\'`, а остальные символы C0 — как `\xNN`, а SQLite рендерит значение с `U+0000` как UTF-8-выражение `CAST(X'…' AS TEXT)`, тогда как обычные значения сохраняют удвоенные апострофы. `U+0000` в строке или char в PostgreSQL отклоняется с `NotSupportedException`, где названы PostgreSQL и `U+0000` (само значение никогда не выводится), как при трансляции литерала, так и перед каждым выполнением связанного параметра — включая последующие выполнения кэшированной команды. Гарантия не эмулирует нативные ограничения — нативный `LIKE` или сравнение текста в SQLite останавливается на первом NUL, а коллации и padding ведут себя нативно — а SQL вызывающего кода (сырой SQL, хранимые процедуры, сырые переопределения) сохраняет существующий транспорт параметров, который вне гарантии точной передачи. |

## Известные крайние случаи

- **Столкновение одноимённых захваченных переменных.** Захваченная переменная, читаемая глобальным фильтром запросов, и другая захваченная переменная, читаемая пользовательским `On(...)`, с одинаковым именем CLR дают одно и то же имя параметра, поэтому плейсхолдеры сталкиваются; переименуйте одну из переменных.
- **Привязка фильтров к сырому источнику — best-effort и непроверяемая.** `FromSql`/`From(string)` применяют глобальный фильтр только после того, как [`BindEntity<TEntity>`](xref:NextORM.Core.EntityBuilderExtensions.BindEntity``1(NextORM.Core.EntityBuilder{NextORM.Core.TableAlias},System.Collections.Generic.IReadOnlyCollection{System.String})) объявит тип сущности и выходные столбцы; фильтр с отсутствующими обязательными столбцами пропускается с предупреждением `RawSourceFilterSkipped` на категории `NextORM.QueryFilters` (причина `MissingColumns`, физические имена mapped-столбцов), а не бросает исключение, тогда как при пустом объявленном списке столбцов фильтр с доказанной пустой зависимостью всё же применяется, а фильтр, зависящий от столбца, или неопределённый фильтр пропускается с причиной `UndeterminedColumns`. Список столбцов — это слово вызывающего: nextorm не разбирает сырой SQL и не проверяет его по схеме, поэтому объявленный столбец, который фрагмент на самом деле не возвращает, принимается и может заставить фильтр сработать против неверной формы. Привязка не является гарантией безопасности; провайдер без поддержки сырых источников отклоняет источник. См. [Фильтры на привязанных сырых источниках](query-filters.md#фильтры-на-привязанных-сырых-источниках).

## Не ограничения

Следующее полностью реализовано и проверено; это описано на отдельных страницах и не является
ограничением:

- соединения любого типа (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, а также `CROSS APPLY`/`OUTER APPLY` и lateral-эквивалент там, где поддерживается; нет `FULL JOIN` в MySQL/MariaDB) и арности 2–8, включая производный запрос с любой стороны (первичный источник `FROM` или присоединяемая таблица);
- производные/подзапросные источники, читаемые через явный внешний `Select`, включая переименованные и вычисляемые внутренние столбцы (см. [Подзапросы](../guide/07-subqueries.md#подзапрос-как-источник-from)), и DTO/record/конструкторные проекции при прямом чтении (см. [Проекции](../guide/02-projections.md#dto)) — ограничение формы выражения выше касается только чтения производного источника *без проекции*;
- коррелированные скалярные подзапросы и коррелированные `EXISTS`/`IN`/`ANY`/`ALL` в `SELECT`, `WHERE`, `ORDER BY` и `HAVING` у каждого SQL-провайдера на любой глубине вложенности (см. [Подзапросы](../guide/07-subqueries.md));
- `CASE WHEN` / тернарный оператор / `switch`, `COALESCE`, числовой `CAST`;
- строковые, математические и date/time скалярные функции и `LIKE`;
- кросс-провайдерные скалярные строковые/числовые функции ([`SqlFunctions.Sql`](xref:NextORM.Core.SqlFunctions.Sql) `left`/`right`/`lpad`/`rpad`/`repeat`/`reverse`/`space`/`concat_ws`/`translate`/`ascii`/`@char`) с описанными выше гейтами по имени;
- арифметика дат (`date_add`/`end_of_month`/`date_diff`/`date_from_parts` и `DateTime.Add*`) в PostgreSQL, SQL Server, ClickHouse, MySQL/MariaDB и SQLite, а также `date_trunc` в PostgreSQL/SQL Server/ClickHouse и `string_agg` в PostgreSQL/SQL Server/ClickHouse/MySQL/MariaDB/SQLite;
- серверная трансляция `DateTimeOffset` — `.Now`/`.UtcNow`, семь частей даты и семь членов `Add*` у каждого SQL-провайдера (клиентские часы/локальная зона никогда не используются; offset сохраняет только SQL Server) (см. [Дата и время](../scalar-functions/03-date-and-time.md#datetimeoffset));
- битовые (`bit_and`/`bit_or`/`bit_xor`), статистические (`corr`/`covar_*`) и `argMin`/`argMax` агрегаты в ClickHouse;
- бинарные столбцы — свойство или проекция `byte[]` отображается на `bytea` (PostgreSQL), `varbinary`/`image` (SQL Server) или `blob` (SQLite);
- потоковое чтение LOB в PostgreSQL, SQL Server и SQLite — одна колонка `byte[]`/`string` читается как `Stream`/`TextReader` с `CommandBehavior.SequentialAccess` и памятью O(буфера), без материализации всего значения (в SQLite источник запроса должен раскрывать `rowid`), а PostgreSQL, SQL Server и SQLite дополнительно отдают многоколоночный результат как принадлежащий вызывающему `DbDataReader` через `ToDataReader`/`ToDataReaderAsync` (в SQLite этот reader буферизованный и без локатора, поэтому LOB-колонка читается целиком, а не чанками);
- 64-битные беззнаковые целые — свойство или проекция `ulong`/`ulong?` материализуется через аксессор построителя строк `DbDataReader.GetFieldValue<ulong>` у провайдеров с нативным беззнаковым типом (ClickHouse `UInt64`, MySQL/MariaDB `BIGINT UNSIGNED`), без SQL-приведения; в PostgreSQL, SQL Server и SQLite беззнакового целого нет, и этот диапазон выражается только `numeric`/`decimal`;
- `IN` по списку/массиву, логические `!` и унарные операторы;
- `SELECT DISTINCT`, `INTERSECT`/`EXCEPT`, CTE (включая рекурсивные), оконные функции и `GROUP BY ROLLUP`/`CUBE`/`GROUPING SETS` (`CUBE`/`GROUPING SETS` нет в MySQL/MariaDB);
- модифицирующие CTE (`WITH n AS (INSERT|UPDATE|DELETE ... RETURNING ...)`, однотабличные и join/multi-table) на PostgreSQL, читаются типизированно через [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1) (см. [модифицирующий CTE](../guide/17-insert-statement.md#модифицирующий-cte-postgresql));
- `OUTPUT ... INTO <target>` на SQL Server — `Returning(...).OutputInto(target)` записывает изменённые строки в существующую таблицу, `Returning(...).OutputIntoThenOutput(target)` записывает их и возвращает клиенту (см. [гайд по вставке](../guide/17-insert-statement.md#запись-изменённых-строк-в-таблицу-output-into));
- key-upsert `Returning()` — PostgreSQL/SQLite добавляют `RETURNING` к `ON CONFLICT ... DO UPDATE`, SQL Server рендерит `MERGE ... OUTPUT`; MySQL/MariaDB отклоняют его с `NotSupportedException` (см. [upsert](../guide/21-merge-statement.md#возврат-слитых-строк));
- пользовательские скалярные функции (`[SqlFunction]`) и табличные функции (`[SqlTableFunction]`);
- серверные/кластерные табличные функции ClickHouse `url`/`s3`/`file`/`remote`/`remoteSecure`/`cluster`/`clusterAllReplicas`, предобъявленные на `SqlFunctions.ClickHouse.*` с generic-интерфейсом строки `TRow`, объявляемым вызывающим (гейт — [`SupportsTableFunction`](xref:NextORM.Core.ISqlDialect.SupportsTableFunction(System.String)); см. [Табличные функции](../guide/13-table-valued-functions.md#встроенные-табличные-функции));
- предикаты полнотекстового поиска (`SqlFunctions.Sql.contains`/`freetext`) в SQL Server, PostgreSQL и MySQL/MariaDB, полнотекстовое ранжирование (SQL Server `containstable`/`freetexttable` с `KEY`/`RANK`, PostgreSQL `ts_rank`/`ts_rank_cd`), текстовые JSON-функции (`json_value`/`json_query`/`json_modify`/`isjson`) в SQL Server и MySQL/MariaDB и табличные функции SQL Server `openjson`/`string_split` (а также пользовательские обёртки `[SqlTableFunction]`, включая MySQL `JSON_TABLE` через `CallClause`); кросс-провайдерные предикаты `contains`/`freetext` по-прежнему не поддерживаются на SQLite (он бросает), зато доступна его собственная поверхность запросов FTS3/FTS4/FTS5 (`Match`, FTS5 `FTS5bm25`/`Highlight`/`Snippet`/`Rank`, помощники FTS3/4 и табличный источник `FROM` `MatchTable` FTS5), а также специфичный для SQLite command builder обслуживания FTS5 (`CreateSqliteFts5CommandBuilder`: `AutoMerge`/`CrisisMerge`/`Merge`/`Optimize`/`Rebuild`/`IntegrityCheck` с sync/async терминалами);
- хинты уровня инструкции в SQL Server (`OPTION (...)`), PostgreSQL и MySQL/MariaDB (`/*+ ... */`), табличные хинты в SQL Server (`Hint(...)`, `WithTableHint(...)`, пер-join `JoinOptions.WithJoinTableHint(...)`), хинты join/подзапроса/области видимости (`JoinOptions.WithJoinHint`, `FromOptions.WithSubQueryHint`, `WithTablesInScopeHint`), JSON-вывод (`ForJson(...)` → `FOR JSON PATH`/`AUTO`) и XML-вывод (`ForXml(...)` → `FOR XML`);
- методы типа XML в SQL Server (`xml_value`/`xml_query`/`xml_exist` → `xml.value('xpath', 'type')`/`xml.query('xpath')`/`xml.exist('xpath')`, а также rowset `.nodes` через `xml_nodes` как источник `CrossApply`/`OuterApply`);
- raw SQL для запроса целиком ([`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)) / [`PrepareFromSql`](xref:NextORM.Core.EntityExtensions.PrepareFromSql``1(NextORM.Core.EntityBuilder{``0},System.String))) и как композируемый источник `FROM` ([`FromSql`](xref:NextORM.Core.DataContextExtensions.FromSql(NextORM.Core.IDataContext,System.String,System.Object)), рендерится как производная таблица), а также пути переиспользования неявного кэша планов / [`Prepare`](xref:NextORM.Core.EntityBuilderExtensions.Prepare``1(NextORM.Core.EntityBuilder{``0},System.Boolean,System.Threading.CancellationToken));
- выполнение сырых команд в контексте (`ExecuteRaw`/`ExecuteRawAsync`, а также хранимые процедуры через `ExecuteProcedure`/`ExecuteProcedureAsync`, возвращающие освобождаемый `ProcedureResult`) с именованными параметрами/`DbType`/`Size`, последовательными наборами результатов и выходными параметрами/возвращаемым значением (см. [Сырой SQL](../guide/14-raw-sql.md#выполнение-сырых-команд-executeraw));
- переопределение источника на запрос (`WithTableName`/`WithSchema`/`WithDatabase`/`WithServer`/`WithTableExpression`) у всех SQL-провайдеров, входит в ключ кэша планов (см. [Переопределение источника для запроса](../guide/01-query-sources.md#переопределение-источника-для-запроса)).
