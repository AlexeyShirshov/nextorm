# Ограничения и возможности вне области охвата

> nextorm — построитель запросов с небольшой явной поверхностью DML: он генерирует инструкции `SELECT` (и параметризованные `INSERT ... VALUES`, `INSERT ... SELECT`, key upsert, `MERGE`, `DELETE` и `UPDATE`) и материализует их результаты, и намеренно оставляет отслеживание изменений и `SaveChanges` вызывающей стороне.

**Предварительные требования:** [Provider overview](../providers/overview.md) · [API reference](api-reference.md)

## Обзор

На этой странице перечислены возможности, которые **не** являются частью nextorm, с однострочной причиной для каждой.

## Ограничения

| Блок, где есть ограничения | Обоснование |
|---|---|
| **DML — остаточные ограничения** | **`INSERT ... VALUES`, `INSERT ... SELECT` и key upsert реализованы** ([`CreateInsertBuilder`](../guide/15-insert-statement.md); возврат строк через `RETURNING`/`OUTPUT` на PostgreSQL, SQLite и SQL Server, строки батча неупорядочены; серверный источник поднимает свои CTE перед `INSERT` и отклоняет рантайм-плейсхолдеры `SqlFunctions.Parameter`). PostgreSQL также поддерживает **модифицирующие CTE** (`With(имя, insert)`/`With(имя, update)`/`With(имя, delete)` для однотабличных и join/multi-table тел `INSERT`/`UPDATE`/`DELETE`, каждое требует проекцию `RETURNING` → [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1), [модифицирующий CTE](../guide/15-insert-statement.md#модифицирующий-cte-postgresql)). **Upsert** ([`CreateMergeBuilder`](xref:NextORM.Core.DataContextExtensions.CreateMergeBuilder``1(NextORM.Core.IDataContext,System.Action{NextORM.Core.EntityMetadataBuilder{``0}})) → [`MergeBuilder<T>`](xref:NextORM.Core.MergeBuilder`1), [upsert](../guide/19-merge-statement.md#upsert-key-merge)) рендерит родную форму провайдера — `INSERT ... ON CONFLICT ... DO UPDATE` (PostgreSQL, SQLite), `INSERT ... ON DUPLICATE KEY UPDATE` (MySQL, MariaDB) или `MERGE ... USING (VALUES ...)` (SQL Server); ClickHouse их отклоняет. При активном глобальном фильтре запросов полный `MERGE` (SQL Server, PostgreSQL 15+) изолирует цель в предикате `ON`, поэтому скрытая строка никогда не сопоставляется, не обновляется и не удаляется, а key upsert `ON CONFLICT` / `ON DUPLICATE KEY` **отказывает** с `NotSupportedException` (fail closed; `IgnoreFilters()` их восстанавливает). Ключ источника, совпавший со скрытой строкой цели, всё равно вскрывает нативную ошибку нарушения уникальности провайдера из insert-ветки — по любому задетому уникальному индексу, а не только по ключу совпадения (оракул существования; составной ключ, включающий столбец фильтра, смягчает только первичный/ключ совпадения), тогда как merge только с update- или delete-веткой — молчаливый no-op — а pre-check значений источника остаётся отдельным чтением с окном TOCTOU (`QueryFilterValidator`), проверяющим значения источника, а не строки цели (см. [Изоляция цели записи](../advanced/query-filters.md#изоляция-цели-записи)). **`DELETE`** ([`CreateDeleteBuilder`](../guide/16-delete-statement.md) → [`DeleteBuilder<T>`](xref:NextORM.Core.DeleteBuilder`1), `Delete<T>(entity)`, [удаление](../guide/16-delete-statement.md)) рендерит параметризованный `DELETE FROM <table> [WHERE ...]` — по предикату, по объявленному ключу сущности или всю таблицу с явным `All()`; `Returning()` возвращает удалённые строки на PostgreSQL/SQLite (`RETURNING`) и SQL Server (`OUTPUT`), `CreateTruncateBuilder<T>()` рендерит `TRUNCATE TABLE`, ClickHouse удаляет через `ALTER TABLE ... DELETE ... SETTINGS mutations_sync = 1`. Multi-table `DELETE` по INNER-соединению ([`From<T>().Join(...).Delete()`](../guide/16-delete-statement.md#удаление-по-соединению)) поддерживается на PostgreSQL, SQL Server, MySQL и MariaDB и отклоняется SQLite и ClickHouse. **`UPDATE`** ([`CreateUpdateBuilder`](../guide/17-update-statement.md) → [`UpdateBuilder<T>`](xref:NextORM.Core.UpdateBuilder`1), `Update<T>(entity)`) рендерит параметризованный `UPDATE <table> SET ... [WHERE ...]` на PostgreSQL, SQL Server, SQLite, MySQL и MariaDB; ClickHouse обновляет через `ALTER TABLE ... UPDATE ... SETTINGS mutations_sync = 1` (синхронно, но число затронутых строк не возвращает); `Returning()` возвращает обновлённые строки на PostgreSQL/SQLite (`RETURNING`) и SQL Server (`OUTPUT`), а в MariaDB — только при явно настроенной версии сервера 13.0+. Multi-table `UPDATE` по INNER-соединению ([`From<T>().Join(...).CreateUpdateJoinBuilder()`](../guide/17-update-statement.md#обновление-из-join)) поддерживается на PostgreSQL/SQLite (`FROM`), SQL Server и MySQL/MariaDB и отклоняется ClickHouse. Полный `MERGE` с ветками `WHEN MATCHED`/`WHEN NOT MATCHED`/`WHEN NOT MATCHED BY SOURCE` и `MERGE ... RETURNING`/`OUTPUT` доступны на SQL Server и PostgreSQL 15+ и отклоняются остальными провайдерами. Отслеживания изменений и `SaveChanges` нет: запись — это явные команды. Запрос можно материализовать в постоянную таблицу через `CREATE TABLE ... AS SELECT` ([`ToTempTable`/`ToTable`](../guide/18-create-table-as.md)) на PostgreSQL, SQLite, MySQL, MariaDB, SQL Server и ClickHouse: SQL Server рендерит `SELECT ... INTO` (таблица уровня сессии — `ToTable("#name")`), ClickHouse — `CREATE TABLE ... ENGINE = MergeTree ... AS SELECT`. Временная форма `ToTempTable` доступна только на PostgreSQL, SQLite, MySQL и MariaDB: в SQL Server нет `CREATE TEMPORARY TABLE ... AS SELECT` (используйте `#name`), а ClickHouse не допускает временный `AS SELECT`. Утверждение с побочным эффектом и последующее чтение можно отправить одним батчем через общий `BatchBuilder` (материализации `CreateTempTable`/`CreateTable` и DML-шаги `Insert`/`Update`/`Delete`/`Truncate` перед одним читающим запросом), одним round trip на одной сессии, на PostgreSQL, SQL Server, MySQL, MariaDB и SQLite; ClickHouse отклоняет батч с `NotSupportedException`, а DML-шаг не может запрашивать возврат строк (`Returning()` даёт другой тип билдера). SQL Server отправляет батч одной `;`-склеенной командой, а не `SqlBatch`, который выполняет каждую команду в своей области видимости, поэтому `#temp` остаётся видимой между утверждениями. Выполнение батча не проходит через интерцепторы запросов: их события несут `DbCommand`, тогда как команда `DbBatch` — это `DbBatchCommand`. |
| **Синтаксис, зависящий от версии сервера** | Две возможности зависят от версии сервера и гейтятся **явно настроенной версией** — nextorm никогда не опрашивает живой сервер. Агрегатный `FILTER (WHERE ...)` в PostgreSQL требует 9.4+; диалект, привязанный к более старой версии, отклоняет его через `NotSupportedException`, а незаданная версия предполагает 9.4+ и включает его. `UPDATE ... RETURNING` в MariaDB включается только при явной 13.0+ ([`SupportsUpdateReturning`](xref:NextORM.Core.ISqlDialect.SupportsUpdateReturning)); незаданная или более старая версия отклоняет его через `NotSupportedException`, а `RETURNING` у insert/delete и `ANY_VALUE` (13.2) не меняются. PostgreSQL накладывает одну неизменяемую версию сервера на **конкретный тип контекста** на всё время жизни процесса, потому что `FILTER` влияет на кэшируемый SQL `SELECT`; другая версия для того же конкретного типа бросает `InvalidOperationException`, поэтому процессу, которому нужно несколько версий PostgreSQL, следует объявить отдельный подкласс контекста на каждую. MariaDB **не накладывает такой защиты**: на одном типе контекста допустимы разные версии, так как её гейтируемая операция (`UPDATE ... RETURNING`) — мутация, чей SQL не кладётся в кэш планов. См. [провайдер PostgreSQL](../providers/postgres.md#версия-сервера) и [провайдер MariaDB](../providers/mariadb.md#версия-сервера). |
| **`Prepare()` / кэш планов для DML** | Каждая мутация рендерит и выполняет одну команду за вызов — билдеры мутаций намеренно не готовятся и не кладутся в кэш планов. Оптимизация в nextorm нацелена только на read-only запросы (явный `Prepare`, неявный кэш планов, бенчмарки). |
| **Bulk-copy флаги вне SQL Server** | `BulkInsertOptions.CheckConstraints`/`TableLock`/`KeepNulls`/`FireTriggers` отображаются в `SqlBulkCopyOptions` на нативном пути `SqlBulkCopy` в SQL Server. Путь `COPY` в PostgreSQL и портируемый `INSERT ... VALUES` (MySQL/MariaDB/SQLite/ClickHouse, а также SQL Server, когда `Returning*` или `KeepIdentity` переключают запись на портируемый путь) отклоняют запрошенный флаг через `NotSupportedException`, а не игнорируют его. ClickHouse `MaxDegreeOfParallelism`/`WithoutSession` не выставляются: `ClickHouseBulkCopy` в `ClickHouse.Driver` 1.4.0 устарел, а не-устаревший `ClickHouseClient.InsertBinaryAsync` требует собственного клиента; сессия — настройка строки подключения (`UseSession`), а не пер-записная опция. `UseInternalTransaction` намеренно не выставляется (nextorm не открывает неявную транзакцию). См. [Массовая вставка](../guide/20-bulk-insert.md#опции-bulk-copy-в-sql-server). |
| **Неявные навигационные запросы / соединения из навигационных свойств** | Связь объявляется явно через `HasMany`/`HasOne` или [`RelationshipAttribute`](xref:NextORM.Core.RelationshipAttribute), а [`JoinInto`](xref:NextORM.Core.EntityBuilder`1) загружает дочернюю коллекцию или ссылку за один денормализованный round trip — one-to-many, one-to-one и, через явный junction (`HasManyThrough`/`JoinOptions.ManyToMany`), many-to-many; по умолчанию LEFT, есть перегрузка INNER и fallback с явными ключами (см. [Связи](relationships.md)). **Неявные навигационные запросы поддерживаются для объявленных связей**: ссылочная навигация используется как скалярная цепочка или проверка присутствия, а коллекционная предоставляет ровно четыре прямых терминала (`Any`/`Count`/`LongCount`/свойство `Count`), разворачиваемых на сервере в коррелированный подзапрос или `LEFT JOIN`; коллекционную навигацию можно адаптировать через `AsEntityBuilder<T>` (см. [Неявные навигационные запросы](../guide/29-implicit-navigation.md)). Конвенция по внешним ключам и неявный вывод соединений по-прежнему отсутствуют; LINQ-композиция после адаптера, проекция самого ссылочного адаптера и перегрузки с предикатом падают закрыто. Многошаговая проверка присутствия (`a.Parent.Parent == null`) и ссылочный адаптер (`Any`/`Count`/`LongCount` ≡ `nav != null`) поддержаны на всех SQL-провайдерах; коллекция, достигнутая через ссылку, поддержана на всех SQL-провайдерах, кроме ClickHouse, который не умеет коррелировать подзапрос по присоединённому источнику и отклоняет форму через `NotSupportedException`; `Count`/свойство `Count` — проверяемый `int` (64-битный счёт сужается только при материализации и бросает `OverflowException` вне диапазона), тогда как `LongCount` — 64-битный сквозным. Гейт ClickHouse reference→collection — **принятое ограничение провайдера** (не дефект), а навигация по temp-table/TVP-источнику **отложена**: читающий источник ленивой временной таблицы — нетипизированный `TableAlias` без навигационной поверхности, поэтому член навигации по нему прочитать нельзя (триггер — источник навигации, скомбинированный с temp-table/TVP-путём); навигация, объявленная до границы временной таблицы, по-прежнему разворачивается в материализующий `CREATE TEMPORARY TABLE ... AS SELECT`. `JoinInto` отклоняет с `NotSupportedException` составной ключ связи или junction, связь many-to-many под `AsSingleQuery`, необъявленную связь (кроме перегрузки с явными ключами), производный (`As`) или соединённый источник проекции, вид соединения, отличный от `Inner`/`Left`, несовпадающие типы явных ключей и более семи дочерних коллекций; смешивание `JoinInto` с любым другим соединением на одном билдере отклоняется (объявляйте `JoinInto` только на простом источнике сущности), а ClickHouse-опция `j => j.WithStrictness(Any)` на `JoinInto` усекает загруженную коллекцию до одного ребёнка, тогда как остальные модификаторы (`All`, `Asof`, `Global`) проходят без изменений; метаданные связи «падают закрыто» при неотображённом внешнем ключе, principal-типе без ключа или несовпадении типов FK/principal-ключа. Явные соединения остаются общей поверхностью: [`Join`](xref:NextORM.Core.EntityBuilder`1.Join``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`LeftJoin`](xref:NextORM.Core.EntityBuilder`1.LeftJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`RightJoin`](xref:NextORM.Core.EntityBuilder`1.RightJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`FullJoin`](xref:NextORM.Core.EntityBuilder`1.FullJoin``1(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``0,System.Boolean}},System.Action{NextORM.Core.JoinOptions}))/[`CrossJoin`](xref:NextORM.Core.EntityBuilder`1.CrossJoin``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) (см. [Соединения](../guide/02-joins.md)). **Дедупликация требует отображённого ключа**: дедупликация родителей и идентичность ребёнка возвращаются к ссылочной идентичности, когда у соответствующей стороны не объявлен ключ, а на SQL-провайдере каждая строка — новый экземпляр, поэтому повторы/декартовы строки сохраняются — задайте родителю и ребёнку отображённый ключ (`[Key]`/`Key()`/соглашение `Id`) или используйте перегрузку с явными ключами и ключевым ребёнком. `IRelationshipMetadata.Inverse` разрешается лениво при **первом чтении** и кэшируется, поэтому регистрируйте обе стороны до его чтения. |
| **Выбор соединённой сущности целиком** | После соединения накопленная проекция позиционна (`Item1`..`Item8`, по одному элементу на источник в порядке соединений), и выбирать можно только её колонки (`Select(p => p.Item1.Id)`); член проекции, являющийся сущностью целиком (`Select(p => p.Item1)`), колонкой не является и отклоняется. Придайте сторонам осмысленные имена, спроецировав в именованный тип (`Select(p => new { Order = p.Item1.Id, Customer = p.Item2.RequiredString })`); см. [Соединения](../guide/02-joins.md#адресация-проекции). |
| **Коррелированный источник `APPLY` / `LATERAL`** | [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) принимают лямбду, получающую строку левой стороны, поэтому применяемый источник может ссылаться на внешнюю строку у провайдера с lateral-источником (SQL Server `CROSS/OUTER APPLY`, PostgreSQL/MySQL/MariaDB `... LATERAL`). Диалекты без lateral-источника (SQLite, ClickHouse) отклоняют `APPLY`. Лямбда корреляции не может ссылаться на проекцию соединения — применяйте её к источнику из одной сущности. |
| **[`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}})) / [`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) на SQL-провайдерах** | [`SelectMany`](xref:NextORM.Core.EntityBuilder`1.SelectMany``1(System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0}}}))/[`GroupJoin`](xref:NextORM.Core.EntityBuilder`1.GroupJoin``3(NextORM.Core.EntityBuilder{``0},System.Linq.Expressions.Expression{System.Func{`0,``1}},System.Linq.Expressions.Expression{System.Func{``0,``1}},System.Linq.Expressions.Expression{System.Func{`0,System.Collections.Generic.IEnumerable{``0},``2}})) бросают `NotSupportedException`; явная поверхность соединений [`CrossApply`](xref:NextORM.Core.EntityBuilder`1.CrossApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions}))/[`OuterApply`](xref:NextORM.Core.EntityBuilder`1.OuterApply``1(NextORM.Core.EntityBuilder{``0},System.Action{NextORM.Core.JoinOptions})) покрывает коррелированный эквивалент (см. [Соединения](../guide/02-joins.md)). |
| **Коррелированный скаляр: терминалы `First`/`Single` и их `*OrDefault`-формы** | При nullable-проекции отсутствие строки даёт `null`, при non-nullable value-проекции терминалы `FirstOrDefault`/`SingleOrDefault` дают `default` (например `0`). `First`/`Single` на non-nullable value-проекции бросают исключение, если строки нет. `Single`/`SingleOrDefault` при более чем одной строке бросают у всех провайдеров, чьи скалярные подзапросы проверяют кардинальность (PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse); SQLite её не проверяет, поэтому там числовой `Single`/`SingleOrDefault` при более чем одной строке поднимает ошибку БД через рендер-гард `case when count(*) > 1 then <числовое переполнение> else value end`, а нечисловая проекция отклоняется с `NotSupportedException`. |
| **Блокирующие табличные хинты вне SQL Server** | Блокирующие табличные хинты (`WithTableHint("nolock")` → `WITH (NOLOCK)`) поддерживаются только в SQL Server, для таблицы запроса в `FROM` и, через пер-join опцию `JoinOptions.WithJoinTableHint`, переданную соединению; нативные index-хинты MySQL/MariaDB (`USE`/`FORCE`/`IGNORE INDEX`), SQLite (`INDEXED BY`/`NOT INDEXED`) и SQL Server (`WITH (INDEX(...))`) — отдельная поверхность ([`WithIndex`](../guide/13-query-hints.md#index-хинты), [`ISqlDialect.IndexHints`](xref:NextORM.Core.ISqlDialect.IndexHints)). Хинты уровня инструкции подключены в SQL Server (`OPTION (...)`), PostgreSQL и MySQL/MariaDB (`/*+ ... */`); SQLite и ClickHouse отклоняют `Hint(...)` через `NotSupportedException`. Хинты join (`JoinOptions.WithJoinHint`), подзапроса (`FromOptions.WithSubQueryHint`) и области видимости (`WithTablesInScopeHint`) следуют тем же гейтам: SQL Server рендерит join-хинт внутри `JOIN`, а хинт области — как `WITH (...)` на каждой таблице (хинт подзапроса он отклоняет, так как T-SQL не может добавить подсказку к подзапросу), PostgreSQL/MySQL/MariaDB сворачивают их во встроенный `/*+ ... */`, а SQLite/ClickHouse их отклоняют (см. [Хинты запросов](../guide/13-query-hints.md)). |
| **ВЕРХНИЙ регистр SQL-ключевых слов — конструкторы row/tuple остаются каноничными для провайдера** | `DataContextBuilder.UseKeywordCase(KeywordCase.Upper)`, `EntityBuilder<TEntity>.WithKeywordCase(...)` и `QueryCommand<T>.WithKeywordCase(...)` поднимают регистр ключевых слов, которые эмитит ядро сборки инструкции (`select`, `from`, `where`, `join`, `group by`, `order by`, `with`, `insert`, `values`, ...), трансляторы выражений (`and`/`or`/`not`, `case`/`when`/`then`/`else`/`end`, `cast(... as ...)`, `is [not] null`, `like`, `in`, `exists`, `over` и оконные фреймы), общие диалектные клозы (алиасы `as`, пагинация `limit`/`offset`/`fetch`/`top`, `with [recursive]`, ключевые слова join, table/index-хинты) и **все диалектные клозы**: `for json`/`for xml`, модификаторы группировки (`rollup`/`cube`/`grouping sets`/`with totals`), `for system_time ...`, `apply`, `settings`, `final`, `sample`, DML `returning`/`output`, query-hint `option (...)`/`option (maxrecursion ...)` и capability-клозы (`for update`/`for share`, `tablesample ... repeatable`, `limit by`, `array join`, `distinct on`, `pivot`/`unpivot`). Конструкторы row/tuple `ROW(...)` (PostgreSQL) и `tuple(...)` (ClickHouse) трактуются как функциональные конструкторы и сохраняют каноничное написание провайдера в обоих режимах (согласовано с политикой имён функций). Идентификаторы, строковые литералы, имена функций, имена типов и raw SQL не меняются никогда, а `KeywordCase.Lower` (по умолчанию) побайтово совпадает с прежним выводом. |
| **Поэлементный доступ к серверному массиву/JSON (`x[i]`)** | Поддерживается только захваченная (замкнутая) коллекция, индексируемая внутри запроса ([lookup по захваченной коллекции](../guide/01-filtering-where.md#lookup-по-захваченной-коллекции-dictcolumn)): ключ-константа сворачивается в параметр, ключ-колонка даёт переносимый `CASE`. Поэлементный доступ к серверной array/JSON-колонке или к array-returning выражению (`groupArray(x)[0]`, `array_agg(x)[1]`, `json['k']`) не имеет переносимой SQL-формы и бросает `NotSupportedException` (кастомный индексер — тоже) вместо привязки всей коллекции. | **`untuple` (ClickHouse)** | `untuple(tuple)` не отображается: он разворачивает кортеж в несколько колонок результата, и у такого выражения нет единой скалярной CLR-формы в проекции. | **Поверхность row-значений (кортежей): остаточные ограничения** | Конструкторы row (`System.Tuple.Create(a, b)` / `new Tuple<T1, T2>(a, b)`) поддержаны как **прямые операнды сравнения** `==`/`!=` в предикатах (`WHERE`/`HAVING`/`JOIN ON`): PostgreSQL рендерит `ROW(a, b)` и `(row).fN`, ClickHouse — `tuple(a, b)`/`tupleElement`, а MySQL/MariaDB/SQLite — плоский ANSI `(a, b)` (например, `(a, b) = (c, d)`), который эти движки принимают как операнд сравнения строк. `.ItemN` inline-конструктора сворачивается в скалярный аргумент везде. В MySQL/MariaDB/SQLite конструктор в `Select`/`ORDER BY`/`GROUP BY` или как аргумент функции, а также любой серверный `.ItemN` бросают `NotSupportedException` при подготовке (с именем провайдера); SQL Server отклоняет конструкторы. Операторы `<`/`>`/`<=`/`>=` и реляционные операнды `ValueTuple` невыразимы в C#/деревьях выражений (языковая граница, а не пробел продукта). Tuple `IN`/`Contains` по **списку значений** плоских `System.Tuple`/`System.ValueTuple` арности 1..7 — **реализован** ([#193](https://github.com/AlexeyShirshov/nextorm/issues/193)) в row-форме провайдера — `ROW(a, b) IN (ROW(...), ...)` в PostgreSQL, `tuple(a, b) IN (tuple(...), ...)` (и `GLOBAL IN` для `global_in`) в ClickHouse, `(a, b) IN ((...), ...)` в MySQL/MariaDB и `(a, b) IN (VALUES (...), ...)` в SQLite, — а SQL Server отклоняет **любую** форму кортежа заранее с `NotSupportedException` (`SQL Server does not support tuple IN/Contains translation.`) — включая null-коллекцию, null-элемент ссылочного кортежа, арность ≥8 и вложенные кортежи, — поэтому ошибка вычисления там всплыть не может; на поддерживающих провайдерах пустой список — `1 = 0`, null-коллекция бросает `ArgumentNullException`, nullable-элемент кортежа (`List<(int, int)?>`) бросает `NotSupportedException`, строки с null-компонентами совпадают через явные гардированные ветви, а арность ≥8/`Rest`/вложенные кортежи бросают `NotSupportedException`. Tuple-типизированный `QueryCommand` (подзапрос) в правой части и `Rest`/вложенные кортежи отложены (пока не поддерживаются, обещания будущего milestone нет). Материализация «сырого» `ROW(...)`/row-значения обратно в `System.Tuple<...>` — **реализована в PostgreSQL** ([#194](https://github.com/AlexeyShirshov/nextorm/issues/194)): одна колонка `ROW(...)` (арность 1..7) материализуется в соответствующий `System.Tuple<...>` по обычной строке подключения, а зарегистрированный вызывающим именованный composite — в именованный тип, когда вызывающий предоставляет настроенный `NpgsqlDataSource` (см. [Сырой SQL](../guide/12-raw-sql.md#сырые-postgresql-строки-и-composite-типы)). `ValueTuple`, арность ≥8, вложенный/пустой `ROW`, несколько или смешанные колонки-записи, незарегистрированный именованный composite и именованный composite, объявленный как `System.Tuple`, остаются под гардом с `NotSupportedException`. См. [Скалярные функции](../scalar-functions/index.md). |

| **Состояние агрегатных функций ClickHouse (`-State`/`-Merge`, `runningAccumulate`)** | `uniqState`/`sumState`/`countState`/… возвращают opaque-значение `AggregateFunction(...)`, которое nextorm не моделирует: `ClickHouse.Driver` 1.4.0 бросает `AggregateFunctionException` из `FrameworkType`/`Read`/`Write`, поэтому такую колонку нельзя материализовать в CLR-значение или передать как него (сообщение драйвера указывает на парный `-Merge`). | **Форматирование строк и коллация за пределами документированного подмножества** | `string.Format`/интерполяция/`value.ToString(format)` транслируют только culture-invariant подмножество: числа `N`/`F`/`D`/`X` (зависит от провайдера) и токены даты `yyyy yy MM dd HH mm ss` с разделителями `- / . : T` и пробелом. | **Регулярные выражения** | `Regex.IsMatch`/`Regex.Replace` с константным шаблоном транслируются на PostgreSQL, MySQL/MariaDB, ClickHouse, SQLite и SQL Server 2025+ ([`SupportsRegex`](xref:NextORM.Core.ISqlDialect.SupportsRegex)); в SQL Server совпадение рендерится как `REGEXP_LIKE`, которому нужен уровень совместимости БД 170, а `REGEXP_REPLACE` доступна на любом уровне — в SQL Server 2022 и раньше функций `REGEXP_*` нет. | **Несколько result-set'ов из батча: нетерпеливо и последовательно** | **Поддерживается** на провайдерах с `SupportsBatch` (PostgreSQL, SQL Server, MySQL, MariaDB, SQLite): `AddQuery<TResult>` добавляет сколько угодно результат-несущих запросов, а `Execute()`/`ExecuteAsync()` выполняют батч один раз и возвращают `BatchResult` — результат напрямую перечисляем: `foreach`/`await foreach` даёт по одному курсору `ResultSet` на набор, каждый раскрывает `Index`/`FieldCount`/`ColumnNames` и читает собственный набор через `Read<T>()`/`ReadAsync<T>()` с типом на набор, что и позволяет читать наборы с разными типами элементов; позиционный путь `Read<TResult>()` остаётся для последовательности одного `T`, каждый набор читается один раз и с проверкой типа, а два режима обхода нельзя смешивать (см. [Выполнение утверждений одним батчем](../guide/23-sql-batch.md#несколько-наборов-результатов)). ClickHouse отклоняет батчи. Сырые команды покрыты отдельно: `ProcedureResult` следует той же модели курсоров поверх своего живого reader'а — перечисляйте его (`foreach`/`await foreach`) или вызывайте `Read<T>()` по одному набору на вызов, по порядку (см. [Оптимистичная конкурентность и отслеживание изменений](../guide/24-optimistic-concurrency.md). В ClickHouse транзакций нет, он их отклоняет. |
| **Интеграция с EF Core: мост `SaveChanges` и маппинг на контекст** | Пакет [`nextorm.entityframeworkcore`](integration-efcore.md) выполняет чтения и запись nextorm поверх соединения существующего EF Core `DbContext` и его текущей транзакции и отображает сущности из EF `IModel`; чтения и запись nextorm, выполненные там, участвуют в этой общей транзакции (проверено на PostgreSQL, SQL Server и MySQL), но синхронизации отслеживания изменений и моста `SaveChanges` нет: DML nextorm идёт в обход трекера изменений EF, поэтому записанные им строки трекеру неизвестны. Маппинг регистрируется в процесс-глобальном кэше метаданных nextorm с ключом по `Type`, поэтому **на процесс существует не более одного маппинга на CLR-тип** — два `DbContext`, отображающие один тип по-разному, не могут обслуживаться одновременно: вторая, отличающаяся регистрация бросает `InvalidOperationException`. Мост `SaveChanges`/отслеживания изменений явно вне области. У нереляционного EF-провайдера `InMemory` нет `DbConnection`, он не поддерживается. Глобальные фильтры запросов, объявленные в EF-модели, **импортируются** в конвейер фильтров nextorm для поддерживаемых реляционных адаптеров; контекст, привязанный к мосту, чьи импортированные метаданные фильтров позже удалены (`DataContextCache.Clear()` или скользящее вытеснение), отказывает безопасно документированным `InvalidOperationException` на следующем запросе или сборке DML вместо выполнения без фильтра, а восстанавливается созданием/пере-привязкой контекста через мост. Срез «ClickHouse без EF-адаптера» и сертификация общего соединения специально для MariaDB остаются открытыми единицами `1.0.9-b`. См. [Интеграция с EF Core](integration-efcore.md) и [Мост фильтров запросов EF Core](ef-core-query-filters.md). |
| **Таймаут команды в ClickHouse** | `UseCommandTimeout`/`WithCommandTimeout` задают ADO.NET `DbCommand.CommandTimeout` у каждого SQL-провайдера, но `ClickHouse.Driver` 1.4.0 не отображает его на HTTP-запрос — вместо этого запрос ограничивает `Timeout` соединения (по умолчанию две минуты), поэтому там значение не действует. Переопределение на запрос применяется к читающим запросам; команды DML и батчи используют значение контекста по умолчанию. |
| **PostgreSQL `oid` и другие системные типы на базе `uint` через параметр `uint`** | Npgsql отображает `oid` и другие системные типы на базе `uint` (например `cid`) на CLR `uint`, поэтому чтение в свойство `uint` работает, но nextorm связывает параметр `uint` как `xid`, а у `oid = xid` нет оператора (SQLSTATE 42883) — поэтому сравнение или запись такой цели через параметр `uint` падает. Сравнивайте через приведение к `bigint` (`Where(e => (long)e.Oid == (long)value)`) или выполняйте сырой SQL с параметром `bigint` и явным приведением `::oid`. См. [провайдер PostgreSQL](../guide/provider-specific/postgresql.md). |
| **Интерцепторы за пределами жизненного цикла команды/соединения** | Поставленный интерфейс — [`IQueryInterceptor`](xref:NextORM.Core.IQueryInterceptor) и [`IConnectionInterceptor`](xref:NextORM.Core.IConnectionInterceptor) (см. [Интерцепторы](../infrastructure/03-interceptors.md)). Exception-интерцептора нет — транслируйте исключение провайдера через `try`/`catch` вокруг вызова терминала. Интерцептор не должен менять `CommandText` (команда принадлежит кэшированному плану). Глобальные фильтры запросов — отдельный слой. |
| **Динамические колонки — сторона записи** | **Сторона чтения** реализована: свойство с сеттером, допускающее присваивание из `Dictionary<string, object?>`, помеченное [`DynamicColumnsAttribute`](xref:NextORM.Core.DynamicColumnsAttribute) (или флюентно `EntityPropertyBuilder<T>.DynamicColumnsStore`), получает не сопоставленные колонки строки, когда сущность запрашивается целиком, — инструкция рендерит `select <mapped>, *` (``select t1.<mapped>, `t1`.*`` в MySQL/MariaDB, чей диалект алиасит `*` через `RequiresQualifiedSelectStar`), и хранилище материализуется из набора результатов у каждого SQL-провайдера (см. [Динамические колонки](../guide/27-dynamic-columns.md)). **Сторона записи реализована для `INSERT`, `UPDATE` и `MERGE`**: ключи словаря-хранилища рендерятся физическими колонками, а их значения — связанными параметрами. Ключи сортируются порядково (ordinal), поэтому порядок колонок детерминирован; каждый динамический ключ квотируется квотированием диалекта, даже когда глобальная опция квотирования идентификаторов (`UseQuotedIdentifiers`) выключена, а соглашение об именовании пропускается (ключ используется как имя физической колонки); пустой ключ или ключ с символом NUL отклоняется. Присутствующий ключ со значением `null` пишет SQL `NULL`, а отсутствующий ключ опускается — в `INSERT` применяется значение по умолчанию колонки, в `UPDATE`/`MERGE` колонка остаётся неизменной (очистить колонку, опустив её ключ, нельзя); многострочный `INSERT` требует одинакового набора ключей во всех строках, а в `MERGE` динамические колонки идут в source/`INSERT`/`SET` и никогда в `ON`. Значения связываются из рантайм-CLR-значения без пер-ключевого `IPropertyValueConverter`/JSON (pass-through), что зеркалит материализацию стороны чтения. **Оставшиеся ограничения:** нет пер-ключевых конвертеров и JSON-колонок; nextorm не отслеживает изменения; колонку нельзя очистить опусканием ключа; нет allow-list ключей (ключи вместо этого квотируются и валидируются). Сторона чтения по-прежнему ограничена одним физическим источником (запрос с соединениями отклоняет хранилище с `NotSupportedException`) и сущностью, запрашиваемой целиком (явная проекция хранилище не собирает). На SQL-чтении хранилище создаётся, даже если изначально оно `null`; на записи `null`-хранилище или хранилище без ключей не даёт динамических колонок. Сущность с хранилищем должна быть ссылочного типа: сущность value-типа (`struct`), объявляющая хранилище, отклоняется с `InvalidOperationException` при построении метаданных, а не упаковывается молча (boxing) — используйте ссылочный тип. |
| **Динамические колонки — конструктор без параметров** | Сущность, объявляющая хранилище динамических колонок, должна быть ссылочного типа и иметь публичный конструктор без параметров. Хранилище материализуется через member-init (каждая сопоставленная колонка привязывается по имени, а хранилище получает поля `*`), поэтому обычная стратегия самого длинного конструктора к ней не применяется; сущность с хранилищем без публичного конструктора без параметров отклоняется при подготовке с `QueryPreparationException`. То же хранилище читает и сторона записи. |
| **Конвертеры значений в `TimeSpan` в табличных параметрах на провайдерах без нативного типа длительности** | В общем шве записи конвертер владеет провайдерным представлением (сконвертированный `TimeSpan` связывается как есть), но у табличного параметра нет нативного связывания длительности в SQL Server, SQLite и ClickHouse. Поэтому столбец отображаемой сущности, конвертер которого нацелен на `TimeSpan`, отклоняется через `NotSupportedException` при построении столбцов параметра, до потребления строк; связывайте сконвертированное значение как его целочисленное хранение. PostgreSQL (`interval`) и MySQL/MariaDB (`TIME`) сохраняют сконвертированный `TimeSpan`. |
| **Потоковое чтение LOB (`ToStream`/`ToTextReader`) вне PostgreSQL, SQL Server, SQLite ** | Терминалы стриминга возвращают `Stream`/`TextReader`, владеющий `DbDataReader` и per-call `DbCommand` до освобождения; в этом выпуске они реализованы для PostgreSQL, SQL Server и SQLite. В SQLite источник запроса должен раскрывать `rowid` (обычная rowid-таблица): таблица `view` или `WITHOUT ROWID` падает fail-closed с сырым `Microsoft.Data.Sqlite.SqliteException: no such column: rowid`, без буферизованного фолбэка. Локатор можно добавить только к одноисточниковой проекции, поэтому соединения/несколько источников, `DISTINCT`/`DISTINCT ON`, `UNION`, `GROUP BY` и агрегаты не поддерживаются (могут падать с ошибкой драйвера), а для одноколоночной проекции переопределение сырым `WithSql` отклоняется с `NotSupportedException` (rowid-локатор нельзя безопасно добавить), тогда как сырая проекция из двух и более колонок отклоняется обычным `InvalidOperationException`. MySQL/MariaDB и ClickHouse отклоняют терминал через `NotSupportedException`; буферизованная проекция `byte[]`/`string` остаётся доступной у каждого провайдера. Многоколоночный терминал `ToDataReader`/`ToDataReaderAsync` доступен на PostgreSQL, SQL Server и SQLite: PostgreSQL/SQL Server отдают sequential-access reader, а SQLite возвращает буферизованный reader без локатора (без `rowid`, `FieldCount` равен проекции, LOB-колонка читается целиком, а не чанками), поэтому ограничение rowid-таблицы выше относится только к скалярным потоковым терминалам. MySQL/MariaDB и ClickHouse не имеют поддержки sequential access и отклоняют его. См. [Потоковое чтение больших объектов](../guide/26-large-objects.md). |
| **Экспорт CSV (`WriteCsv`/`WriteCsvAsync`) поверх неподдерживаемых проекций** | Терминалы CSV отдают результат `Select` в предоставленный вызывающим `Stream` на каждом SQL-провайдере (PostgreSQL, SQL Server, SQLite, MySQL, MariaDB, ClickHouse); поток назначения никогда не закрывается. Терминал CSV читает каждую поддерживаемую колонку без боксинга, включая числовые колонки SQL Server: после открытия reader'а он определяет фактический storage-тип колонки через hook `MapTypedColumnExpression` у провайдера, читает её storage-типизированным getter'ом и конвертирует типизированным `Convert.To<T>`, никогда через `GetValue`/`Convert.ChangeType(object)` (с [#168](https://github.com/AlexeyShirshov/nextorm/issues/168) та же storage-типизированная диспетчеризация — `MapColumnExpression`, разрешающий тип поля reader'а в рантайме, — лежит и в основе общего пути буферизованной материализации, поэтому обычный `ToList` тоже больше не боксит числовые значения SQL Server). Колонка проекции, у которой нет единой скалярной CSV-формы либо чей storage-тип неизвестен и не поддаётся конвертации, — вложенная сущность или коллекция, массив, отличный от `byte[]`, кортеж, словарь, произвольный объект или колонка, отображённая через объектный конвертер либо фолбэк на `GetValue`, — отклоняется до записи заголовка (и любой строки данных). `null`/`DBNull` пишется как настроенный `NullMarker` (по умолчанию `\N`), а пустая строка — как пустое поле, поэтому их можно различить, а остальной диалект (UTF-8 без BOM, экранирование по RFC 4180, CRLF, invariant-культура, форматы `O`/`D`) фиксирован. Защита от инъекции формул в табличные процессоры (CWE-1236) опциональна: `ExcelMode = true` добавляет префикс `'` полю, начинающемуся с `=`, `+`, `-` или `@`, после любого `ValueTransform` и до экранирования по RFC 4180, поэтому вызывающему, экспортирующему недоверенные данные, следует её включить (по умолчанию выключена). Колонка `byte[]` читается как поле целиком (типизированный `GetFieldValue<byte[]>`) и кодируется в Base64 для строки, поэтому память ограничена наибольшим полем/строкой, а не фиксированным буфером; chunked LOB streaming — будущий срез (триггер: спрос на экспорт крупных бинарных колонок). Запрос, читающий ленивую временную таблицу, созданную через `AsTempTable`, — не одна инструкция (нужен батч `DROP` + `CREATE TEMPORARY TABLE ... AS SELECT` + чтение на одной сессии), поэтому терминал отклоняет его с `NotSupportedException` до записи заголовка (и любой строки данных), не выполняя батч и без буферизованного фолбэка. См. [Потоковое сохранение данных](../guide/28-streaming-data.md#csv). |

## Известные крайние случаи

- **Столкновение одноимённых захваченных переменных.** Захваченная переменная, читаемая глобальным фильтром запросов, и другая захваченная переменная, читаемая пользовательским `On(...)`, с одинаковым именем CLR дают одно и то же имя параметра, поэтому плейсхолдеры сталкиваются; переименуйте одну из переменных.
- **Привязка фильтров к сырому источнику — best-effort и непроверяемая.** `FromSql`/`From(string)` применяют глобальный фильтр только после того, как [`BindEntity<TEntity>`](xref:NextORM.Core.EntityBuilderExtensions.BindEntity``1(NextORM.Core.EntityBuilder{NextORM.Core.TableAlias},System.Collections.Generic.IReadOnlyCollection{System.String})) объявит тип сущности и выходные столбцы; фильтр с отсутствующими обязательными столбцами пропускается с предупреждением `RawSourceFilterSkipped` на категории `NextORM.QueryFilters` (причина `MissingColumns`, физические имена mapped-столбцов), а не бросает исключение, тогда как при пустом объявленном списке столбцов фильтр с доказанной пустой зависимостью всё же применяется, а фильтр, зависящий от столбца, или неопределённый фильтр пропускается с причиной `UndeterminedColumns`. Список столбцов — это слово вызывающего: nextorm не разбирает сырой SQL и не проверяет его по схеме, поэтому объявленный столбец, который фрагмент на самом деле не возвращает, принимается и может заставить фильтр сработать против неверной формы. Привязка не является гарантией безопасности; провайдер без поддержки сырых источников отклоняет источник. См. [Фильтры на привязанных сырых источниках](query-filters.md#фильтры-на-привязанных-сырых-источниках).

## Не ограничения

Следующее полностью реализовано и проверено; оно появляется в столбце *готово* анализа пробелов,
а не в списке выше:

- соединения любого типа (`INNER`, `LEFT`, `RIGHT`, `FULL`, `CROSS`, а также `CROSS APPLY`/`OUTER APPLY` и lateral-эквивалент там, где поддерживается; нет `FULL JOIN` в MySQL/MariaDB) и арности 2–8, включая производный запрос с любой стороны (первичный источник `FROM` или присоединяемая таблица);
- коррелированные скалярные подзапросы и коррелированные `EXISTS`/`IN`/`ANY`/`ALL` в `SELECT`, `WHERE`, `ORDER BY` и `HAVING` у каждого SQL-провайдера на любой глубине вложенности (см. [Подзапросы](../guide/05-subqueries.md));
- `CASE WHEN` / тернарный оператор / `switch`, `COALESCE`, числовой `CAST`;
- строковые, математические и date/time скалярные функции и `LIKE`;
- кросс-провайдерные скалярные строковые/числовые функции ([`SqlFunctions.Sql`](xref:NextORM.Core.SqlFunctions.Sql) `left`/`right`/`lpad`/`rpad`/`repeat`/`reverse`/`space`/`concat_ws`/`translate`/`ascii`/`@char`) с описанными выше гейтами по имени;
- арифметика дат (`date_add`/`end_of_month`/`date_diff`/`date_from_parts` и `DateTime.Add*`) в PostgreSQL, SQL Server, ClickHouse, MySQL/MariaDB и SQLite, а также `date_trunc` в PostgreSQL/SQL Server/ClickHouse и `string_agg` в PostgreSQL/SQL Server/ClickHouse/MySQL/MariaDB/SQLite;
- битовые (`bit_and`/`bit_or`/`bit_xor`), статистические (`corr`/`covar_*`) и `argMin`/`argMax` агрегаты в ClickHouse;
- бинарные столбцы — свойство или проекция `byte[]` отображается на `bytea` (PostgreSQL), `varbinary`/`image` (SQL Server) или `blob` (SQLite);
- потоковое чтение LOB в PostgreSQL, SQL Server и SQLite — одна колонка `byte[]`/`string` читается как `Stream`/`TextReader` с `CommandBehavior.SequentialAccess` и памятью O(буфера), без материализации всего значения (в SQLite источник запроса должен раскрывать `rowid`), а PostgreSQL, SQL Server и SQLite дополнительно отдают многоколоночный результат как принадлежащий вызывающему `DbDataReader` через `ToDataReader`/`ToDataReaderAsync` (в SQLite этот reader буферизованный и без локатора, поэтому LOB-колонка читается целиком, а не чанками);
- 64-битные беззнаковые целые — свойство или проекция `ulong`/`ulong?` материализуется через аксессор построителя строк `DbDataReader.GetFieldValue<ulong>` у провайдеров с нативным беззнаковым типом (ClickHouse `UInt64`, MySQL/MariaDB `BIGINT UNSIGNED`), без SQL-приведения; в PostgreSQL, SQL Server и SQLite беззнакового целого нет, и этот диапазон выражается только `numeric`/`decimal`;
- `IN` по списку/массиву, логические `!` и унарные операторы;
- `SELECT DISTINCT`, `INTERSECT`/`EXCEPT`, CTE (включая рекурсивные), оконные функции и `GROUP BY ROLLUP`/`CUBE`/`GROUPING SETS` (`CUBE`/`GROUPING SETS` нет в MySQL/MariaDB);
- модифицирующие CTE (`WITH n AS (INSERT|UPDATE|DELETE ... RETURNING ...)`, однотабличные и join/multi-table) на PostgreSQL, читаются типизированно через [`MutationCteQuery<T>`](xref:NextORM.Core.MutationCteQuery`1) (см. [модифицирующий CTE](../guide/15-insert-statement.md#модифицирующий-cte-postgresql));
- `OUTPUT ... INTO <target>` на SQL Server — `Returning(...).OutputInto(target)` записывает изменённые строки в существующую таблицу, `Returning(...).OutputIntoThenOutput(target)` записывает их и возвращает клиенту (см. [гайд по вставке](../guide/15-insert-statement.md#запись-изменённых-строк-в-таблицу-output-into));
- key-upsert `Returning()` — PostgreSQL/SQLite добавляют `RETURNING` к `ON CONFLICT ... DO UPDATE`, SQL Server рендерит `MERGE ... OUTPUT`; MySQL/MariaDB отклоняют его с `NotSupportedException` (см. [upsert](../guide/19-merge-statement.md#возврат-слитых-строк));
- пользовательские скалярные функции (`[SqlFunction]`) и табличные функции (`[SqlTableFunction]`);
- серверные/кластерные табличные функции ClickHouse `url`/`s3`/`file`/`remote`/`remoteSecure`/`cluster`/`clusterAllReplicas`, предобъявленные на `SqlFunctions.ClickHouse.*` с generic-интерфейсом строки `TRow`, объявляемым вызывающим (гейт — [`SupportsTableFunction`](xref:NextORM.Core.ISqlDialect.SupportsTableFunction(System.String)); см. [Табличные функции](../guide/11-table-valued-functions.md#встроенные-табличные-функции));
- предикаты полнотекстового поиска (`SqlFunctions.Sql.contains`/`freetext`) в SQL Server, PostgreSQL и MySQL/MariaDB, полнотекстовое ранжирование (SQL Server `containstable`/`freetexttable` с `KEY`/`RANK`, PostgreSQL `ts_rank`/`ts_rank_cd`), текстовые JSON-функции (`json_value`/`json_query`/`json_modify`/`isjson`) в SQL Server и MySQL/MariaDB и табличные функции SQL Server `openjson`/`string_split` (а также пользовательские обёртки `[SqlTableFunction]`, включая MySQL `JSON_TABLE` через `CallClause`); кросс-провайдерные предикаты `contains`/`freetext` по-прежнему не поддерживаются на SQLite (он бросает), зато доступна его собственная поверхность запросов FTS3/FTS4/FTS5 (`Match`, FTS5 `FTS5bm25`/`Highlight`/`Snippet`/`Rank`, помощники FTS3/4 и табличный источник `FROM` `MatchTable` FTS5);
- хинты уровня инструкции в SQL Server (`OPTION (...)`), PostgreSQL и MySQL/MariaDB (`/*+ ... */`), табличные хинты в SQL Server (`Hint(...)`, `WithTableHint(...)`, пер-join `JoinOptions.WithJoinTableHint(...)`), хинты join/подзапроса/области видимости (`JoinOptions.WithJoinHint`, `FromOptions.WithSubQueryHint`, `WithTablesInScopeHint`), JSON-вывод (`ForJson(...)` → `FOR JSON PATH`/`AUTO`) и XML-вывод (`ForXml(...)` → `FOR XML`);
- методы типа XML в SQL Server (`xml_value`/`xml_query`/`xml_exist` → `xml.value('xpath', 'type')`/`xml.query('xpath')`/`xml.exist('xpath')`, а также rowset `.nodes` через `xml_nodes` как источник `CrossApply`/`OuterApply`);
- raw SQL для запроса целиком ([`WithSql`](xref:NextORM.Core.EntityExtensions.WithSql``1(NextORM.Core.EntityBuilder{``0},System.String)) / [`PrepareFromSql`](xref:NextORM.Core.EntityExtensions.PrepareFromSql``1(NextORM.Core.EntityBuilder{``0},System.String))) и как композируемый источник `FROM` ([`FromSql`](xref:NextORM.Core.DataContextExtensions.FromSql(NextORM.Core.IDataContext,System.String,System.Object)), рендерится как производная таблица), а также пути переиспользования неявного кэша планов / [`Prepare`](xref:NextORM.Core.EntityBuilderExtensions.Prepare``1(NextORM.Core.EntityBuilder{``0},System.Boolean,System.Threading.CancellationToken));
- выполнение сырых команд в контексте (`ExecuteRaw`/`ExecuteRawAsync`, а также хранимые процедуры через `ExecuteProcedure`/`ExecuteProcedureAsync`, возвращающие освобождаемый `ProcedureResult`) с именованными параметрами/`DbType`/`Size`, последовательными наборами результатов и выходными параметрами/возвращаемым значением (см. [Сырой SQL](../guide/12-raw-sql.md#выполнение-сырых-команд-executeraw));
- переопределение источника на запрос (`WithTableName`/`WithSchema`/`WithDatabase`/`WithServer`/`WithTableExpression`) у всех SQL-провайдеров, входит в ключ кэша планов (см. [Переопределение источника для запроса](../querying/02-query-sources.md#переопределение-источника-для-запроса)).
