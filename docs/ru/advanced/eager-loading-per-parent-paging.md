# Постраничная выборка на родителя при жадной загрузке (`LoadWith`)

> `LoadWith` может применить собственные `Limit`/`Offset`/`Page` дочернего запроса **независимо к каждому родителю**. Сначала выполняются фильтрация и сортировка детей, поэтому страница, которую получает родитель, — это срез `фильтр → порядок → Skip → Take` по его собственным детям; дочерний запрос с глобальным лимитом никогда не «съедает» строки последующих родителей. Корневой пейджинг остаётся независимым, а родитель без подходящих детей сохраняется с пустой коллекцией. В основе — секционированный `row_number()`-источник, батчируемый так же, как обычная жадная загрузка, и поддерживаемый в обоих режимах: `EagerLoadMode.SplitQuery` и `EagerLoadMode.SingleQuery`.

**Предварительные требования:** [Жадная загрузка дочерних коллекций (`LoadWith`)](eager-loading.md) · [Соединения](../guide/02-joins.md) · [Связи и однозапросная загрузка (`JoinInto`)](relationships.md)

## Обзор

Обычная `LoadWith` загружает **все** подходящие дочерние строки для каждого родителя, а порядок навигации оставляет дочернему запросу. Когда дочерний запрос несёт собственный пейджинг (`Take`/`Skip`, доступный как `Limit`/`Offset`/`Page`), nextorm трактует этот пейджинг как **на родителя**, а не как один глобальный лимит на весь дочерний результат:

```csharp
var parents = ctx.From<Order>()
    .LoadWith(o => o.Items,
        c => c.From<OrderItem>().OrderBy(i => i.CreatedAt).Offset(1).Limit(2), // 2-й и 3-й элемент каждого заказа
        o => o.Id, i => i.OrderId)
    .OrderBy(o => o.Id)
    .ToList();
```

Каждый заказ получает собственный срез: `Offset`/`Limit` разрешаются по детям именно этого заказа, а не по конкатенации всех детей. Поэтому можно безопасно пейджить дочерний запрос, у которого много родителей; ни один ребёнок более позднего родителя не вытесняется строками первого.

Это отличается от применения `Skip`/`Take` **после** материализации: страница вычисляется базой данных внутри секции каждого родителя и применяется до того, как дети присоединены.

## Порядок вычисления для каждого родителя

Для каждого родителя эффективный конвейер таков:

1. **Фильтрация** — собственный `Where` дочернего запроса (и его эффективная область query-фильтров) отбирает детей-кандидатов.
2. **Сортировка** — эффективный `OrderBy` дочернего запроса упорядочивает кандидатов каждого родителя. Направление и поведение null-сортировки провайдера сохраняются, несколько ключей применяются по порядку.
3. **Skip** — нормализованный `Offset`/`Skip` отбрасывает столько ведущих кандидатов.
4. **Take** — нормализованный `Limit`/`Take` оставляет столько из оставшихся кандидатов.

Нормализация пейджинга следует существующему контракту [`Paging`](../guide/04-sorting-and-paging.md), а не второй реализации: `Take(0)` означает «без лимита» и **не** включает пейджинг, поэтому родитель сохраняет всех детей; `Skip` за конец списка детей родителя и родитель без подходящих детей дают пустую коллекцию. Настоящей странице нужен дочерний `OrderBy` (см. ниже). Границы защищены от переполнения так же, как в обычном пейджинге.

## Корневой пейджинг остаётся независимым

Пейджинг родителей и пейджинг детей — разные границы разных источников. `.Offset(...)`/`.Limit(...)` на внешнем билдере по-прежнему выбирают строки родителей; дочерняя страница разрешается для каждого родителя после этого и никогда не меняет набор родителей:

```csharp
var parents = ctx.From<Order>()
    .LoadWith(o => o.Items, c => c.From<OrderItem>().OrderBy(i => i.CreatedAt).Limit(2), o => o.Id, i => i.OrderId)
    .OrderBy(o => o.Id)
    .Offset(10)   // корень: родители 11..20
    .Limit(10)
    .ToList();    // каждый выбранный родитель всё равно получает свои 2 детей
```

## Родители без детей сохраняются

Родитель, у которого все дети отфильтрованы, отброшены `Skip` или у которого детей нет вовсе, всё равно возвращается — с **пустой** коллекцией. Фильтр ранга живёт внутри дочернего источника, а не как предикат, который мог бы убрать бездетных родителей из внешнего результата. В режиме `SingleQuery` это следует из `LEFT JOIN`; в режиме `SplitQuery` родительский statement не меняется, а сшиватель оставляет несопоставленных родителей пустыми.

## Оба режима жадной загрузки

Постраничная выборка на родителя доступна в обеих стратегиях; режим по-прежнему выбирает только способ доставки строк.

### Split-query (по умолчанию)

Родительский statement не меняется. Один батчированный дочерний statement на чанк не более чем из 1000 различных родительских ключей несёт **секционированный ранжирующий** производный источник, а граница страницы фильтрует каждую секцию:

```sql
-- родительский statement (не меняется дочерней страницей)
select id, name from "order" as 't1' order by t1.id

-- один батчированный дочерний statement на чанк ключей (представительная форма)
select t1.id, t1.order_id, t1.created_at
from (
    select *, row_number() over (partition by order_id order by created_at) as __nextorm_rn
    from order_item
) as t1
where t1.order_id in (@k0, @k1, @k2)
  and t1.__nextorm_rn > 1 and t1.__nextorm_rn <= 3
```

Ключ секции — полный ключ связи с родителем, а сортировка окна — эффективная сортировка дочернего запроса. Составные ключи связи с родителем (`ValueTuple` из компонентов ключа) поддерживаются на этом split-пути в SQLite, PostgreSQL, MySQL, MariaDB и ClickHouse; SQL Server отвергает составную форму до выполнения (см. ниже). Колонка ранга внутренняя: она используется только для фильтрации производного источника и никогда не попадает во внешнюю проекцию или материализованную сущность. Батчирование не меняется — два round trip при не более чем 1000 родителях, без N+1.

### Single-query (`EagerLoadMode.SingleQuery`)

Ранжированный дочерний источник встраивается в единственную денормализованную команду вместо отдельного statement, поэтому постраничная выборка на родителя остаётся **одним** round trip:

```sql
-- представительная форма: ранжированный ребёнок — производный источник, присоединяемый к каждому родителю
select t1.id, t1.name, t3.id, t3.order_id, t3.created_at
from "order" as t1
left join (
    select *, row_number() over (partition by order_id order by created_at) as __nextorm_rn
    from order_item
) as t3 on t1.id = t3.order_id and t3.__nextorm_rn > 1 and t3.__nextorm_rn <= 3
order by t1.id, t3.created_at
```

Поскольку ранжированный ребёнок — **вложенный** производный источник, его `ORDER BY` уровня statement не выдаётся внутри производной таблицы (некоторые провайдеры отвергают там `ORDER BY`); сортировка, сопоставляющая детей с родителями, переносится во внешнюю команду. Колонка ранга, как и в split-режиме, убирается из проекции.

## Поддерживаемые и неподдерживаемые формы дочернего запроса

Ранжированный дочерний источник поддерживает:

- предикат `Where` дочернего запроса, применяемый **до** ранжирования;
- `OrderBy` дочернего запроса (один или несколько ключей, по возрастанию/убыванию), сопровождающий пейджинг;
- `Limit`/`Offset`/`Page` (только skip, только take, skip+take), включая skip за конец; `Take(0)` — «без лимита» и не включает пейджинг, то есть это обычная непейджированная загрузка;
- те же формы ключа связи с родителем и проекции, что поддерживает обычная `LoadWith`.

Отвергается **до генерации любого SQL**:

- **голый `OrderBy`** дочернего запроса в режиме `SingleQuery`, не сопровождаемый пейджингом, — денормализованное соединение по-прежнему не может выразить только выходную сортировку детей (в split-режиме этого ограничения нет);
- формы дочернего запроса, которые ранжированный источник не может свернуть, — `Distinct`, `GroupBy`, `Having` и прочие агрегатные/групповые/множественные формы — отвергаются в **обоих режимах** (split и single-query), поскольку ранжирующее понижение рендерит только собственные `Where` и `OrderBy` ребёнка;
- постраничная выборка на родителя вместе с `WITH TIES` (`WithTies()`): ранжированный источник сохраняет фиксированное число строк на секцию и не может выразить семантику «связанные с последней строкой», поэтому комбинация отвергается до любого SQL (`NotSupportedException`);
- пейджированный ребёнок **без `OrderBy`** в любом режиме — странице на родителя нужна сортировка окна, а `row_number()` без `ORDER BY` недопустим в таких провайдерах, как SQL Server;
- `EagerLoadMode.Correlated`, который остаётся зарезервированным и отвергается в этом релизе;
- постраничная выборка на родителя через **`JoinInto`**, сохраняющий собственный fail-closed guard;
- постраничная выборка на родителя в провайдере **in-memory**, у которого нет SQL-окна, — пейджированный дочерний запрос жадно отвергается с `NotSupportedException` (непейджированная жадная загрузка там не меняется);
- составные ключи связи с родителем (`ValueTuple`) на пути **single-query** и в **SQL Server** (оба пути) — существующие guard'ы tuple-`IN` и равенства ключей отвергают их до выполнения любого SQL, тогда как split-путь поддерживает их в SQLite, PostgreSQL, MySQL, MariaDB и ClickHouse; скалярные (одноколоночные) ключи связи не затронуты.

Отвергается это на **любом** терминале: во время подготовки, до выполнения родительского statement и до вставки записи в план. Реляционного клиентского fallback нет — страница никогда не перевыражается как глобальный `LIMIT` на детей.

## Связи порядка и страницы без сортировки

Ранжирование даёт каждому родителю детерминированную последовательность только для **полного** порядка. Когда сортировка детей имеет связи, точный состав страницы не обещается: гарантируется лишь совпадение по количеству и принадлежности. Чтобы страница на родителя была детерминированной, сортируйте по уникальному ключу. Пейджированный ребёнок без `ORDER BY` вовсе отвергается до выполнения: у окна не было бы допустимого порядка (см. выше).

## Замечания по провайдерам

| Провайдер | Постраничная выборка на родителя |
|---|---|
| SQLite | да — оконные функции и производный источник |
| PostgreSQL | да — оконные функции и производный источник |
| SQL Server | да — фильтр ранга применяется внутри производного источника; вложенный источник не несёт `ORDER BY` уровня statement |
| MySQL / MariaDB | да, если сервер поддерживает оконные функции (см. prerequisite по серверу ниже) |
| ClickHouse | да, если сервер поддерживает оконные функции и производные источники |
| In-memory | отвергается fail-closed (`NotSupportedException`) — нет SQL-окна; реляционный клиентский пейджинг не подставляется |
| `JoinInto` | отвергается fail-closed — per-parent top-N относится к возможностям `LoadWith` |

Поддержка оконных функций — это **prerequisite совместимости сервера**, а не автоматически согласуемая возможность: nextorm выдаёт секционированное `row_number()`-понижение против того провайдера, который вы настроили, и вы нацеливаетесь на движок с поддержкой оконных функций и производного источника. Для этого переписывания никакая возможность `ISqlDialect` не согласуется и минимальная версия автоматически не определяется. Провайдер in-memory отвергается fail-closed, поскольку у него нет SQL-окна; реляционного клиентского fallback нет.
