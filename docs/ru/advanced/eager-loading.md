# Жадная загрузка дочерних коллекций (`LoadWith`)

> `LoadWith` заполняет коллекцию на стороне родителя одним дополнительным дочерним запросом на чанк ключей — два round trip при не более чем 1000 родителях, без N+1 — и сшивает дочерние записи с уже материализованными родителями в памяти. По умолчанию используется split; вызовите `AsSingleQuery()`, чтобы получить родителей и все объявленные коллекции одним денормализованным round trip.

**Предварительные требования:** [Быстрый старт](../getting-started/02-quickstart.md) · [Соединения](../guide/02-joins.md) · [Подзапросы](../guide/05-subqueries.md)

## Обзор

В nextorm связи не выводятся из соглашений, поэтому граф не загружается по конвенции маппера. `LoadWith` объявляет один уровень жадной загрузки явно: член коллекции на стороне родителя, фабрику дочернего запроса и два селектора ключей, которые сопоставляют дочерние записи родителям, — и не использует метаданные связей. Связь живёт в запросе, а не в метаданных сущности; однозапросную альтернативу на объявленных метаданных см. в [`JoinInto`](relationships.md).

Это аналог linq2db `LoadWith` и EF Core `Include`, ограниченный первым уровнем (без вложенных загрузок). По умолчанию используется split-query; опциональный режим single-query (`AsSingleQuery`) выполняет один денормализованный round trip.

## Сигнатура

```csharp
public EntityBuilder<TEntity> LoadWith<TChild, TKey>(
    Expression<Func<TEntity, ICollection<TChild>>> collection,
    Func<IDataContext, EntityBuilder<TChild>> childQuery,
    Expression<Func<TEntity, TKey>> parentKey,
    Expression<Func<TChild, TKey>> childKey)
    where TKey : notnull;
```

- `collection` — член [`ICollection<TChild>`](xref:System.Collections.Generic.ICollection`1) на стороне родителя, который нужно заполнить.
- `childQuery` — строит дочерний запрос из контекста данных, которому принадлежит родительский запрос.
- `parentKey` / `childKey` — селекторы, по которым определяется, какие дочерние записи принадлежат какому родителю.
- `TKey` должен быть не-nullable типом (`where TKey : notnull`), например `int` или `string`. Значение ключа `null`, встреченное в рантайме, пропускается и никогда не сопоставляется.

`LoadWith` возвращает **копию** билдера с объявлением, поэтому исходный билдер не меняется, а несколько загрузок можно объединять в цепочку:

```csharp
var orders = ctx.From<Order>()
    .Where(o => o.CustomerId == customerId)
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId)
    .OrderBy(o => o.Id)
    .ToList();
```

Как и любой модификатор билдера, `LoadWith` требует, чтобы generic-тип ключа был известен в точке вызова; если селектор допускает неявное преобразование, укажите тип ключа явно или приведите тела обоих селекторов к одному типу.

## Семантика split-query

Объявление **не** входит в родительский SQL. После материализации родительского запроса:

1. Различные непустые родительские ключи собираются **в порядке родителей** и разбиваются на чанки не более чем по **1000** ключей.
2. Один дочерний запрос на чанк выполняет `WHERE childKey IN (<ключи чанка>)` — отдельный statement, без `JOIN` и без запроса на каждого родителя.
3. Дочерние записи группируются по `childKey` и назначаются родителям, чей `parentKey` совпадает.

Поэтому запрос с не более чем 1000 различных родительских ключей выполняет ровно **два round trip**: один родительский statement и один дочерний. Большие наборы ключей добавляют по одному дочернему statement на каждый дополнительный чанк; родительский statement всё равно выполняется один раз. N+1 нет: число дочерних statement'ов зависит от размера набора ключей, а не от числа родителей.

Предикат чанка — обычный список `IN`, поэтому он так же участвует в кэше планов и привязке параметров провайдера, как `Contains` по захваченной коллекции.

При отмене `ToListAsync`/`ToArrayAsync` токен проверяется между чанками ключей и между несколькими объявлениями `LoadWith`, поэтому отменённый вызов прекращает выдавать дальнейшие дочерние statement'ы.

## Режим single-query (`AsSingleQuery`)

По умолчанию `LoadWith` использует split-форму выше — два или более round trip, по одному на чанк ключей. Вызовите `AsSingleQuery()` на билдере, чтобы получить родителей и все объявленные коллекции **одной** денормализованной командой:

```csharp
var orders = ctx.From<Order>()
    .Where(o => o.CustomerId == customerId)
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId)
    .AsSingleQuery()
    .ToList();
```

- **Один round trip, без чанкования ключей.** Источник родителя и каждый объявленный дочерний запрос соединяются одной командой `LEFT JOIN`. Списка `IN` и размера чанка нет, поэтому любое число родителей — включая более 1000 различных ключей — извлекается этой же командой, без молчаливого отката к split.
- **Встраивается только собственный `Where` дочернего запроса.** Дочернее условие, например `c => c.From<OrderItem>().Where(i => i.Active)`, включается в предикат `ON` соединения, поэтому фильтрует дочерние записи, не отбрасывая родителей без детей.
- **Остальные формы дочернего запроса отвергаются.** Одно денормализованное соединение не может применить к каждому родителю модификаторы, дополнительные соединения или clauses уровня таблицы, поэтому дочерний запрос с любым из `OrderBy`, `Limit`/`Offset`/`Page`, `Distinct`, `GroupBy`, `Having`, `DistinctOn`, `LimitBy`, соединением (`Join`/`LeftJoin`/`SemiJoin`/`AntiJoin`/…), `Final`, `PreWhere`, `ArrayJoin`, `TableSample`, `Sample`, `ForSystemTime`, `ForUpdate`/`ForShare`, `Window`, `Settings`, CTE, table/index hint или производным (`As`) источником бросает [`NotSupportedException`](xref:System.NotSupportedException) уже при материализации `AsSingleQuery()`. Split-режим учитывает их все; используйте split (без `AsSingleQuery`), когда дочернему запросу нужна форма сложнее `Where`.
- **Области фильтров родителя и ребёнка объединяются, одинаково в split- и single-query режиме.** Эффективная область ребёнка — это всегда объединение его собственной области `IgnoreFilters` и родительской. `IgnoreFilters()` на родителе отключает и фильтры объявленных детей (область «всё» поглощает собственную область ребёнка), а селективный `IgnoreFilters(...)` родителя доходит и до детей. И наоборот: `IgnoreFilters(...)` внутри дочернего запроса отключает только фильтры этого ребёнка, а родительские продолжают действовать. То же правило действует и при загрузке стандартной split-формой, и при `AsSingleQuery()`.
- **Тип родителя должен объявлять mapped-ключ.** Денормализованные строки дедуплицируются по этому ключу, поэтому родитель без ключа бросает [`NotSupportedException`](xref:System.NotSupportedException) с указанием настроить ключ или использовать split-режим, которому ключ не нужен. Строки с одинаковым mapped-ключом схлопываются в одного родителя; split-режим сохраняет их раздельно.
- **Тип ключа должен поддерживать равенство по значению.** Предикат соединения строится через оператор равенства, поэтому тип ключа без него — например, структура без перегрузки `==` или ссылочный тип, `==` которого выродился бы в сравнение ссылок, — бросает [`NotSupportedException`](xref:System.NotSupportedException). Split-режим сравнивает ключи стандартным компаратором равенства и работает с такими типами.
- **Назначение и порядок не меняются.** Тот же stitching дедуплицирует родителей и заполняет каждую коллекцию, поэтому [правило назначения](#правило-назначения) и [гарантии порядка](#порядок-и-дедупликация) ниже действуют в обоих режимах.
- **Только один обычный источник сущности.** `AsSingleQuery` нельзя комбинировать с другими соединениями на одном билдере; вызов на запросе, уже несущем обычное (не `JoinInto`) соединение, бросает [`NotSupportedException`](xref:System.NotSupportedException).
- **Дальнейшая композиция запрещена.** После `LoadWith`/`AsSingleQuery` нельзя вызывать `Select` или `As` (у команды-проекции нет загрузчика) либо `Join`/`Apply` (присоединённый билдер не несёт ни спецификаций загрузки, ни режима). Каждая такая композиция бросает [`NotSupportedException`](xref:System.NotSupportedException) вместо молчаливого оставления коллекций пустыми; сначала материализуйте результат stitching-терминалом.

Split остаётся режимом по умолчанию: предпочитайте его, когда результат дочернего запроса по чанкам меньше денормализованного произведения соединения, и переключайтесь на `AsSingleQuery`, когда важнее один round trip.

## Только первый уровень

Загружаются только объявленные дочерние записи. Дочерний запрос — это обычный `EntityBuilder<TChild>`; собственного загрузчика он не несёт, а вложенные `LoadWith` не учитываются, поэтому коллекции второго уровня не заполняются. N-level eager loading (второй уровень и глубже) **не поддерживается** ни в split-, ни в single-query режиме; для второго уровня выполните отдельный запрос.

## Правило назначения

Для каждого родителя загрузчик выбирает целевую коллекцию:

| Текущее значение `collection` | Член доступен для записи | Поведение |
|---|---|---|
| не null | любой | очищается и заполняется заново |
| `null` | да | назначается новый список |
| `null` | нет (read-only) | [`NotSupportedException`](xref:System.NotSupportedException) |

Read-only коллекция поддерживается, если она инициализирована пустой коллекцией и никогда не переприсваивается:

```csharp
public sealed class Order
{
    public int Id { get; set; }
    public ICollection<OrderItem> Items { get; } = new List<OrderItem>();
}
```

Read-only член не отображается на колонку БД, поэтому его инициализация не влияет на родительский `SELECT`.

## Порядок и дедупликация

- **Порядок родителей сохраняется.** Дочерние записи назначаются родителям в том порядке, в котором их вернул родительский запрос; загрузчик никогда не переупорядочивает родителей.
- **Порядок дочерних записей следует за дочерним запросом.** Дочерние записи сохраняют порядок дочернего statement'а, поэтому добавьте `OrderBy` в `childQuery`, если порядок важен.
- **Одинаковые родительские ключи делят данные (split).** Два родителя с одинаковым ключом получают коллекции с одними и теми же дочерними записями (у каждого родителя свой экземпляр коллекции). В single-query режиме mapped-ключ родителя служит идентичностью дедупликации, поэтому строки с одинаковым ключом схлопываются в одного родителя — используйте split, когда такие строки должны остаться раздельными.
- **Несовпавшие дочерние записи игнорируются.** Дочерняя запись, чей ключ не совпал ни с одним родителем, не назначается, а родитель, у которого нет дочерних записей, получает пустую коллекцию.
- **Null-ключи никогда не сопоставляются.** Родительский или дочерний ключ, равный `null` в рантайме, пропускается; он никогда не ищется и не ломает группировку.

## Повторные объявления

Член коллекции можно объявить **только один раз** на запрос. Повторный вызов `LoadWith` для того же члена бросает [`InvalidOperationException`](xref:System.InvalidOperationException): два объявления выполнили бы два дочерних запроса для одной коллекции, и позднее присваивание отбросило бы раннюю загрузку. Объявляйте каждый член не более одного раза и используйте разные члены для загрузки нескольких коллекций:

```csharp
ctx.From<Order>()
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId)
    .LoadWith(o => o.Payments, c => c.From<Payment>(), o => o.Id, p => p.OrderId); // другой член
```

## Граница терминалов

Спецификация загрузки учитывается **только** четырьмя stitching-терминалами:

- [`ToList()`](xref:NextORM.Core.EntityBuilderExtensions.ToList``1(NextORM.Core.EntityBuilder{``0},System.ReadOnlySpan{System.Object})) и [`ToListAsync()`](xref:NextORM.Core.EntityBuilderExtensions.ToListAsync``1(NextORM.Core.EntityBuilder{``0},System.Object[])).
- `ToArray()` и `ToArrayAsync()`.

Они выполняют родительский запрос — плюс split-запросы детей, или одну денормализованную команду с `AsSingleQuery()` — и сшивают материализованные строки в коллекции.

Любой другой терминал вычисляет **только** родительский запрос и не выполняет eager loading; он не выдаёт ни дочерний запрос, ни запрос загрузки, поэтому коллекции сохраняют то значение, с которым сущность была материализована (обычно пустое):

- `ToHashSet` / `ToHashSetAsync` и `ToDictionary` / `ToDictionaryAsync`.
- `First` / `FirstAsync` и `FirstOrDefault` / `FirstOrDefaultAsync`.
- `Single` / `SingleAsync` и `SingleOrDefault` / `SingleOrDefaultAsync`.
- `ToEnumerable` и `ToAsyncEnumerable`.
- `ToCommand` и любой полученный из него `QueryCommand<T>`.

`Any` / `AnyAsync` и `Count` / `CountAsync` — **скалярные** терминалы: они возвращают одно значение и тоже никогда не выполняют eager loading. `ToCommand()` игнорирует спецификацию намеренно — именно поэтому дочерний запрос выполняется без рекурсии в загрузчик родителя. Материализуйте родителей одним из четырёх stitching-терминалов, когда коллекции должны быть заполнены.

## Метаданные связей и `JoinInto`

`LoadWith` не создаёт и не использует метаданные навигаций; связь выражается двумя селекторами ключей в каждом месте вызова. В nextorm также есть модель метаданных для **объявленных** связей (`HasMany`/`HasOne` или [`[Relationship]`](xref:NextORM.Core.RelationshipAttribute)) и однозапросный загрузчик [`JoinInto`](relationships.md), который заполняет одну дочернюю коллекцию одним `LEFT JOIN` (или `INNER JOIN`) и сшивает денормализованные строки обратно с дедуплицированными родителями. Используйте `JoinInto`, когда связь объявлена как метаданные отношений, и `LoadWith`, когда она выражается ad hoc селекторами ключей в месте вызова; `LoadWith` с `AsSingleQuery()` тоже сводится к одному денормализованному запросу, поэтому оба делят одну материализацию single-query, контракт присваивания и гарантии порядка. Связи по-прежнему никогда не выводятся из соглашений или внешних ключей. Граф загружается явно, по одному объявленному уровню на вызов.
