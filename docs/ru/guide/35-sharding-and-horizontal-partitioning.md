# Шардирование и горизонтальное партиционирование

nextorm умеет разносить один тип сущности по нескольким серверам баз данных. В основе три понятия:

- **Шард** — один сервер со своей строкой подключения. Это деталь развёртывания: сегодня их три,
  завтра десять.
- **Бакет** — стабильная единица размещения. Его номер не меняется и не зависит от числа шардов;
  именно он определяет физическое имя таблицы или схемы.
- **Бакет принадлежит шарду** через консистентное хеширование, поэтому сервер можно добавить или
  убрать, не переименовывая ни одной таблицы.

Приложение работает в разрезе бакетов. Идентификаторы шардов нужны только для адресации серверов:
они никогда не попадают в SQL-идентификатор, и результат запроса по шардам не группируется.

Шардирование опирается на
[область сопоставления времени выполнения](33-runtime-mapping-scope.md): бакет передаётся как
`MappingScope`, топология оборачивает провайдер метаданных, а роутер его разрешает. Сам механизм
области не зависит от шардирования и описан на отдельной странице.

## Объявление shard key

Shard key — одно или несколько читаемых свойств экземпляра:

```csharp
[ShardKey(nameof(Tenant))]
public sealed class Order
{
    public int Id { get; set; }
    public string Tenant { get; set; } = "";
    public decimal Total { get; set; }
}
```

Значения ключа хешируются детерминированной некриптографической функцией, поэтому один и тот же
ключ попадает в тот же бакет в любом процессе и после перезапуска. Поддержаны `int`, `long`, `short`,
`byte`, `Guid`, `string`, `bool`, `DateTime`, `DateTimeOffset`, `decimal` и `null`; любой другой тип
приводит к исключению при маршрутизации.

## Настройка топологии

`ShardTopology` хранит число бакетов, режим размещения, кольцо и строку подключения каждого шарда.
Число бакетов задаётся обязательно — значения по умолчанию нет, потому что это свойство данных, а не
библиотеки:

```csharp
var topology = new ShardTopology(bucketCount: 1024);
topology.AddShard("pg-1", "Host=pg-1;Database=app");
topology.AddShard("pg-2", "Host=pg-2;Database=app");

var builder = new DataContextBuilder()
    .UseSharding(topology)
    .UseDataRouting(routing => routing
        // Простейшая топология: одна строка подключения. Она обслуживает только команды,
        // которые не попадают в бакет, — нешардированные сущности, сырой SQL и транзакцию
        // контекста. Это не адрес маршрутизации: она никогда не решает, на каком шарде
        // выполнится шардированная команда.
        .UseDefaultTopology("main", "Host=pg-1;Database=app_master"));

using var context = new PostgresDataContext(builder);
```

Контекст создаётся только из билдера: его собственное соединение берётся у дефолтной топологии, а
передать в конструктор ещё и строку подключения нельзя. `UseSharding` устанавливает `ShardRouter` в
качестве резолвера scope и оборачивает текущий провайдер метаданных в шард-осведомлённый декоратор,
поэтому существующий `IEntityMetadataProvider` продолжает работать. Каждая команда, направленная в
бакет, выполняется на соединении шарда-владельца, которое контекст открывает лениво, по одному на шард,
из топологии; дефолтный хост в этом решении не участвует.

### Размещение бакета

Режим размещения определяет, как номер бакета превращается в физическое имя. Оба режима зависят
только от номера бакета и никогда — от набора шардов.

В `SchemaPerBucket` — режиме по умолчанию — бакет становится схемой, а таблица сохраняет своё
сопоставленное имя:

```text
{placeholder}_{bucket}.{table}
```

`{placeholder}` — схема, в которую сопоставлена сущность, либо литерал `bucket`, если схема не
объявлена; `{table}` — сопоставленное имя таблицы без изменений. В `TableSuffix` суффикс несёт имя
таблицы, а схема не меняется:

| Сущность | Бакет | `SchemaPerBucket` (по умолчанию) | `TableSuffix` |
| --- | --- | --- | --- |
| `Order` — таблица `Orders`, без схемы | 1 | `bucket_1.Orders` | `Orders_1` |
| `Invoice` — схема `sales`, таблица `invoices` | 1 | `sales_1.invoices` | `sales.invoices_1` |
| `Order` | 7 | `bucket_7.Orders` | `Orders_7` |

```csharp
// SchemaPerBucket — по умолчанию; суффиксную таблицу нужно попросить явно.
var byTable = new ShardTopology(bucketCount: 1024, BucketPlacementMode.TableSuffix);
```

Тот же ответ доступен коду, который собирает SQL сам:

```csharp
var placement = context.GetPhysicalTableName<Order>(new MappingScope("1"));
// placement.Schema == "bucket_1", placement.TableName == "Orders"
// placement.QualifiedName == "bucket_1.Orders"
```

### Raw SQL и имя бакета

Для планировщика raw SQL непрозрачен, поэтому сам по себе он не переписывается. Когда имя нужно
самому запросу, привяжите сущность к raw-источнику и используйте один из токенов:

| Токен | Во что раскрывается |
| --- | --- |
| `{table}` | сопоставленное имя таблицы, например `Orders_1` |
| `{schema}` | сопоставленная схема, например `sales_1` или `bucket_1` |
| `{qualified}` | `<schema>.<table>` либо только таблица, если схема не объявлена |

```csharp
var top = context.FromSql("select Id, Tenant, Total from {qualified} where Total > @min", new { min = 100 })
    .BindEntity<Order>(["Id", "Tenant", "Total"])
    .WithShardKey(tenant)                    // или .WithScope(...) для явного бакета
    .Select(order => new { order.Id, order.Total })
    .OrderByDescending(row => row.Total)
    .ToList();
```

Токены раскрываются при построении плана — из метаданных привязанной сущности и области сопоставления
команды, там же, где имя получает обычный источник, — поэтому выполняется SQL с `bucket_7.Orders`
(или `Orders_7`), и запрос идёт на шард этого бакета. Квотирование — по настройке контекста
(`QuoteIdentifiers`). Фрагмент без трёх токенов выводится дословно, а фигурные скобки, не являющиеся
токеном, остаются как есть. `{schema}` для сущности без схемы — ошибка: используйте `{table}` или
`{qualified}`.

`ExecuteRaw`/`ExecuteProcedure` выполняются на собственном соединении контекста и не несут scope,
поэтому не могут адресовать таблицу бакета на его шарде; для этого используйте `FromSql` со scope либо
соберите запрос для контекста, уже направленного на шард.

### Свои функции хеширования

Обе стадии хеширования заменяемы. `ConsistentHashRing` принимает делегаты `BucketHash`
(байты ключа → бакет) и `ShardHash` (бакет + идентификатор шарда → оценка), а `UseSharding` принимает
любую реализацию `IShardTopology`, поэтому собственная топология может отдавать такое кольцо вместо
встроенного:

```csharp
var ring = new ConsistentHashRing(
    shardIds: ["pg-1", "pg-2"],
    bucketCount: 1024,
    bucketHash: (key, count) => MyHash.ToBucket(key, count),
    shardHash: (bucket, shardId) => MyHash.Score(bucket, shardId));

var topology = new MyTopology(ring);   // любая реализация IShardTopology
using var context = new PostgresDataContext(nonRoutedDefaultConnectionString, new DataContextBuilder().UseSharding(topology));
```

Своя функция должна быть детерминированной между процессами и перезапусками: маршрутизация хранится
в данных, поэтому смена функции перемещает строки. Идентификаторы бакета и шарда проверяются;
идентификатор шарда не может быть пустым и никогда не попадает в SQL.

## Маршрутизация одной строки

`INSERT`, `UPDATE` и `DELETE` определяют бакет по экземпляру сущности и выполняются на соединении
шарда-владельца:

```csharp
context.CreateInsertBuilder<Order>()
    .Values(new Order { Id = 1, Tenant = "acme", Total = 10m })
    .Insert();

context.Update(new Order { Id = 1, Tenant = "acme", Total = 12m });
context.Delete(new Order { Id = 1, Tenant = "acme" });
```

Точечное чтение маршрутизируется по равенству shard key в предикате:

```csharp
var orders = context.From<Order>()
    .Where(order => order.Tenant == tenant)
    .Select(order => order.Total)
    .ToList();
```

Также работают явный ключ и явный scope:

```csharp
context.From<Order>().WithShardKey(tenant).ToList();
context.From<Order>().WithScope(new MappingScope("512")).ToList();   // номер бакета строкой
```

Предикат без равенства по shard key **отклоняется до SQL**, а не читает молча таблицу по умолчанию
и не сканирует все шарды. Добавьте равенство, вызовите `WithShardKey(...)` или сделайте fan-out по
бакетам.

## Fan-out по бакетам

`AcrossBuckets()` выполняет запрос по одному разу на бакет и возвращает **по одному вектору
результата на бакет**. Массив индексируется номером бакета — его длина равна заданному числу
бакетов, — а библиотека никогда не объединяет, не переупорядочивает и не агрегирует данные между
бакетами:

```csharp
var totals = context.From<Order>()
    .AcrossBuckets()
    .Where(order => order.Total > 100m)
    .Select(order => order.Total)
    .ToList();

// totals.Length == числу бакетов; totals[b] — строки бакета b
var grandTotal = totals.SelectMany(vector => vector).Sum();   // решение принимает вызывающий код
```

Операторы уровня бакета (`Where`, `OrderBy`, `Distinct`, `Select`) применяются к каждому бакету
независимо: `OrderBy` сортирует каждый вектор, а не даёт глобально упорядоченную
последовательность.

Скалярные терминалы возвращают по одному значению на бакет:

```csharp
int[] counts = context.From<Order>().AcrossBuckets().Count();
bool[] any = context.From<Order>().AcrossBuckets().Any();
Order[] first = context.From<Order>().AcrossBuckets().OrderBy(order => order.Id).First();
```

`AcrossBuckets(...).Buckets` перечисляет бакеты, которые покрывает fan-out. `AsAsyncEnumerable()`
отдаёт результат по одному вектору в порядке бакетов и последовательно, поэтому большой fan-out не
обязан материализовать все бакеты сразу.

## Выполнение и параллелизм

Fan-out группирует бакеты по шарду-владельцу:

- бакеты одного шарда выполняются **последовательно** на единственном соединении этого шарда;
- разные шарды выполняются **параллельно**, с лимитом, который по умолчанию равен числу шардов;
- `AcrossBuckets(parallelism: 1)` делает весь fan-out последовательным; значение ограничивается
  диапазоном `[1, shardCount]`.

```csharp
var vectors = await context.From<Order>()
    .AcrossBuckets(parallelism: 4)
    .Where(order => order.Total > 0m)
    .ToListAsync(cancellationToken);
```

## Кэш, идентичность и ребалансировка

- Планы, метаданные и материализаторы строк ключуются по `(тип сущности, mapping scope)`, поэтому два
  бакета никогда не делят подготовленную команду, префикс параметров или закэшированное имя таблицы.
- Быстрые пути без scope (общая команда `Any`, артефакты скалярных терминалов) для бакетного builder
  не используются: команда со scope готовится и выполняется только для этого бакета.
- Размещение бакета зависит только от его номера. Добавление или удаление сервера никогда не
  переименовывает таблицу или схему — ни передеплой, ни изменение DDL не нужны.
- Используется консистентное (rendezvous) хеширование без виртуальных узлов: новый шард забирает
  только выигранные бакеты (примерно `1/(K+1)`), а удаление шарда возвращает ровно эти бакеты прежним
  владельцам. Со встроенной лавинной оценкой 4096 бакетов распределяются по трём шардам как
  32.25 / 34.30 / 33.45 %.
- Когда бакет меняет владельца, его строки остаются на старом сервере. Их перенос — ответственность
  приложения; библиотека лишь вычисляет кольцо и размещение.

## Шардирование как маршрутизация по данным

Шардирование — одно правило общей модели маршрутизации. `ShardTopology` реализует `IHostTopology` (см.
[«Маршрутизация данных по топологиям»](34-routing-data-to-topologies.md)): роутер шардирования забирает
типы сущностей с объявленным shard key или с областью бакета, а топология превращает бакет в строку
подключения владеющего шарда. Остальной механизм маршрутизации — правило «один запрос — одна
топология», пиннинг хоста и транзакции на маршрутизированном хосте — работает для шардированных
запросов без изменений:

```csharp
// Удержать сессию на одном шарде, например на том, который собираетесь загрузить.
context.PinHost("sharding", "pg-2");
```

Имя топологии, на которое ссылаются правила шардирования, — `"sharding"`.

Батч и ленивая временная таблица — по одной сессии каждый, поэтому маршрутизируются как единое целое:
батч, все шаги которого относятся к одному бакету, выполняется на шарде этого бакета, а чтение
временной таблицы бакета `b` требует задать ту же область и исходному запросу — тогда
`CREATE ... AS SELECT` и чтение делят один шард ([«Один батч — одна топология»](34-routing-data-to-topologies.md)).
Батч, которому нужны два бакета, отклоняется; выполняйте по батчу на бакет.

## Ограничения

- Результат fan-out — векторы по бакетам. Глобальные `ORDER BY`, `LIMIT`/`OFFSET`, `DISTINCT` и
  агрегаты между бакетами не композируются: объединяйте векторы на клиенте.
- Fan-out охватывает несколько соединений, поэтому не покрывается одной транзакцией и команды разных
  бакетов не атомарны друг относительно друга.
- Перенос данных при ребалансировке, распределённые транзакции (2PC) и смена числа шардов онлайн с
  сохранением таблицы бакета на старом сервере — вне области.
- Значение, переданное через `params` и существующее только во время выполнения, не извлекается из
  предиката; захватите его в замыкании, вызовите `WithShardKey(...)` или используйте fan-out.
- Массовая вставка (`BulkInsertBuilder`) в этой версии не учитывает шардирование.
- `ExecuteRaw`/`ExecuteProcedure` выполняются на соединении контекста и не несут область: таблицу
  бакета на его шарде адресуйте через `FromSql` со scope или через контекст, уже направленный на шард.
