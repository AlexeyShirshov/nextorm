# Шардирование и горизонтальное партиционирование

Шардирование позволяет распределить таблицы одного типа сущности по нескольким серверам баз данных.
**Бакет** — логическое место таблицы или схемы; **шард** — физический сервер, где оно хранится. Номер
бакета остаётся неизменным при добавлении и удалении серверов, поэтому имя таблицы или схемы не меняется:

- **Шард** — один сервер со своей строкой подключения. Это деталь развёртывания: сегодня их три,
  завтра десять.
- **Бакет** — стабильная единица размещения. Его номер не меняется и не зависит от числа шардов;
  именно он определяет физическое имя таблицы или схемы.
- **Бакет принадлежит шарду** через консистентное хеширование, поэтому сервер можно добавить или
  убрать, не переименовывая ни одной таблицы.

Приложение адресует данные через бакеты. Идентификаторы шардов нужны только для выбора сервера: они не
попадают в SQL-идентификаторы, и результаты запроса не группируются по шардам.

## Зачем разделять бакеты и шарды

Бакет — это стабильный логический адрес таблицы или схемы; шард — физический сервер, на котором сейчас
хранится этот бакет. Благодаря такому разделению кольцо может назначить тот же бакет другому серверу,
если набор шардов изменится, не меняя имя таблицы или схемы. Библиотека вычисляет бакет и выбирает его
шард, но не переносит строки бакета.

Обязанности приложения и nextorm разделены так:

| Задача | Приложение | nextorm |
|---|---|---|
| Адресовать строку | Объявляет ключ шардирования и передаёт его значение либо передаёт известный вариант бакета. | Вычисляет стабильный бакет по ключу. |
| Создать и разместить данные | Создаёт схему или таблицу для каждого бакета. | Получает физическое имя из номера бакета и сопоставляет бакет с шардом. |
| Перенести бакет на другой шард | Копирует затронутые строки на нового владельца. | Заново вычисляет владельца бакета по кольцу. |

## Последовательность настройки

Настройте шардирование и направляйте запросы по ключу или номеру бакета:

1. Выберите постоянное `bucketCount` и режим размещения бакетов. Число бакетов относится к данным и не
   имеет значения по умолчанию в библиотеке.
2. Объявите ключ шардирования для каждой маршрутизируемой сущности (см. [Объявление shard key](#объявление-shard-key)).
3. Создайте `ShardTopology`, добавьте строки подключения шардов, зарегистрируйте топологию через
    `UseSharding` и настройте топологию по умолчанию для операций без маршрутизации по шардам (см.
   [Настройка топологии](#настройка-топологии)).
4. Для точечных операций используйте равенство по ключу или явный бакет; многострочные записи группируйте
   по бакетам (см. [Маршрутизация одной строки](#маршрутизация-одной-строки) и
   [Работа по бакетам и шардам](#работа-по-бакетам-и-шардам)).
5. Создайте таблицы или схемы бакетов самостоятельно. Если бакет сменит владельца, приложение должно
   перенести его строки: nextorm не выполняет миграцию данных.

Шардирование опирается на
[вариант сопоставления времени выполнения](33-runtime-mapping-variant.md): бакет передаётся как
`MappingVariant`, топология оборачивает провайдер метаданных, а роутер его разрешает. Сам механизм
варианта не зависит от шардирования и описан на отдельной странице.

`IShardTopology : IHostTopology` — шардовая топология не отдельный механизм: она наследует общий контракт
топологии («дай соединение для этой команды») и добавляет к нему кольцо, шарды и режим размещения —
ровно так же, как `RoundRobinTopology` является ещё одной такой топологией. `TryGetHost` получает тот же
`TopologyContext`: бакет приходит в `context.Variant` (туда его положил роутер в роли резолвера
варианта), кольцо превращает его в идентификатор шарда, а идентификатор — в строку подключения.
Закреплённый `context.HostId` перекрывает бакет. Без варианта бакета топология команду не заявляет, и та
остаётся на соединении контекста — тот же `false`, что возвращает любая другая топология.

## Объявление shard key

Shard key — одно или несколько читаемых свойств экземпляра:

```csharp
[ShardKey(nameof(Tenant))]
public sealed class Order
{
    public int Id { get; set; }
    public string Tenant { get; set; } = "";
    public decimal Total { get; set; }
}
```

Значения ключа хешируются детерминированной некриптографической функцией, поэтому один и тот же
ключ попадает в тот же бакет в любом процессе и после перезапуска. Поддержаны `int`, `long`, `short`,
`byte`, `Guid`, `string`, `bool`, `DateTime`, `DateTimeOffset`, `decimal` и `null`; любой другой тип
приводит к исключению при маршрутизации.

## Настройка топологии

`ShardTopology` хранит число бакетов, режим размещения, кольцо и строку подключения каждого шарда.
Число бакетов задаётся обязательно — значения по умолчанию нет, потому что это свойство данных, а не
библиотеки:

```csharp
var topology = new ShardTopology(bucketCount: 1024);
topology.AddShard("pg-1", "Host=pg-1;Database=app");
topology.AddShard("pg-2", "Host=pg-2;Database=app");

var builder = new DataContextBuilder()
    .UseSharding(topology)
    .UseDataRouting(routing => routing
        // Простейшая топология: одна строка подключения. Она обслуживает только команды,
        // которые не попадают в бакет, — нешардированные сущности, сырой SQL и транзакцию
        // контекста. Это не адрес маршрутизации: она никогда не решает, на каком шарде
        // выполнится шардированная команда.
        .UseDefaultTopology("main", "Host=pg-1;Database=app_master"));

using var context = new PostgresDataContext(builder);
```

Контекст создаётся только из билдера: его собственное соединение берётся у дефолтной топологии, а
передать в конструктор ещё и строку подключения нельзя. Каждая команда, направленная в бакет,
выполняется на соединении шарда-владельца, которое контекст открывает лениво, по одному на шард, из
топологии; дефолтный хост в этом решении не участвует.

`UseSharding` не заводит второй механизм — он собирает шардирование из тех же трёх слоёв:

- **вариант**: `ShardRouter` *становится* `IEntityVariantResolver`, а `ShardEntityMetadataProvider`
  оборачивает текущий `IEntityMetadataProvider`, поэтому ваш собственный провайдер продолжает работать и
  по-прежнему обязан делегировать вариант по умолчанию;
- **маршрутизация**: та же топология регистрируется в таблице топологий (`builder.AddTopology(topology)`)
  под именем `"sharding"`, а `ShardRouteResolver` — обычное правило `IEntityRouteResolver`, которое
  забирает шардированные типы и любую команду с вариантом бакета;
- **шардирование**: что такое бакет, где он лежит физически и что хеширует shard key.

### Размещение бакета

Режим размещения определяет, как номер бакета превращается в физическое имя. Оба режима зависят
только от номера бакета и никогда — от набора шардов.

В `SchemaPerBucket` — режиме по умолчанию — бакет становится схемой, а таблица сохраняет своё
сопоставленное имя:

```text
{placeholder}_{bucket}.{table}
```

`{placeholder}` — схема, в которую сопоставлена сущность, либо литерал `bucket`, если схема не
объявлена; `{table}` — сопоставленное имя таблицы без изменений. В `TableSuffix` суффикс несёт имя
таблицы, а схема не меняется:

| Сущность | Бакет | `SchemaPerBucket` (по умолчанию) | `TableSuffix` |
| --- | --- | --- | --- |
| `Order` — таблица `Orders`, без схемы | 1 | `bucket_1.Orders` | `Orders_1` |
| `Invoice` — схема `sales`, таблица `invoices` | 1 | `sales_1.invoices` | `sales.invoices_1` |
| `Order` | 7 | `bucket_7.Orders` | `Orders_7` |

```csharp
// SchemaPerBucket — по умолчанию; суффиксную таблицу нужно попросить явно.
var byTable = new ShardTopology(bucketCount: 1024, BucketPlacementMode.TableSuffix);
```

Тот же ответ доступен коду, который собирает SQL сам:

```csharp
var placement = context.GetPhysicalTableName<Order>(new MappingVariant("1"));
// placement.Schema == "bucket_1", placement.TableName == "Orders"
// placement.QualifiedName == "bucket_1.Orders"
```

### Raw SQL и имя бакета

Для планировщика raw SQL непрозрачен, поэтому сам по себе он не переписывается. Когда имя нужно
самому запросу, привяжите сущность к raw-источнику и используйте один из токенов:

| Токен | Во что раскрывается |
| --- | --- |
| `{table}` | сопоставленное имя таблицы, например `Orders_1` |
| `{schema}` | сопоставленная схема, например `sales_1` или `bucket_1` |
| `{qualified}` | `<schema>.<table>` либо только таблица, если схема не объявлена |

```csharp
var top = context.FromSql("select Id, Tenant, Total from {qualified} where Total > @min", new { min = 100 })
    .BindEntity<Order>(["Id", "Tenant", "Total"])
    .WithShardKey(tenant)                    // или .WithVariant(...) для явного бакета
    .Select(order => new { order.Id, order.Total })
    .OrderByDescending(row => row.Total)
    .ToList();
```

Токены раскрываются при построении плана — из метаданных привязанной сущности и варианта сопоставления
команды, там же, где имя получает обычный источник, — поэтому выполняется SQL с `bucket_7.Orders`
(или `Orders_7`), и запрос идёт на шард этого бакета. Квотирование — по настройке контекста
(`QuoteIdentifiers`). Фрагмент без трёх токенов выводится дословно, а фигурные скобки, не являющиеся
токеном, остаются как есть. `{schema}` для сущности без схемы — ошибка: используйте `{table}` или
`{qualified}`.

`ExecuteRaw`/`ExecuteProcedure` выполняются на собственном соединении контекста и не несут scope,
поэтому не могут адресовать таблицу бакета на его шарде; для этого используйте `FromSql` с вариантом либо
соберите запрос для контекста, уже направленного на шард.

### Свои функции хеширования

Обе стадии хеширования заменяемы. `ConsistentHashRing` принимает делегаты `BucketHash`
(байты ключа → бакет) и `ShardHash` (бакет + идентификатор шарда → оценка), а `UseSharding` принимает
любую реализацию `IShardTopology`, поэтому собственная топология может отдавать такое кольцо вместо
встроенного:

```csharp
var ring = new ConsistentHashRing(
    shardIds: ["pg-1", "pg-2"],
    bucketCount: 1024,
    bucketHash: (key, count) => MyHash.ToBucket(key, count),
    shardHash: (bucket, shardId) => MyHash.Score(bucket, shardId));

var topology = new MyTopology(ring);   // любая реализация IShardTopology

var builder = new DataContextBuilder()
    .UseSharding(topology)
    // Только для того, что не попадает в бакет: нешардированные сущности, сырой SQL, транзакция контекста.
    .UseDataRouting(routing => routing.UseDefaultTopology("main", "Host=pg-1;Database=app_master"));

using var context = new PostgresDataContext(builder);
```

Своя функция должна быть детерминированной между процессами и перезапусками: маршрутизация хранится
в данных, поэтому смена функции перемещает строки. Идентификаторы бакета и шарда проверяются;
идентификатор шарда не может быть пустым и никогда не попадает в SQL.

## Маршрутизация одной строки

`INSERT`, `UPDATE` и `DELETE` определяют бакет по экземпляру сущности и выполняются на соединении
шарда-владельца:

```csharp
context.CreateInsertBuilder<Order>()
    .Values(new Order { Id = 1, Tenant = "acme", Total = 10m })
    .Insert();

context.Update(new Order { Id = 1, Tenant = "acme", Total = 12m });
context.Delete(new Order { Id = 1, Tenant = "acme" });
```

Точечное чтение маршрутизируется по равенству shard key в предикате:

```csharp
var orders = context.From<Order>()
    .Where(order => order.Tenant == tenant)
    .Select(order => order.Total)
    .ToList();
```

Также работают явный ключ и явный scope:

```csharp
context.From<Order>().WithShardKey(tenant).ToList();
context.From<Order>().WithVariant(new MappingVariant("512")).ToList();   // номер бакета строкой
```

`WithShardKey` принимает по значению на свойство ключа, в объявленном порядке; раздел
[«Бакет строки»](#бакет-строки) ниже описывает допустимые типы значений и то, как спросить роутер о
бакете без запроса.

Предикат без равенства по shard key **отклоняется до SQL**, а не читает молча таблицу по умолчанию
и не сканирует все шарды. Добавьте равенство, вызовите `WithShardKey(...)` или сделайте fan-out по
бакетам.

## Бакет строки

`WithShardKey(...)` принимает значения shard key **в объявленном порядке** — у составного ключа по
значению на свойство — и возвращает builder, чей вариант равен бакету, в который хешируется этот набор:

```csharp
context.From<Order>().WithShardKey(tenant);          // у Order объявлен [ShardKey(nameof(Tenant))]
// то же самое: context.From<Order>().WithVariant(router.ResolveShard(typeof(Order), [tenant]))
```

Составной ключ принимает по значению на свойство, в объявленном порядке:

```csharp
[ShardKey(nameof(Tenant), nameof(Region))]
public sealed class Shipment { /* ... */ }

context.From<Shipment>().WithShardKey(tenant, region);
```

* Порядок задаёт атрибут либо ваш `IShardKeyProvider`, переданный в `UseSharding(topology, keyProvider)`.
* Число значений должно совпадать с ключом точно; `null` — такое же значение, как и любое другое.
* **Типы** значений входят в ключ: `int 5` и `long 5` дают разные бакеты, а поддержаны только `null`,
  `int`, `long`, `short`, `byte`, `Guid`, `string`, `bool`, `DateTime`, `DateTimeOffset` и `decimal`.
  Свойство-ключ типа enum, `uint`, `double`, `float` или `char` даёт `ArgumentException` вместо
  хеширования.
* Возвращается новый builder: тот, у которого вызвали метод, остаётся без варианта. Когда бакет уже
  известен, `WithVariant(new MappingVariant("512"))` — то же самое.

### Спросить бакет у контекста

`GetShardRouter()` возвращает роутер, которым маршрутизирует контекст, поэтому бакет можно получить, не
строя запрос и не храня топологию рядом. `TryGetShardRouter` сообщает, шардирован ли контекст вообще:

```csharp
var router = context.GetShardRouter();             // бросит исключение, если шардинг не настроен

int bucket = router.GetBucket(order);              // по экземпляру: читает свойства ключа
MappingVariant variant = router.GetScope(bucket);    // этот бакет как вариант — сразу для WithVariant

var same  = router.ResolveShard(typeof(Order), [order.Tenant]);   // по явным значениям
var shard = router.GetShard(bucket);                              // "pg-2"
```

`GetShardRouter()` — это тот объект, который `UseSharding` поставил резолвером варианта у builder'а и
который сохранил контекст, поэтому бакет, полученный здесь, — ровно тот бакет, на котором выполнится
запрос. `GetBucket` бросает исключение для типа без shard key, а `Resolve` для него возвращает
`MappingVariant.Default`. Остальной контракт — `GetShardKey`, `ShardIds`, `BucketCount` — перечислен
на `IShardRouter`.

Для списка строк ту же работу делает контекст: `GroupByBucket(rows)` разрешает каждый экземпляр и
возвращает по группе на бакет, в порядке номеров, — с номером `Bucket`, адресующим его `Variant` и
строками `Rows`.

Строка подключения шарда — это данные топологии, а не маршрутизации: соединение шарда контекст
открывает сам по идентификатору шарда, и топология нужна только коду, который открывает своё
ADO.NET-соединение.

### Работа по бакетам и шардам

Запись маршрутизируется по экземпляру, поэтому группе строк бакет не нужно считать вручную — ей нужен
**один SQL-оператор на бакет**, потому что бакет — это физическая таблица на шарде. `GroupByBucket`
разрешает каждую строку роутером самого контекста и отдаёт по группе на бакет. Многострочный insert
принимает строки группы и записывает их за одно обращение к базе данных; строки разных бакетов в одном insert
отклоняются до SQL, ведь один `INSERT` называет одну таблицу:

```csharp
foreach (var entitiesPerBucket in context.GroupByBucket(orders))
{
    context.CreateInsertBuilder<Order>()
        .Values(entitiesPerBucket.Rows)  // один многострочный INSERT на бакет
        .Insert();
}
```

Несколько SQL-инструкций по одному бакету можно объединить в батч: одна сессия, одно обращение к базе данных, один вариант.

```csharp
foreach (var entitiesPerBucket in context.GroupByBucket(orders))
{
    context.CreateBatchBuilder()
        .Insert(context.CreateInsertBuilder<Order>().Values(entitiesPerBucket.Rows))
        .Query(context.From<Order>().WithVariant(entitiesPerBucket.Variant).Select(order => order.Id))
        .ToList();                   // все шаги на шарде этого бакета, за одно обращение к базе данных
}
```

То же и для чтения: адресуйте **бакет**, а не шард, — сервер выберет роутер.
`GetPhysicalTableName<Order>(variant)` отвечает, где бакет лежит физически (`bucket_7.Orders` либо
`Orders_7` в режиме суффикса); [«Один батч — одна топология»](34-routing-data-to-topologies.md) содержит
правило для батчей целиком.

### Когда нужен пин

Маршрутизация выбирает хост **на каждую команду**, поэтому чтениям, записям и батчам пин не нужен —
сервер уже определяет бакет. Пин нужен для обратного случая: состояние, которое должно пережить одну
команду на одном сервере.

`PinHost(topology, hostId)` удерживает все команды топологии на одном хосте, пока жив дескриптор:

- серверная сессия, которую вы подготовили, — временная таблица, `SET`, advisory lock, prepared
  statement, — где следующая команда обязана попасть в то же соединение;
- read-your-write на выборщике, который вращается (`RoundRobinTopology`), где две команды иначе попали
  бы на разные серверы;
- шард, который собираетесь загружать и хотите держать прогретым.

```csharp
var router = context.GetShardRouter();
var shards = context.GroupByBucket(orders)
    .GroupBy(entitiesPerBucket => router.GetShard(entitiesPerBucket.Bucket));

foreach (var shard in shards)
{
    using var pin = context.PinHost("sharding", shard.Key);   // у этой топологии host id — это id шарда
    // все команды топологии идут на этот шард, пока блок не закончится
}
```

У шардовой топологии host id **и есть** идентификатор шарда, а пиннинг перекрывает бакет: пока он жив,
все команды топологии идут на запиненный шард, какой бы бакет ни был в варианте. Группируйте по шарду
до пиннинга и не адресуйте внутри блока бакет другого шарда. Топологию по умолчанию пиннить нельзя —
её хост фиксируется при создании контекста, потому что там выполняются запросы без маршрутизации по шардам, сырой SQL
и транзакция контекста. Пиннинг принадлежит топологии, а не контексту: новый пин заменяет старый,
освобождение старого дескриптора тогда ничего не делает, а `UnpinHost` снимает его без дескриптора.

## Fan-out по бакетам

`AcrossBuckets()` выполняет запрос по одному разу на бакет и возвращает **по одному вектору
результата на бакет**. Массив индексируется номером бакета — его длина равна заданному числу
бакетов, — а библиотека никогда не объединяет, не переупорядочивает и не агрегирует данные между
бакетами:

```csharp
var totals = context.From<Order>()
    .AcrossBuckets()
    .Where(order => order.Total > 100m)
    .Select(order => order.Total)
    .ToList();

// totals.Length == числу бакетов; totals[b] — строки бакета b
var grandTotal = totals.SelectMany(vector => vector).Sum();   // решение принимает вызывающий код
```

Операторы уровня бакета (`Where`, `OrderBy`, `Distinct`, `Select`) применяются к каждому бакету
независимо: `OrderBy` сортирует каждый вектор, а не даёт глобально упорядоченную
последовательность.

Скалярные терминалы возвращают по одному значению на бакет:

```csharp
int[] counts = context.From<Order>().AcrossBuckets().Count();
bool[] any = context.From<Order>().AcrossBuckets().Any();
Order[] first = context.From<Order>().AcrossBuckets().OrderBy(order => order.Id).First();
```

`AcrossBuckets(...).Buckets` перечисляет бакеты, которые покрывает fan-out. `AsAsyncEnumerable()`
отдаёт результат по одному вектору в порядке бакетов и последовательно, поэтому большой fan-out не
обязан материализовать все бакеты сразу.

## Выполнение и параллелизм

Fan-out группирует бакеты по шарду-владельцу:

- бакеты одного шарда выполняются **последовательно** на единственном соединении этого шарда;
- разные шарды выполняются **параллельно**, с лимитом, который по умолчанию равен числу шардов;
- `AcrossBuckets(parallelism: 1)` делает весь fan-out последовательным; значение ограничивается
  диапазоном `[1, shardCount]`.

```csharp
var vectors = await context.From<Order>()
    .AcrossBuckets(parallelism: 4)
    .Where(order => order.Total > 0m)
    .ToListAsync(cancellationToken);
```

## Кэш, идентичность и ребалансировка

- Планы, метаданные и материализаторы строк ключуются по `(тип сущности, mapping variant)`, поэтому два
  бакета никогда не делят подготовленную команду, префикс параметров или закэшированное имя таблицы.
- Быстрые пути без scope (общая команда `Any`, артефакты скалярных терминалов) для бакетного builder
  не используются: команда с вариантом готовится и выполняется только для этого бакета.
- Размещение бакета зависит только от его номера. Добавление или удаление сервера никогда не
  переименовывает таблицу или схему — ни передеплой, ни изменение DDL не нужны.
- Используется консистентное (rendezvous) хеширование без виртуальных узлов: новый шард забирает
  только выигранные бакеты (примерно `1/(K+1)`), а удаление шарда возвращает ровно эти бакеты прежним
  владельцам. Со встроенной лавинной оценкой 4096 бакетов распределяются по трём шардам как
  32.25 / 34.30 / 33.45 %.
- Когда бакет меняет владельца, его строки остаются на старом сервере. Их перенос — ответственность
  приложения; библиотека лишь вычисляет кольцо и размещение.

## Шардирование как маршрутизация по данным

Шардирование — одно правило общей модели маршрутизации. `ShardTopology` реализует `IHostTopology` (см.
[«Маршрутизация данных по топологиям»](34-routing-data-to-topologies.md)): роутер шардирования забирает
типы сущностей с объявленным shard key или с вариантом бакета, а топология превращает бакет в строку
подключения владеющего шарда. Это ровно те два контракта, на которых стоит шардирование: общий
`IHostTopology` и [`MappingVariant`](33-runtime-mapping-variant.md). Шардирование не расширяет их и не
подменяет — оно только решает, кто кладёт бакет в вариант и что этот бакет означает физически.
Остальной механизм маршрутизации — правило «один запрос — одна топология», пиннинг хоста и транзакции
на маршрутизированном хосте — работает для шардированных запросов без изменений:

```csharp
// Удержать сессию на одном шарде, например на том, который собираетесь загрузить.
context.PinHost("sharding", "pg-2");
```

Имя топологии, на которое ссылаются правила шардирования, — `"sharding"`.

Батч и ленивая временная таблица — по одной сессии каждый, поэтому маршрутизируются как единое целое:
батч, все шаги которого относятся к одному бакету, выполняется на шарде этого бакета, а чтение
временной таблицы бакета `b` требует задать тот же вариант и исходному запросу — тогда
`CREATE ... AS SELECT` и чтение делят один шард ([«Один батч — одна топология»](34-routing-data-to-topologies.md)).
Батч, которому нужны два бакета, отклоняется; выполняйте по батчу на бакет.

## Ограничения

- Результат fan-out — векторы по бакетам. Глобальные `ORDER BY`, `LIMIT`/`OFFSET`, `DISTINCT` и
  агрегаты между бакетами не композируются: объединяйте векторы на клиенте.
- Fan-out охватывает несколько соединений, поэтому не покрывается одной транзакцией и команды разных
  бакетов не атомарны друг относительно друга.
- Перенос данных при ребалансировке, распределённые транзакции (2PC) и смена числа шардов онлайн с
  сохранением таблицы бакета на старом сервере — вне области.
- Значение, переданное через `params` и существующее только во время выполнения, не извлекается из
  предиката; захватите его в замыкании, вызовите `WithShardKey(...)` или используйте fan-out.
- Массовая вставка (`BulkInsertBuilder`) в этой версии не учитывает шардирование.
- `ExecuteRaw`/`ExecuteProcedure` выполняются на соединении контекста и не несут вариант: таблицу
  бакета на его шарде адресуйте через `FromSql` с вариантом или через контекст, уже направленный на шард.
