# Динамические колонки

> Сопоставленная сущность может складывать не сопоставленные колонки строки в словарь, ключи которого
> берутся из набора результатов (схемы базы), а не из CLR-свойств — **сторона чтения** — и записывать
> этот словарь обратно физическими колонками в `INSERT`, `UPDATE` и `MERGE` — **сторона записи**. Обе
> стороны используют одно и то же `DynamicColumnsStore`.

**Предварительные требования:** [Запросы и проекции](01-filtering-where.md) · [Сущности и метаданные](../getting-started/03-entities-and-metadata.md)

## Обзор

Обычная сущность nextorm сопоставляет фиксированный набор CLR-свойств фиксированному набору колонок.
Если та же таблица несёт колонки, которые конкретная модель не объявляет (таблица расширяемых
атрибутов, разреженный набор необязательных колонок, схема, общая для нескольких моделей), такие
колонки просто не читаются.

**Хранилище динамических колонок** — это свойство с сеттером, помеченное
[`DynamicColumnsAttribute`](xref:NextORM.Core.DynamicColumnsAttribute) (или fluent-методом
[`EntityPropertyBuilder<T>.DynamicColumnsStore`](xref:NextORM.Core.EntityPropertyBuilder`1.DynamicColumnsStore)).
Когда сущность запрашивается **целиком**, генерируемый `SELECT` добавляет к сопоставленным колонкам
`*` источника, и хранилище наполняется всеми возвращёнными колонками, имена которых не совпадают с
сопоставленными. Тип хранилища должен допускать присваивание из `Dictionary<string, object?>` —
обычно `Dictionary<string, object?>`, `IDictionary<string, object?>` или
`IReadOnlyDictionary<string, object?>`.

```csharp
[SqlTable("product")]
public class Product
{
    [Key]
    public int Id { get; set; }

    public string? Name { get; set; }

    [DynamicColumns]
    public Dictionary<string, object?> Attributes { get; set; } = new();
}
```

```csharp
var products = ctx.From<Product>().ToList();

foreach (var product in products)
{
    // "Id" и "Name" — сопоставленные свойства; все остальные колонки таблицы "product"
    // (например "weight", "colour", "supplier_code") попадают в словарь.
    foreach (var (column, value) in product.Attributes)
        Console.WriteLine($"{column} = {value ?? "<null>"}");
}
```

Генерируемая инструкция:

```sql
select Id, Name, * from product
```

Сопоставленные колонки, как и раньше, читаются по порядковому номеру; хранилище читает следующие за
ними поля через `IDataRecord.GetName`/`GetValue`, пропуская поля, имена которых совпадают с
сопоставленными (сравнение регистронезависимо и после удаления подчёркиваний и приведения к нижнему
регистру, поэтому snake_case физическое имя совпадает со своим PascalCase-свойством). Ключи хранилища
сохраняют имя колонки базы данных в точности (словарь ordinal); регистронезависимо только пропускающее
сравнение с сопоставленными колонками.

## Запись динамических колонок

То же хранилище записывается обратно в `INSERT`, `UPDATE` и `MERGE`: ключи словаря становятся именами
физических колонок, а значения — связанными параметрами. Хранилище читается из сущности (или из каждой
строки батча) во время выполнения, поэтому открытый набор колонок сохраняется без сопоставленного
свойства на каждую колонку:

```csharp
var product = new Product
{
    Id = 7,
    Name = "Widget",
    Attributes = new Dictionary<string, object?>
    {
        ["weight"] = 1.5m,
        ["supplier_code"] = "ACME",
    },
};

ctx.CreateInsertBuilder<Product>().Values(product).Insert();
```

Генерируемая инструкция (показано квотирование PostgreSQL/SQLite; каждый диалект использует своё):

```sql
insert into product (Id, Name, "supplier_code", "weight") values (@p0, @p1, @p2, @p3)
```

Сторона записи зафиксирована следующими правилами:

* **Ключи — это физические имена колонок.** Ключ используется как есть — соглашение об именовании
  пропускается — и каждый динамический ключ квотируется квотированием идентификаторов диалекта, даже
  когда глобальная опция `UseQuotedIdentifiers` выключена.
* **Порядок ключей детерминирован.** Ключи сортируются порядково (`StringComparer.Ordinal`) до рендера,
  поэтому порядок колонок не зависит от порядка перечисления словаря.
* **`null` против отсутствующего ключа.** Присутствующий ключ со значением `null` пишет SQL `NULL`;
  ключ, отсутствующий в словаре, опускается — в `INSERT` применяется значение по умолчанию колонки, а в
  `UPDATE`/`MERGE` колонка остаётся неизменной (очистить колонку, опустив её ключ, нельзя).
* **Многострочный `INSERT`.** Каждая строка должна предоставить одинаковый набор ключей; несовпадение
  отклоняется с `InvalidOperationException`.
* **`MERGE`.** Динамические колонки идут в source, ветку `INSERT` и matched-`SET`, но никогда в условие
  `ON`.
* **Значения связываются как рантайм-CLR-значения** (pass-through): нет пер-ключевого конвертера
  значений, нет JSON-маппинга и нет фабрикуемых `IPropertyMetadata`.
* **Некорректные ключи отклоняются.** Пустой ключ или ключ, содержащий символ NUL, бросает
  `ArgumentException`.

## Fluent-маппинг

Используйте [`DynamicColumnsStore`](xref:NextORM.Core.EntityPropertyBuilder`1.DynamicColumnsStore),
когда маппинг объявляется fluent-методами, а не атрибутами:

```csharp
var products = ctx.From<Product>(b => b
    .Property(x => x.Id).Key()
    .Property(x => x.Name)
    .Property(x => x.Attributes).DynamicColumnsStore());
```

Хранилище не может одновременно объявлять имя колонки, конвертер значений/JSON или пару range-колонок;
свойство обязано иметь сеттер.

## Матрица провайдеров

Хранилище не зависит от движка: колонки берутся из набора результатов, а их имена читаются из
reader'а, поэтому сама материализация диалектного хука не требует. Единственное диалектное различие —
форма `*`: в MySQL/MariaDB capability [`ISqlDialect`](xref:NextORM.Core.ISqlDialect)
`RequiresQualifiedSelectStar` (по умолчанию `false`, переопределён в `true` на MySQL и наследуется
MariaDB) заставляет инструкцию алиасить сопоставленные колонки и `*`.

| Провайдер | Чтение | Запись | Примечание |
|---|---|---|---|
| PostgreSQL | да | да | `select <mapped>, *`; типы значений берутся из `DbDataReader`/рантайм-CLR-значения |
| SQL Server | да | да | сопоставленные идентификаторы остаются без кавычек, если кавычки не включены; динамические ключи квотируются всегда |
| MySQL / MariaDB | да | да | ``select t1.<mapped>, `t1`.*``; сопоставленные колонки и `*` алиасятся |
| SQLite | да | да | `select <mapped>, *`; сторона записи следует динамической типизации SQLite |
| ClickHouse | да | да | колонки таблицы должны существовать; её `MERGE` отклоняется независимо от хранилища |
| In-memory | да | нет | провайдер in-memory возвращает зарегистрированную строку и сторону записи не реализует |

## Ограничения

Хранилище применимо только к запросу по **одному физическому источнику**, читаемому целиком
(`ctx.From<TEntity>()` и его терминалы). Оно не применяется к явной проекции
(`Select(x => new { ... })`), а запрос с соединениями отклоняется с `NotSupportedException`, потому
что добавляемый `*` захватил бы и колонки соединённой таблицы. Коррелированный подзапрос по сущности
также не собирает хранилище.

На стороне чтения ключи настолько надёжны, насколько надёжна породившая их схема: хранилище никогда не
рендерит ключ в SQL, поэтому через имена колонок инъекция невозможна — имена порождает база, а не
вызывающая сторона. На стороне записи ключи поставляет вызывающая сторона, поэтому каждый ключ
валидируется (см. [Запись динамических колонок](#запись-динамических-колонок)) и квотируется
квотированием идентификаторов диалекта.

К хранилищу применимы два правила формы сущности. Сущность должна быть **ссылочного типа**: сущность
value-типа (`struct`), объявляющая хранилище, отклоняется с `InvalidOperationException` при построении
метаданных, а не упаковывается молча (boxing) — используйте класс. Она также должна иметь **публичный
конструктор без параметров**, потому что хранилище материализуется через member-init; сущность с
хранилищем без него отклоняется при подготовке с `QueryPreparationException`.

## Ограничения возможностей

Сторона записи несёт следующие ограничения:

* **Нет пер-ключевых конвертеров и JSON-колонок.** Динамическое значение связывается из своего
  рантайм-CLR-значения, зеркаля материализацию стороны чтения; чтобы сохранить сконвертированное
  значение или JSON, сопоставьте обычное свойство с конвертером значений или JSON-колонкой.
* **Нет отслеживания изменений.** nextorm никогда не отслеживает словарь: каждая запись — явный
  `INSERT`, `UPDATE` или `MERGE`, и записываются только переданные вами ключи.
* **Колонку нельзя очистить опусканием ключа.** Отсутствующий ключ означает «значение по умолчанию»
  в `INSERT` и «оставить без изменений» в `UPDATE`/`MERGE`; чтобы записать SQL `NULL`, передайте явный
  `null`.
* **Нет allow-list ключей.** Ключи валидируются (непустые, без NUL) и всегда квотируются, но
  allow-list разрешённых имён колонок отсутствует.
* **In-memory-провайдер сторону записи не реализует** (его сторона чтения возвращает зарегистрированный
  словарь как есть).
* **Ссылочный тип с публичным конструктором без параметров.** Сущность с хранилищем должна быть
  классом: сущность value-типа (`struct`) отклоняется с `InvalidOperationException` при построении
  метаданных (без молчаливого boxing), а класс без публичного конструктора без параметров отклоняется
  при подготовке с `QueryPreparationException` (см. [Ограничения](#ограничения)).
* **`null`-хранилище или пустое хранилище означает отсутствие динамических колонок.** На SQL-чтении
  хранилище создаётся из набора результатов, даже если изначально оно `null`; на записи
  `null`-хранилище или хранилище без ключей не даёт динамических колонок.

См. [Ограничения и возможности вне области охвата](../advanced/limitations.md).
