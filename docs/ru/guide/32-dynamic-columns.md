# Динамические колонки (сторона чтения)

> Сопоставленная сущность может складывать не сопоставленные колонки строки в словарь, ключи которого
> берутся из набора результатов (схемы базы), а не из CLR-свойств. Это **сторона чтения** возможности
> `DynamicColumnsStore`; запись ключей словаря обратно колонками не реализована.

**Предварительные требования:** [Запросы и проекции](01-querying-and-projections.md) · [Сущности и метаданные](../getting-started/03-entities-and-metadata.md)

## Обзор

Обычная сущность nextorm сопоставляет фиксированный набор CLR-свойств фиксированному набору колонок.
Если та же таблица несёт колонки, которые конкретная модель не объявляет (таблица расширяемых
атрибутов, разреженный набор необязательных колонок, схема, общая для нескольких моделей), такие
колонки просто не читаются.

**Хранилище динамических колонок** — это свойство с сеттером, помеченное
[`DynamicColumnsAttribute`](xref:NextORM.Core.DynamicColumnsAttribute) (или fluent-методом
[`EntityPropertyBuilder<T>.DynamicColumnsStore`](xref:NextORM.Core.EntityPropertyBuilder`1.DynamicColumnsStore)).
Когда сущность запрашивается **целиком**, генерируемый `SELECT` добавляет к сопоставленным колонкам
`*` источника, и хранилище наполняется всеми возвращёнными колонками, имена которых не совпадают с
сопоставленными. Тип хранилища должен допускать присваивание из `Dictionary<string, object?>` —
обычно `Dictionary<string, object?>`, `IDictionary<string, object?>` или
`IReadOnlyDictionary<string, object?>`.

```csharp
[SqlTable("product")]
public class Product
{
    [Key]
    public int Id { get; set; }

    public string? Name { get; set; }

    [DynamicColumns]
    public Dictionary<string, object?> Attributes { get; set; } = new();
}
```

```csharp
var products = ctx.From<Product>().ToList();

foreach (var product in products)
{
    // "Id" и "Name" — сопоставленные свойства; все остальные колонки таблицы "product"
    // (например "weight", "colour", "supplier_code") попадают в словарь.
    foreach (var (column, value) in product.Attributes)
        Console.WriteLine($"{column} = {value ?? "<null>"}");
}
```

Генерируемая инструкция:

```sql
select Id, Name, * from product
```

Сопоставленные колонки, как и раньше, читаются по порядковому номеру; хранилище читает следующие за
ними поля через `IDataRecord.GetName`/`GetValue`, пропуская поля, имена которых совпадают с
сопоставленными (сравнение идёт дословно и после удаления подчёркиваний и приведения к нижнему
регистру, поэтому snake_case физическое имя совпадает со своим PascalCase-свойством).

## Fluent-маппинг

Используйте [`DynamicColumnsStore`](xref:NextORM.Core.EntityPropertyBuilder`1.DynamicColumnsStore),
когда маппинг объявляется fluent-методами, а не атрибутами:

```csharp
var products = ctx.From<Product>(b => b
    .Property(x => x.Id).Key()
    .Property(x => x.Name)
    .Property(x => x.Attributes).DynamicColumnsStore());
```

Хранилище не может одновременно объявлять имя колонки, конвертер значений/JSON или пару range-колонок;
свойство обязано иметь сеттер.

## Матрица провайдеров

Хранилище не зависит от движка: колонки берутся из набора результатов, а их имена читаются из
reader'а, поэтому ни один провайдер не нуждается в диалектном хуке.

| Провайдер | Чтение | Примечание |
|---|---|---|
| PostgreSQL | да | `select <mapped>, *`; типы значений берутся из `DbDataReader` |
| SQL Server | да | идентификаторы остаются без кавычек, если кавычки не включены |
| MySQL / MariaDB | да | `select <mapped>, *` |
| SQLite | да | `select <mapped>, *` |
| ClickHouse | да | колонки таблицы должны существовать; хранилище читается как любой другой результат |
| In-memory | да | провайдер in-memory возвращает зарегистрированную строку, поэтому возвращается её собственный словарь `Attributes` |

## Ограничения

Хранилище применимо только к запросу по **одному физическому источнику**, читаемому целиком
(`ctx.From<TEntity>()` и его терминалы). Оно не применяется к явной проекции
(`Select(x => new { ... })`), а запрос с соединениями отклоняется с `NotSupportedException`, потому
что добавляемый `*` захватил бы и колонки соединённой таблицы. Коррелированный подзапрос по сущности
также не собирает хранилище.

Ключи настолько надёжны, насколько надёжна породившая их схема. Хранилище никогда не квотирует и не
рендерит ключ в SQL, поэтому через имена колонок инъекция невозможна — имена порождает база, а не
вызывающая сторона.

## Ограничения возможностей

**Сторона записи не реализована.** `INSERT`/`UPDATE`/`MERGE` не рендерят ключи словаря колонками;
поддерживаемый сегодня способ сохранить открытый набор полей — конвертер значений или JSON-колонка.
См. [Ограничения и возможности вне области охвата](../advanced/limitations.md).
