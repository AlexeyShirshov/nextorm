# Маршрутизация данных по топологиям

Маршрутизация решает, какое соединение выполнит запрос. nextorm отделяет это решение от самого
запроса: запрос пишется по типу сущности как обычно, а набор правил сопоставляет этому типу
**топологию** — именованный источник соединений. Перед каждой маршрутизируемой командой движок
спрашивает у топологии хост и выполняет запрос на нём.

Правило сопоставления бывает двух видов:

- **По структуре** — атрибут на типе сущности или сборке, префикс пространства имён или собственный
  резолвер. Правило — свойство кода.
- **По данным** — роутер шардирования превращает shard key или область бакета в топологию. Это тот же
  механизм, что описан в разделе
  [«Шардирование и горизонтальное партиционирование»](35-sharding-and-horizontal-partitioning.md),
  но со стороны маршрутизации.

Топология может содержать серверы кольца шардов, несколько обычных соединений, выбираемых по очереди,
или что угодно ещё, что умеет назвать соединение. Движок не интерпретирует, что за ней стоит: вес,
здоровье и нагрузка — дело самой топологии.

## Маршрутизация по структуре

Топологии и правила регистрируются на построителе контекста:

```csharp
var builder = new DataContextBuilder()
    .UseDataRouting(routing => routing
        .UseDefaultTopology("main", "Host=app-1;Database=app")
        .AddTopology(new RoundRobinTopology(
            "reports",
            "Host=reports-1;Database=warehouse",
            "Host=reports-2;Database=warehouse"))
        .RouteNamespace("MyApp.Reports", "reports"));

using var context = new PostgresDataContext(builder);
```

Маршрутизированный контекст создаётся только из билдера. Его собственное соединение — то, которым
пользуются немаппированные на правило сущности, raw SQL и транзакция контекста, — это хост
**дефолтной топологии**, а простейшая топология и есть одна строка подключения. Передать в конструктор
контекста ещё и строку подключения нельзя: тогда на вопрос «куда идут команды без правила» было бы два
ответа. Цепочка `DataContextBuilder` подчиняется тому же правилу: `UsePostgres(connectionString)` (или
`UseSqlite(filepath)`, …) — форма без роутинга, а `UsePostgres()` без параметров создаёт контекст только
из билдера.

`RoundRobinTopology` — эталонная реализация маршрутизации без шардирования: одно соединение на
команду, по кругу. Идентификаторы хостов — `host-1`, `host-2`, … в порядке объявления, либо любые свои
через конструктор с `IEnumerable<HostTarget>`. Для строки подключения `UseDefaultTopology` регистрирует
именно такую топологию из одного хоста; чтобы использовать свою, зарегистрируйте её и назовите —
`UseDefaultTopology("main")`.

Остальные правила устроены так же:

```csharp
[RouteTo("crm")]
public sealed class Customer
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
}
```

- `[RouteTo("crm")]` на типе маршрутизирует этот тип; тот же атрибут на сборке — все объявленные в ней
  типы.
- `RouteNamespace("MyApp.Crm", "crm")` маршрутизирует все типы, полное имя которых лежит под префиксом.
  Если подходят несколько префиксов, побеждает самый длинный.
- `RouteAssembly(typeof(Customer).Assembly, "crm")` маршрутизирует целую сборку.
- `UseResolver(rule)` добавляет собственное правило `IEntityRouteResolver`; правила перебираются в
  порядке регистрации.

Порядок проверки: атрибут типа, атрибут сборки, собственные резолверы, правила пространств имён, правила
сборок. Тип принадлежит ровно одной топологии, поэтому два правила, которые расходятся в ответе, — это
ошибка, а не молчаливое предпочтение:

```text
Entity 'MyApp.Crm.Customer' is routed to both 'crm' and 'archive'.
```

Правило, ссылающееся на незарегистрированную топологию, — тоже ошибка. Объявленные правила пространств
имён и сборок проверяются при создании контекста; атрибут — при первой маршрутизации своего типа.

## Один запрос — одна топология

Запрос — это одна серверная операция, поэтому движок собирает все типы сущностей, которые он читает
или пишет: источник `FROM`, соединения, подзапросы, CTE, ветви операций над множествами и цель
изменяющего запроса, — и требует, чтобы они договорились:

- все маршрутизированные источники должны разрешиться в **одну** топологию;
- источники без правила допустимы: они едут на том хосте, который выбрали маршрутизированные
  источники, поэтому шардированную таблицу можно соединить с небольшой справочной таблицей, которая
  есть на каждом шарде.

Запрос, которому нужны две разные топологии, отклоняется до выполнения:

```text
The statement reads 'Crm.Customer' routed to topology 'crm' and
'Billing.Invoice' routed to topology 'billing'. One SQL statement runs on one host, so its sources must
belong to a single topology; split it into one command per topology.
```

Разделите такой запрос на отдельные команды или перенесите оба типа в одну топологию. nextorm никогда не
объединяет результаты разных хостов.

## Один батч — одна топология

Батч (`CreateBatchBuilder`) — это одна SQL-сессия и один round trip, а не несколько запросов, которым
случайно оказалось по пути, поэтому правило действует на батч целиком: типы сущностей всех его шагов
должны сходиться в одну топологию и один вариант сопоставления. Хост выбирает первый
маршрутизированный шаг, шаг без правила едет вместе с ним, а шаг, которому нужна другая топология или
другой вариант, отклоняется **при построении батча** — `ToSql()` падает так же, ещё до открытия
соединения:

```text
A batch runs on one host, but its statements span topologies 'billing' and 'crm'. A batch is one SQL
session (one round trip), so every statement of it must belong to a single topology; split it into one
batch per topology.
```

Если в батче есть хотя бы один шаг с побочным эффектом — DML, материализация, захват вывода или raw-шаг
— топология спрашивается про writer (`CommandKind.Write`); батч из одних result-запросов спрашивает
reader. Внутри маршрутизированной транзакции весь батч присоединяется к её хосту, а батч, который ушёл
бы с него, падает так же, как любая другая команда.

### Временные таблицы — это тоже один батч

Ленивая временная таблица — ровно этот случай. Чтение источника `AsTempTable` выполняет один батч —
`DROP`, `CREATE TEMPORARY TABLE ... AS SELECT`, затем чтение — в одной сессии, значит и на одном хосте,
а таблица материализуется из исходного запроса **под его собственным вариантом**. Задавайте вариант и
источнику, и чтению:

```csharp
var variant = new MappingVariant("3");

var source = context.From<Order>()
    .WithVariant(variant)                     // строки бакета 3
    .Select(order => new { order.Id, order.Total })
    .AsTempTable();

var rows = context.From(source)
    .WithVariant(variant)                     // тот же бакет: один батч, один хост
    .Select(row => new { Id = row.GetInt32("Id"), Total = row.GetDecimal("Total") })
    .ToList();
```

Источник, который разрешается в другой бакет, отклоняется: его `CREATE ... AS SELECT` и чтение
потребовали бы двух хостов.

Энергичная материализация подчиняется тому же правилу: `ToTable`/`ToTempTable` пишет литеральное имя
цели, поэтому маршрутизируется по сущностям, которые читает **исходный запрос**, а не по типу
проецируемой строки, и выполняется под scope этого запроса. При `DropExisting` удаление уходит вместе с
созданием на тот же хост.

`ExecuteRaw`, `ExecuteProcedure` и bulk insert в маршрутизации не участвуют: они работают на соединении
контекста. Батч — это способ удержать несколько запросов вместе на одном маршрутизированном хосте.

## Соединения, транзакции и пиннинг

У каждого хоста своё лениво открываемое соединение, кэшируемое по ключу `topology/host` на время жизни
контекста и закрываемое вместе с ним. Дефолтная топология спрашивается один раз, при создании контекста:
её хост становится соединением контекста, поэтому им пользуются команды без правила, raw SQL и
транзакция контекста. Он стабилен на всё время жизни контекста: закрепляйте хост явно или
маршрутизируйте команды в другую топологию, а не ждите, что дефолтный хост будет меняться на команду.

Транзакция покрывает одно соединение. Пока она открыта на соединении контекста, команда, уходящая на
другой хост, падает с явной ошибкой, а не пишет вне транзакции.

Чтобы выполнить транзакцию на маршрутизированном хосте, начните её через `IRoutedTransactionManager`
(методы-расширения объявлены на `DataContext`, поэтому в обычном случае приведение не нужно):

```csharp
using var transaction = context.BeginTransaction(new RouteTarget("reports"));

context.CreateInsertBuilder<ReportRow>()
    .Value(row => row.Id, 1)
    .Insert();

transaction.Commit();
```

Начатая транзакция прикрепляет топологию к выбранному хосту до её завершения: каждая команда, которая
туда маршрутизируется, попадает в неё, а не выбирает другой хост. Команда, которая ушла бы с этого хоста,
падает; явный пиннинг, уводящий топологию в сторону, пока транзакция открыта, — тоже. Один контекст несёт
одну транзакцию за раз; точки сохранения остаются на соединении контекста.

Явный пиннинг удерживает сессию на одном сервере и по другим причинам — реплика, которую вы прогрели,
шард, который собираетесь загрузить:

```csharp
using (context.PinHost("reports", "host-2"))   // выборщик больше не выбирает
{
    // все команды, маршрутизированные в "reports", здесь идут на host-2
}
// дескриптор снял пиннинг; выборщик снова выбирает
```

`host-2` — это **идентификатор хоста**, `HostTarget.Id`, который топология возвращает для команды и
который уникален внутри этой топологии. `RoundRobinTopology("reports", cs1, cs2)` называет хосты
`host-1`, `host-2`, … в порядке переданных строк подключения, так что выше это второй сервер; свои
идентификаторы задаются явными `HostTarget`:

```csharp
new RoundRobinTopology("reports",
[
    new HostTarget("eu", "Host=reports-1;Database=warehouse"),
    new HostTarget("us", "Host=reports-2;Database=warehouse"),
]);
```

У шардовой топологии идентификаторы хостов — это идентификаторы шардов (`AddShard("pg-2", ...)`,
перечислены в `ShardIds` — и в `IShardRouter.ShardIds` у роутера, который отдаёт шардированный
контекст), а `RoundRobinTopology.Hosts` перечисляет свои хосты. Ваша реализация `IHostTopology` задаёт
идентификаторы сама в `TryGetHost`: в интерфейсе есть только `Name` и `TryGetHost`, потому что хосты
могут быть динамическими, поэтому идентификаторы, по которым вы пинните, храните в своей конфигурации.
Сам контекст хосты не перечисляет. `PinHost` резолвит идентификатор через топологию и бросает
`ArgumentException`, если та его не знает, — устаревший идентификатор падает громко, а не пиннит
молча в другое место.

`PinHost` возвращает дескриптор, который снимает пиннинг при освобождении, поэтому пиннинг покрывает
ровно тот блок, который вы задали `using`. `UnpinHost("reports")` снимает его явно, когда дескриптор
не сохраняется. Пиннинг принадлежит топологии: повторный пиннинг той же топологии заменяет его, и
освобождение старого дескриптора тогда ничего не делает.

Топология обязана вернуть закреплённый хост из `TryGetHost` (или отказаться); контекст это проверяет и
падает, а не маршрутизирует втихую в другое место.

## Своя топология

Топология — одно свойство и один метод:

```csharp
public sealed class HealthAwareTopology : IHostTopology
{
    public string Name => "reports";

    public bool TryGetHost(in TopologyContext context, out HostTarget host)
    {
        // context.Variant — вариант сопоставления, в котором выполняется команда
        // context.Kind    — CommandKind.Read или CommandKind.Write
        // context.HostId  — закреплённый хост или null, если можно выбирать
        host = context.Kind == CommandKind.Read ? PickReadReplica() : PickPrimary();
        return true;
    }
}
```

`TryGetHost` возвращает `false`, чтобы оставить команду на собственном соединении контекста (хосте
дефолтной топологии). Всё остальное —
взвешенный выбор, балансировка по частоте запросов, проверки здоровья, разделение чтения и записи —
реализуется внутри метода.

## Связь с шардированием

Шардирование — это правило по данным той же модели: shard key (или вариант бакета при fan-out) выбирает
топологию `"sharding"`, а `ShardTopology` превращает бакет в хост шарда. Ничто на этой странице не
требуется для шардирования, и шардирование не требует структурных правил. Если настроены оба механизма,
правило шардирования — обычный собственный резолвер, который забирает шардированные типы сущностей.
