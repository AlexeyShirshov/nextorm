# Шардирование и горизонтальное партиционирование

nextorm умеет направлять один тип сущности в несколько физических таблиц или схем через одно
соединение. Используется слой сопоставления, описанный в разделе
[Переопределение источника для запроса](01-query-sources.md#переопределение-источника-для-запроса),
и mapping scope: шардирование добавляет поверх `MappingScope`, `IEntityScopeResolver` и
`IEntityMetadataProvider` кольцо консистентного хеширования, топологию шардов и роутер.

## Объявление shard key

Shard key — одно или несколько читаемых свойств экземпляра:

```csharp
[ShardKey(nameof(Tenant))]
public sealed class Order
{
    public int Id { get; set; }
    public string Tenant { get; set; } = "";
    public decimal Total { get; set; }
}
```

Значения ключа хешируются детерминированной некриптографической функцией с фиксированным seed,
поэтому один и тот же ключ попадает в тот же шард в любом процессе и после перезапуска. Поддержаны
`int`, `long`, `short`, `byte`, `Guid`, `string`, `bool`, `DateTime`, `DateTimeOffset`, `decimal` и
`null`; любой другой тип приводит к исключению при маршрутизации.

## Настройка шардов

`ShardTopology` хранит идентификаторы шардов, кольцо и физическое размещение каждого шарда:

```csharp
var topology = new ShardTopology();          // 128 виртуальных узлов на шард, 4096 бакетов
topology.AddShard("shard_eu", schema: "eu");
topology.AddShard("shard_us", schema: "us");

var builder = new DataContextBuilder().UseSharding(topology);
using var context = new PostgresDataContext(connectionString, builder);
```

Идентификатор шарда становится частью SQL-идентификатора, поэтому проверяется при регистрации:
только буквы, цифры и подчёркивание. Если имя таблицы для шарда не задано явно, таблица называется
`{mappedTable}_{shardId}`; явная схема заменяет сопоставленную схему для этого шарда.

`UseSharding` устанавливает `ShardRouter` в качестве резолвера scope и оборачивает текущий провайдер
метаданных в шард-осведомлённый декоратор, поэтому существующий `IEntityMetadataProvider` продолжает
работать.

## Маршрутизация записи

`INSERT`, `UPDATE` и `DELETE` определяют шард по экземпляру сущности:

```csharp
context.CreateInsertBuilder<Order>()
    .Values(new Order { Id = 1, Tenant = "acme", Total = 10m })
    .Insert();

context.Update(new Order { Id = 1, Tenant = "acme", Total = 12m });
context.Delete(new Order { Id = 1, Tenant = "acme" });
```

Многострочная вставка, строки которой попадают в разные шарды, отклоняется до выполнения SQL:
сгруппируйте строки по шарду и вставляйте группы отдельно. Вставка только по колонкам не содержит
shard key и требует явного `WithShardKey(...)`.

## Маршрутизация чтения

Точечное чтение маршрутизируется по равенству shard key в предикате:

```csharp
var orders = context.From<Order>()
    .Where(order => order.Tenant == tenant)
    .Select(order => order.Total)
    .ToList();
```

Также работают явный ключ и явный scope:

```csharp
context.From<Order>().WithShardKey(tenant).ToList();
context.From<Order>().WithScope(new MappingScope("shard_eu")).ToList();
```

Предикат без равенства по shard key **отклоняется до SQL**, а не читает молча таблицу по умолчанию
и не сканирует все шарды. Добавьте равенство, вызовите `WithShardKey(...)` или собирайте данные по
шардам явно.

## Сбор с нескольких шардов

`AcrossShards()` выполняет по одной команде на выбранный шард и объединяет строки на клиенте:

```csharp
var all = context.From<Order>()
    .AcrossShards()
    .Where(order => order.Total > 100m)
    .Select(order => order.Total)
    .ToList();

var some = context.From<Order>().AcrossShards("shard_eu", "shard_us").ToList();
```

Глобальные сортировка, пагинация, `DISTINCT` и агрегаты не выводятся из конкатенации результатов по
шардам: `OrderBy`, `Take`, `Skip`, `Distinct`, `Count`, `Any`, `First` и `Single` на fan-out запросе
бросают `NotSupportedException`. Выполняйте их на одном шарде либо сливайте материализованные строки
на клиенте.

## Кэш, идентичность и ребалансировка

- Планы и метаданные ключуются по `(тип сущности, mapping scope)`, поэтому два шарда никогда не
  делят подготовленную команду, префикс параметров или закэшированное имя таблицы.
- Команда, подготовленная для одного scope, не переиспользуется для другого, в том числе через
  быстрые пути переиспользования планов без значений.
- Новые публичные члены вносятся в `PublicAPI.Unshipped.txt` и подчиняются обычным правилам
  совместимости API.
- Консистентное хеширование перемещает примерно `1/(K+1)` ключей при добавлении `(K+1)`-го шарда, но
  ключ, сменивший шард, теперь указывает на таблицу, данные в которую писались по старому кольцу.
  Перенос строк — ответственность приложения; библиотека лишь вычисляет кольцо и размещение.

## Ограничения

- Соединение на шард, распределённые транзакции (2PC), перенос данных при ребалансировке и смена
  числа шардов онлайн без bump версии топологии — вне области.
- Значение, переданное через `params` и существующее только во время выполнения, не извлекается из
  предиката; захватите его в замыкании, вызовите `WithShardKey(...)` или используйте fan-out.
- Массовая вставка (`BulkInsertBuilder`) в этой версии не учитывает шардирование.
- Кросс-шардовые `ORDER BY`/`LIMIT`/`OFFSET`/`DISTINCT`/агрегаты не композируются глобально.
