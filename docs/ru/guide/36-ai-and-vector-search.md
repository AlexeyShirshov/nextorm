# ИИ и векторный поиск

Это руководство для разработчиков, которые создают семантический поиск или генерацию с дополнением по
найденным данным (retrieval-augmented generation, RAG) на nextorm. Используйте его, чтобы сохранять
эмбеддинги внешних моделей и находить ближайшие документы через общий API векторного поиска nextorm.
nextorm отвечает только за хранение и поиск в базе: он не генерирует эмбеддинги, не интегрируется с
моделями эмбеддингов или большими языковыми моделями (LLM) и не строит промпты.

## Перед началом

Перед использованием примеров подготовьте следующее:

- Контекст данных, настроенный для PostgreSQL или SQL Server. См. [настройку провайдера PostgreSQL](../connecting-providers/postgres.md)
  или [настройку векторного поиска SQL Server](../connecting-providers/sqlserver.md#поиск-по-векторам).
- Колонку-вектор в базе и сопоставленное с ней свойство сущности. Размерность колонки должна
  совпадать с размерностью модели эмбеддингов; см. [векторный поиск PostgreSQL](provider-specific-sql/postgresql.md#унифицированный-api-поиска-ближайших-соседей)
  или [настройку векторного поиска SQL Server](../connecting-providers/sqlserver.md#поиск-по-векторам).
- Внешнюю модель эмбеддингов или готовую последовательность координат. Используйте одну модель и
  предобработку для документов и запросов и сохраняйте одинаковую размерность векторов.

Типичный конвейер генерации с дополнением по найденным данным (RAG):

1. Внешняя модель эмбеддингов преобразует каждый документ в вектор.
2. Приложение сохраняет документ и вектор в базе.
3. Во время запроса та же модель эмбеддингов и совместимая предобработка превращают вопрос пользователя
   в вектор той же размерности.
4. nextorm запрашивает у базы ближайшие `topK` строк.
5. Приложение может передать найденный текст вместе с вопросом пользователя внешней большой языковой
   модели (LLM).

## Общий API векторов и поиска

`IVectorValue` — общий контракт значения-вектора со свойством `Dimensions`. `Vector` — его
независимая от провайдера реализация:

```csharp
using NextORM.Core;

var vector = new Vector(new[] { 0.12f, -0.34f, 0.56f });
var parsed = Vector.Parse("[0.12,-0.34,0.56]");
System.Console.WriteLine($"{vector.Dimensions}; {parsed.Dimensions}");
```

Ожидаемый вывод:

```text
3; 3
```

### Проверьте значения вектора

Конструктор копирует переданный `IEnumerable<float>`, отклоняет `NaN` и бесконечность, а при null
выбрасывает `ArgumentNullException`. `Parse` принимает заключённый в квадратные скобки список конечных
чисел одинарной точности, разделённых запятыми, в инвариантном числовом формате; неверный формат вызывает
`FormatException`.

Пустой вектор можно создать или разобрать, но нельзя использовать в поисковом запросе:
`VectorSearch` требует хотя бы одну размерность. Тип и размерность вектора запроса должны совпадать с
сопоставленным столбцом-вектором. Сервер базы может отклонить запрос, если размерности не совпадают с
сохранёнными векторами.

### Равенство и хеширование векторов

`Vector` использует точное сравнение значений: векторы равны, если у них одинаковая размерность,
а каждая координата имеет то же значение `float` и находится на том же месте. Сравнение не использует
допуск или метрику сходства; `+0f` и `-0f` считаются равными. Для вычисления расстояния или сходства
используйте `VectorSearch` или `SqlFunctions.VectorDistance`.

Это меняет прежнее поведение сравнения по ссылке: независимо созданные векторы с одинаковыми
координатами теперь равны. Это значение используют `==`, `Equals`, `HashSet<Vector>`,
`Dictionary<Vector, TValue>` и LINQ `Distinct()`. Если нужно проверить, ссылаются ли две переменные на
один объект, используйте `object.ReferenceEquals(first, second)`. `GetHashCode()` предназначен для хешируемых
коллекций; его результат действует только в процессе и не является сохраняемым идентификатором или
мерой сходства.

Например, конструктор и парсер создают одну запись множества для одинаковых координат:

```csharp
using System.Collections.Generic;
using NextORM.Core;

var first = new Vector(new[] { 0.12f, -0.34f });
var second = Vector.Parse("[0.12,-0.34]");
var uniqueVectors = new HashSet<Vector> { first, second };
System.Console.WriteLine(uniqueVectors.Count);
```

Ожидаемый вывод:

```text
1
```

`EntityBuilder<TEntity>.VectorSearch<TVector>` принимает `vectorSelector`, `queryVector`, `metric` и
положительный `topK`; необязательный `mode` по умолчанию равен `VectorSearchMode.Exact`. Тип `TVector`
ограничен интерфейсом `IVectorValue`, результат имеет тип
`QueryCommand<VectorSearchResult<TEntity>>`. Каждый результат содержит найденную сущность `Entity` и
nullable-расстояние `double? Distance`. Для всех общих метрик меньшее расстояние означает большую близость:

| Метрика | Значение |
|---|---|
| `VectorDistanceMetric.Cosine` | Косинусное расстояние |
| `VectorDistanceMetric.Euclidean` | Евклидово расстояние (L2) |
| `VectorDistanceMetric.DotProduct` | Отрицательное скалярное произведение, а не положительное сходство по скалярному произведению |

Выбирайте метрику, ожидаемую моделью эмбеддингов и индексом базы. Если модель требует нормализации
векторов, последовательно применяйте её при сохранении и запросе. Не предполагайте, что нормализация
делает расстояния разных метрик или моделей сравнимыми или что для них подходит единый порог оценки.

Предполагается, что `context` настроен для поддерживаемого провайдера, а `Document` сопоставляет
`Category` и `Embedding`. Переменная `category` содержит категорию для фильтрации. Запрос возвращает
точные ближайшие векторы с косинусной метрикой для этой категории:

```csharp
var queryVector = new Vector(new[] { 0.12f, -0.34f, 0.56f });
var exactHits = context.From<Document>()
    .Where(document => document.Category == category)
    .VectorSearch(
        document => document.Embedding,
        queryVector,
        VectorDistanceMetric.Cosine,
        topK: 5,
        mode: VectorSearchMode.Exact)
    .ToList();

foreach (var hit in exactHits)
{
    Document document = hit.Entity;
    double? distance = hit.Distance;
}
```

Чтобы запросить приближённый поиск, укажите режим явно:

```csharp
var approximateHits = context.From<Document>()
    .Where(document => document.Category == category)
    .VectorSearch(
        document => document.Embedding,
        queryVector,
        VectorDistanceMetric.Cosine,
        topK: 5,
        mode: VectorSearchMode.Approximate)
    .ToList();
```

В примере команда материализуется вызовом `.ToList()`. Фильтры `Where` сохраняются. Векторный поиск
задаёт собственную сортировку по возрастанию расстояния и ограничение `topK`, заменяя ранее заданную
пользовательскую сортировку, limit или offset. Для приближённого поиска SQL Server действует более
строгая проверка: пользовательская сортировка или постраничный вывод отклоняются, а не заменяются.

Для скалярного расстояния в обычной проекции используйте SQL-маркер
`SqlFunctions.VectorDistance(left, right, metric)`. Он возвращает nullable-расстояние и переводится
поддерживаемыми провайдерами базы; сам по себе он не добавляет сортировку ближайших соседей или
ограничение `topK`:

```csharp
var distances = context.From<Document>()
    .Select(document => new
    {
        document.Id,
        Distance = SqlFunctions.VectorDistance(
            document.Embedding, queryVector, VectorDistanceMetric.Cosine)
    })
    .ToList();
```

## Сопоставьте сущности и сохраните эмбеддинги

### Сопоставьте колонку-вектор

Сопоставьте свойство-вектор так же, как остальные колонки сущности. Размерность колонки в базе должна
совпадать с размерностью результата модели эмбеддингов. В примере для иллюстрации используются три
координаты; реальные модели обычно имеют другую фиксированную размерность:

```csharp
public sealed class Document
{
    public int Id { get; set; }
    public string Category { get; set; } = "";
    public string Body { get; set; } = "";
    public Vector Embedding { get; set; } =
        new Vector(new[] { 0f, 0f, 0f });
}
```

### Сохраните документ и его эмбеддинг

Предположим, что `category` и `body` содержат данные документа, а `embeddingValues` — это
`IEnumerable<float>`, полученный от внешнего по отношению к nextorm сервиса эмбеддингов. Оберните значения
в `Vector` и используйте обычный builder вставки:

```csharp
var document = new Document
{
    Id = 1,
    Category = category,
    Body = body,
    Embedding = new Vector(embeddingValues)
};

context.CreateInsertBuilder<Document>()
    .Values(new[] { document })
    .Insert();
```

Сопоставление сущности, таблица, колонки и схема базы остаются ответственностью приложения.
PostgreSQL использует расширение pgvector и колонку `vector(n)` с заданной размерностью; SQL Server —
колонку `VECTOR(n)` с заданной размерностью. nextorm не генерирует этот DDL и не создаёт векторные
индексы. Настройка и требования движков описаны в разделе
[«Настройка и сведения о провайдерах»](#настройка-и-сведения-о-провайдерах).

## Точный и приближённый поиск по провайдерам

`Exact` и `Approximate` — разные запросы, а не взаимозаменяемые подсказки производительности.
Провайдеры без поддержки векторного поиска отклоняют его; nextorm не переключает молча метрику или
режим поиска.

В таблице сведены возможности и ограничения каждого провайдера в обоих режимах:

| Провайдер | `Exact` | `Approximate` |
|---|---|---|
| PostgreSQL | Использует функции расстояния pgvector для сортировки отфильтрованных строк. Это точный поиск ближайших соседей; сортировка по функции не подходит для индексов HNSW/IVFFlat, использующих операторы расстояния. | Использует соответствующий оператор расстояния pgvector (`<=>`, `<->` или `<#>`). Запрос может использовать подходящий индекс HNSW или IVFFlat, но решение об использовании принимает планировщик PostgreSQL. |
| SQL Server | Использует `VECTOR_DISTANCE` и сортирует по выбранному расстоянию. Вызывающий код должен объявить мажорную версию SQL Server не ниже 17; nextorm не опрашивает движок. | Использует явно настроенную грамматику `VECTOR_SEARCH`. Требуются preview-функция базы и подходящий индекс DiskANN; см. [требования к приближённому поиску SQL Server](#требования-к-приближённому-поиску-sql-server). |
| Остальные провайдеры, включая in-memory | Не поддерживается, если только диалект явно не объявляет поддержку векторного поиска. | Не поддерживается, если только диалект явно не объявляет поддержку векторного поиска. |

Объявление версии SQL Server — это гейт возможностей библиотеки, а не подтверждение того, что сборка
подключённого движка поддерживает выбранную грамматику `VECTOR_SEARCH`. Явно выберите `TopN` или
`WithApproximate` для целевого движка. `TopN` проверен вживую на SQL Server `17.0.5005.3`;
`WithApproximate` покрыт только тестами генерации SQL и требует проверки на целевой сборке.

### Требования к приближённому поиску SQL Server

Для приближённого поиска SQL Server нужен подходящий векторный индекс DiskANN. Следует включить
preview-функцию базы; индексируемой таблице нужны первичный ключ и не менее 100 векторов, не равных
NULL. DDL схемы и индексов управляется приложением. Запрос обязан использовать прямую физическую
таблицу сущности; соединения, группировка, `DISTINCT`, производный источник, пользовательская
сортировка и постраничный вывод не допускаются. Фильтры `Where` сохраняются, но nextorm не обещает,
что движок предварительно отфильтрует приблизительных кандидатов или обеспечит конкретную полноту
результатов и стратегию повторного вычисления расстояния.

## Проверьте результат поиска

При выполнении векторного запроса в своей базе проверьте следующее:

- Убедитесь, что каждая возвращённая сущность соответствует фильтрам запроса.
- Проверьте, что число результатов не превышает `topK`.
- Убедитесь, что ненулевые значения `Distance` расположены по возрастанию; явно обработайте null.

Сравните `Approximate` и `Exact` для одного запроса, метрики и фильтров, чтобы оценить качество
результатов. Не ожидайте одинаковых наборов строк или гарантированной полноты поиска. Изучите фактический
план выполнения, чтобы подтвердить использование ожидаемого векторного индекса; допустимость индекса
для запроса PostgreSQL не гарантирует, что планировщик его выберет. Измеряйте производительность на
своей нагрузке: ни один режим не обещает конкретную задержку или пропускную способность.
