# NativeAOT

> Нативные приложения на .NET 11 для `linux-x64`: `<PublishAot>true</PublishAot>` — единственная
> настройка. Скомпилированная модель, отдельная генерация запросов и ручной код не нужны.

**Что нужно заранее:** [Подключения](01-connections.md) · [Конвертеры значений и JSON-колонки](03-value-converters.md).

## Включение

```xml
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <RuntimeIdentifier>linux-x64</RuntimeIdentifier>
</PropertyGroup>
```

```bash
dotnet publish -c Release
```

Действуют стандартные требования NativeAOT: `clang`, `zlib1g-dev` и нативный тулчейн под выбранный RID.

## Что поддерживается

Провайдеры: **SQLite, PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse**.

Поверхность запросов: типизированные и анонимные проекции, фильтры, сортировка, постраничность,
агрегаты, `GROUP BY`/`HAVING`, join'ы, CTE, оконные функции (где их поддерживает провайдер),
JSON-функции SQLite, массивы ClickHouse, `SelectGroup`/`SelectGroupHaving`,
`SelectWhereMin`/`SelectWhereMax`, переиспользование подготовленных команд, коррелированные
подзапросы.

Каждый поддерживаемый сценарий исполняется и нативно, и под JIT, и сверяется построчно: количество
строк и значения должны совпадать. Проверка выполняется автоматически на каждом изменении, поэтому
«работает нативно» — это не разовая акция, а постоянное условие сборки.

## Ограничения

- EF Core bridge (`nextorm.entityframeworkcore`), массовая вставка, маппинг сырого SQL и DML-билдеры в
  нативную сборку пока не входят — для этих сценариев оставайтесь на обычном JIT-рантайме.
- Конвертеры `System.Text.Json` работают через `JsonSerializerContext`: сериализация остаётся
  рефлексивной, поэтому контекст нужно настроить как обычно.
- Запросы вне перечисленной поверхности могут упасть при первом исполнении. Прогоните свой набор
  запросов на нативной сборке до релиза.
- Пакеты пока не помечены `IsAotCompatible`, поэтому анализаторы не предупреждают о проблеме заранее —
  проверка происходит во время выполнения.

## Производительность

Нативная публикация убирает JIT и холодный старт — на короткоживущих процессах это основной выигрыш:
старт и один небольшой запрос занимают десятки миллисекунд вместо почти секунды, а отчёт по базе
13 ГБ ниже отрабатывает за десятые доли секунды вместо одной-двух.

У этого выигрыша есть цена: без JIT выражения материализатора строк исполняются интерпретатором —
примерно вдвое дольше и в несколько раз больше аллокаций, чем у скомпилированного кода. Сборка снимает
большую часть сама: генератор покрывает все типы проекций, объявленные в вашей сборке — именованные
типы и record-DTO, а также анонимные типы — поэтому подготовленный запрос сохраняет обычную скорость и
в нативной сборке. На подготовленной команде в 500 строк по три колонки это 543 → 364 µs и
246 → 39 KB.

```csharp
// без атрибута и без регистрации: покрывается автоматически
public sealed record OrderSummary(int Id, string? Customer, decimal Total);

var summaries = context.From<Order>()
    .Select(order => new OrderSummary(order.Id, order.Customer, order.Total))
    .ToList();

var rows = context.From<Order>().Select(order => new { order.Id, order.Customer }).ToList();
```

Потоковые терминалы этой цены не платят: `WriteCsv` и `WriteJson` не материализуют строки и пишут
scalar-колонки уже скомпилированным кодом в том числе в нативной сборке.

Для массовых выгрузок широких строк на AOT-рантайме интерпретация всё же заметна: такие задачи проще
оставить на JIT.

## Проверка на реальном приложении

`oc-report` — утилита отчётов по базе SQLite на 13 ГБ — публикуется нативно без правок исходников,
кроме `PublishAot=true`: бинарник 8.2 МБ, прогон 0.12 с, пик памяти 30 МБ.

Эталонное приложение —
[`examples/nextorm.examples.oc-report`](https://github.com/AlexeyShirshov/nextorm/tree/main/examples/nextorm.examples.oc-report).

## Если запрос падает

Откройте issue с минимальным воспроизводящим запросом, целевом RID, версией .NET SDK и выводом
`dotnet publish`. Нативный reproducer ценнее JIT-ового: часть ошибок проявляется только после
публикации.
