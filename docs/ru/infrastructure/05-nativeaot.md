# NativeAOT

> Для приложений на .NET 11 с целевой платформой `linux-x64` или `win-x64` включите нативную публикацию через
> `<PublishAot>true</PublishAot>`. Скомпилированная модель, отдельная генерация запросов и ручной
> код не нужны.

**Что нужно заранее:** [Соединения](01-connections.md) · [Конвертеры значений и JSON-колонки](03-value-converters.md).

## Включение

Перед публикацией установите зависимости NativeAOT на машине сборки:

- **Linux x64:** `clang`, `zlib1g-dev` и нативный тулчейн.
- **Windows x64:** Visual Studio или Visual Studio Build Tools с компонентом **Разработка классических
  приложений на C++** (Desktop development with C++), включая MSVC x64 и Windows SDK.
  Для `win-x64` выполняйте публикацию на Windows.

Добавьте эти свойства в файл проекта:

```xml
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <RuntimeIdentifier>linux-x64</RuntimeIdentifier>
</PropertyGroup>
```

Затем опубликуйте приложение:

```bash
dotnet publish -c Release
```

Для Windows задайте `RuntimeIdentifier` равным `win-x64` либо переопределите RID при публикации:

```powershell
dotnet publish -c Release -r win-x64
```

Запустите полученный `.exe` из каталога публикации. SQLite не требует сервера БД или контейнеров;
серверным провайдерам нужна живая БД — локальная, удалённая или в контейнере.

Маппинг сущностей тоже компилируется: пакет поставляет source-генератор, который описывает каждую
сущность `[SqlTable]`/`[Table]` из вашей сборки — таблицу, колонки, ключи, точность, collation,
длительности, пары колонок диапазона, фильтры запросов, конвертеры значений/JSON и навигации связей,
включая базовые классы, — и построение маппинга читает это описание вместо рефлексии по членам типа. Тип вне покрытия остаётся на
рефлексивном пути, поэтому ничего не нужно регистрировать и включать.

## Что поддерживается

Провайдеры: **SQLite, PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse**.

Поддерживаемая поверхность запросов включает:

- **Запросы и результаты:** типизированные и анонимные проекции, материализацию сущностей целиком,
  фильтры, сортировку, постраничность, агрегаты, `GROUP BY`/`HAVING`, join'ы, CTE, поддерживаемые
  провайдером оконные функции, переиспользование подготовленных команд и коррелированные подзапросы.
- **Особенности провайдеров:** JSON-функции SQLite и массивы ClickHouse.
- **Маппинг и связи:** конвертеры значений, JSON-колонки (см. [JSON-колонки](#json-колонки)) и
  нетерпеливую загрузку объявленной коллекции `[Relationship]` через split-загрузчик (`LoadWith`) или
  одним запросом (`LoadWith(..., EagerLoadMode.SingleQuery)` и `JoinInto`), включая проверенные
  варианты «многие ко многим» со скалярным и составным ключом.
- **Запись и сырой SQL:** билдеры insert, update и delete, массовую вставку и маппинг строк сырого SQL
  (`ExecuteRaw`, скалярные результаты и результаты в виде сущности).
- **Потоковая передача:** `WriteCsv`, `WriteJson` и асинхронную последовательность строк
  (`ToAsyncEnumerable`).

В репозитории есть проверки сравнения нативного исполнения с JIT для представительных сценариев
SQLite и запросов к разным провайдерам. Проверки серверных провайдеров используют отдельный
опубликованный нативный бинарник и живую базу каждого провайдера; в том числе проверяются графы
нетерпеливой загрузки одним запросом с выполнением одной SQL-команды и сверкой с настоящим
JIT-запуском. Покрытие представительное, а не исчерпывающее, и не является автоматической гарантией
совместимости для любой комбинации запросов. Перед релизом проверьте собственный набор запросов на
нативной сборке.

### Проверка на Windows

2026-11-18 репозиторный `nextorm.aot.runner` опубликован и запущен на Windows x64 с .NET SDK
11.0.100 (`win-x64`). Все **40 SQLite-сценариев** прошли и совпали с JIT-контролем на одной и той же
заполненной базе. Проверены проекции, агрегаты, коррелированные подзапросы, join'ы, CTE, оконные функции,
конвертеры, связи, потоковая передача, сырой SQL, DML и массовая вставка.

Это проверка текущих исходников, а не отдельный прогон опубликованных NuGet-пакетов.
Серверные провайдеры на Windows в этом прогоне не проверялись: покрытие на Linux не означает
подтверждение на Windows. Публикация успешна, но содержит предупреждения trim/AOT-анализаторов.

Воспроизведение из корня репозитория на Windows:

```powershell
dotnet publish tests/nextorm.aot.runner -c Release -r win-x64
dotnet build tests/nextorm.integration.tests -c Debug
$env:DOTNET_SYSTEM_GLOBALIZATION_INVARIANT = "1"
$env:NEXTORM_AOT_EVIDENCE = "1"
$env:NEXTORM_AOT_EVIDENCE_DIR = Join-Path $env:TEMP ("nextorm-aot-" + [guid]::NewGuid())
dotnet run --project tests/nextorm.integration.tests -c Debug --no-build -- -class NextORM.Integration.Tests.AotNativeRunTests -noColor
```

Используйте отдельную сессию PowerShell: переменные окружения действуют на последующие дочерние процессы.
Нативный runner использует invariant globalization, поэтому JIT-контроль должен использовать её тоже:
иначе формат десятичных чисел различается (`1.5` и `1,5`) даже при равных числовых результатах.
Каталог результатов содержит `native-run.log` и `oracle.md`. Контейнеры для этой проверки не нужны.

## JSON-колонки

Сторона маппинга JSON-колонки готова к нативной сборке: конвертер создаётся сгенерированным кодом,
без динамической инстанциации generic-типа. Сам JSON-документ сериализует `System.Text.Json`, и
обрезанному приложению нужно отдать контрактные метаданные, которые он не может построить рефлексией.
Объявите source-генерируемый контекст со всеми хранимыми типами модели — описание сущности, собранное
на компиляции, находит этот контекст и сериализует через его опции, поэтому во время работы ничего
настраивать не нужно:

```csharp
[JsonSerializable(typeof(Address))]
internal sealed partial class AppJsonContext : JsonSerializerContext;
```

Колонка со своими опциями сериализатора (`b.Property(x => x.Address).JsonColumn(o => o.Options = ...)`)
сохраняет их; контекст даёт контрактные метаданные, а не настройки. На обычном JIT-рантайме контекст не
нужен: тип, который не объявлен ни в одном контексте, сериализуется с опциями по умолчанию.

## Ограничения

- EF Core bridge (`nextorm.entityframeworkcore`) в нативную сборку пока не входит — для этого сценария
  оставайтесь на обычном JIT-рантайме.
- Результат-колонка типа tuple в ClickHouse, если типы элементов не зарегистрированы драйвером, не
  материализуется в нативной сборке. Выбирайте отдельные колонки через `tupleElement(...)` или
  получайте tuple как текст и разбирайте его на клиенте.
- Запросы вне перечисленной поверхности могут упасть при первом исполнении. Прогоните свой набор
  запросов на нативной сборке до релиза: анализаторы не видят сквозь динамический конвейер запросов,
  поэтому проверка — это нативный прогон.

## Производительность

Нативная публикация убирает JIT и холодный старт — на короткоживущих процессах это основной выигрыш:
старт и один небольшой запрос занимают десятки миллисекунд вместо почти секунды, а отчёт по базе
13 ГБ ниже отрабатывает за десятые доли секунды вместо одной-двух.

У этого выигрыша есть цена: без JIT выражения материализатора строк исполняются интерпретатором —
примерно вдвое дольше и в несколько раз больше аллокаций, чем у скомпилированного кода. Сборка снимает
большую часть сама: генератор покрывает все типы проекций, объявленные в вашей сборке — именованные
типы и record-DTO, а также анонимные типы — поэтому подготовленный запрос сохраняет обычную скорость и
в нативной сборке. На подготовленной команде в 500 строк по три колонки это 543 → 364 µs и
246 → 39 KB.

Например, для этих проекций не нужны атрибуты или регистрация:

```csharp
// без атрибута и без регистрации: покрывается автоматически
public sealed record OrderSummary(int Id, string? Customer, decimal Total);

var summaries = context.From<Order>()
    .Select(order => new OrderSummary(order.Id, order.Customer, order.Total))
    .ToList();

var rows = context.From<Order>().Select(order => new { order.Id, order.Customer }).ToList();
```

Потоковые терминалы этой цены не платят: `WriteCsv` и `WriteJson` не материализуют строки и пишут
scalar-колонки уже скомпилированным кодом в том числе в нативной сборке.

Для массовых выгрузок широких строк на AOT-рантайме интерпретация всё же заметна: такие задачи проще
оставить на JIT.

## Проверка на реальном приложении

`oc-report` — утилита отчётов по базе SQLite на 13 ГБ — публикуется нативно без правок исходников,
кроме `PublishAot=true`: бинарник 8.2 МБ, прогон 0.12 с, пик памяти 30 МБ.

## Если запрос падает

Создайте issue с минимальным воспроизводящим запросом, целевым RID, версией .NET SDK и выводом
`dotnet publish`. Нативный reproducer ценнее JIT-ового: часть ошибок проявляется только после
публикации.
