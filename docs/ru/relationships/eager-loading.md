# Жадная загрузка дочерних коллекций (`LoadWith`)

> Используйте `LoadWith`, когда нужны заказы вместе с их позициями. Он получает дочерние строки и
> заполняет ими коллекцию каждого заказа; ленивая загрузка не используется.

**Предварительные требования:** [Быстрый старт](../getting-started/02-quickstart.md) · [Соединения](../guide/04-joins.md) · [Подзапросы](../guide/07-subqueries.md)

Чтобы загрузить каждый подходящий заказ вместе с позициями, укажите ключ родителя и ключ ребёнка:

```csharp
var orders = ctx.From<Order>()
    .Where(o => o.CustomerId == customerId)
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId)
    .OrderBy(o => o.Id)
    .ToList();
```

Здесь используется split-режим по умолчанию. Запрос получает подходящие заказы, затем `LoadWith`
пакетно выбирает их позиции и добавляет каждую позицию к заказу, у которого `Id` совпадает с
`OrderItem.OrderId`. Число дочерних запросов зависит от набора ключей заказов, а не от количества заказов.

## Выберите стратегию загрузки

Эта таблица поможет выбрать, как nextorm получает строки родителей и детей:

| Стратегия | Когда выбрать | Что происходит |
|---|---|---|
| `SplitQuery` (по умолчанию) | Нужно избежать большого денормализованного соединения или использовать форму дочернего запроса, доступную только в split-режиме. | Родители запрашиваются один раз, затем дочерние строки — пакетами ключей (не более 1000 ключей и 2000 параметров ключей в пакете). |
| `SingleQuery` | Важно выполнить чтение за одно обращение к базе данных, а дочерний запрос укладывается в ограничения single-query ниже. | Родители и объявленные коллекции выбираются вместе через `LEFT JOIN`. |
| `Auto` | Нужен консервативный автоматический выбор. | Для обычной загрузки выбирает `SplitQuery`; стоимость не оценивает и при ошибке на другую стратегию не переключается. |
| Режим контекста | Нужна одна стратегия по умолчанию для запросов без явного режима. | Задаёт запасной режим только для этого контекста; режим запроса имеет приоритет. |

`Correlated` зарезервирован и отвергается. `Take`/`Skip` дочернего запроса применяется отдельно к
каждому родителю (см. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md)).
Дочерний запрос может объявить ещё один `LoadWith`, чтобы загрузить конечный вложенный граф; для всего
графа действует одна стратегия.

## Обзор

nextorm никогда не выводит связи из соглашений об именовании. Объявите каждую связь `LoadWith` либо
явными селекторами ключей — коллекцией родителя, фабрикой дочернего запроса и ключами обеих сторон, —
либо через уже заданные метаданные связи (см. [Форма с объявленными метаданными](#форма-с-объявленными-метаданными)).
Дочерний запрос — обычный `EntityBuilder<TChild>` и может объявить следующий `LoadWith`, образуя конечный
граф любой глубины. Связь принадлежит запросу, а не метаданным сущности.

Однозапросная альтернатива на объявленных
метаданных — [`JoinInto`](relationships.md). Режим `EagerLoadMode.SingleQuery` загружает родителей и
детей за одно обращение к базе данных; вложенные графы работают в обоих режимах там, где их поддерживает
провайдер (см. [Вложенные графы](#вложенные-графы-второй-уровень-и-глубже)).

## Сигнатура

```csharp
public EntityBuilder<TEntity> LoadWith<TChild, TKey>(
    Expression<Func<TEntity, ICollection<TChild>>> collection,
    Func<IDataContext, EntityBuilder<TChild>> childQuery,
    Expression<Func<TEntity, TKey>> parentKey,
    Expression<Func<TChild, TKey>> childKey,
    EagerLoadMode mode = EagerLoadMode.Default)
    where TKey : notnull;
```

- `collection` — член [`ICollection<TChild>`](xref:System.Collections.Generic.ICollection`1) на стороне родителя, который нужно заполнить.
- `childQuery` — строит дочерний запрос из контекста данных, которому принадлежит родительский запрос.
- `parentKey` / `childKey` — селекторы, по которым определяется, какие дочерние записи принадлежат какому родителю.
- `mode` — режим жадной загрузки для всего билдера (см. [Выбор режима](#выбор-режима)); `EagerLoadMode.Default` наследует текущий выбор билдера, а при его отсутствии — context-wide default (`DataContextBuilder.UseEagerLoadMode`, по умолчанию `SplitQuery`).
- `TKey` должен быть не-nullable типом (`where TKey : notnull`), например `int` или `string`. Значение ключа `null`, встреченное в рантайме, пропускается и никогда не сопоставляется.

`LoadWith` возвращает **копию** билдера с объявлением, поэтому исходный билдер не меняется, а несколько загрузок можно объединять в цепочку:

Как и любой модификатор билдера, `LoadWith` требует, чтобы generic-тип ключа был известен в точке вызова; если селектор допускает неявное преобразование, укажите тип ключа явно или приведите тела обоих селекторов к одному типу.

### Форма с объявленными метаданными

Если связь уже объявлена, `LoadWith` читает её вместо явных селекторов ключей. Четыре перегрузки покрывают обе формы навигации, каждая — с дочерним запросом и без него:

```csharp
public EntityBuilder<TEntity> LoadWith<TChild>(
    Expression<Func<TEntity, ICollection<TChild>>> collection,
    EagerLoadMode mode = EagerLoadMode.Default);

public EntityBuilder<TEntity> LoadWith<TChild>(
    Expression<Func<TEntity, ICollection<TChild>>> collection,
    Func<IDataContext, EntityBuilder<TChild>> childQuery,
    EagerLoadMode mode = EagerLoadMode.Default);

public EntityBuilder<TEntity> LoadWith<TChild>(
    Expression<Func<TEntity, TChild?>> reference,
    EagerLoadMode mode = EagerLoadMode.Default) where TChild : class;

public EntityBuilder<TEntity> LoadWith<TChild>(
    Expression<Func<TEntity, TChild?>> reference,
    Func<IDataContext, EntityBuilder<TChild>> childQuery,
    EagerLoadMode mode = EagerLoadMode.Default) where TChild : class;
```

```csharp
var orders = ctx.From<Order>()
    .Where(o => o.CustomerId == customerId)
    .LoadWith(o => o.Items)                                   // объявленная 1:N
    .LoadWith(o => o.Customer, c => c.From<Customer>())       // объявленная N:1
    .ToList();
```

- **Только объявленные связи.** Навигация должна быть объявлена через `HasMany`, `HasOne`, `HasOneToOne`, `HasManyThrough` или `[Relationship]` (см. [Связи](relationships.md)). nextorm не выводит связь из соглашения об именовании, не сопоставляет ключевые столбцы по имени и никогда не откатывается к первому компоненту составного ключа.
- **Маршрут определяется формой навигации.** Коллекционные перегрузки загружают коллекционные кардинальности (one-to-many и many-to-many), ссылочные — ссылочные (many-to-one и one-to-one). Коллекционная навигация никогда не загружается ссылочным маршрутом: несовпадение кардинальности и маршрута бросает [`NotSupportedException`](xref:System.NotSupportedException) в точке вызова, и то же происходит в обратную сторону.
- **Упорядоченные компоненты сопоставляются позиционно.** Составной ключ — это упорядоченные списки компонентов связи: родительский компонент в позиции `i` сопоставляется с дочерним компонентом в позиции `i` в порядке объявления (а для ключа по умолчанию — в порядке метаданных сущности).
- **Короткая форма использует обычный источник контекста.** Без `childQuery` дочерним запросом служит обычный источник `From<TChild>()` контекста, поэтому действуют маппинг и глобальные фильтры связанного типа и никакой побочный источник не вводится. Перегрузка с `childQuery` позволяет ребёнку нести собственные `Where`, `OrderBy` или страницу на родителя.
- **Всё остальное общее.** Режимы, пакетная обработка в split, объединение запросов в single-query, правило назначения, порядок, вложенные графы и граница терминалов — те же, что описаны на этой странице для формы с явными ключами. Обе формы используют одну идентичность плана: объявление, которое выбирает ровно объявленную связь 1:N, попадает в ту же закэшированную запись плана из любой формы.

Повторное объявление одной и той же навигации на одном билдере бросает [`InvalidOperationException`](xref:System.InvalidOperationException) в обеих формах, а защиты от циклов и конфликта вложенных режимов действуют без изменений.

### Объявленные связи: кардинальность, ключи и ограничения

| Объявленная кардинальность | Чем объявляется | Маршрут `LoadWith` |
|---|---|---|
| one-to-many | `HasMany` / `[Relationship]` на стороне коллекции | коллекционный |
| many-to-many | `HasManyThrough` с явной таблицей связи | коллекционный |
| many-to-one | `HasOne` / `[Relationship]` на стороне ссылки | ссылочный |
| one-to-one | `HasOneToOne` | ссылочный |

**Дочерние запросы и пакетная обработка.** Дочерний запрос сопоставляет все объявленные компоненты ключа: для каждого компонента используется свой предикат `IN`, а компоненты с одинаковой позицией в ключах родителя и ребёнка сопоставляются друг с другом.

Чтобы не превышать допустимое число параметров, ключи делятся на пакеты: в каждом не более 1000 ключей и 2000 параметров ключей. Поэтому однокомпонентный ключ позволяет обработать 1000 родителей за пакет, а составной ключ требует меньших пакетов. Родительский запрос выполняется один раз, а число дочерних запросов зависит от количества ключей, а не от числа родителей: N+1 не возникает.

`SingleQuery` выполняет ту же связь за одно обращение к базе данных, используя `LEFT JOIN`.

**Постраничная выборка на родителя.** `Limit`/`Offset`/`Page` дочернего запроса поддерживается для коллекционной навигации с ключом из одного компонента. В split-режиме дочерние строки ранжируются в отдельном запросе; в single-query ранжированный источник включается в общий SQL-запрос. В последнем случае ребёнок не должен объявлять собственный `LoadWith`.

**Кардинальность ссылки.** Ссылочная навигация назначает не более одной связанной записи на родителя: отсутствие совпадения назначает `null`, одна различающаяся полная идентичность назначается, а **более одной различающейся идентичности для одного родителя** бросает [`InvalidOperationException`](xref:System.InvalidOperationException) до изменения любого родителя — повторяющиеся физические записи с одной идентичностью допустимы (назначается первая). Навигация только для чтения загружается, лишь когда её текущее значение уже является найденной записью; иначе она падает закрыто.

**Вхождения many-to-many.** Таблица связи читается отдельным дочерним запросом в split-режиме или через производное link-соединение в single-query. Каждая допустимая связка добавляет один элемент: повторные связки остаются разными, а связка с `null` в компоненте родителя или ребёнка не добавляет элемент. Две коллекции по одной таблице связи группируются независимо.

**Терминалы.** Форму с метаданными обслуживают те же четыре терминала, которые заполняют коллекции (`ToList`, `ToListAsync`, `ToArray`, `ToArrayAsync`); `Any`/`Count` остаются скалярными, а любой другой терминал вычисляет только родителя. Вложенный граф, объявленный дочерним запросом, следует неизменному контракту [Вложенные графы](#вложенные-графы-второй-уровень-и-глубже).

Каждый из перечисленных случаев отвергается с [`NotSupportedException`](xref:System.NotSupportedException) до генерации любого SQL и до вставки записи в план-кэш, а не отбрасывается молча:

- постраничная выборка на родителя (`Limit`/`Offset`/`Page`) у ребёнка связи с **составным ключом**: разделу на родителя нужен один компонент ключа;
- страница на родителя у **ссылочного** ребёнка или у ребёнка **many-to-many**: top-N требует прямого раздела по родителю, которого не даёт ни одна связанная запись, ни таблица связи;
- вложенный граф под **ссылочной** навигацией или навигацией **many-to-many** в режиме `SingleQuery` (split его поддерживает): найденная ссылочная запись или link-строка уже занимает элемент проекции, который понадобился бы вложенному графу;
- форма ребёнка, которую `SingleQuery` не умеет сворачивать, — всё, что выходит за собственные `Where`, `OrderBy` и страницу по одному компоненту (см. [Режим single-query](#режим-single-query-eagerloadmodesinglequery));
- больше дочерних коллекций, чем позволяет предел арности проекции;
- провайдер **in-memory**: форма с объявленными метаданными работает только на SQL и отвергается при подготовке запроса для родителей — до выполнения SQL и записи в план-кэш (форма с явными ключами сохраняет свою поддержку in-memory);
- повторное объявление одной навигации и циклический граф.

## Выбор режима

Аргумент `mode` выбирает, как загружаются объявленные коллекции, через публичный enum [`EagerLoadMode`](xref:NextORM.Core.EagerLoadMode). В таблице указаны числовые значения и поведение каждого режима:

| Член | Значение | Смысл |
|---|---|---|
| `EagerLoadMode.Default` | `0` | Явный выбор отсутствует: наследуется режим, уже активный на билдере, а при его отсутствии — context default ниже. |
| `EagerLoadMode.SplitQuery` | `1` | Принудительный split-режим для всего билдера. |
| `EagerLoadMode.SingleQuery` | `2` | Принудительный single-query режим для всего билдера. |
| `EagerLoadMode.Correlated` | `3` | Коррелированная загрузка на родителя. Распознаётся, но **не поддерживается** в этом релизе; запрос, который к ней сводится, отвергается. |
| `EagerLoadMode.Auto` | `4` | Автоматический выбор, разрешаемый один раз консервативным правилом ниже. |

Режим принадлежит **всему билдеру**, а не отдельному объявлению, и один разрешённый режим покрывает весь вложенный граф (каждый уровень, объявленный его дочерними запросами):

- Явный режим действует на каждую коллекцию, объявленную на билдере, включая объявленную раньше, пока режим ещё был `Default`.
- Последующий `LoadWith(..., EagerLoadMode.Default)` (или опущенный аргумент) наследует текущий режим и никогда его не сбрасывает.
- Повтор одного и того же явного режима разрешён.
- Смешение двух разных явных режимов — сначала `SingleQuery`, затем `SplitQuery` или наоборот — бросает [`NotSupportedException`](xref:System.NotSupportedException): для одной коллекции нельзя выполнить денормализованное соединение, а для другой — отдельный дочерний запрос.
- Значение, отличное от пяти определённых членов enum, бросает [`ArgumentOutOfRangeException`](xref:System.ArgumentOutOfRangeException) с `ParamName == "mode"`, а исходный билдер остаётся неизменным.

Режим разрешается в момент вызова `LoadWith`; сама спецификация загрузки не меняется, поэтому смена режима никогда не меняет [правило назначения](#правило-назначения) или [гарантии порядка](#порядок-и-дедупликация).

### Context-wide default

[`DataContextBuilder.UseEagerLoadMode(EagerLoadMode)`](xref:NextORM.Core.DataContextBuilder.UseEagerLoadMode(NextORM.Core.EagerLoadMode)) задаёт context-wide default для коллекций `LoadWith`, чей запрос не объявляет явный режим. По умолчанию это `EagerLoadMode.SplitQuery`, этот режим работает так:

```csharp
var builder = new DataContextBuilder()
    .UseSqlite(connection)
    .UseEagerLoadMode(EagerLoadMode.SingleQuery);
using var dataContext = builder.CreateDataContext();
```

- Значение default должно быть одной из четырёх конкретных стратегий — `SplitQuery`, `SingleQuery`, `Correlated` или `Auto`. `EagerLoadMode.Default` отвергается с [`ArgumentOutOfRangeException`](xref:System.ArgumentOutOfRangeException): это sentinel наследования, а не настройка контекста, и его нельзя применять рекурсивно.
- Настройка контекста никогда не меняет статическое/глобальное значение; каждый контекст несёт собственную настройку, доступную только для чтения как `EagerLoadMode` на [`IDataContext`](xref:NextORM.Core.IDataContext) / [`DataContext`](xref:NextORM.Core.DataContext).
- Default разрешается один раз, до генерации любого SQL, а разрешённое значение входит в ключ план-кэша, поэтому два запроса с разными стратегиями никогда не делят закэшированный план.

### Приоритет

Эффективная стратегия — `query override ?? context default`: явный `LoadWith(..., mode)` выигрывает у context default, а при отсутствии явного выбора применяется context default. Внутри билдера `EagerLoadMode.Default` продолжает наследовать режим, выбранный более ранним `LoadWith`.

### Консервативный `Auto`

`Auto` — **консервативный диспетчер**, а не оптимизатор по стоимости. Он никогда не угадывает возможности провайдера и никогда не повторяет упавшее выполнение другой стратегией:

| Запрошенная операция | Поведение в этом релизе |
|---|---|
| Обычная поддерживаемая `LoadWith`, `Auto` | Сводится к `SplitQuery`. |
| Обычная `LoadWith`, явные `SplitQuery`/`SingleQuery` | Существующая split/single реализация и guard'ы. |
| `LoadWith`, явный `Correlated` | Отвергается до генерации любого SQL и до записи в план-кэш. |
| Запрос, требующий per-parent top-N (дочерний `Limit`/`Offset`/`Page`) | Применяется на каждого родителя через ранжированный дочерний источник, батчируемый как любой split-запрос; `Auto` никогда не переинтерпретирует его как глобальный лимит на детей или неограниченную загрузку (см. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md)). |
| `JoinInto` | Фиксированный single-query; не зависит от context default (см. [Метаданные связей и `JoinInto`](#метаданные-связей-и-joininto)). |
| Нет жадных загрузок | Нет диспетчеризации eager-load и нет мутации команды, специфичной для eager-load. |

`Auto` выбирает `SingleQuery`, только когда его запросили явно; автоматический выбор single, произвольное построение `APPLY`/`LATERAL` и угадывание возможностей провайдера не вводятся.

### `Correlated` и постраничная выборка на родителя

`EagerLoadMode.Correlated` не имеет реализованного пути выполнения в этом релизе. Режим распознаётся, но отвергается с [`NotSupportedException`](xref:System.NotSupportedException) **во время подготовки — до генерации SQL и до вставки записи в план**. Поэтому запрос для родителей не выполняется, а кэш планов не меняется. Значение enum зарезервировано для отдельно отслеживаемой работы над коррелированной выборкой.

Отказ происходит на **любом** терминале, в том числе на не-list терминалах ниже, которые вычисляют только родителя. Такой терминал сначала проверяет набор `LoadWith`: явный `Correlated` отвергается до построения родительского запроса, а не молча отбрасывается. При этом не-list терминал по-прежнему не заполняет коллекцию.

Собственные `Limit`/`Offset`/`Page` дочернего запроса **не** отвергаются: оба режима — `SplitQuery` и `SingleQuery` — применяют страницу отдельно к каждому родителю через секционированный источник `row_number()`. Фильтрация и сортировка дочерних строк выполняются до постраничной выборки; родительские границы действуют независимо, а родители без детей сохраняются.

`Auto` выполняет такую загрузку через split-диспетчер. Он не превращает `Limit`/`Offset`/`Page` в общий лимит на всех детей и не интерпретирует постраничную загрузку как загрузку без ограничений.

Постраничная выборка на родителя — возможность `LoadWith`: `JoinInto` отвергает её до выполнения. Провайдер in-memory также отклоняет постраничный дочерний запрос без перехода к клиентской обработке — в нём нет SQL-окон. Непейджированная жадная загрузка в in-memory не меняется. Подробнее см. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md).

## Семантика split-query

Объявление **не** входит в запрос для родителей. После получения родительских строк:

1. Различные непустые родительские ключи собираются **в порядке родителей** и делятся на пакеты не более чем по **1000** ключей.
2. Для каждого пакета выполняется отдельный дочерний запрос с `WHERE childKey IN (<ключи пакета>)` — без `JOIN` и без отдельного запроса для каждого родителя.
3. Дочерние записи группируются по `childKey` и добавляются родителям с совпадающим `parentKey`.

Поэтому при не более чем 1000 различных родительских ключей выполняются ровно **два обращения к базе данных**: одно для родителей и одно для детей. Для каждого дополнительного пакета ключей выполняется ещё один дочерний запрос; запрос для родителей по-прежнему выполняется один раз. N+1 нет: число дочерних запросов зависит от размера набора ключей, а не от числа родителей.

```sql
-- запрос для родителей
select id, name
 from order

-- дочерний запрос (один на пакет не более чем из 1000 различных родительских ключей)
select id, order_id, name
 from order_item where order_id in (@k0, @k1, @k2)
```

Предикат пакета — обычный список `IN`, поэтому он участвует в кэше планов и привязке параметров провайдера так же, как `Contains` по захваченной коллекции.

При отмене `ToListAsync`/`ToArrayAsync` токен проверяется между пакетами ключей и между несколькими объявлениями `LoadWith`, поэтому отменённый вызов прекращает выполнять следующие дочерние запросы.

## Режим single-query (`EagerLoadMode.SingleQuery`)

По умолчанию `LoadWith` использует split-форму выше: родительский запрос и отдельный дочерний запрос для каждого пакета ключей требуют двух или более обращений к базе данных. Передайте `EagerLoadMode.SingleQuery` последним аргументом `LoadWith` (режим действует на весь билдер) или задайте режим контекста через `UseEagerLoadMode(EagerLoadMode.SingleQuery)`, чтобы получить родителей и все объявленные коллекции **за одно обращение к базе данных**:

```csharp
var orders = ctx.From<Order>()
    .Where(o => o.CustomerId == customerId)
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId,
        EagerLoadMode.SingleQuery)
    .ToList();
```

Тогда SQL-запрос объединяет родителя и детей через `LEFT JOIN`:

```sql
select t1.id, t1.name, t2.id, t2.order_id, t2.name
 from order as t1
 left join order_item as t2 on t1.id = t2.order_id
```

Собственный `Where` дочернего запроса встраивается в `ON` соединения, поэтому фильтрует дочерние записи, не отбрасывая родителей без детей:

```sql
select t1.id, t1.name, t2.id, t2.order_id, t2.name
 from order as t1
 left join order_item as t2 on t1.id = t2.order_id and t2.active
```

- **Одно обращение к базе данных, без пакетной обработки ключей.** Источник родителя и каждый объявленный дочерний источник объединяются через `LEFT JOIN`. Списка `IN` и ограничения на размер пакета нет, поэтому за одно обращение можно получить любое число родителей, включая более 1000 различных ключей; автоматического перехода в split-режим нет.
- **Встраивается только собственный `Where` дочернего запроса.** Дочернее условие, например `c => c.From<OrderItem>().Where(i => i.Active)`, включается в предикат `ON` соединения, поэтому фильтрует дочерние записи, не отбрасывая родителей без детей.
### Ограничения дочернего запроса в режиме `SingleQuery`

Дочерний запрос с `Limit`/`Offset`/`Page` (с собственным `OrderBy` или без него) ранжирует строки через секционированный источник `row_number()` и применяет страницу отдельно к каждому родителю (см. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md)).

Обычный `OrderBy` без `Limit`/`Offset`/`Page` задать в `SingleQuery` нельзя: он задаёт порядок детей для каждого родителя, а не порядок общей денормализованной выборки. Исключение — форма с объявленными метаданными ([Форма с объявленными метаданными](#форма-с-объявленными-метаданными)): она применяет собственный `OrderBy` ребёнка к порядку его элементов. Остальные ограничения действуют и для этой формы.

`SingleQuery` также отвергает запросы с `Distinct`, `GroupBy`, `Having`, `DistinctOn`, `LimitBy`, соединениями (`Join`/`LeftJoin`/`SemiJoin`/`AntiJoin`/…), `Final`, `PreWhere`, `ArrayJoin`, `TableSample`, `Sample`, `ForSystemTime`, `ForUpdate`/`ForShare`, `Window`, `Settings`, CTE, table/index hint или производным источником (`As`). При материализации такие формы вызывают [`NotSupportedException`](xref:System.NotSupportedException).

Split-режим поддерживает перечисленные формы. Выберите его, если дочернему запросу нужна композиция сложнее собственного `Where`. Формы ClickHouse из этого списка (`LimitBy`, `Final`, `PreWhere`, `ArrayJoin`, `Sample`, `Settings`) доступны как методы-расширения из `NextORM.ClickHouse` (`using NextORM.ClickHouse;`).

Действуют и другие ограничения режима `SingleQuery`:

- **Области фильтров родителя и ребёнка объединяются, одинаково в split- и single-query режиме.** Эффективная область ребёнка — это всегда объединение его собственной области `IgnoreFilters` и родительской. `IgnoreFilters()` на родителе отключает и фильтры объявленных детей (область «всё» поглощает собственную область ребёнка), а селективный `IgnoreFilters(...)` родителя доходит и до детей. И наоборот: `IgnoreFilters(...)` внутри дочернего запроса отключает только фильтры этого ребёнка, а родительские продолжают действовать. То же правило действует и при загрузке стандартной split-формой, и при `EagerLoadMode.SingleQuery`.
- **Тип родителя должен объявлять mapped-ключ.** Денормализованные строки дедуплицируются по этому ключу, поэтому родитель без ключа бросает [`NotSupportedException`](xref:System.NotSupportedException) с указанием настроить ключ или использовать split-режим, которому ключ не нужен. Строки с одинаковым mapped-ключом схлопываются в одного родителя; split-режим сохраняет их раздельно.
- **Тип ключа должен поддерживать равенство по значению.** Предикат соединения строится через оператор равенства, поэтому тип ключа без него — например, структура без перегрузки `==` или ссылочный тип, `==` которого выродился бы в сравнение ссылок, — бросает [`NotSupportedException`](xref:System.NotSupportedException). Split-режим сравнивает ключи стандартным компаратором равенства и работает с такими типами.
- **Вложенные графы соединяются по уровню.** Дочерний запрос, который сам объявляет `LoadWith`, планируется как вложенный граф: билдер выдаёт по одному `LEFT JOIN` на узел и собирает все уровни из одного result set (см. [Вложенные графы](#вложенные-графы-второй-уровень-и-глубже)). На каждом уровне сворачивается только собственный `Where` ребёнка, а узел, который одновременно объявляет детей и пейджится на родителя, отвергается.
- **Правила назначения и порядка сохраняются.** В обоих режимах механизм загрузки удаляет повторы родителей и заполняет коллекции по тем же правилам (см. [Правило назначения](#правило-назначения) и [Порядок и дедупликация](#порядок-и-дедупликация)).
- **Только один обычный источник сущности.** `EagerLoadMode.SingleQuery` нельзя комбинировать с другими соединениями на одном билдере; вызов на запросе, уже несущем обычное (не `JoinInto`) соединение, бросает [`NotSupportedException`](xref:System.NotSupportedException).
- **Дальнейшая композиция запрещена.** После `LoadWith` в режиме single-query нельзя вызывать `Select` или `As`: проекция не поддерживает eager loading. Нельзя также добавлять `Join`/`Apply`: присоединённый билдер не хранит сведения о загрузке и её режиме. Каждый такой вызов бросает [`NotSupportedException`](xref:System.NotSupportedException), а не возвращает сущности с пустыми коллекциями. Сначала получите результат через `ToList` или `ToArray`.

Split остаётся режимом по умолчанию: выбирайте его, когда пакетные дочерние результаты меньше денормализованного результата соединения. Используйте `EagerLoadMode.SingleQuery`, когда важнее получить данные за одно обращение к базе, а ограничения этой стратегии подходят вашему дочернему запросу.

## Вложенные графы (второй уровень и глубже)

Дочерний запрос — обычный `EntityBuilder<TChild>`, поэтому в нём можно объявить следующий `LoadWith`. Так загружается конечный граф любой глубины: `Root → Mids → Leaves → Tips …`.

На каждом уровне объявление по-прежнему указывает коллекцию родителя, фабрику дочернего запроса и два селектора ключей. Для всех уровней сохраняются те же правила назначения, порядок и обработка ключей `null`.

```csharp
var roots = ctx.From<Root>()
    .LoadWith(
        r => r.Mids,
        c => c.From<Mid>()
            .OrderBy(m => m.SortKey)
            .LoadWith(m => m.Leaves, l => l.From<Leaf>().OrderByDescending(x => x.SortKey), m => m.Id, l => l.MidId),
        r => r.Id,
        m => m.RootId)
    .ToList();
```

В режиме split по умолчанию запрос для родителей выполняется один раз. На каждом дочернем уровне отдельный запрос выполняется для каждого пакета ключей (не более 1000): первый уровень использует ключи корней, следующий — различные ключи `Mid`, полученные на первом уровне. Каждый уровень делит ключи на пакеты независимо:

```sql
-- запрос для родителей
select id, name
 from root

-- дочерний запрос первого уровня (один на пакет не более чем из 1000 ключей корней)
select id, root_id, sort_key, name
 from mid where root_id in (@k0, @k1)
 order by sort_key

-- дочерний запрос второго уровня (один на пакет не более чем из 1000 ключей первого уровня)
select id, mid_id, sort_key, name
 from leaf where mid_id in (@k0, @k1, @k2)
 order by sort_key desc
```

С `EagerLoadMode.SingleQuery` весь граф загружается за одно обращение к базе данных; SQL включает `LEFT JOIN` для каждого узла:

```sql
select t1.id, t1.name, t2.id, t2.root_id, t2.sort_key, t2.name, t3.id, t3.mid_id, t3.sort_key, t3.name
 from root as t1
 left join mid as t2 on t1.id = t2.root_id
 left join leaf as t3 on t2.id = t3.mid_id
```

В показанном виде фрагмент работает только в split-режиме: single-query объединяет только собственный `Where` каждого узла, поэтому два вызова `OrderBy` приведут к [`NotSupportedException`](xref:System.NotSupportedException) с указанием `OrderBy`. Уберите сортировку (или оставьте режим split по умолчанию), чтобы выполнить граф за одно обращение к базе данных.

Для всего графа действует следующий контракт:

- **Один режим на весь граф.** Стратегия, разрешённая для корня (`SplitQuery`, `SingleQuery`, context default или консервативный `Auto`), применяется к каждому уровню. Вложенное объявление не может запросить другой явный режим: `LoadWith(..., EagerLoadMode.X)` у ребёнка, чей разрешённый режим отличается от режима графа, бросает [`NotSupportedException`](xref:System.NotSupportedException) (`... mixes modes ...`). `EagerLoadMode.Default` у ребёнка просто наследует режим графа.
- **Порядок/top-N на каждом уровне.** Дочерний запрос каждого уровня сохраняет собственный эффективный `OrderBy`, а его собственные `Take`/`Skip` на родителя применяются внутри родителей этого уровня (split-режим, SQL-провайдеры). Порядок первого уровня не меняется, а два соседних уровня могут упорядочиваться независимо.
- **Идентичность по предкам.** Потомки группируются по **ancestor-composite идентичности** — ключ первого уровня плюс ключ второго уровня плюс … — поэтому один и тот же ключ ребёнка под двумя разными предками собирается под каждым предком независимо. Null-ключ на любом уровне никогда не сопоставляется и не падает, а пустой промежуточный результат просто не загружает потомков.
- **Split учитывает любую форму дочернего запроса на каждом уровне** так же, как на первом; **single-query** сворачивает в `LEFT JOIN` только собственный `Where` каждого узла.

### Матрица провайдеров и фронтендов

| Вложенный граф / форма | Split (`SplitQuery`, `Auto`) | Single-query (`EagerLoadMode.SingleQuery`) |
|---|---|---|
| Вложенный `LoadWith` (глубина 2+), у ребёнка только `Where` | да — каждый уровень, все SQL-провайдеры и in-memory | да — по одному `LEFT JOIN` на узел, все SQL-провайдеры и in-memory |
| Вложенный `OrderBy` / `Distinct` / `GroupBy` / соединения / прочие формы, отличные от `Where` | да — каждый уровень | отвергается fail-closed (на каждом уровне сворачивается только собственный `Where` ребёнка) |
| `Take`/`Skip` на родителя на каждом уровне (`Limit`/`Offset`/`Page`) | да на каждом уровне у SQL-провайдеров; in-memory-провайдер отвергает пейджированный дочерний запрос (нет SQL-окна) | отвергается, когда пейджированный узел ещё и объявляет детей — у ранжированного ребёнка нет пер-уровневого рендеринга |

SQL-провайдеры (SQLite, PostgreSQL, SQL Server, MySQL/MariaDB, ClickHouse) выполняют вложенную загрузку в обоих режимах. Провайдер in-memory загружает вложенные графы для детей без постраничного вывода и по-прежнему отклоняет запросы с постраничной выборкой для ребёнка. Тот же контракт соблюдается в сочетании с [`JoinInto`](relationships.md): загружаются и присоединённая коллекция, и более глубокие уровни. А проекция сущности из неявной навигации (`Select(n => new { n.Id, Parent = n.Parent })`) вместе с вложенным графом `LoadWith` до выполнения бросает [`NotSupportedException`](xref:System.NotSupportedException), а не теряет вложенный граф молча.

### Fail-closed формы

Каждый невыразимый вложенный граф отвергается до генерации любого SQL и до вставки записи в план-кэш, а не молча теряет потомка или откатывается к другой стратегии:

- **неподдерживаемая форма ребёнка на любом уровне** (single-query): вложенный ребёнок, который не сводится к `Where` — `OrderBy`, `Distinct`, `GroupBy`, `Having`, `DistinctOn`, соединение, clause уровня таблицы или производный (`As`) источник, — бросает [`NotSupportedException`](xref:System.NotSupportedException) с именем формы (см. [Режим single-query](#режим-single-query-eagerloadmodesinglequery));
- **вложенный per-parent пейджинг** (single-query): узел, который одновременно объявляет детей и пейджится на родителя, бросает `NotSupportedException` (`Limit/Offset/Page`); split поддерживает пейджинг на каждом уровне у SQL-провайдеров;
- **переполнение арности проекции**: сведение графа в один денормализованный SQL-запрос с более чем семью дочерними коллекциями (предел арности [`Projection<T1..T8>`](relationships.md#один-round-trip)) бросает `NotSupportedException`; объявите более мелкий граф или используйте split-режим;
- **конфликт вложенного режима**: ребёнок, запрашивающий явный режим, отличный от режима графа, бросает `NotSupportedException` (`... mixes modes ...`);
- **циклы**: объявление, чья ancestor-composite идентичность повторяется, — самоссылающаяся сущность или фабрика ребёнка, рекурсивно возвращающая саму себя, — детерминированно бросает `NotSupportedException`: требуется конечный ацикличный граф, а не ограничение глубины;
- **пейджированный дочерний запрос в in-memory**: in-memory не поддерживает постраничную загрузку дочерних строк, но поддерживает вложенную загрузку без постраничного ограничения.
- **форма с объявленными метаданными на провайдере in-memory**: перегрузки `LoadWith` по метаданным работают только на SQL и отвергаются при построении родительской команды — до любой команды, SQL и записи в план-кэш и без изменения флага кэша контекста; форма с явными ключами сохраняет описанную выше поддержку in-memory.

## Правило назначения

Для каждого родителя загрузчик выбирает целевую коллекцию:

| Текущее значение `collection` | Член доступен для записи | Поведение |
|---|---|---|
| не null | любой | очищается и заполняется заново |
| `null` | да | назначается новый список |
| `null` | нет (read-only) | [`NotSupportedException`](xref:System.NotSupportedException) |

Read-only коллекция поддерживается, если она инициализирована пустой коллекцией и никогда не переприсваивается:

```csharp
public sealed class Order
{
    public int Id { get; set; }
    public ICollection<OrderItem> Items { get; } = new List<OrderItem>();
}
```

Read-only член не отображается на колонку БД, поэтому его инициализация не влияет на родительский `SELECT`.

## Порядок и дедупликация

- **Порядок родителей сохраняется.** Дочерние записи назначаются родителям в том порядке, в котором их вернул родительский запрос; загрузчик никогда не переупорядочивает родителей.
- **Порядок дочерних записей следует за дочерним запросом.** Дочерние записи сохраняют порядок, заданный запросом; добавьте `OrderBy` в `childQuery`, если порядок важен.
- **Одинаковые родительские ключи делят данные (split).** Два родителя с одинаковым ключом получают коллекции с одними и теми же дочерними записями (у каждого родителя свой экземпляр коллекции). В single-query режиме mapped-ключ родителя служит идентичностью дедупликации, поэтому строки с одинаковым ключом схлопываются в одного родителя — используйте split, когда такие строки должны остаться раздельными.
- **Несовпавшие дочерние записи игнорируются.** Дочерняя запись, чей ключ не совпал ни с одним родителем, не назначается, а родитель, у которого нет дочерних записей, получает пустую коллекцию.
- **Null-ключи никогда не сопоставляются.** Родительский или дочерний ключ, равный `null` в рантайме, пропускается; он никогда не ищется и не ломает группировку.

## Повторные объявления

Член коллекции можно объявить **только один раз** на запрос. Повторный вызов `LoadWith` для того же члена бросает [`InvalidOperationException`](xref:System.InvalidOperationException): два объявления выполнили бы два дочерних запроса для одной коллекции, и позднее присваивание отбросило бы раннюю загрузку. Объявляйте каждый член не более одного раза и используйте разные члены для загрузки нескольких коллекций:

```csharp
ctx.From<Order>()
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId)
    .LoadWith(o => o.Payments, c => c.From<Payment>(), o => o.Id, p => p.OrderId); // другой член
```

## Граница терминалов

Спецификация загрузки учитывается **только** четырьмя терминалами, которые заполняют коллекции:

- [`ToList()`](xref:NextORM.Core.EntityBuilderExtensions.ToList``1(NextORM.Core.EntityBuilder{``0},System.ReadOnlySpan{System.Object})) и [`ToListAsync()`](xref:NextORM.Core.EntityBuilderExtensions.ToListAsync``1(NextORM.Core.EntityBuilder{``0},System.Object[])).
- `ToArray()` и `ToArrayAsync()`.

Они выполняют родительский запрос и split-запросы для детей либо загружают родителей и детей за одно обращение к базе данных с `EagerLoadMode.SingleQuery`. Затем строки связываются с родителями и заполняют коллекции.

Любой другой терминал вычисляет **только** родительский запрос и не выполняет eager loading; он не выдаёт ни дочерний запрос, ни запрос загрузки, поэтому коллекции сохраняют исходное значение (обычно пустое):

- `ToHashSet` / `ToHashSetAsync` и `ToDictionary` / `ToDictionaryAsync`.
- `First` / `FirstAsync` и `FirstOrDefault` / `FirstOrDefaultAsync`.
- `Single` / `SingleAsync` и `SingleOrDefault` / `SingleOrDefaultAsync`.
- `ToEnumerable` и `ToAsyncEnumerable`.
- `ToCommand` и любой полученный из него `QueryCommand<T>`.

`Any` / `AnyAsync` и `Count` / `CountAsync` — **скалярные** терминалы: они возвращают одно значение и тоже никогда не выполняют eager loading. `ToCommand()` намеренно игнорирует спецификацию: так дочерний запрос выполняется без рекурсивного вызова загрузчика родителя. Если нужно заполнить коллекции, получите родителей одним из четырёх терминалов, которые перечислены выше.

Не-list терминал всё равно проверяет набор `LoadWith` перед построением команды только для родителя. Явный `Correlated` или постраничный дочерний запрос, применяемый отдельно к каждому родителю, вызывает [`NotSupportedException`](xref:System.NotSupportedException) без SQL и без записи в кэш планов; запрос не игнорируется молча. Та же проверка охватывает объявленный вложенный граф, поэтому цикл или конфликтующий режим отвергается до построения команды только для родителя.

Фабрика дочернего запроса должна быть чистой и идемпотентной. При первой проверке терминала она вызывается не более одного раза для каждой пары спецификации eager loading и контекста; при выполнении повторно используется сохранённый дочерний запрос.

## Слот проекции вместо заполнения навигации

`LoadWith` заполняет навигацию загруженной сущности. Когда коллекция на родителя нужна в
спроецированном результате, член проекции может назвать объявленную навигацию —
`Select(p => new { p.Id, p.Comments })` — либо адаптировать её в конвейер на родителя —
`p.Comments.AsEntityBuilder<Comment>().Where(..).OrderBy(..).Limit(..).Select(..).ToList()`. Это поверхность
**проекции**, а не загрузчика: материализация идёт маршрутами этого загрузчика (поэтому режимы split и
single-query, число SQL-инструкций и правила идентичности — те же, что описаны здесь), после чего спроецированная
форма вычисляется в памяти. У неё свои границы — нет отсечения колонок в SQL, закрытый набор операторов
адаптера и нет `Limit` поверх many-to-many — они описаны в
[Слотах коллекционной проекции](collection-projection.md).

## Метаданные связей и `JoinInto`

`LoadWith` не создаёт и не использует метаданные навигаций; связь задаётся двумя селекторами ключей в каждом месте вызова. В nextorm также есть метаданные для **объявленных** связей (`HasMany`/`HasOne` или [`[Relationship]`](xref:NextORM.Core.RelationshipAttribute)) и загрузчик [`JoinInto`](relationships.md), который заполняет одну дочернюю коллекцию через `LEFT JOIN` (или `INNER JOIN`) и распределяет денормализованные строки по родителям. Используйте `JoinInto`, когда связь объявлена в метаданных, и `LoadWith`, когда она задаётся селекторами ключей в месте вызова. В режиме `EagerLoadMode.SingleQuery` `LoadWith` также загружает данные за одно обращение к базе данных, поэтому оба способа используют одинаковые правила обработки результатов, назначения коллекций и порядка. `JoinInto` — **фиксированная** single-query операция: в отличие от `LoadWith`, она никогда не обращается к настройке режима контекста. Поэтому даже если контекст настроен на `UseEagerLoadMode(EagerLoadMode.SplitQuery)`, `Correlated` или `Auto`, `JoinInto` остаётся в single-query режиме. Связи не выводятся из соглашений или внешних ключей. Граф загружается явно: каждый вызов `LoadWith` задаёт одну связь, а вложенный `LoadWith` в дочернем запросе объявляет следующий уровень.
