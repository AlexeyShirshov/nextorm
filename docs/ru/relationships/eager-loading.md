# Жадная загрузка дочерних коллекций (`LoadWith`)

> `LoadWith` заполняет коллекцию на стороне родителя и сшивает дочерние записи с уже материализованными родителями в памяти. По умолчанию используется split-query: один дополнительный дочерний запрос на чанк ключей, два round trip при не более чем 1000 родителях, без N+1. Передайте `EagerLoadMode.SingleQuery` (или задайте context-wide default), чтобы получить родителей и все объявленные коллекции одним денормализованным round trip. Стратегия выбирается явно: split, single-query, консервативный `Auto` или context default; `Correlated` остаётся зарезервированным и отвергается, а собственные `Take`/`Skip` дочернего запроса применяются к каждому родителю (см. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md)). Дочерний запрос может сам объявлять `LoadWith`, поэтому конечный граф вкладывается на любую глубину (второй уровень и глубже) и выполняется в едином режиме на весь граф.

**Предварительные требования:** [Быстрый старт](../getting-started/02-quickstart.md) · [Соединения](../guide/04-joins.md) · [Подзапросы](../guide/07-subqueries.md)

## Обзор

В nextorm связи не выводятся из соглашений, поэтому граф не загружается по конвенции маппера. `LoadWith` объявляет одно ребро жадной загрузки явно: член коллекции на стороне родителя, фабрику дочернего запроса и два селектора ключей, которые сопоставляют дочерние записи родителям, — и не использует метаданные связей. Дочерний запрос — обычный `EntityBuilder<TChild>` и может нести собственный `LoadWith`, поэтому объявления образуют конечный граф, включая второй уровень и глубже. Связь живёт в запросе, а не в метаданных сущности; однозапросную альтернативу на объявленных метаданных см. в [`JoinInto`](relationships.md).

Это аналог linq2db `LoadWith` и EF Core `Include`. По умолчанию используется split-query; опциональный режим single-query (`EagerLoadMode.SingleQuery`) выполняет один денормализованный round trip, а вложенный граф поддержан в обоих режимах там, где провайдер его выражает (см. [Вложенные графы](#вложенные-графы-второй-уровень-и-глубже)).

## Сигнатура

```csharp
public EntityBuilder<TEntity> LoadWith<TChild, TKey>(
    Expression<Func<TEntity, ICollection<TChild>>> collection,
    Func<IDataContext, EntityBuilder<TChild>> childQuery,
    Expression<Func<TEntity, TKey>> parentKey,
    Expression<Func<TChild, TKey>> childKey,
    EagerLoadMode mode = EagerLoadMode.Default)
    where TKey : notnull;
```

- `collection` — член [`ICollection<TChild>`](xref:System.Collections.Generic.ICollection`1) на стороне родителя, который нужно заполнить.
- `childQuery` — строит дочерний запрос из контекста данных, которому принадлежит родительский запрос.
- `parentKey` / `childKey` — селекторы, по которым определяется, какие дочерние записи принадлежат какому родителю.
- `mode` — режим жадной загрузки для всего билдера (см. [Выбор режима](#выбор-режима)); `EagerLoadMode.Default` наследует текущий выбор билдера, а при его отсутствии — context-wide default (`DataContextBuilder.UseEagerLoadMode`, по умолчанию `SplitQuery`).
- `TKey` должен быть не-nullable типом (`where TKey : notnull`), например `int` или `string`. Значение ключа `null`, встреченное в рантайме, пропускается и никогда не сопоставляется.

`LoadWith` возвращает **копию** билдера с объявлением, поэтому исходный билдер не меняется, а несколько загрузок можно объединять в цепочку:

```csharp
var orders = ctx.From<Order>()
    .Where(o => o.CustomerId == customerId)
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId)
    .OrderBy(o => o.Id)
    .ToList();
```

Как и любой модификатор билдера, `LoadWith` требует, чтобы generic-тип ключа был известен в точке вызова; если селектор допускает неявное преобразование, укажите тип ключа явно или приведите тела обоих селекторов к одному типу.

## Выбор режима

Аргумент `mode` выбирает, как загружаются объявленные коллекции, через публичный enum [`EagerLoadMode`](xref:NextORM.Core.EagerLoadMode). Числовые значения фиксированы и совместимы при миграции: `Default=0`, `SplitQuery=1` и `SingleQuery=2` сохраняют исторический смысл для тех, кто хранит или сравнивает enum, а `Correlated=3`/`Auto=4` добавлены в конец:

| Член | Значение | Смысл |
|---|---|---|
| `EagerLoadMode.Default` | `0` | Явный выбор отсутствует: наследуется режим, уже активный на билдере, а при его отсутствии — context default ниже. |
| `EagerLoadMode.SplitQuery` | `1` | Принудительный split-режим для всего билдера. |
| `EagerLoadMode.SingleQuery` | `2` | Принудительный single-query режим для всего билдера. |
| `EagerLoadMode.Correlated` | `3` | Коррелированная загрузка на родителя. Распознаётся, но **не поддерживается** в этом релизе; запрос, который к ней сводится, отвергается. |
| `EagerLoadMode.Auto` | `4` | Автоматический выбор, разрешаемый один раз консервативным правилом ниже. |

Режим принадлежит **всему билдеру**, а не отдельному объявлению, и один разрешённый режим покрывает весь вложенный граф (каждый уровень, объявленный его дочерними запросами):

- Явный режим действует на каждую коллекцию, объявленную на билдере, включая объявленную раньше, пока режим ещё был `Default`.
- Последующий `LoadWith(..., EagerLoadMode.Default)` (или опущенный аргумент) наследует текущий режим и никогда его не сбрасывает.
- Повтор одного и того же явного режима разрешён.
- Смешение двух разных явных режимов — `SingleQuery` затем `SplitQuery` или наоборот — бросает [`NotSupportedException`](xref:System.NotSupportedException): одна SQL-команда не может совместить денормализованное соединение для одной коллекции с отдельным чанковым statement'ом для другой.
- Значение, отличное от пяти определённых членов enum, бросает [`ArgumentOutOfRangeException`](xref:System.ArgumentOutOfRangeException) с `ParamName == "mode"`, а исходный билдер остаётся неизменным.

Режим разрешается в момент вызова `LoadWith`; сама спецификация загрузки не меняется, поэтому смена режима никогда не меняет [правило назначения](#правило-назначения) или [гарантии порядка](#порядок-и-дедупликация).

### Context-wide default

[`DataContextBuilder.UseEagerLoadMode(EagerLoadMode)`](xref:NextORM.Core.DataContextBuilder.UseEagerLoadMode(NextORM.Core.EagerLoadMode)) задаёт context-wide default для коллекций `LoadWith`, чей запрос не объявляет явный режим. По умолчанию это `EagerLoadMode.SplitQuery`, поэтому ненастроенный контекст сохраняет историческое поведение:

```csharp
var builder = new DataContextBuilder()
    .UseSqlite(connection)
    .UseEagerLoadMode(EagerLoadMode.SingleQuery);
using var dataContext = builder.CreateDataContext();
```

- Значение default должно быть одной из четырёх конкретных стратегий — `SplitQuery`, `SingleQuery`, `Correlated` или `Auto`. `EagerLoadMode.Default` отвергается с [`ArgumentOutOfRangeException`](xref:System.ArgumentOutOfRangeException): это sentinel наследования, а не настройка контекста, и его нельзя применять рекурсивно.
- Настройка контекста никогда не меняет статическое/глобальное значение; каждый контекст несёт собственную настройку, доступную только для чтения как `EagerLoadMode` на [`IDataContext`](xref:NextORM.Core.IDataContext) / [`DataContext`](xref:NextORM.Core.DataContext).
- Default разрешается один раз, до генерации любого SQL, а разрешённое значение входит в ключ план-кэша, поэтому два запроса с разными стратегиями никогда не делят закэшированный план.

### Приоритет

Эффективная стратегия — `query override ?? context default`: явный `LoadWith(..., mode)` выигрывает у context default, а при отсутствии явного выбора применяется context default. Внутри билдера `EagerLoadMode.Default` продолжает наследовать режим, выбранный более ранним `LoadWith`.

### Консервативный `Auto`

`Auto` — **консервативный диспетчер**, а не оптимизатор по стоимости. Он никогда не угадывает возможности провайдера и никогда не повторяет упавшее выполнение другой стратегией:

| Запрошенная операция | Поведение в этом релизе |
|---|---|
| Обычная поддерживаемая `LoadWith`, `Auto` | Сводится к `SplitQuery`. |
| Обычная `LoadWith`, явные `SplitQuery`/`SingleQuery` | Существующая split/single реализация и guard'ы. |
| `LoadWith`, явный `Correlated` | Отвергается до генерации любого SQL и до записи в план-кэш. |
| Запрос, требующий per-parent top-N (дочерний `Limit`/`Offset`/`Page`) | Применяется на каждого родителя через ранжированный дочерний источник, батчируемый как любой split-запрос; `Auto` никогда не переинтерпретирует его как глобальный лимит на детей или неограниченную загрузку (см. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md)). |
| `JoinInto` | Фиксированный single-query; не зависит от context default (см. [Метаданные связей и `JoinInto`](#метаданные-связей-и-joininto)). |
| Нет жадных загрузок | Нет диспетчеризации eager-load и нет мутации команды, специфичной для eager-load. |

`Auto` выбирает `SingleQuery`, только когда его запросили явно; автоматический выбор single, произвольное построение `APPLY`/`LATERAL` и угадывание возможностей провайдера не вводятся.

### `Correlated` и постраничная выборка на родителя

`EagerLoadMode.Correlated` не имеет реализованного пути выполнения в этом релизе. Он распознаётся и отвергается с [`NotSupportedException`](xref:System.NotSupportedException) **во время подготовки — до генерации любого SQL и до вставки записи в план**, поэтому отвергнутый запрос не выполняет родительский statement и не портит план-кэш. Значение enum зарезервировано для работы над коррелированной выборкой, отслеживаемой отдельно. Отвергается это на **любом** терминале, в том числе на не-list терминалах ниже, которые вычисляют только родителя. Такой терминал сначала проверяет набор `LoadWith`, поэтому явный `Correlated` отвергается до построения родительской команды, а не молча отбрасывается; при этом не-list терминал по-прежнему не материализует коллекцию.

Собственные `Limit`/`Offset`/`Page` дочернего запроса **не** отвергаются: они применяются независимо к каждому родителю через секционированный `row_number()`-дочерний источник в обоих режимах — `SplitQuery` и `SingleQuery`, — причём фильтрация и сортировка детей идут до пейджинга, корневые границы остаются независимыми, а родители без детей сохраняются. `Auto` применяет пейджированную загрузку через свой split-диспетчер, и пейджированная загрузка никогда не переинтерпретируется как глобальный лимит на детей или неограниченная загрузка. Per-parent top-N — возможность `LoadWith`: `JoinInto` отвергает её до выполнения, а провайдер in-memory отвергает пейджированный дочерний запрос fail-closed (у него нет SQL-окна), тогда как непейджированная жадная загрузка там не меняется. См. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md).

## Семантика split-query

Объявление **не** входит в родительский SQL. После материализации родительского запроса:

1. Различные непустые родительские ключи собираются **в порядке родителей** и разбиваются на чанки не более чем по **1000** ключей.
2. Один дочерний запрос на чанк выполняет `WHERE childKey IN (<ключи чанка>)` — отдельный statement, без `JOIN` и без запроса на каждого родителя.
3. Дочерние записи группируются по `childKey` и назначаются родителям, чей `parentKey` совпадает.

Поэтому запрос с не более чем 1000 различных родительских ключей выполняет ровно **два round trip**: один родительский statement и один дочерний. Большие наборы ключей добавляют по одному дочернему statement на каждый дополнительный чанк; родительский statement всё равно выполняется один раз. N+1 нет: число дочерних statement'ов зависит от размера набора ключей, а не от числа родителей.

```sql
-- родительский statement
select id, name
 from order

-- дочерний statement (по одному на чанк не более чем из 1000 различных родительских ключей)
select id, order_id, name
 from order_item where order_id in (@k0, @k1, @k2)
```

Предикат чанка — обычный список `IN`, поэтому он так же участвует в кэше планов и привязке параметров провайдера, как `Contains` по захваченной коллекции.

При отмене `ToListAsync`/`ToArrayAsync` токен проверяется между чанками ключей и между несколькими объявлениями `LoadWith`, поэтому отменённый вызов прекращает выдавать дальнейшие дочерние statement'ы.

## Режим single-query (`EagerLoadMode.SingleQuery`)

По умолчанию `LoadWith` использует split-форму выше — два или более round trip, по одному на чанк ключей. Передайте `EagerLoadMode.SingleQuery` последним аргументом `LoadWith` (режим действует на весь билдер) или задайте context-wide default через `UseEagerLoadMode(EagerLoadMode.SingleQuery)`, чтобы получить родителей и все объявленные коллекции **одной** денормализованной командой:

```csharp
var orders = ctx.From<Order>()
    .Where(o => o.CustomerId == customerId)
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId,
        EagerLoadMode.SingleQuery)
    .ToList();
```

Тогда билдер выдаёт одну денормализованную команду вместо двух statement'ов выше:

```sql
select t1.id, t1.name, t2.id, t2.order_id, t2.name
 from order as t1
 left join order_item as t2 on t1.id = t2.order_id
```

Собственный `Where` дочернего запроса встраивается в `ON` соединения, поэтому фильтрует дочерние записи, не отбрасывая родителей без детей:

```sql
select t1.id, t1.name, t2.id, t2.order_id, t2.name
 from order as t1
 left join order_item as t2 on t1.id = t2.order_id and t2.active
```

- **Один round trip, без чанкования ключей.** Источник родителя и каждый объявленный дочерний запрос соединяются одной командой `LEFT JOIN`. Списка `IN` и размера чанка нет, поэтому любое число родителей — включая более 1000 различных ключей — извлекается этой же командой, без молчаливого отката к split.
- **Встраивается только собственный `Where` дочернего запроса.** Дочернее условие, например `c => c.From<OrderItem>().Where(i => i.Active)`, включается в предикат `ON` соединения, поэтому фильтрует дочерние записи, не отбрасывая родителей без детей.
- **Пейджинг сворачивается в ранжированный источник; остальные формы дочернего запроса отвергаются.** Дочерний запрос с `Limit`/`Offset`/`Page` (со своим `OrderBy` или без него) сворачивается в секционированный `row_number()`-производный источник и пейджится на каждого родителя (см. [Постраничная выборка на родителя при жадной загрузке](eager-loading-per-parent-paging.md)). **Голый** `OrderBy` дочернего запроса, не сопровождаемый пейджингом, — это по-прежнему выходной модификатор на родителя, который одно денормализованное соединение выразить не может; кроме того, одно денормализованное соединение не может применить соединения или clauses уровня таблицы, поэтому дочерний запрос с голым `OrderBy`, `Distinct`, `GroupBy`, `Having`, `DistinctOn`, `LimitBy`, соединением (`Join`/`LeftJoin`/`SemiJoin`/`AntiJoin`/…), `Final`, `PreWhere`, `ArrayJoin`, `TableSample`, `Sample`, `ForSystemTime`, `ForUpdate`/`ForShare`, `Window`, `Settings`, CTE, table/index hint или производным (`As`) источником бросает [`NotSupportedException`](xref:System.NotSupportedException) уже при материализации single-query команды. Split-режим учитывает их все; используйте split (не передавайте `EagerLoadMode.SingleQuery` или передайте `EagerLoadMode.SplitQuery`), когда дочернему запросу нужна форма сложнее `Where`. Специфичные для ClickHouse формы из этого списка (`LimitBy`, `Final`, `PreWhere`, `ArrayJoin`, `Sample`, `Settings`) — методы-расширения из `NextORM.ClickHouse` (`using NextORM.ClickHouse;`).
- **Области фильтров родителя и ребёнка объединяются, одинаково в split- и single-query режиме.** Эффективная область ребёнка — это всегда объединение его собственной области `IgnoreFilters` и родительской. `IgnoreFilters()` на родителе отключает и фильтры объявленных детей (область «всё» поглощает собственную область ребёнка), а селективный `IgnoreFilters(...)` родителя доходит и до детей. И наоборот: `IgnoreFilters(...)` внутри дочернего запроса отключает только фильтры этого ребёнка, а родительские продолжают действовать. То же правило действует и при загрузке стандартной split-формой, и при `EagerLoadMode.SingleQuery`.
- **Тип родителя должен объявлять mapped-ключ.** Денормализованные строки дедуплицируются по этому ключу, поэтому родитель без ключа бросает [`NotSupportedException`](xref:System.NotSupportedException) с указанием настроить ключ или использовать split-режим, которому ключ не нужен. Строки с одинаковым mapped-ключом схлопываются в одного родителя; split-режим сохраняет их раздельно.
- **Тип ключа должен поддерживать равенство по значению.** Предикат соединения строится через оператор равенства, поэтому тип ключа без него — например, структура без перегрузки `==` или ссылочный тип, `==` которого выродился бы в сравнение ссылок, — бросает [`NotSupportedException`](xref:System.NotSupportedException). Split-режим сравнивает ключи стандартным компаратором равенства и работает с такими типами.
- **Вложенные графы соединяются по уровню.** Дочерний запрос, который сам объявляет `LoadWith`, планируется как вложенный граф: билдер выдаёт по одному `LEFT JOIN` на узел и собирает все уровни из одного result set (см. [Вложенные графы](#вложенные-графы-второй-уровень-и-глубже)). На каждом уровне сворачивается только собственный `Where` ребёнка, а узел, который одновременно объявляет детей и пейджится на родителя, отвергается.
- **Назначение и порядок не меняются.** Тот же stitching дедуплицирует родителей и заполняет каждую коллекцию, поэтому [правило назначения](#правило-назначения) и [гарантии порядка](#порядок-и-дедупликация) ниже действуют в обоих режимах.
- **Только один обычный источник сущности.** `EagerLoadMode.SingleQuery` нельзя комбинировать с другими соединениями на одном билдере; вызов на запросе, уже несущем обычное (не `JoinInto`) соединение, бросает [`NotSupportedException`](xref:System.NotSupportedException).
- **Дальнейшая композиция запрещена.** После `LoadWith` в режиме single-query нельзя вызывать `Select` или `As` (у команды-проекции нет загрузчика) либо `Join`/`Apply` (присоединённый билдер не несёт ни спецификаций загрузки, ни режима). Каждая такая композиция бросает [`NotSupportedException`](xref:System.NotSupportedException) вместо молчаливого оставления коллекций пустыми; сначала материализуйте результат stitching-терминалом.

Split остаётся режимом по умолчанию: предпочитайте его, когда результат дочернего запроса по чанкам меньше денормализованного произведения соединения, и переключайтесь на `EagerLoadMode.SingleQuery`, когда важнее один round trip.

## Вложенные графы (второй уровень и глубже)

Дочерний запрос — обычный `EntityBuilder<TChild>`, поэтому он может объявлять собственный `LoadWith`, и загрузчик рекурсивно уходит вглубь: `Root → Mids → Leaves → Tips …` загружается уровень за уровнем на любую конечную глубину. В объявлении ничего не меняется — каждый `LoadWith` по-прежнему называет одну родительскую коллекцию, одну фабрику дочернего запроса и два селектора ключей, — и на каждом уровне действуют те же правило назначения, гарантии порядка и правило null-ключей.

```csharp
var roots = ctx.From<Root>()
    .LoadWith(
        r => r.Mids,
        c => c.From<Mid>()
            .OrderBy(m => m.SortKey)
            .LoadWith(m => m.Leaves, l => l.From<Leaf>().OrderByDescending(x => x.SortKey), m => m.Id, l => l.MidId),
        r => r.Id,
        m => m.RootId)
    .ToList();
```

Для всего графа действует следующий контракт:

- **Один режим на весь граф.** Стратегия, разрешённая для корня (`SplitQuery`, `SingleQuery`, context default или консервативный `Auto`), применяется к каждому уровню. Вложенное объявление не может запросить другой явный режим: `LoadWith(..., EagerLoadMode.X)` у ребёнка, чей разрешённый режим отличается от режима графа, бросает [`NotSupportedException`](xref:System.NotSupportedException) (`... mixes modes ...`). `EagerLoadMode.Default` у ребёнка просто наследует режим графа.
- **Порядок/top-N на каждом уровне.** Дочерний запрос каждого уровня сохраняет собственный эффективный `OrderBy`, а его собственные `Take`/`Skip` на родителя применяются внутри родителей этого уровня (split-режим, SQL-провайдеры). Порядок первого уровня не меняется, а два соседних уровня могут упорядочиваться независимо.
- **Идентичность по предкам.** Потомки группируются по **ancestor-composite идентичности** — ключ первого уровня плюс ключ второго уровня плюс … — поэтому один и тот же ключ ребёнка под двумя разными предками собирается под каждым предком независимо. Null-ключ на любом уровне никогда не сопоставляется и не падает, а пустой промежуточный результат просто не загружает потомков.
- **Split учитывает любую форму дочернего запроса на каждом уровне** так же, как на первом; **single-query** сворачивает в `LEFT JOIN` только собственный `Where` каждого узла.

### Матрица провайдеров и фронтендов

| Вложенный граф / форма | Split (`SplitQuery`, `Auto`) | Single-query (`EagerLoadMode.SingleQuery`) |
|---|---|---|
| Вложенный `LoadWith` (глубина 2+), у ребёнка только `Where` | да — каждый уровень, все SQL-провайдеры и in-memory | да — по одному `LEFT JOIN` на узел, все SQL-провайдеры и in-memory |
| Вложенный `OrderBy` / `Distinct` / `GroupBy` / соединения / прочие формы, отличные от `Where` | да — каждый уровень | отвергается fail-closed (на каждом уровне сворачивается только собственный `Where` ребёнка) |
| `Take`/`Skip` на родителя на каждом уровне (`Limit`/`Offset`/`Page`) | да на каждом уровне у SQL-провайдеров; in-memory-провайдер отвергает пейджированный дочерний запрос (нет SQL-окна) | отвергается, когда пейджированный узел ещё и объявляет детей — у ранжированного ребёнка нет пер-уровневого рендеринга |

SQL-провайдеры (SQLite, PostgreSQL, SQL Server, MySQL/MariaDB, ClickHouse) исполняют вложенные split и вложенные single-query; in-memory-провайдер исполняет вложенные графы для непейджированных детей и сохраняет существующее fail-closed отклонение пейджированного ребёнка. Фронтенды согласованы с этим контрактом: уровень [`JoinInto`](relationships.md) сочетается с вложенным графом `LoadWith` — и присоединённая коллекция, и более глубокие вложенные уровни сшиваются, — а проекция с материализацией сущности из неявной навигации (`Select(n => new { n.Id, Parent = n.Parent })`) вместе с вложенным графом `LoadWith` — проверенно отклоняемая форма: до выполнения бросается [`NotSupportedException`](xref:System.NotSupportedException), а не молчаливая потеря вложенного графа.

### Fail-closed формы

Каждый невыразимый вложенный граф отвергается до генерации любого SQL и до вставки записи в план-кэш, а не молча теряет потомка или откатывается к другой стратегии:

- **неподдерживаемая форма ребёнка на любом уровне** (single-query): вложенный ребёнок, который не сводится к `Where` — `OrderBy`, `Distinct`, `GroupBy`, `Having`, `DistinctOn`, соединение, clause уровня таблицы или производный (`As`) источник, — бросает [`NotSupportedException`](xref:System.NotSupportedException) с именем формы (см. [Режим single-query](#режим-single-query-eagerloadmodesinglequery));
- **вложенный per-parent пейджинг** (single-query): узел, который одновременно объявляет детей и пейджится на родителя, бросает `NotSupportedException` (`Limit/Offset/Page`); split поддерживает пейджинг на каждом уровне у SQL-провайдеров;
- **переполнение арности проекции**: сведение графа в одну денормализованную команду более чем для семи дочерних коллекций (потолок арности [`Projection<T1..T8>`](relationships.md#один-round-trip)) бросает `NotSupportedException`; объявите более мелкий граф или используйте split-режим;
- **конфликт вложенного режима**: ребёнок, запрашивающий явный режим, отличный от режима графа, бросает `NotSupportedException` (`... mixes modes ...`);
- **циклы**: объявление, чья ancestor-composite идентичность повторяется, — самоссылающаяся сущность или фабрика ребёнка, рекурсивно возвращающая саму себя, — детерминированно бросает `NotSupportedException`: требуется конечный ацикличный граф, а не ограничение глубины;
- **пейджированный дочерний запрос в in-memory**: существующее fail-closed отклонение #211 (нет SQL-окна) не меняется; непейджированная вложенная загрузка там работает.

## Правило назначения

Для каждого родителя загрузчик выбирает целевую коллекцию:

| Текущее значение `collection` | Член доступен для записи | Поведение |
|---|---|---|
| не null | любой | очищается и заполняется заново |
| `null` | да | назначается новый список |
| `null` | нет (read-only) | [`NotSupportedException`](xref:System.NotSupportedException) |

Read-only коллекция поддерживается, если она инициализирована пустой коллекцией и никогда не переприсваивается:

```csharp
public sealed class Order
{
    public int Id { get; set; }
    public ICollection<OrderItem> Items { get; } = new List<OrderItem>();
}
```

Read-only член не отображается на колонку БД, поэтому его инициализация не влияет на родительский `SELECT`.

## Порядок и дедупликация

- **Порядок родителей сохраняется.** Дочерние записи назначаются родителям в том порядке, в котором их вернул родительский запрос; загрузчик никогда не переупорядочивает родителей.
- **Порядок дочерних записей следует за дочерним запросом.** Дочерние записи сохраняют порядок дочернего statement'а, поэтому добавьте `OrderBy` в `childQuery`, если порядок важен.
- **Одинаковые родительские ключи делят данные (split).** Два родителя с одинаковым ключом получают коллекции с одними и теми же дочерними записями (у каждого родителя свой экземпляр коллекции). В single-query режиме mapped-ключ родителя служит идентичностью дедупликации, поэтому строки с одинаковым ключом схлопываются в одного родителя — используйте split, когда такие строки должны остаться раздельными.
- **Несовпавшие дочерние записи игнорируются.** Дочерняя запись, чей ключ не совпал ни с одним родителем, не назначается, а родитель, у которого нет дочерних записей, получает пустую коллекцию.
- **Null-ключи никогда не сопоставляются.** Родительский или дочерний ключ, равный `null` в рантайме, пропускается; он никогда не ищется и не ломает группировку.

## Повторные объявления

Член коллекции можно объявить **только один раз** на запрос. Повторный вызов `LoadWith` для того же члена бросает [`InvalidOperationException`](xref:System.InvalidOperationException): два объявления выполнили бы два дочерних запроса для одной коллекции, и позднее присваивание отбросило бы раннюю загрузку. Объявляйте каждый член не более одного раза и используйте разные члены для загрузки нескольких коллекций:

```csharp
ctx.From<Order>()
    .LoadWith(o => o.Items, c => c.From<OrderItem>(), o => o.Id, i => i.OrderId)
    .LoadWith(o => o.Payments, c => c.From<Payment>(), o => o.Id, p => p.OrderId); // другой член
```

## Граница терминалов

Спецификация загрузки учитывается **только** четырьмя stitching-терминалами:

- [`ToList()`](xref:NextORM.Core.EntityBuilderExtensions.ToList``1(NextORM.Core.EntityBuilder{``0},System.ReadOnlySpan{System.Object})) и [`ToListAsync()`](xref:NextORM.Core.EntityBuilderExtensions.ToListAsync``1(NextORM.Core.EntityBuilder{``0},System.Object[])).
- `ToArray()` и `ToArrayAsync()`.

Они выполняют родительский запрос — плюс split-запросы детей, или одну денормализованную команду с `EagerLoadMode.SingleQuery` — и сшивают материализованные строки в коллекции.

Любой другой терминал вычисляет **только** родительский запрос и не выполняет eager loading; он не выдаёт ни дочерний запрос, ни запрос загрузки, поэтому коллекции сохраняют то значение, с которым сущность была материализована (обычно пустое):

- `ToHashSet` / `ToHashSetAsync` и `ToDictionary` / `ToDictionaryAsync`.
- `First` / `FirstAsync` и `FirstOrDefault` / `FirstOrDefaultAsync`.
- `Single` / `SingleAsync` и `SingleOrDefault` / `SingleOrDefaultAsync`.
- `ToEnumerable` и `ToAsyncEnumerable`.
- `ToCommand` и любой полученный из него `QueryCommand<T>`.

`Any` / `AnyAsync` и `Count` / `CountAsync` — **скалярные** терминалы: они возвращают одно значение и тоже никогда не выполняют eager loading. `ToCommand()` игнорирует спецификацию намеренно — именно поэтому дочерний запрос выполняется без рекурсии в загрузчик родителя. Материализуйте родителей одним из четырёх stitching-терминалов, когда коллекции должны быть заполнены. Не-list терминал по-прежнему проверяет набор `LoadWith` перед построением команды только для родителя: явный `Correlated` или дочерний per-parent top-N запрос отвергается с [`NotSupportedException`](xref:System.NotSupportedException) (без SQL и без записи в план-кэш), а не молча игнорируется. Та же проверка при подготовке покрывает объявленный вложенный граф, поэтому цикл или конфликтующий вложенный режим отвергается до построения команды только для родителя. Фабрика дочернего запроса должна быть чистой и идемпотентной; она вызывается не более одного раза для каждой пары спецификации eager loading и контекста при первой терминальной проверке, а мемоизированный дочерний запрос повторно используется при выполнении.

## Метаданные связей и `JoinInto`

`LoadWith` не создаёт и не использует метаданные навигаций; связь выражается двумя селекторами ключей в каждом месте вызова. В nextorm также есть модель метаданных для **объявленных** связей (`HasMany`/`HasOne` или [`[Relationship]`](xref:NextORM.Core.RelationshipAttribute)) и однозапросный загрузчик [`JoinInto`](relationships.md), который заполняет одну дочернюю коллекцию одним `LEFT JOIN` (или `INNER JOIN`) и сшивает денормализованные строки обратно с дедуплицированными родителями. Используйте `JoinInto`, когда связь объявлена как метаданные отношений, и `LoadWith`, когда она выражается ad hoc селекторами ключей в месте вызова; `LoadWith` с `EagerLoadMode.SingleQuery` тоже сводится к одному денормализованному запросу, поэтому оба делят одну материализацию single-query, контракт присваивания и гарантии порядка. `JoinInto` — **фиксированная** single-query операция: в отличие от `LoadWith`, она никогда не обращается к context default, поэтому контекст, настроенный на `UseEagerLoadMode(EagerLoadMode.SplitQuery)`, `Correlated` или `Auto`, оставляет `JoinInto` на single-query пути. Связи по-прежнему никогда не выводятся из соглашений или внешних ключей. Граф загружается явно: каждый вызов `LoadWith` объявляет одно ребро, а вложенный `LoadWith` внутри дочернего запроса объявляет следующий уровень.
