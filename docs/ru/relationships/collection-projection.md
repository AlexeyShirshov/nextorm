# Слоты коллекционной проекции (`Select`)

> Проекция может назвать **объявленную** коллекционную навигацию одним из своих членов: прямая форма
> `Select(p => new { p.Id, p.Comments })` и форма через адаптер
> `p.Comments.AsEntityBuilder<Comment>().Where(..).OrderBy(..).Limit(..).Select(..).ToList()` обе проецируют
> **коллекцию на родителя** в объявленный вами тип результата. Движок материализует граф сущностей через
> существующий маршрут жадной загрузки — split по умолчанию и одна денормализованная инструкция в режиме
> single-query — а затем применяет конвейер адаптера и строит спроецированную форму **в памяти**. Число
> инструкций — это число инструкций жадной загрузки: оно не растёт с числом родителей, и в SQL не добавляется
> никакая корреляционная колонка. Эта страница описывает поставленную поверхность v1 и её ограничения.

**Предварительные требования:** [Связи и однозапросная загрузка (`JoinInto`)](relationships.md) · [Жадная загрузка дочерних коллекций (`LoadWith`)](eager-loading.md) · [Проекции](../guide/02-projections.md)

## Обзор

Слот коллекционной проекции — это обычный член проекции, значением которого является целая коллекция одной
навигации:

```csharp
var posts = ctx.From<Post>()
    .Where(p => p.Published)
    .OrderBy(p => p.Id)
    .Select(p => new { p.Id, p.Comments })
    .ToList();

foreach (var post in posts)
    foreach (var comment in post.Comments)
        Console.WriteLine($"{post.Id}: {comment.Id}");
```

Поверхность определяют три вещи:

- **Связь должна быть объявлена** — `HasMany`, `HasManyThrough` или `[Relationship]` на коллекционной стороне
  (см. [Связи](relationships.md)). Член коллекционного типа без объявленной связи — обычное проецируемое
  значение, а не слот; из соглашения об именах или имени внешнего ключа ничего не выводится.
- **Поддерживаются обе коллекционные кардинальности** — one-to-many и many-to-many. Спроецированная **ссылка**
  (many-to-one / one-to-one) тоже поддерживается, когда в проекции есть и коллекционный слот, и подчиняется
  собственному правилу кардинальности ([ниже](#спроецированные-ссылки-и-кардинальность)).
- **Проекция вычисляется в памяти, после материализации.** SQL выбирает строки сущностей; операции адаптера и
  форма назначения применяются к уже материализованной коллекции. В v1 нет ни отсечения колонок в SQL, ни
  проталкивания колонок DTO — см. [Ограничения v1](#ограничения-v1).

Публичный тип результата — ровно тот, который вы объявили: `Select` по-прежнему возвращает
[`QueryCommand<TResult>`](xref:NextORM.Core.QueryCommand`1), а `TResult` несёт коллекционный член в том виде, в
каком он написан.

## Объявление сущностей

Примеры на этой странице используют один граф: `Post → Comment → Reaction`, `Post ↔ Tag` через `PostTag` и
ссылку `Comment.Author`.

```csharp
[SqlTable("post")]
public sealed class Post
{
    [Key, Column("id")] public int Id { get; set; }
    [Column("title")] public string? Title { get; set; }
    [Column("published")] public bool Published { get; set; }

    public List<Comment> Comments { get; } = [];
    public ICollection<Tag> Tags { get; } = new List<Tag>();
}

[SqlTable("comment")]
public sealed class Comment
{
    [Key, Column("id")] public int Id { get; set; }
    [Column("post_id")] public int PostId { get; set; }
    [Column("author_id")] public int AuthorId { get; set; }
    [Column("created_at")] public DateTime CreatedAt { get; set; }
    [Column("active")] public bool Active { get; set; }

    public List<Reaction> Reactions { get; } = [];
    public Author? Author { get; set; }
}

[SqlTable("reaction")]
public sealed class Reaction
{
    [Key, Column("id")] public int Id { get; set; }
    [Column("comment_id")] public int CommentId { get; set; }
    [Column("kind")] public string? Kind { get; set; }
}

[SqlTable("tag")]
public sealed class Tag
{
    [Key, Column("id")] public int Id { get; set; }
    [Column("name")] public string? Name { get; set; }
}

[SqlTable("post_tag")]
public sealed class PostTag
{
    [Column("post_id")] public int PostId { get; set; }
    [Column("tag_id")] public int TagId { get; set; }
}

[SqlTable("author")]
public sealed class Author
{
    [Key, Column("id")] public int Id { get; set; }
    [Column("name")] public string? Name { get; set; }
}
```

Связи объявляются один раз, на стороне, владеющей коллекцией:

```csharp
_ = ctx.From<Post>(cfg => cfg
    .HasMany(p => p.Comments, c => c.PostId)
    .HasManyThrough<Tag, PostTag, int, int>(
        p => p.Tags, p => p.Id, l => l.PostId, t => t.Id, l => l.TagId));

_ = ctx.From<Comment>(cfg => cfg
    .HasMany(c => c.Reactions, r => r.CommentId)
    .HasOne(c => c.Author, c => c.AuthorId));
```

## Прямой слот

Прямая форма проецирует сам член навигации:

```csharp
var posts = ctx.From<Post>()
    .Where(p => p.Published)
    .OrderBy(p => p.Id)
    .Select(p => new { p.Id, p.Comments })
    .ToList();

// select ... from post as t1 where t1.published            -- инструкция 1 (split)
// select ... from comment as t1 where t1.post_id in (@k0)  -- инструкция 2, одна на чанк ключей
```

- **Нет дочерних строк — пустая коллекция.** Пост без комментариев попадает в результат с пустой коллекцией
  `Comments` — никогда не `null`.
- **Порядок и дубликаты наследуются от дочерних строк.** Прямая форма не объявляет порядок, поэтому порядок
  внутри каждой коллекции — это порядок дочерней инструкции; добавляйте `OrderBy` адаптера, когда он важен.
  Слот many-to-many хранит один элемент на **различную строку связки** (картезианский повтор одной строки
  связки схлопывается; буквально продублированная связка остаётся двумя элементами).
- **Две инструкции для слота one-to-many в режиме split** — инструкция родителя и одна пакетная дочерняя
  инструкция по ключам родителей. Дочерняя инструкция нарезается на чанки, то есть выполняется одна инструкция
  на 1000 ключей родителей, а не одна на родителя.

## Слот через адаптер

Форма через адаптер стартует с той же навигации и применяет конвейер к каждому родителю до проецирования:

```csharp
var pageSize = 2;
var authorId = 7;

var posts = ctx.From<Post>()
    .Where(p => p.Published)
    .OrderBy(p => p.Id)
    .Select(p => new
    {
        p.Id,
        Recent = p.Comments
            .AsEntityBuilder<Comment>()
            .Where(c => c.Active && c.AuthorId == authorId)
            .OrderBy(c => c.CreatedAt)
            .ThenBy(c => c.Id, OrderDirection.Desc)
            .Limit(pageSize)
            .Select(c => new CommentRow { Id = c.Id, CreatedAt = c.CreatedAt })
            .ToList(),
        Tags = p.Tags.AsEntityBuilder<Tag>().OrderBy(t => t.Name).ToArray(),
    })
    .ToList();
```

`AsEntityBuilder<T>()` — тот же адаптер навигации, который отвечает на `Any`/`Count` (см.
[Неявные навигационные запросы](implicit-navigation.md)); внутри проекции он продолжается в коллекционный
конвейер:

| Оператор | Смысл внутри слота |
|---|---|
| `Where(predicate)` | Фильтрует элементы этого родителя до упорядочивания и постраничного вывода. Предикат может читать текущего родителя (`i => i.PostId == p.Id`). |
| `OrderBy` / `OrderByDescending` | Первичное упорядочивание элементов этого родителя, по возрастанию или по убыванию (`OrderDirection`). |
| `ThenBy` / `ThenByDescending` | Дополнительные ключи упорядочивания, применяются в порядке вызова после первичного ключа. |
| `Limit(count)` | Оставляет не более `count` элементов **этого родителя** после фильтрации и упорядочивания — для слотов one-to-many и many-to-many одинаково. Для слота many-to-many счёт идёт по **выжившим вхождениям связки** (см. ниже). Захваченное значение читается при исполнении. |
| `Select(projection)` | Проецирует каждый элемент в тип элемента слота (DTO, record или анонимная форма). |
| `ToList()` / `ToArray()` | Завершает слот и выбирает форму назначения. |

- **Каждый оператор применяется к каждому родителю, в памяти.** Конвейер выполняет
  `фильтрация → упорядочивание → limit → select` над материализованными дочерними строками каждого родителя,
  поэтому `Limit` — это страница **на родителя**, а не глобальный `LIMIT`/`TOP`/`FETCH`. Число инструкций не
  меняется: слот через адаптер стоит столько же инструкций, сколько прямой слот (2 в split / 1 в single для
  one-to-many глубины один), каким бы ни был размер страницы.
- **Страница many-to-many считается по выжившим вхождениям связки.** Страница режет навигацию, которую вернул
  загрузчик: повторная строка связки повторяет своего ребёнка и занимает собственный слот, висячая связка (строка
  junction, чья дочерняя строка отсутствует) исключается из счёта и из страницы, а родитель, у которого все
  связки висячие, получает пустую коллекцию. Вхождения читаются, после чего страница отсекается в памяти —
  SQL-ранжирования по junction в этом релизе нет, — поэтому страница стоит столько же инструкций и выбирает
  столько же колонок, сколько слот many-to-many без `Limit`; число прочитанных строк она не уменьшает.
- **Конвейер декларативен, это не выполнение LINQ по коллекциям.** Операторы считываются из дерева выражений и
  вычисляются по материализованной коллекции; лямбды сохраняют ссылку на параметр проекции, поэтому
  коррелированный предикат видит текущего родителя без перекомпиляции.
- **Захваченное значение перепривязывается при каждом исполнении.** Одна команда, построенная с `pageSize = 1`
  и исполненная повторно после смены значения на `2`, вернёт `[10]`, а затем `[10, 11]` — значение читается при
  запуске конвейера и никогда не зашивается в ключ плана или в скомпилированный делегат.
- **`Offset` не входит в набор адаптера.** Адаптер принимает семь операторов выше; `Limit` — единственный
  оператор постраничного вывода, а `Offset`/`Skip` отвергаются по имени, как и любой другой неподдерживаемый
  оператор.

## Вложенные слоты (глубина 2 и больше)

Слот вкладывается через `Select(...)` адаптера: вложенный слот объявляется на дочернем элементе, поэтому один и
тот же путь кода обслуживает любую глубину.

```csharp
var posts = ctx.From<Post>()
    .Where(p => p.Id == 1)
    .Select(p => new
    {
        p.Id,
        Comments = p.Comments
            .AsEntityBuilder<Comment>()
            .Where(c => c.Active)
            .OrderBy(c => c.CreatedAt)
            .Select(c => new
            {
                c.Id,
                Reactions = c.Reactions
                    .AsEntityBuilder<Reaction>()
                    .OrderBy(r => r.Kind)
                    .Limit(3)
                    .Select(r => r.Kind)
                    .ToList(),
            })
            .ToList(),
    })
    .ToList();
```

- **Одна инструкция на уровень.** В режиме split граф выше стоит три инструкции (родитель, комментарии,
  реакции); цепочка из трёх уровней — четыре, а уровень many-to-many добавляет инструкцию связки. Режим
  single-query сворачивает весь граф в одну инструкцию. Числа постоянны для 1, 3 и 30 корней.
- **Каждый уровень фильтрует, упорядочивает и разбивает на страницы свои элементы.** `Limit` применяется к
  элементу **своего** уровня: на первом уровне он ограничивает комментарии каждого поста, на втором — реакции
  каждого комментария. Упорядочивание первого уровня не зависит от порядка второго, и два соседних уровня могут
  упорядочиваться независимо.
- **Вложенный слот должен находиться внутри `Select(...)` адаптера.** Встроенная дочерняя форма в прямой
  проекции, которая сама несёт слот (`Select(p => new { p.Id, X = new { p.Comments } })`), отвергается по
  имени: движок не может адресовать форму, построенную вне адаптера.
- **Many-to-many вкладывается тоже.** Слот над `Comment → Tag` внутри графа глубины два загружается своим
  набором инструкций уровня и возвращает корректные строки, в том числе в режиме single-query.

## Split и single-query

Слоты материализуются маршрутом жадной загрузки, поэтому **весь спроецированный граф** исполняется в том
режиме, который этот маршрут разрешает: split по умолчанию, одна денормализованная инструкция, когда контекст
выбирает single-query:

```csharp
var builder = new DataContextBuilder()
    .UseSqlite(connection)
    .UseEagerLoadMode(EagerLoadMode.SingleQuery);
using var ctx = builder.CreateDataContext();

var posts = ctx.From<Post>()
    .Select(p => new { p.Id, p.Comments })
    .ToList();   // одна инструкция для родителя и его комментариев
```

| Граф | Split (по умолчанию) | Single-query |
|---|---|---|
| глубина 1, one-to-many | 2 | 1 |
| глубина 1, many-to-many | 3 (родитель + связка + тег) | 1 |
| глубина 2 | 3 | 1 |
| глубина 2 с уровнем many-to-many | 4 | 1 |
| глубина 3 | 4 | 1 |
| тот же граф, 1 / 3 / 30 корней | то же число | то же число |

Один режим покрывает все уровни: вложенный уровень не может исполняться в режиме, отличном от режима корня,
точно так же, как в графах `LoadWith` (см. [Жадная загрузка дочерних коллекций](eager-loading.md#вложенные-графы-второй-уровень-и-глубже)).

## CLR-формы

Тип **члена назначения** слота должен быть одной из семи форм над типом элемента, который производит слот:

| Форма | Прямой слот | Слот через адаптер |
|---|---|---|
| `List<T>` | да | да (`ToList()`) |
| `T[]` | не выразима | да (`ToArray()`) |
| `IEnumerable<T>` | да | да |
| `ICollection<T>` | да | да |
| `IList<T>` | да | да |
| `IReadOnlyCollection<T>` | да | да |
| `IReadOnlyList<T>` | да | да |

Прямая форма может объявить только назначение, **присваиваемое из объявленного CLR-типа навигации**, поэтому
навигация типа `List<T>` покрывает шесть коллекционных интерфейсов, но никогда `T[]` — массив существует только
через `ToArray()` адаптера, который материализует настоящий `T[]`.

**Любая другая форма отвергается закрыто, без подстановки.** `HashSet<T>`, собственный коллекционный тип или
назначение `object` отвергаются до генерации любого SQL:

```
The collection projection slot 'Post.Comments' is declared as 'System.Collections.Generic.HashSet`1[Comment]':
only List<T>, T[], IEnumerable<T>, ICollection<T>, IList<T>, IReadOnlyCollection<T> and IReadOnlyList<T> are
supported, and no other shape is substituted.
```

То же правило действует для выражения, которое не является ни прямым членом, ни цепочкой адаптера:
`.ToHashSet()` на объявленной коллекционной навигации отвергается сообщением *"… is not a supported collection
slot: declare it as a direct navigation member or as a navigation adapter (nav.AsEntityBuilder<T>() ...
.ToList()/.ToArray())."* Колоночная коллекция скалярного типа (например `byte[]`) навигацией не является и
остаётся обычным проецируемым значением.

## Терминалы и беспараметрические перегрузки

Слот несёт спроецированная команда, поэтому исполняют его обычные материализующие терминалы:

- `QueryCommand<TResult>.ToList()` / `.ToArray()` — спроецированный результат;
- `EntityBuilder<TEntity>.ToList()` / `.ToArray()` — форма сущности, когда проекцией является вся сущность.

Эти четыре **беспараметрические** перегрузки входят в поставленную публичную поверхность:

```csharp
public static List<TEntity> ToList<TEntity>(this EntityBuilder<TEntity> builder);
public static TEntity[] ToArray<TEntity>(this EntityBuilder<TEntity> builder);
public List<TResult> ToList();
public TResult[] ToArray();
```

Они существуют потому, что цепочка адаптера должна быть **выразима в дереве выражений**: соседние перегрузки
`params ReadOnlySpan<object?>` — это `ref struct` с раскрываемым `params`-набором, на который дерево выражений
ссылаться не может (`CS8640`/`CS9226`). Каждая беспараметрическая перегрузка переадресует в свою пару с
`ReadOnlySpan` и пустым span, не связывая параметров, поэтому вызов без аргументов исполняет ровно тот же
запрос, а существующие вызовы сохраняют прежний смысл.

Любой другой терминал на команде со слотом отвергается по имени: коллекционная проекция вычисляется после
материализации, поэтому терминал, которому пришлось бы её стримить или агрегировать (например
`ToEnumerable()`), бросает `NotSupportedException` до исполнения любого SQL.

## Спроецированные ссылки и кардинальность

Проекция, несущая коллекционный слот, может также проецировать **ссылочную** навигацию (`Comment.Author`) на
любом уровне. Такая ссылка сохраняет контракт ссылочной жадной загрузки, ограниченный этой проекцией:

- нет совпадения → `null`;
- одна различимая идентичность → материализованная сущность;
- **больше одной различимой идентичности на одного родителя** → `InvalidOperationException` до того, как станет
  наблюдаема хоть одна спроецированная строка:

```
The reference navigation 'Comment.Author' matched more than one distinct 'Author' for a single parent;
a reference navigation requires at most one related row per parent.
```

Повторяющиеся физические строки с одной идентичностью (один и тот же автор, попавший в картезианское
произведение дважды) допускаются и схлопываются в один экземпляр. Исключение возникает во время материализации —
до запуска проектора, — поэтому наружу не может уйти ни частично заполненный список, ни частично
спроецированный DTO.

## Пустое значение и `null`

Два вида отсутствия остаются различимыми на любом уровне:

| Ситуация | Значение |
|---|---|
| объявленная коллекция без строк (отфильтрованы, выпали из страницы или их нет вовсе) | **пустая коллекция** |
| спроецированная ссылка без подходящей строки | **`null`** |
| ссылка присутствует, дочерние строки присутствуют | сущности и коллекции |

Родитель без дочерних строк никогда не выпадает из результата: коллекция пуста, а строка родителя остаётся.

## Отвергаемые формы до любого SQL

Всё, что поверхность v1 выразить не может, отвергается **при связывании проекции** — до построения SQL, до
исполнения любой команды и до вставки записи в план. Каждый отказ ниже наблюдался при **0 инструкций** и
является `NotSupportedException`:

| Отвергаемая форма | Пример | Что называет сообщение |
|---|---|---|
| `GroupBy` внутри адаптера | `p.Comments.AsEntityBuilder<Comment>().GroupBy(c => c.AuthorId)…` | белый список операторов адаптера |
| `Distinct`, `Union`, `Except`, `Intersect` или соединение внутри адаптера | `…AsEntityBuilder<Comment>().Distinct()…` | белый список операторов адаптера |
| явная группировка, скомпонованная с проекцией | `GroupBy` / `SelectGroup` вместе со слотом | *"cannot be combined with grouping"* |
| внешний терминал, отличный от `ToList`/`ToArray` | `.ToEnumerable()` на команде со слотом | *"supports only ToList() and ToArray()"* |
| провайдер in-memory | любой слот над `InMemoryDataContext` | *"requires a SQL provider"* |
| неподдерживаемая форма назначения | `HashSet<T>`, `object`, собственный коллекционный тип | список семи форм |
| коллекционное выражение, не являющееся слотом | `p.Comments.ToHashSet()`, LINQ-композиция по «голой» навигации | *"not a supported collection slot"* |
| вложенный слот во встроенной дочерней форме | дочерний `new { … }` в прямой форме, несущий слот | *"nested slot must be declared inside an adapter Select(...)"* |

Отвергнутая проекция не оставляет следа: она не производит ни SQL, ни кэшированного плана, и следующая
корректная проекция на том же контексте исполняется правильно.

## Ограничения v1

1. **Проекция вычисляется в памяти по полностью материализованным сущностям.** SQL выбирает строки сущностей
   (все смапленные колонки родителя и каждого дочернего уровня); конвейер адаптера и форма назначения
   применяются после этого. В этом релизе **нет отсечения колонок в SQL и нет проталкивания колонок DTO** —
   `Select` внутри адаптера сужает спроецированную CLR-форму, а не список выборки SQL.
2. **`Limit` для many-to-many отсекается после загрузки.** Строки связки и связанные дочерние строки каждого
   родителя читаются, после чего **выжившие вхождения** каждого родителя отсекаются до страницы. Число инструкций
   и выбранные колонки — как у слота many-to-many без `Limit`; SQL-партиции `row_number()` по junction в этом
   релизе нет, поэтому страница не уменьшает число прочитанных строк. Постраничный вывод дочернего запроса
   one-to-many сохраняет своё ранжированное SQL-понижение.
3. **Набор операторов адаптера закрыт:** `Where`, `OrderBy`, `OrderByDescending`, `ThenBy`, `ThenByDescending`,
   `Limit`, `Select` с завершением `ToList()`/`ToArray()`. `GroupBy`, `Distinct`, `Union`/`Except`/`Intersect`,
   соединения и `Offset` отвергаются по имени до SQL, как и явная композиция с группировкой, неподдерживаемый
   внешний терминал, ветка in-memory и собственный слот.
4. **Сломанная кардинальность ссылки бросает исключение при материализации.** `InvalidOperationException` с
   именем навигации — до любого частичного результата; повторяющиеся физические строки одной идентичности
   схлопываются штатно.
5. **Отсутствие — это пустая коллекция или `null`:** отсутствующая ссылка проецируется как `null`,
   отсутствующие дочерние строки — как пустая коллекция на любом уровне.
6. **ClickHouse отвергает повторяющиеся псевдонимы списка выборки.** Если два проецируемых источника в одной
   инструкции имеют одинаковые имена свойств (например, ссылка во вложенном графе many-to-many отдаёт
   `ParentId`, а другой уровень — тоже `ParentId`), построитель эмитит два псевдонима с одним именем, и
   ClickHouse падает с `Code: 179 … MULTIPLE_EXPRESSIONS_FOR_ALIAS`; остальные пять провайдеров это принимают.
   Дайте проецируемым свойствам разные имена (физическая колонка при этом не меняется).

| Провайдер | Прямые слоты и слоты через адаптер | Split и single-query |

| PostgreSQL | да | да |
| SQL Server | да | да |
| MySQL | да | да |
| MariaDB | да | да |
