# Неявные навигационные запросы

> **Объявленная** связь превращает навигационное свойство в конструкцию запроса: ссылочное свойство
> можно использовать как скалярную цепочку или проверку присутствия, а коллекционное предоставляет
> ровно четыре прямых терминала (`Any`, `Count`, `LongCount` и свойство `Count`). nextorm разворачивает
> навигацию на сервере в коррелированный подзапрос или `LEFT JOIN`; он никогда не читает CLR-граф
> объектов и не подгружает коллекцию лениво. `Count`/`Count()` материализуются как проверяемый `int`
> (64-битный счёт сужается до `int` только при материализации), а `LongCount()` остаётся 64-битным
> сквозным.

**Предварительные требования:** [Связи и однозапросная загрузка (`JoinInto`)](relationships.md) · [Сущности и метаданные](../getting-started/03-entities-and-metadata.md) · [Соединения (JOIN)](../guide/04-joins.md)

## Обзор

Навигационный запрос доступен, только когда связь **объявлена** в метаданных mapping: `HasMany`/`HasOne`/
`HasOneToOne`/`HasManyThrough` или атрибут [`[Relationship]`](relationships.md). Соглашения
по именам внешних ключей **не** применяются, и член, не участвующий в объявленной связи, никогда не
трактуется как навигация.

При объявленной связи поддерживаются две формы навигации:

* **ссылочная** (`c.Parent`) — цепочки скалярных членов, проверки присутствия и проекция ссылки целиком;
* **коллекционная** (`p.Children`) — четыре прямых терминала ниже и адаптер `AsEntityBuilder<T>`.

Всё управляется метаданными: на провайдере in-memory зарегистрированные наборы данных и метаданные
связей авторитетны, поэтому результат совпадает с SQL-провайдерами даже при пустом или несогласованном
CLR-графе объектов.

Навигационный запрос вычисляет скаляр/кардинальность либо проецирует одну объявленную ссылку или
коллекцию — он никогда не материализует вложенный граф объектов. Чтобы заполнить вложенный граф
коллекций (второй уровень и глубже), используйте `LoadWith` с дочерним запросом, объявляющим
собственный `LoadWith` (см.
[Вложенные графы](eager-loading.md#вложенные-графы-второй-уровень-и-глубже)); чтобы вернуть коллекции на
родителя *внутри спроецированного результата*, используйте
[слот коллекционной проекции](collection-projection.md).

## Ссылочная навигация

### Скалярные цепочки

Цепочка членов через ссылочную навигацию транслируется в связанный источник. nextorm добавляет `LEFT
JOIN` для пути и читает член из присоединённого псевдонима:

```csharp
var rows = ctx.From<Child>()
    .Where(c => c.Id == id)
    .Select(c => new { c.Id, ParentName = c.Parent!.Name })
    .ToList();

// select c.Id, p.Name
// from child as c
// left join parent as p on c.ParentId = p.Id
```

Разворачивание ссылки всегда **`LEFT JOIN`** — у связи нет флага обязательности, а `INNER` молча
отбросил бы ребёнка с висячим внешним ключом. Поэтому висячий внешний ключ даёт `NULL`, и
`c.Parent!.Name` материализуется как `null`.

Цепочка может пересекать более одного ссылочного перехода (`c.Parent!.Parent!.Name`): nextorm добавляет
по одному `LEFT JOIN` на переход, и отсутствие распространяется на каждом переходе, поэтому пропавший
промежуточный родитель остаётся отсутствующим, а не «воскресает» через ключ по умолчанию. Self-ссылки
(`n.Parent!.Name` у самореферентной сущности) и два ссылочных пути с одним и тем же CLR-типом
(`o.Buyer`, `o.Seller`) тоже поддержаны: каждый объявленный путь (корень + путь членов + лексическая
область) привязывает собственный псевдоним, и пути никогда не сливаются по CLR-типу. Повторное
использование одного пути в `Where`, `Select` и `OrderBy` по-прежнему соединяет его один раз.

### Проверки присутствия

`c.Parent == null` / `c.Parent != null` проверяют фактическое существование связанной строки по
non-nullable идентифицирующему principal-ключу связи, а **не** по одному значению внешнего ключа.
Ребёнок, чей внешний ключ указывает на отсутствующего родителя, считается **отсутствующим**:

```csharp
var withParent = ctx.From<Child>().Where(c => c.Parent != null).ToList();
var withoutParent = ctx.From<Child>().Where(c => c.Parent == null).ToList();
```

Проверка присутствия может пересекать более одного ссылочного перехода (`c.Parent!.Parent != null`,
`c.Parent!.Parent == null`): отсутствующая строка на **первом**, промежуточном или последнем переходе
делает всю цепочку отсутствующей, а `==`/`!=` остаются взаимно согласованными. То же верно и для
провайдера in-memory, где цепочка обходится по зарегистрированным наборам данных, а не по CLR-графу.

### Проекция ссылки целиком

Проекция самой ссылки даёт `null` для отсутствующей строки и полностью материализованную сущность для
присутствующей:

```csharp
var rows = ctx.From<Child>()
    .Select(c => new { c.Id, Parent = c.Parent })
    .ToList();

var present = rows[0].Parent;   // principal-сущность, либо
var absent = rows[1].Parent;    // null, когда внешний ключ висячий

// select c.Id, p.Id, p.Age, p.Name
// from child as c
// left join parent as p on c.ParentId = p.Id
```

Проекция ссылки целиком поддерживается на всех провайдерах, включая in-memory. Провайдер in-memory
разрешает сущность (или `null`) по отображённым foreign/principal-ключам против зарегистрированного
набора данных — он никогда не читает заполненный CLR-граф навигации приёмника, поэтому даже
несогласованный граф даёт сущность, корректную по FK. Проекция коллекции, достигнутой через
отсутствующую ссылку, даёт пустую коллекцию, а не ошибку.

### Null-контракт

Nullable-скаляр, полученный из ссылки, следует SQL-null-семантике `LEFT JOIN`:

```csharp
var rows = ctx.From<Child>()
    .Select(c => new
    {
        c.Id,
        Age = (int?)c.Parent!.Age,          // SQL NULL, когда родителя нет
        AgeOrDefault = (int?)c.Parent!.Age ?? 0,
    })
    .ToList();
```

**Unlifted** non-nullable скаляр (`c.Parent!.Age` типа `int`), родитель которого может отсутствовать,
отклоняется при подготовке с [`QueryPreparationException`](xref:NextORM.Core.QueryPreparationException),
называющим путь навигации и тип результата, вместо тихого чтения `default(int)`. Приведите член к
nullable-типу или задайте явный fallback (`?? 0`).

Null-компенсация согласована в предикатах и в bool/value-проекциях, включая инвертированные формы:
`c.Parent!.Name != "x"`, её отрицание `!(c.Parent!.Name == "x")`, nullable-операнд
`c.Parent!.Score == null` и дизъюнкцию, допускающую строки без родителя
(`c.IsActive || c.Parent!.Name == "x"`). Ребёнок с висячим внешним ключом участвует с SQL-семантикой
`NULL` — он **включается** в `!=`/отрицание/`OR` — вместо тихого отбрасывания или сравнения со
значением по умолчанию.

### Ссылки внутри коррелированного предиката

Ссылочную навигацию можно использовать и **внутри коррелированного подзапроса** — тела
`EXISTS`/`IN` или коррелированного скалярного подзапроса, — где переход разрешается на внешнем
запросе, а вложенное тело сравнивает с присоединённым псевдонимом:

```csharp
var inner = ctx.From<Child>();

var hop1 = ctx.From<Parent>()
    .Where(p => SqlFunctions.Sql.exists(inner.Where(c => c.ParentId == p.Id && c.GroupCode == p.Group!.Code)))
    .Select(p => p.Id)
    .ToList();

// select t1.id
// from parent as t1
// left join group as t2 on t1.group_id = t2.id
// where exists(select * from child as t3 where (t3.parent_id = t1.id and t3.group_code = t2.code))
```

Разворачивание принадлежит **внешней** команде: её join выдаётся один раз на внешнем запросе, а
присоединённый псевдоним регистрируется как outer reference вложенной команды, поэтому
коррелированное тело читает `t2.code`, а не несёт навигацию свободным параметром. Более глубокая
цепочка (`c.Group!.Root!.Label`, переход 2+) добавляет по одному `LEFT JOIN` на переход на внешней
команде и читает самый глубокий псевдоним внутри тела — глубина перехода не является особым случаем:

```csharp
var hop2 = ctx.From<Parent>()
    .Where(p => SqlFunctions.Sql.exists(inner.Where(c => c.ParentId == p.Id && c.GroupCode == p.Group!.Root!.Label)))
    .Select(p => p.Id)
    .ToList();

// ... left join group as t2 on t1.group_id = t2.id
//     left join root as t3 on t2.root_id = t3.id
// ... exists(select * from child as t4 where (t4.parent_id = t1.id and t4.group_code = t3.label))
```

В этой позиции работают все три ссылочные формы:

* **скалярное сравнение** с членом ссылки (`c.GroupCode == p.Group!.Code`);
* **проверка присутствия** по самой ссылке (`p.Group != null` / `p.Group == null`, рендерится как
  `t2.id is not null` / `t2.id is null` по присоединённому principal-ключу);
* **скалярная проекция** коррелированным подзапросом (`.Select(c => p.Group!.Code)`) — скалярное
  значение ссылки, а **не** жадная загрузка объекта целиком.

Один и тот же ссылочный путь, использованный двумя коррелированными предикатами одной команды,
переиспользует один присоединённый псевдоним (один `LEFT JOIN`, оба коррелированных тела читают его).
Null-семантика следует внешнему `LEFT JOIN`: висячий внешний ключ даёт `NULL` присоединённого ключа,
поэтому коррелированное сравнение неопределённо и строка не совпадает; nullable внешний ключ со
значением `NULL` тоже никогда не совпадает; а отсутствующая строка на промежуточном переходе цепочки
2+ делает отсутствующим весь переход. Проверка присутствия внутри тела проверяет non-nullable
идентифицирующий principal-ключ самого глубокого перехода — в точности как вне коррелированного
предиката, поэтому `!=`/`==` и цепочка с nullable-FK остаются взаимно согласованными.

Это **предикатная/скалярная** форма: она не добавляет ни коллекционных возможностей, ни новой формы
соединения и никогда не откатывается к `APPLY`/`LATERAL` на каждого родителя. Выдаваемая форма —
портируемый `LEFT JOIN` плюс коррелированный `EXISTS`/скалярный подзапрос на каждом SQL-провайдере:

| Провайдер | Ссылочный переход внутри коррелированного предиката | Статус |
|---|---|---|
| SQLite | да | SQL-форма + live (в т.ч. отсутствие `APPLY`) |
| PostgreSQL | да | SQL-форма + shared live |
| SQL Server | да | SQL-форма + shared live |
| MySQL | да | SQL-форма + shared live |
| MariaDB | да | SQL-форма; live отложен (триггер: отдельный live-harness или расхождение с MySQL) |
| ClickHouse | да | SQL-форма (без `APPLY`); live отложен (триггер: live-фикстура с коррелированным `EXISTS` или изменение формы) |

[Ограничение ClickHouse для коллекции через ссылку](#коллекционная-навигация) не меняется:
поддержан сам ссылочный переход, а *коллекция*, достигнутая через ссылку, по-прежнему отвергается.
Провайдер in-memory в эту матрицу не входит — форма является серверной трансляцией предиката.

## Коллекционная навигация

Объявленная коллекция поддерживает ровно **четыре** parameterless-терминала. Они сворачиваются в
коррелированный подзапрос по связанному источнику — **никогда** в `OUTER`-join, который размножил бы
строки родителей:

| Форма | Результат | Разворачивание |
|---|---|---|
| `p.Children.Any()` | `bool` | коррелированный `EXISTS` |
| `p.Children.Count()` | `int` | коррелированный 64-битный `COUNT_BIG`; проверяемое сужение до `int` только при материализации |
| `p.Children.LongCount()` | `long` | коррелированный 64-битный `COUNT_BIG` сквозным (без сужения) |
| `p.Children.Count` (свойство) | `int` | то же, что `Count()` |

```csharp
var rows = ctx.From<Parent>()
    .Select(p => new
    {
        p.Id,
        HasChildren = p.Children.Any(),
        ChildCount = p.Children.Count(),
        ChildCount64 = p.Children.LongCount(),
        ChildCountProperty = p.Children.Count,
    })
    .ToList();
```

Пустая коллекция даёт `false`/`0`/`0`/`0`. `Count()` и свойство `Count` вычисляются на
**64-битном счёте внутри базы**: SQL эмитит широкий счёт `COUNT_BIG` без сужающего преобразования,
поэтому **предикат**, **bool-проекция** или **арифметика** над счётом сравнивают/комбинируют истинное
широкое значение и всегда точны — усечения или переполнения не происходит. Проверяемое сужение до `int`
происходит **только там, где материализуется `int`** — скалярная проекция или член проекции типа `int`
— и бросает нетронутый `OverflowException` на **каждом** провайдере,
когда счёт превышает `Int32.MaxValue`. `LongCount()` возвращает настоящий 64-битный счёт сквозным (без
сужения). Провайдер in-memory следует той же границе: `Count()` и свойство `Count` совпадают с
`Enumerable.Count` и бросают `OverflowException` для каждого потребителя, а `LongCount()` остаётся
64-битным.

### Кардинальность и дубликаты

Прямые терминалы сообщают кардинальность **объявленной связи**:

* коллекция one-to-many считает подходящие строки детей;
* коллекция many-to-many считает **junction-строки, у которых отображённый ребёнок существует** —
  junction-строка с отсутствующим ребёнком (**висячая связь**) исключается, не считается и не делает
  коллекцию непустой;
* дублирующиеся junction-строки, ссылающиеся на одного и того же существующего ребёнка, считаются
  каждая — они не дедуплицируются и неявный `DISTINCT` не применяется;
* коллекция many-to-many, у которой все junction-строки висячие, даёт `false`/`0`/`0`/`0`.

## Адаптер: `AsEntityBuilder<T>`

**Коллекционную** навигацию можно адаптировать к полноценному
[`EntityBuilder<T>`](xref:NextORM.Core.EntityBuilder`1) через `AsEntityBuilder<T>` и затем использовать с
теми же прямыми терминалами:

```csharp
ctx.From<Parent>()
    .Select(p => new
    {
        p.Id,
        Has = p.Children.AsEntityBuilder().Any(),          // T выводится из ICollection<Child>
        Count = p.Children.AsEntityBuilder<Child>().Count(),
    });
```

Адаптер — это маркер: он должен находиться **внутри дерева выражения запроса**, где транслятор
разрешает приёмник в объявленный навигационный путь. Вызов его как обычного метода — вне дерева
выражения, в том числе на захваченной коллекции — всегда бросает
[`NotSupportedException`](xref:System.NotSupportedException); он никогда не возвращает null- или
default-маркер. Захваченный `IEnumerable` — это обычная in-memory-коллекция, а не навигация.

Публичная поверхность также предоставляет **ссылочную** перегрузку `AsEntityBuilder<T>(object?)`,
которую нужно вызывать с явным generic-аргументом, чтобы она не перехватывала вывод коллекционной формы
(`c.Parent!.AsEntityBuilder<Parent>()`). Она даёт ссылочную семантику на SQL и in-memory: `Any()`
проверяет присутствие, а `Count()`/`LongCount()` возвращают `1`, когда ссылка присутствует, и `0`, когда
она отсутствует — в точности как `c.Parent != null`. Проекция самого **маркера** адаптера (а не одного из
этих терминалов) и LINQ-композиция после адаптера по-прежнему не поддерживаются и падают закрыто.

Адаптер — это поверхность **запроса**: он отвечает про присутствие и количество внутри запроса. Заполнение
навигации у уже материализованных родителей — задача [`LoadWith`](eager-loading.md): его форма с
объявленными метаданными (`LoadWith(navigation)` / `LoadWith(navigation, childQuery)`) читает ту же
объявленную связь, которую транслирует эта страница, и возвращает сущности с заполненной навигацией (см.
[Форма с объявленными метаданными](eager-loading.md#форма-с-объявленными-метаданными)). Коллекционный слот
`Select` и композиция `AsEntityBuilder … Where/OrderBy/Limit/Select(...).ToList()` — **отдельная поверхность
проекции**: она поставлена, со своими ограничениями v1, в
[Слотах коллекционной проекции](collection-projection.md) — проекция возвращает коллекции на родителя внутри
формы результата и не является альтернативой загрузке через `LoadWith`. Запреты ниже описывают адаптер как
конструкцию запроса (`Any`/`Count`/`LongCount`); адаптер в проекции подчиняется правилам своей страницы.

## Провайдеры

| Провайдер | Ссылочные цепочки / присутствие | Ссылка целиком | Коллекционные терминалы | In-memory |
|---|---|---|---|---|
| SQLite | да | да | да | да |
| PostgreSQL | да | да | да | да |
| SQL Server | да | да | да | да |
| MySQL / MariaDB | да | да | да | да |
| ClickHouse | да | да | да | да |
| In-memory | да | да | да | — |

На ClickHouse запросу со ссылочной навигацией нужны настоящие SQL `NULL` на неприсоединённой стороне
внешнего join'а. nextorm подставляет `join_use_nulls = 1` **локально для запроса** — только для запроса
с разворачиванием ссылки, никогда как сессионную или глобальную настройку — и отклоняет явный
конфликтующий `join_use_nulls = 0` до исполнения.

Коллекция, достигнутая **через ссылку** (`child.Parent.Children`), на ClickHouse недоступна. Это
**принятое ограничение провайдера** (одобрено), а не дефект: движок не умеет коррелировать подзапрос
по присоединённому источнику, поэтому nextorm отклоняет эту форму явным
[`NotSupportedException`](xref:System.NotSupportedException) (*«cannot correlate a subquery on a joined
source»*) вместо генерации SQL, на котором движок падает. Запрашивайте коллекцию из её собственного
источника или используйте явное соединение.

На провайдере in-memory зарегистрированные наборы данных и объявленные метаданные авторитетны:
заполненное навигационное свойство никогда не читается, и результат совпадает с SQL-провайдерами даже
при пустом или несогласованном CLR-графе. Если у связанного типа объявленной навигации нет
зарегистрированного набора данных/mapping, подготовка бросает
[`BuildSqlCommandException`](xref:NextORM.Core.BuildSqlCommandException) с именем таблицы
(`Table name is not registered`) — обычная диагностика missing-source, а не тихий пустой/`null`
результат.

Сгенерированный SQL, ключ плана и возвращаемые строки одинаковы для холодного плана, попадания в тёплый
кэш и неподготовленного (prepared) прогона. Навигационный запрос не отключает общий кэш планов
`.Any()`/`.Count()`.

## Ограничения и отклоняемые формы

Неявная навигация — намеренно узкая поверхность. Следующее отклоняется с
[`NotSupportedException`](xref:System.NotSupportedException) (а unlifted-скаляр — с
[`QueryPreparationException`](xref:NextORM.Core.QueryPreparationException)) и никогда не откатывается к
клиентскому исполнению:

* **Перегрузки с предикатом** у `Any`/`Count`/`LongCount` (`p.Children.Any(c => ...)`,
  `p.Children.Count(c => ...)`, `p.Children.LongCount(c => ...)`).
* **Прямая LINQ-композиция** по коллекционной навигации — `Where`, `OrderBy`/`OrderByDescending`,
  `Select`, `Skip`, `Take`, `Distinct`, `GroupBy`, `GroupJoin`, `SelectMany`, join'ы, set-операции
  (`Union`/`Except`/`Intersect`) и материализация (`ToArray`/`ToList`). Компонуйте их через адаптер
  `AsEntityBuilder<T>` [слота коллекционной проекции](collection-projection.md) (только поддерживаемое
  подмножество).
* **Дополнительные терминалы** — `First`/`First(predicate)`, `Single`/`SingleOrDefault`,
  `Last`/`LastOrDefault`, `Contains`, `Sum`, `Average` и другие агрегаты.
* **Захваченные и внешние маркеры** — захваченный enumerable не является навигацией, а
  `AsEntityBuilder` вне дерева выражения запроса всегда бросает.
* **Необъявленные навигации** — ссылочный или коллекционный член без объявленной связи не выводится по
  соглашению.
* **Навигация в ключах группировки/пейджинга** — `GROUP BY`, `DISTINCT ON`, `LIMIT BY` и ключи
  экстремальной строки не вычисляют навигацию (используйте там явные соединения).
* **Навигация по temp-table/TVP-источнику** — отложена: читающий источник ленивой временной таблицы
  (`ctx.From(tempTableSource)`) — это нетипизированный `TableAlias` без навигационной поверхности,
  поэтому член навигации по нему прочитать нельзя. Триггер — источник навигации, скомбинированный с
  temp-table/TVP-путём. Навигация, объявленная **до** границы временной таблицы, по-прежнему
  разворачивается в материализующий `CREATE TEMPORARY TABLE ... AS SELECT`; стройте навигацию по строкам
  временной таблицы через явное соединение или из mapped-источника.
* **LINQ-композиция после адаптера вне слота проекции** — цепочки операторов после `AsEntityBuilder<T>` не
  являются конструкцией запроса: как навигационный запрос адаптер распознаёт только прямые терминалы.
  Единственная поставленная композиция — [слот коллекционной проекции](collection-projection.md), где адаптер
  продолжается конвейером `Where`/`OrderBy`/`ThenBy`/`Limit`/`Select` на родителя с завершением
  `ToList()`/`ToArray()`.
* **Проекция самого ссылочного адаптера** — проекция маркера ссылки как такового
  (`Select(c => new { X = c.Parent!.AsEntityBuilder<Parent>() })`) не является колонкой и отклоняется;
  используйте терминалы `Any`/`Count`/`LongCount`.
* **Это не поверхность загрузки** — адаптер и перечисленные выше формы композиции никогда не заполняют
  навигацию. Загрузка объявленной навигации выполняется через [`LoadWith`](eager-loading.md) на
  родительском запросе, и его форма с объявленными метаданными читает ту же объявленную связь.
  [Слот коллекционной проекции](collection-projection.md) — третья, проекционная форма: он возвращает
  коллекцию на родителя внутри спроецированного результата, а не заполняет навигацию сущности.

### Составные ключи связи

Связь может охватывать несколько компонентов. Ссылочный, коллекционный и many-to-many SQL-маршруты
коррелируют по **каждому** объявленному компоненту в порядке объявления — не по одной колонке и не
только по первому компоненту. Null-семантика по компонентам следует SQL: любой null-компонент внешнего
ключа не даёт связи (проверка присутствия сообщает, что связанной строки нет, а скалярная цепочка даёт
`null`), и сопоставления **`null == null`** нет — null-компонент внешнего ключа никогда не совпадает с
null-компонентом principal-ключа. Компоненты сопоставляются позиционно, а списки компонентов приходят из
метаданных связи (см. [Упорядоченные селекторы ключей](relationships.md#упорядоченные-селекторы-ключей)).

Эта составная область — только SQL-маршруты. In-memory-провайдер сохраняет прежнюю границу: составной
ключ связи по-прежнему отклоняется его навигационным путём с `NotSupportedException` (объявление и
метаданные провайдер-нейтральны, но компонентное сопоставление в in-memory не добавляется). Для составной
implicit-навигации используйте SQL-провайдер.

Для явной, полнофункциональной поверхности связей используйте
[`JoinInto`](relationships.md) и явные операторы соединения; общие границы — в
[Ограничениях](../advanced/limitations.md).
