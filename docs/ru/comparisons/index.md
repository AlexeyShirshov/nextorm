# Сравнения: Nextorm против Dapper, linq2db и EF Core

Этот раздел поможет выбрать библиотеку по нужным приложению возможностям запросов, провайдерам и
способу изменения данных. Здесь Nextorm сравнивается с библиотеками, с которыми её чаще всего
сопоставляют; оценки — снимок на определённую дату, а не универсальный рейтинг:

| Библиотека | Профиль |
|---|---|
| **Dapper** | Микро-ORM: рукописный SQL плюс маппинг объектов; без LINQ и без отслеживания изменений. |
| **linq2db** | Зрелая LINQ-to-SQL ORM: связи, отслеживание изменений, широкий набор провайдеров и database-first-инструменты. |
| **Entity Framework Core** | Полноценная ORM: отслеживание изменений, связи, миграции и LINQ. |

Nextorm — это **конструктор запросов и мапер без отслеживания изменений**. Он поддерживает запросы
для отчётности и анализа, а также явные команды записи по существующей схеме. Nextorm генерирует
SQL, переносимый между провайдерами; результаты бенчмарков охватывают только поставляемые сценарии.

Сравнение состоит из четырёх частей:

- **[Возможности](capabilities.md)** — одна матрица на уровне конструктов: что поддерживает каждая
  библиотека и где нет.
- **[Функции провайдеров](provider-features.md)** — ширина API по каждому движку против linq2db.
- **[Бенчмарки](benchmarks.md)** — поставляемые сценарии на SQLite со ссылками на полные отчёты BenchmarkDotNet.
- **[Feature-бенчмарки](feature-benchmarks.md)** — результаты по отдельным возможностям,
  сгруппированные по форме запроса. Здесь показан только неявный кэш планов Nextorm, без прогонов
  `Prepare()`, а библиотеки расположены в столбцах.

## Как читать оценки

- **yes** — библиотека предоставляет возможность напрямую через документированный API.
- **partial** — возможность поддерживается с оговорённым ограничением либо ещё не реализована, хотя
  её можно реализовать.
- **no** — возможность не поддерживается.

Оценки — это суждения по **публичной документации** каждой библиотеки на **2026-10-04**. Если у конкурента
есть открытый issue по пробелу, он указан ссылкой. В ячейке Nextorm ограничение, налагаемое самой СУБД,
называется в скобках; оценку это не понижает. Это лишь сводка — [руководство](../engine/index.md)
и [справочник API](../advanced/api-reference.md) авторитетны для Nextorm, а документация конкурента —
для конкурента.

## Область и честность сравнения

- Оценки описывают библиотеку, а не конкретную СУБД. Ограничения провайдера указаны в
  соответствующих ячейках.
- Бенчмарки проведены на одной машине и одном провайдере (SQLite). Это ориентир для указанных
  сценариев, а не гарантия для другой нагрузки; методика и оговорки приведены на странице
  [бенчмарков](benchmarks.md).
- Сравнение посвящено **пересечению возможностей**. Моделирование связей и отслеживание изменений —
  осознанные границы Nextorm, а не недостающие реализации заявленных возможностей.

## Где Nextorm впереди

В пересекающихся конструктах матрицы Nextorm не уступает этим трём библиотекам или превосходит их.
Ниже перечислены дополнительные возможности; указанные ограничения конкретных провайдеров
по-прежнему действуют:

- **Полную аналитическую поверхность запросов**: все типы соединений, включая `APPLY`/`LATERAL`,
  соединения с производными таблицами, строгость соединений/`GLOBAL` в ClickHouse, `DISTINCT` (плюс
  `DISTINCT ON`/`WITH TIES`/`TABLESAMPLE`), CTE (рекурсивные, а в PostgreSQL — модифицирующие), оконные
  функции (именованные окна, `GROUPS`, `EXCLUDE` кадра), `ROLLUP`/`CUBE`/`GROUPING SETS`, временные
  таблицы (`FOR SYSTEM_TIME`), блокировки строк и хинты уровня инструкции/таблиц/индексов.
- **Полную явную поверхность записи** без отслеживания изменений: `INSERT`/`UPDATE`/`DELETE`/полный
  `MERGE`, массовая вставка (`COPY`/`SqlBulkCopy` или чанковый `VALUES`), `CREATE TABLE AS SELECT`/
  временные таблицы и транзакции — всё явные команды, без `SaveChanges`.
- **Больше поверхности типов и маппинга**: нативный `Range<T>` (и маппинг `[RangeColumns]` парой,
  которого у других нет), массивы и функции высшего порядка, row values/кортежи, динамические схемы
  результата, поиск по захваченной коллекции и необязательный класс сущности.
- **Настраиваемый вывод SQL**: включаемые явно квотирование идентификаторов, соглашения об именовании и
  регистр ключевых слов, переопределяемые для отдельной команды, — тогда как linq2db квотирует по
  умолчанию и фиксирует имена в схеме отображения.
- **Расширяемость через компоненты запроса.** Сторонний разработчик может добавить структурный
  оператор, меняющий генерируемый SQL, например дополнительный предикат или изменённый источник
  строк.
  Новый оператор сохраняет кэш планов, привязку параметров и независимость от провайдера обычного
  запроса.
  Для этого не нужны friend-доступ, глобальный реестр или сырой SQL. В linq2db и EF Core есть
  интерцепторы и маппинг функций, но нет структурного контракта компонентов с интеграцией кэша
  планов.
- **Zero-config миграция на NativeAOT.** В проверенной области (все шесть провайдеров на .NET 11 /
  `linux-x64`) потребителю достаточно изменить только `PublishAot=true`. Не нужны compiled model,
  precompilation, opt-in анализатора или интерцепторов, регистрация сущностей и запросов, linker-
  дескрипторы или roots. EF Core требует compiled model и interceptor-based precompilation запросов
  и
  не поддерживает динамически компонуемые запросы. Dapper требует пакет `Dapper.AOT`,
  `[module: DapperAot]`, свойство `InterceptorsNamespaces` и статически известный SQL. linq2db
  официально не поддерживает
  NativeAOT.

  На приложении отчётов по SQLite объёмом 13 ГБ Nextorm опубликовался нативно без изменений
  исходников
  (бинарный файл 8.2 MB, 0.12 s, 30 MB RSS); публикация EF Core дала 17.3 MB / 0.23 s / 42 MB после
  двух обходных решений для кодогенерации. Измеренная поддержка охватывает все шесть провайдеров, но
  остаётся неполной: EF Core bridge, массовая вставка, маппинг сырого SQL и DML-билдеры остаются на
  JIT
  ([#370](https://github.com/AlexeyShirshov/nextorm/issues/370)). Преимущество — стоимость миграции,
  а не полный паритет возможностей под AOT. См. [руководство по
  NativeAOT](../infrastructure/05-nativeaot.md).
- **Производительность по бенчмаркам**: быстрейший на каждом end-to-end сценарии, быстрейший на
  каждом сценарии с явной подготовкой запроса (с наименьшими аллокациями везде, кроме IN-списка) и
  опережает обычные
  linq2db и EF Core при повторных запросах с кэшем (см. [бенчмарки](benchmarks.md)).

## Точки роста

Работа, которая ещё предстоит в рамках заявленной области, отделена от осознанных границ. Это
помогает отличить недостающую реализацию от функции, которую Nextorm не ставит целью предоставлять:

- **Производительность при повторных запросах с кэшем**: неявный кэш планов всё ещё отстаёт от
  Dapper примерно в 1.32–1.75× на
  соединении четырёх таблиц, CTE, рекурсивном CTE и IN-списке (как инлайн, так и захваченном).
  Аллокаций при этом больше, чем в подготовленном режиме; работа над разрывом идёт (см.
  [бенчмарки](benchmarks.md)).
- **Интеграция с EF Core**: адаптер `ToNextOrm` транслирует лишь ограниченный набор операторов —
  `Select`, `Include`/навигации, `Join`, `GroupBy`, `EF.Property`/`EF.Functions`,
  `AsSplitQuery`, raw-SQL-источники и подзапросы не транслируются, — а слайсы общей транзакции MariaDB и
  отсутствия EF-адаптера у ClickHouse остаются открытыми (см.
  [Интеграция с EF Core](../advanced/integration-efcore.md)).
- **Eager loading и связи**: eager loading `LoadWith` покрывает конечные вложенные графы (второй уровень и
  глубже, с единым режимом на граф и порядком/top-N на каждом уровне) в split- и выразимом single-query-режиме;
  `JoinInto` соединяет и группирует по каждому объявленному компоненту ключа, включая составные внешние,
  principal- и junction-ключи, а загрузка M:N-графа одним запросом eager loading по-прежнему вне области.
- **Более глубокие формы запросов**: `SelectMany`/`GroupJoin` не транслируются на SQL-провайдерах,
  `APPLY`/`LATERAL` не принимает проекцию соединения, а корреляция in-memory ограничена глубиной один.
- **Динамическая сборка SQL**: сборка SQL во время выполнения остаётся вне поверхности конструктора.
- **Нативные типы за гейтом провайдера**: нативные range/multirange, нативные JSON-колонки и массивы
  доступны не у всех провайдеров; остальные используют маппинг парой/текстом либо отклоняют их.
- **Широта провайдеров**: меньше провайдеров, чем у linq2db и EF Core (нет Oracle, Firebird, DB2,
  SAP HANA, Informix, Sybase и SQL CE).

Моделирование связей, отслеживание изменений/`SaveChanges`, миграции и кодогенерация под существующую БД —
**осознанные границы**, а не точки роста; они перечислены в
[«Ограничениях и функциях вне области»](../advanced/limitations.md). Две границы композиции — того же рода:
коррелированный `APPLY` расширяет существующую цепочку соединений, но останавливается на восьми источниках
всего, а in-memory-провайдер ограничивает коррелированные подзапросы глубиной один, тогда как каждый
SQL-провайдер вкладывает их произвольно. Самому `APPLY`/`LATERAL` нужен lateral-источник: MariaDB 11.4,
SQLite и ClickHouse отклоняют его до исполнения, а провайдер in-memory не поддерживает его. Это границы
формы API и провайдеров, а не отсутствующие возможности SQL, — поддерживаемые формы описаны в
[матрице возможностей](capabilities.md) и в руководстве.

## Итог

Для чтения, отчётности и явного изменения данных по существующей схеме стоит рассмотреть Nextorm,
если его возможности и ограничения провайдеров подходят приложению. Он генерирует переносимый SQL
для SQL Server, PostgreSQL, MySQL/MariaDB, SQLite и ClickHouse, поддерживает широкий набор запросов
и позволяет явно выполнять запись без накладных расходов на отслеживание изменений. На поставляемых
сценариях его результаты бенчмарков не ниже результатов Dapper, EF Core и linq2db; эти замеры
сделаны на SQLite и не предсказывают поведение любой нагрузки.

В проверенной области NativeAOT для публикации Nextorm достаточно `PublishAot=true`; EF Core требует
compiled model и precompilation запросов, а Dapper — пакет `Dapper.AOT` и opt-in интерцепторов.
Dapper остаётся самым лёгким вариантом для рукописного SQL с маппингом объектов. linq2db и EF Core
стоит выбирать, когда тот же слой должен моделировать связи, отслеживать изменения или генерировать
слой данных по живой схеме — возможности, которые Nextorm сознательно оставляет в стороне.
