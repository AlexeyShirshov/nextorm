# Сравнения: Nextorm против Dapper, linq2db и EF Core

Этот раздел — краткое сравнение Nextorm с библиотеками, с которыми её чаще всего сопоставляют, **на
определённую дату**:

| Библиотека | Профиль |
|---|---|
| **Dapper** | Микро-ORM: рукописный SQL плюс маппинг объектов; без LINQ и без отслеживания изменений. |
| **linq2db** | Зрелая LINQ-to-SQL ORM: связи, отслеживание изменений, широкий набор провайдеров и database-first-инструменты. |
| **Entity Framework Core** | Полноценная ORM: отслеживание изменений, связи, миграции и LINQ. |

Nextorm — это **конструктор запросов и мапер без отслеживания изменений**: он покрывает аналитическую
поверхность запросов и явную поверхность записи, генерирует переносимый между провайдерами SQL и
бенчмаркится на поставляемых сценариях.

Сравнение состоит из двух частей:

- **[Возможности](capabilities.md)** — матрица по категориям: что поддерживает каждая библиотека и где нет.
- **[Бенчмарки](benchmarks.md)** — поставляемые сценарии на SQLite со ссылками на полные отчёты BenchmarkDotNet.

## Как читать оценки

- **yes** — поддержка первого класса.
- **partial** — поддержка с оговорённым ограничением либо реализуемо, но не реализовано.
- **no** — не поддерживается.

Оценки — это суждения по **публичной документации** каждой библиотеки на **2026-09-25**. Если у конкурента
есть открытый issue по пробелу, он указан ссылкой. В ячейке Nextorm ограничение, налагаемое самой СУБД,
называется в скобках; оценку это не понижает. Это лишь сводка — [руководство](../guide/01-querying-and-projections.md)
и [справочник API](../advanced/api-reference.md) авторитетны для Nextorm, а документация конкурента —
для конкурента.

## Область и честность сравнения

- Оценки описывают библиотеку, а не конкретную СУБД. Ограничения по провайдерам указаны по месту.
- Бенчмарки — микробенчмарки на одной машине и одном провайдере (SQLite); это сигнал на момент времени, а не
  гарантия. Методика и оговорки — на странице [бенчмарков](benchmarks.md).
- Сравнение намеренно про **пересечение**. Моделирование связей и отслеживание изменений сознательно вне
  области Nextorm и перечислены как таковые, а не как пробелы.

## Где Nextorm впереди

На общей поверхности Nextorm не уступает этим трём библиотекам или превосходит их, а вдобавок даёт:

- **Полную аналитическую поверхность запросов**: все типы соединений, включая `APPLY`/`LATERAL`,
  соединения с производными таблицами, строгость соединений/`GLOBAL` в ClickHouse, `DISTINCT` (плюс
  `DISTINCT ON`/`WITH TIES`/`TABLESAMPLE`), CTE (рекурсивные, а в PostgreSQL — модифицирующие), оконные
  функции (именованные окна, `GROUPS`, `EXCLUDE` кадра), `ROLLUP`/`CUBE`/`GROUPING SETS`, временные
  таблицы (`FOR SYSTEM_TIME`), блокировки строк и хинты уровня инструкции/таблиц/индексов.
- **Полную явную поверхность записи** без отслеживания изменений: `INSERT`/`UPDATE`/`DELETE`/полный
  `MERGE`, массовая вставка (`COPY`/`SqlBulkCopy` или чанковый `VALUES`), `CREATE TABLE AS SELECT`/
  временные таблицы и транзакции — всё явные команды, без `SaveChanges`.
- **Больше поверхности типов и маппинга**: нативный `Range<T>` (и маппинг `[RangeColumns]` парой,
  которого у других нет), массивы и функции высшего порядка, row values/кортежи, динамические схемы
  результата, поиск по захваченной коллекции и необязательный класс сущности.
- **Настраиваемый вывод SQL**: включаемые явно квотирование идентификаторов, соглашения об именовании и
  регистр ключевых слов, переопределяемые для отдельной команды, — тогда как linq2db квотирует по
  умолчанию и фиксирует имена в схеме отображения.
- **Производительность по бенчмаркам**: быстрейший на каждом измеряемом сценарии с наименьшими
  аллокациями на prepared-пути и впереди обычных linq2db и EF Core на warm-пути (см.
  [бенчмарки](benchmarks.md)).

## Точки роста

Честный противовес разделу выше — работа, которая ещё впереди по scope, отдельно от осознанных границ:

- **Производительность на warm-пути**: prepared-путь быстрейший на каждом измеряемом сценарии, но неявный
  кэш планов всё ещё отстаёт от Dapper примерно в 1.15–1.6× на CTE, рекурсивном CTE, соединении четырёх
  таблиц и захваченном IN-списке (инлайн-IN-список — на уровне); работа над разрывом идёт (см.
  [бенчмарки](benchmarks.md)).
- **Интеграция с EF Core**: запланирована, но не поставлена — пакета в духе `linq2db.EntityFrameworkCore`
  пока нет.
- **Хранимые процедуры, динамический SQL и несколько result set**: сырой SQL покрывает запрос целиком, но
  вызов хранимой процедуры и материализация нескольких result set по порядку отложены.
- **Более глубокие формы запросов**: `SelectMany`/`GroupJoin` работают только на in-memory-провайдере,
  `APPLY`/`LATERAL` не принимает проекцию соединения, а корреляция in-memory ограничена глубиной один.
- **Нативные типы за гейтом провайдера**: нативные range/multirange, массивы и нативные JSON-колонки
  сосредоточены в PostgreSQL; остальные провайдеры используют маппинг парой/текстом либо отклоняют их.
- **Широта провайдеров**: меньше провайдеров, чем у linq2db и EF Core (нет Oracle, Firebird, DB2,
  SAP HANA, Informix, Sybase и SQL CE).

Моделирование связей, отслеживание изменений/`SaveChanges`, миграции и кодогенерация под существующую БД —
**осознанные границы**, а не точки роста; они перечислены в
[«Ограничениях и функциях вне области»](../advanced/limitations.md).

## Итог

Для чтения, отчётности и явного изменения данных по существующей схеме Nextorm — более сильный выбор:
переносимый SQL для SQL Server, PostgreSQL, MySQL/MariaDB, SQLite и ClickHouse, широкая поверхность
запросов, явная поверхность записи без накладных расходов на отслеживание изменений и результаты
бенчмарков на уровне или выше Dapper, EF Core и linq2db на поставляемых сценариях. Dapper остаётся самым
лёгким вариантом для рукописного SQL с маппингом объектов; linq2db и EF Core остаются лучшим выбором,
когда тот же слой должен ещё и моделировать связи, отслеживать изменения или генерировать слой данных из
живой схемы — то, что Nextorm сознательно оставляет в стороне.
