## 1. Замысел (Intent), цели и не-цели

### 1.1 Замысел

Цель задачи — **убрать политику оператора `SelectGroup` из ядра (Core)**. Пользователи должны иметь возможность добавлять аналогичные функции (пример — `SelectGroupHaving`) **без будущих изменений Core под каждый новый оператор**.

Корректируется прежнее предположение: наличие в Core сгруппированных SQL-примитивов **не означает**, что вывод ключей (inference) обязан оставаться в Core. Нет необходимости публиковать весь планировщик (planner) — требуется публичный механизм расширения подготовки запросов, достаточный для реализации подобных операторов вне Core.

Ключевая идея: `SelectGroup` — это оператор уровня расширения, который использует публичные возможности Core для анализа проекции и построения SQL, но не является частью политики ядра.

### 1.2 Две архитектурные слои

1. **Core — общие публичные инструменты подготовки запросов (generic public preparation tools).** Core владеет общими SQL-примитивами (GROUP BY/HAVING/DISTINCT/агрегаты), маппингом, материализацией, квотированием, провайдерами, кешами/клонами, валидацией. Core публикует минимальный декларативный механизм вклада в подготовку запроса, достаточный для построения операторов группировки вне Core. Core не содержит политики конкретного оператора `SelectGroup` и не знает имён операторов расширений.
2. **Расширения — подготовленное семейство операторов (prepared operator family).** `nextorm.extensions` реализует `SelectGroup` и `SelectGroupHaving` поверх публичных инструментов Core. Третья сторона ссылается только на Core и может реализовать собственный оператор группировки со своей политикой, не внося изменений в Core и не участвуя в нашем пакете расширений. Реализация внешнего оператора может отличаться от нашей; Core предоставляет инструменты, а не нашу политику.

### 1.3 Не-цели (явно вне scope)

- Никакого reflection emit, динамических типов-носителей ключей (dynamic key carrier types), IVT (in-process test infra / внутренних тестовых примитивов) в публичном механизме.
- Никакого raw SQL, глобального реестра обработчиков (global handler registry), публичного целого планировщика (public whole planner).
- Никакого нового синтаксиса SQL-диалектов, пользовательских SQL-рендереров, общего оптимизатора.
- Обычный `GroupBy`, стандартная трансляция SQL, маппинг, материализация, квотирование и правила провайдеров остаются собственностью движка (engine-owned).
- Удаление `SelectWhereMinOld` / `MaxOld` **не входит** в задачу (принятое ранее решение сохраняет их до выполнения AC6).
- Не заявляется сохранение in-memory поведения (явный отказ).

### 1.4 Цели (требования, одобренные пользователем)

- `SelectGroup` полностью переносится в `nextorm.extensions`.
- В Core не остаётся анализатора, флагов или специальных веток, относящихся к `SelectGroup`.
- `SelectGroupHaving(projection, condition)` обеспечивает ту же логику вывода ключей, что и `SelectGroup`, плюс условие в `HAVING`.
- Публичный механизм не использует IVT/raw SQL и не требует правок Core под каждый оператор.
- Существующая SQL-семантика `SelectGroup` сохраняется.
- In-memory не поддерживается; отсутствие поддержки заявляется явно (явный отказ).
- Нет регрессии производительности относительно текущего `SelectGroup`, включая тёплый кеш планов; нет регрессии накладных расходов для запросов без компонентов.
- Семантические оракулы — прямые ожидаемые значения, а не «паритет с legacy»; живые тесты — в отдельном интеграционном проекте расширений.
- Документация на английском и русском.

## 3. Оператор API (расширения)

**Решения архитектора, предлагаются на ревью письменного дизайна.**

Пакет `nextorm.extensions` предоставляет обычные методы расширения:

- `SelectGroup<TEntity, TResult>(this EntityBuilder<TEntity> source, Expression<Func<TEntity, TResult>> projection)` → `QueryCommand<TResult>`.
- `SelectGroupHaving<TEntity, TResult>(this EntityBuilder<TEntity> source, Expression<Func<TEntity, TResult>> projection, Expression<Func<TEntity, bool>> condition)` → `QueryCommand<TResult>`.

Общая реализация: создание неизменяемого компонента + `source.WithComponent(...).Select(projection)`; **без копирования `SelectCore`**. Условие типизировано по исходному `TEntity`, как существующий `Having` (не `TResult`). Исходное проекционное выражение сохраняется (source projection expression). Нулевые входы бросают `ArgumentNullException`. Пользовательская проекция не изменяется. Существующий source `Having` **AND**-ится с добавленным условием, не заменяется. Ключами становятся **только** проекция; условие никогда не добавляет ключей.

Обе API расширений разделяют одну реализацию вывода (Having — не второй анализатор). In-memory: явный `NotSupportedException` для обоих операторов; отказ происходит в общем компоненте подготовки **до** SQL-пути (unit-тесты без БД).

## 4. Общий аддитивный API дизайна Core

**Решения архитектора, предлагаются на ревью письменного дизайна.** Имена рабочие; окончательная косметическая номенклатура оставлена плану, контракт не опционален.

- Сохраняются существующие `IQueryComponent` / `Prepare` / `BuildQuery` и существующие числовые значения вклада. Не добавляются обязательные члены, ломающие внешние реализации.
- Добавляется **опциональный** публичный интерфейс контекста подготовки (prepare-context), предоставляющий неизменяемый вид на **неподготовленную** проекцию / тип источника / WHERE / HAVING / модификаторы сортировки и группировки, а также обобщённые сервисы классификации выражений и семантического сравнения. Контекст Core реализует его; старые реализации не затронуты.
- Добавляется **опциональный** дескриптор (например, `IQueryPreparationDescriptor : IQueryComponentDescriptor`), несущий неизменяемый декларативный `QueryPreparationContribution`.
- В существующее перечисление добавляется обобщённый вид вклада (например, `ExclusiveGrouping`) — **без** флага, специфичного для `SelectGroup`. Дескриптор объявляет эффекты; **он не должен мутировать** raw-поля `QueryCommand`.
- Публичный результат допускает логическое определение группировки как **упорядоченный вектор скалярных lambda-ключей** (без фабрики типов во время выполнения), переопределение HAVING, аддитивный предикат источника, требование DISTINCT. Переопределение предложения — три состояния (без изменений / очистить / заменить); исходные raw-поля никогда не меняются.
- **«Группировка отсутствует» ≠ «явная область глобального агрегата с нулём ключей»**: объект группировки с пустым набором ключей представляет глобальную агрегацию; непустой набор — ключевую. Core владеет общим рендерингом GROUP BY/HAVING для обоих; в Core нет enum `SelectGroupMode`.
- Политика проекции-константы в пакете: **без** группировки + очистка эффективного HAVING + аддитивный валидированный константный предикат + требование DISTINCT (сохраняет исходные ноль строк при пустом входе). Истинный глобальный агрегат: нулевой ключ группировки + эффективный HAVING. Ключевой: ключи + эффективный HAVING.
- Историческое поведение обычного несгруппированного HAVING **не меняется молча** миграцией: обобщённая нулевая группировка активирует корректный рендеринг только для явного вклада группировки/формы; добавить обычные регрессионные тесты.

## 5. Владение и сервисы

**Решения архитектора, предлагаются на ревью письменного дизайна.**

- Вывод (inference visitor) и валидация покрытия SelectGroup, исключения окон/подзапросов, правила составных скалярных ключей — **в пакете**.
- Удаляются оригинальный анализатор / режим / внутренние флаги `IsSelectGroup` / специальные ветки компаратора планов / in-memory оценщик SelectGroup и позитивные тесты. Общие примитивы обычного in-memory GROUP BY/агрегатов и прочий код сохраняются, если используются независимо (проверка Roslyn-влияния до удаления).
- Core предоставляет обобщённые факты на уровне выражения: агрегат vs скаляр vs окно vs подзапрос, а также точное эффективное разрешение метода/типа через `SqlFunctionAttribute` и встроенные/провайдерные семейства агрегатов (факторизация реально общего из внутренностей в общий сервис, а не выставление всего анализатора). Отдельного реестра агрегатов и дублирующего «магического» списка имён в пакете **нет**.
- Классификация должна совпадать с SQL-трансляцией; аргументы агрегатов с FILTER/DISTINCT — непрозрачны.
- Предоставляется **семантическое равенство выражений**, отличное от свободного от значений равенства формы плана: литералы — по значению, параметры источника — альфа-эквивалентны, цели замыканий — по идентичности ссылки + путь члена, неизвестные узлы — консервативно неравны; без вычисления захваченных значений. Пакет использует его для дедупликации ключей/покрытия; компаратор планов слепо переиспользовать нельзя.
- Движок по-прежнему транслирует подготовленные скалярные выражения группировки через существующие маппинги/конвертеры/защиты multi-column, алиасы/квотирование/материалацию/привязку.

## 6. Жизненный цикл

**Решения архитектора, предлагаются на ревью письменного дизайна.**

Порядок:

1. Исходный неизменяемый логический ввод + объявленные компоненты.
2. Поиск сырого рецепта по исходной форме, включая `IQueryComponentShape`.
3. При промахе: расширение навигации + общий `Prepare`/валидация/дескриптор компонента.
4. Применение декларативных эффектов к **отдельному эффективному состоянию подготовки** **до** `PrepareColumns`/`PrepareGrouping`.
5. Обычная подготовка предложений.
6. Поиск подготовленного ключа плана.
7. При промахе: существующий путь рендера `BuildQuery` с вкладом.
8. Хранение в кеше.

Точное размещение относительно `From`/`Join` может быть выбрано на этапе плана для сохранения корректной привязки выражений, но ввод вывода остаётся сырыми lambda источника, и все вклады применяются до подготовки предложений/поиска ключа плана. Нормализация **не строится** в `BuildQuery` (SQL). Существующие перестроения строк не меняются.

Повторный hit сырого рецепта переиспользует план, свежие параметры, без вывода и реконструкции рендера. Допустим обычный hit подготовленного плана: нормальная подготовка, но без `BuildQuery`.

`ResetPreparation` очищает/перевыводит эффективное состояние. Клоны/клоны кеша несут неизменяемое подходящее состояние. Каждая исходная сырая команда остаётся идентичной через reset/reprepare; накапливающихся AND/DISTINCT **нет**. Все логические эффекты участвуют в равенстве/хеше дескриптора и эффективном ключе плана. Raw-идентичность компонента включает условие наряду с настройками; захваченные значения перепривязываются, не замораживаются.

Требования к производительности пути без компонентов: без аллокаций снимков/состояния вклада и вызовов новых сервисов; без отключения кеша и мутации разделяемой (sticky) команды.

## 7. Композиция

**Решения архитектора, предлагаются на ревью письменного дизайна.**

- Аддитивные предикаты AND-ятся до группировки один раз вместе с пользовательскими/глобальными фильтрами.
- Один слот владельца группировки; тот же слот заменяется, разные слоты группировки — детерминированный отказ подготовки.
- `ExclusiveGrouping` и существующий `ExclusiveRowSource` **взаимно отвергаются** в любом порядке (не обещается произвольное reshape/group-композиция).
- Явные `GroupBy`/`Rollup`/`Cube`/`GroupingSets`/`Totals` конфликтуют — отвергаются **пакетом**, читающим сырой снимок; общий движок обеспечивает владение слотом/записью.
- Требование DISTINCT — монотонное OR на эффективном состоянии; пользовательский DISTINCT не снимается.
- Несовместимые писатели — отказ, не «последний побеждает».
- Наличие общей группировки питает существующие guard'ы eager/JoinInto/проекции коллекций через обычный `.Select` и общие проверки возможностей, **никогда** через проверки имени `SelectGroup`.
- Все неподдерживаемые случаи отвергаются **до** выполнения в БД; отсутствие поддержки бэкенда/диалекта — явно, без тихого отката.

## 8. Семантика (сохраняемое поведение)

**Решения архитектора, предлагаются на ревью письменного дизайна.**

Сохраняется сырая логика вывода: максимальные свободные от агрегатов зависящие от строки подвыражения проекции — первыми, дедупликация по первому появлению; аргументы агрегатов/FILTER/DISTINCT — непрозрачны; WHERE источника игнорируется выводом; все существующие скалярные формы проекции и guard'ы источника; покрытие ключами HAVING и выражения ORDER BY (сначала весь ключ, без вывода функциональной зависимости), существующие правила ordinal; окна/подзапросы отвергаются в исходных контекстах, WHERE-подзапросы допустимы.

Три исхода — **только семантика пакета**: ключевой / глобальный / константный; режимы **не** переносятся в Core. Именование HAVING логическое: условие только из констант использует существующую физическую перезапись SelectGroup в WHERE, а не невалидный HAVING, специфичный провайдеру, для констант. SQL — все шесть провайдеров, включая nullable-ключи, пользовательские атрибуты/функции/конвертеры/алиасы. In-memory удалён по решению пользователя, не регрессия для исправления.

## 9. Миграция

**Решения архитектора, предлагаются на ревью письменного дизайна.**

- Никаких `*Old`/`Ex` алиасов и core-обёрток для `SelectGroup`; тот же выводимый вызов требует пакет + `using NextORM.Extensions`.
- Ломающее бинарное изменение — намеренная релокация; явные generic-вызовы вида `.SelectGroup<Dto>` могут потребовать вывода типов или обоих `<TEntity, TResult>`; документировать, без обещания фиктивной совместимости исходников.
- Обновить все затронутые публичные docs/xref EN/RU, примеры/ссылки пакетов, внешние/алиасные/CTE-вызовы.
- В неактивном генераторе никакого special-casing имён; существующие знания о `SelectGroup` удалить или обобщить до разрешения типа возврата, если активные релевантные тесты докажут необходимость.
- Снимки PublicAPI при наличии — обновить.
- Удаление `SelectWhereMinOld`/`MaxOld` и старый AC6 #365 — **вне scope**.

Примечание: тесты, сейчас находящиеся в IVT-проектах провайдеров, сами по себе недостаточны; требуется изолированный потребитель.

### Примечания к AC (решения review)

- AC3: автономный потребитель использует только публичный Core; пакетные guard'ы `Select` (eager/JoinInto/проекция коллекций) наследуются вызовом `WithComponent(...).Select(projection)` без копирования/экспорта приватных guard'ов; типы исключений и отказ до выполнения в БД сохраняются, текст имени оператора может отличаться; группировка-осведомлённый отказ проекции коллекций добавляется централизованно при необходимости, не по имени оператора; позитивные legacy-тесты обычного `Select` остаются нетронутыми.
- AC4: живая проверка — шесть провайдеров отдельно и независимо: PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse, SQLite (MariaDB — отдельная независимая живая evidence, не только MySQL).
- AC6: оба пакетных компонента в `Prepare` проверяют `public context.Command.DataContext is InMemoryDataContext` (включая пользовательские подклассы) и бросают `NotSupportedException` со словом `in-memory`; generic Core не получает веток под конкретный оператор; отказ не опирается на SQL-callback `BuildQuery`.
- AC7: `IQueryComponentShape` обязателен для наших двух пакетных операторов (оба селектора + raw-условие + стабильные настройки); общий механизм по-прежнему допускает сторонние компоненты без shape по существующему raw-cache-ineligible fallback; подготовленное кеширование остаётся включённым; нулевой `Prepare` на подтверждённом eligible raw hit, без гарантии нулевого `Prepare` на fallback plan hit.
- AC10: API фиксирован как два generic-параметра `<TEntity, TResult>`; обычный вывод типов работает, старый явный одиночный `<TResult>` намеренно не поддерживается; без overload/обёртки совместимости; миграция документирует оба аргумента или их опускание. Генератор исходников: удалить SelectGroup-специфичную обработку имени; не добавлять распознавание `SelectGroupHaving`; при зависимости активных тестов генератора/алиасов от разрешения типа возврата — обобщать по типу возврата, без списка операторов; активацию сейчас неиспользуемого генератора не делать задачей.
- AC11: временной gate явно включает два именованных проекта (`nextorm.core.tests`/соответствующий unit и `nextorm.integration.tests` + `nextorm.extensions.integration.tests`); дополнительное время реальных тестов — бюджет верификации, не требование отсутствия регрессии производительности продуктовых запросов.

## 11. Протокол производительности

**Решения архитектора, предлагаются на ревью письменного дизайна.**

- Заморозить базовую линию **CURRENT** до изменения в изолированном worktree/сборке; записать коммит/источник/SDK/пакеты/настройку BDN. Базовая реализация **не копируется** в продукт.
- Сравнение кандидата `SelectGroup` со старым `SelectGroup`; `SelectGroupHaving` — **с**, и **без** preexisting Having: с — старое `.Having(existing).Having(condition).SelectGroup(projection)` vs новое `.Having(existing).SelectGroupHaving(projection, condition)`; без — старое `.Having(condition).SelectGroup(projection)`. Эквивалентность SQL и параметров обязательна.
- Сценарии: ключевой/глобальный/константный; скалярные/составные ключи; простые/смешанные агрегаты; отфильтрованные сгруппированные/Having; перепривязка захваченных/позиционных.
- Фазы: конструкция / холодная подготовка / тёплый hit рецепта / fallback подготовленного hit / выполнение.
- Контроли без компонентов: семь приёмочных + обычный `GroupBy` + существующие контролы экстремумов.
- Время **и** управляемые аллокации: без регрессии; на подтверждённом raw hit вывод вызывается ноль раз.
- Парное counterbalanced контролируемое тёплое измерение с A/A-проверкой шума; количество методов/выборок/конфигурация и точное статистическое правило решения замораживаются в плане реализации до DO и не могут вводить положительный допуск на замедление.
- Неопределённое измерение не считается PASS; значимая/реальная регрессия или рост аллокаций — не PASS. Общий T323 7-кейсовый набор **не** используется как базовая линия фичи.
- Запуск бенчмарков на этапе дизайна не требуется.

## 12. Интеграционное покрытие (решение архитектора)

**Решения архитектора, предлагаются на ревью письменного дизайна.**

После переноса всех живых тестов фичи выделенный интеграционный gate должен собирать **оба** проекта — core и extensions — последовательно в одной коллекции покрытия, затем агрегировать как один отчёт. Сохранить существующий scope модулей + добавить модуль `nextorm.extensions` для реально перенесённого/нового продуктового кода; метрики движка/провайдеров оставлять отдельно видимыми, чтобы не маскировать знаменатель. Пороги без изменений; полные измеренные результаты — базовая линия/после. Продуктовый хелпер — под `tools/` (не `.pdca`); CI/тесты не зависят от внутренних specs. При провале порогов — добавить тесты/закрыть пробелы, без снижения/исключений/отказов от порогов. Это часть миграции, а не способ сделать код невидимым.

## 13. Отклонённые альтернативы

- Фасад-переименование с сохранением флагов в Core (нарушает удаление политики).

- Выбран декларативный эффект — минимальный обобщённый механизм, достаточный для двух третьесторонних случаев группировки, а не произвольный оптимизатор SQL.

## 15. Разрешение вопросов review (корректирующие решения)

**Решения архитектора, предлагаются на ревью письменного дизайна.** Уже отвеченные/младшие вопросы зафиксированы явно:

1. Пакетные entry-вызовы используют обычный `WithComponent(...).Select(projection)` и наследуют те же guard'ы `Select` (eager/JoinInto/проекция коллекций); приватные guard'ы не экспортируются/не копируются; те же типы исключений и отказ до выполнения в БД; текст имени оператора может отличаться; группировка-осведомлённый отказ проекции коллекций добавляется централизованно при необходимости, не по имени оператора; позитивные legacy-тесты обычного `Select` не трогаются.
2. Оба пакетных компонента в `Prepare` проверяют `public context.Command.DataContext is InMemoryDataContext` (включая пользовательские подклассы) и бросают `NotSupportedException` со словом `in-memory`; generic Core не получает веток под конкретный оператор; отказ не опирается на SQL-callback `BuildQuery`.
3. `IQueryComponentShape` обязателен для наших двух пакетных операторов (оба селектора + raw-условие + стабильные настройки); общий механизм допускает сторонние компоненты без shape по существующему raw-cache-ineligible fallback; подготовленное кеширование остаётся включённым; нулевой `Prepare` на подтверждённом eligible raw hit, без гарантии нулевого `Prepare` на fallback plan hit.
4. Живая проверка: шесть провайдеров отдельно и независимо — PostgreSQL, SQL Server, MySQL, MariaDB, ClickHouse, SQLite (MariaDB — отдельная независимая evidence).
5. Новое условие AND-ится с уже существующим Having **всегда до общей валидации**. Для проекции-константы: валидировать весь объединённый предикат как не зависящий от строки/покрытый, затем опустить объединённый предикат в эффективный WHERE ровно один раз; очистка эффективного Having предотвращает только дубль эмиссии, а не отбрасывание условия; невалидные ссылки на строку проваливают. Для глобального агрегата объединённый валидированный Having — реальный HAVING.
6. Каждый добавленный/существующий Having-предикат валидируется против выведенных ключей проекции; непокрытый `x.Amount` при ключе только `x.Category` проваливает `QueryPreparationException` (если не внутри агрегата); авто-фильтрация в WHERE отсутствует, кроме валидированного константного вырожденного режима.
7. API фиксирован как два generic-параметра `<TEntity, TResult>`; обычный вывод типов работает; старый явный одиночный `<TResult>` намеренно не поддерживается; без overload/обёртки совместимости; миграция документирует оба аргумента или их опускание.
8. Генератор исходников: удалить SelectGroup-специфичную обработку имени; не добавлять распознавание `SelectGroupHaving`; при зависимости активных тестов генератора/алиасов от разрешения типа возврата — обобщать по типу возврата, без списка операторов; активацию сейчас неиспользуемого генератора не делать задачей.
9. Временной gate явно включает два именованных проекта; дополнительное время реальных тестов — бюджет верификации, не требование отсутствия регрессии производительности продуктовых запросов.
10. Базовая линия производительности — **и с**, и **без** preexisting Having: с — старое `.Having(existing).Having(condition).SelectGroup(projection)` vs новое `.Having(existing).SelectGroupHaving(projection, condition)`; без — старое `.Having(condition).SelectGroup(projection)`; эквивалентность SQL и параметров обязательна.
