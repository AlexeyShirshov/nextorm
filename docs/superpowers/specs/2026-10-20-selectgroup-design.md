## 1. Проблема и цель

Сейчас, чтобы получить сгруппированный плоский результат, приходится дважды перечислять
group-ключи: сначала в `GroupBy(...)`, затем в `Select(...)`. Это дублирование, и при
изменении ключей легко получить рассинхронизацию.

Цель: убрать это дублирование, **сохранив явный opt-in** (никакой автоматической группировки
в обычном `Select`) и **обычный `TResult`** — плоский, строго типизированный результат.

Это **архитектурное изменение анализа выражений**, а не «сахар на две лямбды».

## 2. Отклонённый дизайн «две лямбды»

Рассматривался вариант с двумя лямбдами (key selector + projection) и последующим
«сплющиванием» анонимного типа. Он **отклонён**: сплющивание анонимного типа не может дать
обычный строго типизированный плоский вывод. Поэтому API строится на одной проекции с
выводом ключей из её содержимого.

## 3. API

Концептуальная сигнатура на существующей поверхности `EntityBuilder`:

```csharp
SelectGroup<TResult>(Expression<Func<TEntity, TResult>> projection)
```

- Возврат команды, guard'ы и правила формы — те же, что у `Select`.
- Наследуется существующая поддержка joined `Projection<T1, ...>`.
- Обычный `Select` и явный `GroupBy` **не меняются**.

## 4. Пример

```csharp
ctx.From<Product>()
   .SelectGroup(p => new
   {
       ProductID        = p.Item1.ProductId,
       ProductName      = p.Item3.Name,
       SalesQuarter     = SqlFunctions.Sql.date_trunc("quarter", p.Item2.OrderDate),
       QuarterlyRevenue = SqlFunctions.Sql.sum(p.Item1.LineTotal),
       QuarterlyQty     = SqlFunctions.Sql.sum(p.Item1.OrderQty),
   });
```

Результат — все пять плоских полей. SQL и результаты эквивалентны явному
`GroupBy(...).Select(...)` с теми же ключами.

## 5. Правила вывода (согласованы)

Работа ведётся в **текущей SQL-области запроса** над **скалярными выходными выражениями**
проекции; анонимный тип / DTO-конструктор сам по себе **не** трактуется как group-ключ.

Правила:

1. **Сбор.** Собираются максимальные row-dependent aggregate-free подвыражения.
2. **Порядок.** Детерминированный, в порядке первого появления.
3. **Пропуск.** Константы и captured-параметры пропускаются; дубликаты выражений
   дедуплицируются.
4. **Целые ключи.** `date_trunc('quarter', OrderDate)` остаётся **целиком** ключом, а не
   `OrderDate`.
5. **Гранулярность подвыражений.** `sum(Amount) + Adjustment` → ключ `Adjustment`;
   `sum(Amount) + Price * Qty` → ключ `Price * Qty`, **не** `Price` и `Qty` по отдельности.
6. **Агрегаты непрозрачны.** Аргументы агрегатного вызова, `DISTINCT`-вход и `FILTER`-предикат
   **никогда** не протекают в group-ключи.
7. **Спуск.** Чистые скалярные функции, оборачивающие агрегат, «спускаются» для вывода;
   распознанный агрегатный вызов пропускается целиком.
8. **Проекция сохраняется.** Исходная проекция остаётся как есть; никакой клиентской
   группировки, динамических типов и reflection-emit слияния плоского типа.

## 6. Вырожденные случаи

**Согласовано:**

- **Агрегатов нет, ключи есть** → уникальные комбинации через `GROUP BY`; это **не** обычный
  построчный select.
- **Только агрегаты, ключей нет** → глобальная агрегация **без** `GROUP BY`.

**Architect default (не согласовано пользователем):**

- **Проекция полностью row-independent и без агрегатов** → DISTINCT-подобная уникальная
  проекция по отфильтрованному источнику (пустой вход → ноль строк), без невалидного пустого
  `GROUP BY`.
- Для глобальной агрегации сохраняются существующие семантики провайдера: `count`/`sum`/`NULL`/
  пустой вход.
- Никакой новой семантики для numeric rounding/`NULL` не вводится.

## 7. Having и OrderBy

Ключи выводятся **только из проекции**. Существующие `Having` и expression-`OrderBy`
валидируются против выведенных ключей. «Голое» непокрытое выражение внешней строки даёт
**ошибку до выполнения на БД**; группировка никогда не расширяется молча.

- `.Having(p => SqlFunctions.Sql.sum(p.Amount) > p.Limit)` при проекции
  `{ ProductId, Total = sum(Amount) }` — **ошибка**, пока `p.Limit` не покрыт ключом:
  `p.Limit` — поле внешней строки и должно входить в выведенные ключи.
- `.Having(p => SqlFunctions.Sql.sum(p.Amount) > threshold)` с captured `threshold` —
  **валидно**; новый ключ не добавляется. Captured-переменные и константы в `Having`/`OrderBy`
  разрешены.
- Разрешены агрегаты и выражения, вычисленные из уже доступных ключей/констант.
- **Структурное сравнение** обязано распознать полный ключ `date_trunc(...)` **до** спуска:
  использование самого ключа разрешено, «сырой» `OrderDate` — нет.
- **Функциональные зависимости не выводятся**, даже если конкретная БД их допускает.
- `OrderBy` по ординалу сохраняет существующую валидацию индекса; ключи при этом не
  расширяются.
- `WHERE` остаётся **pre-group** фильтром и не участвует в выводе группировки.
- **Важно (существующее ограничение renderer'а).** Сейчас `HAVING` эмитится только при
  непустой группировке. Новый глобальный `SelectGroup` с агрегатом и `Having` **обязан**
  сохранить `HAVING` — либо **явно отклонить** неподдерживаемый backend; молчаливое
  отбрасывание `HAVING` недопустимо. Изменение renderer'а ограничено новым API и **не**
  переопределяет поведение legacy-запросов.

## 8. Несовместимости

**Согласовано:**

- Предсуществующий явный `GroupBy` / `Rollup` / `Cube` / `GroupingSets` → **ошибка**, без
  переопределения и без слияния.
- Window-функции в проекции / `Having` / `OrderBy` → отклоняются в v1; обычное поведение
  `Select` с window не меняется.
- Скалярные/коррелированные подзапросы в этих выражениях → исключаются/отклоняются в v1:
  вложенная query-область **не** инспектируется, внутренний агрегат **не** считается внешним.
  Существующие подзапросы в `WHERE` **не** запрещаются.
- **Отклонение безусловно и не зависит от вывода ключей.** Отдельная валидация обходит
  релевантное дерево текущего выражения (проекция, `Having`, expression-`OrderBy`), включая
  аргументы агрегатов и `FILTER`-предикат; при встрече подзапросного выражения — ошибка.
  Спуск во вложенную query-область для вывода ключей **никогда** не выполняется. То, что при
  выводе ключей агрегатный вызов трактуется как непрозрачный, не отменяет эту проверку:
  валидация и вывод — отдельные проходы.
- Прочие модификаторы не меняются, если не несовместимы по существующим capability-проверкам;
  расширение поддержки провайдеров не изобретается.

## 9. Кастомные функции: `SqlFunctionAttribute.IsAggregate`

Изначально идея была «только встроенные агрегаты»; по явному запросу пользователя она
расширена на кастомные функции.

- В существующий `SqlFunctionAttribute` добавляется публичное свойство
  `bool IsAggregate { get; set; }` со значением по умолчанию `false`.
- Использование: `[SqlFunction("my_sum", IsAggregate = true)]`.
- Эффективный `IsAggregate = true` ведёт себя как граница встроенного агрегата: ключи внутри
  аргументов **не** извлекаются.
- Неаннотированный или `IsAggregate = false` вызов `SqlFunction` — скалярный; он может быть
  выведен как целый ключ.
- Это **декларация автора**, а не runtime-угадывание и не чтение метаданных БД.
- `Name`/`Schema`/синтаксис рендера сохраняются.
- **Architect default:** используется то же эффективное разрешение method/class-атрибута, что
  и в существующем SQL-трансляторе (не создаётся конфликтующий precedence). Разрешение —
  **точная замена атрибута целиком**, без слияния отдельных свойств: если у метода есть
  `[SqlFunction]`, он используется полностью; иначе — атрибут объявляющего типа.
  `IsAggregate` по умолчанию `false`; `[SqlFunction(IsAggregate = true)]` на классе действует
  только при отсутствии method-атрибута, а method-атрибут `[SqlFunction("f")]` заменяет
  class-атрибут целиком (эффективно `IsAggregate = false`). Это поведение документируется и
  покрывается тестами.
- **Коллизия классификации в renderer'е — не out of scope, требуется корректная семантика.**
  Пользовательский CLR-метод `[SqlFunction("my_scalar")]`, названный `sum`, с
  `IsAggregate = false` — скалярная функция: рендерится под объявленным SQL-именем и **никогда**
  не перехватывается как встроенный агрегат. С `IsAggregate = true` он рендерится как
  пользовательская SQL-функция и служит непрозрачной агрегатной границей. Точный классификатор
  и renderer обязаны согласованно различать эти случаи; при необходимости правятся
  builtin/advanced dispatch-guard'ы или precedence аннотации. Механизм и минимальный объём
  рефакторинга выбирает планировщик; обязательного сплошного переписывания трансляторов нет,
  но обход коллизии не может быть waive'нут. Если затрагивается общий dispatch — нужны
  regression-тесты и через обычный `Select`. Legacy-поддерживаемый встроенный SQL **не**
  меняется.
- Аннотация **не** обещает исполнение кастомной функции в in-memory: неподдерживаемые
  функции отклоняются явно, а не исполняются случайно по совпадению имени.
- Новый реестр агрегатов не вводится.
- Аннотация **не** обещает: существование функции в БД либо `FILTER`-синтаксис диалекта.
  Неподдерживаемые провайдеры падают явно по существующему capability-поведению.
- Идентичность распознавания — `MethodInfo`/объявляющий тип/сигнатура либо эквивалентный
  точный реестр, **не** по имени: пользовательская скалярная функция с именем `sum` не должна
  считаться встроенным агрегатом.
- Входят встроенные distinct/filter/string/advanced/provider-агрегаты, которые движок уже
  транслирует; новые семейства SQL-агрегатов не реализуются.

## 10. Архитектура

**Architect choices (внутренняя раскладка; builder может выбрать другую):**

- Общая агрегатная классификация используется и для вывода, и для валидации `SelectGroup`.
- Renderer и точный агрегатный классификатор обязаны согласованно разрешать коллизию
  пользовательской аннотации и встроенного имени (см. §9): корректная семантика важнее
  минимизации диффа, но объём рефакторинга выбирает планировщик.
- Обязательного сплошного рефакторинга всех трансляторов **нет**.
- Opt-in состояние доносится до стадии подготовки, где уже известны нормализованные формы
  колонок.
- Рендеринг и материализация явной группировки переиспользуются, где это возможно.
- Валидация выполняется **до** выполнения запроса.
- Reusable builder/source query и общие `QueryCache`-команды **не мутируются**; корректность
  эквивалентности/дифференциации plan cache, captured-значения и rebinding параметров при
  исполнении сохраняются.
- Дедупликация **семантически безопасна**: существующий plan comparer может игнорировать
  литералы/captured-значения, поэтому слепо использовать его для слияния разных
  grouping-выражений **нельзя**.
- In-memory поддерживает выведенную группировку только в пределах существующих
  агрегатов/capability и **никогда** не использует первую строку, чтобы замаскировать
  невалидные `Having`/`OrderBy`.

## 11. Ошибки

- Тип: `QueryPreparationException` или существующее консистентное preparation-исключение.
- Диагностика должна быть понятной: конфликт группировки, window/подзапросы, непокрытые
  `Having`/`OrderBy` — с указанием offending-выражения и контекста.
- Неподдерживаемый backend-агрегат остаётся ошибкой провайдера (существующее поведение).
- Никогда не выполняется молчаливый fallback в клиентский eval и никогда не меняется
  группировка.

## 12. Приёмка и тесты (эскиз)

1. Оригинальный joined-пример с кварталами → эквивалентный SQL и эквивалентные результаты
   относительно явного `GroupBy` + `Select`.
2. Паритет форм проекций: scalar / anonymous / DTO — существующие shape-правила.
3. Целый ключ `date_trunc`; смешанные выражения; дубликаты ключей; корректность литералов и
   замыканий (различные значения не сливаются).
4. Только агрегаты (включая пустой вход и `NULL`); без агрегатов — уникальные комбинации
   (включая `NULL` и keyless-константы по architect default).
5. Принимаемые и отклоняемые `Having`/`OrderBy`, включая выражения из уже доступных
   ключей, captured-переменные/константы (например
   `.Having(p => SqlFunctions.Sql.sum(p.Amount) > threshold)`) и ординал; поле внешней строки
   `p.Limit` в `Having` отклоняется, если не покрыто ключом.
6. Отклонение явных групп; отклонение window и подзапросов — **безусловно**, включая
   подзапрос внутри аргументов агрегата и `FILTER`-предиката, независимо от вывода ключей;
   спуск во вложенную query-область не выполняется; подзапросы в `WHERE` по-прежнему работают.
7. Кастомные scalar vs помеченные aggregate, включая коллизию имён и scope/defaults атрибута:
   `[SqlFunction("my_scalar")]`-метод с именем `sum` и `IsAggregate = false` рендерится как
   скаляр под объявленным именем, `IsAggregate = true` — как непрозрачная агрегатная граница;
   method-атрибут заменяет class-атрибут целиком (без слияния свойств). Если общий dispatch
   исправляется, те же проверки проходят и через обычный `Select`; legacy встроенный SQL не
   меняется. Неподдерживаемая в in-memory кастомная функция отклоняется явно, без исполнения
   по совпадению имени.
8. `FILTER`-предикат **никогда** не становится ключом.
9. Source builder не мутируется; переиспользование plan cache с rebinding параметров; нет
   общего `Cache = false`.
10. Unit SQL по провайдерным проектам (где поддерживается); реальные интеграционные тесты на
    БД для переносимых случаев; provider-specific диалекты — в соответствующих тестах.
11. In-memory — только существующие поддерживаемые агрегаты, тесты в unit-проекте.

Гигиена: FluentAssertions, CRLF, `net10.0`, warnings-as-errors. **Сейчас тесты не
запускаются**, потому что реализации нет.

## 13. Non-goals

- LINQ `IGrouping` / материализованные группы.
- Собственный aggregation engine.
- Вложенные группированные проекции.
- Вывод группировки из `Having`/`OrderBy`.
- Функциональные зависимости.
- Window-функции и подзапросы (в рамках нового API, v1).
- Произвольные новые возможности БД.
- Изменение `Select`.
