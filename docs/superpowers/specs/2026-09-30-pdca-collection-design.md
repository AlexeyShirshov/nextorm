# pdca-collection — дизайн

- **Дата:** 2026-09-30
- **Статус:** approved (design), implementation plan — следующий шаг
- **Пара к:** глобальный скилл `pdca-dotnet`

## 1. Context & goal

`pdca-dotnet` умеет вести **один** цикл PLAN → DO → CHECK → ACT. Когда на вход
приходит **список независимых задач**, контракт явно говорит: это N отдельных
циклов, которые в автономном режиме исполняются **последовательно** («independence
is about isolation, not about pausing»). Реальной параллельности для списка задач
нет.

Цель: скилл `pdca-collection`, который принимает список задач, **кластеризует** их
в группы, запускает группы **параллельно** (по worktree на группу), а внутри группы
выполняет задачи **последовательно** (каждая задача — свой полный pdca-цикл, свой
бранч, автокоммит), и в конце интегрирует результат в текущий бранч.

Форма верхнего уровня — это PDCA **коллекции**: `P` = кластеризация,
`D` = инфраструктура + трекинг + merge, `C` = верификация, `A` = отчёт.

### Non-goals

- Не заменяет `pdca-dotnet` — использует его как базу для каждой задачи.
- Не управляет push/PR (push — никогда; PR — отдельный явный запрос).
- Не решает сам, откуда берётся список задач: **вход формирует пользователь**
  (список issue, текстовый перечень, файл-план — что угодно).

## 2. Key decisions

| Аспект | Решение |
|---|---|
| Артефакт | новый скилл `pdca-collection` + субагент `lane` + exception в `AGENTS.md` |
| Верхний уровень | PDCA коллекции: P=кластеризация, D=инфра+трекинг+merge, C=верификация, A=отчёт |
| Группировка | DAG-зависимости + общие файлы/модуль; решение принимает агент |
| Изоляция групп | 1 worktree на группу; группы параллельны |
| Внутри группы | последовательно: задача → своя ветка → автокоммит; следующая ветвится от закоммиченного tip предыдущей |
| Механика лейнов | `lane`-агент на группу (двухуровневые агенты) |
| Merge | `git merge --no-ff` ветки группы в текущий бранч, по одной, последовательно |
| Сбой задачи | lane стоп, оставшиеся задачи группы blocked; другие группы доводятся и мержатся |
| Вход | пользователь сам решает, как задачи попадают в скилл |

## 3. Architecture & components

### 3.1 Скилл `pdca-collection`

- Глобальный: `~/.config/opencode/skills/pdca-collection/SKILL.md`.
- Загружается **вместе с** `pdca-dotnet`: коллекция — надстройка, база (гейты,
  роли, state machine цикла) не дублируется, а переиспользуется.
- Определяет:
  - цикл коллекции (P/D/C/A) и его гейты;
  - правила кластеризации (вход → DAG → группы);
  - git/worktree-модель;
  - формат файла статуса коллекции и финального отчёта;
  - merge-exception (см. 3.3).

### 3.2 Субагент `lane`

- Файл: `~/.config/opencode/agents/lane.md`.
- `mode: subagent`.
- `permission`:
  - `task: allow` — вложенно вызывает `planner`, `coder`, `check`, `escalate`
    (роли `pdca-dotnet`);
  - `edit: deny`, `bash: deny` — сам **не** правит и не запускает команды: это
    делают вложенные субагенты (роль `coder`);
  - `skill: allow` — загружает `pdca-dotnet`.
- Модель — как у оркестратора (дешёвая): `lane` координирует, а решения/вердикты
  отдают `planner`/`check`.
- `lane` ведёт **одну** группу: работает в её worktree, гоняет её задачи
  последовательно, возвращает сводку.

### 3.3 Exception в `AGENTS.md`

`AGENTS.md` репозитория запрещает merge-коммиты. Вносится явное исключение:

> Для циклов, запущенных скиллом `pdca-collection` в режиме явно разрешённого
> автокоммита, разрешаются: (a) коммиты в ветках `collection/**` внутри worktree
> цикла, (b) `git merge --no-ff` ветки группы в текущий бранч. Вне такого цикла
> правила «never merge» и «no commits unless explicitly asked» сохраняются.

Исключение добавляется в `AGENTS.md` того репозитория, где гоняется коллекция
(для nextorm — проектный `AGENTS.md`). Глобальное правило git (no push) не
меняется; «no commits unless asked» сохраняется вне режима автокоммита.

## 4. Жизненный цикл коллекции (ведёт primary)

### P — кластеризация

1. Пользователь формирует вход: список задач в любом виде.
2. `scout` собирает **footprint** и зависимости:
   - файлы/модули, которые затронет каждая задача (через `roslyn` — refs/types);
   - явные зависимости между задачами (например, «B требует API из A»);
   - общие внешние ресурсы, если релевантно (БД, порт), — по указанию пользователя.
3. `planner` строит DAG и режет на группы:
   - одна группа = связная компонента/линия по зависимостям и общим файлам;
   - между группами footprint не пересекается;
   - внутри группы задачи упорядочены топологически.
4. Группы + порядок задач фиксируются в **файле статуса коллекции** (см. §7).

### D — инфраструктура + трекинг + merge

1. Инфра создаётся через `coder` (команды): по worktree на группу в
   `<repo>-worktrees/<collection-id>/<group>` и ветка `collection/<id>/group-<g>`.
   Для nextorm путь уже разрешён в `opencode.json` (`external_directory`).
2. `lane`-агенты запускаются **параллельно** (по одному `Task` на группу) и
   исполняют группы (см. §5).
3. По завершении группы `coder` по команде primary выполняет `git merge --no-ff`
   её ветки в **текущий** бранч. Merge'и выполняются **последовательно** (один за
   другим), чтобы не гонять основное дерево. Конфликт → `coder` делает
   `git merge --abort`, группа failed, gate `C` не пройден; другие группы не
   трогаются.
4. При автокоммите: merge-коммит группы создаётся сразу; сообщение начинается с
   идентификатора задачи/issue, если задача привязана к issue (`#17 <summary>`).
5. Primary ведёт статус: какая группа/задача done / blocked / merged.

### C — верификация

После остановки **всех** лейнов, через `coder` в основном дереве:

1. Проверка, что все успешные группы смержены и нет незавершённого
   merge-состояния (после любого конфликта выполнен `git merge --abort`).
2. `dotnet build` — 0 warnings / 0 errors (для nextorm:
   `dotnet build nextorm.slnx -c Release`).
3. Тесты соответствующего скоупа.
4. Покрытие не ниже порога проекта (nextorm: `MIN_LINE_COVERAGE=85`,
   `MIN_BRANCH_COVERAGE=75`).
5. Перф-приёмка, если коллекция трогает query-path (nextorm: cached-path
   acceptance; см. `nextorm-pdca`).
6. Любой провал → gate коллекции не пройден → `A` фиксирует это; цикл коллекции
   не считается успешным.

### A — завершение

1. Финальный отчёт: группы, задачи, ветки, изменения merged/blocked, evidence
   (команды, выводы, `file:line`).
2. Снос worktree и временных веток.
3. Файл статуса коллекции: закрывается/удаляется по той же гигиене, что и в
   `pdca-dotnet`.
4. Push — никогда.

## 5. Жизненный цикл лейна (на группу)

Лейн работает только в своём worktree (абсолютные пути, `cd <WT>`).

Для каждой задачи группы **по порядку**:

1. Создаёт ветку `collection/<id>/task-<g>-<k>` от закоммиченного tip предыдущей
   задачи (для первой — от ветки группы/base).
2. Ведёт полный цикл `pdca-dotnet`: PLAN (гейт 1) → DO (code/tests/docs
   параллельно) → CHECK (аудит + линзы) → ACT (статус-файл задачи).
3. Автокоммит по завершении задачи: всё закоммичено в её ветку, иначе следующая
   задача не сможет ветвиться от «закоммиченного результата предыдущей».
   Коммитятся **только файлы задачи** (`git add <paths>`), не `git add -A`.

Правила:

- Ветка задачи — единица коммита; worktree на задачу не создаётся.
- **Сбой задачи** (её `C` не прошёл после loop-back/escalate): лейн
  **останавливается**, оставшиеся задачи группы помечаются `blocked`, лейн
  возвращает сводку. Другие лейны не трогаются.
- Результат группы = tip последней успешно закоммиченной задачи; ветка группы
  `collection/<id>/group-<g>` ff-продвигается на этот tip, и именно её мержит primary.
- Лейн возвращает компактную сводку: ветка-результат, done/blocked, указатели на
  evidence-файлы. Код/диффы/логи в контекст не тащит.

## 6. Git / worktree модель

```
current-branch (main/target)
│
├─ merge --no-ff collection/<id>/group-A   ← группа A (worktree A)
│     └─ collection/<id>/task-A-1 → task-A-2 → task-A-3   (цепочка веток задач)
│
└─ merge --no-ff collection/<id>/group-B   ← группа B (worktree B)
      └─ collection/<id>/task-B-1 → task-B-2
```

- 1 worktree на группу; ветка группы `collection/<id>/group-<g>` ff-продвигается на
  tip каждой завершённой задачи и в конце равна tip последней.
- Внутри группы — цепочка веток задач; следующая ветвится от tip предыдущей.
- Интеграция — `merge --no-ff` ветки группы в текущий бранч, по одной,
  последовательно.
- Конфликт merge → gate коллекции `C` не пройден.
- Push и merge не в текущий бранч — вне рамок.

## 7. Status-файлы и отчёты

### Файл статуса коллекции

`docs/specs/status/collection-<slug>.md` (конвенция репо). Содержит:

- вход (список задач) и `collection-id`;
- таблицу групп: id, задачи, порядок, worktree, ветка, статус;
- таблицу задач: id, группа, ветка, статус (pending / in-progress / done /
  blocked), ссылка на статус-файл задачи (merge — на уровне группы, у задачи
  статуса `merged` нет);
- решения фаз коллекции (кластеризация, merge-стратегия);
- Done / Verified / Blocked.

### Отчёт для следующей сессии

Формат — как в `pdca-dotnet` §ACT (в обычном режиме), с акцентом на незакрытые
задачи и заблокированные группы.

## 8. Failure semantics

| Событие | Поведение |
|---|---|
| Задача падает | lane стоп; оставшиеся задачи группы → `blocked`; другие группы продолжают |
| Группа завершилась частично | primary мержит только успешно закоммиченный tip (если есть); в отчёте — blocked-задачи |
| Merge-конфликт группы | `git merge --abort`; группа failed; gate `C` не пройден; другие группы не трогаются |
| Регресс build/тестов/покрытия/перфа | gate `C` не пройден; цикл коллекции не закрыт |
| Лейн вернул «нет результата» | группа = blocked, merge не делается |

## 9. Параметры (дефолты)

| Параметр | Дефолт |
|---|---|
| Локация скилла | глобальная `~/.config/opencode/skills/pdca-collection/` |
| Локация агента | глобальная `~/.config/opencode/agents/lane.md` |
| Потолок параллелизма | `min(#групп, cap)`, `cap` = 4 (настраивается) |
| Worktree-каталог | `<repo>-worktrees/<collection-id>/<group>` |
| Merge | `git merge --no-ff` по группе, последовательно |

## 10. Testing / verification скилла

Скилл — это workflow-артефакт, «тесты» = воспроизводимый прогон на маленькой
синтетической коллекции:

- 2 группы × 2 задачи; одна задача специально падает на `C`.
- Проверяем:
  1. лейны стартуют параллельно, каждый в своём worktree;
  2. внутри группы ветки задач идут цепочкой, автокоммит после каждой;
  3. успешные группы мержатся `--no-ff` по одной;
  4. упавшая задача стопает свой лейн, вторая группа доходит до merge;
  5. финальный отчёт корректно помечает blocked;
  6. гейты `pdca-dotnet` не пропущены (чек-лист).

## 11. Relationship to pdca-dotnet

- `pdca-collection` **не переопределяет** state machine и гейты `pdca-dotnet`; он
  добавляет уровень над ними.
- Каждая задача внутри группы = полноценный цикл `pdca-dotnet` (свой статус-файл,
  свои гейты, свои роли).
- Роли (`planner`, `coder`, `check`, `escalate`, `scout`) — те же, что в
  `pdca-dotnet`; новых ролей нет, кроме агента-обёртки `lane`.

## 12. Risks

- **Вложенная делегация.** `lane` — субагент, который сам вызывает `Task`. Нужно
  проверить, что harness это позволяет на нужную глубину; иначе fallback — плоский
  primary (см. обсуждение, подход B).
- **Гонки в основном дереве.** Merge'и групп выполняются последовательно; при
  конфликтах — стоп.
- **Стоимость/ресурсы.** Параллельные worktree + сборки/Testcontainers нагружают
  CPU/диск; отсюда `cap`.
- **Противоречие с правилами репо:** merge-коммиты запрещены текущим `AGENTS.md` —
  снимается явным исключением (§3.3).

## 13. Future

- Плагин-шедулер (программный fan-out top-level сессий) — если вложенная
  делегация окажется недостаточной.
- Динамическая рекластеризация по ходу (сейчас — один раз в `P`).
- Интеграция с issue-tracker для автоматического `#n` в коммитах.
