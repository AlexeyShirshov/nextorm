# PostgreSQL: чтение элемента массива по SQL-индексам

**Состояние:** Письменная спецификация утверждена пользователем 2026-11-24. Следующий шаг — отдельный план реализации. План не утверждён, реализация не начата.
**Трекинг:** GitHub issue: [#417](https://github.com/AlexeyShirshov/nextorm/issues/417) · milestone: [1.0.12](https://github.com/AlexeyShirshov/nextorm/milestone/10)

## Зачем

Прочитать один элемент массива на сервере без загрузки матрицы на клиент, ручного SQL, расширения PostgreSQL или установленной пользовательской SQL-функции (UDF). Для `Tensor.Data` типа `float[,]`:

```csharp
ctx.From<Tensor>().Select(t => SqlFunctions.Postgres.array_element(t.Data, 2, 3))
```

Целевой SQL — `SELECT data[2][3] FROM tensors`. Для `{{1,2,3},{4,5,6}}` результат — `6f`; сервер возвращает только скаляр `real` или SQL `NULL`.

## Согласованный публичный контракт

- `array_element` принимает от 1 до 6 целочисленных SQL-индексов, ровно по одному на ось для `T[]`, `T[,]`, `T[,,]`, `T[,,,]`, `T[,,,,]` и `T[,,,,,]` соответственно. Ранг задаёт объявленный CLR-тип; неверное число индексов не компилируется. Поэтому контракт не использует `System.Array` или вариадический `params int[]`.
- Индексы — координаты PostgreSQL без пересчёта на `±1` и без `array_lower`. Нижняя граница обычно равна 1, но может быть другой. При несовпадении фактической размерности массива в строке с числом индексов скалярное чтение PostgreSQL возвращает `NULL`.
- Результат для `real[][]` — `float?`, для `integer[]` — `int?`, для `text[]` — `string?` независимо от nullable-аннотаций колонки. Nullable-форма объявленного типа элемента и SQL-nullability результата — разные свойства. SQL `NULL`, отсутствующий элемент (в том числе за границей), `NULL`-элемент и пустой массив не подменяются `default(T)` ненулевого типа.
- Охват — настоящие PostgreSQL-массивы элементов, которые провайдер уже умеет читать как скаляры. Сам `bytea` (хотя представлен в CLR как `byte[]`) и `multirange` не являются операндами-массивами; ступенчатый CLR-массив не заменяет прямоугольный. Из этого не следует безусловный запрет для `pgvector`, `bytea[]` или `range[]`: применяются те же условия. Контракт не добавляет маппинги и не обещает определять физический тип произвольной пользовательской схемы.

Выбран явный маркер. Обычный CLR-индексатор имел бы другую базу индексов и другую семантику отсутствующего элемента. Ручной SQL остаётся обходным путём, а SQL-UDF требует развёртывания; оба варианта не удовлетворяют запросу.

## Инженерные предложения к ревью

- Поддержать SQL-выражения индексов типа `int` и `int?`: литералы, захваченные значения, параметры времени выполнения и колонки. Nullable-результат должен компоноваться в `Select` и `Where`.
- Принимать типизированное выражение массива известного ранга, в том числе колонку. Для поддерживаемых составных операндов скобки сохраняют приоритет, а перевод не дублирует вычисление.
- Использовать отдельную ветку PostgreSQL в существующем переводе выражений. На других диалектах отклонять маркер, не генерируя PostgreSQL SQL и не вычисляя его на клиенте. Обычный CLR-индексатор и перевод обращения к захваченным коллекциям через `CASE` не меняются. Срезы, `UPDATE` по индексам, изменения чтения и записи целых матриц, их маппинга или DDL — вне объёма.
- Подтвердить форму публичного API статически типизированными вызовами для значимых, ссылочных и nullable-элементов. Спецификация не фиксирует непроверенную форму `T?` без ограничения типа или перегрузки, различающиеся только ограничениями типа.

## Приёмка для будущего плана

1. Подтвердить компиляцией все ранги 1–6 и статически nullable-результаты, включая `float[,]` → `float?`, `float?[,]` → `float?`, `int[]` → `int?` и `string[]` → `string?`. Неверное число индексов должно отклоняться компилятором, а не во время выполнения.
2. Проверить форму SQL и реальное выполнение в PostgreSQL: пример с результатом `6f`, ранги 1 и 6, нестандартную нижнюю границу, SQL `NULL`, `NULL`-элемент, пустой массив, выход за границы и несовпадение размерности.
3. Проверить, что изменяемые индексы не зашиваются в переиспользуемый план, другой провайдер отклоняет маркер, скалярный `bytea` не путается с массивом, а существующие обращения к захваченным коллекциям не меняются.
