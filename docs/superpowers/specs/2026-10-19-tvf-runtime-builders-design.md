## 1. Контекст и проблема

Сейчас метаданные табличных функций (TVF) в nextorm задаются статически:

- атрибутом `SqlTableFunctionAttribute`;
- методами-заглушками, возвращающими `IQueryable`;
- старым API `FromTableFunction` и compatibility-фабриками.

Такой подход имеет принципиальные ограничения:

1. **Нет runtime-метаданных.** Имя функции, схема и опции фиксируются атрибутом и
   недоступны как runtime-объект.
2. **Теряются аргументы вызова.** Заглушка, возвращающая `IQueryable`, не несёт
   исходный `MethodCallExpression`; корреляция аргумента с внешней колонкой
   (`CrossApply`/`OuterApply`) невозможна корректно.
3. **Нет обычной композиции.** Внутри источника нельзя использовать привычную цепочку
   `EntityBuilder` (`Where`/`Select`/сортировки/пейджинг/джойны) с сохранением лямбд,
   проекций и корреляции.
4. **Неверная идентичность для кэша.** `MethodInfo` фабрики не описывает динамические
   имя/схему/опции/форму результата; identity объекта дескриптора — тоже неверный ключ.
5. **Контекст протекает в дескриптор.** Попытка «привязать» TVF к `DataContext` в
   конструкторе или хранить nullable-контекст ведёт к скрытым placeholder-контекстам,
   проглатыванию null-ref и загрязнению переиспользуемых объектов.

Нужен архитектурный рефакторинг источников TVF, а не небольшой хак в конструкторе.
Scope может потребовать изменений инфраструктуры core-билдера; полную цепочку нельзя
урезать, чтобы этих изменений избежать.

## 2. Цель

**[Требование пользователя]** Заменить метаданные из статических атрибутов и
методов-заглушек, возвращающих `IQueryable`, на **реальные runtime-объекты**, которые
создаются обычными статическими фабричными методами. Обход выражений в рантайме должен
распознавать источник, фабрика которого возвращает производный
`TvfEntityBuilder<T>`.

**[Требование пользователя]** Все API источников TVF должны принимать
**expression-lambda**, потому что прямой вызов `Factory(42)` теряет аргументы.

**[Требование пользователя]** Внутри lambda должна работать обычная композиция
`EntityBuilder`, а не белый список операторов.

## 3. Термины

- **TVF-фабрика** — обычный статический метод, возвращающий `TvfEntityBuilder<T>`.
- **Дескриптор TVF** — runtime-объект `TvfEntityBuilder<T>` (или его производный тип),
  содержащий имя/схему/опции и метаданные строки.
- **Lambda-источник** — выражение вида `() => Tvf.MyTvf(42)` или
  `user => Tvf.MyTvf(user.Id)`, передаваемое в `From`/`Join`/`CrossApply`/`OuterApply`.
- **Внешний `MethodCallExpression`** — узел выражения, описывающий вызов фабрики с
  аргументами; он является каноническим носителем аргументов.
- **Аргумент** — скалярное SQL-выражение в позиции параметра фабрики; не CLR-значение,
  вычисленное до генерации SQL.

## 4. Согласованный дизайн

### 4.1 Runtime-дескриптор вместо атрибутов

**[Требование пользователя]** `TvfEntityBuilder<T>` наследует `EntityBuilder<T>` и
содержит:

- имя TVF;
- схему;
- опции TVF;
- метаданные строки результата.

**[Требование пользователя]** Конструктор TVF **не требует и не хранит значения
SQL-аргументов**. Значения аргументов не являются частью метаданных дескриптора.

**[Требование пользователя]** Фабрика действительно возвращает дескриптор в рантайме.
Запрещены:

- рефлексия или интерпретация тела фабрики;
- атрибуты как источник TVF-метаданных;
- заглушки, единственное действие которых — `throw`;
- «магическое» распознавание по имени метода без реального объекта.

Пример объявления:

```csharp
public static TvfEntityBuilder<Row> MyTvf(int id) => new("my_tvf", "dbo");
```

Здесь `id` — только позиция аргумента в выражении. Значение `id` не должно влиять на
имя, схему, опции или форму результата.

### 4.2 Контракт фабрики

**[Требование пользователя]** Скалярные параметры фабрики задают только позиции
аргументов выражения. Метаданные **обязаны быть независимы от значений параметров**:

- никаких преобразований аргументов;
- никаких ветвлений по значениям аргументов;
- никаких конверсий, меняющих SQL-выражение аргумента;
- никакого вычисления коррелированного аргумента в CLR-значение.

**[Требование пользователя]** Материализация дескриптора (когда и как он создаётся или
снимается) — выбор плана реализации, но он обязан:

- сохранять аргументы как выражения;
- не вычислять коррелированные SQL-аргументы как CLR-значения;
- не пытаться определить итоговые SQL-аргументы через скалярную «пустую»/dummy-оценку
  внешних колонок.

**[Требование пользователя]** Каноническими считаются аргументы **внешнего**
`MethodCallExpression`. Любая производная форма не должна подменять их значениями по
умолчанию.

### 4.3 Почему API источников — только lambda

**[Требование пользователя]** Прямой вызов `Factory(42)` теряет выражение аргумента:
в метод попадает уже вычисленное значение, а не узел выражения. Поэтому источники TVF
принимаются только как expression-lambda.

Примеры:

```csharp
ctx.From(() => Tvf.MyTvf(42));

ctx.From<User>().CrossApply(user => Tvf.MyTvf(user.Id));
ctx.From<User>().OuterApply(user => Tvf.MyTvf(user.Id));
```

Для `Join` источник передаётся как `() => Tvf.MyTvf(42)` вместе с существующими
селекторами и условием. **[Требование пользователя]** Точную полную сигнатуру `Join` в
этом документе не изобретаем: она фиксируется планом по факту текущего API. Нельзя
придумывать непроверенную перегрузку и выдавать её за согласованную.

### 4.4 Полная композиция внутри lambda

**[Требование пользователя]** Внутри lambda поддерживается обычная цепочка
`EntityBuilder`, а не белый список:

```csharp
ctx.From(() => Tvf.MyTvf(42).Where(r => r.Id > 0).Select(r => new { r.Id }));
```

`Where`, `Select`, сортировки, пейджинг, джойны и прочие обычные операторы сохраняют
свою семантику. Вложенные лямбды, проекции и корреляция сохраняются.

**[Требование пользователя]** Полная цепочка не может быть урезана ради упрощения
реализации. Если для неё нужны изменения core-билдера, они входят в scope будущего
плана.

### 4.5 Контекст и исполнение

**[Требование пользователя]** Дескриптор и построение цепочки остаются независимыми
от контекста.

- Дескриптор **никогда не привязывается и не мутируется** для присоединения
  `DataContext`.
- Обработка запроса и команды могут использовать `ctx` как обычно.
- Сам по себе дескриптор ничего не исполняет.
- Исполнение: `ctx.From(lambda).ToList()`.
- Новый сокращённый `ToList(ctx)` **не добавляется**. `ToList(ctx)` существует только
  у `IPreparedQueryCommand` (`src/nextorm.core/DataContext/Cache/IPreparedQueryCommand.cs:106`),
  не у билдера.
- Контекстно-независимое создание/контейнер может существовать, но прямое
  использование без аргументов не является новым транспортом аргументов.

### 4.6 Совместимость с существующим builder API

**[Требование пользователя]** Существующие `From(builder)`/`Join(builder)` для
не-TVF источников сохраняют прежнее поведение.

**[Требование пользователя]** Новый TVF обязан работать через типизированные
ссылки/клоны/композицию `EntityBuilder`, а не только через статический тип производного
получателя. Нельзя опираться исключительно на то, что переменная объявлена как
`TvfEntityBuilder<T>`; сценарии с `EntityBuilder<T>`, клонами и апкастами должны
сохранять TVF-семантику.

### 4.7 Аргументы как SQL-выражения

**[Требование пользователя]** Сохраняются обычные скалярные SQL-выражения в аргументах:

- захваты (captures);
- явный `Parameter<T>`;
- вложенные SQL-функции там, где они поддержаны.

**[Требование пользователя]** Фабрика не преобразует аргументы. Исходное выражение
аргумента `MethodCall` само может содержать поддержанное SQL-выражение.

## 5. Ломающая миграция

**[Требование пользователя]** Удаляются:

- `SqlTableFunctionAttribute`;
- старый API `FromTableFunction`;
- старые TVF-объявления-заглушки, возвращающие `IQueryable`;
- старые compatibility-фабрики, такие как `CreateQueryBuilderFromTableFunction`, если
  они присутствуют в коде.

**[Требование пользователя]** Не допускаются:

- obsolete-shim;
- двойная TVF-модель;
- скрытая поддержка старого способа «на всякий случай».

**[Требование пользователя]** Мигрируют:

- все встроенные TVF-объявления провайдеров;
- существующие тесты;
- примеры;
- бенчмарки;
- документация EN и RU.

**[Требование пользователя]** Нон-TVF механизм скалярных `SqlFunction` не меняется.

**[Решение архитектора]** Существующие имена TVF-каталога и фабрик по возможности
сохраняются; возвращаемые типы при этом меняются.

## 6. Паритет существующих возможностей

**[Требование пользователя]** На runtime-метаданных должны быть эквиваленты:

- `Name`;
- `Schema`;
- `WithClause`;
- `CallClause`;
- `VerbatimArguments`;
- `ResultSchema`.

**[Решение архитектора]** Точная упаковка этих опций — на этапе плана.

**[Требование пользователя]** Сохраняются:

- result schema `None`/`LeadingArgument`/`AliasColumnList`;
- метаданные mapped Row, материализация, конвертеры, nullability;
- поведение диалектов: `SupportsTableFunction` vs custom wrappers,
  `SupportsResultSchema`, `SupportsApply`;
- безопасность и валидация verbatim-аргументов;
- wrapper-касты;
- alias column lists;
- прежнее поведение неподдержанных провайдеров, включая отказ InMemory для TVF.

**[Требование пользователя]** Поддержку InMemory для TVF **не добавляем**.

**[Требование пользователя]** Не переименовываем result-schema enum и не чиним
несвязанные пробелы «заодно».

## 7. Параметризация, план и кэш

**[Требование пользователя]** Идентичность SQL-источника и ключ кэша включают:

- runtime-имя функции;
- схему;
- опции;
- форму результата;
- форму выражений аргументов.

**[Требование пользователя]** Ключ **не может** быть:

- только `MethodInfo` фабрики;
- identity объекта дескриптора.

**[Требование пользователя]** На попадании в кэш значения вызова обновляются. Не
допускаются:

- устаревшие замыкания;
- устаревшие внешние ссылки;
- «залипающие» изменения `QueryCommand.Cache`.

**[Требование пользователя]** Переиспользование одного дескриптора в разных контекстах
не меняет его и не загрязняет параметры.

**[Требование пользователя]** Метаданные фабрики (имя/схема/опции) не зависят от
**значений параметров** и участвуют в идентичности источника и ключе кэша. Поддержка
mutable ambient/DI-конфигурации, изменение метаданных на попадании в кэш и произвольный
capture lifecycle **не является требованием** этого редизайна; это ограничение объёма, а
не запрет обычных статических фабрик.

**[Решение архитектора]** План должен установить нормальную семантику snapshot на
конструкцию: метаданные immutable/snapshot, чтобы мутация не влияла на кэш.

## 8. Ошибки

**[Требование пользователя]** Явно падать, а не подставлять значения по умолчанию,
должны как минимум:

- неподдержанная корреляция;
- неподдержанный провайдер;
- захваченный дескриптор, у которого потеряно выражение аргумента.

**[Решение архитектора]** Конкретные типы исключений — на этапе билдера.

Нельзя «лечить» такие случаи скрытым placeholder-контекстом или проглатыванием
null-ref.

## 9. Чистота фабрик

**[Решение архитектора]** Чистота фабрики означает отсутствие побочных эффектов;
количество её вызовов не гарантируется, поэтому полагаться на побочные эффекты нельзя.

**[Требование пользователя]** Дизайн не расширяется до произвольных вычислений или
замыканий фабрики, которые интерпретируются как SQL. Фабрика — это объявление
источника и его метаданных, а не произвольный код на языке выражений.

**[Требование пользователя]** Поддержка mutable ambient/DI-конфигурации, изменение
метаданных дескриптора на попадании в кэш и произвольный capture lifecycle **не входят в
требования** этого редизайна. Это ограничение объёма, а не запрет обычных статических
фабрик: фабрика возвращает собственные runtime-метаданные (имя/схема/опции), которые
участвуют в ключе кэша.

## 10. Решения архитектора и открытые вопросы плана

### 10.1 Architect calls (не требования пользователя)

- Материализация дескриптора и момент его создания.
- Точная упаковка опций `WithClause`/`CallClause`/`VerbatimArguments`/`ResultSchema`.
- Конкретные типы исключений.
- Сохранение имён каталога/фабрик по возможности.
- Число вызовов фабрики не гарантируется; фабрики чистые.
- Immutable/snapshot-семантика метаданных на конструкцию.

### 10.2 Открытые вопросы для будущего плана реализации

1. Внутренний lowering и переиспользуемая машинерия source-expression.
2. Реализация композиции без привязки TVF к контексту: без скрытого
   placeholder-контекста и без проглатывания null-ref.
3. Конкретные сигнатуры `From`/`Join`/`CrossApply`/`OuterApply` и способ сохранения
   формы аргументов при клонировании и апкастах.
4. Точный формат cache-key и refresh-рецепта для TVF.
5. Как именно дескриптор сохраняет аргументы как выражения, не вычисляя
   коррелированные SQL-аргументы как CLR-значения.

Эти пункты — builder decisions. Их нельзя выдавать за уже согласованные
пользовательские требования.

## 12. Матрица приёмки

Приёмка относится к будущей реализации; сейчас тесты не запускаются.

1. **Метаданные фабрики.** Имя/схема/опции корректны и не зависят от значений
   аргументов.
2. **`From` и параметры.** Литерал, захват, `null`, SQL-выражение; смена значений
   параметров между попаданиями в кэш даёт корректные значения и не даёт stale-план.
3. **Join.** Обычный `Join` с новым lambda-источником; смешанные не-TVF источники
   сохраняют прежнее поведение.
4. **Корреляция.** `CrossApply` и `OuterApply` с аргументом-членом внешней строки,
   захватами и вложенной композицией; нет потери колонок через `default(T)`.
5. **Полная цепочка.** Включая type-changing `Select`, клоны и апкасты к базовому
   `EntityBuilder`, повторное использование запроса/источника и изоляцию между
   контекстами.
6. **Провайдеры.** Паритет фич всех текущих провайдеров: SQL-генерация и
   интеграционные тесты на реальных БД. Перед запуском загрузить инструкции репозитория
   по интеграционным тестам; skips нельзя выдавать за green; неподдержанные провайдеры
   дают явные ошибки.
7. **Cache source identity.** Две чистые статические фабрики возвращают один и тот же
   тип Row и одинаковые формы выражений аргументов, но разные метаданные TVF
   (имя/схема/опции): план одной не должен переиспользоваться для другой. При идентичных
   метаданных источника действует обычная семантика кэша плана.
8. **Миграция.** Ноль старых удалённых TVF API-объявлений/вызовов в docs/tests/
   benchmarks, кроме исторических internal specs.
9. **Качество.** .NET 10, warnings-as-errors, FluentAssertions в тестах, CRLF.

Отдельно фиксируется: метаданные фабрики независимы от **значений параметров**, а
имя/схема/опции входят в идентичность источника и ключ кэша. Mutable ambient/DI-конфигурация,
изменение метаданных на попадании в кэш и произвольный capture lifecycle **не являются
требованиями** этого редизайна.

## 13. Вне объёма (non-goals)

- Общий редизайн context-free движка сверх необходимого для цепочки TVF.
- Новые серверные TVF-фичи и рост каталога.
- Исполнение в InMemory.
- `ToList(ctx)`.
- Обратная совместимость со старой TVF-моделью.
- Изменение API скалярных функций.
- Коммиты, пуш, мерж в рамках этой задачи.

## 14. Этапность и handoff

1. Пользователь ревьюит и одобряет **полный письменный документ**.
2. Только после одобрения создаётся **отдельный план реализации**.
3. Реализация начинается не раньше одобрения плана.

На этом текущий этап останавливается: реализация не разрешена. Открытые
реализационные выборы остаются builder decisions и не переклассифицируются в
пользовательские одобрения.

**[Результат builder-check]** После удаления непрошенного требования о динамической
конфигурации (mutable ambient/DI, изменение метаданных на cache hit, произвольный capture
lifecycle) открытых **пользовательских** вопросов не остаётся: оставшиеся пункты §10.2 —
builder decisions, а не ожидание решений пользователя.
