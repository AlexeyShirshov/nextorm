# Миграции схемы из метаданных NextORM

Письменная дизайн-спецификация от 2026-11-26 утверждена пользователем.
Трекинг: целевой майлстоун [1.0.13](https://github.com/AlexeyShirshov/nextorm/milestone/11)
выбран пользователем; GitHub issue [#423](https://github.com/AlexeyShirshov/nextorm/issues/423).

## Цель и границы

Генерировать из итоговых метаданных NextORM обозримый и редактируемый SQL для goose.
NextORM готовит файлы, а внешний goose применяет их без NextORM. Дизайн не вводит
собственный runner или таблицу версий, не генерирует классы миграций в стиле EF
и не сравнивает модель с живой БД.

Для шардированных моделей в Git хранится один набор для данного провайдера,
фиксированного набора бакетов и режима размещения. Dev с 16 бакетами на одной БД
и prod с теми же 16 бакетами на четырёх БД используют байтово одинаковые SQL-файлы
и общий снимок без повторной генерации.

С первого релиза в область поддержки входят PostgreSQL, SQL Server, SQLite,
MySQL, MariaDB и ClickHouse. Провайдер in-memory не входит. Поддержка провайдера
не означает, что генератор умеет выразить любой переход его схемы.

## Архитектура

Общий механизм сравнивает две нормализованные схемы одного провайдера и выделяет
структурные изменения. Адаптер провайдера задаёт нормализацию и эквивалентность типов
и их характеристик, например точности, учитывает возможности диалекта и для каждого
перехода выдаёт либо SQL, либо конкретную диагностику.

Шесть отдельных генераторов упростили бы учёт местных особенностей, но дублировали
бы правила сравнения и диагностику. Для предыдущего состояния выбран переносимый
снимок схемы рядом с SQL: не нужно хранить Git SHA, восстанавливать старый код или
создавать Git-коммит для генерации. Снимок не является C#-кодом.

### Варианты шардированной генерации

- **Выбран:** один параметризованный goose SQL на изменение шардированных моделей
  для провайдера и режима, один общий по бакетам снимок. Goose запускается на каждый
  бакет со своим журналом.
- **Отклонён:** конкретные файлы по бакетам с уникальными версиями, сборка каталога
  из готовых файлов по владельцу и один журнал на БД. Запусков меньше, но файлов
  больше и каталог нужно собирать перед применением.

Набор не содержит каталогов наподобие `pg-1` и `pg-2`, привязанных к dev.
Деплой определяет текущего владельца бакета и подключение по действующей топологии
NextORM (`IShardRouter` / `IShardTopology`). Генератор не фиксирует список хостов.

Решардинг вне объёма задачи. Одна смена владельца не порождает миграцию, `CREATE`,
перенос, переименование, `DROP`, изменение истории или переключение трафика.
Смена режима размещения или размера набора бакетов не считается автоматическим
переходом между раскладками. Initial для пустой схемы в заданной топологии и
обычные изменения модели остаются в объёме задачи.

## Какие таблицы входят в модель

1. Указать одну или несколько сборок, провайдера и конфигурацию маппинга.
   Для шардированной модели задать фиксированный набор бакетов и режим размещения.
2. Найти в выбранных сборках типы с `[SqlTable]` или `[Table]`. Обнаружение работает
   в новом процессе, без предварительных вызовов `From`.
3. Добавить обычные типы через сохраняемую явную регистрацию. Она переиспользует
   фактическую конфигурацию маппинга, а не вводит второй язык её описания.
4. Получить эффективные метаданные через `IEntityMetadataProvider.GetMetadata(Type, in MappingVariant)`
   и существующий общий путь применения атрибутов, fluent-маппинга и конвертеров.

Поиск не выполняет произвольные лямбды запросов. Ни присутствие в `RepositoryContext`,
ни прогрев кэша не определяют владение таблицей. Не каждый POCO или DTO входит в модель.

В снимок входят физическая схема и таблица, колонки, типы провайдера и их точность,
допустимость NULL, ключи и другие свойства, действительно выраженные метаданными.
Неоднозначная подсказка маппинга не становится ограничением БД. Переименование
свойства CLR при неизменном физическом маппинге не меняет схему.

Для `CREATE TABLE` (включая Initial) и последующего `ADD COLUMN` целевой физический
тип и применимые ограничения, в частности допуск NULL, определяет эффективный
C#-маппинг. Источник — действующие правила маппинга и DI: тип, nullable-аннотации,
явная конфигурация там, где она предусмотрена, а для физического типа также
конвертер и диалект. Например, в PostgreSQL без переопределений `int` даёт
`integer NOT NULL`, а `int?` — `integer` с допуском NULL. При включённых nullable
reference types одного `PropertyType` недостаточно: генератор или его проекция
должны читать nullable-аннотацию самого свойства (например, через
`NullabilityInfoContext`), различая `string` и `string?`, а не выводить её из
`System.Type` или C#-инициализатора. Это требование, а не готовое поведение:
`IPropertyMetadata` предоставляет `PropertyInfo` и `Converter`, но не готовые
флаги допустимости NULL, обязательности или серверного значения по умолчанию.
Индексы вне метаданных и правила
включения FK не меняются.

Генератор использует те же физические правила именования, что и путь выполнения
запросов NextORM. Например, при именах по умолчанию для бакета 7 `SchemaPerBucket`
даёт `bucket_7.Orders`, а `TableSuffix` — `Orders_7`. Если диалект не поддерживает
выбранное размещение, генератор выдаёт диагностику. Снимок описывает схему и
размещение независимо от владельцев; SQL и снимок не содержат привязки бакетов
к владельцам, DSN, логинов или адресов.

**Предложение автора:** для одной физической таблицы в цепочке требуется одно полное,
непротиворечивое описание. При конфликте вариантов генератор сообщает о конфликте,
а не пытается молча слить частичные маппинги.

## Файлы и история

У каждого провайдера свой набор с линейной непротиворечивой историей. Шардированный
набор относится к фиксированному набору бакетов и режиму размещения. При изменении
одной области генератор создаёт пару: файл `<version>_<name>.sql` с `-- +goose Up` и
`-- +goose Down`, если генератор строит обратный переход, и одноимённый версионный
файл снимка. Снимок показывает целевую схему **после Up**.

Пример истории нешардированного каталога:

```text
001_initial.sql
001_initial.snapshot.json
002_add_reporting_index.sql
003_add_status.sql
003_add_status.snapshot.json
```

Для версии `003` базой служит снимок `001`: более новый ручной SQL `002` не заменяет
его. Генератор ищет последний по версии снимок только в выбранном наборе. На
пустой истории он строит полный Initial от пустой схемы. Если структурных изменений
нет, он не создаёт файлов. Следующее изменение строится офлайн по последнему
локальному снимку: генератор не ждёт применения предыдущего шага на всех БД.

**Предложение автора:** не перезаписывать занятые версии молча, сериализовать снимки
детерминированно, записывать версию формата и провайдера. При ошибке не публиковать
неполный набор файлов логического шага.

### Применение шардированного набора

В бакетном SQL штатные аннотации `-- +goose envsub on` и `-- +goose envsub off`
ограничивают область подстановки. В физические идентификаторы подставляется только
проверенный целочисленный ID бакета, например `${BUCKET}`; идентификаторы цитируются
по правилам диалекта. Это не подстановка произвольного SQL и не новая система шаблонов.

1. Для каждого бакета процесс деплоя проверяет ID и допустимый диапазон, выбирает
   подключение к текущему владельцу и запускает обычный goose с бакетным `-dir`
   и уникальным для бакета `-table`, например `goose_db_version_b7`. Даже если
   несколько бакетов на одной БД, общий журнал заставил бы второй бакет пропустить
   версию, уже отмеченную первым.
2. Общий SQL процесс деплоя запускает из отдельного `-dir` один раз на каждую
   целевую БД, где он нужен, с собственным журналом, а не по разу на бакет.

DDL общих таблиц не попадает в бакетные файлы и наоборот. **Уточнение архитектора:**
для логического шага, меняющего обе области, сохраняется один общий целевой снимок
и два отдельных SQL-файла, по одному в каждом изолированном исполняемом наборе.
Один логический шаг имеет одну версию. Если изменились обе области, общий и
бакетный SQL могут иметь одинаковый номер в своих отдельных каталогах и журналах.
Внутри одного goose-набора версии не дублируются. Для неизменившейся области
пустой SQL ради номера не создаётся. Для одной области остаётся один SQL и снимок.
Нешардированному проекту не нужны `BUCKET`, `envsub` или дополнительные журналы.

Процесс деплоя отвечает за обход целей, выполнение всех требуемых частей и порядок
зависимостей: Up применяет предпосылки до зависимых изменений, Down — наоборот.
При необходимости деплой выполняет шаги до нужной версии средствами штатного goose.
Универсального порядка запуска двух каталогов целиком нет. Атомарности между
запусками или БД нет: успешно выполненные части при частичном успехе сами не
откатываются, а повторный запуск учитывает их журналы. Если DDL внутри одной
нетранзакционной миграции выполнен частично, оператор проверяет фактическое
состояние; автоматический безопасный повтор или ремонт не гарантируется.
Невозможный межшардовый FK или неразрешимая зависимость требуют явной диагностики
и безопасного ручного SQL, а не молчаливого пропуска.

### Журнал бакета и откат Initial

История относится к логическому бакету, а не к каждой SQL-схеме: `sales_7` и
`billing_7` могут относиться к одному бакету 7 и использовать один журнал. В
PostgreSQL с goose v3.30.2 возможен `-table bucket_7.goose_db_version`, если схема
существует до первого `goose up` и остаётся доступной при Down. Для Initial на
пустой БД или при нескольких схемах маппинга пример — `-table public.goose_db_version_b7`
в уже существующей схеме. Место журнала выбирает деплой, снимок его не фиксирует.

**Предлагаемый защитный default:** `Initial.Down` выполняется только в целевой БД
и, для бакетного SQL, только в том бакете, где журнал отмечает Initial как
применённую. Он удаляет только созданные Initial управляемые табличные объекты и
ограничения: без `DROP SCHEMA CASCADE`, удаления журнала, посторонних объектов
или других бакетов. Откат может оставить пустую схему. Если внешние зависимости
мешают безопасному откату, требуется явное вмешательство, а не каскадное удаление.

## Старт с существующей БД

Scaffold уже читает схему БД и генерирует маппинги. Направление для будущей работы —
общий формат снимка, ограниченного выбранной управляемой схемой. Это не утверждение,
что Scaffold уже экспортирует такой формат.

Пользователь явно отложил только процедуру, позволяющую считать Initial применённой
к уже существующей БД, до начала реализации и повторной проверки возможностей
актуального релиза goose. Для спецификации и планирования остального генератора
вопрос закрыт как отложенный: интеграцию с журналом goose не разрабатываем,
приёмку генератора от наличия `stamp` не ставим в зависимость. Это не отменяет
контракт совместимого снимка из Scaffold и не исключает будущей поддержки процедуры.

## Ручное ревью и ограничения

Для обычной управляемой схемы каждый из шести провайдеров обязан автоматически
генерировать SQL для следующих операций:

- Создание таблицы в Initial или при добавлении новой модели после Initial.
- `ADD COLUMN` для колонки, описанной C#-моделью, с допуском NULL или `NOT NULL`
  по эффективному маппингу, если диалект допускает переход и не нужен выбор
  значений пользователем.
- Удаление обычной колонки или таблицы без блокирующих зависимостей, с явным
  предупреждением о потере данных.

В этих условиях диагностика или предложение написать SQL вручную не заменяют
автогенерацию. Целевая схема и снимок сохраняют `NOT NULL`, если его требует
маппинг: генератор не заменяет его на NULL ради простоты обновления. Он не читает
живую БД для подсчёта строк. Если добавление применимо только к пустой таблице,
он явно указывает это предусловие и риск ошибки на непустой таблице.

Если для непустой таблицы нет безопасного автоматического перехода без заданного
серверного значения или правила заполнения, генератор выдаёт адресную диагностику
и указывает явный ручной переход. Например, этапы могут быть такими: временный
допуск NULL → `UPDATE` со значениями, заданными пользователем → `NOT NULL`.
Генератор не придумывает ноль или пустую строку и не считает `default(T)` или
инициализатор C# серверным значением для старых строк. Наличие `NOT NULL` в
целевом DDL не гарантирует его применение к любым старым данным.

Для сложных операций — изменения типа, перевода в `NOT NULL`,
заполнения данных (backfill) или перестройки таблицы — адаптер генерирует безопасный
вариант либо сообщает конкретную причину и указывает необходимый ручной переход.
Одинаковая автоматизация всех случаев и поддержка любого режима шардирования
в любом диалекте не гарантируются.

Генератор не угадывает намерение при неоднозначном переименовании. При удалении он
выдаёт заметное предупреждение с именем объекта и риском потери данных. Если
`DROP` + `ADD` означает переименование, при ревью можно заменить эти операции в Up
и Down на переименование. Если целевая схема не меняется, снимок править не нужно.
Down возвращает структуру, но не восстанавливает удалённые данные.

Ручная правка сгенерированного перехода сохраняет согласованность SQL и снимка.
Самостоятельной ручной миграции для объекта вне модели снимок не
нужен. Например, индексы вне метаданных не входят в сравнение схем; это граница
дизайна, а не обещание позже добавить их в метаданные. Goose применяет такой ручной
SQL в соответствующем исполняемом наборе вместе с генерируемыми миграциями.

Внешние ключи (FK) по связям — сохраняемая опция генератора для выбранного
провайдера, по умолчанию выключенная. «Не управлять» не означает «удалить»:
выключение не удаляет ранее сгенерированный FK, отсутствие ручного FK в модели не
удаляет его, а повторное включение не дублирует уже учтённый FK.

Если информации или поддержки не хватает, диагностика называет провайдера, объект,
причину и указывает, какой SQL требуется подготовить вручную. Генератор не выдаёт
исполняемый TODO, фиктивную пустую миграцию или снимок, изображающий успешный переход.
**Предложение автора:** явно доработать переход вручную, прежде чем помещать
согласованные файлы в исполняемые каталоги.

Например, изменение типа в SQLite может потребовать пересборки таблицы с сохранением
индексов и триггеров, неизвестных модели. Генератор не должен молча их терять.
В ClickHouse первичный ключ ORM, ключ сортировки и физический FK не взаимозаменяемы.
Дизайн не обещает эмуляцию ограничений и не фиксирует все настройки провайдеров.

## Будущие критерии проверки

- Холодное обнаружение и запуск с прогретым кэшем дают одну схему. Типы с атрибутами
  и явно зарегистрированные обычные типы входят в неё; посторонние типы — нет.
- Схема отражает итоговый маппинг, включая тип после конвертера и его характеристики.
- Повторная генерация без изменений, ручной SQL вне модели и переименование только
  свойства CLR не дают новых файлов. Следующий diff использует правильный снимок.
- Для каждого из шести провайдеров goose применяет сгенерированный SQL к тестовой
  БД: создание таблицы в Initial и после него, добавление колонки из C#-модели,
  удаление колонки и таблицы без блокирующих зависимостей. При создании и
  добавлении проверяются физический тип, допуск NULL и `NOT NULL` там, где
  переход безопасен. Для обоих удалений проверяется предупреждение о потере данных.
- Для каждого провайдера проверяется отрицательный случай: непустая таблица
  требует заполнения обязательной колонки, но значения или правило не заданы.
  Генератор явно указывает предусловие либо необходимый ручной переход по
  возможностям диалекта. Нет тихой подмены `NOT NULL` на NULL или фиктивного default.
- Каталоги провайдеров изолированы. Ручное переименование сохраняет данные и
  соответствует целевому снимку.
- Для одной модели, фиксированного набора бакетов и режима одни и те же байты SQL
  и снимка работают с двумя картами владельцев: 16 бакетов на одной БД и те же 16
  на четырёх БД. Смена только владельца не создаёт миграцию или запись в истории.
- На одной физической БД два бакета с разными `-table` получают изменение каждый.
  Повтор для того же бакета не повторяет DDL, а общий SQL не выполняется дважды.
  Для смешанного шага каждый `-dir` видит только SQL своей области.
- Оба режима размещения используют имена пути выполнения запросов; неподдерживаемый
  диалектом режим и неразрешимые межшардовые зависимости получают диагностику.
- FK не выходят за управляемую область; выключение и повторное включение опции не
  удаляют и не дублируют существующие ключи по описанным правилам.
- Неподдерживаемый переход или переход, затрагивающий объект вне управления,
  не проходит молча. Для выбранных и представимых объектов цикл
  БД → Scaffold → маппинг → снимок сохраняет нормализованную схему.

Технический интерфейс регистрации и CLI, размещение классов и JSON-схема снимка —
решения для плана. Перечисленные проверки относятся к будущей реализации.
