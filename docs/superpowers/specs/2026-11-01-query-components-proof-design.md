## 1. Зачем это нужно и согласованная цель

Цель — доказать, что сторонний пакет может добавлять самостоятельные компоненты к стандартному конвейеру `QueryCommand`, сохраняя обычные расширения и инфраструктуру исполнения. Конкретным proof является внешняя реализация полной текущей переносимой семантики `SelectWhereMin/Max` для всех реляционных семейств БД, включая MariaDb.

Компонент присоединяется обычным extension method. Он не наследует команду, не требует правки core для каждого нового оператора, `InternalsVisibleTo`, регистрации обработчика и не генерирует raw SQL. Это компоненты, а не альтернативные команды. Один слот Min/Max общий: присоединение Max заменяет Min и наоборот. Не предполагаются неявные вложенные запросы min→max. Независимые части допускаются, но произвольная совместимость любых компонентов не обещается: неподдерживаемые сочетания должны давать явную ошибку подготовки.

Общие структурные примитивы должны быть публичными, но узкими; публиковать весь планировщик или SQL builder нельзя. Пользовательский диалект может менять рендеринг представимых конструкций, но не добавляет логические узлы, которых нет в модели. Производительность должна быть не хуже встроенной переносимой реализации, включая теплый кэш. Выбран порядок доказательства: сначала внешний proof; миграция встроенной реализации не входит в задачу.

Вне цели: In-memory; нативное ускорение по провайдерам; перенос, удаление или переадресация встроенного API; универсальная композиция операторов; специальная оптимизация или новая семантика для произвольного SQL.

## 2. Фактическая исходная точка

Следующие сведения — статическая инспекция исходников, не результат выполнения тестов или сборки.

- `EntityBuilder.SelectWhereExtreme` в `src/nextorm.core/Builders/EntityBuilder.cs:2961–2993` устанавливает внутренний `ExtremeRowClause`; `ApplyCommandOptions` в том же файле (`:472`) копирует его в команду. Это единственный слот: новое значение заменяет старое.
- Типизированная команда — `sealed` `QueryCommand<TResult>` (`src/nextorm.core/QueryCommand.TResult.cs:13`). Подготовка экстремальных колонок видна в `QueryCommand.QueryPreparer.cs:129` и `:3712–3727`.
- `SqlBuilder` (`src/nextorm.core/DataContext/SqlBuilder.cs`) имеет специальную диспетчеризацию (`:54–55`), переносимую SQL-реализацию ранжирования (`:1171–1216`) и собственный внешний SELECT (`:1457–1566`). Сам builder — `internal readonly struct`.
- Сейчас нет публичной формы скрытого/пропускаемого дополнительного столбца, независимой от CLR-проекции, либо повторно используемого публичного wrapper для структурного rewrite. У `SelectExpression.OutputName` внутренний доступ, а `SelectList` доступен только для чтения. Публичные окна и derived `From/As` полезны, но сами по себе не доказывают сохранение полной формы запроса.
- Графы `QueryCommand`/`FromExpression` существуют, но это не означает наличия общего публичного SQL AST. `CustomData` не подходит как семантическое хранилище компонентов: оно не является частью ключа и отсутствует в кэшированных клонах.

Issue #302 касается одобренного внутреннего lowering агрегатов `All`; публичного API там нет, реализация не выполнена, и отдельная авторизация сохраняется. Его не менять и не считать зависимостью данного proof. #153 — прецедент внешнего диалекта без friend-доступа. #319 — возможный кандидат на build-once, но не предпосылка и не зависимость. Текущий renderer встроенных экстремумов остается без изменений.

## 3. Архитектура компонентов

Ниже — рекомендации архитектора, предлагаемые для письменного одобрения. Имена и сигнатуры иллюстративны, точный API выбирает builder; пользовательскими решениями они еще не являются.

Builder и типизированная команда получают first-class набор логических компонентов. Операция присоединения (условное имя `WithComponent`) иммутабельна и возвращает производный builder тем же общим стилем, что существующие fluent APIs. Для команды без компонентов необходим быстрый путь с null/empty состоянием: не создавать на каждую команду пустые массивы/словарь или новый dispatcher service.

Компонент владеет логической конфигурацией и выражениями; обработчик перемещается вместе с ним. Не вводятся глобальный реестр, сканирование reflection или общая изменяемая статическая регистрация. Это обычная пользовательская реализация, без проверки имени провайдера в core.

Слот идентифицируется стабильным маркером типа (`Type`), а Min и Max используют общий маркер. Помимо слота, равенство и hash учитывают тип реализации компонента, его семантический дискриминатор (например, min/max) и полное логическое состояние: две библиотеки с одинаковым маркером слота, но разной реализацией, не должны случайно сравниваться равными. Повторное присоединение в слот заменяет значение, сохраняя исходную позицию слота; новый слот добавляется в конец. Не применять строковые bags или публичную семантику `CustomData`. Порядок детерминирован; компоненты не склеивают произвольные SQL-строки.

После присоединения семантическая конфигурация логически неизменяема. Это не запрещает уже поддерживаемую семантику захваченных значений в выражениях: движок по-прежнему связывает их при выполнении. Подготовленное состояние отделено от логического и не мутирует его или builder.

Контракт покрывает четыре ответственности — одним интерфейсом с контекстами либо несколькими, как решит builder:

1. логический вклад и слот;
2. подготовка/валидация с общими механизмами подготовки выражений;
3. структурные hash/равенство с engine expression comparers и правилами идентичности параметров;
4. построение структурного вклада через контекст, принадлежащий движку.

Контексты подготовки и построения ограничены вызовом; компонент не сохраняет их или внутренние буферы после окончания жизненного цикла. Подготовленные логические дескрипторы хранятся при команде. Кэшированный план не должен захватывать свежие значения первого исполнения. Clone, snapshot, reset и reprepare имеют явный жизненный цикл. Живые клоны и снимки кэша сохраняют неизменяемые семантические дескрипторы, а связывание параметров каждого исполнения обновляет runtime values. При существующем reset инвалидируются подготовленный/сгенерированный граф и hash; замороженный ключ нельзя менять незаметно.

## 4. Минимальный структурный контракт

Это не публичный универсальный SQL AST. Предлагаются публичные непрозрачные/типизированные handles с engine ownership для подготовленных источников, выражений/колонок и query fragments; внутренняя модель остается свободной. Контекст различает исходную область строк источника и внешнюю оболочку результата: исходные строки заменяются, а затем движок один раз применяет исходные projection/result type, distinct и output order. Нельзя ранжировать уже полностью спроецированный и отсортированный результат.

Исходные метаданные команды и сопоставления должны сохраняться автоматически. Реализация отдельного оператора не должна вручную копировать поля запроса. Нужны следующие общие возможности:

- получить derived source;
- передать все исходные физические колонки с привязкой к источнику;
- добавить типизированное скрытое вспомогательное выражение с collision-safe handle/именем;
- построить публичные window expressions и predicates;
- заменить row source и перемапить исходные handles;
- отфильтровать по производному вспомогательному столбцу;
- спроецировать исходную форму без скрытого значения.

Исходная строка не обязана упаковываться в анонимный CLR carrier или генерируемый CLR type. Движок отвечает за multi-column mappings, converters, aliases, quoting, захваченные и позиционные параметры, форму результата и materialization. Нельзя раскрывать `SqlBuilder`, `StringBuilder` или внутренний alias provider. Сгенерированная структура идет через обычный renderer. Примитивы общие: не публиковать `MakeExtremeRow` и не добавлять произвольный hook для SQL из custom expression.

Диалект поддерживает стандартные операции, как и сегодня; новые варианты синтаксиса могут быть реализованы поддерживаемыми dialect hooks. Полностью отсутствующий структурный примитив потребует отдельного изменения контракта; произвольная синтаксическая выразительность не обещается.

## 5. Конвейер и совместимость компонентов

Для первой версии вклад ограничен аддитивными source predicates и одним исключительным изменением row source. Этого достаточно для независимого компонента-предиката и extrema. Все аддитивные predicates применяются через AND до выбора строки; порядок вызова extension methods не меняет фазу. Если два разных слота требуют reshape row source, подготовка отклоняет комбинацию. Вложенного объединения или nesting нет. Min/Max одного слота заменяются до проверки конфликта.

Компоненты объявляют эффекты вклада при подготовке; движок проверяет ограниченные конфликты ресурсов и component-specific ограничения. Компонент может читать публичное, read-only представление поддерживаемых возможностей/компонентов, но не чужое private state. В первом контракте нет обязательств поддерживать компоненты, которые меняют projection, output sorting или весь произвольный SQL statement. Это намеренно минимальный proof, а не обещание для всех операторов.

Концептуальный pipeline:

`attach → normalize/prepare expressions + validate + hash/equality key → cache lookup → HIT: reuse executable cached plan + fresh binding; MISS: structural BuildQuery contributions → ordinary SQL emission + standard mapper/parameter extraction → immutable plan storage`.

Это схема интеграции, не утверждение о каждом текущем shortcut или точном порядке внутренних вызовов. На доказанном warm hit `BuildQuery` не вызывается и relational graph не перестраивается. Prepare может обходиться существующим проверенным ранним cache-hit маршрутом только если descriptors и parameter binding представлены корректно. Нельзя отключить кэш/fast paths у команд с компонентами и объявить performance выполненным. Исходные условия и global filters применяются ровно один раз; исходные projection, distinct и sorting — после выбора строки.

## 6. Внешний proof: точная семантика

Proof — отдельная test-only class library без friend-доступа, с обычной core reference. Расширения называются, например, `ExternalSelectWhereMin` и `ExternalSelectWhereMax`, чтобы избежать затенения встроенного instance method. Проверяются overload для builder с целой строкой и для проекционного результата `QueryCommand`, selector `TValue`, необязательный group key и tie policy `One` по умолчанию. Один общий slot-компонент содержит внутренний enum Kind; алгоритм реализуется через общие публичные примитивы. Нельзя делегировать встроенным `SelectWhereMin/Max`, `ExtremeRowClause` или `IExtremeRowRenderer`. Built-ins остаются неизменными.

Переносимый алгоритм совпадает с текущим rank-based baseline: доступные строки учитывают действующие фильтры и исключают строки, у которых любой value component равен `IS NOT NULL`-условию (то есть null value исключен); для `One` используется `row_number`, для `All` — `rank`. Группировка — partition по компонентам ключа. Лексикографический порядок компонентов значения: ASC для min, DESC для max. Внешний фильтр оставляет rank=1; затем применяются исходные projection, `DISTINCT` и пользовательский output order. Скрытые aliases не пересекаются с mapped/selected именами.

Null group key образует допустимую собственную partition. Любой null value component исключает строку. Пустой или целиком null набор дает ноль строк. Для `One` идентичность выбранной среди равных строк не определена; не добавлять выдуманный tie-break из output order. `All` возвращает все ties. Порядок составных компонентов — порядок объявления. Сравнение floating values остается provider-defined как в текущем переносимом поведении; portability для нормализации NaN не обещается. Не терять корректность converter и multi-column mapped payload.

Все нынешние границы совместимости extrema сохраняются, а не расширяются новым proof. Сверяться с `src/nextorm.core/Query/ExtremeRowCompatibility.cs:32–105`: CTE, HAVING, именованные окна, OVER в select list, GROUP BY, joins, LIMIT BY, ARRAY JOIN, PREWHERE, paging, DISTINCT ON, set operations, sampling, temporal, locks, hints, FINAL, SETTINGS, FOR JSON/XML; требуется mapped physical source, SELECT INTO запрещен. `DISTINCT` и output `OrderBy` остаются допустимыми.

Read-only feature view и общие validation facilities должны позволить внешнему потребителю выразить ограничения без internals. Несовместимые несколько компонентов диагностируются до SQL. Запрещенные возможности существующего extrema сохраняют внешне наблюдаемый контракт исключений. Общий конфликт компонента получает отдельную diagnostic ошибку подготовки с указанием слотов/типов.

## 7. Артефакты и тестовая стратегия реализации

Помощник proof — отдельный test-only проект, повторно используемый существующими public-extensibility unit tests, реальными integration tests и benchmark harness. Производственные проекты на него не ссылаются; фиктивный IVT не добавляется. Точное имя/путь проекта выбирает planner реализации.

Проверки должны включать no-friend reflection guard и факт компиляции внешней библиотеки; source-contract проверки гарантируют, что реализация не вызывает встроенные/internal методы и не генерирует raw SQL. SQL-generation проверки охватывают семейства провайдеров, collision скрытых aliases, markers параметров, форму результата, `row_number` против `rank`. Не требуется идентичность SQL-текста или aliases: требуется эквивалентная реляционная стратегия без дополнительных scans/sorts/joins относительно текущего переносимого алгоритма.

Live integration matrix: PostgreSQL, SQL Server, MySQL, MariaDb, ClickHouse, SQLite. Для MariaDb нужен live fixture, если существующий не подходит; запуск MySql не считается доказательством MariaDb. Использовать conventions проекта: без InMemory в integration, FluentAssertions, перед прогонами контейнерного набора загрузить skill запуска integration tests. Тесты без БД — в unit projects. Семантические случаи включают перечисленные выше правила, фильтры/global filters, converters, nullable/composite grouping, projection/distinct/sort.

Проверить независимый source predicate вместе с extrema; replacement Min→Max и Max→Min одного слота; отказ reshape разных слотов. Counter fixture подтверждает, что на доказанном warm hit `BuildQuery` не вызывается. Проверить clone/snapshot/reset; равные формы с разным expression state; hash collisions при корректном неравенстве; изменение captured и positional values при warm cache без устаревших параметров и межкомандной утечки. Ключ равенства учитывает component type, slot, operation и структурные выражения. Добавить regression для незатронутых команд. Не применять sticky отключение кэша к общим `QueryCommand`.

## 8. Критерий производительности

Baseline — текущий выпущенный portable ranking, не native PostgreSQL/ClickHouse и не будущая стратегия #302. Если сейчас выбрался бы native renderer, для baseline и proof используется один и тот же dialect subclass с `ExtremeRowRenderer == null`; прочие возможности сохраняются.

Сравниваются builder construction, cold prepare/SQL и warm cached execute/preparation, allocations и throughput. Набор включает One/All, global/grouped/composite, а также команды без компонентов. Данные, provider settings, projection и filters одинаковы. Пользователь не предоставлял произвольный процент допустимой регрессии: принятие требует отсутствия измеримого  замедления и лишних аллокаций относительно сопоставимого baseline. Статистический шум или неопределенность — не pass: увеличить измерения либо оставить критерий нерешенным.

End-to-end время БД недостаточно, чтобы скрыть host overhead. Сравнить SQL shape, а для репрезентативных данных — планы и фактическое время БД. SQLite не доказывает производительность всех провайдеров. Если архитектура не удовлетворяет цели, остановиться и переработать; не отключать кэш и не ослаблять критерий. Benchmark harness умеет разделять warm/cached пути, но SQL extrema BDN baseline пока не заявлен как существующий; его следует добавить уже в разрешенной фазе реализации. Полный BDN запуск сейчас не разрешен.

## 9. Не-цели, совместимость и критерии приемки

API только additive. Не требуется seal/unseal существующих типов; не менять существующие сигнатуры, defaults или поведение; не переписывать built-in; не публиковать internals целиком; не вводить plugin registry, raw SQL component, общий SQL optimizer, новые dialect syntax или доставку native optimization. In-memory исключен. Пустой набор компонентов сохраняет быстрый путь. Публичная реализация должна добавить EN и RU docs и samples; это внутренний spec, ему не требуется двуязычная версия. Публичная документация не ссылается на specs. Описать ограничения custom dialect и безопасную неизменяемость компонентов. Существующие external dialect renderer contracts сохраняются.

Критерии приемки будущей реализации:

1. **AC1 — внешний доступ:** no-friend portable proof собирается и работает через обычный публичный API.
2. **AC2 — семантика:** полное указанное поведение проверено на provider matrix, включая MariaDb.
3. **AC3 — слоты и композиция:** replacement и ограниченные конфликты ведут себя определенно и диагностируются.
4. **AC4 — lifecycle/cache:** hash/equality, параметры, clone/reset и snapshots не дают stale values или утечки.
5. **AC5 — структурный контракт:** скрытые/pass-through формы строятся общим контекстом и обычным renderer; нет специальных операторных ветвей в core.
6. **AC6 — performance:** нет измеримой регрессии относительно portable baseline; есть controls и проверка warm пути.
7. **AC7 — совместимость:** поведение существующего built-in не изменено.
8. **AC8 — поставка:** документация, tracking и применимые gates выполнены.

Ни один критерий не заявляется выполненным этим документом.

## 10. Происхождение решений и handoff

Пользователь явно выбрал proof-first, внешний ordinary extension, текущую полную portable семантику включая MariaDb, без core-поправки на каждый оператор и без нативного acceleration/миграции built-in. Остальные детали ниже — рекомендации архитектора для письменного одобрения, а не отдельные решения пользователя: Type-based slot markers; сохранение позиции слота при replacement; фаза source predicate перед единственным reshape; `BuildQuery` только на miss; proof-специфичные имена; test-only helper library; forced-portable baseline.

Builder может выбрать точные типы/имена интерфейсов, разделение интерфейсов и размещение файлов, но не менять согласованную семантику или timing. Главные риски — неизвестная стоимость корректной поддержки hidden-column mappings и cache routes. Прототип не выполнен; реализуемость и производительность не доказаны. Если недостающие primitives или ограничения не позволяют полный proof либо целевую производительность, сообщить blocker и переработать дизайн; scope нельзя менять молча. Спецификация не авторизует реализацию всей subtree.

Материалы для handoff: [#362](https://github.com/AlexeyShirshov/nextorm/issues/362), [#302](https://github.com/AlexeyShirshov/nextorm/issues/302), [#153](https://github.com/AlexeyShirshov/nextorm/issues/153), [#319](https://github.com/AlexeyShirshov/nextorm/issues/319); файлы и диапазоны исходников указаны в разделе 2 и разделе 6. `docs/**` текущая схема `docs/**` (asset `docs/assets/diagrams/selectwheremin-current.svg`, ) описывает только текущее состояние: не редактировать и не маркировать как предлагаемую архитектуру.

## Уточнения после свежей builder-проверки

Исторически: проверка полноты выполнена отдельным свежим scout; восемь вопросов разобраны архитектором. На тот момент ответы ниже были решениями архитектора для письменного рассмотрения USER. Текущий статус: письменная спецификация утверждена USER 2026-11-01; план и продуктовая реализация не авторизованы.

1. **Приёмка производительности (AC6).** Допустимый бюджет регрессии — нулевой: latency не выше, throughput не ниже, bytes/op не больше сопоставимого текущего встроенного PORTABLE baseline. Неопределённый результат означает НЕВЫПОЛНЕННЫЙ AC6 и блокирует приёмку, а не разрешение отгрузить риск. Для доказательства архитектор предлагает 99%-й доверительный интервал парного отношения latency external/baseline с верхней границей <= 1.0 (либо эквивалентную нижнюю границу отношения throughput >= 1.0); allocated bytes/op <= baseline в каждом обязательном сопоставимом сценарии. Это строгий предложенный протокол, не отдельно согласованная USER численная настройка. Если доказать условие не удаётся, нужны повторные измерения/перепроектирование; критерий не ослабляется. Длительности jobs, iterations, число независимых запусков и размеры данных фиксирует утверждаемый план ДО сравнительных измерений. Нового timing-based CI gate задача не требует. Обязательная матрица: Min/Max × One/All × global/grouped × scalar/composite, полная сущность и представительный projection/filter, no-component warm-cache controls; construction/cold preparation/warm hit отдельно. SQL/correctness — шесть SQL-семейств; host-overhead — SQLite и отличающиеся provider-generation пути; SQL-стратегия и DB-планы/производительность — на каждом живом семействе. Непроверенный провайдер не считается пройденным. Нельзя скрывать медленный сценарий усреднением; технически тождественные пути можно объединять только с обоснованием в плане.

2. **Oracle для One.** Проверять принадлежность выбранной строки множеству допустимых экстремальных строк и ровно одного победителя на каждую непустую eligible-группу. При равных ключах идентификатор победителя не фиксирован. Для All сравнивать полное мультимножество, порядок — лишь при заданном output order. Differential comparison с built-in допустим для уникального экстремума; built-in не единственный oracle корректности.

3. **Второй компонент.** Независимый source-predicate и конфликтующий reshape — test-only fixtures, не дополнительные поставляемые публичные операторы. Они используют публичный контракт и отдельные слоты; source predicate применяется до extrema.

4. **Присоединение и типы.** Первую публичную attach-операцию требуется предоставить только на EntityBuilder<TEntity> до Select/ToCommand; она возвращает НОВОЕ ЗНАЧЕНИЕ ТОГО ЖЕ EntityBuilder<TEntity>, не подкласс. Состояние переносится в обычный существующий sealed QueryCommand<TResult>. Нового wrapper/альтернативного command-типа и unseal нет. Отдельный публичный attach к уже созданному QueryCommand<TResult> в начальный scope не входит. Clone сохраняет TResult и семантические дескрипторы.

5. **Документация.** Обновить существующие docs/advanced/extensibility.md и docs/ru/advanced/extensibility.md, API docs и inline C# snippets о НОВЫХ КОНТРАКТАХ КОМПОНЕНТОВ И СТРУКТУРНЫХ ПРИМИТИВАХ. Proof-библиотека остаётся test-only, не публикуется в NuGet и не получает отдельного продуктового guide. Новые runnable examples/, страницы и toc-секции не требуются. Публичные docs не ссылаются на specs.

6. **Forced-portable baseline.** Нужный hook уже публичен: наследник PostgresDialect/ClickHouseDialect возвращает ExtremeRowRenderer == null, наследник provider context переопределяет Dialect. Пример: tests/nextorm.publicextensibility.tests/ExternalDialectExtensibilityTests.cs:257–275. Это test/benchmark setup для обоих сопоставляемых вариантов, НЕ новый UseDialect/config API.

7. **Свой диалект.** Нового диалекта/синтаксиса и native-оптимизации в proof не требуется. Возможность использовать существующие dialect hooks сохраняется и документируется; test override пункта 6 не является новой SQL-фичей.

8. **Gates (AC8).** Действуют текущие warnings-as-errors, FluentAssertions и integration-scoping conventions, unit/provider suites и live integration evidence. Текущие whole-solution coverage 85% line/75% branch и integration 65% line/74% branch main-only gates не снижаются; новый core-код не исключается из denominator для обхода gate. Skip провайдера не доказывает поддержку провайдера. Нового timing CI gate нет; coverage-конфиги не расширяются искусственно test-only helper-кодом. Запуск реализации и проверок возможен только после отдельного разрешения.

Текущая диаграмма подтверждена: docs/assets/diagrams/selectwheremin-current.svg. Она описывает существующую реализацию, не предлагаемый pipeline.
