# Implementation plan: shared SQL plan cache

- Issue: [#16 — Thread safety](https://github.com/AlexeyShirshov/nextorm/issues/16)
- GitHub status: In progress (`category:started`), milestone `1.0.12`
- Contract: [approved design](../specs/2026-11-21-shared-cache-thread-safety-design.md)
- Implementation base: `65520e9ce`, branch `feat/issue-16-shared-plan-cache`

Keep the implicit stores thread-local until both the lookup keys and the plans they reach are safe to share. Do not change explicit `Prepare`, cache policy `None`, or the caller's responsibility to avoid overlapping operations on one context or connection.

- [x] **Detach streaming execution from the planning context.** Reproduce retention with a live SQLite stream and keep its cached holder alive during collection. Create the enumerator using the executing context's logging options. Preserve buffered explicit preparation and buffered-to-streaming implicit reuse.
- [ ] **Separate binding from plan state.** Audit writes to holder-owned parameters and both seed and refresh paths. Pass invocation values from the ordinary planner and native binders to command checkout without writing into the published holder or retaining invocation values there. Exercise buffered, scalar, streaming, and fallback binding paths. Verify actual values at `CommandExecuting` as well as query results.
- [ ] **Prove the publication graph and compatibility.** Audit normalized keys, raw preparation entries, native shapes, compiled mappers, metadata, and provider caches transitively. Classify each store by owner, linking path, publication/mutation, and verdict. Remove caller-owned state from cached graphs, including nested and referenced expressions. Key incompatible mappings, provider settings, and SQL shapes separately without keying ordinary bound scalars or connections.
- [ ] **Publish one canonical shared entry.** Switch proven-safe implicit stores to process-wide publication. Losing candidates and indices must not keep alternative holders alive. Verify identity on coordinated cold misses and on warm public calls across unrelated contexts and physical threads. Recheck purge and quiescent clear, including rebuilding the entry after clear.
- [ ] **Verify execution and update the English and Russian docs.** Check command reuse by exact connection, fresh/disposed readers, sequential awaits, explicit `Prepare`, `None`, and existing guards. Run affected unit tests and bounded live-provider groups with native xUnit ID reconciliation. Update the plan-cache and interceptor guides only for implemented behavior.

## Audit started

| Store or family | Ownership and path | Publication or mutation | Verdict and source |
| --- | --- | --- | --- |
| Implicit SQL holder, streaming setup | `QueryPlanner` publishes the holder through `QueryPlanStore`; the holder could outlive the planning context. | The old enumerator delegate read instance fields on `QueryPlanner` and was installed or replaced on a streaming preparation. | Retention reproduced by `SqliteSharedPlanStreamingTests`. Keep the streaming capability flag on the holder and the enumerator and its logging configuration on the execution path. See `DbPreparedQueryCommand.EnableStreaming` and `QueryExecutor.RequireEnumerator`. |
| Structural hash scratch | `ExpressionPlanEqualityComparer` reuses scratch on each thread, including threads that serve independent contexts in sequence. | A heap snapshot showed `_tlsVisitorOwner` was still the comparer owned by the disposed context's live query. Both the owner and the visitor's registry previously outlived the hash call. | Keep only the scratch visitor in TLS. Release the registry and logger in `finally`; a nested hash uses a separate accumulator. See `ExpressionPlanEqualityComparer.GetHashCode` and `Visitor.ComputeHash`. |
| Native binding | `NativeAnyRoute` and `NativeProjectionRoute` select a holder from the native index. | Native hits read closure values into a `BoundQueryInvocation`; checkout applies them under the exact connection's lease. The native binder and visitor do not store those values on the holder. | Native warm writes are isolated. Ordinary preparation and factory seeds still need the separate check below. |
| Ordinary binding and seeds | An ordinary generated plan with refreshed parameters passes a `BoundQueryInvocation` to checkout on both misses and hits. | The factory keeps names and type facets, but no initial values for those plans. On a new connection, the provider creates parameters from the invocation's values; on reuse, checkout binds them under that connection's lease. The stream keeps its array until reader open. | Generated mutable binds are isolated. Audit stable seeds and caller-owned SQL semantics alongside the publication graph before process-wide sharing. |
| Normalized SQL keys | `QueryPlanStore.Set` stores the `QueryPlan` after `GetSqlCacheVersion` replaces the live command with a comparison-only cache clone. | The SQL key removes `OuterRegistry` links along cloned command edges. Covered predicates, prepared columns, both sort roots, and join expressions replace nonliteral reference-type member receivers when plan equality already ignores their values. Direct literals and query-command-valued members keep their existing comparison and hashing. | Partial detachment. Clause objects, components, remaining source forms, and captures outside those receiver positions still need reachability checks. `GetCacheVersion` on the in-memory path keeps its existing clone behavior. |
| Primary plan equality and publication | `QueryPlan` owns the normalized command and its comparer; the public command's internal key slot can memoize the stored key. | `GetSqlCacheVersion` mutates the key before insertion. Structural expression equality uses call-local state; hashing uses thread-local scratch that releases its registry. `Set` currently replaces the dictionary value. | Equality scratch is not a global publication blocker. Publication must select one holder and return its key; only a fresh candidate may be frozen, never a key another invocation can already read. |
| Raw index | `QueryPlanStore.SetRaw` stores the normalized key, its holder, and a raw descriptor. Receiver tokens are non-owning and ordered by occurrence. | `TryGetRaw` verifies the descriptor before staging. When preparation preserves eligible `WHERE` and `ORDER BY` expressions, the descriptor stores comparison-only syntax and the recipe uses the current command's own clauses. | A hash match cannot authorize staging an unequal covered expression or a different receiver. Other prepared shapes still use the existing thread-local executable snapshot. |
| Query components | The normalized clone originally copied the components, descriptors, and effective preparation inputs. The raw index also kept the original `ComponentSet`. | The normalized key uses comparison-only descriptors for packaged grouping and extrema. The raw index snapshots the outer component shape; staging preserves the live command's outer component list. | Live SQLite proves the two normalized paths and the raw component path without captures. Nested raw components, captured selectors and effective clauses, and opaque third-party descriptors still need checks. |
| Native index identity | `QueryPlanStore.TryGetNative` verifies exact tokens after probing a hash bucket. | The header compares physical source fields, mapping and dialect identities, and context defaults (quoting, naming, keyword case, timeout). Custom naming conventions contribute weak-key identity tokens, not a reference to the convention or an identity hash. | The covered fields no longer use hash-only equality. `SetNative` only replaces an entry if it has the same `ShapeKey` object. It does not deduplicate independently created structural equals or check ownership in the primary map. Resolve both before sharing the index. |
| Naming convention compatibility | Normalized and raw SQL keys use non-owning convention tokens, consistent with native and column-name caching. | The raw descriptor compares explicit and effective convention identities before staging. It does not invoke user equality or hash overrides. The normalized cache clone keeps the custom convention's token instead of the service. | Equal custom objects can still choose different columns; their plans must not alias. The separate raw preparation recipe still retains the convention it needs to render. |
| Dialect identity | Normalized keys, raw descriptors, and native tokens use the effective SQL dialect. | Built-in instances register immutable configuration values on construction. PostgreSQL, MariaDB, and ClickHouse include version; SQL Server includes major version, engine edition, and vector syntax. Other dialect implementations participate by weak-key identity. | An equal configuration can reuse a plan without sharing a dialect, connection, or context object. The mapper cache is a separate store and still needs its own compatibility check. |
| SQL-keyed row-mapper cache | `RowMapperFactory.GetOrBuild` publishes compiled delegates through `MapperCache`. | `MapperColumnShape` takes an ordered snapshot of materializer inputs, including entity-item grouping and the per-column streaming flag. A hash only rejects or selects candidates; equality compares the columns. The key has no select expression or converter instance. | Key detachment does not detach the compiled delegate. `ConvertFromProvider` emits the converter as a constant. Audit converter ownership and externally supplied materializers separately. The `ExecuteRaw` reader-shape cache is a separate path. |
| Column name cache | `MemberInfoExtensions.GetPropertyColumnName` shares a process-wide column-name dictionary. | Default mapping reads registered metadata; scoped mapping calls the executing context's metadata provider. The dictionary keeps identity tokens, not provider or convention instances. Registration can invalidate names by entity type. | The equal-provider collision is reproduced on live SQLite. The dictionary never calls the custom provider's `Equals`; two distinct services get distinct tokens. |
| Select lists and scalar expression accessors | `DataContextCache` publishes metadata, select lists, and `ExpressionsCache` delegates across contexts. | Metadata writers share `MetadataRegistrationGate`. Metadata-less derived sources don't publish into the type-keyed select-list cache. `ValueExpressionAccessor` builds both the scalar key and delegate from the same slot-parameterized body. | Captured and static members, folded values, computed column names, pair-range bounds, and window frame evaluations no longer publish input values in the accessor cache. This doesn't verify how the SQL plan key distinguishes SQL-shaping values. |
| Subquery expression accessors | `CorrelatedQueryExpressionVisitor` and `NormSqlTranslator` also write to `ExpressionsCache`. | Uncorrelated builder terminals and direct command operands that are constants or constant-rooted members use `ValueExpressionAccessor`. More complex operands and the SQL translator branches (`NormSqlTranslator.cs:264`, `:352`) still key on original expressions. | Direct `EXISTS` operand detachment passed on live SQLite. The writer at `CorrelatedQueryExpressionVisitor.cs:181` uses the non-preparing constructor, whose only engine caller is `InMemoryRowMaterializer`; it is not a SQL L1 producer. |
| Collection expression accessors | `DataContextCache.InValuesCache` serves `IN`, dictionary lookups, and provider array and map operands. | The timed dictionary publishes a parameterized expression key and a delegate compiled from that same tree. Its generated reads name a slot and type, never a specific runtime value; each call owns its argument list. Unsupported expression nodes use call-local evaluation. | Engine-created entries no longer root collection owners. They reuse the delegate for the same CLR shape and distinguish exact member identities. A race can compile equivalent accessors without exchanging invocation state. |
| Stable parameter seeds | For generated implicit plans, `QueryPlanner` retains a seed in `PreparedCommandFactory` only when the expression is stable and the provider value is a known immutable scalar. The parameter template snapshots layout, type facets, and origin flags. | Inline `IN` and tuple elements can become mutable provider values after conversion. Such values are supplied per invocation, even though the expression is stable. | Verified with a converted SQLite BLOB on two connections. Caller-supplied SQL uses the separate binding path described in the next row. |
| Caller-supplied SQL | `WithSql` attaches a `RawSqlOverride` to the live command. `PrepareFromSql` requests L1 only when the caller sets `PrepareFromSqlMode.StoreInCache`; ordinary execution of `WithSql` can also reach L1. | The key compares the raw text and ordered parameter names. Both a hit and a miss read the current bag; a cached holder stores layout but not those values. A non-cached preparation still owns its values. | Verified on live SQLite in the focused build. The raw override and its reflection properties stay on the live command, not on the published key. |
| Composable SQL sources | `FromSql` sources have an instance-based key. A table-valued function has a structural SQL identity and a separate runtime factory expression. | The normalized clone drops the `FromSql` parameter bag and keeps an opaque token for its existing source identity. It keeps TVF metadata and comparison-only arguments but not the factory receiver. The renderer and parameter walk still use the live source. | Does not broaden raw SQL reuse or change `WithSql`/`PrepareFromSql`. Opaque derived fragments, component graphs, special source metadata, and arbitrary constants still need a transitive ownership check. |
| Default `FROM` lookup and mapping identity | `QueryPlanner.GetFrom` shares reflected sources only for the built-in metadata provider and the default variant. | Normalized and native keys and raw descriptors distinguish custom metadata providers and variant resolvers by weak-key identity. The normalized source comparison checks the table, schema, and source flags. | Different custom mappings must not adopt each other's `FROM` or compiled SQL. This identity does not keep a custom mapping service alive. |
| L2 command state | A holder owns a `ConditionalWeakTable` keyed by exact `DbConnection`. Both references in its last-pair memo are weak. | `Acquire` takes a per-state lease before binding. Implicit holders register their state by exact connection with weak keys. `DbConnectionManager.DisposeConnection` and `ConnDisposed` forget the connection's states without reading L1 or touching the provider commands. | Selective cleanup and command reuse on distinct connections passed on live SQLite, including cleanup from a different physical thread. This verifies holders published in the primary store; native aliases still need a canonical ownership check. |

## Scalar accessor ownership and raw receiver occurrences

- With plan caching deliberately disabled, the SQLite scalar-owner regression failed on `3165a8c7`: the row was correct and the process-wide `ExpressionsCache` contained an accessor, but the first owner was still alive. On the scalar-accessor candidate the owner was collected while that accessor stayed cached. - The Debug solution build for the scalar accessor change passed without warnings. The same build passed 31 selected live SQLite results, 75 focused core results, and 10,464 provider results including all eight explicit SQL Server cases. Exact result IDs reconciled. The opt-in SQLite rowid LOB test was skipped. Evidence: `/tmp/opencode/integration/issue-16-scalar-accessor.EsIknr/`.
- On that build, `raw-occurrence-probe.cs` exposed a separate issue: queries with receiver sequences `A, B, A` and `A, B, B` sent `Target=1` twice and both returned row `1`.
