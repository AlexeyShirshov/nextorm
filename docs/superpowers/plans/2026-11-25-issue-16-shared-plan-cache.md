# Implementation plan: shared SQL plan cache

- Issue: [#16 — Thread safety](https://github.com/AlexeyShirshov/nextorm/issues/16)
- GitHub status: In progress (`category:started`), milestone `1.0.12`
- Contract: [approved design](../specs/2026-11-21-shared-cache-thread-safety-design.md)
- Implementation base: `65520e9ce`, branch `feat/issue-16-shared-plan-cache`

Keep the implicit stores thread-local until both the lookup keys and the plans they reach are safe to share. Do not change explicit `Prepare`, cache policy `None`, or the caller's responsibility to avoid overlapping operations on one context or connection.

- [x] **Detach streaming execution from the planning context.** Reproduce retention with a live SQLite stream and keep its cached holder alive during collection. Create the enumerator using the executing context's logging options. Preserve buffered explicit preparation and buffered-to-streaming implicit reuse.
- [ ] **Separate binding from plan state.** Audit writes to holder-owned parameters and both seed and refresh paths. Pass invocation values from the ordinary planner and native binders to command checkout without writing into the published holder or retaining invocation values there. Exercise buffered, scalar, streaming, and fallback binding paths. Verify actual values at `CommandExecuting` as well as query results.
- [ ] **Prove the publication graph and compatibility.** Audit normalized keys, raw preparation entries, native shapes, compiled mappers, metadata, and provider caches transitively. Classify each store by owner, linking path, publication/mutation, and verdict. Remove caller-owned state from cached graphs, including nested and referenced expressions. Key incompatible mappings, provider settings, and SQL shapes separately without keying ordinary bound scalars or connections.
- [ ] **Publish one canonical shared entry.** Switch proven-safe implicit stores to process-wide publication. Losing candidates and indices must not keep alternative holders alive. Verify identity on coordinated cold misses and on warm public calls across unrelated contexts and physical threads. Recheck purge and quiescent clear, including rebuilding the entry after clear.
- [ ] **Verify execution and update the English and Russian docs.** Check command reuse by exact connection, fresh/disposed readers, sequential awaits, explicit `Prepare`, `None`, and existing guards. Run affected unit tests and bounded live-provider groups with native xUnit ID reconciliation. Update the plan-cache and interceptor guides only for implemented behavior.

## Audit started

| Store or family | Ownership and path | Publication or mutation | Verdict and source |
| --- | --- | --- | --- |
| Implicit SQL holder, streaming setup | `QueryPlanner` publishes the holder through `QueryPlanStore`; the holder could outlive the planning context. | The old enumerator delegate read instance fields on `QueryPlanner` and was installed or replaced on a streaming preparation. | Retention reproduced by `SqliteSharedPlanStreamingTests`. Keep the streaming capability flag on the holder and the enumerator and its logging configuration on the execution path. See `DbPreparedQueryCommand.EnableStreaming` and `QueryExecutor.RequireEnumerator`. |
| Structural hash scratch | `ExpressionPlanEqualityComparer` reuses scratch on each thread, including threads that serve independent contexts in sequence. | A heap snapshot showed `_tlsVisitorOwner` was still the comparer owned by the disposed context's live query. Both the owner and the visitor's registry previously outlived the hash call. | Keep only the scratch visitor in TLS. Release the registry and logger in `finally`; a nested hash uses a separate accumulator. See `ExpressionPlanEqualityComparer.GetHashCode` and `Visitor.ComputeHash`. |
| Native binding | `NativeAnyRoute` and `NativeProjectionRoute` select a holder from the native index. | Native hits read closure values into a `BoundQueryInvocation`; checkout applies them under the exact connection's lease. The native binder and visitor do not store those values on the holder. | Native warm writes are isolated. Ordinary preparation and factory seeds still need the separate check below. |
| Ordinary binding and seeds | An ordinary generated plan with refreshed parameters passes a `BoundQueryInvocation` to checkout on both misses and hits. | The factory keeps names and type facets, but no initial values for those plans. On a new connection, the provider creates parameters from the invocation's values; on reuse, checkout binds them under that connection's lease. The stream keeps its array until reader open. | Generated mutable binds are isolated. Audit stable seeds and caller-owned SQL semantics alongside the publication graph before process-wide sharing. |
| Normalized keys | `QueryPlanStore.Set` stores the `QueryPlan` after `GetCacheVersion` replaces the live command with a cache clone in place. | The cache clone copies referenced queries, `FROM`, CTE queries, sorting, and prepared column descriptors. The expressions inside those descriptors and the prepared predicates still travel by reference, as does `OuterRegistry`. | The clone is not proof of detachment. Audit captured constants and nested registries before publication. |
| Raw index | `QueryPlanStore.SetRaw` stores the normalized key, its holder, and a raw descriptor. The descriptor keeps raw expressions plus non-owning receiver tokens in occurrence order. | `TryGetRaw` verifies the descriptor before the planner applies cached preparation. `ApplyPreparationFrom` copies joins, sorting, and prepared column descriptors, but still reads the stored expression and nested command graphs. | A bucket collision and a different receiver at the same occurrence both reject the candidate. The raw expressions and staged preparation still need detachment before process-wide publication. |
| Native index identity | `QueryPlanStore.TryGetNative` verifies exact tokens after probing a hash bucket. | The header compares physical source fields, mapping and dialect identities, and context defaults (quoting, naming, keyword case, timeout). Custom naming conventions contribute weak-key identity tokens, not a reference to the convention or an identity hash. | The covered fields no longer use hash-only equality. Verify canonical holder ownership before sharing the index. |
| Dialect identity | Normalized keys, raw descriptors, and native tokens use the effective SQL dialect. | Built-in instances register immutable configuration values on construction. PostgreSQL, MariaDB, and ClickHouse include version; SQL Server includes major version, engine edition, and vector syntax. Other dialect implementations participate by weak-key identity. | An equal configuration can reuse a plan without sharing a dialect, connection, or context object. The mapper cache is a separate store and still needs its own compatibility check. |
| SQL-keyed row-mapper cache | `RowMapperFactory.GetOrBuild` publishes compiled delegates through `MapperCache`. | `MapperColumnShape` takes an ordered snapshot of materializer inputs, including entity-item grouping and the per-column streaming flag. A hash only rejects or selects candidates; equality compares the columns. The key has no select expression or converter instance. | Key detachment does not detach the compiled delegate. `ConvertFromProvider` emits the converter as a constant. Audit converter ownership and externally supplied materializers separately. The `ExecuteRaw` reader-shape cache is a separate path. |
| Column name cache | `MemberInfoExtensions.GetPropertyColumnName` shares a process-wide column-name dictionary. | Default mapping reads registered metadata; scoped mapping calls the executing context's metadata provider. The dictionary keeps identity tokens, not provider or convention instances. Registration can invalidate names by entity type. | The equal-provider collision is reproduced on live SQLite. The dictionary never calls the custom provider's `Equals`; two distinct services get distinct tokens. |
| Select lists and scalar expression accessors | `DataContextCache` publishes metadata, select lists, and `ExpressionsCache` delegates across contexts. | Metadata writers share `MetadataRegistrationGate`. Metadata-less derived sources don't publish into the type-keyed select-list cache. `ValueExpressionAccessor` builds both the scalar key and delegate from the same slot-parameterized body. | Captured and static members, folded values, computed column names, pair-range bounds, and window frame evaluations no longer publish input values in the accessor cache. This doesn't verify how the SQL plan key distinguishes SQL-shaping values. |
| Subquery expression accessors | `CorrelatedQueryExpressionVisitor` and `NormSqlTranslator` also write to `ExpressionsCache`. | The uncorrelated builder-terminal path uses `ValueExpressionAccessor` to read the current builder. Other producers still key on original expressions and can compile parameters, closures, or a visitor receiver into the accessor. | Partially detached. Keep the accessor and normalized plan audits separate: a recipe can read fresh expressions only after its command has itself been built from the current invocation. |
| Collection expression accessors | `DataContextCache.InValuesCache` serves `IN`, dictionary lookups, and provider array and map operands. | The timed dictionary publishes a parameterized expression key and a delegate compiled from that same tree. Its generated reads name a slot and type, never a specific runtime value; each call owns its argument list. Unsupported expression nodes use call-local evaluation. | Engine-created entries no longer root collection owners. They reuse the delegate for the same CLR shape and distinguish exact member identities. A race can compile equivalent accessors without exchanging invocation state. |
| Stable parameter seeds | `QueryPlanner` retains values marked stable in `PreparedCommandFactory` when no invocation refresh is required. The parameter template snapshots only layout, type facets, and origin flags. | Inline `IN` values and stable tuples pass through `ConvertToProviderValue` before their stability flag is set. `InValues.IsStableValueExpression` also allows value types that can contain references. The resulting seed is used to create a parameter on each connection. | Shape stability doesn't imply ownership or immutability. Verify stable and caller-owned raw SQL seed graphs before sharing holders. |
| Caller-supplied SQL | `WithSql` attaches a `RawSqlOverride` whose factory reads the properties of the supplied parameter object. `PrepareFromSql` requests L1 only when the caller sets `PrepareFromSqlMode.StoreInCache`; ordinary execution of `WithSql` can also reach L1. | Today the SQL text participates in the lookup, but the factory is invoked only on a miss. The holder keeps the resulting values instead of using the generated-query invocation path. | Preserve the supported raw modes; do not let an implicit process-wide store publish caller-owned values. Prove lifetimes and current binding behavior before changing this path. |
| Default `FROM` lookup and mapping identity | `QueryPlanner.GetFrom` shares reflected sources only for the built-in metadata provider and the default variant. | Normalized and native keys and raw descriptors distinguish custom metadata providers and variant resolvers by weak-key identity. The normalized source comparison checks the table, schema, and source flags. | Different custom mappings must not adopt each other's `FROM` or compiled SQL. This identity does not keep a custom mapping service alive. |
| L2 command state | A holder owns a `ConditionalWeakTable` keyed by exact `DbConnection`. | `Acquire` takes a lease before binding. `DbConnectionManager.DisposeConnection` and `ConnDisposed` enumerate `QueryPlanStore.Values` to detach their connection. | Partial audit. The enumeration only exposes primary holders on the current thread. Verify `ResetConnection` and native holder ownership before widening publication. |

## Native compatibility evidence

- A live SQLite probe reproduced a compatibility mismatch on the cold-binding candidate: two contexts with timeouts of 7 and 19 seconds both returned the correct row, but the second command used the first context's timeout of 7. The normal key already compares the resolved timeout; the native header didn't carry it. The probe did not start or use a server.
- `NativeList_DifferentContextTimeouts_UseTheirOwnPlan` pairs live results and `CommandExecuting` timeouts, and checks that repeating a compatible call still hits the native index. `Matches_ShouldVerifyThePhysicalSourceAndCommandTimeout` checks that the structural comparison rejects different source schemas and different timeouts independently of bucket hashing.
- The old primary-generation transition reset the raw index but not the native index. If the primary store was read first after `Clear`, the native index could see the new generation on the primary store and still serve its old alias. The transition now drops both indices. `NativeList_ClearThenReadPrimaryStore_DoesNotReuseTheOldNativeEntry` checks that the next call publishes a replacement and only subsequent calls reuse it.
- The solution build and affected unit/provider suites passed: 13,201 results passed, no failures, and one opt-in diagnostics case skipped. The rebuilt live SQLite assembly discovered the timeout and clear regressions, and all 15 results passed with no missing, duplicated, or skipped IDs. See `verified-key-candidate.sha256`, `verified-key-discovery.json`, and `verified-key-run.jsonl` under `/tmp/opencode/integration/issue-16-cold.kXGKmT/`. The process-wide store is still disabled.

## Prepared graph ownership

- `CacheKeyAndStagedRecipe_DoNotShareMutableQueryParts` found that the original command and its published key shared the sort array (`graph-baseline-raw.jsonl`). The same transfer allowed a warm staged recipe to share joins, sort slots, and mutable select descriptors with the key.
- The cache clone now owns its sort array and a copy of each prepared column descriptor. Raw apply copies the sorts, joins, and prepared columns before installing them into a live command. A cache clone no longer copies the originating logger. The copies still share expression nodes and may reach `OuterRegistry`, component state, and nested graphs.
- At this stage, `CopyTo` still copied `LookupPartitions`, including evaluated dictionary entries. Normalized `IN` and lookup keys still accepted matching shape hashes without comparing the arity, count, and null-mask structure.
- The updated solution builds without warnings. ## Derived select lists and collection shape

- A live SQLite query with a nested metadata-less derived source returned the expected rows but left its query-specific column list in the type-keyed select-list cache. Only lists built from entity metadata enter that cache now; the derived projection stays on its own command. The regression failed before the change and passed afterward.
- Scalar list counts and null presence, tuple arity and ordered null slots, and lookup entry counts now contribute exact value-free tokens. The hashes remain useful for lookup, but both normalized equality and the memoized key compare the exact shape. Forced `WHERE` and `PREWHERE` hash collisions reproduced false matches before the change.
- The Debug solution build passed. On one frozen integration build, 21 live SQLite results passed across two processes with all 18 native case IDs and 21 result IDs reconciled. Coverage includes the derived-list regression, existing binding and lifetime cases, tuple lists, and CTEs. Local evidence: `/tmp/opencode/integration/issue-16-shape.ysH8y3/`.
- A dictionary lookup on two independent SQLite connections returned each caller's own row and sent its own key/value entries at `CommandExecuting`, but the normalized key kept the first invocation's evaluated entries. Cache clones now keep only the lookup shape, not those evaluated entries. Raw preparation does not stage row-dependent lookups from a stored command.
- A weak-reference test using a constant expression isolated another retention path: `ExpressionKey` held the query registry even though the expression didn't. The registry is now used only during hashing. The expression itself and the delegates stored by individual accessor producers still need separate ownership checks.
- The latest Debug solution build passed with no warnings. The 62 focused core results and 22 live SQLite results passed, including both retention regressions. On the frozen SQLite build, all 19 discovered case IDs and 22 result IDs reconciled without skips; the two fixture groups ran in separate processes. See `final-core-focused.jsonl`, `final-candidate.sha256`, and `final-{local,seeded}-{discovery,run}`.
- The broader SQLite run exposed nine tests still casting a bound invocation to its underlying plan. The corrected tests compare plan identity separately from invocation values; the cache-clear regression also executes both invocations. All 45 cases in the affected cache-clear, TVF, and plan-key groups passed with matching IDs (`final-sqlite-classes.jsonl`).
- The complete SQLite provider suite passed 2,406 results, with one opt-in rowid LOB probe skipped and no failures. Every started result ID had exactly one terminal result (`final-sqlite-unit.jsonl`).
