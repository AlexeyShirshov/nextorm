# Статья 3. Как устроен Nextorm: от описания запроса до результата — структурированный план

> **Статус:** предварительный план и тезисы для обсуждения, не связный текст. Прозу пишет автор.
>
> **Место в серии:** статья 1 — происхождение и мотивация; статья 2 — исследование производительности; статья 3 — устройство Nextorm и инженерные решения, позволяющие объединить выразительный API и низкие накладные расходы.
>
> **Аудитория:** .NET-разработчики, знакомые с C# и основами SQL; объяснять механизм на конкретном сквозном запросе.
>
> **Центральный вопрос:** как устроена ORM, которая позволяет структурно описывать запросы и повторно использовать дорогостоящую подготовительную работу?
>
> **Основной тезис:** единый QueryCommand описывает запрос целиком; деревья выражений C# используются как части его структуры; подготовка, генерация SQL и материализация результата выполняют разные задачи и имеют разные возможности для повторного использования.

## Предлагаемая последовательность

### 1. От задачи к архитектуре
**Задача:** сформулировать ограничения решения, а не пересказывать историю WORM.
- Хотим описывать запрос программно, без SQL-строк в прикладном коде.
- Нужны выразительность, контролируемая генерация SQL, разные СУБД и минимальные накладные расходы при повторных выполнениях.
- Показать один короткий типовой запрос, который будет проходить через всю статью.
- Не смешивать «статически типизированный API» с доказательством семантической корректности любого SQL-запроса.

### 2. QueryCommand — единое представление запроса
**Задача:** показать центральную структурную идею.
- QueryCommand хранит аспекты запроса (фильтрация, проекция, сортировка, группировка и другие поддерживаемые части); это описание, а не готовый SQL.
- Пользовательское построение запроса и последующая обработка отделены.
- Наследование идеи WORM QueryCmd, но реализация и API другие.
- Иллюстрация: схема состава объекта и пример его построения.
- Проверить по текущему коду точные названия свойств/типов, прежде чем публиковать их.

### 3. Выражения C# вместо собственного языка построения условий
**Задача:** объяснить главный сдвиг от WORM к Nextorm.
- Деревья выражений интегрированы в основной механизм описания запроса, а не существуют только как вход отдельного LINQ-провайдера.
- Типизированность и инструменты IDE — достоинства такого способа описания.
- LINQ как query provider и System.Linq.Expressions — не одно и то же: не называть Nextorm полноценным LINQ-провайдером без подтверждения.
- Важное разграничение: обработка expression tree для SQL не равна Expression.Compile и не превращает SQL в нативный код.

### 4. Путь запроса до SQL
**Задача:** показать стадии обработки, их границы и ответственность.
- От QueryCommand через подготовку/нормализацию к SQL-представлению и параметрам.
- Отдельная роль диалекта SQL и различий между СУБД.
- Что известно заранее и что остаётся значениями параметров времени выполнения.
- Вставить схему pipeline, опираясь на текущий код; не объявлять перечисление стадий окончательным без сверки.

### 5. Выполнение и отображение результата
**Задача:** пояснить, зачем компилировать выражения в .NET.
- Генерация SQL и materialization/row mapping — разные задачи.
- Делегаты маппинга могут компилироваться и повторно использоваться для быстрого преобразования строк результата в объекты.
- Со слов автора, именно ускорение маппинга было исходной целью компиляции выражений; иные применения не приписывать исходному замыслу.
- Показать схему «строка данных → mapper → результат», без неподтверждённых цифр выигрыша.

### 6. Cached и Prepared: что именно повторно используется
**Задача:** связать внутреннее устройство с темами второй статьи.
- Cached Queries: обычное построение, автоматическая подготовка/кэширование используемых структур.
- Prepared Queries: явная подготовка программистом, затем повторное выполнение с разными параметрами.
- Кэш планов/подготовленной работы, **не** кэш результатов запроса.
- Не путать библиотечный Prepare с серверным SQL PREPARE без точной проверки реализации.
- Объяснить границы применимости и время подготовки; избегать обещаний «всегда быстрее».

### 7. Цена решений и компромиссы
**Задача:** честно назвать границы архитектуры.
- Нет change tracking и кэша результатов — сознательный выбор в пользу простоты контроля накладных расходов, но с потерей определённых удобств.
- Сложность трансляции C#-выражений: не каждое выражение обязательно имеет допустимый SQL-эквивалент.
- Кросс-СУБД поддержка требует явных диалектных решений; переносимость зависит от поддерживаемого подмножества возможностей.
- Краткая итоговая схема, показывающая как совместно работают описание, подготовка, SQL и маппинг.
