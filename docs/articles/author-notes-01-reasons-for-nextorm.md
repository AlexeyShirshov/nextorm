# Почему не продолжили WORM: тезисы автора

> Источник мотивации: устное объяснение автора от 27.10.2026. Это авторские воспоминания, а не выводы из Git-истории. Только тезисы; прозу для публикации пишет автор.

## Преемственность WORM → Nextorm — уточнение автора

- **Ключевая авторская формулировка (передача смысла, не цитата):** Nextorm — по существу новая реализация WORM на современном технологическом стеке, а не отказ от его базовой концепции.
- **По словам автора:** основные концепции, подходы и приёмы проектирования ORM в целом сохранились; на данный момент автор не перечисляет их по отдельности.
- **Что изменилось:** кодовая база и язык (VB.NET → C#), технологическая платформа (.NET Framework → .NET Core / современный .NET), внутренние способы реализации.
- **Основной названный автором пересмотр:** вместо стремления кэшировать практически всё, включая результаты запросов, Nextorm кэширует только планы запросов; проблемы WORM с инвалидированием, weak references, памятью и аллокациями подтверждены воспоминаниями автора.
- **Отдельная ранее подтверждённая граница функциональности:** в Nextorm нет change tracking, который существовал в WORM. Формулировка «почти всё сохранил» относится к **базовым идеям и приёмам**, а не к буквальному сохранению всех возможностей и подсистем.
- **Проверить по коду:** формирование модели запроса, генерацию SQL, отображение результатов, SQL-диалекты, типизацию запросов и их подготовку — сопоставить по отдельности в обеих кодовых базах.
- **Важно:** не утверждать без проверки, что исходники буквально перенесены или API сохранился один к одному.
- **Редакционное следствие:** прежний тезис «Nextorm не попытка повторить WORM, а полное переосмысление ответственности ORM» **слишком категоричен**. Правильнее показать преемственность ядра идей и точечные, но существенные архитектурные упрощения.

## Центральная преемственность: объект-команда запроса (устное уточнение 27.10.2026)

- Автор вспомнил, что **основой WORM уже был объект со всеми аспектами запроса** (SELECT, WHERE, ORDER BY, GROUP BY и др.). Точное имя в коде — [`QueryCmd`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/obm/QueryCmd/QueryCmd.vb#L18-L25); свойства [`FromClause` и `SelectClause`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/obm/QueryCmd/QueryCmd.vb#L2570-L2589).
- **LINQ-провайдер добавлен к этой уже существовавшей системе:** он переводил `System.Linq.Expressions` в внутренний `QueryCmd`/фильтры; SQL затем строился по внутренней модели ([`WormLinqProvider`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/net3.5/linqprovider/Provider.vb#L69-L75), [`QueryVisitor.VisitMethodCall`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/net3.5/linqprovider/Provider.vb#L1017-L1060)).
- **В Nextorm центральный объект сохранился как концепция, здесь уже буквально называется `QueryCommand`:** содержит условия, группировку, сортировку, проекции и другие части запроса как лямбды/другие объекты ([`QueryCommand.cs`](https://github.com/AlexeyShirshov/nextorm/blob/main/src/nextorm.core/Query/QueryCommand.cs#L65-L86), [`EntityBuilder.SelectCore`](https://github.com/AlexeyShirshov/nextorm/blob/main/src/nextorm.core/Builders/EntityBuilder.cs#L343-L371)).
- **Архитектурная эволюция:** в Nextorm `Expression<Func<...>>` являются нативным описанием частей `QueryCommand`, а не только входом отдельного LINQ-провайдера; поддержка `IQueryable`/обычного LINQ-провайдера — другая ответственность, её **не приписывать Nextorm** только по факту работы с деревьями выражений.
- **Мотивация автора, уточнение:** сохранённый объектный граф запроса + нативная поддержка expression trees. **Компиляцию выражений автор изначально связывал именно с ускорением маппинга результатов**, а не со всем конвейером запросов. Это не означает компиляцию SQL-предикатов в исполняемый .NET-код.
- **Уточнение по фактическому коду:** SQL всё ещё строится обходом деревьев (`BaseExpressionVisitor`, `PredicateTranslator`, `SqlBuilder`); [`RowMapperFactory`](https://github.com/AlexeyShirshov/nextorm/blob/main/src/nextorm.core/DataContext/RowMapperFactory.cs#L339-L366) компилирует отдельное выражение `IDataRecord → TResult` для быстрого отображения строки. Не смешивать **трансляцию Expression в SQL** с **компиляцией Expression в исполняемый делегат**.
- **Редакционный вывод:** не описывать Nextorm как отказ от промежуточного `QueryCommand`. Ключевая сквозная идея — **структурный объект-команда между пользовательским API и SQL**; отличается способ наполнения объекта и обработки его выражений.

## Почему QueryCommand и выражения C# оказались удачным сочетанием — слова автора (27.10.2026)

- **Единый объект запроса:** хранить в одном `QueryCommand` все аспекты формирования SQL (`WHERE`, `ORDER BY`, `GROUP BY` и др.) удобно с архитектурной точки зрения. Автор считает это проверенным принципом, унаследованным от WORM.
- **Нативная работа с expression trees:** описывать части запроса через выражения C# удобнее для прикладного программиста, чем вручную собирать собственную модель условий. Это сознательный выбор современного API при сохранении объекта-команды.
- **Авторская цель компиляции (дополнительное уточнение 27.10.2026):** речь **только об ускорении маппинга результатов** за счёт компилируемых делегатов. Другие потенциальные применения автор пока не определял и не берётся их перечислить. Технические опоры: [`RowMapperFactory` строит делегат материализации и вызывает `Compile()`](https://github.com/AlexeyShirshov/nextorm/blob/main/src/nextorm.core/DataContext/RowMapperFactory.cs#L339-L366), [`MapperCache` переиспользует делегат](https://github.com/AlexeyShirshov/nextorm/blob/main/src/nextorm.core/DataContext/RowMapperFactory.cs#L210-L224).
- **Отдельный факт текущей реализации, не смешивать с мотивацией автора:** [`ParamRefreshRecipe.CompileWriter`](https://github.com/AlexeyShirshov/nextorm/blob/main/src/nextorm.core/DataContext/Cache/ParamRefreshRecipe.cs#L413-L428) компилирует обновление параметра. Это **не доказательство**, что компиляция параметров была исходной целью.
- **Техническая граница:** `Expression.Compile()` создаёт исполняемый делегат .NET (обычно через динамически сгенерированный IL и JIT-компиляцию), **не превращает дерево выражения в SQL**. SQL создаётся при обходе дерева специальными трансляторами; его затем выполняет СУБД. Не писать, будто произвольный предикат `WHERE` компилируется в машинный код и исполняется внутри БД.
- **Синтез:** важен не отказ от старой архитектуры, а сочетание **проверенной модели `QueryCmd`/`QueryCommand`** и **типизированных/компилируемых выражений C#**. Разбор конкретных компилируемых этапов можно вынести в отдельную техническую статью.

## Производительность — преемственная цель (уточнение автора, 27.10.2026)

- **Авторская мотивация:** высокая производительность была одной из целей ещё при разработке WORM; именно стремление к скорости побуждало к широкому кэшированию.
- **Преемственность:** в Nextorm задача высокой производительности не возникла позднее, а **перешла из WORM** и стала одной из ключевых целей.
- **Иерархия целей производительности (ответ автора 27.10.2026):**
  - **Главное — минимальное время выполнения запроса**; ориентир при сравнении — **Dapper**.
  - **Аллокации тоже важны**, но вторичны по отношению ко времени; цель — не допускать излишних аллокаций и держать их **приблизительно на уровне linq2db**.
  - Dapper и linq2db используются как **разные ориентиры для разных метрик**; это цели автора, а не утверждение о достигнутом результате во всех сценариях.
- **Конкурентная стратегия по словам автора:** высокая скорость рассматривается как преимущество Nextorm при сравнении с более зрелыми библиотеками, в частности **linq2db**; по времени ориентир — **Dapper**.
- **Отличие стратегии реализации:** в WORM скорость достигалась, в том числе, кэшированием результатов с высокой ценой по памяти и сложности; в Nextorm — ставка на подготовку/повторное использование планов и эффективное преобразование результатов, без кэша результатов.
- **Исторические формулировки README:** [20.09.2023](https://github.com/AlexeyShirshov/nextorm/blob/7ee4651280ed2f902297e14bf562d89cea281a30/readme.md) акцентирует отказ от ручного SQL и **не заявляет** скорость Dapper целевым критерием; [09.12.2023](https://github.com/AlexeyShirshov/nextorm/blob/40c792cb09ffb6713da60d3c19f01384d76b2de2/readme.md) явно называет производительность уровня Dapper. **Вывод:** изменилась публичная формулировка, а не момент возникновения стремления к высокой скорости.
- **Граница доказательств:** намерение конкурировать с linq2db — заявление о цели позиционирования, **не подтверждение абсолютного превосходства**. Для утверждений об измерениях нужны воспроизводимые сценарии, указание версии библиотеки/провайдера, подготовленного или обычного пути и затрат памяти — [текущие сравнения и бенчмарки](https://github.com/AlexeyShirshov/nextorm/blob/main/docs/ru/comparisons/benchmarks.md).
- **Ответ на вопрос о метриках получен:** приоритет № 1 — время выполнения (ориентир Dapper); вторичный приоритет — аллокации (ориентир linq2db). При сравнении фиксировать одинаковые сценарии, провайдер и режим подготовки; показатели конкретного бенчмарка не подменять целевыми.

## Причины начать новую библиотеку

- **Накопленный legacy-код в WORM / OML:**
  - Большой объём кода, написанного за годы разработки.
  - Сложность сопровождения и дальнейшего развития.
  - Продолжать поддержку прежней кодовой базы было трудно; новая реализация на современном стеке сохранила основные концепции, но не старую техническую основу.
- **Выбор языка:**
  - WORM реализован главным образом на **Visual Basic .NET**.
  - К моменту работы над Nextorm VB.NET стал, по оценке автора, нишевым по сравнению с **C#**.
  - C# был выбран для новой реализации как более активно развивавшийся язык с более широким применением в .NET.
  - Не превращать авторскую оценку положения языков в неподтверждённое официальное заявление Microsoft.
- **Переход на .NET Core как технологический повод для новой реализации:**
  - Автор вспоминает исходную разработку на .NET Framework 2.0, затем переход на 3.0 и 3.5; проект надолго остался на старом стеке.
  - Появление .NET Core стало дополнительным аргументом в пользу переписывания с нуля.
  - **Проверка кода:** поздний основной проект WORM [`obm/Worm.Orm.vbproj`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/obm/Worm.Orm.vbproj#L23-L30) указывает `TargetFrameworkVersion=v4.0`; [`Worm.Linq.vbproj`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/net3.5/linqprovider/Worm.Linq.vbproj#L11-L18) указывает `v3.5`. Поэтому «до 4.0 так и не обновлял» не использовать как факт.
- **Пересмотр идеи «кэшировать всё»:**
  - Изначальная установка WORM: максимально широкое кэширование, в том числе параметров/подготовки запросов и **результатов выполнения запросов**.
  - Накопленный опыт: подробное кэширование породило множество проблем:
    - поддержка кэша и сложная инвалидация;
    - необходимость работать с weak references;
    - большой расход памяти и множество аллокаций.
  - Со слов автора: библиотека была быстрой, но высокая скорость достигалась существенной ценой по памяти и аллокациям; численных замеров здесь нет.
  - Решение при создании Nextorm: отказаться от кэширования результатов; сохранить **кэширование планов запросов**.
  - Ключевое различие: **повторное использование плана ≠ повторное использование полученных строк данных**.

## Отказ от change tracking — позиция автора

- **Источник решения:** собственный многолетний опыт проектирования ORM (WORM), а также критическое отношение к модели change tracking в EF Core.
- **Предпочтительная модель использования:** разработчик, понимающий SQL и реляционные СУБД, непосредственно и явно управляет чтением и изменением данных.
- **Нежелательные издержки по оценке автора:**
  - хранение дополнительного состояния сущностей и исходных значений/«теневых копий»;
  - удержание и отслеживание графа объектов в памяти сервиса;
  - усложнение жизненного цикла объектов и правил сохранения;
  - рост потребления памяти и накладных расходов при выполнении;
  - ошибки и затруднения у пользователей, не знакомых с семантикой tracking.
- **Архитектурный вывод:** в Nextorm не вводить автоматическое отслеживание изменений и не возлагать на библиотеку управление графом изменяемых сущностей; вместо этого — явные операции с данными.
- **Статус:** это **субъективная инженерная оценка автора**, а не универсальный вывод «tracking всегда бесполезен» и не измеренное сравнение с EF Core.
- **Точность формулировок:** «теневые копии» — объяснение автором накладных расходов отслеживания; не утверждать, будто EF Core всегда создаёт полные копии сущностей или что все режимы EF Core одинаково отслеживают изменения.
- **Для будущей статьи:** обсуждать **компромисс между удобством автоматического состояния и явным контролем, сложностью и накладными расходами**; уточнять сценарии, когда tracking действительно полезен.

## Польза change tracking и причины выбора явного DML — уточнение автора

- **Не отвергать change tracking целиком:**
  - мощный и удобный механизм, особенно для **quick start**;
  - позволяет работать привычными концепциями ООП — классами, объектами, свойствами, методами;
  - пользователь может на старте не разбираться в SQL, хранении данных и конкретных запросах, генерируемых ORM.
- **Наблюдение автора об эволюции разработчика:**
  - по мере роста опыта разработчик неизбежно сталкивается с SQL и поведением СУБД;
  - может перейти от редактирования отслеживаемых объектов к явным `INSERT`, `UPDATE`, `DELETE`;
  - **не обобщать** этот путь как обязательный для всех разработчиков и проектов: это описание опыта и позиции автора.
- **Сопоставление способов изменения данных:**
  - tracking-путь: создать/получить объект → изменить свойства → отследить состояние → `SaveChanges` → SQL;
  - явный DML-путь: непосредственно сформировать операцию изменения нужных строк/значений;
  - в массовых изменениях явный DML может обходиться без загрузки и материализации множества сущностей;
  - сравнивать расходы по конкретным сценариям: не заявлять, что tracking всегда медленнее.
- **Уточнение по EF Core из официальной документации (проверено 27.10.2026):**
  - [EF Core 7](https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-7.0/whatsnew) добавил `ExecuteUpdate` и `ExecuteDelete`: операции над множеством строк без загрузки объектов и без change tracking.
  - **Точная дата:** [8 ноября 2022 года — официальный анонс EF Core 7](https://devblogs.microsoft.com/dotnet/announcing-ef7/). Это более чем через 15 лет после [раннего зафиксированного коммита WORM от 23 мая 2007 года](https://github.com/AlexeyShirshov/oml/commit/2371f4bab9ce746717ae21d0054bc51e7c0ff93b).
  - **Историческая граница:** до EF Core 7 прямой `UPDATE`/`DELETE` можно было выполнять через сырой SQL; новыми стали именно LINQ-методы `ExecuteUpdate`/`ExecuteDelete`, позволяющие обойти загрузку сущностей и change tracking.
  - [Документация о сохранении данных](https://learn.microsoft.com/en-us/ef/core/saving/) отдельно сравнивает эти операции с `SaveChanges` и описывает выигрыш для массовых изменений.
  - **Уточнение авторского воспоминания:** публично документированного симметричного `ExecuteInsert` в стандартном API EF Core 10 нет; [вставка](https://learn.microsoft.com/en-us/ef/core/saving/basic) обычно выполняется через `Add`/`SaveChanges`, а прямой SQL доступен через [`ExecuteSql`](https://learn.microsoft.com/en-us/ef/core/performance/efficient-updating).
  - Наличие `ExecuteUpdate`/`ExecuteDelete` показывает востребованность явного DML в EF Core, но **само по себе не доказывает** заимствование идей из WORM/Nextorm.
- **Для будущего аргумента:**
  - сформулировать выбор не как «ORM с tracking плох», а как «для выбранной аудитории и задач Nextorm явное управление SQL-операциями важнее автоматизации состояний объектов»;
  - честно обозначить сценарии, где tracking полезен: быстрая разработка, неизвестный заранее набор изменений, редактирование сложных графов объектов.

- **WORM — широкое тестирование кэша:** [`Cache.vb`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/TestProject1/Query/Cache.vb), [`ImmCache.vb`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/TestProject1/Query/ImmCache.vb), [`SmartCache.vb`](https://github.com/AlexeyShirshov/oml/blob/Worm2010/TestProject1/Query/SmartCache.vb).
- **Nextorm — явно задокументированный механизм:** [описание конвейера и кэша планов](https://github.com/AlexeyShirshov/nextorm/blob/main/docs/ru/engine/index.md), [`Prepare()` и повторное использование](https://github.com/AlexeyShirshov/nextorm/blob/main/docs/ru/engine/03-plan-cache-and-reuse.md).

## Что ещё нужно уточнить у автора

- **Уже подтверждено автором:** сложность сопровождения/инвалидации кэша, weak references, повышенное потребление памяти и большое число аллокаций.
- **Требует уточнения:** были ли проблемы согласованности между процессами и транзакциями? Можно ли найти конкретный инцидент или измерения памяти?
- **Ответ автора:** tracking добавляет стоимость памяти, исполнения и сложности для целевого пользователя Nextorm. Осталось уточнить конкретные случаи из WORM и возможные контрпримеры, где tracking приносил пользу.
- **Ответ автора:** практически все базовые концепции и приёмы WORM были сохранены. Следующий шаг — составить проверяемую по коду карту соответствий; не требовать от автора немедленно перечислять детали по памяти.
- Какой конкретный практический случай лучше всего иллюстрирует переход от кэша результатов к кэшу планов?
