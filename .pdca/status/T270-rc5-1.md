## Measurement method
- **Metrics & units:**
  1. **Allocation ratio (primary):** `Allocated(Nextorm_Funnel) / Allocated(Linq2Db_Funnel)` (dimensionless ratio of BDN `[MemoryDiagnoser]` managed bytes/KB allocated per single operation).
  2. **Mean execution time:** `Mean(Nextorm_Funnel)` in milliseconds (`ms`) per single operation.
  3. **Result cardinality & content:** Exact 3-row funnel output over `datasets.hits_v1`.
  4. **Compiler diagnostics:** Count of warnings (`W`) and errors (`E`) on `examples/nextorm.examples.clickhouse.analytics` (`-c Release`).
- **Denominator:** Single benchmark invocation of `Nextorm_Funnel` (build + execute + materialise 3 rows) divided by single benchmark invocation of `Linq2Db_Funnel` in the same paired BenchmarkDotNet run (`Operation = 1`).
- **Inclusion / exclusion filters:**
  - Included: Client-side .NET managed heap allocations reported by BenchmarkDotNet `[MemoryDiagnoser]` for the `*Funnel*` benchmark arms (`Nextorm_Funnel`, `Linq2Db_Funnel`, plus optional LINQ-vs-LINQ control if added).
  - Excluded: ClickHouse server-side memory, container startup/warmup outside the measured benchmark iterations, unrelated benchmarks.
- **Comparability conditions:**
  - Release build (`-c Release`), BenchmarkDotNet `ShortRun` + `InProcessEmitToolchain` + `[MemoryDiagnoser]`.
  - Live ClickHouse container over warm `datasets.hits_v1` volume via `DOCKER_HOST=unix:///mnt/wsl/podman-sockets/podman-machine-default/podman-user.sock`.
  - Strictly one benchmark process at a time (no concurrent container/CPU contention).
  - At least two independent runs before and at least two independent runs after; ratio evaluated on paired runs, and mean time evaluated against `189.7 ms` accounting for the standing `<~20 %` `ShortRun` noise floor.
  - If the shared query path (`src/nextorm.core/**`) is modified, the 7-case project acceptance benchmark (`benchmarks/nextorm.benchmark` with `--anyCategories=acceptance`) is also comparable in Release mode on quiescent CPU.
- **Thresholds & provenance:**
