## 2. Goal and non-goals

Add source-less counterparts of **all five existing predicate-based `JoinInto` shapes**. Each must behave like the corresponding explicit-source call supplied with a bare `_dataProvider.From<TChild>()`, except that a null predicate is rejected before source resolution. Verify compiler binding, mapping/error parity, forwarding, generated SQL, live materialization and bilingual documentation.

**Non-goals**

- No synthesized relationship predicate or relationship-key discovery: that belongs to T331.
- No fix for dropped child-source filters: that belongs to T309.
- No overloads on `JoinedEntityBuilder`.
- No changes to existing signatures, mapping precedence, supported join kinds, materialization or provider capabilities.
- No examples, unrelated refactoring, package updates or generated documentation edits.
- No retrospective repository audit as an acceptance gate.

**T331 decision:** T330 ships independently. Explicit predicates support custom ON conditions and do not require declared relationship metadata. T331 adds metadata-driven forms; it does not subsume this API. Do not implement any of its synthesized-ON work.

**T309 decision:** retain the current queue position. Proceed with an explicit **bare-source/no-child-filter equivalence** contract. Delegation preserves the explicit API's behavior both before and after T309; it does not implement a second interpretation of child sources. Documentation must direct callers needing a child filter to the explicit-source API and describe its availability accurately at execution time. Do not make dropped filters an expected result or a passing regression oracle.

## 5. Minimal solution and alternatives

**Essence:** remove the mandatory source argument for the common bare-source case.

**Constraints:** retain existing overloads, resolution semantics, validation contracts, constraints and provider behavior; reject null predicates before source construction.

**Choice:** add all five counterparts. Each performs the necessary early predicate validation, then delegates through `_dataProvider.From<TChild>()` to the corresponding existing overload. Preserve existing generic parameters, including any key-type parameters. Do not introduce a shared resolver.

| Approach | Benefit | Cost / risk | Decision |
|---|---|---|---|
| Five thin validating wrappers | Small change; explicit equivalence; no new provider implementation | Repeated small predicate guard; compiler-binding verification required | **Chosen** |
| Shared validation/source-construction seam | Removes a little repetition | Broadens internal change and may reorder validation or resolution | Reject unless D1 demonstrates a concrete necessity; return to PLAN before widening |
| Fold into T331 | Fewer separately tracked changes | Loses predicate-only usage; couples unrelated ON synthesis | Reject |

Also rejected:

- Optional `child` parameter: cannot provide the requested leading-argument omission without a different overload shape and introduces binding risks.
- Changing existing signatures: breaks callers.
- New resolver or fallback table: violates mapping and failure parity.
- Shipping only collection forms: leaves an avoidable symmetry gap; all five share the same bounded delegation approach.
