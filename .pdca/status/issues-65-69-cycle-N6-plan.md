## Архитектурное решение по блокеру `AcrossShards` (фиксируется для Шага 2, поставка в `N=7`)
- **Выбранный вариант v1:** клиентский fan-out поверх по-шардовых команд (`EntityBuilder<T>.WithScope(shardScope)` на каждый целевой шард из кольца с последовательным/асинхронным объединением потоков результатов), а не single-`EntityBuilder` и не SQL `UNION ALL`.
- **Границы v1:** поддерживает фильтрацию `Where`, проекцию `Select`, материализацию `ToList`/`ToArray`/`AsAsyncEnumerable` по всем или выбранным шардам; **явно не поддерживает** глобальные кросс-шардовые `ORDER BY`, `LIMIT`/`OFFSET`, `DISTINCT`, `GROUP BY` и агрегаты (при попытке — детерминированный `NotSupportedException`). В `N=6` закладывается совместимость API (`WithShardKey`), сам `AcrossShards` сдаётся в `N=7` под критерием `AC-69-FANOUT` на whole-step CHECK.

## Критерии приёмки цикла `N=6` (и привязка к требованиям #69)
- **`AC-69-RING` (Consistent hashing & детерминизм):** кольцо консистентного хеширования с виртуальными узлами на базе внутрирепозиторного детерминированного `XxHash32` (`Expressions/XxHash32.cs`) отображает значения `ShardKey` (`int`, `long`, `string`, `Guid`) в один и тот же `MappingScope` между запусками процесса; добавление/удаление одного шарда из $K$ переназначает только долю ключей $\approx 1/K$ (не более $2/K$ на выборке $\ge 1\,000$ ключей), не вызывая полного перехеширования.
- **`AC-69-META` (Изоляция таблиц/схем и защита от инъекций):** провайдер/декоратор метаданных шардирования отображает `(Type, MappingScope)` в физическое имя таблицы/схемы шарда; идентификаторы шардов валидируются при регистрации, а значения `ShardKey` никогда не интерполируются в SQL-идентификаторы (негативное условие: невалидный идентификатор шарда отвергается при конфигурации).
- **`AC-69-ROUTE-DML` (Точечная маршрутизация записи):** `Insert`, `Update`, `Delete` по экземпляру/набору экземпляров и `WithShardKey(key)` разрешают `MappingScope` целевого шарда из значения shard key сущности; пакетный `InsertBuilder.Values(entities)` с сущностями разных шардов без явного единого шарда завершается детерминированной ошибкой, не записывая строки в неверный шард и не меняя sticky-состояние общих команд.
- **`AC-69-ROUTE-READ` (Точечная маршрутизация чтения и изоляция кэша):** запрос к шардированной сущности с равенством по ключу шарда (`Where(e => e.ShardKey == val)`) или явным `WithShardKey(val)` / `WithScope(scope)` автоматически направляется в `MappingScope` соответствующего шарда, генерирует SQL с таблицей/схемой и префиксом параметров этого шарда и изолирует записи в `_fromCache`/plan cache по `(Type, MappingScope)`.
- **`AC-69-FAILFAST` (Запрет скрытого full-scan):** запрос или мутация (`Select`, `Update`, `Delete`) шардированной сущности без извлекаемого равенства по `ShardKey` и без явного `WithShardKey`/`WithScope` (а в `N=7` — или `AcrossShards`) немедленно выбрасывает исключение до выполнения SQL (негативное условие: молчаливый запрос к `MappingScope.Default` или обход всех шардов по умолчанию запрещён).
- **`AC-69-PARITY` (Паритет без шардирования):** при неактивном шардировании (или для нешардированных сущностей в том же `DataContext`) генерируемый SQL, имена параметров и ключи кэша планов побайтово/структурно идентичны поведению до изменений.
- **`AC-69-HYGIENE` (Сборка, структура папок, Public API):** решение собирается с `0` предупреждений и `0` ошибок (`TreatWarningsAsErrors=true`); в каждой затронутой папке `src/**` и `tests/**` $\le 10$ непосредственных файлов `.cs` (новые типы шардирования выделяются в отдельную подпапку, например `src/nextorm.core/Sharding/`); все новые публичные API внесены в `src/nextorm.core/PublicAPI.Unshipped.txt`; окончания строк CRLF.
- *(Примечание о полноте Шага 2:* критерии Фазы 3 — мульти-шардовый сбор `AC-69-FANOUT`, живые СУБД `AC-69-LIVE`, документация EN+RU `AC-69-DOCS` и бенчмарк `AC-69-BENCH` — входят в обязательный контракт `N=7` и финальный whole-step CHECK #69; ни одна фаза не переносится за пределы milestone 1.0.10).*

## Метод измерения (для численных и гигиенических порогов)
- **Равномерность/монотонность кольца (`AC-69-RING`):** метрика — доля изменивших шард ключей $\Delta = \text{moved}/M$ на фиксированном детерминированном наборе $M \ge 1\,000$ ключей при переходе $K \to K+1$ шардов ($K \ge 3$); порог: $\Delta \le 2/(K+1)$ и $100\%$ детерминизм повторного вызова.
- **Гигиена сборки и папок (`AC-69-HYGIENE`):** метрика — число диагностик компилятора (порог `0 errors, 0 warnings`) и число прямых файлов `*.cs` на каталог в затронутых путях (порог $\le 10$).
- **Бенчмарк query-path (на whole-step CHECK в `N=7`):** BenchmarkDotNet (`benchmarks/nextorm.benchmark`, `-c Release`), сравнение `Where` точечного чтения без шардирования и с шардированием на одной машине/TFM `net11.0` для подтверждения отсутствия деградации нешардированного пути.
- Согласно `references/plan.md` (§Plan hygiene, §Evidence boundary), PLAN фиксирует стабильные ID критериев `AC-69-*` и метод измерения, но не замораживает строки манифеста или команды до DO; на выходе DO/CHECK каждый `AC-69-*` обязан иметь закрытую запись свидетельства (без `open`).
