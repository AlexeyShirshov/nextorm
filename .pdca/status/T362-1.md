### The decision being implemented (option A)
#338 says the reset half of the T328 retry scope is **BLOCKED-by-driver**: "the driver exposes no typed reset signal". Today's recon shows that framing is **only half true**, and the fix is to split the obligation:

- The **post-partial-response RST** surfaces as a **bare `System.Net.Http.HttpIOException`**, and `HttpIOException` **does carry a typed signal from .NET itself**: `HttpRequestError` (`ResponseEnded` for a prematurely ended response). Evidence in-repo: `tests/nextorm.core.tests/ClickHouseRetry/ClickHouseTransientClassifierTests.cs:110` already constructs exactly `new HttpIOException(HttpRequestError.ResponseEnded, "The response ended prematurely.")` — and pins it as **fail-closed**. So the typed signal exists one layer below the driver; we do not need to wait for it.
- The **pre-response RST** surfaces as `ClickHouseServerException` with `ErrorCode = -1` and no inner chain, which is genuinely indistinguishable from a genuine server error → **stays fail-closed**.

So the scope is: **retry the post-response reset, keep the pre-response reset closed, and prove both empirically.**

### What to change

### The probe is the important part
Today's test *constructs* the exception by hand, which proves only that the classifier agrees with a literal — not that the classifier matches what the driver actually throws. Build a **controlled reset** and observe the real shape:

- A local `TcpListener` that accepts a connection, reads the request line/headers, then:
  - **case A (post-response)**: writes a valid HTTP/1.1 response head plus a **partial** body (e.g. chunked with one chunk then truncation), then sends a real RST — `socket.LingerState = new LingerOption(true, 0)` before `Close()` (or `SO_LINGER {on,0}`);
  - **case B (pre-response)**: reads the request and RSTs **without** writing any response byte.
- Point `ClickHouse.Driver` at `http://127.0.0.1:<port>` and **assert the exception shape it actually produces** in each case (type and, for `HttpIOException`/`HttpRequestException`, the `HttpRequestError` value). That assertion is the deliverable: it either confirms the split (A typed, B not) or refutes it — in which case say so and adjust, because the whole option rests on it.
- Then wire the retrier end-to-end over a listener that **RSTs on attempt 1 and serves a complete response on attempt 2**, and assert the caller gets the complete result with **no duplicated or partial rows** and exactly two attempts.
- Keep the listener deterministic and time-bounded (no `Thread.Sleep` loops; use `Task`/timeouts) so the test cannot hang CI.

### The probe decided the contract — and it decided it *for* option A

Two reset points measured with `ClickHouse.Driver` **1.4.0** over loopback (`rv1/probe-shapes.md`,
`rv1/probe-driver-shapes.log`, probe source `rv1/probe-program.cs.txt`), plus a control:

| Case | Listener behaviour | Observed shape |
|---|---|---|
| A — post-response reset | valid `HTTP/1.1 200` + `Transfer-Encoding: chunked`, **one complete row (99)**, then `LingerState = LingerOption(true, 0)` + close, no terminating chunk | `System.Net.Http.HttpIOException`, `HttpRequestError = ResponseEnded`, **no inner chain** |
| B — pre-response reset | request read, **zero** response bytes, RST | `ClickHouseServerException`, `ErrorCode = -1`, no inner chain |
| Control — genuine 503 | well-formed `HTTP/1.1 503` + `Content-Length: 0`, graceful close | `ClickHouseServerException`, `ErrorCode = -1` — **identical to B** in type, code and message |

Both faults provably reached the listener (`POST /`), so neither is a client-side refusal.

Three consequences, each of which changed the implementation:

1. **The typed signal exists one level below the driver.** #338's premise — "the driver exposes no
   typed reset signal" — is true only for the pre-response case. The post-response reset is typed by
   .NET's own HTTP stack, so option A needed no driver release.
2. **The pre-response half is provably indistinguishable** from a genuine empty-body 503 (same type,
   same `ErrorCode`, same message), so it *stays* fail-closed — not as a conservatism, but because
   nothing on the ADO surface separates it from a real server error.
3. **`ConnectionError` was not the measured value** and is therefore *not* accepted; only
   `ResponseEnded` matches. A wider net would have been a guess wearing the costume of a fix.
4. **The retry obligation is real, not a formality**: in case A the driver had already delivered
   row 99 to the reader when the fault surfaced, so a retrier that reused a buffer would report a
   failed attempt's rows as a fresh result.
