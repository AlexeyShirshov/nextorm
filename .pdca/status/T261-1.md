## Goal

Fix #261 so PostgreSQL crypto functions receive an inline `byte[]` as one `bytea` argument, not concatenated integer literals.

Preserve existing SQL and behavior for captured arrays, `SqlFunctions.Parameter<byte[]>`, columns, nulls, and string arguments. No public API changes, new abstraction, provider-wide literal change, or unrelated collection work.

Tracking: #261 — https://github.com/AlexeyShirshov/nextorm/issues/261 (repo identity from `.git/config:8`).

## Root cause

`ExtendedScalarFunctionTranslator.EmitCrypto` bypasses array-operand handling at `src/nextorm.core/Visitors/ExtendedScalarFunctionTranslator.cs:233-259`. Its non-parameter pass calls `VisitToString` at `:255`.

`BaseExpressionVisitor.VisitToString` at `src/nextorm.core/Visitors/BaseExpressionVisitor.cs:678-683` clones a plain visitor (`:883-892`). BCL array traversal visits each inline byte, and `TryEmitValue` appends primitive values without separators (`:777-813`). The parameter pass registers no whole-array parameter (`:757-771`).

The observed error is therefore an **integer SQL literal**, not an incorrectly typed existing parameter. Existing Npgsql binding already handles captured byte arrays correctly. Live probe on PG 17.11 emitted `select sha256(979899) as "H" from simple_entity where id = 1` → `42883: function sha256(integer) does not exist`; the same defect affects `digest(new byte[]{…},'sha256')` and `sha512(new byte[]{…})`.

## Decision and alternatives

**Essential goal:** lower an inline binary construction as one SQL operand.

**Constraints:** local change; preserve existing SQL paths; do not evaluate row-dependent columns; preserve both translation passes and parameter refresh; no new shared abstraction without a second consumer.

**Chosen minimum:** change `EmitCrypto` locally. For a `byte[]`-typed inline `NewArrayExpression`, use the existing whole-array operand machinery rather than ordinary visitor traversal. Cover both array initialization and array bounds, including `new byte[0]`.

This is deliberately **not** "parameterize every byte-array-typed expression": a bytea column must remain a SQL column. Existing captured, explicit-parameter, constant/null, and column paths remain unchanged unless reconnaissance demonstrates that the existing machinery requires a different integration point; that finding returns to PLAN before broadening the patch.

For the four SHA functions, the eligible position is their sole argument. For `digest`, it is **argument zero of the byte-array overload only**. The algorithm argument and `digest(string,string)` keep current emission.

| Approach | Pros | Cons / cost / risk | Decision |
|---|---|---|---|
| Local typed inline-array handling in `EmitCrypto`, reusing existing operand machinery | Small footprint; existing parameter infrastructure; no new abstraction | Must verify empty arrays and refresh recipes; low implementation cost, medium integration risk | **Choose** |
| Route every crypto argument through general function/array emission | Less special casing | Could change captured parameter names, text/algorithm literals, or column handling | Reject: exceeds minimum and threatens SQL identity |
| Global `TryEmitValue(byte[])` handling | Broad literal coverage | Inline expressions do not necessarily reach it as one constant; affects unrelated consumers | Reject: wrong scope and incomplete root-cause coverage |
| PostgreSQL hex `bytea` literal emission | No parameter refresh for static literals | New escaping/provider-literal path; SQL expansion; duplicate representation policy | Reject: unnecessary second mechanism |
| Change `PostgresDataContext.CreateParam` typing | Central binding location | No parameter exists in the failing path; touches T264/T305 ownership | Reject: wrong layer |
| Shared digest contract with T254 | Superficial naming consistency | CH has a different input/output contract; no second consumer for this abstraction | Reject: violates overlay invariant 1 |

Existing machinery to validate: `SqlOperandTranslator.cs:20-88,181-202` and `InValuesEvaluator.cs:24-50`.
