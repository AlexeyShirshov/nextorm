## Goal
Deliver SQL Server server-side composition over captured INSERT/UPDATE/DELETE/MERGE rows without changing existing public signatures, PostgreSQL SQL, or T301 assignment semantics. Essence: declare a table variable, capture mutation output into it, then execute an ordinary composable query in the same batch. Constraints: extend-only, typed refusals, live SQL Server proof, no context-wide mutable capture/cache state. Optimum: extend `BatchBuilder`, reuse its parameter ownership and result matcher, and suppress the existing automatic table-variable read-back only for the new batch capture step.

## Acceptance criteria (binding)
Goal: decide and implement the SQL Server counterpart of the PostgreSQL data-modifying CTE, or fail closed explicitly.
Authoritative issue acceptance (verbatim, `https://api.github.com/repos/AlexeyShirshov/nextorm/issues/266` — title "SQL Server: composable DML OUTPUT (INSERT/UPDATE/DELETE/MERGE output as a queryable source)", state open, labels ["enhancement"], milestone 1.0.9-rc4, 0 comments):
- The rows a SQL Server `INSERT`/`UPDATE`/`DELETE`/`MERGE` returns can be read as a source of a follow-up query in the same round trip through a supported API (or the capability is rejected with an actionable `NotSupportedException` and the workaround is documented).
- PostgreSQL `MutationCteQuery` behavior is byte-identical.
- Affected integration suites green on SQL Server (real container) and no regression on the other providers.

Chosen batch-scoped typed capture implements issue candidate 1: its "not a composable source" caveat is satisfied by composing the table-variable source through an `EntityBuilder` into the same batch, in a single round trip — not as a standalone composable source; candidates 2/3 remain rejected as already recorded.
- **AC1 → bullet 1:** projection/filter/order/limit/join/aggregate; negative: standalone/cross-batch/unregistered sources receive typed refusal.
- **AC2 → bullets 1+3:** same-batch capture/read-back with independent mutation/query parameters; negative: invalid capture/read-back cases fail closed.
- **AC3 → bullets 1+2+3:** EN/RU docs, matrix and restrictions match implementation; negative: contradictory documentation fails acceptance.
- **AC4 → bullets 2+3:** existing Returning/OutputInto/OutputIntoThenOutput/sync-async behavior and PostgreSQL full-string assertions remain unchanged; negative: any regression fails acceptance.
- **AC5 → bullet 3:** live SQL Server, zero failed/skipped targeted cases; negative: a failed or skipped targeted case fails acceptance.

## Public API decision (extend-only)
Chosen: batch-scoped typed capture on existing `BatchBuilder` (no new public type). Planned signatures:
`public BatchBuilder OutputIntoTableVariable<TEntity,TResult>(InsertReturningBuilder<TEntity,TResult> mutation, string variableName, string columnDefinitions);` plus identical overloads for `UpdateReturningBuilder<TEntity,TResult>`, `DeleteReturningBuilder<TEntity,TResult>`, `MergeReturningBuilder<TEntity,TResult>`; `public EntityBuilder<TResult> FromOutput<TResult>(string variableName);`; `public EntityBuilder<TableAlias> FromOutputTable(string variableName);`. Finish through existing `Query<TResult>(QueryCommand<TResult>)`/`AddQuery<TResult>(QueryCommand<TResult>)`; existing `Execute`/`ExecuteAsync` stay the terminals. No new async method → `Async` suffix rule respected.
| Alternative | Benefits | Cost/risk; decision |
|---|---|---|
| BatchBuilder capture + existing Query/AddQuery | Explicit lifetime; existing parameter prefixes/result sets; no new terminal family | Medium: capture-only rendering, ownership validation, MERGE rendering; **chosen** (issue candidate 1) |
| `ctx.WithOutputInto(...)` scope | Familiar mutation-CTE fluency | High: hides batch lifetime in query execution/planner ownership; rejected (issue candidate 2) |
| Typed refusal + documented workaround | Smallest implementation | Does not deliver composition; rejected as default (issue candidate 3), reconsider only via justified replan |
Single composition seam: `IBatchExecutor.RenderBatch` (`DataContext/Roles/IBatchExecutor.cs:26`), extending its internal step descriptor; reuse OUTPUT rendering and `BatchResultMaterializer<TResult>` (`BatchBuilder.cs:614`). Capture descriptors carry source identity/projection, not assignments. Names accept one documented table-variable identifier with optional leading `@`, normalized once; duplicate names, mismatched typed sources, use-before-capture, context/batch mismatch and zero actual output columns are typed refusals. Column definitions remain trusted caller SQL (documented, not advertised as injection-safe). Unsupported-provider message retains stable `OUTPUT INTO`; ownership/shape messages retain stable `batch output source`; no full-message compatibility promise for new messages; existing mutation-CTE refusal text unchanged.

## Root cause / gap
`MutationCteQuery.cs:153-158` deliberately rejects non-PG — do not weaken. `SqlMutationBuilder.cs:1153-1171` emits an immediate read-back with no composition hook; `OutputIntoBuilder.cs:22` exposes no row terminals; `DataContext.cs:855-859` discards its read-back; `BatchBuilder.cs:136-249` lacks capture steps though it already owns queries/results; `DataContext.cs:1390-1442` owns statement-local `b{i}_` parameter prefixes. MERGE needs a batch-only OUTPUT-INTO rendering route because its fluent public form is absent.
