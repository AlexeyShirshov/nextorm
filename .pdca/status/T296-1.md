## Task and goal
Render syntactic nullable null literals as SQL `IS NULL` / `IS NOT NULL`, consistently across the two translation consumers, without changing parameter semantics or public APIs.

## 1. Goal in essence; what the statement did not say
- Literal shape -> evidence: compiler-produced `Convert(Constant(null, object), int?)`; both consumers currently miss it.
- Projection reachability -> resolved by `.pdca/T296/rv1/inputs/probe-reachability.txt`: SELECT, WHERE, COUNT and derived operands reproduce the defect.
- Captured null versus literal -> evidence: documentation distinguishes them; captured values remain parameters in this cycle.
- `HasValue` support -> evidence: currently unmapped; adding member translation is independent scope, deferred within rc4.
- Public API/capability additions -> unnecessary: six dialects already accept shared `IS [NOT] NULL` syntax.
- In-memory behavior -> unchanged: `InMemoryConditionFactory.cs:46,79` compiles the original predicate and already preserves C# semantics.
- Shared integration fixture contents -> do not assume the existing fixture matches the issue; tests must own an isolated three-row dataset.
- Dirty worktree -> 36 foreign entries exist. Preserve them, including `examples/**`; overlapping task-owned edits require attribution before editing, not automatic replacement.
- No outside blocker is established. Implementation-time uncertainty must return as a targeted evidence request, not an acceptance waiver.

## 2. Acceptance criteria
- AC1: nullable literal `==` emits `IS NULL`; negative: neither `= null` nor a null parameter substitutes for the literal.
- AC2: nullable literal `!=` emits `IS NOT NULL`; negative: neither `!= null` nor `<> null`.
- AC3: live SQLite red<->green: preserved baseline produces `= null` / `[]` and `!= null` / `[]`; fixed code returns sorted `[1]` and `[2,3]` respectively and captures correct SQL.
- AC4: both independent consumers work: WHERE/COUNT and boolean projection; derived operand `(x.Int + 1)` remains intact. Negative: fixing only the WHERE fast path is insufficient.
- AC5: bare null, string null, nullable enum/DateTime, reversed operands, and compiler-produced nullable `default` retain correct null-literal behavior. Negative: non-null constants must not become null predicates.
- AC6: captured null/non-null values remain parameterized; `HasValue`/`!HasValue` retain typed unsupported behavior. Negative: no closure evaluation, silent semantic expansion, or generic exception regression.
- AC7: build succeeds with zero warnings/errors; tests, configured evidence gates and mutation requirements pass. Negative: skips, suppressions or open applicable evidence rows cannot substitute for evidence.
- AC8: EN/RU describe the corrected literal semantics and retained limitations. Negative: neither language promises captured-null or `HasValue` support.

## 3. Root cause and landing sites
- `src/nextorm.core/Visitors/WhereExpressionVisitor.cs:27-42,57-69`: bare-constant probes miss `Convert(Constant(null,...), int?)`, selecting the `= `/`!= ` fast path.
- `src/nextorm.core/Visitors/PredicateTranslator.cs:354-357,368-375`: the independent bare-constant probe misses the same unary node; fallback operators at `:493-494` combine with null emission at `BaseExpressionVisitor.cs:779-780`.
- Fix detection at both probes; keep existing operator emission and operand rendering. Add the shared internal predicate beside `TypeFacts.UnwrapConvert`, `src/nextorm.core/Visitors/TypeFacts.cs:22-25`.
- Do not change `BaseExpressionVisitor.TryEmitValue`, dialect implementations, or expression-node architecture.

## 4. Minimal solution and alternatives
Essence: recognize syntactic null through safe conversion wrappers. Constraints: no evaluation, public API, per-dialect fork, cache mutation, or broad expression rewriting. Optimum: one tiny internal predicate used by two proven consumers.

| Approach | Benefit | Cost / risk | Decision |
|---|---|---|---|
| Shared internal null-literal predicate in `TypeFacts` | Two consumers stay consistent; very small change | Must distinguish safe conversions from executable conversions | Choose |
| Duplicate conversion checks at both sites | Lowest initial wiring cost | Divergence and duplicated edge handling | Reject |
| Globally normalize expressions / add null AST node | Broad future reuse | Much larger semantic footprint; no need for this fix | Reject |
| Evaluate captures or add null-safe equality now | Addresses additional symptoms | Changes parameter/cache semantics; overlaps T288 | Reject |

Planned helper name: `TypeFacts.IsNullLiteral` (planned, not an existing symbol). Recognize null constants behind method-free, null-preserving `Convert`/`ConvertChecked` wrappers only; do not unwrap the rendered operand globally. Reject user-defined conversions and conversion chains requiring a non-nullable value result. Do not evaluate members, calls or closures.
