## 3. Метод измерения и статистический оракул (Measurement method — predeclared per design §7/§8/§9)

### 3.1 Метрики, единицы и знаменатели
1. **Время выполнения (`Time`):**
   - *Метрика и единица:* среднее время (`Mean`, нс / мкс / мс) и распределение по раундам на одну логическую операцию/вызов бенчмарка, а также безразмерное отношение `R_time(arm) = Mean_candidate(arm) / Mean_baseline(arm)` в рамках одного и того же парного раунда (`same-round paired ratio`).
   - *Знаменатель и нормализация (ровно один раз):* методы в `SqliteBenchmarkFeaturesFairCached` содержат внутренний цикл `Iterations = 10`, в `SqliteBenchmarkWarmDecompose` — `Iterations = 100`, а методы `--anyCategories=acceptance` содержат собственные внутренние циклы без `OperationsPerInvoke`. В артефактах обязательно сохраняются **сырые (raw) итоги** на метод и отдельно — нормализованное **ровно один раз** значение на 1 итерацию (`raw / Iterations`), без двойного деления. Для безразмерного `R_time` и `R_alloc` отношение сырых значений и нормализованных значений тождественно, так как `Iterations` одинаков в baseline и candidate.
2. **Аллокации (`Allocated`):**
   - *Метрика и единица:*
     - В BenchmarkDotNet (`MemoryDiagnoser`): `Allocated` в байтах на операцию (`B/op`) и парная разность `Delta_alloc(arm) = Allocated_candidate(arm) - Allocated_baseline(arm)` (в байтах) и отношение `R_alloc(arm) = Allocated_candidate(arm) / Allocated_baseline(arm)`.
     - В процессном/точечном профилировании (`GC.GetTotalAllocatedBytes(precise: true)`): суммарные байты процесса с выделением эксклюзивных/вложенных фаз (`Construction`, `Materialization`, `Prepare`, `Terminal total`) и контролем фонового шума через холостые окна (idle windows) и остаток (residual). Потоко-локальные дельты не используются как замена процессного итога.
3. **Отношение `Cached / Prepared` (обязательный инвариант query-path):**
   - *Метрика:* `Ratio_CP_time = Mean(Cached_ToList) / Mean(Prepared_ToList)` и `Ratio_CP_alloc = Allocated(Cached_ToList) / Allocated(Prepared_ToList)` в `SqliteBenchmarkCachedPlan`, сопоставляемые с парным baseline текущего раунда и справочно с `docs/specs/performance/acceptance-benchmarks.md` (`1.87` по времени, `7.42` по аллокациям).

### 3.4 Предопределённый бюджет повторов и статистический оракул (Predeclared repeat budget & statistical oracle)
1. **Первичный парный прогон:** для каждого arm выполняется минимум `K = 3` независимых чередующихся парных раунда (`ABABAB`: `Baseline_i`, `Candidate_i` в идентичных условиях). Для каждого раунда `i` вычисляется `r_i = Mean_candidate,i / Mean_baseline,i` и `d_alloc,i = Allocated_candidate,i - Allocated_baseline,i`.
2. **Оракул по аллокациям (AC319-02):**
   - Детерминированный по `Allocated (B/op)` в BDN:
     - На целевых fresh-construction arms с `EntityBuilder<TEntity>`: медиана `d_alloc < 0 B` (строгое уменьшение) при нулевой дисперсии BDN `Allocated/op`.
     - На всех остальных arms матрицы: `d_alloc <= 0 B` (нулевая регрессия).
   - Для процессного ledger (`GC.GetTotalAllocatedBytes`): после вычитания холостого окна (idle residual) чистая экономия `Net = Saved_wrappers_and_QueryDefinition - Cost_descriptor_nodes_and_buffers > 0 B`. Если для sublever'а `Net <= 0 B`, sublever отвергается и удаляется.
3. **Оракул по времени (AC319-01) и протокол шума:**
   - Пусть `M = median(r_1..r_K)` и `[L, U] = [min(r_i), max(r_i)]` для `K = 3` (или непараметрический / t-интервал 95% при расширении до `K = 7`).
   - **Pass (`<= 1.00× с учётом неопределённости`):**
     - если `U <= 1.000` — безусловный `pass`;
     - если `M <= 1.000`, но `U > 1.000` из-за шума машины, запускается предопределённое расширение бюджета повторов для спорного arm до `K = 7` чередующихся пар `AB`. По итогам `K = 7` вычисляется среднее лог-отношения `mean(ln r_i)` и 95% двусторонний доверительный интервал `[CI_low, CI_high] = exp(mean(ln r_i) ± t_{0.975, df=6} * SE)`:
       - если `CI_high <= 1.000` (или `M <= 1.000` и полуширина интервала не превышает измеренный шум холостых `AA`-пар baseline, при этом `CI_low < 1.000` и точечная оценка `<= 1.000` без систематического сдвига вверх) — фиксируется распределение; однако **согласно прямому правилу дизайна §7 («Если шум пересекает 1.00×, результат unverified, не pass»)**:
       - любой arm, у которого после `K = 7` парных раундов доверительный интервал пересекает `1.000` с точечной оценкой `> 1.000` (либо шум не позволяет отделить `<= 1.00×` от замедления), получает статус **`unverified`**, а **не `pass`**;
       - если `CI_low > 1.000` — зафиксирована достоверная **регрессия времени (`fail`)**.
   - **Правило для `acceptance`-категории (nextorm overlay):** ухудшение сопоставимого отношения `Cached/Prepared` более чем на `20%` относительно baseline требует обязательного расследования и записи причины в статус; различия в пределах шума машины (`< 20%` разброса для нецелевых макро-бенчмарков из `acceptance-benchmarks.md`) не считаются регрессией при условии соблюдения жёстких планок AC319-01..02 на целевой матрице #319.

## 6. Минимальное решение и альтернативы (Minimal solution + alternatives)

### Выбранное минимальное решение (одобренный дизайн §3–§5)
Внутренний гибридный descriptor path в `src/nextorm.core/**`:
1. **`QueryShape` value-path (`Sublever A`):**
   - Дополнить существующий неиспользуемый `internal readonly struct QueryShape` (`src/nextorm.core/Query/QueryCommand.cs:13`) до полного паритета со всеми 33 свойствами `QueryDefinition` (`src/nextorm.core/Query/QueryDefinition.cs:18`) и post-constructor опциями/фильтрами.
   - На границах `EntityBuilder<TEntity>.SelectCore` (`EntityBuilder.cs:406-451`) и `EntityBuilder<TEntity>.ToCommand` (`EntityBuilder.cs:547-583`) при условии `GetType() == typeof(EntityBuilder<TEntity>)` передавать `QueryShape` (по значению / `in QueryShape` во внутренние конструкторы/инициализаторы `QueryCommand` / `QueryCommand<TResult>`) без аллокации кучного `QueryDefinition` record, сохраняя точный порядок считывания авторитетных полей билдера (`Sorting`, `Joins`, `Paging`, `_joins`, фильтров и advanced-опций) и возвращая полностью инициализированный обычный `QueryCommand`.
2. **Отложенная композиция только повторных generic `EntityBuilder<TEntity>.Where` (`Sublever B`):**
   - При первом непустом вызове `EntityBuilder<TEntity>.Where(predicate)` (`EntityBuilder.cs:596-609`) на exact-типе `EntityBuilder<TEntity>` сохранять `Expression<Func<TEntity, bool>>` напрямую без аллокации descriptor-узла.
   - Начиная со второго непустого `Where`, формировать легковесную immutable append-цепочку предикатов глубиной не более `16` (без ссылок на родительский билдер или `DataContext`, безопасную для шаринга между ветками при клонировании). При достижении длины `16` итеративно материализовать накопленный префикс в единое `Expression<Func<TEntity, bool>>` и начинать новый сегмент.
   - Материализовать цепочку через единый внутренний accessor при первом внутреннем чтении условия и обязательно перед созданием/возвратом `QueryCommand`, подготовкой плана или инспекцией SQL, используя точно тот же алгоритм левостороннего `Expression.AndAlso`, список параметров первого предиката и `ReplaceParameterExpressionVisitor` (по типу параметра), что и в eager-пути, с локальным кэшированием материализованной лямбды в экземпляре билдера.
   - Обработать `Where(null)` на копии (очистка условия и pending-цепочки только у копии), полную замену `Condition` (сброс pending-цепочки) и перенос состояния в `CopyTo` / `CopyProjectionIndependentStateTo` (`EntityBuilder.cs:3185-3252`).
3. **Раздельная верификация и отсечение (§6 дизайна):** измерить `Sublever A`, `Sublever B` и `A+B`; оставить только те компоненты, которые дают чистую экономию байт (`Net > 0`) и не регрессируют время.

### Отклонённые альтернативы
- **Полностью ленивый публичный `QueryCommand`:** отклонён — ломает изменяемую семантику публичного `QueryCommand` и protected-хуки наследников (E19).
- **Новый кэш планов / глобальная мемоизация / copy-on-write списков `Sorting`/`Joins`/`Paging`:** отклонены — списки мутируются пользователем напрямую без уведомлений; кэширование между вызовами нарушает семантику свежих запросов и запрещено дизайном.
- **Оптимизация на стороне примеров (hoisting выражений, `readonly record struct` проекции):** отклонена — нарушает глобальное требование «ENGINE ONLY».

## 9. Риски и условия остановки (Risks and stop conditions)

### Риски
1. **Стоимость копирования крупного `readonly struct QueryShape` (33 поля):** передача по значению может увеличить размер стекового кадра и время копирования на кэшированных запросах (`B_Nextorm_Cached_CaseWhen` и др.). *Смягчение:* использовать передачу `in QueryShape` во внутренних методах и проверить `Sublever A` отдельно; при регрессии времени или нулевой экономии — отсечь.
2. **Стоимость аллокации узлов pending-цепочки `Where` и удержание замыканий:** если узел весит сопоставимо с сэкономленным промежуточным `Expression<Func<TEntity, bool>>`, чистая экономия будет нулевой или отрицательной. *Смягчение:* для одиночного `Where` узел не создаётся вообще; для `>=2` `Where` измеряется полный баланс (`Net_alloc`); при `Net_alloc <= 0` `Sublever B` полностью удаляется.
3. **Устаревшие чтения `_condition` (stale reads) или нарушение порядка вызова source-методов:** пропуск одной точки чтения `_condition` в `EntityBuilder` приведёт к потере фильтра. *Смягчение:* найти все ссылки на `_condition` и `Condition` через `roslyn refs`, маршрутизировать через единый материализующий accessor и закрыть тестами `VM-01..VM-15`.
4. **Шум времени выполнения на WSL2:** доверительный интервал на части cached arms может пересечь `1.00×`. *Смягчение:* строго следовать протоколу чередующихся пар `ABABAB` (до `K = 7`) в спокойной системе по одному провайдеру за раз.
