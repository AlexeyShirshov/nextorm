## Goal (essence)

Make PostgreSQL `interval` materialisation truthful: a calendar month has no lossless `TimeSpan`
representation, so the column-mapper path must reject **any** nonzero month component (positive or
negative) with an actionable error, convert representable zero-month intervals exactly, leave
time-of-day mappings untouched, and stop documenting a 30-day approximation that the driver never
performed.

Non-goals: no months-capable public CLR type, no NodaTime dependency, no scalar/raw-composite/JSON
path redesign (deferred with triggers), no other provider changes.

## Acceptance criteria

| ID | Required behaviour | Negative case |
|---|---|---|
| AC01 | Mapped `make_interval` results with positive **or negative** months throw `InvalidCastException` with an actionable calendar-month explanation | Negative months must not silently disappear |
| AC02 | Runtime month parameters are evaluated from each returned interval value; cached mapper reuse is safe | Cached reuse must not retain a previous zero-month decision |
| AC03 | Zero-month days/microseconds convert exactly with checked arithmetic; nullability and `DefaultOnNull` preserved | Null must not invoke an interval read; overflow must not wrap |
| AC04 | `justify_days`, `justify_hours`, `age` follow the same **result-component** rule | Function-name allowlists must not permit a month-bearing result |
| AC05 | PostgreSQL `time` / existing time-of-day mappings keep the existing accessor and behaviour | A `TimeSpan` target alone must not select `NpgsqlInterval` |
| AC06 | Configured converters keep precedence; range/multirange intact; other providers untouched | Provider override must not intercept an explicit converter |
| AC07 | EN, RU and XML documentation state the rule and the mapper-only scope; the false 30-day claim is removed everywhere | No claim of universal scalar/streaming protection |

P1 by construction: AC01–AC06. P2: AC07 (still required).

## Root cause

1. A PostgreSQL expression can produce an interval carrying calendar months.
2. The projection exposes a `TimeSpan` CLR target with no SQL-type descriptor at mapper build
   (`SelectExpression.Expression` is null for a plain entity column; no `DbType`/`SqlType` member).
3. The reader therefore uses the driver's `TimeSpan` conversion (`SelectExpression.cs:176-201`,
   `RowMapperFactory.cs:118-153`).
4. Pinned Npgsql 10.0.3 (`Directory.Packages.props:31`) checks only `months > 0`: positive months
   throw, **negative months are silently truncated**.
5. Checking the returned `TimeSpan` (or catching its conversion) cannot enforce signed-month safety.
   SQL generation is correct (`ExtendedScalarFunctionTranslator.cs:200-231`).

## Decision and alternatives

**Chosen:** provider-local mapper correction in `PostgresDataContext.MapColumnExpression`
(`src/nextorm.postgres/PostgresDataContext.cs:256-336`) with a helper
`src/nextorm.postgres/PostgresIntervalReader.cs`: per materialised `TimeSpan` value inspect
`reader.GetDataTypeName(index)`; for `interval` read `NpgsqlTypes.NpgsqlInterval`, reject
`Months != 0`, convert zero-month `Days`/`Time` (microseconds) with checked arithmetic; otherwise
keep the existing accessor. Per-column compiled mapper, per-value discriminator.

| Option | Pros | Cons / risk | Verdict |
|---|---|---|---|
| Translation-time rejection of constant months | Smallest change | Misses runtime values, `age`, entity columns; constant/parameter split complicates caching | Rejected |
| **Interval-aware mapper reader (chosen)** | Detects both signs and all interval-producing expressions; provider-local | Per-value `GetDataTypeName` check; bypass paths remain outside | **Chosen** |
| General reader-interception contract | Would cover scalar/raw/JSON | Broad core/provider footprint, compatibility risk | Deferred (trigger: those paths requested) |
| Months-capable public type / NodaTime | Faithful calendar model | New public surface or new dependency; larger blast radius | Not chosen |
