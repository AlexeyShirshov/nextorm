# T288 — `IS [NOT] DISTINCT FROM`

## 1. Goal and what the issue did not say

Implement explicit null-safe comparison:

- `SqlFunctions.Sql.is_distinct_from<T>(T left, T right)`
- `SqlFunctions.Sql.is_not_distinct_from<T>(T left, T right)`

Both return non-nullable `bool`. Preserve ordinary `==` / `!=` SQL semantics.

Tracking: [#288](https://github.com/AlexeyShirshov/nextorm/issues/288). All required functional slices remain in milestone `1.0.9-rc4`.

### Resolved omissions

| Omission | Decision |
|---|---|
| SQL Server version floor | Portable emulation; no SQL Server 2022 dependency. |
| SQLite syntax floor | Use verified `IS` / `IS NOT`. |
| ClickHouse scalar-native availability | Native spellings are unusable on verified 25.8: Code 48. Use emulation. |
| Runtime NULL versus NRT annotations | Runtime NULL safety wins; explicitly reject NRT annotations alone as proof for ordinary-comparison folding (§4). |
| MariaDB shared-suite coverage | Add dedicated live MariaDB tests; do not substitute MySQL execution. |
| Captured NULL parameters | Explicit helpers support them without changing ordinary equality or specializing cached SQL to current values. |
| Dirty-document ownership | Unknown; preserve all foreign hunks and route attribution conflicts to the collection parent. |
| Commit/merge permission | None added by this plan. |

## 4. Minimal solution and alternatives

### Three answers

1. **Essential goal:** explicit two-valued NULL-safe comparison.
2. **Constraints:** unchanged ordinary equality, provider ownership, cache safety, existing Boolean lowering, dirty-document preservation, rc4 completion.
3. **Minimum:** two public helpers, one focused translator, one dialect capability, six provider dispositions, and one shared in-memory equality implementation.

### Public API

Append the two generic helpers inside `SqlFunctions.CommonFunctions`, exposed through `SqlFunctions.Sql`.

- Common generic operand type `T`; nullable value types use nullable `T`.
- Both return `bool`.
- Follow existing helper-body and XML-documentation conventions.
- Literal `null` may require an explicit generic type or cast when C# cannot infer `T`.
- No new implicit cross-type conversion family.

| Alternative | Pros | Cons / cost / risk | Decision |
|---|---|---|---|
| Two explicit sibling helpers | Clear semantics; issue-compatible; easy parity testing | Two dispatch entries | **Chosen** |
| Rewrite `==` / `!=` | No new helper API | Breaks ordinary SQL semantics and T296 boundary | Rejected |
| New public comparison-builder abstraction | Extensible | Unnecessary API/refactor | Rejected |

### Dialect seam

Add a focused null-safe-comparison capability alongside the existing capability interfaces:

- Support flags for distinct and not-distinct independently.
- Native/emulated disposition for each form.
- Dialect-owned rendering for each form.
- Default unsupported behavior; all six supported dialects explicitly opt in.
- MariaDB may inherit MySQL rendering, but its disposition is explicitly tested.

Expose it through the existing `ISqlDialect`/`SqlDialectBase` architecture. Do not add provider-name switches to expression visitors.

| Alternative | Pros | Cons / cost / risk | Decision |
|---|---|---|---|
| Dedicated operator capability using existing capability architecture | Correct ownership; contextual Boolean rendering; explicit flags | Small coordinated core/provider change | **Chosen** |
| Treat syntax as ordinary scalar function via whitelist | Reuses function registration | Operators, complements, and Boolean shaping do not have uniform function syntax | Rejected |
| Provider switches in visitor | Small initial patch | Core/provider coupling | Rejected |
| Native-only implementation | Less code | Omits required providers | Rejected |

### Validation and folding

Validate before simplifying.

1. Unwrap supported conversion wrappers through `TypeFacts.UnwrapConvert`.
2. Accept the same effective CLR operand type after nullable unwrapping, or conversions already accepted by the existing translator.
3. Reject incompatible types with `NotSupportedException` containing exactly:
   **`Null-safe comparison requires compatible operand types.`**
4. Two literal NULLs fold to `true` for not-distinct and `false` for distinct.
5. One literal NULL lowers to `IS NULL` / `IS NOT NULL`.
6. Two statically non-nullable CLR value operands may lower to `=` / `<>` only when the SQL expression path cannot introduce NULL, including outer-join null extension.
7. Do not fold parameter values at planning time.
8. Non-null constant folding uses existing provider-compatible folding rules; do not invent CLR string folding.

### Explicit disposition of the issue’s non-nullable-operands DoD

**Reject the item as written insofar as it treats NRT non-nullable reference annotations alone as proof of runtime/SQL non-nullability.**

An NRT annotation does not prevent `default!`, a NULL supplied through reflection, captured NULLs, or SQL null extension. Lowering such operands to ordinary equality could violate Q02.

Implement conservative non-nullable CLR value folding as above. Keep null-safe rendering for reference operands unless existing SQL metadata independently proves non-nullability. Add tests showing:

- Proven non-nullable value operands produce `=` / `<>`.
- Nullable values do not.
- NRT-annotated reference operands containing NULL remain NULL-safe.
- Null-extended operands do not take the ordinary-comparison fast path.

This is an explicit scope decision recorded for issue #288, not a silent omission or a deferral to another milestone.

### SQL Server NULL-parameter rule

Choose SQL type from metadata, never the current value:

1. Bound column/provider mapping.
2. Otherwise the existing common CLR-type provider mapping.
3. Preserve converter/provider type.
4. Bind/cast NULL operands where the SQL position needs an explicit type.
5. If no mapping exists, reject before execution with:
   **`Null-safe comparison requires a SQL Server type mapping for null operands.`**

Two literal NULLs fold. Two parameters currently containing NULL do not fold.

### In-memory

Use one common implementation:

- Both NULL → equal.
- Exactly one NULL → unequal.
- Otherwise supported CLR equality, using `EqualityComparer<T>.Default`.
- Distinct is the complement.

Rewriter recognition precedes its fallback. Document CLR/database string-collation differences.
