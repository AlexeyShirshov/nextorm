## 1. Goal and acceptance criteria

Goal: the SQLite façade must stop advertising a function the shipped engine does not have, and must fail **before** execution instead of surfacing a server error.

- **AC1 (refusal, positive):** preparing a query that calls `SqlFunctions.Sqlite.soundex(...)` on SQLite throws `NotSupportedException` with the exact message `The SQLite function 'soundex' is not supported by this provider.` for a column argument, a string literal and a typed-null (`string?`) argument.
- **AC1 (negative):** no SQL text is produced and no command reaches the server; in particular the former outcome `SQLite Error 1: 'no such function: soundex'.` can no longer be produced through the ORM path.
- **AC2:** `SqliteFunctionRenderer.Supports("soundex")` is `false`; a direct `Render("soundex", args)` bypass throws the renderer's existing unsupported-function exception; the negative is that no bypass path emits `soundex(...)`.
- **AC3:** two preparations of the **same query instance** reject independently (no first-call-only rejection, no cached successful preparation); the observed command-execution counter stays at its post-setup baseline (zero new executions).
- **AC4 (API isolation):** the public member and signature `SqliteFunctions.soundex(string?)` are unchanged (no removal, no `[Obsolete]` warning — warnings are errors); every other supported SQLite scalar keeps its native form and positive test; foreign-provider rejection of the SQLite façade and the core InMemory behavior remain intact; no UDF registration and no mutation of shared command/cache state.
- **AC5 (docs):** XML doc, EN/RU public docs and the two internal capability inventories consistently describe `soundex` as unsupported on SQLite; the negative is no remaining unqualified "supported on SQLite" claim in those sources.

## 2. Decision

**Chosen: pessimistic refusal (aligns with T280).** Retain `NextORM.Core.SqliteFunctions.soundex(string?)` for source/binary compatibility, remove `"soundex"` from the SQLite advertisement so the existing translation gate fails closed, and keep direct rendering failing. Keeping the member preserves **source/binary** compatibility, not **behavioral** compatibility: the behavioral change is intentional and documented. No API removal, no version/package change, no `[Obsolete]`.

Mechanism: `src/nextorm.sqlite/SqliteFunctionRenderer.cs:14-17` (`SupportedNames`, `"soundex"` at `:17`) → `Supports` `:35` becomes false → `src/nextorm.core/Visitors/SqliteFunctionTranslator.cs:58-59` throws before the sole `Render` call at `:137`; a direct `Render` throws at `SqliteFunctionRenderer.cs:55`.

Rejected alternatives:
- **Managed UDF emulation** (register `soundex` on the connection like `regexp`/the aggregates in `src/nextorm.sqlite/SQLiteFunctions.cs:18-46`, hooked at `SqliteDataContext.cs:45-50`): would make the function work, but introduces a new algorithm/NULL/registration contract, must match SQL Server semantics (`SqlServerDialect.cs:1071`), and is a feature, not a correction of a false advertisement.
- **Conditional/native emission** (emit only if the engine reports `SQLITE_SOUNDEX`): capability would have to be discovered per connection and cached; the shipped engine (`sqlite_version()` 3.53.4, `SQLitePCLRaw.bundle_e_sqlite3` 3.0.5) reports `sqlite_compileoption_used('SQLITE_SOUNDEX')=0`, so the advertised positive is false for the product's own runtime, and a conditional path would reintroduce silent divergence.
- **Silent no-op or NULL substitution** — rejected outright: it is the failure mode the issue reports.

## 3. Root cause and fail-closed point
