## 2. Goal and non-goals

Make the framework static property expression `CultureInfo.InvariantCulture` acceptable to the existing `string.Format` translator wherever its surrounding overload and format are already supported. Verify the result through six provider SQL-generation suites and live execution of every applicable supported provider/form cell, while preserving constant-provider behavior, null-provider behavior, rejection text, dispatch and SQL emission.

**Non-goals:** arbitrary provider-expression evaluation; execution of getters; support for additional cultures, overloads, format strings, providers or SQL functions; public API or capability changes; unrelated translator cleanup; edits under `examples/**`; global package, harness or coverage-policy changes.

## 4. Root cause

Supplied authoritative anchor, to be reverified in D0:

- `src/nextorm.core/Visitors/StringFormatTranslator.cs:184-194`: `RequireInvariantProvider` recognizes a constant carrying `CultureInfo.InvariantCulture`, but not the framework static property's `MemberExpression`.
- The supplied finding states that `Unwrap` removes conversion wrappers only. Its exact definition and call-site anchors were **not supplied**; D0 records them through Roslyn rather than inventing line numbers.
- Consequently, the normal property-expression shape reaches the existing fail-closed exception before otherwise-supported formatting can proceed.

The defect concerns provider-expression recognition, not formatting emission.

## 5. Decision and alternatives

### Minimal solution: three answers

1. **Essence:** admit precisely the canonical framework static property expression.
2. **Constraints:** preserve constant and null arms, exact rejection text, existing conversions, dispatch and emission; never evaluate expressions or invoke provider getters.
3. **Optimum:** add one narrow structural recognition arm in `RequireInvariantProvider`, identifying the static property by its exact framework declaring type and member identity.

Metadata inspection is allowed; obtaining the provider by executing its getter is not.

| Approach | Benefit | Cost / risk | Decision |
|---|---|---|---|
| Narrow structural recognition of the canonical framework property | Meets the owner decision; local change; no user-code execution | Requires explicit negative shape tests | **Chosen** |
| Evaluate provider expressions and compare their values | Accepts many expression shapes | Executes getters/user code, changes accepted surface and failure behavior | Rejected |
| Broader invariant-expression helper or translator refactor | Potential reuse | Enlarges footprint and acceptance surface without necessity | Rejected |

No cleanup is deferred from the required fix. Broader expression support and translator refactoring are deferred until a separately approved requirement explicitly requests them.
