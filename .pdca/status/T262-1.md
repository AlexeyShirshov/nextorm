## Root cause
`ExtendedScalarFunctionTranslator.cs:299-315`, specifically `:314`, calls the args-only dialect overload, bypassing the arg-type-aware PostgreSQL overload at `PostgresDialect.cs:508-511`.
The args-only implementation at `PostgresDialect.cs:497-502` falls through to uncast emission at `SqlDialectBase.cs:646-647`; PostgreSQL has no two-double overload.

## Minimal solution
**Essence:** select PostgreSQL’s native `log(numeric,numeric)` without changing callers.
**Constraints:** preserve public API, operand order, null semantics, one-argument mapping, provider isolation, and predecessor changes.
**Optimum:** add a name-and-arity-specific branch to PostgreSQL’s args-only `MakeMathFunction`; cast both operands to `numeric`, irrespective of inferred CLR/SQL type.

| Alternative | Benefit | Cost/risk | Decision |
|---|---|---|---|
| Native call, casts in args-only PG overload | Correct server overload; one product file | Numeric server arithmetic/materialization must be verified | **Choose** |
| Pass argument types from `EmitMath` | General typed dispatch | Changes shared math dispatch across providers; unnecessary here | Reject |
| `ln(x)/ln(base)` | Avoids two-argument overload | Changes rounding/semantics and hides native function | Reject |
| Change facade to decimal arguments | Matches native input type | Public API/behavior break; changes caller conversions | Reject |
| Version/capability gate | Could reject unsupported capabilities | No evidenced version-specific limitation; does not fix overload selection | Reject |

Keep existing one-argument mapping unchanged. Do not add a decimal overload, scalar-function registration, or capability gate.
