## Root cause, provenance, and uncertainty

- Root cause: ClickHouse `DateTime` is 4-byte seconds (range max 2106-02-07 06:28:15); `addYears` on DateTime goes through `UInt32 execute(...) { static_cast<UInt32>(time_zone.addYears(...)) }` (ClickHouse `src/Functions/FunctionDateOrDateTimeAddInterval.h:662`), so 2023+100y = 2123 wraps by 2^32 s to 1987-04-10 07:17:14 — exactly the issue's observed value. `addYears` on DateTime64 returns DateTime64 (`…AddInterval.h:650`).
- Pinned server 25.8 DateTime64 range is `[1900-01-01, 2299-12-31 23:59:59.99999999]` (`v25.8.33.6-lts` docs; source `DATE_LUT_MIN_YEAR 1900`/`DATE_LUT_MAX_YEAR 2299` in `src/Common/DateLUTImpl.h`, out-of-range clamps to 2299-12-31). Master docs' `0000..9999` wording postdates 25.8 (commit `a2edc94`, 2026-07-15) — NOT applicable.
- Suites are green today because the only live century assertion is `tests/nextorm.integration.tests/Coverage8/Cycle8ClickHouseResidualTests.cs:289,305` (`2000 + 100y = 2100`, inside the 2106 limit).
- Discrepancy recorded: the issue body says the failing case came from `tests/nextorm.integration.tests/ClickHouse/ClickHouseDateAndSessionExecutionTests.cs`, but at HEAD (`15a4d0bc`) that file has no century case (`:91-130` covers year…microseconds + decade only); the new T256 live test is therefore the first committed red case.
- Driver `ClickHouse.Driver` 1.4.0 binds CLR `DateTime` as 4-byte `DateTime`.
- `git status --porcelain` could not be verified by scout (shell denied) — expect foreign `examples/**` modifications.

## Decision and rejected alternatives

- Normalize the operand to `DateTime64(6)` for **year, decade, century** before `addYears`, keeping the existing amount parenthesization: `addYears(toDateTime64(v, 6), n)` / `addYears(toDateTime64(v, 6), (n) * 10)` / `addYears(toDateTime64(v, 6), (n) * 100)`.
- Scale **6**, not 3: preserves DateTime64(3)/(6) and existing DateTimeOffset microseconds; DateTime64(9) is normalized to microseconds (sub-µs discarded — documented).
- Millennium: override ClickHouse capability reporting so `SupportsDateAddField("millennium")` is false and add a defensive `NotSupportedException` naming the pinned-server range limitation. No follow-up unit required — the slice is closed by refusal + tests + docs + roadmap row.
- Decade: in scope through representable results (crossing 2106 up to 2299); results outside 1900–2299 are an explicit documented limitation (no checked arithmetic).
- Result type becomes `DateTime64(6)` for the three affected units; reader precedent (`ClickHouseDataContext.cs:85`, DateTime64 → CLR DateTime) must be verified live for materialization, comparisons/filters and DateTimeOffset inputs. Public API unchanged.
- Constraints: preserve the 3-arg `MakeDateAdd` signature and the 4-arg DTO path, provider capabilities, nullable behavior, and unchanged-unit rendering.

| Alternative | Pros | Cons / cost / risk |
|---|---|---|
| Promote operand to DateTime64(6) for year/decade/century — chosen | Fixes the whole year family through one mechanism; preserves µs | Result type change for three units; reader/materialization must be proven live |
| Century-only promotion | Smallest textual change | Leaves the identical year/decade mechanism broken; rejected |
| Documented millennium clamping | No refusal surface | Returns misleading dates; rejected |
