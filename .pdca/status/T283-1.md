## 2. Goal and acceptance criteria

**Observable goal:** a query using the explicit MySQL marker `json_storage_free` returns the same nullable integer result as independently executed MySQL 8.4 SQL, including JSON-column and SQL-NULL cases. Other providers reject the marker instead of emitting an unsupported or semantically different function.

**Bounded slice:** implement **only `JSON_STORAGE_FREE`**. It exercises the existing scalar-function seam without adding variadic, aggregate, table-valued, cryptographic, or session-dependent APIs. It provides a practical diagnostic for MySQL binary-JSON storage after updates.

This is a slice boundary, **not a claim that residual functions are absent**. Issue #283 remains open for its residual catalogue.

| Requirement | Acceptance | Negative case |
|---|---|---|
| R01 | Exactly one new public marker with the signature in §5 and XML documentation | No accidental additional marker, overload, or `CommonFunctions` addition |
| R02 | MySQL capability accepts and renders `json_storage_free` | Unknown names remain rejected |
| R03 | Exact renderer output and ordinary expression translation are tested | Wrong function name, omitted argument, or extra argument fails |
| R04 | Live MySQL values match an independent raw ADO.NET oracle | Malformed JSON cannot silently produce a successful mapped value |
| R05 | SQL NULL maps to `long?` NULL | NULL is not converted to zero |
| R06 | MariaDB and all other listed providers reject the new marker | No accidental MariaDB inheritance or fallback SQL emission |
| R07 | Existing declared marker coverage and behavior remain intact | A newly unsupported existing marker or exposed-but-unwired marker fails |
| R08 | EN/RU public documentation and roadmap accurately describe the slice | No claim that the whole catalogue is complete; no public link to internal specs |
| R09 | Required builds, scoped unit suites, and the boundary integration run have usable evidence | Missing logs, failed tests, or skipped selected MySQL scenarios do not count as passing evidence |

### Per-function acceptance

All new test symbols and artifacts named below are **planned**, not existing symbols.

| Selected function | Exact renderer invocation and expected SQL fragment | Exact CLR return | Live literal case | NULL case | Negative case |
|---|---|---|---|---|---|
| `JSON_STORAGE_FREE` | `Render("json_storage_free", ["'{\"a\":1}'"])` → `JSON_STORAGE_FREE('{"a":1}')` | `long?` | Raw oracle: `SELECT JSON_STORAGE_FREE('{"a":1}')`; capture the exact integer and compare the translated scalar result to it | Raw oracle: `SELECT JSON_STORAGE_FREE(NULL)`; proposed contract is SQL NULL and mapped `null`, verified before implementation proceeds | `'{bad'`: raw oracle and translated query must both fail with corresponding MySQL error identity; unsupported providers throw `NotSupportedException` before execution |

Additional exact renderer cases:

- `["NULL"]` → `JSON_STORAGE_FREE(NULL)`.
- `["payload"]` → `JSON_STORAGE_FREE(payload)`.
- `["@p0"]` → `JSON_STORAGE_FREE(@p0)`.

These are exact **function-fragment** expectations, not invented whole-query aliases or parameter naming conventions.

For the literal result, this plan deliberately uses an independent raw-server oracle rather than asserting an unverified numeric constant. Record the literal, raw value, CLR runtime type, converted `Int64` value, and translated result.

Argument contract:

- Exactly one scalar `string?` argument.
- SQL NULL is distinct from the JSON text `"null"`.
- Non-null valid JSON literals, captured strings, and string-mapped JSON columns are supported.
- Zero/many-argument public calls and non-string public arguments are excluded by the signature.
- No client-side JSON parsing, stringification, validation, or NULL substitution.
- Invalid JSON behavior belongs to MySQL; no new client exception policy.
- MySQL’s integer result must map to nullable `Int64` without lossy conversion. A failed mapping is a defect, not permission to change the oracle.

## 3. Minimal solution and alternatives

**Goal in essence:** expose one correctly gated, correctly typed MySQL JSON-storage diagnostic.

**Constraints:** retain the capability-object architecture; no dependencies, public infrastructure redesign, translator-wide changes, forbidden paths, or sibling-scope repairs.

**Optimum:** one marker, one MySQL capability/renderer addition, explicit MariaDB exclusion, focused regression tests, and bilingual documentation.

| Approach | Benefit | Cost / risk | Decision |
|---|---|---|---|
| One-function `JSON_STORAGE_FREE` slice on the existing seam | Small, observable, useful; no new argument machinery | Requires verifying binary-JSON semantics and MariaDB exclusion | **Chosen** |
| Add `JSON_STORAGE_SIZE` alongside it | Related user-facing topic | Storage-size equivalents need a separate portability decision; enlarges the API and acceptance matrix | Rejected for this slice |
| Implement the complete issue catalogue | Broad coverage | Unverified inventory, mixed scalar/aggregate/table forms, version/plugin constraints, large API surface | Rejected |

Further rejected groups and concrete reasons appear in §15.

## 5. Public API and portability decision

Planned addition to `src/nextorm.core/Query/SqlFunctions.MySql.cs`:

```csharp
public long? json_storage_free(string? json)
```

The implementation follows the existing marker-body convention. XML `<summary>` documentation must explain:

- server-side execution only;
- MySQL binary-JSON storage semantics;
- SQL-NULL propagation;
- unsupported-provider rejection;
- that returned bytes are not a portable JSON-text length.

No new overload, generic parameter, optional argument, or `params` form.

**Portability decision:** keep this marker on `MySqlFunctions`, not `CommonFunctions`, because the intended operation is MySQL’s binary-JSON update-storage accounting, not generic JSON size or string length.

This semantic distinction is a **verification prerequisite**, not an established vendor-documentation fact. D1 must consider each provider’s own documentation. A semantically equivalent operation expressible by at least two providers invalidates this placement under the portability rule and requires PLAN revision; it must not be silently waived.

The exact lowercase marker spelling is the planned API. D1 must verify the existing name-resolution convention before implementation. A convention mismatch returns to PLAN rather than introducing an unplanned translator mapping.
