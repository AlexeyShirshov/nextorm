## 2. Goal and non-goals

Correctly materialise ClickHouse `Array(Nullable(Decimal(38,10)))` results into CLR `decimal?[]`, for inline and captured inputs, without changing unrelated materialisation.

**Non-goals**

A driver conversion can reject a representation whose scaled mantissa exceeds 96 bits even if removing trailing zeros could make its mathematical value representable. This unit deliberately preserves the pinned driver's conversion semantics; it does not add trailing-zero trimming or rounding.

## 4. Root cause and evidence

Verified failure chain:

- `SelectExpression.cs:270–275`: array accessor obtains the driver value through `GetValue`.
- `RowMapperFactory.cs:341–342`: single-column cast.
- `RowMaterializerBuilder.cs:229–230`: member binding.
- `QueryExecutor.cs:839`: scalar fallback; `ConvertScalar` at `:780`, callers at `:864` and `:890`.

With `ClickHouse.Driver 1.4.0`, default `UseCustomDecimals=true` makes the source array `ClickHouseDecimal?[]`, not `decimal?[]`. An array cast does not apply element conversion operators.

Driver evidence supplied to PLAN:

- `DecimalType.cs:41`: framework type is `ClickHouseDecimal`.
- `NullableType.cs:16`, `ArrayType.cs:26`, typed reader `:106`: nullable-array representation.
- Explicit decimal conversion/`ToDecimal` rejects an oversized mantissa with `OverflowException`.
- Tag `1.4.0` does not trim trailing zeros.

Existing live class:

`NextORM.Integration.Tests.ClickHouseNullableArrayParameterTests`

Its current parameter cases are not evidence that result materialisation works. D1 adds and proves the output regression.

## 5. Decision and alternatives

**Goal in essence:** convert the affected array's elements before the existing materialisation casts.

**Constraints:** retain default driver configuration, avoid public API changes and core-to-driver package coupling, preserve exact conversion/error semantics, and cover every affected materialisation route.

**Chosen minimum:** an internal, narrowly dispatched **row-materialisation element converter**. It converts only the affected ClickHouse nullable-decimal array result into a new `decimal?[]`, preserving nulls and invoking the driver's actual decimal operator for non-null elements.

The dispatch must identify the affected ClickHouse mapping/source type, not merely "any type with a decimal operator." Bind conversion to the actual runtime source element type without adding a ClickHouse package reference to core. Prefer a directly invoked compiled conversion delegate rather than reflection invocation, so overflow surfaces unchanged.

Use the same internal conversion operation at the affected result boundaries, including the scalar fallback where applicable. Do not add independent conversion implementations to each cast site.

| Approach | Advantages | Disadvantages / cost / risk | Decision |
|---|---|---|---|
| Narrow internal materialisation element converter | Operates where source and destination types are known; preserves reader/input behaviour; reusable across affected result forms. | Must connect all result routes and narrowly guard dispatch. Moderate implementation risk. | **Chosen.** |
| ClickHouse-specific result-conversion hook | Strong provider ownership. | An existing suitable hook has not been established; introducing a new public hook violates scope. Potentially larger architecture change. | Rejected for this unit. |
| Reader normalisation | Could make downstream casts work uniformly. | Changes reader-visible values and potentially unrelated decimal results; larger lifecycle/typing surface. | Rejected. |

Flipping `UseCustomDecimals=false` is rejected by premise: it changes scalar and other decimal materialisation client-wide.

**Bounded mechanism check:** D0 must establish that this internal dispatch and reuse are possible without a public signature change or core driver dependency. If not, do not improvise a public hook: return to PLAN with the concrete dependency/seam evidence.
