## Minimal solution and decisions

### Three answers

- **Essential goal:** introduce total nullable captured comparisons and mapped presence predicates at the three approved expression positions.
- **Non-negotiable constraints:** stable parameterised SQL and plan identity; existing refresh and provider mapping; SQL Server boolean legalisation; unchanged join structure and excluded contexts; no public API.
- **Optimum:** narrowly contextual internal translation, reusing existing parameter registration, comparison-operand rendering, correlation and dialect boolean mechanisms.

### Alternatives

| Approach | Pros | Cons / risk | Cost |
|---|---|---|---|
| **Context-gated internal shared translation** | Covers WHERE, SELECT and ON consistently; retains parameter infrastructure. | Must preserve nested predicate/scalar boundaries. | Moderate; chosen |
| General nullable-expression normalisation | Centralised rules. | Reaches column↔column and unapproved value contexts; violates scope. | High; rejected |
| Provider-specific or runtime-value specialisation | Can shorten SQL. | Duplicates logic; runtime specialisation violates SQL/cache invariants. | High; rejected |

### Architect decisions — binding

1. **Context boundary.** Introduce only the minimum internal context/state necessary to distinguish approved predicate use, approved boolean SELECT use, and other value use. `AsPredicate` alone is insufficient to identify all approved positions. Set context at actual renderer/visitor entry points and preserve/restore it across nested translation; do not enable rewriting globally for every `bool` expression.
2. **Captured operand classification.** Recognise actual closure/static captured nullable/string values from expression structure and existing parameter machinery, not their evaluated value. Do not classify every `MemberExpression` as captured. Preserve conversion/provider-type information through `VisitComparisonOperand`.
3. **Comparison shape.** Use the approved total equality and three-arm inequality emulation unless D0 proves an already-existing dialect mechanism with the same contract. Do not add #288 or a new native-operator feature. The inequality is:
   ```text
   (a IS NULL AND p IS NOT NULL)
   OR (a IS NOT NULL AND p IS NULL)
   OR (a IS NOT NULL AND p IS NOT NULL AND a <> p)
   ```
   Equality uses the approved two-arm form. Parentheses may follow existing builder conventions.
4. **Parameter reuse.** Register/render a captured operand using the existing machinery, then reuse its parameter fragment. Preserve one logical captured parameter, all physical occurrences, converters and refresh fallback. Never mutate `QueryCommand.Cache`.
5. **Presence translation.** Recognise `HasValue` only on a mapped nullable receiver in an approved context. Render its receiver as a DB expression; do not disturb `.Value`, captured `HasValue`, or unrelated member resolution.
6. **Boolean SELECT.** Assemble the predicate in predicate context, then use existing dialect scalar legalisation once at the expression’s scalar boundary. SQL Server uses its existing `MakeBooleanPredicate`/CASE machinery; do not wrap intermediate `AND`/`OR` children into incompatible scalar shapes.
7. **JOIN.** Change only ON expression translation. No changes to join APIs, join-kind selection, relational ordering, row preservation or cardinality machinery.
8. **Live gaps.** Add narrowly scoped real-connection MariaDB/ClickHouse integration tests using existing provider/container infrastructure. Do not invent a `CommonTestSuite` subclass or expand that hierarchy solely for this task.
9. **Cache evidence.** Use actual prepared-plan reference identity, not SQL equality or hashes as a substitute. Use existing non-public test access and cache-isolated collections.
10. **No API expansion.** If implementation requires public surface changes, stop that candidate and return to PLAN/escalation; do not implement them.
