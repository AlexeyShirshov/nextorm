## 2. Goal — essence

For `array_reverse`, `array_sort` and `uuidv7`, PostgreSQL preparation must either:

1. produce SQL supported by the explicitly configured server version, with the requested semantics; or
2. refuse deterministically before sending the unsupported expression to PostgreSQL.

Unknown version must not advertise these uncertain functions. Refusal must not become NULL, a no-op, an unchanged array, a different UUID version, or a raw driver `42883`.

This goal is limited to the three reported names. It is not a certification of every PostgreSQL function.

## 5. Decisions

### Minimal solution: three answers

- **Goal:** truthful capability plus deterministic refusal, without semantic substitution.
- **Constraints:** explicit configuration only; no live-version probing; preserve unaffected providers/functions; honor locks and current write authority.
- **Optimum:** add the smallest per-name array capability seam to the existing dialect surface; implement PostgreSQL decisions centrally; reuse the UUID refusal mechanism.

### Per-name choices

| Name | Choice | Alternatives rejected |
|---|---|---|
| `array_reverse` | **Refuse on PostgreSQL at every configured/unconfigured version.** | **SQL emulation:** plausible but not a small bug fix until shape, dimensionality, bounds, NULL and empty semantics are established. **Gate at PG18:** contradicts supplied evidence that no core PostgreSQL version provides this function. **Unchanged input/NULL:** silently wrong. |
| `array_sort` | **Refuse below PG18 and when version is unset; native SQL for explicit PG18+.** | **SQL emulation:** adds ordering/collation/NULL/shape semantics and a subquery execution path. **Optimistic default emission:** reproduces the reported PG17 failure. **Refuse even explicit PG18+:** unnecessarily removes a supported native function. |
| `uuidv7` | **Refuse below PG18 and when version is unset; native SQL for explicit PG18+.** | **`gen_random_uuid()`:** v4, not v7; changes time-ordering semantics. **Client-side UUID generation:** changes server-expression execution and evaluation cardinality. **Optimistic emission/NULL:** driver failure or silent semantic loss. |

### Array emulation assessment

The suggested reverse expression is a credible **candidate**, not a verified replacement:

`COALESCE((SELECT array_agg(x ORDER BY ord DESC) FROM unnest(a) WITH ORDINALITY AS t(x,ord)), a)`

Sorting would use the corresponding `ORDER BY x` expression.

Benefits: potentially supports PG17; aggregation preserves the element type in the suggested construction; the fallback is intended to preserve empty input rather than returning aggregate NULL.

Unresolved costs and risks:

- ordering of NULL elements and collation;
- NULL input versus empty input;
- dimensions, lower bounds and flattening;
- evaluating a nontrivial input expression more than once;
- SQL typing of null/empty literals and projected aliases;
- semantic differences between a future native sort and the proposed expression.

Those semantics are **not asserted as established**. Refusal avoids executing this unverified replacement. No emulation-semantic experiment is necessary for the selected fix. Reopening emulation requires a separately bounded PG17 probe covering those cases.

### Unset-version policy

Choose **targeted pessimistic refusal** for these three names.

This deliberately changes the existing `Instance` expectations for `array_sort` and `uuidv7`; `array_reverse` is removed regardless of version. The relevant SQL-generation and capability tests must change.

Do **not** silently inherit both conflicting precedents:

- T278/T280 supply the defect-class principle: correct capability/refuse.
- PostgreSQL currently documents unset as permissive.
- This plan introduces a documented exception for these names, not a global reinterpretation of `_version == null`.

Existing aggregate-filter gates and all unrelated unset-version behavior remain unchanged. No `DbConnection.ServerVersion`/`server_version_num` auto-detection is added.

### Capability seam

**Planned API, not an existing symbol:** add `SupportsArrayFunction(string name)` to the existing `ISqlDialect` surface, with matching virtual implementation on `SqlDialectBase`.

- Default decision for the two newly guarded translation cases preserves their existing `SupportsArrays` gate.
- PostgreSQL overrides: reverse false; sort true only for explicit version ≥18.
- Core calls the seam for reverse/sort before argument translation.
- Do not opportunistically route every existing array function through it.
- Keep `SupportsArrays` and `SupportsArrayFunctions` family meanings unchanged.

This is an additive member on existing types, not a new capability interface/type. The two independently different function cases are its concrete consumers. D1 must verify default-interface/virtual-member conventions before implementation.

For UUIDs, keep the existing `IUuidGenerators` abstraction. PostgreSQL obtains a capability object reflecting its immutable configured version; `Supports` and `Render` must agree. Preserve `gen_random_uuid` behavior.
