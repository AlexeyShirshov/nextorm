### 2. Root cause
- Core emits ORDER BY (`SqlBuilder.cs:369-404`) → LIMIT BY (`:406-430`) → SETTINGS (`:432-442`) → paging (`:444-448`) → FOR UPDATE (`:453-461`).
- `src/nextorm.core/DataContext/SqlBuilder.cs:439-440` appends SETTINGS before `:446-447` appends `MakePage(...)`; same StringBuilder, no reordering pass.
- ClickHouse paging text `limit n [offset m]`: `src/nextorm.clickhouse/ClickHouseDialect.cs:827-838`; offset-only `limit 18446744073709551615 offset m`.
- `First`/`FirstOrDefault` ⇒ `Paging.Limit = 1` (`EntityBuilderExtensions.cs:351-359`, `:368-376`; `QueryCommand.TResult.cs:507-517`, `:547-556`); `Single`/`SingleOrDefault` ⇒ 2 (`EntityBuilderExtensions.cs:385-403`, `QueryCommand.TResult.cs:584-593`, `:619-627`); correlated scalar `.First()` (`CorrelatedQueryExpressionVisitor.cs:1545-1554`).
- Only ClickHouse enables `SupportsSettings` (`ClickHouseDialect.cs:502-503`; base default false `SqlDialectBase.cs:318-323`): a shared-core ordering defect exposed only by ClickHouse.

### 3. Minimal solution and rejected alternatives
- **Decision 1:** move the existing SETTINGS append block immediately after paging, before the existing FOR UPDATE block → ORDER BY → LIMIT BY → LIMIT/OFFSET → SETTINGS → FOR UPDATE.
- **Decision 2:** `ClickHouseDialect.cs` is NOT edited.
- Rejected: ClickHouse-only SQL post-processing (parses/rewrites finished SQL; nesting/UNION hazards); wrapping the aggregate in a subquery (changes query shape, misses ordinary paging/other terminals); new `MakeSettingsAfterPaging` hook (new abstraction with one consumer, duplicate ordering policy — overlay invariant 1).
- SETTINGS must follow both LIMIT BY and ordinary paging; placement stays scoped to the SELECT being built (never relocated globally across UNION); FORMAT is an output-level suffix.
- Constraints preserved: SQL text inside clauses, capability guards, terminal semantics, command/cache state (no shared-`QueryCommand` mutation), FOR UPDATE behaviour.
