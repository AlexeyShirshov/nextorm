## Original task

Unit **T363** (issue **#350**) of the `rc4` pdca collection — a **library defect** found by the examples.

### The defect, measured (do not re-derive)
A CTE whose projection targets a **named DTO** loses its column aliases **when the projection's source is itself a CTE**:

```sql
-- BROKEN: source is a CTE
source as (select id, nullableint as "num" from complex_entity),
named  as (select "id", "num" from source as "t1")        -- no 'as "Id"' / 'as "Num"'
       select "Id" from named as "t1"                      -- 42703 on PostgreSQL
-- CORRECT: same shape, source is a table
inner  as (select id as "Id", nullableint as "Int" ...)     select "Id" from inner as "t1"
```

The consumer then references the **DTO member name** (`"Id"`) while the CTE declared the **source column names** (`"id"`), so:
- **PostgreSQL** fails with `42703 column t1.AirplaneCode does not exist` (case-sensitive);
- **ClickHouse** fails with `UNKNOWN_IDENTIFIER`;
- **SQL Server** passes only because its default collation is case-insensitive — i.e. the defect is silently masked there.

Found while converting `examples/` to named aliases (#231): `postgres AircraftDelayChains`, `clickhouse Retention`. `[Column("…")]` attributes on the DTO change **neither** the declaration **nor** the consumer (measured: `.pdca/T361/rv1/t361-probe2.txt` on branch `collection/rc4/task-47-231`), so the fix is in the SQL builder, not in user code.

### Root cause

`src/nextorm.core/Visitors/MemberTranslator.cs` — the three fallback branches that render a **derived**
(CTE / sub-query) column reference (`:518-540` entity-typed via `FindQueryCommand`, `:791-820`
parameter-typed, and `AppendDerivedColumn:1036-1048`) emit the identifier `innerCol.PropertyName` — the
source's **declared output name** (`"id"`) — but never told the visitor which identifier they had just
rendered. `SqlSourceRenderer.MakeColumn:1522-1546` decides the rename alias by comparing
`visitor.ColumnName` against `selExp.PropertyName`; with the bookkeeping missing that comparison never
fired, so the declaration body stayed `select "id", "num"` and the outer chain's `select "Id"` missed it.

The **table** path works because `AppendColumn`/`VisitMember` (`:506`, `:788`) *do* set
`visitor.ColumnName`. So the defect is an asymmetry between the two source kinds, not a missing feature.

### Fix

1. `BaseExpressionVisitor` — a new **internal** `DerivedColumnName` signal, deliberately **separate** from
   `ColumnName`: a first attempt that reused `ColumnName` broke
   `TypedCte_JoinOfTwoCtesOfSameClrType_ShouldBindBySourceSlot` (recorded red in `rv1/unit-core.log`),
   because `ColumnName` also drives final-select-list aliasing. `DerivedColumnName` is declaration-only.
2. `MemberTranslator` (3 sites) — set `DerivedColumnName = innerCol.PropertyName` exactly where the
   derived identifier is rendered.
3. `SqlSourceRenderer.MakeColumn` — a new alias arm gated on
   `ExactProjectionAliases && renameAware && DerivedColumnName != null && PropertyName != null &&
   !OrdinalEquals(DerivedColumnName, PropertyName)`, i.e. it fires **only** for a typed-CTE declaration
   whose projection renames the column; the same-name guard therefore emits no redundant alias.

### Risk handed to CHECK explicitly

`DerivedColumnName` is a mutable signal on the visitor. The fix relies on `MakeColumn` being consulted
for **that** column immediately after the reference is rendered (the same assumption `ColumnName` already
makes). CHECK should try to falsify the stickiness: a projection whose first member is a derived
(renamed) column and a later member is a **physical** column, in a context where
`ExactProjectionAliases` is on, must not gain a spurious alias from the earlier signal.

## CHECK record

### CHECK #1 — `not accepted` → DO (finding `F-01`)

The checker accepted the root cause, the single-source fix, red-first validity and every hygiene
counter, and raised one **medium/blocking** finding: `DerivedColumnName` is mutable state that is never
cleared, so — by inspection of the diff — a typed-CTE declaration that renders a *renamed derived*
column first and a *physical* column second would see the stale signal and emit a **spurious alias** on
the physical column.

### Loop-back n=2 — the finding is `refuted`, and the refutation is pinned as behaviour

`F-01` assumed the visitor survives across select-list entries. It does not:
`SqlSourceRenderer.MakeColumn:1497` obtains its visitor from `SqlBuildContext.CreateColumnVisitor:131-132`,
which **always constructs a new `BaseExpressionVisitor`** — so `DerivedColumnName`'s entire lifetime is
one column, and the read happens in the same call that renders it. `ColumnName` never needed clearing
for the same reason.

Rather than add a redundant reset (which would encode a false premise in the code), the loop-back:

1. added `Mixed_body_should_alias_the_renamed_derived_column_only` — the exact configuration `F-01`
   describes: a CTE-derived renamed column **first**, then a **physical** column whose identifier already
   equals the member name, in a typed-CTE declaration body. Measured output:
   `mixed as (select t1."num" as "Renamed", t2.id from …)` — the rename is aliased, the physical column
   stays **bare**, no alias is carried over. **7/7** in the class.
2. documented the invariant on the signal itself ("scope is one select-list entry … if visitors are ever
   pooled, this member must be reset with `ColumnName`"), so a future pooling change cannot break it
   silently — the sentence names the test that would turn red.
3. re-ran the gates: `nextorm.slnx` **0 warnings / 0 errors**; `nextorm.core.tests` **3966 / 0 failed**;
   `nextorm.postgres.tests` **1727 / 0 failed** (1726 + the new mixed-body test).
