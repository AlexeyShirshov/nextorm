## Root cause + violated invariant

`NavigationExpansion.GetOrCreate:395-462` creates/reuses a joined parameter; `GetOrCreateReferencePrefix:376-393` returns it without registering an outer reference. `RewriteLambda:356-364` creates separate visitors while sharing command-local expansion state.
The missing link is **boundary normalization of that joined parameter**: it belongs to the outer command's `NavigationPaths`, but is not necessarily in the inner command's `_outerParams`, is not automatically registered in shared `OuterReferences`, and is not copied into the inner command's `NavigationPaths`. Consequently an outer navigation parameter can remain free inside the nested query expression. `GetQueryCommand:1458-1512` compilation/registration and the fresh inner `SqlBuilder` at `NormSqlTranslator.cs:295-296` cannot infer its ownership.
**Violated invariant:** every cross-command parameter reference must retain identity and use the established outer-reference registration/alias path — not merely an identically named SQL alias. `IsNavigationRoot:640-661` alone does not supply that registration.

## Decision and rejected alternatives

**Decision.** Normalize the missing boundary reference at `CorrelatedQueryExpressionVisitor.GetQueryCommand:1458-1459`: extend the preparation-local normalization input to include free joined parameters whose exact identities are owned by the enclosing command's `NavigationPaths`. Do not mutate `_outerParams`, copy arbitrary navigation dictionaries, or infer ownership by parameter name.
Reuse `ReplaceConstantsExpressionVisitor.VisitMember` (`ExpressionExtensions.cs:214-215`), `GetOuterRefMarkerCI:226-229`, `QueryCommand.AddOuterReference:1191-1207`. The joined parameter is registered through the existing outer registry and represented by `OuterRefMarker<T>`; existing marker detection (`:1368-1386`) and `GetQueryCommand:1476-1512` establish `cmd.OuterRegistry`. Translation then uses `OuterReferences[index]` at `MemberTranslator.cs:463-490,961-990`; `AliasResolver.GetOuterAliasFromParam:22-29` searches outer scopes. No `ParentCommand`/`OuterCommand` is introduced.
For nullable key joins, reuse `CorrelatedQueryExpressionVisitor.VisitAlignedReferenceComparison:1266-1280` and `AlignNavigationKeys:864`; lift non-nullable operands before equality construction at `NavigationExpansion.cs:432-437`, preserving existing presence compensation.
**D1 bounded design acceptance:** normalization handles both member access and bare joined-reference presence, preserves root-registry indexes through nesting, and leaves ordinary correlated `p.Id` unchanged. A failed candidate returns to PLAN; it does not authorize a new registry.

| Rejected approach | Benefit | Rejection: cost/risk |
|---|---|---|
| APPLY/LATERAL rewrite | Explicit lateral scope | Nonportable; violates SQLite/ClickHouse constraint; changes SQL architecture unnecessarily. |
| Stop expansion at nested lambdas | Small traversal change | Leaves supported navigation expressions unresolved; evades rather than repairs correlation. |
| New ancestry/reference registry | Explicit ownership model | Duplicates `OuterRegistry`/`RootRegistry`; high cache/clone/translator impact. |

Design-checklist **PASS for planning**: identity, null semantics, alias scope, cache ownership, provider portability, API compatibility, dependency ownership and evidence obligations covered.
