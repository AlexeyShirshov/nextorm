````markdown
```text
## Intent

Typed entity entry points on a provider-neutral application context, ergonomic nextorm-specific repository API, not a provider-independent business repository abstraction. Example proposed API: `class AppDbContext(IDataContext context): DbContext(context) { public IRepository<Order> Orders => Repository<Order>(); }`. `Orders` supports `From`/`Join` as direct mapped table source, `Where`/`OrderBy`/`Limit` yielding existing `EntityBuilder<T>`, `ToList`/`Count` (+ async twins), and fresh `MakeInsert`/`MakeUpdate`/`MakeDelete` builders. No tracking or `SaveChanges`.

## Agreed design

- Abstract `DbContext` is a non-executing facade over a borrowed `IDataContext`, does NOT implement `IDataContext`; expose `DataContext` for low-level APIs. Always bind query/DML builders to the exact inner provider context to preserve filtering/bindings/cache/transactions and concrete provider capabilities. Scoped DI: provider registered separately, `AppDbContext` receives it; facade doesn't dispose borrowed provider.
- `IRepository<T>` small contract: `IDataContext DataContext {get;}` and `EntityBuilder<T> Query();` extensions provide convenience, no `IQueryable`/`IEnumerable` or separate query engine. `Repository<T>(optional Action<EntityMetadataBuilder<T>>)` caches source wrapper per facade/CLR entity type, not query or mutation state; mapping follows existing process-wide first-registration semantics.
- `From(repository)` and `Join(repository, predicate)` mean mapped table, not `From(EntityBuilder)` derived subquery. Reject source repo from another underlying context instance. `From(filtered builder)` retains existing subquery behavior.
- Extend `EntityBuilder<T>` with `Delete`/`DeleteAsync` bulk terminals for single mapped entity/table roots plus explicit `Where`, filter scope, optional ordering and `Limit`. Preserve all user predicates and filter settings. One server SQL statement, no entity materialization/client IDs/per-row commands. Extend explicit `DeleteBuilder` with `OrderBy`/`OrderByDescending`/`Limit` using same implementation.
- Positive `Limit N` guarantees at most N selected rows under a declared unique non-null key mapping consistent with actual schema; composite keys supported. Sort optional, unsorted selection arbitrary; sort ties need user key tiebreaker; concurrency uses normal DB isolation without stronger guarantees. Server-side selected-key query, dialect-specific rendering. Ordinary unbounded predicate delete doesn't require key.
- Explicit `Where` needed for short query `Delete`; global filters/`Limit` alone don't satisfy safety gate; whole-table intent uses `MakeDelete().All().Delete()`. Explicit `Limit(0)` must be rejected before SQL, never reinterpreted as unlimited (existing SELECT `Limit(0)` is unlimited); preserve explicit limit provenance across clones/DML conversion without changing existing SELECT semantics. Existing query methods are copy-on-write, not an immutable type.
- Reject positive `Offset`, `WithTies`, projections, grouping, set operations, raw/named unbound sources, CTE/derived query sources and unsupported query options before execution rather than silently dropping semantics. Existing joined delete stays a separate path, no new joined-limited deletion.
- Bounded DELETE planned to be supported on PostgreSQL, SQL Server, MySQL/MariaDB, SQLite (planned support, not existing verified support); SQLite mustn't depend on optional `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`. ClickHouse bounded DELETE explicitly `NotSupportedException` in initial version; plain mutation semantics unchanged, no new affected-count guarantees. InMemory unchanged/no mutation support.

## Acceptance criteria

Independent query chains and fresh DML builders; `From`/`Join` without artificial subquery; mapping and global filters including `IgnoreFilters` preserved; exact inner context identity, transaction/cache isolation and cross-context rejection; real DB evidence for ordered/unordered bounded deletion, composite keys, `<=N` with more matching rows than cap; no SQL/side effects for invalid zero cap, absent key, unsupported source/options/provider; sync/async parity/cancellation; EN/RU public guides/examples and SQL-generation tests plus provider-backed integration tests (skipped container suites are not green). Preserve CRLF in any eventual files.

## Delivery boundaries

One design, two implementation work packages: (A) facade/repository/source adapters; (B) query DELETE bridge and bounded mutation SQL/validation. No new `Delete<T>()`/`Insert<T>()` starters, tracking, `SaveChanges`, automatic properties/reflection/generator, `IQueryable` DSL, Update-from-query, bounded joined deletion, context-local mapping, client-side paging deletion or ClickHouse limited mutation.
````

1. **[Категория: `requirements-handoff` / `criteria-coverage`]** **Явное включение инвариантов безопасности и исполнения из `Agreed design` в `Acceptance criteria` при оформлении issue**
