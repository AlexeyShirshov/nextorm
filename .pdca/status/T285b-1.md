## Minimal solution

**Essence:** small provider-local entry points, truthful capability gates, native translation where verified, otherwise early named refusal.

**Constraints:** preserve provider SQL shape, existing aggregate/window semantics, shared G1 changes, and `total`; do not turn a native window function into a scalar aggregate.

**Optimum:** reuse existing member, capability and translator conventions. Implement only verified native forms and narrow documented native composition for median.

| Approach | Pros | Cons / cost / risk |
|---|---|---|
| **Provider-specific native forms and fail-closed refusals** | Matches owner decision; no hidden semantic conversion | Moderate translator/test work; depends on existing ordered-set/window infrastructure |
| Provider-specific emulation | Potentially broader availability | Larger SQL/semantic/performance surface; explicitly rejected for this task |
| Provider-specific names backed by a portable internal rewrite | Superficially uniform | Risks hiding cardinality/type differences; rejected |

**Choice:** first approach. PostgreSQL/SQL Server median may use native `percentile_cont(0.5)` in the provider's own shape. This is explicit native composition, **not** SQLite emulation.
