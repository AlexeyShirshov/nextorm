## 5. Закрытие пробелов постановки и вопросов дизайна (Gap closure)

1. **Общее представление вектора vs провайдерные адаптеры.** В `nextorm.postgres` уже есть `PgVector`/`PgHalfVector`/`PgSparseVector`/`PgBit`; `nextorm.core` не ссылается на провайдеры и распознаёт их по полному имени (`TypeFacts`); SQL Server 2025 хранит `VECTOR(n)` как float32/float16, обменивается JSON-массивом, драйвер 6.1.7 умеет `SqlVector<float>`. Решение: общий векторный тип/контракт в `NextORM.Core` (совместимый с `PgVector` через перегрузки/неявное преобразование) **и** поддержка существующих провайдерных типов без ломающих изменений.
2. **Область управления индексами и предпосылки ANN.** Полноценный кросс-провайдерный миграционный движок индексов не требуется; предпосылки ANN (`PREVIEW_FEATURES = ON`, `CREATE VECTOR INDEX ... TYPE = 'DiskANN'`; `USING hnsw/ivfflat` в PostgreSQL) проверяются в интеграционных тестах и документируются.
3. **Семантика метрик и результатов.** SQL Server: `'cosine'`, `'euclidean'`, `'dot'` (отрицательное скалярное произведение), результат — строка таблицы + `distance`, по возрастанию. Решение: единое перечисление метрик (`Cosine`, `Euclidean`/`L2`, `DotProduct`/`NegativeInnerProduct`) с инвариантом «меньше `Distance` = ближе»; единый тип результата (`VectorSearchResult<TEntity>` со сущностью и `Distance`); SQL Server approximate → `VECTOR_SEARCH` + `TOP (k) WITH APPROXIMATE` + `ORDER BY distance`; SQL Server exact → `VECTOR_DISTANCE(...) AS distance ... ORDER BY distance`; PostgreSQL → `ORDER BY <col> <op> @p LIMIT k` (переиспользование транслятора pgvector, индекс HNSW/IVFFlat выбирает СУБД); плюс единая скалярная функция расстояния (`SqlFunctions.VectorDistance(metric, col, query)`), транслируемая в `VECTOR_DISTANCE(...)` на SQL Server 2025+ и в операторы `<->`/`<=>`/`<#>` на PostgreSQL.
