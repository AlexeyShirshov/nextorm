## Goal

Сделать составную связь обычной provider-neutral моделью отношений: публично объявляемые упорядоченные компоненты, единая структурная валидация и использование **всех** компонентов существующими SQL-маршрутами `JoinInto` и implicit navigation.

Сохранить:

- шесть прежних бинарных сигнатур и семантику старых вызовов;
- утверждённый API A–J без перепроектирования;
- demand-time resolution, отсутствие обещания eager validation в `From<T>()`;
- ручной `IRelationshipMetadata` и `DataContextCache.Metadata`;
- существующее in-memory поведение без новой поддержки/нормализации;
- границу #249: **никаких новых `LoadWith` entrypoints или eager-mode plumbing**.

Минимальный результат — один parser, одна структурная модель и один согласованный механизм разрешения/проверки компонентов; не новый relationship framework.

## Normative API

Источник истины: утверждённая спецификация `docs/superpowers/specs/2026-10-17-composite-relationship-keys-design.md:286-345`. Это internal evidence, не публичная ссылка.

Все A–J возвращают `EntityMetadataBuilder<T>`.

| ID | Точная сигнатура |
|---|---|
| A | `HasMany<TChild>(Expression<Func<T,ICollection<TChild>>> navigation, Expression<Func<TChild,object?>> foreignKey, Expression<Func<T,object?>> principalKey) where TChild : class` |
| B | `HasMany<TChild>(Expression<Func<TChild,object?>> foreignKey, Expression<Func<T,object?>> principalKey) where TChild : class` |
| C | `HasOne<TChild>(Expression<Func<T,TChild?>> navigation, Expression<Func<T,object?>> foreignKey, Expression<Func<TChild,object?>> principalKey) where TChild : class` |
| D | `HasOne<TChild>(Expression<Func<T,object?>> foreignKey, Expression<Func<TChild,object?>> principalKey) where TChild : class` |
| E | `HasOneToOne<TChild>(Expression<Func<T,TChild?>> navigation, Expression<Func<T,object?>> parentKey, Expression<Func<TChild,object?>> childForeignKey) where TChild : class` |
| F | `HasManyThrough<TChild,TJunction>(Expression<Func<T,IEnumerable<TChild>>> navigation, Expression<Func<T,object?>> parentKey, Expression<Func<TJunction,object?>> junctionParentForeignKey, Expression<Func<TChild,object?>> childKey, Expression<Func<TJunction,object?>> junctionChildForeignKey) where TChild : class where TJunction : class` |
| G | `HasMany<TChild>(Expression<Func<TChild,object?>> foreignKey) where TChild : class` |
| H | `HasOne<TChild>(Expression<Func<T,object?>> foreignKey) where TChild : class` |
| I | `HasOneToOne<TChild,TKey>(Expression<Func<T,TChild?>> navigation, Expression<Func<TChild,TKey>> childForeignKey) where TChild : class` |
| J | `HasManyThrough<TChild,TJunction>(Expression<Func<T,IEnumerable<TChild>>> navigation, Expression<Func<TJunction,object?>> junctionParentForeignKey, Expression<Func<TJunction,object?>> junctionChildForeignKey) where TChild : class where TJunction : class` |

A–F задают explicit principal; G–J используют full default PK. I выводит anonymous `TKey`; B/D/G/H требуют explicit `<TChild>`, F/J — explicit `<TChild,TJunction>`. J выводит оба PK; customisation — F, не reordered overload.

**Запреты:** не расширять/заменять шесть старых сигнатур; не добавлять `IsKey` overloads или отдельное семейство `TFk/TPk`. При реальном противоречии компиляции/семантики нормативному target остановить соответствующую часть и запросить **утверждённую пользователем поправку спецификации**, а не менять API самостоятельно.

## Decisions

### Минимальное решение: три ответа

1. **Суть:** ordered component lists от declaration до SQL/cache identity.
2. **Неприкосновенные ограничения:** API A–J, legacy compatibility, SQL null semantics, manual escape hatch, demand validation, граница #249, unchanged in-memory.
3. **Оптимум:** additive overloads + shared parser + централизованная structural resolution; существующие composite equality/identity механизмы повторно использовать после проверки их применимости.

| Выбор | Плюсы | Минусы / стоимость / риск |
|---|---|---|
| **Additive A–J, legacy forwarding, shared internal parser — выбран** | Нормативный API; одна семантика selector; сохраняет binary signatures | Средняя стоимость; overload binding требует воспроизводимого oracle |
| Widen/replace шесть прежних сигнатур | Меньше внешне похожих методов | Нарушает binary compatibility и утверждённый target; отклонено |
| Новая generic FK/PK family | Теоретически сильнее type inference | Известный `CS0121`; отклонено спецификацией |

| Structural implementation | Плюсы | Минусы / стоимость / риск |
|---|---|---|
| **Один internal parser + один structural validator/resolution contract — выбран** | Producer/manual parity, общие ошибки, YAGNI | Нужно аккуратно разделить syntax и demand-time validation |
| Parser/guards в каждом overload/visitor | Меньше начального wiring | Дублирование, несовпадающие ошибки и cache gaps; отклонено |
| Новый публичный key/relationship abstraction | Расширяемость | Лишняя API/миграция, out of scope; отклонено |

Не вводить row-value tuples, публичный PK-order API или capability/provenance flags.

## Assumptions and dependencies

### Consumer requirement для #249 — дословно

> deterministically **ordered** key component lists on `IRelationshipMetadata` (FK order = selector order; principal order = selector order or metadata PK order), validation of malformed/partial metadata occurring before SQL and before cache insert (so #249 can rely on "invalid never reaches execution"), a typed error for arity/type/duplicate/unmapped components, and full-mapping + occurrence-scope cache identity for composite navigations.

Typed errors: null expression — `ArgumentNullException`; structural/syntax invalid declaration — `NotSupportedException` с entity/navigation и offending component/count.

### Что постановка не сказала

| Пробел | Разрешение / риск |

| Metadata PK order не имеет публичного aggregate API | Использовать существующий детерминированный property metadata order; не вводить новый public API; проверить reproducibility |

Обязательно валидировать manual mapping до SQL/успешного plan-cache insertion; не вводить обход для manual metadata. - P251-00 завершён; оснований для escalation сейчас нет.
- Неизвестный API binding/live harness — **in-cycle prerequisites**, а не разрешение обходить acceptance.

### Binding-regression oracle — обязательный reconnaissance

До добавления overloads:

1. Через Roslyn зафиксировать точные прежние шесть signatures и resolved bindings representative calls.
2. Воспроизводимые in-repo compilation fixtures включают scalar, inferred navigation, explicit generic arguments, typed expression variables и object selectors.
3. После добавления A–J oracle проверяет compile diagnostics и фактически выбранные symbols.
4. Для object selectors допустимый rebinding проверяется **по итоговой ordered metadata/ошибкам**, не объявляется неизменным binding.
5. Сохранение binary signature проверяется metadata/reflection и pre-change compiled consumer в текущем цикле; последний — дополнительное evidence, не единственный воспроизводимый oracle.
6. Если нужен Roslyn package в test project, сначала проверить existing references; новую версию добавлять только через CPM.

Критерий reconnaissance: все normative positive snippets компилируются без ambiguity, old semantic outputs сохранены, rejected generic-family ambiguity не возвращена. Несоответствие normative API — возврат за spec amendment, не новый overload design.
