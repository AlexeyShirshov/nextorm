## 2. Goal and boundaries

Add two navigation-first, metadata-driven `JoinInto` overloads: reference navigation and collection navigation. Both infer the child type, obtain its source through the existing source-less delegation, and use declared relationship keys rather than a caller-supplied key restatement. An optional predicate is an **additional filter**, never a replacement for declared relationship equality. Both new forms use left-join semantics.

### Scope decisions

- **T330 ships independently.** Reuse its source-less delegation; do not reimplement its five counterparts.
- **Compatibility boundary:** the five existing source-explicit overloads and T330's five source-less counterparts retain signatures and behavior. The stronger predicate-as-filter semantics belong to the new navigation-first API. Documentation must distinguish these API families; this task does not claim to repair legacy explicit-ON calls.
- Add exactly two navigation-first overloads, each accepting an optional filter. Do **not** expose `JoinType` on these new overloads in this unit. Explicit join types remain available through existing APIs.
- T251 owns relationship declaration and composite metadata contracts. Consume them without a second resolver or fallback interpretation.
- T249 owns `LoadWith`, including its child-factory shape. No `LoadWith` or child-factory implementation here.
- T309's scope was not supplied. D0 must retrieve its collection scope and confirm the boundary; no work may be attributed to T309 by guesswork.

### Non-goals

No legacy predicate reinterpretation, predicate-equivalence analyzer, new relationship declarations, provider capability expansion, custom child-source/factory overload, materializer redesign, public method rename, examples changes, dependency upgrades or threshold changes.

## 5. Minimal solution and alternatives

**Essence:** navigation selects declared metadata; metadata establishes identity and ON; the optional predicate only narrows matches.

**Constraints:** preserve legacy APIs, metadata orientation and ordering, configured-source precedence, junction behavior, left-parent preservation and provider guards.

**Choice:** resolve through the existing relationship path; for direct relationships construct ordered equality conjunctions and append any optional filter using consistent expression parameters. Route source acquisition through T330's existing delegation. For junction relationships, retain existing junction synthesis and add only the filter in its established child-edge position.

| Alternative | Benefit | Cost / risk | Decision |
|---|---|---|---|
| Metadata ON + optional filter | Removes key restatement; coherent with junction semantics | Must preserve parameter binding and left-join filter placement | **Chosen** |
| Keep verbatim predicate; document hazard | Smallest implementation | Does not satisfy metadata-driven semantics | Reject |
| Validate and always throw unless predicate restates keys | Fail-closed | Requires brittle expression-equivalence analysis; rejects useful filters | Reject |
| Require explicit always-true predicate | Reuses existing surface | Fails requested bare navigation ergonomics | Reject |
| Separate `JoinIntoByRelationship` name | Avoids overload competition | Unnecessary API divergence from `LoadWith` | Reject unless actual compiler evidence invalidates the required overload shape; then replan |

No filter means "no additional restriction." It does not expose a caller obligation to supply an always-true expression.
